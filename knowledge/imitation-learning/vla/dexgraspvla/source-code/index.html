三、训练调用链、forward语义与warm start

flowchart TB
  T[train.py / Hydra] --> W[TrainDexGraspVLAControllerWorkspace]
  W --> P[instantiate policy]
  P --> E[instantiate ObsEncoder]
  P --> D[construct TransformerForActionDiffusion]
  P --> S[instantiate DDIMScheduler]
  W --> DS[dataset / dataloader / normalizer]
  W --> L[self.model batch training=true]
  L --> C[forward to compute_loss]
  C --> E
  C --> D
  C --> S

文本回退： train.py 由 hydra.main 解析顶层 _target_，实例化 TrainDexGraspVLAControllerWorkspace；workspace 创建 policy、dataset、optimizer 与 scheduler。每批进入 self.model(batch, training=True)，再由 forward 转到 compute_loss，并调用观测编码器、手工构造的 DiT 与 DDIM scheduler。

DexGraspVLAController.forward 不是推理入口：它归一化动作、编码观测、做批内噪声匹配和加噪，再让 TransformerForActionDiffusion 预测 epsilon 或 scheduler 目标。真实推理入口是 predict_action。DiT 没有单独 Hydra _target_；policy 从 shape_meta、obs_encoder.output_shape()、层数与头数配置组装模型。

start_ckpt_path 默认也不是严格断点续训。training.resume=false 时 optimizer 被排除存档；加载后 global_step 与 epoch 归零，normalizer 又按当前数据重拟合。因此默认语义是模型权重 warm start。严格续训还必须恢复 optimizer、scheduler、计数器和 normalizer，并核对数据身份。

normalizer 是模型权重之外的数值 ABI。即使参数逐字节相同，只要当前数据重拟合得到不同尺度，同一物理动作就会对应不同归一化坐标；只恢复 optimizer 而遗漏 normalizer 也不构成严格续训。部署 bundle 因而必须把 checkpoint、normalizer、processor、shape metadata 与固定配置作为同一身份验证单元。

四、构造副作用、线程拓扑与共享状态

RoboticsSystem.__init__ 加载配置后立即初始化机器人，随后设置初始姿态、加载 controller/planner、建立缓存并启动线程；构造对象本身就会触碰硬件，不是等 run() 才连接。把解析、校验、连接和使能拆为显式阶段是建议，不是当前实现。

manual五线程、planner六线程及名义节拍
线程 源码节拍 边界
臂控制 sleep 0.01，名义上限约100 Hz 不是实时保证
手控制 sleep 0.05，名义上限约20 Hz 不是硬件确认频率
相机 无显式 sleep 依赖阻塞采集
键盘 执行中 select 0.1 s 只写结束布尔量
超时 sleep 1 s 只结束当前抓取
VLM核验 阻塞请求后 sleep 0.1 仅 planner 模式，非10 Hz

臂、手、相机、键盘和超时线程总是启动；planner 额外启动 VLM 抓取核验，所以 manual 为 5、planner 为 6。图像、目标关节、计数器和 in_post_run 无锁共享，没有队列、时间戳或原子快照。由此可能出现 image/mask 错位、目标消费前被覆盖，以及多个线程写结束标志但首个触发原因丢失。

sleep 只给出循环在理想空载下的等待下界：实际周期还包含 Python 调度、采集、网络请求、CAN-FD 调用和锁外工作。100 Hz、20 Hz 与 0.1 s 均不能作为实测服务等级。若要建立运行合同，需要单调时钟、每轮开始结束时间、队列深度、deadline miss、frame age 和 acknowledgment 的分位统计，当前全部为 NOT_RUN。

五、观测路径、13维状态与两层动作映射

get_state() 把七维机械臂关节按物理限位映射到 [-1,1]，再拼接六维手状态成为 13 维。RGB 除以 255 后用 bilinear resize；mask 用 nearest resize，再以 0.5 二值化；低维状态转 float32。当前 n_obs_steps=1，但仍使用历史缓存结构。

策略输出到硬件调用的两层映射
阶段 变换 公开边界
normalizer反变换 `predict_action` 将归一化样本还原到数据集动作空间 依赖训练数据拟合的 action normalizer
机械臂前7维 `q_i=l_i+(x_i+1)(u_i-l_i)/2` `scale` 假设 x_i∈[-1,1]
灵巧手后6维 直接交给 `right_hand.execute_action` 单位和驱动解释未公开

公开仓库没有示教采集代码，Zarr 动作单位也未直接定义，所以不能由部署公式反推公开数据已按关节限位归一化。接入新数据必须逐维实测范围和单位。scale 前没有 clip，超出 [-1,1] 会映射过配置限位；未公开硬件驱动是否再次限幅。部署前必须补 finite、range 和 joint-limit 检查。

这里存在两个不同坐标空间：normalizer 的反变换输出“训练数据动作空间”，scale 又把臂分支当作归一化关节比例映射到物理限位；手分支却绕过该公式。只有采集端定义、统计制品和驱动接口共同证明单位一致时，两层映射才闭合。任何一层身份不明都应阻断下发，而不是用数值看似落在范围内作为替代证据。

六、64预测、6次写目标与观测刷新

策略一次输出 (64,13) 动作块，execute_action 硬编码 for k in range(6)。循环只刷新 observation、覆盖 target_right_arm_joint、置 update_target 并覆盖手目标；没有 sleep、动作队列、序号或低层完成确认。因此源码能保证的是主线程依次写六个目标，不能保证低层完整执行六个彼此可分辨的控制步，后 58 项也不进入该循环。

六次 get_obs 同样没有固定采样间隔。相机线程可能尚未产生新帧，缓存可能重复同一帧或写入极近邻帧；推理代码没有统一 20 Hz 节拍器。论文的 20 Hz/K=6 是实验时序，不能倒推公开循环稳定为 20 Hz 或 0.3 秒内完整消费六项。

“写入六次”和“执行六步”属于不同事件。前者由主线程赋值次数计数，后者至少要求低层线程读取不同序号、驱动接受、机器人开始响应并报告完成。若 mailbox 只保存最新值，较早目标可以在任何物理响应前被覆盖。观测刷新也需要 frame ID 才能区分新帧、重复帧与缓存副本。

首个可观察分歧。 要裁决写入与消费，必须记录 action 序号、写入时间、低层读取时间、驱动 acknowledgment 和对应 frame ID；只看最终成功率无法判断中间目标覆盖。

七、两点CubicSpline、终点遗漏与数学边界

cubic_spline_interpolation_7d 每关节只给 SciPy CubicSpline 当前点与目标点两个结点。默认边界条件下两点样条退化为直线，实际为 q_i(t)=(1-t)q_i(0)+tq_i(1)；函数名含 cubic 不能证明速度连续、加速度受限或存在 S 曲线动态。

采样使用 t=arange(0,1,Δt)，右端点 1 不包含。当 Δt=1/20 时，最后参数为 0.95。随后的误差循环追踪数组末点，而不是原始目标，因此当前完成检查只到 95% 插值点。

等间隔位置应使用包含终点的 linspace，并等待每个目标被确认消费。
平滑动态应显式给出速度、加速度、jerk 与边界条件。
在线重规划应从当前实测位置和速度开始，避免覆盖目标造成不连续。

这三项都是工程建议，不是当前实现；页面不会把建议写成源码已经具备的保证。

两点退化结论只描述位置插值函数的数学输出，不评价真实控制器闭环。即使补上终点，也不能自动获得速度或加速度连续；即使驱动最终到达目标，也不能证明中间轨迹按数组逐点消费。位置序列、发送节拍、驱动缓存和底层控制律必须分别验证，不能由函数名或末端误差单独代替。

八、planner状态机、四个VLM任务与bbox验证

flowchart TB
  R[run] --> M{manual}
  M -->|yes| RM[manual bbox / one target]
  M -->|no| S[start command]
  S --> I[init episode and prompt]
  I --> C0{check complete}
  C0 -->|no| P[instruction then bbox]
  P --> G[SAM / Cutie]
  G --> E[reset flags / execute grasping]

文本回退： manual 由人工框选单目标；planner 从 start、episode 初始化、用户 prompt 和开局 check_complete 开始，随后循环 instruction→bbox→SAM/Cutie→reset→execute→reset→check_complete，完成后 close_episode 并回到 start。

VLM任务、解析方式与缺口
任务 解析 缺口
指令提出 直接返回文本 无结构化动作 schema
bbox预测 尝试修 JSON 后读取 `bbox_2d` 缺字段类型、坐标顺序、图像边界、最小面积和可见性校验
抓取结果 先查 true，再查 false 响应同时含两词时优先 True
任务完成 同样做子串布尔解析 不是结构化唯一布尔

结构化 schema、唯一布尔校验和送 SAM 前裁剪是建议而非现状。解析失败必须有可恢复分支，不能默认为继续或成功。

VLM 的文本响应还应保存原文、解析版本和失败原因，避免只留下布尔结果后无法复核。bbox 必须绑定产生它的 frame ID；若相机帧已经更新，即使坐标数值合法，也可能指向错误目标。解析、几何校验、目标可见性与 frame 一致性是四个独立门，任何一个失败都不应进入分割与动作生成。

九、三个False、高度0、超时与终止压缩

每次 reset_flags() 会清零 consecutive_failed_attempts。同一次抓取执行中，VLM 连续三次返回 False 才置 in_post_run；它不是三次独立抓取，也不是 Experiments 的 Ours@3。height_threshold 初始化为 0 且未从配置标定，因此不能解释成离桌 10 cm 的成功阈值。

episode_start 也在每次 reset_flags() 更新。max_episode_duration 超时仅置 in_post_run 结束当前抓取；主线程 reset、check_complete 后仍可能开始下一次。内层 planner 没有全局 deadline 或最大抓取次数，键盘输入也只终止当前抓取。

成功、三个 False、超时和人工中止都被压缩进同一布尔量，无法恢复首个结束原因。更稳妥的协议应使用 SUCCESS / VERIFY_FAILED / TIMEOUT / USER_ABORT / HARDWARE_ERROR 等枚举，并同时记录时间、线程和证据。

全部 fail-closed：硬件类或配置缺失时不构造；量纲、finite、range 或限位未知时不下发；无 frame ID 时不把图像、mask 与状态当作同一快照；parser 模糊或 bbox 无效时不进入 SAM；没有全局 deadline 时不宣称任务具备有限终止保证。

最小加固顺序是：①补 finite、关节、速度、加速度、力矩与工作空间安全层；②把目标改为有序队列或带序号 mailbox 并确认消费；③修正含终点且有动态约束的轨迹；④结束原因枚举；⑤任务级 deadline 与最大抓取次数；⑥同步 frame/mask/state；⑦严格 VLM schema；⑧用录制数据做回放测试，全部通过后才讨论连接真机。

推荐读码九步：①训练配置和 task shape；②dataset 与 normalizer；③ObsEncoder；④TransformerForActionDiffusion；⑤policy 的 compute_loss/predict_action；⑥workspace；⑦planner 的四类 prompt/parser；⑧inference.py 主链与六线程；⑨inference_utils/utils.py 插值。顺序先建立数值空间，再追控制流，最后审计运行边界。

failure taxonomy 用于定位最早可观察分歧，不表示这些故障已在论文实验中发生。建议的回放证据至少包含固定输入、配置/制品哈希、frame 与 action 序号、解析原文、线程时间线和预期阻断点；静态检查通过只说明页面与补丁自洽，不能把任一 failure 标记为真机已验证恢复。
