DexGraspVLA 的控制器使用统一的噪声预测损失训练，但“一个损失”背后仍有大量影响复现的工程语义：如何把 75 步 episode 变成 64 步动作块、尾部如何填充、8 卡下批量和学习率步数如何解释、哪些参数实际更新、验证与 checkpoint 又依据什么。

本页按“数据采集 → 窗口采样 → 归一化 → 分布式批量与调度 → 优化循环 → 评估与存档”的顺序展开。网络结构和扩散公式分别见相邻的 architecture 与 diffusion 子页。

48 × 8本地批量 × 进程数

一、演示数据如何产生

1.1 两阶段采集，不是在线遥操作日志

论文附录给出的流程分为两段：

  1. 将机器人置于 kinesthetic teaching 模式，由操作者直接拖动机械臂和手完成抓取，记录目标关节轨迹。
  2. 复位场景，以记录的关节角为目标执行 PD 控制；在 20 Hz 下同步记录相机图像、当前关节角和目标关节角，之后离线生成目标掩码。

因此数据中的

\[\mathbf s_t\in\mathbb R^{13}\]

是执行时的实际臂手关节角，而

\[\mathbf a_t\in\mathbb R^{13}\]

是 PD 控制目标关节角。二者维度相同、语义不同。

“复现阶段采图可以减少操作者出现在画面中的分布偏移”是由流程推得的合理工程收益，但论文没有把它写成采用两阶段采集的明确原因，不能当作作者已验证的因果结论。

1.2 论文数据规模

项目 一般灵巧抓取 非抓取式扩展
成功演示 2,094 条 1,029 条
训练物体 36 种家用物体 32 种平坦宽面物体
episode 长度 固定 75 步 变长
控制频率 20 Hz 20 Hz
动作块长度 64 100
训练轮数 论文写 84 论文写 200

75 步在 20 Hz 下对应 3.75 秒，与正文“约 3.5 秒”属于同一量级。论文还说明物体和周边杂物会在 episode 之间重新布置，并对成功演示进行质量检查。

二、Zarr、图像预处理与序列窗口

2.1 存储结构

官方样例以 Zarr 保存：

data/
  action          # (K, 13)，PD 目标关节角
  right_state     # (K, 13)，实际关节角
  rgbm            # (K, H, W, 4)，头部 BGR + 掩码
  right_cam_img   # (K, H, W, 3)，腕部 BGR
meta/
  episode_ends    # (J,)，各 episode 的结束位置

公开下载的是 51 条演示的微型样例，用于理解格式并跑通训练；论文使用的 2,094 条完整训练集并未随仓库公开。

2.2 图像和掩码的预处理

rgb = interpolate(rgb / 255.0, size=(518, 518),
                  mode='bilinear', align_corners=False)

mask = interpolate(mask, size=(518, 518), mode='nearest')
mask = (mask > 0.5).float()

RGB 先缩放至 \([0,1]\) 并双线性重采样；掩码用最近邻插值并重新二值化。随后观测编码器还会执行 BGR→RGB、训练期颜色扰动和 DINOv2 所需的 ImageNet 均值/方差标准化。

2.3 为什么一条 75 步轨迹会产生 75 个窗口

一般抓取配置为：

sequence_length = 64
pad_before = 0
pad_after = 63

SequenceSampler 对长度 \(L=75\) 的 episode 使用

\[\text{max\_start}=L-\text{sequence\_length}+\text{pad\_after} =75-64+63=74.\]

起点因此是 \(0,1,\ldots,74\)，恰好 75 个。若没有尾部填充，合法起点只有 \(75-64+1=12\) 个；填充把窗口数增至 6.25 倍，但这些窗口高度重叠，不能理解成新增了 6.25 倍独立演示。

2.4 尾部填充怎样进入损失

当窗口越过 episode 末尾时，采样器用该序列的最后一个元素重复填满。起点 12 需要补 1 步，起点 74 需要补 63 步。

若每个起点每轮各采样一次，一条 episode 的所有窗口共有

\[75\times64=4{,}800\]

个动作位置，其中填充位置为

\[1+2+\cdots+63=2{,}016, \qquad \frac{2{,}016}{4{,}800}=42\%.\]

控制器明确拒绝 valid_mask，默认 MSE 会让这些重复的末动作与真实时间位置等权参与训练。这会强化“到达末态后保持最后目标关节角”的模式；它可能适合抓取保持，也可能改变动作分布，属于复现和迁移到变长任务时必须注意的目标设计，而不是可忽略的存储细节。

三、归一化到底应用在哪里

数据集同时计算动作和状态统计量：

normalizer.fit({
    'action': all_actions,
    'right_state': all_right_states
}, mode='limits')

但控制器训练只调用：

obs = batch['obs']
action = normalizer['action'].normalize(batch['action'])

所以准确结论是：

  • 动作按训练集每个维度的最小值和最大值映射到 \([-1,1]\)；
  • right_state 的统计量会被计算和保存，但当前前向没有使用它；
  • 状态以原始关节角进入线性层，随后经过 LayerNorm；
  • 图像没有使用这个 LinearNormalizer，但仍经过上一节所述的图像预处理。

normalizer 对 replay buffer 中的原始动作拟合，不把窗口尾部人为重复的动作再计入最值统计。训练时仅主进程计算一次并写入文件，其余进程等待后读取相同参数。

四、8 卡批量与学习率步数

4.1 full dataset 下的批量计数

完整一般抓取数据包含

\[N=2{,}094\times75=157{,}050\]

个训练窗口。配置 batch_size: 48，且在 accelerator.prepare 之前：

\[\operatorname{len}(\text{DataLoader}) =\left\lceil\frac{157{,}050}{48}\right\rceil =3{,}272.\]

Accelerate 1.2.1 默认 split_batches=False。8 个进程准备 DataLoader 后，每个进程每轮迭代

\[\frac{3{,}272}{8}=409\]

个本地 batch，每个 batch 仍含 48 个样本；一次 DDP 优化更新的全局批量为

\[48\times8=384.\]

默认 even_batches=True 会在不能整除时复制少量开头样本，使各进程步数一致。完整数据每轮只需补足最后全局批量中的极少数位置，但复现精确样本计数时仍应知道这一行为。

4.2 调度器的“3,272 步”如何与“409 次更新”对齐

源码在分片前创建余弦调度器：

num_training_steps =
    len(train_dataloader) * num_epochs

train_dataloader, model, optimizer, lr_scheduler =
    accelerator.prepare(...)

125 轮时，底层调度器收到

\[S_{\text{total}}=3{,}272\times125=409{,}000.\]

这并不是步数错误。Accelerate 1.2.1 的 AcceleratedScheduler 在 split_batches=False 时，每发生一次真实优化更新，就把底层调度器连续推进 num_processes=8 次。因此：

\[409\ \text{次更新/轮}\times8 =3{,}272\ \text{个内部调度步/轮}.\]

两边在每轮末尾正好对齐。原本看似相差8倍的计数，实际由 Accelerate 包装器显式补偿。

4.3 warmup 的真实长度

lr_warmup_steps=2000 指底层调度器步数。8 卡下相当于：

\[\frac{2{,}000}{8}=250\]

次真实优化更新，约为完整数据的

\[\frac{250}{409}=0.611\]

个 epoch；在 125 轮总调度中占

\[\frac{2{,}000}{409{,}000}\approx0.489\%.\]

这个比例依赖数据规模。若用官方 51 条样例且每条仍为 75 步，则每轮只有 \(\lceil(51\times75)/48\rceil=80\) 个底层调度步，125 轮共 10,000 步；同样的 2,000 步 warmup 将占 20%，约持续 25 个 epoch。样例数据可以跑通代码，但不能直接沿用“完整数据上的训练动力学”来解释。

4.4 余弦公式

diffusers 0.32.1 的调度因子为

\[f(s)= \begin{cases} \dfrac{s}{S_{\mathrm{warm}}}, & s<S_{\mathrm{warm}},\\[6pt] \max\!\left( 0,\frac{1+\cos\!\left( \pi\frac{s-S_{\mathrm{warm}}} {S_{\mathrm{total}}-S_{\mathrm{warm}}} \right)}{2} \right), & s\ge S_{\mathrm{warm}}. \end{cases}\]

源码在每次优化器更新后调用调度器；Accelerate 再按上述规则推进内部步数。

五、优化器、梯度与混合精度

5.1 AdamW 参数分组

公开代码先保留 requires_grad=True 的参数，再按张量维度分组：

decay_params   = [p for p in params if p.dim() >= 2]
nodecay_params = [p for p in params if p.dim() < 2]

AdamW([
  {'params': decay_params,   'weight_decay': 1e-4},
  {'params': nodecay_params, 'weight_decay': 0.0}
], lr=1e-4, betas=(0.95, 0.999), fused=fused_available)

这是一种常见启发式：

  • 线性层、卷积、嵌入表和位置编码等二维及以上参数参与衰减；
  • 偏置和 Norm 的一维 scale 不衰减；
  • 冻结 DINOv2 因 requires_grad=False 不进入优化器，也不分配 Adam 状态。

cond_pos_emb 是三维张量，所以会被施加 weight decay。代码只检查当前 PyTorch 的 AdamW 签名是否包含 fused；满足时传入 fused=True。论文也说明使用 FusedAdamW 加速训练。

5.2 梯度裁剪

accelerator.backward(loss)
clip_grad_norm_(model.parameters(), max_norm=0.5)

阈值 0.5 没有出现在论文 Table 2，但属于公开实现的有效训练设置。论文和源码没有给出选择 0.5 的消融或原因，因此不能把“高噪声样本必然造成梯度尖峰”等解释写成已验证结论。

裁剪位于梯度累积判断之外。官方 gradient_accumulate_every=1 时没有歧义；若改成大于1，代码会在每个 micro-batch 后裁剪部分累积梯度，而且第一次更新会在 global_step=0 时提前发生。非默认累积配置不能被视为已经正确支持。

5.3 BF16

Accelerator(
    log_with='wandb',
    mixed_precision='bf16',
    device_placement=True
)

BF16 写死在训练代码中，并非由训练 YAML 控制。论文将其作用描述为降低显存占用、提升计算效率；仓库 README 也要求多卡配置启用 BF16。若硬件不支持 BF16，需要修改代码并重新验证数值与吞吐，不能只改 YAML。

六、训练循环中真正发生了什么

每个本地 batch 的顺序是：

raw_loss = model(batch, training=True)
loss = raw_loss / gradient_accumulate_every
accelerator.backward(loss)
clip_grad_norm_(model.parameters(), 0.5)

optimizer.step()
optimizer.zero_grad()
lr_scheduler.step()

# use_ema=True 时才执行
ema.step(unwrap_model(model))

默认累积步数为1，因此每个 batch 都更新一次。训练循环在最后一个 batch 内暂不递增 global_step，但会在 epoch 末统一记录日志并递增一次；所以默认配置下每轮总增量仍是409，原实现不存在“每轮少计一步”的问题。

6.1 EMA 配置存在，但默认关闭

YAML 定义了完整 EMA 参数，却设置 use_ema: False。因此默认运行不会复制 EMA 模型、不会更新 EMA，也不会在评估时切换到 EMA 权重。

配置中的注释声称 BatchNorm 会使 EMA 性能下降，但当前控制器主要使用 LayerNorm 和 RMSNorm，没有 BatchNorm。这条注释更像继承自上游训练框架的历史说明，不能作为 DexGraspVLA 已完成 EMA 消融的证据。

6.2 rollout 分支是公开占位实现

训练配置每10轮调用一次 env_runner.run(policy)，但仓库中的 RealGraspImageRunner.run 只返回空字典：

def run(self, policy):
    return dict()

所以公开训练代码中的 rollout 是无副作用占位，不会连接真实机器人，也不会产生成功率。硬件部署代码未完整开源是另一件事，不能据此说训练会在该分支因缺少硬件而失败。

七、验证、训练集采样与注意力导出

7.1 默认没有验证集

grasp.yaml 设置 val_ratio: 0，验证 sampler 长度为0；训练循环还要求 len(val_dataloader) > 0，所以验证损失分支不会运行。

这是可确认的实现事实，但官方没有解释为什么采用零验证比例。不能把它进一步写成“作者证明验证扩散损失与真机成功率无关”或“这不是疏漏”。实际后果是：默认训练没有独立的离线泛化指标。

7.2 每10轮在最后一个训练 batch 上采样

sample_every: 10 的分支由主进程运行，使用该 epoch 最后看到的训练 batch：

  1. 从随机噪声执行16步 DDIM，生成动作块；
  2. 与该训练 batch 的真实动作计算 train_action_mse_error；
  3. 开启 gen_attn_map 时保存注意力和观测。

它衡量训练样本上的随机生成误差，不是验证集指标，也不是机器人任务成功率。

7.3 注意力文件能保存什么

当前公开控制器只保留 batch 前两个样本、第一个动作 token 对全部条件 token 的注意力，覆盖各 DiT 层和16个去噪档位；可视化脚本再逐档位、逐层、逐头输出图片。

论文附录中的 Figure 4 则描述为对全部扩散步、层、头和动作 token 求和后归一化。公开导出代码已经在动作 token 维只留下索引0，因此不能仅靠这条默认导出链路严格复现论文所述的“全部动作 token 聚合”，需要修改注意力保存逻辑。

八、checkpoint：top‑1 之外还有定期权重

默认 checkpoint 配置为：

topk:
  monitor_key: train_loss
  mode: min
  k: 1
save_last_ckpt: False
save_last_snapshot: False

top‑k 管理器会在每轮比较 epoch 平均训练损失，只在 checkpoints/ 中保留当前最小的一份。这里还有两个容易遗漏的事实：

  1. 训练损失没有跨进程 gather；主进程保存时使用的是主进程本地 shard 的 batch 平均，不是八卡全部样本的全局平均。
  2. 训练循环另外在 epoch 索引 40、60、80、100、120 保存 epoch_checkpoints/epoch=*.ckpt，不受 top‑1 删除逻辑影响。

因此“整个训练只留下一个权重”是错误的：

  • 若按论文84轮运行（epoch 索引0–83），可得到 top‑1 以及 40、60、80 三个定期 checkpoint；
  • 若按配置125轮运行（epoch 索引0–124），可得到 top‑1 以及 40、60、80、100、120 五个定期 checkpoint；
  • 因 save_last_ckpt=False，最后一轮不会以“latest”名义额外保存。

九、84 轮与 125 轮的官方分歧

论文正文和 Table 2 都写：

  • 84 epochs；
  • 8 张 A800；
  • BF16 与 FusedAdamW；
  • 训练不到一天。

公开 YAML 则写 num_epochs: 125。两者来自不同官方载体，公开材料没有解释差异，也没有说明发布 checkpoint 使用哪一项。

这不仅是训练时长不同，调度映射也不同：

设置 底层总调度步 每进程真实更新数 调度终点
84 轮 274,848 34,356 第84轮末接近0
125 轮 409,000 51,125 第125轮末接近0

若配置按125轮建立调度，却在完成84轮后停止，则底层内部步为 \(274{,}848\)，warmup 后进度为

\[p=\frac{274{,}848-2{,}000}{409{,}000-2{,}000} \approx0.6704,\]

学习率因子为

\[f=\frac{1+\cos(\pi p)}{2}\approx0.245.\]

也就是说，同样“训练完84轮”，84轮配置已走到余弦末端，而125轮配置仍约为峰值学习率的24.5%。复现时应明确选择并报告：

  • 对齐论文训练描述：使用84轮并让调度总步数同步按84轮计算；
  • 对齐公开 YAML 默认行为：使用125轮；
  • 不要加载125轮调度后简单在84轮处截断，并声称等价于论文设置。

十一、从 checkpoint 开始并不等于严格续训

README 建议通过 policy.start_ckpt_path 加载已有权重。但默认 training.resume=False 时，保存文件会排除 optimizer；初始化又在加载 checkpoint 后把 global_step 和 epoch 重置为0，随后按当前数据重新设置 normalizer 并新建优化器与调度器。

因此默认语义更接近：

加载模型参数进行 warm start 或微调。

它不是恢复原优化器动量、学习率位置和轮数计数的严格断点续训。需要精确恢复训练状态时，必须额外验证 checkpoint 是否包含优化器、加载时对象是否已建立，以及计数器是否被后续代码重置。

十二、复现检查清单

  1. 先确定目标数据规模。 51条样例只能验证流程，不能复现论文训练动力学和成绩。
  2. 保留动作 normalizer。 checkpoint、训练数据与部署时反归一化必须使用同一套统计量。
  3. 确认尾部填充是否符合新任务。 变长任务或非保持型动作可能需要有效位掩码，而当前损失没有。
  4. 按实际 GPU 数重新核对调度。 Accelerate 默认会按进程数多次推进底层 scheduler；不要再手工乘一次。
  5. 不要把 rollout 当真机评估。 公开 runner 只是返回空字典。
  6. checkpoint 选择不能只看 top‑1。 同时比较定期权重，并在真实任务或独立验证集上选择。
  7. 明确84还是125轮。 两者都来自官方材料，但不是同一条学习率曲线。
  8. 把 start checkpoint 称为 warm start。 除非已验证优化器、调度器和计数器全部恢复。
