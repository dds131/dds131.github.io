一、本页在专题中的位置

前五个子页回答“模型是什么、怎样训练”。本页只回答部署问题：一次动作块怎样生成，HTTP 接口实际接受什么，各客户端怎样执行动作，以及把模型接到新机械臂前必须补齐哪些控制与安全环节。

二、动作块推理：代码究竟在递推什么

generate_actions 先编码当前观测，再在固定观测条件下反复预测一整段动作。设动作块长度为 \(H\)、动作维度为 \(D\)、推理步数为 \(K\)、观测条件为 \(c=(o,p,d)\)，其中 \(o\) 是视觉与语言，\(p\) 是 proprio，\(d\) 是 domain id。令 \(P_m\) 表示 action_mode=m 的预处理，\(Q_m\) 表示对应后处理。代码对应的完整递推可写成：

\[\epsilon\in\mathbb R^{H\times D},\quad \epsilon\sim\mathcal N(0,I),\qquad a^{(0)}=0,\] \[t_j=\frac{K-j+1}{K},\qquad x^{(j)}=t_j\epsilon+(1-t_j)a^{(j-1)},\] \[\bigl(\tilde p^{(j)},\tilde x^{(j)}\bigr) =P_m\!\left(p,x^{(j)}\right),\qquad a^{(j)}=f_\theta\!\left(\tilde x^{(j)},t_j,o,\tilde p^{(j)},d\right), \qquad j=1,\ldots,K,\] \[a_{\mathrm{out}}=Q_m\!\left(a^{(K)}\right).\]

因此网络每轮生成的是模型动作空间中的“干净动作块”估计，服务最终返回的是经过模式相关后处理的 \(a_{\mathrm{out}}\)，并非对所有模式都原样返回 \(a^{(K)}\)。该过程不是速度场的数值积分；固定噪声 \(\epsilon\) 在整个循环中复用。

# models/modeling_xvla.py，核心逻辑
enc = self.forward_vlm(input_ids, image_input, image_mask)  # 每个动作块只算一次
x1 = torch.randn(B, self.num_actions, D, device=proprio.device,
                 dtype=proprio.dtype)
action = torch.zeros_like(x1)

steps = max(1, int(steps))
for i in range(steps, 0, -1):
    t = torch.full((B,), i / steps, device=proprio.device,
                   dtype=proprio.dtype)
    x_t = x1 * t[:, None, None] + action * (1 - t)[:, None, None]
    proprio_m, x_t_m = self.action_space.preprocess(proprio, x_t)
    action = self.transformer(domain_id=domain_id,
                              action_with_noise=x_t_m,
                              proprio=proprio_m, t=t, **enc)
return self.action_space.postprocess(action)

2.1 四个容易误解的边界

  • 确定性有条件。在输入、初始噪声、模型权重和确定性算子都相同的前提下，eval() 后的递推应一致；实际 GPU 算子仍可能带来细小的非确定性。通常两次请求差异最大的来源是重新采样的 x1，但不能把它称为唯一可能来源。
  • 零初始化不是一个有效的首轮估计。第一轮 $$t_1=1$$，因此 $$x^{(1)}=\epsilon$$，$$a^{(0)}=0$$ 被系数 0 完全消去；当 $$K=1$$ 时，输出就是网络对纯噪声、$$t=1$$ 与条件 $$c$$ 的一次预测，没有发生“多轮自细化”。
  • 改变 steps 会改变整条递推。新的步数不仅改变 $$t_j$$ 网格，还会改变每一轮预测以及之后的所有混合输入。因此它不是在一条预先固定的轨迹上多取或少取几个点。接口允许任意正整数，但动作质量、延迟和稳定性仍需重新验证。
  • 训练与推理的端点都不完全相同。训练采样近似覆盖 $$0\le t<1$$，推理第一步却使用精确的 $$t=1$$，最后一步停在 $$t=1/K$$ 而不是 0。训练可以逼近两个端点，但页面不应把它描述成完全相同的时间覆盖。

2.2 计算量应怎样理解

阶段 每个请求执行次数 主要计算
视觉语言编码 1 三路图像编码；主视角与文本进入 Florence encoder
动作主干 steps 24 层 Transformer 对整段动作反复自细化
动作空间预处理 steps 行为取决于 action_mode
动作空间后处理 1 sigmoid、裁剪或原样返回，同样取决于 action_mode

把不随递推变化的视觉语言特征移到循环外，是明确的结构性节省；但官方资料没有给端到端延迟或消融实验，不能据此断言它是“低延迟的直接原因”，也不能在没有 FLOPs 与实测数据时断言它比 KV cache 更重要。真实延迟还受精度、图像预处理、网络、动作主干步数与 GPU 并发影响。

2.3 action_mode 决定返回值

模式 模型动作维度 递推前预处理 后处理与返回
ee6d 20 proprio 与动作清零第 9、19 维 两个夹爪 logit 过 sigmoid；通常返回 H × 20
joint 14 proprio 与动作清零第 6、13 维 两个夹爪 logit 过 sigmoid；返回 H × 14
agibot_ee6d 20 原样输入 不做 sigmoid，原样返回 H × 20
auto 模型侧默认上限 20 只把动作补到模型维度；proprio 不补 裁回 real_dim；没有自动夹爪 sigmoid

因此“返回 30×20、夹爪在 [0,1]”只是在 num_actions=30 且使用 ee6d 时成立。通用形状是：

\[\text{return shape}=H\times D_{\text{postprocess}}.\]

auto 不是完整的机器人适配器。X-VLA 官方实现把动作补到 max_action_dim，却原样保留 proprio；所以 proprio 的最后一维仍须等于动作主干期待的宽度。它还要求 real_action_dim ≤ max_action_dim，但源码没有提前校验，超限会在创建负长度 padding 时失败。auto 不会推断各维物理语义、单位、坐标系或夹爪极性。

三、HTTP 服务：最小接口与生产边界

X-VLA 官方部署把 GPU 推理与控制程序分开：deploy.py 加载模型并启动 FastAPI，客户端用 POST /act 请求动作块。它适合研究评测，但不是可直接暴露到生产网络或直接驱动真实机械臂的完整控制服务。

flowchart LR
  A["相机、语言、真实状态"] --> B["客户端适配与序列化"]
  B --> C["POST /act"]
  C --> D["VLM 编码一次"]
  D --> E["动作主干递推 K 次"]
  E --> F["按 action_mode 后处理"]
  F --> G["动作块"]
  G --> H["坐标转换与重采样"]
  H --> I["限位、碰撞与看门狗"]
  I --> J["低层控制器"]
  J --> K["机械臂"]
  K --> A

3.1 deploy.py 的关键参数

参数 默认值 说明
--model_path 必填 模型目录或 Hugging Face 仓库
--processor_path 同 model_path 处理器可单独指定
--LoRA_path None 可选 PEFT adapter
--output_dir ./logs 保存 info.json
--device cuda auto 才会按 CUDA 可用性选择
--port 8010 deploy.py 的端口
--host ip-address-removed 默认监听全部网卡
--disable_slurm False 禁用从 SLURM_NODELIST 推断 host

启动与运行还需注意：

  • 部署脚本以 float32 加载并再次转为 float32，没有 bf16/fp16 命令行开关。
  • deploy.py 默认端口是 8010；直接调用 model.run(processor) 时默认端口是 8000。
  • processor 加载失败只会打印警告，脚本仍会启动服务；此后请求会因 processor=None 进入通用 400。生产脚本应把 processor 加载失败视为启动失败。
  • --LoRA_path 只是运行时装载 PEFT adapter，并不会自动合并权重；基座模型、adapter 与 processor 必须来自相容的训练配置和版本。
  • info.json 在 uvicorn 启动前写入，退出时没有自动删除，因此它只是占用标记，不是健康检查。文件已存在会使脚本在模型加载后退出；应先确认旧进程和端口状态，再清理陈旧文件或更换 output_dir。
  • 检测到 SLURM_NODELIST 时，源码通过字符串切分推断 host，不能可靠展开常见的节点列表表达式。非特定集群环境应使用 --disable_slurm --host HOST，并以实际监听结果为准。

3.2 /act 的真实输入契约

字段 接口是否硬性要求 正确含义
image0 代码没有单独强制，但部署时通常必须提供 收集后处于槽位 0 的图像会与文本共同进入 Florence encoder
image1、image2 可缺省 辅助视角；缺键会使后续视角向前压紧
language_instruction 是 文本指令
proprio 是 未带 batch 维的一维向量；末维必须匹配 checkpoint 的 dim_proprio
domain_id 是 必须满足 0 ≤ id < num_domains，且语义与训练域一致
steps 否 缺省 10；先经 int(...)，再用 max(1, steps)

接口把图像与 proprio 的字段值再次交给 json_numpy.loads；按仓库客户端的契约，应先分别用 json_numpy.dumps 得到字符串，再把这些字符串放进外层 JSON 请求。直接把数组作为外层 JSON 数组并不符合当前实现。固定 ee6d 基础配置的 dim_proprio=20；其他 checkpoint 必须读取自身配置，不能照抄示例维度。

每个图像字段解码后的结果实际支持三类输入：

  1. 已解码、可被 Image.fromarray 接受的 HWC 数组，或可转成该数组的嵌套列表；
  2. 一维 JPEG/PNG 等压缩内容的 uint8 字节数组，由 cv2.imdecode 解码；
  3. 字符串路径，由服务端执行 Image.open(path)；请求字段本身必须是可被 json_numpy.loads 解析出的 JSON 字符串，而不是未经 JSON 编码的裸路径。

普通的一维原始像素不是有效压缩图像，不能按第二类发送。proprio 若已经带 batch 维，服务再次 unsqueeze(0) 后也会形成错误形状。源码没有预先验证这些维度、dtype、大小、压缩格式、数值有限性或 domain_id 范围；内部异常又统一折叠成通用 400，客户端无法区分输入错误与服务端故障。第三类允许请求方指定服务端本地文件路径，生产部署应删除或严格限制该分支。

3.3 相机槽位与颜色通道

服务端依次检查 image0、image1、image2，缺失键会被跳过；处理器再把紧凑列表从末尾补零。因此只传 image0 和 image2 时，原来的 image2 会进入槽位 1。

正确原则不是“一律把两路相机放到0和1”，而是保持 checkpoint 训练时的相机语义与槽位映射。如果必须保留空的中间槽位，应修改协议以接收显式 mask，或发送双方约定的占位图；当前接口不能表达“槽位1缺失但槽位2有效”。

另外，cv2.imdecode(..., IMREAD_COLOR) 返回 BGR 数组，源码随后直接调用 Image.fromarray(v)，没有 BGR→RGB 转换。因此直接传 RGB HWC 数组与传压缩字节可能形成红蓝通道不一致。建议服务端显式转换并检查解码失败：

v = np.asarray(v)
if v.ndim != 1 or v.dtype != np.uint8:
    raise ValueError("encoded image must be a 1-D uint8 buffer")
decoded = cv2.imdecode(v, cv2.IMREAD_COLOR)
if decoded is None:
    raise ValueError("invalid encoded image")
v = cv2.cvtColor(decoded, cv2.COLOR_BGR2RGB)

3.4 研究服务不等于安全控制服务

当前服务只有 /act，没有独立的 readiness/liveness 端点；请求使用普通字典，没有完整的 schema、尺寸、dtype、数值范围和 payload 大小校验，内部异常统一返回 400。服务默认明文 HTTP、无认证，并监听 ip-address-removed；同步端点也没有显式的 GPU 推理锁、队列或并发策略。

接真实机械臂时至少要补齐：

  • 只绑定受控接口，或使用反向代理、认证、TLS 与网络隔离；
  • 禁止服务端路径读取，限制请求大小并验证图像、proprio、domain 与 steps；
  • 为客户端设置连接/读取超时、重试上限和请求序号；
  • 使用单请求队列或显式并发控制，避免多个控制程序争用模型；
  • 实施工作空间、关节、速度、加速度、力矩和碰撞约束；
  • 配置心跳、看门狗、陈旧动作块取消、通信中断安全姿态和独立急停。

模型动作必须先经过安全监督器，不能从 HTTP 返回值直接下发硬件。

四、客户端：动作块怎样变成控制指令

固定提交的 evaluation/ 中共有 17 个评测客户端入口：16 个显式发送 steps=10，RoboTwin 没发送该字段，因而依赖服务端缺省值 10。下面四个代表性客户端展示同一模型接口在执行窗口、状态反馈和夹爪适配上的差异。

基准 domain_id 推理步数 每次请求采用的动作 下一次请求的 proprio 夹爪规则
LIBERO 3 10 30 步 预测 chunk 最后一帧的前 9 维 分数 >0.5 取 +1
CALVIN 2 10 前 20 步 当前下发帧的前 10 维 分数 <0.8 取 +1
Simpler-WidowX 0 10 30 步 当前下发帧的前 10 维 逐任务阈值
RoboTwin-2.0 6 服务端缺省 10 30 步，最多重复请求 10 次 把命令动作写回局部 endpose 分数 >0.7 取 -1

4.1 开环窗口与重新规划频率

这 17 个脚本在当前版本中都没有 temporal ensemble；典型逻辑是队列为空才请求新 chunk，然后逐帧弹出。CALVIN 只装入前 20 步，其他代表性脚本通常装入 30 步；SoftFold 还允许通过参数改变执行长度。因此“当前脚本采用固定窗口开环执行”是代码事实，但不是 X-VLA 模型强制的算法性质。

同步客户端完成一次重新规划的周期近似为：

\[T_{\text{replan}}\approx T_{\text{capture}}+T_{\text{serialize}}+T_{\text{network}} +T_{\text{model}}(K)+T_{\text{decode}} +\frac{H_{\text{exec}}}{f_{\text{ctrl}}}.\]

因此不能简单写成“推理频率等于环境步频除以20–30”。若环境变化快，应缩短 \(H_{\text{exec}}\)，按真实状态重新规划；如果推理与执行异步重叠，还必须丢弃已经过时的动作。

训练处理器在非轨迹末端用 num_actions+1 个点覆盖 qdur，再把第0点作为 proprio、后 \(H\) 点作为动作。若 qdur=4 s 且 \(H=30\)，训练锚点间隔约为 \(4/30\approx0.133 s\)。客户端控制周期若不同，应重采样或重新构造训练目标，不能把“30步”自动解释成“执行4秒”；轨迹末端的覆盖时间还会缩短。

4.2 夹爪输出是分数，不是跨平台校准概率

ee6d 的夹爪通道经过 sigmoid，可解释为 [0,1] 的概率式分数，但官方没有给概率校准实验。固定提交的 17 个评测客户端使用 9 个不同阈值，并存在相反的正负指令约定；这些是具体机器人与任务的客户端约定，不是模型内置阈值：

客户端 阈值 判据
Google-VM coke_can、move_near 0.25 >阈值 取 +1
Google-VA coke_can、move_near、open_close 0.25 >阈值 取 +1
Google-VM place_in 0.28 >阈值 取 +1
Google-VA place_in 0.30 >阈值 取 +1
Google-VM open_close 0.35 >阈值 取 +1
LIBERO 0.50 >阈值 取 +1
VLABench 0.50 ≤阈值 判为张开
SoftFold-Agilex 0.50 >阈值 取闭合位置值
WidowX spoon / RoboTwin 0.70 高分分别映射为 -1
CALVIN / WidowX eggplant 0.80 <阈值 取 +1
WidowX blocks 0.91 <阈值 取 +1
WidowX carrot 0.95 <阈值 取 +1

这些差异同时受机器人指令约定、任务、微调 checkpoint 和控制器影响，不能仅凭阈值分布证明模型输出“完全没有跨任务物理含义”。可靠结论是：仓库没有提供可跨平台照搬的统一阈值与极性。

新平台应先确认控制器中张开/闭合的方向，再用少量带标签的验证样本选择阈值，并在低速、限位和可急停条件下验证；只看无标签输出直方图不足以决定阈值。

4.3 proprio：真实状态与命令记忆必须区分

LIBERO、CALVIN、WidowX 代表性客户端会把模型预测或已经下发的命令写回 proprio；RoboTwin 也把命令动作写回局部观测。它们维护的是“模型认为机械臂到达的位置”，不是传感器确认的真实位置。

这与训练数据并不等价：训练 proprio 是演示轨迹的真实当前状态，客户端回填则是预测/命令状态。二者可以具有相同维度和坐标表示，却会在跟踪误差、碰撞、饱和或通信丢包后逐渐偏离。VLABench 在每次重新规划时读取环境真实 ee_state，说明“自回忆”不是模型接口的必然要求。

真实机器人优先使用时间对齐后的状态估计；若必须使用命令记忆，应明确它只是降级方案，并设置误差监测与重新同步机制。

4.4 RoboTwin 的两个适配细节

  • 客户端读取 head、left、right、front 四路相机，但请求只发送前三路；front 当前是冗余读取。
  • scipy.spatial.transform.Rotation.from_quat 默认输入顺序为 (x,y,z,w)。RoboTwin 客户端没有 scalar_first 开关；若上游使用 (w,x,y,z)，必须先重排。

五、LeRobot 集成：相同模型思想，不同运行栈

LeRobot 的 X-VLA 是独立维护的移植实现，接口、动作注册表、预处理管线和优化器都可能与 2toinf/X-VLA 分化。比较时必须分别注明“官方仓库实现”和“LeRobot 实现”，不能把一边的源码行为放进另一边的表格。

5.1 固定版本文档给出的训练命令

在这里固定的 LeRobot 提交中，文档给出以下从 xvla-base 微调的示例。它是版本化示例，不代表未来版本仍采用相同参数：

pip install -e .[xvla]

lerobot-train \
--dataset.repo_id=YOUR_DATASET \
--output_dir=./outputs/xvla_training \
--job_name=xvla_training \
--policy.path=lerobot/xvla-base \
--policy.repo_id=HF_USER/xvla-your-robot \
--policy.dtype=bfloat16 \
--policy.action_mode=auto \
--steps=20000 \
--policy.device=cuda \
--policy.freeze_vision_encoder=false \
--policy.freeze_language_encoder=false \
--policy.train_policy_transformer=true \
--policy.train_soft_prompts=true

这里的 pip install -e 是源码目录中的可编辑安装命令，不是任意目录都能直接执行的包安装命令。

5.2 冻结开关与学习率不能混为一谈

开关 当前默认值 含义
freeze_vision_encoder false true 才冻结视觉 encoder
freeze_language_encoder false true 才冻结语言 encoder
train_policy_transformer true 是否训练动作 Transformer
train_soft_prompts true 是否训练 soft prompts

同一版 LeRobot 中存在口径冲突：配置类总注释说“默认冻结 VLM”，字段默认值和推荐训练命令却选择不冻结；文档的模型介绍又把 Phase II 描述为冻结 backbone。因此复现实验时必须记录实际四个开关，不能只写“使用默认设置”或笼统写“Phase II”。

当前 LeRobot 的差分学习率是：VLM 用基础学习率的 0.1，soft prompts 默认用 1.0，其他参数用 1.0。X-VLA 官方仓库的 learning_coef=0.1 则同时作用于 VLM 与 soft prompts。两者只有 VLM 的倍率相似，整体优化行为并不等价。

5.3 auto 模式的便利与代价

两套实现都让模型在预训练维度中工作、只对真实维度计算损失，并在输出时裁回真实维度；但当前损失系数不同：

行为 X-VLA 官方仓库 auto 当前 LeRobot auto
真实维度损失 全维等权 MSE 全维等权 MSE
总系数 100 1
夹爪 BCE 无 无
输入端夹爪清零 无 无
输出端 sigmoid 无 无

因此 auto 适合快速接入不同动作维度，但它不会自动理解哪些维度是位置、旋转或夹爪，也不会自动处理单位差异。两套实现对 proprio 的行为并不相同：官方仓库原样传入；LeRobot 的 _prepare_state 则补齐或截断到独立的 max_state_dim。后者避免了“状态必须与动作同宽”的限制，却会在 max_state_dim 过小时静默丢掉尾部状态维。

两套实现都必须让模型容量覆盖真实动作，即 real_dim ≤ max_action_dim。官方仓库超限会在负长度 padding 处失败；LeRobot 在策略包装层先把 action target 截到模型宽度，超限反而可能静默丢维。若位置以米计而其他维度尺度接近 1，等权 MSE 还可能产生梯度失衡；实际程度取决于 normalization 和各维方差。固定 xvla-base 配置把 ACTION 设为 MEAN_STD，这与从零构造时的 IDENTITY 默认值不同。

能够严格满足 EE6D 布局、单位与控制语义的平台，可优先使用 ee6d；否则应为新平台定义显式动作空间，而不是仅靠 auto 补零。

5.4 dataclass 默认值与 checkpoint 配置

LeRobot 从零实例化时的 dataclass 默认值，与 lerobot/xvla-base checkpoint 保存的配置存在差异：

参数 dataclass 默认值 xvla-base 配置
chunk_size 32 30
n_action_steps 32 30
max_state_dim 32 20
optimizer_betas (0.9,0.99) (0.9,0.95)
optimizer_weight_decay 0 1e-4
tokenizer_max_length 64 1024
ACTION normalization IDENTITY MEAN_STD
num_image_views None，按输入推断 3

这不应简单称为“发布权重错误”或“七项不一致缺陷”：from_pretrained 会加载 checkpoint 配置。真正的风险是脱离 checkpoint、手工按 dataclass 或文档默认值从零构造模型。页面和实验记录都应固定 LeRobot 代码提交与 checkpoint revision。

5.5 LeRobot 推理也采用非重叠动作队列

XVLAPolicy.select_action 只在动作队列为空时调用一次 _get_action_chunk，随后把前 n_action_steps 帧依次弹出；它没有对多个重叠 chunk 做 temporal ensemble。predict_action_chunk 则直接返回完整 chunk。固定 checkpoint 中 chunk_size=n_action_steps=30，所以默认会执行完整 30 帧后才重新规划；缩短 n_action_steps 可以更早重规划，但剩余预测会被丢弃，而不是与下一块融合。

LeRobot 的输入默认值也与官方 HTTP 服务不同：缺少 domain_id 时 _get_domain_id 静默返回 0；缺少中间相机键时 _prepare_images 按配置顺序收集仍存在的键，再在末尾补零，同样会压紧槽位。empty_cameras 只能显式增加尾部空相机，不能表达任意中间槽缺失。部署时应让 processor 显式写入 domain，并固定、核验相机 feature 顺序。

5.6 两阶段适配仍需显式实现

普通 scheduler_warmup_steps=1000 只描述学习率 warmup，不会自动复现“先只适配域私有参数，再联合优化”的阶段切换。论文给出两阶段适配思想；固定官方 train.py 只是用 freeze_steps、warmup_steps 和学习率组近似安排训练，而且不会自动创建或重置一个新 prompt。LeRobot 若要复现目标策略，同样必须显式控制冻结状态、域槽位初始化与各参数组学习率，并记录切换步数。

六、迁移到自己的机械臂

6.1 先定义四个不可含糊的契约

动作契约每一维的顺序、单位、绝对/相对含义、坐标系、左右臂排列和夹爪编码。
状态契约proprio 可以与动作同维，但必须说明它是传感器状态、状态估计还是命令记忆。
视觉契约每个槽位对应哪台相机、RGB/BGR、裁剪方式、分辨率和时间戳。
时间契约训练的 `qdur`、动作数、控制频率、执行窗口和推理延迟怎样对应。

ee6d 的20维布局只是表示约定，不意味着 proprio 与 action 在语义上天然“同构”。第0路是进入 Florence encoder 的主视角，但代码没有规定它必须是固定全局相机；应匹配 checkpoint 训练时的相机语义。

6.2 推荐的迁移顺序

  1. 离线定义动作与状态变换。写出从机器人原生状态到模型表示、再从模型动作回到控制器指令的双向变换；单独测试 Rotate6D、四元数顺序、坐标系和单位。
  2. 固定相机槽位。记录每个 image key 的物理相机、颜色空间与预处理；不要依赖缺键压紧的隐式行为。
  3. 选择 domain。为新域分配范围内、尚未占用的 id，并同步数据注册、soft prompt 与域相关投影。训练数据表或 LeRobot 输入缺少 id 时都会回退到槽位0；当前映射中槽位0还被多个数据类型复用，不能把它当成安全默认值。若想借用相近域初始化，应把源槽位参数显式复制到新槽位后再训练；直接复用已占用 id 会让两个域共享并共同改写同一组私有参数。无论哪种方式，相似性都只是初始化假设，不能证明相机和动作语义兼容。
  4. 匹配时间尺度。按目标控制频率选择 `qdur` 与动作数；官方仓库不同数据处理器使用过1、2、3、4、5、10秒等窗口，4秒不是通用常数。
  5. 先做离线回放。检查维度、NaN、边界、轨迹连续性、夹爪极性、阈值和动作速度，再进入仿真或数字孪生。
  6. 加入安全监督器。在模型与控制器之间实施限位、碰撞、速度、看门狗、超时和急停；模型服务永远不是安全控制器。
  7. 低速闭环上线。先执行很短窗口并读取真实状态重规划，确认误差可控后再逐步增加执行窗口。

6.3 上线前验收清单

  • 输出形状是否按当前 checkpoint 的 num_actions 与 action_mode 计算，而不是写死 30×20？
  • domain id 是否在范围内，并与训练的机器人、相机配置和动作投影一致？
  • 压缩图像是否完成 BGR→RGB，三路相机是否保持固定槽位？
  • proprio 是否来自时间对齐的真实状态；若使用命令记忆，是否监测跟踪误差？
  • 动作锚点时间尺度是否与控制频率一致，是否需要插值或重采样？
  • 夹爪极性与阈值是否使用带标签数据校准，并经过低速实机验证？
  • Rotate6D 转回旋转矩阵前是否检查两列向量的范数、共线退化与 NaN？当前辅助函数归一化时没有 epsilon 保护。
  • HTTP 是否有超时、认证、限流、请求校验和并发控制？
  • 是否存在独立于模型的安全限位、看门狗与急停？

七、真正值得记住的知识点与创新边界

  1. 一次观测编码，多次动作自细化。VLM 特征在动作块内部复用，避免每个去噪步重复视觉语言编码；这是推理结构的关键效率点，但不是已经量化证明的低延迟结论。
  2. 域条件不只是标签。domain_id 选择 soft prompt，并参与域相关动作编码/解码；范围正确但语义错误时可能静默产生不合适的动作。
  3. 统一模型空间与平台适配分离。固定实现的双臂 ee6d 模式用20维布局统一部分训练域；这不是所有 X-VLA 平台都必须采用的物理接口，实际机器人仍需要坐标、单位、夹爪和控制周期适配。
  4. 动作 chunk 在效率与反馈之间交换。长执行窗口减少推理请求，却增加开环误差和状态陈旧风险；执行多少步是客户端控制策略，不是模型固定结论。
  5. HTTP 服务与阈值表是工程实现，不是论文创新。它们的价值在于揭示部署契约和适配成本；X-VLA 的核心创新仍是跨 embodiment 的 soft prompts、域相关映射与统一动作建模。
