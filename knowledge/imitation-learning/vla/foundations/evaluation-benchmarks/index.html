一个分数只有绑定了确切评测对象、环境版本、闭环协议、分母、统计方法和原始 trial 证据，才是可解释的结果。协议不一致时，正确结论是“不可直接比较”，而不是继续排榜或用更多 trial 掩盖接口、污染和判据差异。

  • 评测对象不是模型名。 checkpoint、I/O contract、benchmark adapter、trial protocol 与 runtime 共同定义可执行实例。
  • 分母先于百分比。 scheduled、valid、completed、success、safe 和 autonomous 是不同集合。
  • ID/OOD 必须按轴声明。 对象、任务、场景、相机、本体、动作、动力学和时域不能压成一个布尔值。
  • 成功与安全分轴。 unsafe success、人工接管后完成、超时和安全停止必须保留。
  • 失败原因允许 unknown。 symptom 不等于 cause，归因必须绑定同步证据、置信度和裁决记录。

本页只设计评测协议、统计与证据封装，不运行模型、仿真或真机，不上传结果，不生成可直接控制机器人的脚本，也不把示例数值伪装成真实测量。

评测对象与闭环 Trial 契约

评测对象五元组

页面首个公式化定义：

evaluation_object = checkpoint_hash × policy_io_contract_hash × benchmark_adapter_hash × trial_protocol_id × runtime_version

任何一项改变，都至少产生新 evaluation object version：

  • checkpoint 权重、processor、tokenizer、normalization stats 或配置变化；
  • observation/action schema、camera role、frame、unit、action horizon 或 controller consumer 变化；
  • benchmark adapter 的 observation mapping、action mapping、success bridge 或 reset wrapper 变化；
  • trial 的任务集、初始状态、最大步数、retry、干预或终止规则变化；
  • runtime、dependency、precision、hardware path 或外部服务版本变化。

模型家族名只用于分组，不能作为可复现结果 ID。

七个常被混用的单位

| 术语 | 本页定义 | 是否独立统计单位 | | — | — | — | | trial | 按预注册初始条件与预算，从 reset 到终止的一次外部评测单位 | 是，主单位 | | episode | 环境/数据容器中的轨迹单位；可能与 trial 一一对应，也可能不对应 | 仅协议声明后 | | rollout | 策略与环境闭环产生的一段序列 | 通常是 trial 的证据 | | attempt | 为同一目标执行的一次动作/技能尝试 | 通常不是独立 trial | | internal retry | 同一 trial 内由恢复策略触发的重试 | 否；需计数 | | run | 一次进程/作业，可包含多个 trial | 否，除非研究对象是运行稳定性 | | seed | 某一随机源的标识；必须带 namespace | 否；用作分层/配对键 |

“episode 100 次”不能代替“100 个独立 trial”，除非协议说明其独立性、reset 和聚类结构。

结果状态机

最小状态：

scheduled → setup → running → {success, failure, timeout, safety_stop, human_takeover, infrastructure_invalid, protocol_abort}

其中：

  • success：权威成功判据在预算内成立；
  • failure：任务终止且未达成功；
  • timeout：到达步数或墙钟预算；
  • safety_stop：独立安全系统停止；
  • human_takeover：人类获得控制权；
  • infrastructure_invalid：与被测策略无关且有证据的环境/硬件故障；
  • protocol_abort：预注册规则要求中止，例如 reset 无法达到有效初态。

policy crash、非法动作、资源耗尽或长期无响应若由策略/adapter/runtime contract 触发，默认计策略失败，不能移到 infrastructure invalid。

从 checkpoint 到可执行实例

正文先画清五层：

  1. model family：论文/架构族，只用于语义组织；
  2. checkpoint artifact：不可变权重、配置与 processor；
  3. policy I/O contract：观测、动作、时间和 consumer；
  4. benchmark adapter：环境到 policy、policy 到环境的显式映射；
  5. trial protocol：reset、预算、终止、统计和记录规则。

只有五层绑定后，才允许产生 result_id。页面提供反例：相同权重换了相机裁剪、动作归一化、控制频率或 execution horizon，不能沿用原结果 ID。

Trial protocol 必填项

| 阶段 | 必填字段 | 关键问题 | | — | — | — | | 环境 | benchmark/version/commit、assets、task/variation、scene/object | 测试对象是否被唯一定位？ | | 初态 | reset procedure、eligibility predicate、randomization、seed | 何种初态算有效？ | | 策略 | checkpoint selection、state/memory reset、warm-up、cache | trial 之间是否泄漏状态？ | | 观测 | camera roles、resolution、crop、history、prompt、proprio、timestamps | 输入是否和训练/契约一致？ | | 动作 | Action ABI、controller、control rate、prediction/execution horizon、replan | 输出怎样真正执行？ | | 预算 | max steps、wall time、retry/replan/intervention budget | 何时必须结束？ | | 判据 | success、partial progress、failure、timeout、safety | 谁拥有最终判定权？ | | 记录 | logs、video、trace、clock sync、event schema | 是否能重建全过程？ | | 清理 | post-trial reset、object inspection、hardware cooldown | 下一个 trial 是否独立？ |

Reset 与初态资格

reset 不是一句“环境重置”：

  • 仿真需记录环境 seed、对象 pose、关节状态、相机、域随机化和 hidden state；
  • 真机需记录对象身份/姿态、机器人 home、夹爪状态、台面/工具、传感器健康和上一 trial 残留；
  • 初态资格 predicate 与成功 predicate 必须分开；
  • reset 失败不应静默替换为更容易初态；
  • 若重新 reset，保留原 scheduled trial ID、invalid 原因和 replacement link；
  • policy 的 RNN state、KV cache、planner memory、world-model buffer、external memory namespace 和 retry counter 必须按协议清空；
  • 若研究跨 trial 记忆，必须显式定义 carry-over；否则任何 carry-over 都是污染。

Checkpoint 选择与冻结

最终测试前冻结：

  • 候选 checkpoint 列表；
  • selection dataset/protocol；
  • selection metric 与 tie-break；
  • processor/tokenizer/config；
  • adapter；
  • threshold；
  • prompt/template；
  • trial count；
  • final test task/seed list；
  • 允许的 bug-fix 规则。

看过 final test 后换 checkpoint、prompt、相机 crop、阈值、成功判据或重试策略，都应产生新实验版本并公开此前尝试，不得继续称为同一 untouched test。

闭环与开放环

闭环评测至少要求：

observe → preprocess → infer → validate → execute subset → acquire fresh observation → judge/replan → terminate

页面解释三种时域：

  • prediction horizon：模型一次预测多少动作；
  • execution horizon：实际执行多少动作后重新观察；
  • trial horizon：完整 trial 允许的步数或墙钟时间。

一次预测 50 步不等于开放环执行 50 步；反之，只在动作块末端看一帧也不等于高质量闭环。必须记录实际 replan 点、丢帧、stale observation 和未执行动作。

Retry、Recovery 与干预

  • 内部 retry 保留在同一 trial，计 retry_count 与预算消耗。
  • 重新 reset 后再次运行是新 trial 或 replacement，按预注册规则决定。
  • 人类提示、物体复位、控制接管和手动跳过子任务都是 intervention。
  • 自主恢复成功应同时报告首次尝试结果、最终任务结果、恢复次数、额外时间和安全事件。
  • “允许三次直到成功”的指标必须命名为 success_within_k_attempts，不能替代 first-attempt success。
  • 任何重跑/排除都进入 audit log。

权威时间与同步

记录至少四个时钟域：

  • sensor capture；
  • policy request/response；
  • controller command/ack；
  • environment predicate/event。

必须说明同步方法、时间戳来源、允许偏差和丢失处理。不同机时钟未同步时，不得从视频帧序号推断精确 latency。

本节最小检查

用户应能回答：

  • 这是哪个 checkpoint 和哪个 policy contract？
  • benchmark adapter 是否有 hash？
  • trial 在何时开始、何时结束？
  • reset 和 memory clear 是否可验证？
  • failure、timeout、invalid 的分母如何处理？
  • retry 和 intervention 是否改变“自主成功”的含义？
  • 原始 trace 能否重建每个终止原因？

评测对象必须不可变。 manifest 解析 checkpoint、processor、normalization、I/O contract、adapter、environment、protocol 与 runtime 的内容摘要，并用它们生成 evaluation object ID。任何默认值、外部服务、precision 或 controller 变化都创建新对象；同一模型家族下的两个对象可以并列，但不能把后一个结果回填到前一个 ID。

Trial 调度采用追加式事件：scheduled、eligible、resetting、running 与终态各有时间和证据。reset 完成必须得到环境、策略状态、memory、队列和 controller 的确认；只重置场景而保留 recurrent state 会造成跨 trial 泄漏。初态资格失败在执行前可标 invalid，运行后由策略输出、超时或崩溃导致的失败仍属于 trial 分母。

Retry 与 attempt 分开记账。内部 recovery 是同一 trial 的状态变化；协议允许的整次重跑要保留父 trial、触发、是否使用同一初态与最终计分方式。未预注册的“再试一次”不能替换失败结果。网络层幂等重发不应产生第二个物理动作，执行层 attempt 则必须出现在 trace 中。

所有模块用统一 trial clock 或保存可验证转换。视频帧、observation、model start/end、command、controller feedback、success predicate 与 safety event 需要可同步；否则 failure annotation 只能写时间关系 unknown。评测不能只保存最终百分比，应先证明每个终态能回到同一 evaluation object 和原始事件窗口。

协议预注册至少冻结 evaluation object、task/variation、trial 数、初态生成、reset、最大时长/步数、retry、intervention、终态、invalid replacement 与主指标。任何运行后变更都创建 deviation event，说明发现时间、影响范围和旧结果是否仍保留。修复 benchmark bug 可以开启新 protocol version，但不能把修复后的 trial 与旧 trial 无标记混在同一分母。

Reset 资格可用小型探针验证：环境对象、机器人状态、相机、策略 cache、RNN/Transformer history、planner、memory、queue 与随机数状态都达到声明边界。探针失败的 scheduled trial 标 setup-invalid 并保存证据；一旦策略已经观察或行动，后续 reset 失败通常不能倒退为“未开始”。真实机器人上无法精确复现初态时，记录测量范围与 operator，而不是伪造相同 seed。

冻结后生成 protocol checksum，并让 runner 在每个 trial 起始时回显 object/protocol hash。聚合只接受匹配 hash 的记录；若运行中代码、环境或服务重启改变版本，当前 trial 按规则终止并分流。这个握手能阻止同一目录里混入不同 checkpoint、adapter 或 controller 的结果，也使中断续跑不会悄悄改变实验对象。

ID/OOD 分布轴、划分与污染

OOD 不是一个布尔值

本页使用“曝光矩阵”而不是单个 ood: true。每个轴分别记录 pretraining、fine-tuning、selection 和 final test 是否出现。

| 分布轴 | 典型取值 | 必须记录的曝光 | | — | — | — | | task/skill | 已见技能、新技能、组合、新顺序 | 标签、轨迹、成功视频、任务文本 | | instruction | 原句、释义、组合、否定、歧义 | 文本或多模态预训练暴露 | | object | instance、category、shape、texture、state | 实物/资产/图像/视频 | | pose/layout | 位置、朝向、相对关系、遮挡 | 训练随机化范围与测试范围 | | scene | 背景、房间、台面、杂物、照明 | 场景资产和相机画面 | | camera | role、内外参、位置、裁剪、分辨率 | 校准与增强范围 | | embodiment | robot、gripper、tool、kinematics | adapter 与控制数据 | | sensor/modality | RGB、depth、proprio、tactile、language | 缺失/噪声模式 | | action/control | frame、mode、rate、controller、horizon | 训练标签和部署映射 | | dynamics | friction、mass、compliance、payload、latency | simulator/randomization/real session | | temporal | subtask length、sequence length、delay、recovery | 训练 horizon 与 memory | | operator/session | demonstrator、day、site、reset operator | 真机流程与人为因素 | | perturbation | occlusion、distractor、sensor noise、object motion | 强度和组合 |

结果标签应写成 ID-task / OOD-object / OOD-camera 等组合，并附判定依据。只说“zero-shot”或“unseen”不够。

三类 exposure

每一轴至少区分：

  1. label exposure：精确任务标签、指令或对象 ID 出现；
  2. visual/semantic exposure：网页、图像、视频、预训练语料或相近描述出现；
  3. trajectory/control exposure：状态—动作或控制轨迹出现。

“没有用 benchmark demonstration 微调”不等于没有视觉或语义预训练 exposure。

Split 设计

  • task split：技能/组合是否真正未见；
  • object split：按实例、类别或材质，不能在帧级随机拆分同一对象；
  • scene split：资产、布局与背景是否独立；
  • embodiment split：robot/tool/controller 是否独立；
  • temporal split：序列长度或干扰时点是否外推；
  • session split：真机日期/操作者/维护状态分开；
  • perturbation split：强度和组合是否超出训练范围。

所有 split 在数据 release 层固定。不能用 episode 随机划分掩盖同场景、同对象或相邻时间片泄漏。

Contamination ledger

最小污染来源：

  • benchmark demonstrations 进入预训练或微调；
  • benchmark task text/goal image 进入多模态预训练；
  • 相同仿真资产、场景或对象纹理进入训练；
  • synthetic data 复现 test layout；
  • benchmark test 的失败视频被用于提示、阈值或 checkpoint 调整；
  • leaderboard/public result 导致重复人工调参；
  • evaluator、VLM judge 或 success classifier 在 test 上校准；
  • external planner、retriever 或 API 已存有 benchmark 答案；
  • 同一真机 trial 的多相机视图跨 split；
  • 任务别名让重复内容未被去重。

ledger 字段：来源、可能暴露的轴、证据、时间、处理、confidence。若无法判定，写 unknown 并降低结论强度。

OOD 声明模板

每个 OOD 结果必须带：

  • claim：只描述具体轴；
  • reference distribution：训练/选择范围；
  • test distribution：测试范围；
  • held-out mechanism：如何隔离；
  • contamination status；
  • matched controls；
  • sample size；
  • observed effect 与 uncertainty；
  • unsupported extrapolations。

反例：“模型具有强泛化”。合格写法：“在固定 robot、camera、action/controller 与任务语义下，对未出现在 fine-tuning release 的 12 个对象实例进行 120 个 trial；pretraining visual exposure 未知，因此只支持 instance-level adaptation-free evidence。”

Shortcut 与过拟合诊断

页面吸收近期 benchmark 审计提出的问题，但不把单篇审计升级为永久结论。建议诊断：

  • language ablation：移除/打乱指令后性能是否仍高；
  • pose/layout perturbation：训练范围内小变化是否引起大降幅；
  • visual shortcut probe：低容量、无语言或只看背景的 probe 是否接近主模型；
  • data-source dependence：换 demonstration source 或 renderer 是否崩溃；
  • checkpoint sweep：结果是否来自对 test 的 creeping selection；
  • task-balanced uncertainty：所谓提升是否超出区间；
  • hidden nuisance audit：初态、reset 或 object ID 是否暗示答案。

这些诊断是证据，不自动证明 benchmark “无效”；结论必须绑定版本和实验。

Exposure ledger 以轴为行、阶段为列：pretraining、robot pretraining、target adaptation、prompt/threshold tuning、selection 和 final test 分开。每格记录 release、是否直接出现、是否有近重复、来源证据和结论；查不到来源写 unknown。公开网页、视频或 benchmark 说明进入通用预训练也可能形成语义暴露，不能只检查机器人轨迹文件名。

OOD 标签来自对冻结训练世界的差异，不来自测试集名称。新对象但旧场景可标 OOD-object；新相机和视角是 OOD-camera；新 embodiment、Action ABI 或动力学分别标注。多个轴同时变化时保留组合，不用一个“hard OOD”覆盖。每个 axis 还要声明粒度，例如 object category 未见但 instance 已见，或 instruction paraphrase 未见但 task predicate 已见。

Split 先按能避免泄漏的最高相关单位切分：episode 相邻窗口、同一对象实例、同一场景资产、同一演示者或生成模板不能随机散到 train/test 后再声称独立。近重复检测、task template、asset ID、语言规范化和数据派生关系都进入 split manifest。任何在 test 反馈后改变 prompt、阈值、adapter 或 checkpoint 的行为都会把该集合降级为 selection。

Contamination 结论需要可证伪：列出已检查来源、工具版本、匹配规则、false positive 处理和未覆盖范围。clean 只能描述已完成检查的边界，不能等于“没有发现”。对近期预训练数据不透明的模型，应把 benchmark exposure 标为 unknown，并限制 claim；更多 trial 或更窄置信区间不能消除这一来源不确定性。

Exposure 不只来自显式训练样本，还可能来自 prompt 示例、成功判据、任务文本、演示视频、人工筛选和 benchmark-specific debugging。ledger 为每次接触记录主体、时间、内容范围和它是否改变模型、代码或选择。仅由评测人员查看但不反馈给开发流程的证据，与用于调参的暴露分开；一旦反馈发生，相应 test 就不再 untouched。

Unknown 要向 claim 传播。若 pretraining 数据不可审计，不能写 clean OOD，只能在 fine-tuning/selection 维度作已知声明；若对象实例关系不明，OOD-object 结论降级；若 benchmark 任务出现在自然语言预训练但无机器人轨迹，分别标 semantic exposure 和 control exposure。报告可以继续展示结果，但结论必须带这些未知条件。

污染检查会随新证据更新。发现近重复、训练资产或 prompt 泄漏时，不删除旧报告，而是发布 ledger revision，列出受影响 result IDs、重新计算的切片和撤回或保留理由。一个模型在污染切片表现好、干净切片表现弱是有价值诊断，不能通过整体平均隐藏；同样，未发现匹配只支持检查工具覆盖范围内的暂时结论。

Benchmark 适用性与可比性门禁

选择 benchmark 的顺序

不先问“哪个最权威”，而先问研究问题：

  1. 单任务控制还是长序列组合？
  2. lifelong/transfer 还是统一多任务？
  3. 单臂、移动操作还是双臂协作？
  4. 关注视觉/语言泛化、接触控制、家务场景还是 sim-real 对照？
  5. 需要真实机器人验证还是只做受控仿真筛选？
  6. 模型的 observation/action contract 能否无损适配？
  7. 环境版本、任务、资产和 success predicate 是否可固定？
  8. 预算是否足以覆盖 task × seed × variation × checkpoint？

可比性门禁

  1. benchmark family、major/minor version 与 assets 匹配；
  2. task/variation list 与 split 匹配；
  3. demonstration/data budget、pretraining exposure 类别可比；
  4. observation views、resolution、crop、history、proprio、language 匹配；
  5. action ABI、controller、control frequency 与 postprocess 匹配；
  6. prediction/execution horizon、replan 与 retry 匹配；
  7. external planner、memory、world model、detector、retriever/API 匹配或作为明确系统差异；
  8. checkpoint selection 与 tuning budget匹配；
  9. reset、initial state、max steps/wall time、success/partial/safety 判据匹配；
  10. trial/seed、aggregation、CI 与排除规则匹配；
  11. latency 比较时硬件、precision、batch、warm-up 和计时边界匹配。

分类：

  • comparable：门禁匹配，可直接对照；
  • partially_comparable：研究问题相关，但有明确差异；只做定性或分层解释；
  • non_comparable：核心对象/协议不同，不排序；
  • matched_re_evaluation：在同一冻结协议下重新运行，优先级最高。

Benchmark 选择从研究问题开始，而不是从可用排行榜开始。需要短时多任务迁移、长序列组合、受控 sim-real、家庭场景、多样资产、物理交互或多任务泛化时，选择能提供相应任务与协议的基准；结果只回答该问题。七个 benchmark 的名字不是互换单位，也不能用一个单分数拼成“综合 VLA 能力”。

每个结果生成 protocol fingerprint：benchmark 名与版本、suite/task/variation、资产和随机化、observation/camera、action ABI、controller、frequency、prediction/execution horizon、reset、success、trial 数、retry、external module、hardware/runtime。比较器逐字段输出 same、compatible-with-transform、different 或 unknown。任何强契约不同默认 non-comparable，只有预注册映射和配对复测才能升级。

Partially comparable 不是把分数放在同一排序列。报告先列共同子集，再列差异和可支持的有限 claim，例如同一 checkpoint 在两种相机输入下的消融；绝不声称全局优劣。若 task list 只有交集，可在交集上重新聚合并保留原完整结果，但不能通过挑选有利任务制造新排行榜。

Leaderboard 行只作来源索引。版本更新、隐藏测试、提交规则或官方 adapter 变化时，保存快照日期与条目元数据；作者自报、官方服务器和独立复现使用不同 badge。复现更换 robot、skill library、prompt、controller 或 memory 时标 modified protocol，而不是悄悄沿用论文结果名称。

Benchmark adapter 必须有 conformance tests：observation 的相机角色和数值范围、action 的维度/单位/frame、controller mode、episode reset、success bridge、done/timeout、frequency 和 horizon 均与声明一致。用固定输入检查转换、用已知动作检查符号和单位、用官方或最小环境案例验证 success。adapter 能运行不代表语义无损。

比较前先生成逐字段差异表，并把差异分为 identity、transformable、analysis-only 与 blocking。图像分辨率可在双方都使用同一预注册变换时兼容；Action ABI、controller、任务列表或成功判据差异通常 blocking；trial 数不同可在统计层处理但不能忽略。unknown 字段也视为 blocking，除非 claim 明确不依赖该字段且给出理由。

跨 benchmark 只能比较经过共同抽象重新定义的属性，例如各自协议内的 failure distribution 或 latency 边界，且不能把原始 success 数值直接排序。若想研究普遍趋势，应预先定义元分析单位、benchmark 权重与异质性，并承认任务构造相关。网站默认显示独立结果卡和 fit matrix，不提供“总冠军”或把不同量纲归一化后求和的按钮。

Partial metric 不能污染 success

配对比较

少量 runs 与选择偏差

遵循 Henderson 等和 Agarwal 等的共同警告：

  • 点估计不能表达有限 runs 的不确定性；
  • 少量训练 runs 时，均值和中位数可能很不稳定；
  • 报告 interval estimate；
  • 保存所有预注册 runs；
  • 不只展示最佳 seed；
  • checkpoint、超参数和 protocol selection 造成的偏差须公开；
  • 多算法、多任务、多指标同时比较时说明 multiple-comparison 处理或把结论降为探索性；
  • “数值更高”不自动等于可靠提升。

分母链应满足 scheduled ≥ eligible ≥ valid ≥ completed，而 success、safe、autonomous 是 completed 的交叉属性。每个差值都要有枚举原因和逐 trial ID。排除只能依据运行前冻结的 eligibility 或明确外部基础设施规则；看见失败结果后改成 invalid 属于选择偏差。主结果至少同时给 success/scheduled 与 success/valid 的边界视图，并解释两者差异。

统计单位是独立 trial 或更高层 cluster，不是 frame、step 或同一 reset 的重采样。配对设计保存相同初态/seed/场景键，用配对差或层级模型；非配对结果不能套用配对检验。区间方法、bootstrap 层级、随机 seed、run 数和多重比较策略预注册。少量 run 时展示所有点和选择流程，不以 p 值替代效应大小、协议一致性与实际风险。

时延分解 model compute、pre/post-process、RPC/queue、scheduler、controller 和 observation-to-command；报告 p50/p95/p99、jitter、deadline miss、warm-up、batch、precision、hardware、缓存和 observation age。超时 trial 仍进入任务分母，并在时延分布中按协议处理。快而失败与慢而成功不是同一目标，性能、安全和实时性使用并列门禁而非任意总分。

分母审计器从事件账本重算所有集合，而不是信任汇总 CSV。它验证每个 scheduled ID 恰好进入一个终态或仍有明确 pending，replacement 指向父记录，重复 ID、孤立 attempt 与终态冲突都会失败。结果卡保存用于计算的 trial ID hash；任何排除或标签 revision 都产生新 aggregate version，旧表仍可追溯。

缺失与中止需要敏感性分析。对基础设施 invalid、无视频、部分日志、人工 abort 和 policy crash 分别按预注册、保守与替代假设重算关键指标，展示结论是否翻转。不能把“无法判定”统一当失败或成功，但也不能从分母消失。若 missingness 与策略相关，例如某模型更常崩溃，complete-case 分析会偏向它，必须在主结论中指出。

失败分类、诊断与恢复证据

三层记录：Outcome、Symptom、Cause

  • outcome：最终发生了什么，例如 timeout、task failure、unsafe success；
  • symptom：可观察现象，例如目标丢失、重复动作、夹爪闭合但未持有；
  • cause：有证据支持的机制，例如相机时间戳错位、frame mapping 错误、planner 选择不可行技能。

outcome 与 symptom 可以直接记录，cause 需要证据和置信度。不能从“没抓起来”直接推出“视觉模型失败”。

  • recoverable failure：局部失败后按协议自主恢复；
  • terminal failure：预算内未恢复；
  • safe fallback：无法继续但进入受控安全状态；
  • human-rescued completion：接管后完成，不是 autonomous success。

这些标签可组合，不能强迫到单一 success/failure 桶。

Recovery 评测

恢复结论至少绑定：

  • failure class；
  • detector sensitivity/false trigger；
  • recovery action；
  • retry/replan budget；
  • time/step overhead；
  • success after recovery；
  • new safety events；
  • repeated failure；
  • fallback/stop；
  • no-recovery matched baseline。

“演示过一次恢复”不是 recovery rate。恢复能力必须在预定义失败分布或自然失败集合上统计。

标注者与裁决

  • 标注指南含正例、反例和 unknown；
  • 训练集与正式 trial 分开；
  • 可盲掉模型名/期望结果时尽量盲标；
  • 双标一部分或全部高风险失败；
  • 按类别报告 agreement；
  • nominal categories 可用 Cohen/Fleiss kappa 等，但同时给原始一致率和混淆；
  • disagreement 由具备对应模块知识的 reviewer 裁决；
  • taxonomy 更新后不静默覆盖旧标签，保留 migration/version；
  • 高置信 cause 需要日志或复现实验证据，不只靠多数投票。

故障切片仪表

页面建议三联视图：

  1. outcome funnel：scheduled 到各终态；
  2. failure taxonomy：primary × contributing；
  3. timeline：observation、plan、action、controller、安全、predicate 与 recovery。

图表都必须能回到 per-trial 表，不能只显示圆饼图。

失败记录先写 outcome，再写可观察 symptom，最后写 cause。任务未完成是 outcome，物体滑落或动作停滞是 symptom；只有同步 observation、plan、action、controller、monitor 和环境证据支持时，才能把 primary cause 指向 perception、planning、policy、controller 或 runtime。证据不足时保留 unknown，不从末帧外观猜内部模块。

每个失败只有一个主要原因用于互斥统计，但可以有多个 contributing factors；安全事件、干预和恢复状态是正交标签。标注记录证据窗口、时间范围、artifact IDs、置信度、标注者角色、规则版本和可反证条件。标签改变采用 revision，不覆盖旧裁决；低置信和争议项进入复核队列。

标注流程至少包含独立初标、盲化复核、分歧对照和 adjudication。抽样报告一致性与各类别混淆，但一致并不保证正确，仍需权威传感器或系统日志。视频可以辅助语义判断，不能替代未记录的力、controller fault、queue timeout 或安全 veto；隐私、人员图像与场地信息在进入共享 bundle 前按最小化规则处理。

Recovery 评测要绑定原失败类型和预算：触发了哪级恢复、改变了什么、是否形成新 failure、最终是否成功、额外时延和干预。unsafe success、near miss、recoverable failure、terminal failure 与 safe handling 分开。只在恢复后展示成功视频会掩盖恢复触发率和风险，因此主表同时给失败数、恢复尝试、恢复后成功和终止原因。

Failure taxonomy 应有版本化定义、包含/排除例与相邻类别区分。标注者看到的是去模型身份的同步证据窗口，避免被论文主张或结果标签引导；只有裁决者在需要时查看额外日志。每类定期抽样审计 false assignment，并把混淆矩阵反馈到标注指南，而不是修改旧标签来追求更高一致性。

Primary cause 可以表示为因果链中的首个可干预失效：错误 grounding 导致错误 plan，再导致 collision 时，grounding 可为 primary，planning/action 为 contributing，collision 为 symptom/safety outcome。若证据只能看到末端，primary=unknown，保留候选因素。该规则防止团队按组织边界把责任推给最后执行模块，也防止从“抓取失败”直接推断 policy 问题。

Recovery 结论至少有两个分母：可恢复失败中触发恢复的比例，以及触发恢复后 verified task success 的比例；另报恢复引入的安全事件、循环、额外动作和时间。没有恢复触发的失败不能从第二个分母删除而不解释，主动 SafeStop 也不能算恢复成功。比较策略时，recovery policy、预算和 monitor 必须相同或标 non-comparable。

Sim、SIL、HIL、digital-twin 对照与真机是不同证据层。每层冻结物理引擎、渲染、资产、sensor noise、action/control bridge、frequency、latency injection、reset 与 success predicate。视觉相似或结果相关只能支持特定对照，不能宣布真机等价；碰撞模型未覆盖、接触简化或传感器缺失时，相应安全 claim 明确排除。

Sim–Real 声明采用阶梯：sim-only result、matched protocol comparison、correlation study、prospective transfer test、real-world confirmation。升级需要同任务、对象/场景、policy object、Action ABI、trial protocol 和统计单位的证据，并展示失败与不一致。仅在仿真上调到最好再挑真机案例属于 selection，必须保留调参路径和独立真机 final test。

Reproducibility bundle 包含 machine-readable manifest、对象哈希、环境/adapter、任务和初态、raw per-trial record、同步日志、允许的视频、排除表、failure revisions、aggregation code/version 与生成的 result card。bundle 用内容地址和父版本，不使用 latest/final 作为身份；敏感原始材料可留在受控存储，但公开索引仍提供存在性、摘要、权限和审计结论。

最终 claim 从“该 trial 的观察”逐级到“该协议的聚合”“同协议比较”“修改协议复现”和“跨系统假设”。每升一级都列支持条件与禁止外推。交给实时部署页的 latency、jitter、observation age、deadline miss、queue、recovery 与 safety event 必须来自同一 trial trace；没有真实运行时数据时保持 not_measured，不用论文硬件或估计值填空。

独立复算从全新目录和只读 bundle 开始，不读取作者工作区的隐式 cache。验证者解析 manifest、检查 hash、重建环境、运行聚合代码，并比较 raw counts、表格和图的内容摘要；无法获取受控媒体时仍核验访问清单与 trial 索引。复算失败分为缺制品、版本不兼容、结果不一致和不可访问，不能只写“无法复现”。

Bundle 还要支持最小重放：选取成功、普通失败、timeout、安全停止、invalid 和 recovery 各一个 trial，按事件顺序重建状态与指标。无需重跑机器人即可验证 outcome、分母和 failure annotation 是否一致。若聚合依赖手工表格或视频目测而没有机器可读记录，结果最多停留在有限观察层，不能进入高等级比较。

发布记录列出 designed、executed、audited、recomputed 与 externally_reproduced，每个状态绑定范围、日期和证据。网页完成只证明 designed/statically checked；没有真实运行不得生成 successes、latency 或 safety 数字。后续新增 trial、修复标签或更新 benchmark 都发布新 result card revision，不覆盖旧证据，也不把动态 leaderboard 当作稳定事实。

结果发布前还要做 claim-to-evidence 反向抽查。对摘要中的每个数字、比较词和泛化词，追到 result card、aggregate、trial IDs、protocol 与 evaluation object；任何一跳缺失都删除或降级该 claim。再从随机 raw trial 正向计算其终态、分母和切片，确认不会因过滤顺序、空值或标签 revision 得到不同结果。两向审计同时通过，才能证明报告不是与原始证据脱节的静态表格。

对 non-comparable 结果仍可形成研究假设，但必须写清需要什么配对实验才能验证，例如统一 checkpoint、相机、Action ABI、controller、初态与 trial protocol。页面不把“无法比较”当成信息终点，而是输出最小补证设计；在补证完成前，不显示胜负箭头、名次或综合色阶，避免视觉呈现先于文字制造排序印象。

必须明确拒绝的错误表述。

  • “在 LIBERO 上达到 X%，所以模型具备通用机器人能力”错误；只能支持该版本、该任务列表和该协议内的结论。
  • “都叫 LIBERO，因此结果可比较”错误；还需检查 suite、demonstration budget、相机、输入、动作、chunk、reset、成功判据和 trial 数。
  • “CALVIN 分数更高，所以单步操作更强”不成立；其长序列指标与单任务成功率回答的问题不同。
  • “SIMPLER 就是真机评测替代品”错误；它提供受控仿真证据和特定协议内的 sim-real 对照，不自动证明真机成功。
  • “RoboCasa、RoboTwin、ManiSkill 的名字不变，所以结果跨版本可合并”错误；版本、资产、任务和 horizon 变化会改变评测对象。
  • “RLBench 有 100 个任务，所以任何子集结果都代表 100 任务”错误；必须列出任务和 variation。
  • “成功率 80%”信息不足；至少要给 80/100、任务/切片、区间方法和分母处理。
  • “失败后重跑一次不影响结果”错误；未预先声明的重跑会选择性删除失败。
  • “每个随机初始位置都是一个训练 seed”错误；训练随机性与评测条件随机性必须分层。
  • “95% CI 相交就一定无差异，或不相交才算显著”都过度简化；比较方法须与配对、层级和多重比较设计一致。
  • “更多 trial 总能修复不公平协议”错误；样本量不能修复接口、污染或判据不一致。
  • “宏平均和微平均只是显示风格”错误；两者改变任务权重与结论。
  • “policy crash 是无效 trial”通常错误；若由策略输出、内存增长或接口违约触发，应计为策略失败。
  • “success predicate 返回 true 就安全”错误；成功与安全是两个轴。
  • “物体掉落就是抓取模块失败”可能错误；掉落可来自感知、规划、动作生成、controller、碰撞或环境异常。
  • “超时不是失败”错误；若协议规定时间/步数预算，超时是终止类别。
  • “部分完成接近成功，可换算成 0.5 个成功”只能在预注册 partial metric 中使用，不能暗改二元成功。
  • “只看平均 latency 足够”错误；闭环系统还需 p50/p95/p99、jitter、deadline miss 和 observation age。
  • “仿真中没有碰撞就是安全”错误；可能只是碰撞模型、采样频率或传感器未覆盖。
  • “人工接管后完成仍算自主成功”错误；应同时记录 task outcome、autonomy outcome 和 intervention。
  • “不知道原因时选最像的类别”错误；必须允许 unknown，并保留证据置信度。
  • “视频能复现实验”错误；还需代码、模型、环境、协议、seed、原始日志和聚合脚本。
  • “leaderboard 一行就是完整证据”错误；只能作为索引，不能替代 result bundle。
