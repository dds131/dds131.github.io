专题总览 8 统一评测 9 实时部署 10 安全可靠性

实时部署不是让模型“尽量快”，而是让带时间戳和版本的观测，在可证明的预算内经过确定转换生成可验证动作，并由有界调度器提交给明确控制器；任何迟到、乱序、失配或失效都有预先定义的拒绝、降级和回滚路径。

  • 部署对象是完整 bundle。 权重、processor、I/O contract、adapter、runtime、协议、scheduler 与 controller binding 缺一不可。
  • 平均快不等于实时。 deadline、p99、jitter、observation/action age 和 miss count 决定可预测性。
  • 任何 response 都要重新校验。 session、request、observation、contract、expiry、shape、finite 和动作语义不匹配时拒绝执行。
  • 队列必须有界。 overflow、underflow、starvation、stale、duplicate 与 out-of-order 都有显式状态转换。
  • 优化产物是新 artifact。 量化、编译、engine 与缓存变化必须重做数值、接口和闭环验证。

本页只设计系统接口、时序与发布证据，不启动策略服务，不运行推理、SIL/HIL、仿真或机器人动作，不提供真实地址、端口、凭证和控制值。

部署对象、责任拓扑与实时边界

Deployment bundle

页面给出：

deployment_bundle = evaluation_object + processor + observation_adapter + action_adapter + runtime_engine + service_protocol + scheduler + controller_binding + deployment_config

其中每项有 ID、version、content hash、build provenance 和 compatibility range。改变以下任一项都产生新 deployment ID：

  • checkpoint/config/processor/stats；
  • policy I/O contract；
  • crop/resize/color/history/prompt；
  • action decode/unnorm/frame/mapping/limit；
  • runtime、precision、quantization、compile/engine；
  • server/client protocol；
  • queue/chunk/scheduler；
  • controller、robot/tool/calibration；
  • timeout/fallback；
  • hardware/driver/runtime compatibility。

实时类别

| 类别 | 定义 | 本页约束 | | — | — | — | | hard real-time | 任一 deadline miss 都是系统失败 | 只允许经形式/平台证明的低层路径宣称；VLA service 默认不宣称 | | firm real-time | 迟到结果无价值，应丢弃 | 适合定义过期 observation/action response | | soft real-time | miss 会降低质量，但可按规则降级 | 多数高层 policy serving 属此类 | | best-effort | 无可验证 deadline | 只可用于离线/开发，不进入已批准控制链 |

低 latency 不等于 real-time；需要 deadline、miss definition、负载范围和验证证据。

八种速率

至少分开：

  1. sensor capture rate；
  2. observation synchronization/assembly rate；
  3. policy request rate；
  4. inference completion/service rate；
  5. action chunk publication rate；
  6. action dispatch/setpoint rate；
  7. low-level controller update rate；
  8. independent safety/watchdog rate。

另记录 logging/video/telemetry rate，但不得让它们占用控制 deadline。

三种年龄

  • observation age：动作提交时减去其最新有效观测的 capture timestamp；
  • response age：动作提交时减去 server response produced timestamp；
  • action age：当前待执行 action 对应计划生成/有效起点至执行时的时间。

每个年龄都需使用明确时钟域或经验证的 clock mapping。

六条系统不变量

  1. contract invariant：客户端、服务端、adapter、controller 看到的 contract hash 一致。
  2. session invariant：响应只能进入创建它的 session。
  3. monotonic invariant：sequence/commit index 单调，不执行乱序或重复 action。
  4. freshness invariant：观测、响应和 action 不超过各自 validity。
  5. authority invariant：只有 action scheduler/controller adapter 可提交 setpoint，policy server 不能直接写硬件。
  6. safety independence invariant：停止/限位/watchdog 不依赖 policy server 或同一故障域。

双平面拓扑

控制数据平面：

sensors → timestamp/sync → observation adapter → policy client → policy server/runtime → action adapter → scheduler → controller → hardware

监督平面：

health/readiness → metrics/trace → supervisor → release controller → rollback → safety interface

独立安全平面横跨 sensor/controller/hardware，但不依赖 policy 服务。页面必须画出三条平面，禁止把 logger/supervisor 画进动作主路径。

模块责任矩阵

| 模块 | 拥有 | 不拥有 | | — | — | — | | sensor driver | capture timestamp、raw frame/state、health | policy crop/prompt | | observation adapter | schema mapping、sync、preprocess、history/prompt | 模型权重、硬件命令 | | policy client | request、deadline、session、latest observation、response validation | policy internals、controller limits | | policy server | artifact loading、processor/model、inference、response metadata | robot reset、controller、安全停机 | | action adapter | decode、unnorm、frame/unit、mapping、validity | 决定任务成功、绕过 safety | | scheduler | chunk/queue/commit、deadline、fallback request | 修改模型输出语义 | | controller | setpoint tracking、ack、tolerance、低层 update | 解释语言或重跑模型 | | safety system | independent limit/stop/takeover | 模型能力或 benchmark claim | | logger/telemetry | 异步证据记录 | 阻塞控制环 | | supervisor/release | process lifecycle、bundle switch、rollback | 直接生成动作 |

硬/软实时隔离

建议默认：

  • hard/firm domain：驱动、controller update、watchdog、安全 I/O、有限状态 fallback；
  • soft domain：相机编码、policy client、network、GPU inference、planner、日志；
  • bridge：有界 lock-free/ring buffer 或经验证的 real-time-safe interface。

不能因 ros2_control controller 为 realtime-safe，就宣称上游 Python VLA、ROS 2 executor、网络和 GPU 全链硬实时。页面引用 ROS 2 real-time 背景，说明 OS、用户代码、内存、I/O、锁和调度都影响确定性。

部署身份与握手

startup handshake 必须交换：

  • protocol/schema versions；
  • deployment ID；
  • checkpoint/config/processor/stats hashes；
  • policy I/O contract ID/hash；
  • observation/action schema IDs；
  • camera role/order；
  • action dims/order/frame/unit/mode；
  • prediction/execution horizon；
  • supported precision/runtime；
  • max request/response size；
  • timebase/clock sync status；
  • feature/capability flags；
  • robot/controller binding；
  • safety interface version；
  • server/client build commits。

任何 required mismatch 默认 reject，不进行“尽力转换”。可兼容 minor version 必须有显式 migration 与测试。

Liveness、Readiness 与 Functional readiness

  • liveness：进程是否活着；
  • readiness：artifact 已加载、engine 可调用、依赖可用；
  • functional readiness：完成 contract handshake、warm-up、golden request、latency budget、client/controller/safety link；
  • active：release controller 明确放行；
  • degraded：只允许批准的受限模式；
  • draining：不接新请求，处理/丢弃存量；
  • stopped：无动作 authority。

HTTP 200 或 socket 可连接只证明有限 liveness。

生命周期

built → static-validated → replay-validated → SIL → HIL → shadow → canary-approved → active → degraded/draining → rollback/stopped

每次状态迁移有 owner、证据、审批和超时。网页模板只描述流程，不提供真实启动命令。

故障域

至少区分：

  • sensor/driver；
  • clock/synchronization；
  • client process；
  • network/transport；
  • server process；
  • GPU/runtime；
  • adapter；
  • scheduler/queue；
  • controller；
  • robot hardware；
  • logger/telemetry；
  • safety system；
  • release/configuration。

同机不等于同故障域；同进程的 logger、inference 和 scheduler 更容易共同失败。页面要求画出进程/主机/设备边界，但示例使用虚构角色，不写真实地址。

Deployment bundle 是唯一发布单元。 manifest 不只列权重，还解析 processor、tokenizer、prompt、camera/state schema、normalization、action adapter、runtime engine、service protocol、scheduler、controller binding、dependency 与配置的内容摘要。任何组件改变都创建新 bundle ID；运行时不得从 latest 目录拼出“近似组合”，缺少强契约组件时保持 not_ready。

拓扑责任要写到边。Robot client 拥有 capture、硬件时间戳与设备连接；observation adapter 拥有训练语义转换；policy server 只消费已验证输入并返回带身份的 raw output；action adapter 恢复物理语义；scheduler 决定 freshness、chunk 和 deadline；controller 接受 setpoint 并返回 ack/actual state。Logger 只旁路记录，supervisor 管理 lifecycle，独立 safety plane 可以 veto 和 stop，但不依赖 policy 进程存活。

握手采用双向 capability exchange。Client 提交 bundle/contract、robot、camera roles、action mode、controller、clock 和 protocol versions；server 回显其加载的 artifact hashes、supported shapes/profiles、precision、sampling、limits ownership 和 expiry。逐字段一致后才建立 session。可迁移差异必须有已版本化 adapter 和 golden test；未知、过期或只在字符串上相近的版本默认拒绝。

Liveness 只证明进程响应，readiness 证明 artifact 已加载且下游连接成立，functional readiness 还要求 warm-up、golden vector、clock sync、queue、adapter 和 controller dry handshake 通过。HTTP 200、GPU 可见或模型文件存在都不够。状态变化以事件发布，client 在每次 session 和 release 切换后重新确认；ready 失效会阻止新 dispatch，而不是继续消费缓存结果。

Lifecycle 至少包含 created、loading、warming、ready、serving、draining、stopped、failed 与 quarantined。draining 不接收新请求，等待或作废在途工作；failed 不能自行跳回 serving；quarantined bundle 需要新批准。故障域按 sensor/client、network、server/engine、adapter、scheduler、controller、telemetry 与 safety 划分，每个域有检测、隔离、降级和 owner，避免一个进程重启清除全部证据。

实时类别由失败语义决定：hard deadline miss 不可接受；firm 迟到结果无价值且应丢弃；soft 迟到会退化但可记录处理。VLA service 通常不应承担硬实时 servo，controller 与安全回路保留确定性边界。所有预算以最坏允许路径和 tail measurement 验收，不以平均吞吐命名“实时”。

部署身份需要端到端传播。capture event、inference request、action candidate、scheduler decision、controller command 和 ack 都携带 deployment/bundle/contract/session epoch；任何一个节点解析到不同值就拒绝。只在 server 日志打印版本不够，因为 client、adapter 或 controller binding 可能独立更新。发布审计应从任一 command 反向查到完整 bundle，也能从 bundle 查到它产生过的全部 session。

时钟基础设施作为独立依赖验收：记录 clock source、monotonic/wall-clock 关系、跨主机同步方法、offset、uncertainty、resync 和 leap/step 处理。预算计算使用单调时钟，跨主机 trace 使用带不确定性的转换。故意注入 offset、drift、重启和乱序，确认系统会扩大 uncertainty、拒绝精确 latency claim 或进入降级，而不是产生负延迟或把旧响应当新。

故障注入覆盖每个 fault domain：sensor 卡住、client OOM、network partition、server crash、GPU reset、adapter schema mismatch、scheduler starvation、controller reject、logger 磁盘满、安全 heartbeat 丢失和配置 registry 不可用。对每个故障预注册 detection signal、最大检测时间、允许在途动作、隔离范围、fallback 与恢复 authority。共同进程或主机故障还要验证是否会同时失去 telemetry 和 stop channel。

Lifecycle 恢复不能默认回到 serving。failed 之后重新 loading，重新解析 bundle、建立下游连接、warm 全部 profile、运行 golden/functional probe 并创建新 session epoch；旧 request/response/queue 全部失效。若 supervisor 频繁重启形成 crash loop，达到预算后 quarantine 并请求人工。恢复耗时、丢弃工作和 controller 处置进入 availability 结果，而不是只报服务 uptime。

权限按角色最小化：发布系统可以切换 approved bundle，但不能改内容；policy server 可读 artifact，不能批准自身；client 可发 observation，不能绕过 adapter 直接提交命令；scheduler 可拒绝/过期 action，不能修改安全阈值；logger 无控制权限。证书、token 与地址不进入 bundle 示例或网页，真实系统只记录引用和轮换状态。

Bundle schema migration 要有 source/target version、字段映射、默认值、不可逆项和验证 fixture。增加可选 telemetry 字段可能向前兼容，改变 camera role、Action ABI、normalization 或 controller binding 则通常需要新 major version。Migrator 只能转换明确语义；遇到 unknown 字段或失去信息时拒绝。迁移后的 bundle 获取新 hash，不能沿用原身份。

部署审阅使用 BOM（bill of materials）列出每个 artifact 的来源、license、builder、签名、hash、依赖和 vulnerability/compatibility 状态。签名只证明来源与完整性，不证明行为安全；仍需 functional gates。Registry 禁止可变 tag 作为批准依据，tag 只指向不可变 digest，并保存变更审计。

拓扑图还应标出权限与数据分类：raw image、instruction、state、action、logs 分别能否跨主机、保存多久、谁可访问。Remote service 的 TLS/auth 不等于数据用途已批准；本地 sidecar 也可能把敏感媒体写入临时目录。Privacy incident 与控制 incident 使用关联但不同的响应流程。

Fault budget 限制单位时间允许 restart、retry、fallback 与 rollback 次数。频繁暂态失败即使每次恢复，也会扩大 stale 与状态错位风险；超过预算进入 degraded/quarantine。预算重置由稳定窗口或人工授权触发，不随进程重启清零。Availability 报告同时给正常 serving、degraded、not_ready、rollback 和 safe-stop 时间。

输入门禁

顺序：

schema → session → timestamp → freshness → camera roles → calibration → shape/dtype/range → finite/state limits → history/mask → prompt → stats/processor hash → serialize

失败产生结构化 reason，不调用模型。输入门禁与物理安全判定不同。

Capture 在读取设备数据的最早可控点写硬件或单调时间戳、sequence、device/camera role、calibration 和 acquisition status。到达进程的时间另记，不能用 receive time 冒充曝光时间。多相机组装定义容许 skew、选择 nearest/latest 的规则、缺帧与重复帧处理；组装后的 observation 具有新的 version，并保留每个 constituent ID。

相机顺序来自版本化 semantic role registry，而不是字典、USB 枚举或 topic 发现顺序。每个 role 绑定内外参、分辨率、crop 区域、颜色空间与镜像/旋转。重启、热插拔或 calibration 更新后必须重新握手。若模型要求 wrist/front 两路而其中一路缺失，按 contract mask、降级或拒绝；不得用另一相机悄悄填槽。

图像 preprocessing 固定 decode、颜色、range、dtype、crop、resize、interpolation、aspect ratio、padding、normalization 与布局顺序，并用同一 golden image 比较训练/评测/deployment 输出 hash 或容差。硬件 decoder、GPU resize 或 fused kernel 都视为实现变体。视觉上相似不证明张量 parity；EXIF、alpha、压缩、BGR/RGB 和 0–1/0–255 错误需要专门反例。

状态向量保存字段名、语义、frame、unit、order、rate、timestamp、validity 与 missing mask；不同本体通过显式 adapter，而不是按长度截断或补零。gripper、base、joint、force/torque 和 proprio 的参考零点要与 Action ABI 协调。history 窗口定义 spacing、采样/插值、重复、padding、reset 和 action history；episode 切换必须清除旧帧与 recurrent cache。

Prompt 模板绑定 tokenizer、special token、role、task 字符串、占位符和语言规范化。自由文本经长度、编码、允许字段和隐私门禁；server 不自行改写 client prompt。若 task/subgoal 来源不同，分别记录 authority 与 version。prompt change 会改变 policy input，因此需要新 contract 或明确兼容版本，不能当作 UI 文案更新。

Normalization asset 绑定数据 release、robot/embodiment、字段、维度、顺序、统计方法、mask、clipping 与 hash。Client 和 server 只能有一个权威归一化 owner，防止双重处理；action stats 与 observation stats 分开。选择到形状相同但本体不同的 key 必须因 identity mismatch 失败。输入门禁最后检查 schema、shape、finite、range、mask、age 与 contract hash，再允许推理。

训练—部署 parity 应由 fixture 集证明，而不是 README 约定。Fixture 覆盖每个相机 role、状态字段、language、history 长度、missing modality、边界 range 与 reset；保存 raw input、期望中间张量、mask、prompt tokens 和 processor output。对涉及随机 crop/augmentation 的训练路径，部署明确关闭或固定推理规则。实现更新后逐层比较，快速定位差异发生在 decode、crop、normalize 还是拼接。

数据质量状态不能只用 present/absent。图像可能 frozen、over/under-exposed、checksum 重复或时间跳变；状态可能 stale、out-of-range、sensor fault 或 frame unavailable；language 可能为空、截断或编码失败。每种 quality code 进入 mask、拒绝或降级策略，并记录计数。用全零/NaN 隐式表达故障会让模型把错误当普通观测，必须禁止。

多传感同步需区分 capture-time 与 semantic consistency。即使 timestamp 接近，移动相机和机器人状态也可能因 rolling shutter、曝光或 transport 造成几何错位；必要时使用插值/外推，但记录方法、误差和最大跨度。超出范围时重新采集或拒绝，不用最近值无限延长。高速 controller feedback 与低频视觉历史分别采样，不能强行认为同一步 index 同时发生。

Preprocess owner 的 trust boundary 决定 wire schema。若 client 发送 tensor，server 仍验证 dtype/shape/range/processor hash；若发送 raw media，server 验证编码和 metadata 并运行冻结 processor；分层模式为每个中间制品定义 canonical representation。Compression 质量、chroma subsampling 和硬件 decoder 会改变输入，带宽优化也需作为 contract 变更进行 parity 测试。

Normalization 更新遵循 lineage：新数据 release 生成新 stats asset，列出估计样本、过滤、per-field 规则与适用本体；checkpoint 明确依赖哪个 asset。部署不能为“适应当前机器人”在线重算 stats，否则 evaluation object 已改变。统计缺失或 field 不适用通过 mask/identity rule 表达，默认均值零方差一也必须是显式批准的语义。

输入拒绝报告不泄露原始敏感内容，但保留字段、reason、observed metadata、expected contract、trace 和 remediation。连续同类拒绝触发 sensor/client incident，而不是让 server 日志刷屏；采样日志仍能估计频率。输入门禁失败不调用模型，也不产生可执行 fallback action，除非 controller/safety contract 独立规定。

Observation schema 变更采用 producer/consumer compatibility matrix。先部署能同时读取旧/新版本的 consumer，再切 producer，最后移除旧字段；若是强契约变更则使用新 session/bundle 并禁止混流。滚动升级期间每条 message 带 schema version，adapter 不通过“字段存在”猜版本。回滚还要保证旧 consumer 能读取保留数据。

Golden fixture 需要可移植：原始媒体和状态有明确编码、endianness、dtype、metadata 与 hash，期望张量保存容差或规范化摘要。不同平台的 JPEG、resize、floating point 允许的差异预注册；超差时定位算子，而不是扩大到能通过。Fixture 不含真实敏感场景，可用合成图、标定图和脱敏 trace。

History 组装测试覆盖正常等间隔、丢帧、重复、乱序、跨 reset、长 gap 和不同 rate；验证 mask、padding、interpolation 和 newest/oldest order。模型看到的动作历史也要绑定 actually accepted/executed，而不是 raw candidate。若 controller 拒绝或修改命令，历史回填规则明确，否则策略的自回归状态与真实机器人分叉。

输入契约监控关注分布和质量但不在线改变 preprocessing。按 camera/state/task 切片统计 missing、stale、range、brightness、compression、mask 和 rejection；漂移超过预注册边界触发调查或 stop，不自动重算 normalization。任何 adaptive preprocess 都是新算法组件，需要离线和闭环验证，不能由运维脚本临时开启。

短 benchmark 不足以发现热降频；至少有与目标任务持续时间相符的 soak test。

本地、on-device 与 remote 只是放置方式，不改变 contract。Remote 额外记录 encode、upload、server queue、infer、download、reconnect 与 clock conversion；on-device 也要记录共享 GPU/CPU、热限制和进程调度。比较路线时统一输入、precision、engine、sampling、warm-up 和负载，否则不能把位置差异归因为网络或模型。

服务请求至少携带 session_id、request_id、sequence、observation_id/version/timestamp、contract/bundle hash、deadline、priority 和 trace_id；响应回显这些字段以及 server receive/start/end、engine/profile、sampling config、output hash、expiry 和 status。Client 对未知 session、重复、乱序、过期或 contract mismatch 的 response fail closed。服务端 status=ok 仅表示计算完成，不授权动作执行。

推理请求可通过 request_id 幂等去重，动作提交不可因网络 retry 无条件重放。Client timeout 后的 late response 仍可能到达，需要 tombstone/expiry；server 重连后不能重用旧 session sequence。若要安全重试推理，明确是否复用相同 observation、seed/cache 以及它对 stochastic output 的影响。任何自动 retry 都计入 latency 和 deadline。

并发隔离按 robot/session 保留 queue、cache、normalization 与 state，防止跨机器人串线。Dynamic batching 要有最大等待、deadline-aware admission 和 per-session 顺序；负载超限时拒绝或降级，而不是无界收集 batch。多租户 GPU 的 memory pressure、kernel contention 与 priority inversion 进入 p99 测试。吞吐提升不能牺牲单机器人 deadline 或故障隔离。

Sampling/denoising 记录算法、steps、schedule、seed、precision、guidance 与 early-exit；减少 steps 是新 policy artifact，不只是服务参数。Warm-up 覆盖全部允许 shape/profile、history 和 batch；报告冷启动、首次 compile、profile switch、cache eviction 与稳态。若 runtime 在生产中会重启或改变 shape，冷路径必须进入 availability 和 canary，而不能从报告删除。

Compile/engine 绑定源码 graph、weights、opset、builder flags、optimization profile、runtime/driver/GPU 和 calibration hash。生成后做静态 op/schema、golden vector、离线 replay 和闭环 parity；不支持 op 的 fallback kernel 与 graph break 进入性能和语义报告。engine 不跨未知硬件复用，启动时重新校验兼容性和内容摘要。

量化分别报告权重/激活 dtype、per-tensor/channel、校准 release、quant/dequant 边界、溢出与饱和。比较不仅看平均张量误差，还看 action dimension、rare/safety slice、closed-loop、tail latency、memory 与功耗。Batch、KV/feature cache 和复用预处理同样需要版本、key、TTL、隔离和 invalidation。资源遥测包含 CPU/GPU/RAM/VRAM、功率、温度、clock、throttle、OOM 和其他 workload。

Admission control 在入队前估计 deadline slack、profile、预计 service time、当前 queue、memory 和 session priority。无法在 deadline 内完成的请求立即拒绝或进入已批准降级，避免浪费算力后返回过期动作。估计器本身要校准；低估造成 miss，高估造成不必要拒绝，两者都进指标。不同机器人共享服务时设置 per-session 配额，防止一个高频 client 饿死其他 session。

Performance 测量分空载、目标负载、峰值与故障恢复。每种负载固定并发、输入 shape、history、sampling steps、precision、cache、batch、hardware power mode 与持续时间；同时报告吞吐和 per-request latency 分布。短暂 burst 与持续 soak 分开，warm steady state 不能替代重启或 thermal steady state。任何自动调频、MIG/容器限制和 colocated workload 都记录。

优化决策用 Pareto 门禁：closed-loop quality/safety 不退化、p99/deadline 达标、memory/power/temperature 可接受，再比较吞吐。若量化降低平均延迟却增加 rare action error 或 cold p99，不能凭单一均值通过。每种 engine/precision 作为独立 candidate，使用与评测相同的 replay/slice 和明确容差；容差不应把离散 action route、NaN、clipping 或 sign change 当小数值误差。

Compile cache 与 engine registry 绑定 graph/config/input profile/hardware/runtime hash。cache hit 前完整核验，构建中断的临时 artifact 不可见，多个 builder 并发使用原子发布。profile miss 可以选择显式 fallback engine 或拒绝，不能在实时请求中无预算编译。recompile、kernel autotune 和 memory pool growth 事件进入冷路径指标。

Cache key 必须包含所有影响输出的输入和版本：session/observation、history、prompt、task/subgoal、checkpoint、processor、sampling 和 mode。跨 robot/session 禁止共享状态型 cache；只读公共视觉特征若允许共享也需证明数据隔离和 invalidation。Cache hit/miss 分开评测，命中不能掩盖首次任务或状态变化时的最坏延迟。

资源耗尽处理预先排序：拒绝低优先级新请求、停止 batching、释放可回收 cache、切换验证过的轻量 candidate 或进入控制层 fallback。不能临时降低 sampling、precision 或分辨率而仍声称同一 bundle。OOM、driver reset、thermal throttle 后重新初始化形成新 lifecycle epoch，并重新通过 readiness。

性能回归以同一 hardware/runtime/load fixture 比较 LKG 和 candidate，并同时测 warm/cold、single/target concurrency、cache hit/miss 与 soak。报告绝对分布和 paired delta，而不只给百分比加速。若 candidate 改变 output quality、sampling steps 或输入分辨率，性能与行为变更分别标出，不能称为等价优化。

端到端 budget 需要 reserve：controller、network 和 safety event 的变异不能把全部 slack 分给模型。Admission 使用保守预测并随 telemetry 校准，模型优化只消费其 own segment。若某段经常借用其他段余量，说明 budget 分配失真，应调整协议而不是在总时延偶尔达标时忽略。

资源隔离验证 CPU affinity、thread priority、GPU stream/MIG、memory lock/pool、NUMA、network class 和 disk/logger worker。配置只是意图，实际 trace 要证明关键 callback 没被 background job、GC、page fault、视频编码或 batch collector 长时间阻塞。无法保证时按 soft/firm real-time 报告，不虚构 hard guarantee。

功耗与热结果绑定 ambient、fan/cooling、power cap、battery、clock 与持续时长。edge 设备在短 benchmark 后可能降频，remote GPU 也可能受共享负载。soak 中同时监控 latency、error、OOM、throttle 和 output parity；热降频触发 admission/fallback 的规则进入 canary，而不是只在实验室备注。

动作路径采用不可重排的阶段，每一阶段产生输入/输出摘要、版本和拒绝原因。Raw gate 先核对 response/session/request/observation/contract、shape、dtype、finite、range、chunk length 与 mask；错误不能靠 clipping 修复。decode 只解释表示，denormalize 使用绑定 stats；两步 owner 清楚，避免 token/continuous、normalized/physical 混淆。

Delta 动作必须绑定 reference state 与 timestamp。reference 可以是 observation state、last accepted setpoint 或 actual controller feedback，但只能选择 contract 声明的一种；晚到 response 若 reference 已变化，应重新基准化有明确算法，否则拒绝。Absolute target 的 stale 风险不同，保持上一个 absolute setpoint 也不是重放 delta，因此 fallback 按动作语义分别定义。

Frame/unit 转换使用版本化 transform tree 与 calibration，记录 source/target frame、时间、插值和可用性。旋转表示转换要处理 quaternion 顺序、归一、符号等价、Euler branch 和 6D/axis-angle 约定；位置/角度单位不得靠量级猜。任何 transform stale、缺失或跨时间不可用都停止该 action，而不是使用上次矩阵。

Joint mapping 显式列模型维度到机器人 joint 名、顺序、sign、offset、coupling、mimic 与 disabled axis；gripper 单独声明宽度/关节/开合标量、方向和范围。跨本体 adapter 绑定 robot identity。形状相同不证明映射正确，golden vector 应覆盖单轴、边界、全零和已知姿态，实际 controller feedback 用于检测 sign/order 错误。

Deterministic limits 检查 position、velocity、acceleration、jerk、torque/force、workspace、self-collision proxy 与 command delta，但它们不是完整安全系统。限幅发生要记录原值、规则和差异；频繁 clipping 视为 policy/contract failure，不通过静默裁剪维持 success。独立 safety plane 可施加更强 veto，具体阈值由下一页批准。

Rate conversion 明确 hold、interpolate、resample、low-pass、chunk overlap 与 command timestamp。插值必须适配 position/rotation/control mode，不能对 torque 或 delta 任意平滑。Scheduler 只提交未过期、连续且已验证的 setpoint；controller accept ack 包含 command ID 与接收时间，actual execution/feedback 另记。ack 不等于动作完成，也不等于任务成功。

动作链需要双向 golden fixture。正向从已知 raw output 推到预期 setpoint，反向从 controller field 追到模型维度、stats 和 frame；对每个 joint/gripper 逐轴注入正负小量、边界和非法值。Fixture 还覆盖 chunk index、mask、rotation 接近奇异、reference state 变化、transform unavailable 与 late response，确保错误在预期阶段被拒绝。

Raw output 的合法范围与物理限制分开。模型 logits/token/normalized action 先按表示契约检查；decode 后的物理 action 再按本体和 controller contract 检查；独立 safety plane 最后作风险 veto。若 raw 值越界，不能用物理 clipping 伪装成功；若安全 veto，保留原 candidate 和原因但绝不继续 dispatch。

转换中的数值误差要有预算与属性测试。位置单位换算应可逆，rotation 投影结果正交且 determinant 正，quaternion 归一并处理符号等价，joint mapping 一一对应或显式 coupled。对随机合法样本执行 round-trip，对非法样本确认 fail closed。硬件相关 calibration 不嵌入代码常量，而由有 hash、有效期和 robot identity 的 bundle 提供。

Chunk continuity 不等于逐点平滑。系统检查上一个 committed setpoint 与新 chunk 首点的 position/velocity/acceleration/rotation jump，并按 controller 能力选择拒绝、blend、replan 或安全 hold。Blend 本身改变 policy output，需有时域、约束与验证；不能在日志里只保留 blended action 而丢掉原始 candidate。

Controller submission 是带期限的事务：prepare/accept/execute/cancel/complete 或 controller 支持的等价状态。Client 确认 command ID、validity、preemption、resource ownership 和 current controller mode；accept/reject 必须可关联。若 ack 丢失，查询状态或走安全协议，不能盲目 resend。controller mode 在 position/velocity/torque 间变化需新 binding 与重新验证。

实际执行反馈包含 commanded、accepted、executed、tracking error、limit/safety intervention、hardware fault 和 timestamp。评测把 policy intent 与 controller-modified/actual motion 分开，避免将 controller rescue 归为模型能力。动作日志按隐私与体积策略保存，但至少保留可重建拒绝、修改和终止的摘要与 hash。

Controller transaction 需要处理四种不确定：request 未到、到达但 ack 丢、accept 后执行失败、cancel 与 complete 竞争。每种都规定查询、幂等、timeout 和安全动作。没有 exactly-once 保证时，command ID 与 controller state query 用于避免重复；无法确认是否执行的命令进入 uncertain execution，禁止直接发送补偿动作。

Preemption 必须在 controller 能支持的边界发生。Trajectory controller 可能接受整段、实时 setpoint 可能逐周期更新、action interface 可反馈进度；scheduler 根据实际接口声明 committed frontier。cancel acknowledged 前，资源和 reference state 不交给新 chunk。若设备只支持 best-effort cancel，风险和最长残留时域进入 contract。

Rate conversion 的采样定理不是充分条件。低频 policy 经插值到高频 controller 仍可能违反动力学、jerk 或接触约束；高频 candidate 降采样也可能漏事件。转换后在 controller domain 重新检查约束，并以 actual feedback 验证 tracking。temporal ensemble/overlap 若融合多个预测，要保留每个来源 observation 与权重。

Action audit 对原始、decoded、denormalized、transformed、mapped、limited、resampled、submitted 和 executed 分层保存摘要。为了体积可用 hash、统计与触发窗口，但任何 reject/clamp/safety incident 能展开。这样既能查明模型、adapter 还是 controller 改变了动作，也避免只看最终执行轨迹误判 policy 输出。

同步/异步调度、队列与 Deadline

同步模式

时序：

observe → infer → validate → enqueue/execute → next observation

优点：语义简单、response 与 observation 容易对应。风险：推理阻塞造成 stop-and-go。chunked sync 可在一次推理后执行多个 setpoint，但仍需 fresh observation/replan 规则。

异步模式

时序：

client executes current committed actions || captures latest observation || server predicts next chunk || scheduler merges/switches at commit boundary

异步不消除 latency，只把 inference 与 execution 重叠。需要额外字段：

  • observation used；
  • inference start/end；
  • predicted chunk start index/time；
  • already executed prefix；
  • committed prefix；
  • uncommitted suffix；
  • overlap；
  • switch index；
  • queue state；
  • valid horizon；
  • merge/replace method。

RTC 边界

公共页只说明 RTC 是一种针对 Diffusion/Flow action chunk 的异步 inpainting/conditioning 方法，可减少 chunk 边界不连续；算法的 soft mask、VJP、training-time variant、超参和实验留在 RTC 专题。

本页要求所有 RTC 实例仍满足：

  • same contract；
  • committed prefix 不被改写；
  • latency estimate/actual 区分；
  • queue/observation timestamps；
  • algorithm/version；
  • fallback；
  • matched evaluation。

普通 async queue、SmolVLA queue aggregation、RTC 与 Harness Flash Mode 可组合或互斥，不能混称一个算法。

Observation queue

典型控制目标是 latest useful observation，而不是保留所有旧帧：

  • bounded size；
  • enqueue timestamp；
  • latest-only/coalescing policy；
  • required history exception；
  • dropped reason；
  • must-process semantics；
  • dedup/similarity filter；
  • dynamic scene caveat；
  • age at inference start；
  • queue wait；
  • starvation detection。

丢旧观测必须可见，不能以“成功处理最新”掩盖过载。

Action queue

字段：

  • chunk ID；
  • source observation/request；
  • chunk generation time；
  • valid range；
  • action indices；
  • committed prefix；
  • execution cursor；
  • overlap；
  • controller mode；
  • contract/deployment；
  • continuity info；
  • stop/termination；
  • per-action timestamp。

invariants：

  • capacity bounded；
  • monotonic cursor；
  • no duplicate；
  • no cross-session；
  • no expired action；
  • version switch purge；
  • never overwrite committed action silently；
  • queue mutation under defined synchronization；
  • snapshot for logs is non-blocking。

Queue 状态机

EMPTY → FILLING → READY → CONSUMING → LOW_WATER → REFILLING → {STARVED, STALE, OVERFLOW, VERSION_MISMATCH, STOPPING}

每个异常态有 detector、metric、owner、fallback request 和 terminal evidence。LOW_WATER threshold 按 time-to-empty 而不只按 action count；不同 action rate 下 count 不可比。

Deadline 模型

对同步 request：

D_request = latest useful actuation time - request send time

对异步 refill：

D_refill = predicted queue exhaustion time - safety margin - current time

全链预算：

T_capture + T_sync + T_preprocess + T_serialize_up + T_network_up + T_queue + T_infer + T_postprocess + T_network_down + T_validate + T_schedule + T_controller_accept

每段记录 p50/p95/p99/max 和 miss；分段之和只在同一 trace 上计算，不把各自独立 p99 相加冒充全链 p99。

Freshness

response 即使在 request deadline 内，也可能基于过旧观测。必须同时检查：

  • observation age at infer；
  • observation age at dispatch；
  • response age；
  • action valid_until；
  • task/subtask version；
  • scene/reset epoch；
  • controller reference state；
  • safety state version。

freshness 是语义条件，不只是网络 TTL。

Backpressure 与 overload

策略可选：

  • reject new request；
  • latest-only observation；
  • drop oldest not-started observation；
  • cancel obsolete inference if runtime supports；
  • reserve per-robot capacity；
  • disable batching；
  • degrade model/steps only if prevalidated；
  • switch to approved local fallback；
  • controlled stop。

禁止：

  • unbounded queue；
  • 静默增加 execution horizon；
  • 静默降低 camera/history；
  • 自动切换未验证 checkpoint；
  • 把 late response 继续排队。

Overflow、Underflow 与 Starvation

  • observation overflow：输入快于处理；
  • action overflow：产出/网络返回快于消费或重复；
  • queue underflow：没有可执行 action；
  • starvation：长期/refill 未赶上；
  • stale-but-nonempty：队列有动作但全部过期；
  • partial chunk：response 不足 horizon；
  • controller reject：队列有动作但无法提交。

每类单独 metric，不用 queue_size=0 覆盖全部。

Timeout 与 fallback

timeout 分层：

  • capture/sync；
  • request connect/send；
  • server queue；
  • inference；
  • response；
  • action validation；
  • controller ack；
  • execution/tracking；
  • heartbeat/liveliness。

fallback 是接口请求，不在公共页给真实动作：

  • reject and hold approved state；
  • continue committed prefix if still valid；
  • use prevalidated local policy；
  • reduce capability/mode；
  • controlled stop；
  • request human takeover。

具体选择需 safety contract。超时重试前先判定 session、deadline、幂等和动作 authority。

ROS 2 QoS/Executor 检查

如果使用 ROS 2，必须固定：

  • RMW/vendor/version；
  • topic/service/action；
  • history/depth；
  • reliability；
  • durability；
  • deadline；
  • lifespan；
  • liveliness/lease；
  • compatibility events；
  • executor type；
  • callback groups；
  • thread count/affinity/priority；
  • queue behavior；
  • wait set/LET if used；
  • allocation/logging in RT path。

default QoS/Executor 不是稳定跨版本合同。reliable 也不能自动解决 stale 数据。

同步模式按 Observe→Infer→Validate→Dispatch→Ack 串行，易对齐但可能让 controller 等待；异步模式允许 capture、infer 和 execute 重叠，却需要显式处理 stale observation、在途请求和 chunk continuity。切换模式会改变状态分布与错误模式，必须作为新 runtime protocol 重评，不能只改 boolean flag。

RTC 若用于 runtime 只提供 action chunk 调和与连续性算法，其训练假设、mask、VJP/inpainting 和适用模型留在专题页。通用 scheduler 只消费声明的 candidate chunks、committed prefix 和 continuity evidence，不假设任意 VLA 支持 RTC。没有对应 adapter 或验证时退回冻结的普通 chunk 策略。

Observation queue 通常保新丢旧，但必须保留必需 history、event 和多传感同步组；action queue 不能简单 last-write-wins，因为 committed commands 可能已被 controller 接受。每个元素带 source observation、generation time、expiry、bundle、sequence、chunk index 和 status。容量、high/low watermark、drop/coalesce/reject/block 策略与 owner 写入 contract。

Queue 状态至少有 empty、ready、committed、superseded、expired、cancelled、acked 与 failed。只允许有限转换；duplicate/out-of-order 由 sequence 和 idempotency key 识别，跨 session 一律拒绝。切换 chunk 时定义 boundary、blend/hold、未提交 suffix 处置与 continuity check，旧 bundle chunk 不能跨发布边界继续执行。

Deadline 由 capture timestamp 到 controller accept 的端到端 budget，按 sync/assemble、preprocess、transport、queue、infer、postprocess、schedule 分配。每段记录 start/end 和 clock；总 deadline 不是各段平均相加。Freshness 同时看 observation age at infer/actuation、action generation age 和 reference-state age，任何一项超限都可能使动作失效。

Backpressure 从下游反馈 queue watermarks、deadline slack、controller availability 与 resource pressure，触发降采样、拒绝新请求、缩短可替换工作或进入批准 fallback；不能继续堆积。Overflow、underflow、starvation 分开：无队列空间、无可用动作、持续得不到新动作的处理不同。每种状态都有最大持续时间和 escalation。

Timeout 不自动 retry 动作。可重试 inference、hold、stop、retreat 或切换 last-known-good 的选择取决于 absolute/delta、controller 和安全批准。ROS 2 使用时逐 topic 固定 QoS history/depth/reliability/deadline/lifespan、callback group、Executor、priority 和 memory；“reliable”重传旧数据可能比 best-effort 丢旧更危险，必须按语义测量。

队列不变量可机器检查：同一 session sequence 单调；一个 action element 最多进入一次 committed；expired/cancelled/superseded 永不恢复 ready；ack 只能引用已 dispatch command；跨 bundle/session 不连接 chunk；queue horizon 不超过 freshness 和安全预算。状态转换写 event log，用 property-based trace 验证重复、乱序和并发事件不会破坏这些不变量。

异步切换使用明确 cutover。新 response 可替换的只有未 committed suffix；已经提交 controller 的 prefix 通过 cancel/preempt 协议处理。若新 chunk 首点不连续，scheduler 不在未知条件下 hard switch。来自旧 observation 但更早返回和来自新 observation 但更晚返回分别按 observation version 与 expiry 裁决，不按 arrival time 猜“最新”。

Queue horizon 以 wall-clock 和动作步数同时表示。长 chunk 可覆盖推理抖动，却增加 open-loop 和 stale exposure；短 chunk 新鲜但易 starvation。通过 replay/simulation 对 inference tail、network loss、controller rate 和 replan event 扫描容量与 watermarks，选择满足任务与安全预算的点。页面不提供通用长度或频率。

Deadline miss 分析区分 cause：capture/sync、preprocess、transport、admission/queue、infer、postprocess、scheduler、controller ack 或 clock uncertainty。只把 miss 归给 model 会误导优化。每个 miss 记录 slack、queue depth、resource/thermal、profile/cache、fallback 和结果；按负载与 session 切片报告 p99 和 consecutive misses。

Overload 测试逐步增加 request rate、robot sessions、image size/history、sampling steps、logging 和并发 workload，观察 admission、queue、stale reject、miss、OOM 与恢复。系统应有可预测 knee 和有界失败，不能先积压后整体雪崩。恢复负载后 queue、cache、session 与 readiness 回到一致状态，不能继续执行 overload 期间积压动作。

Fallback 也是版本化控制路径。安全 hold、停止、撤退、低频本地 policy 或 last-known-good 各有触发、Action ABI、controller mode、最长持续、退出和 owner。未经评测的 fallback 不因名字“保守”而安全。fallback 触发后保留原 incident，且主 policy 恢复必须经过 hysteresis、ready probe 和新 session，而非下一次 heartbeat 自动切回。

队列模型要区分工作队列与时间序列缓冲。Observation history 可能保留窗口，待推理请求只需最新合格 bundle；action candidate 可有多 chunk，但 committed frontier 单调。将二者都实现为普通 FIFO 会保留过期 observation，也会在恢复后播放旧 action。数据结构和状态机应直接表达各自语义。

可用确定性事件表测试 scheduler：给定 capture、infer complete、deadline、replan、cancel、ack 与 bundle switch 的排序，期望唯一 transition 与 command 序列。对同 timestamp 事件定义 tie-break，例如 safety/cancel 先于 dispatch，new session 先作废旧 response。Property test 随机排列事件，确认不产生跨 session、重复 commit 或 expiry 后 dispatch。

连续 miss 和单次 outlier 的处理不同。一个孤立 deadline miss 可丢弃并记录；连续 miss 表明负载或服务退化，应降低 admission、触发 LKG/fallback 或 stop。窗口、hysteresis 和 recovery 条件预注册，避免在阈值附近振荡。恢复时先清除 stale 队列并建立新 observation，不用旧 backlog 证明吞吐恢复。

Queue telemetry 同时记录瞬时 depth、age distribution、oldest/newest ID、drop/reject/coalesce、service time 与 slack。只看平均 depth 会漏掉少量极旧元素；只看 drop count 会误把保新策略当故障。Dashboard 按 session/bundle/load 切片，告警引用 raw event IDs，便于 incident 后重放。

安全页决定风险、阈值、拒绝、接管、独立控制器和最终安全状态。

验证阶梯逐层冻结输入和通过条件。Static 检查 manifest、schema、hash、unsupported op 与 dependency；golden vector 比较预处理、模型输出和后处理；replay 用真实记录验证全软件路径；SIL 接完整服务与控制软件但无硬件；HIL 验证真实 I/O、时序和 controller；shadow 旁路计算不下发；controlled canary 才在安全批准范围内产生有限动作。

每层失败不会被下一层成功覆盖。Golden parity 可设置数值容差但还要检查离散 route、clip 和 NaN；replay 保持时钟和队列语义；SIL 注入网络、queue、restart 和 overload；HIL 检查 driver、calibration 与 watchdog；shadow 测观察分布和 deadline；canary 有隔离区域、限速、人工接管、trial budget 与 stop rule。当前页面只设计这些协议，不执行任何一层。

Trace 以同一 trace/session/request/observation/action/command ID 串联 capture、assemble、preprocess、send、queue、infer、response、validate、dispatch、ack 和 feedback。Metrics 至少包含各段 p50/p95/p99/max、jitter、deadline miss、queue depth/drop、stale reject、invalid output、controller reject、resource、power、temperature、restart 与 rollback。聚合保留 worst slice 与负载条件。

日志分实时摘要和异步详细记录。实时路径只写有界、预分配或非阻塞事件；图像/视频、序列化和上传在隔离 worker 中完成并受 backpressure。隐私字段、prompt、人员图像、设备标识和内部地址按最小化、权限、保留期与 takedown 管理。Telemetry 故障不能阻塞控制，也不能让关键 audit event 静默丢失。

Alert 只建议或触发预批准自动化：not_ready、contract mismatch、deadline/staleness、queue、invalid action、controller reject、thermal/throttle、safety signal 和 evidence loss 分级。自动重启若会清空状态、改变 engine 或产生动作重放，必须进入状态机；高风险 fallback、解除 stop 和继续 canary 需要明确 authority，不能由监控脚本自行批准。

发布流程 staged→validated→approved→active，以原子指针切换完整 bundle。切换前 drain/abort 在途请求、确认 controller 边界、清空旧 observation/action queue、reset history/cache/memory、重新握手并运行最小探针。last-known-good 预先验证可加载。Rollback 恢复 processor、stats、adapter、engine、protocol、scheduler 和 controller binding，不只换权重；失败版本产生的数据隔离。

交给安全页的信号包括 watchdog heartbeat、ready/healthy、contract mismatch、observation/action stale、invalid output、limit/clipping、queue starvation、timeout、controller fault、operator takeover、rollback 和 incident trace。安全页决定物理限制、hold/stop/retreat、独立 supervisor 与再启动授权；本页保证信号有身份、时间和可靠传递，但不自行设定真实阈值。

Evidence bundle 为每个 verification level 保存 protocol、environment、artifact hashes、输入集、原始 events、门禁、结果和 reviewer。Static/golden/replay 的通过只支持软件与契约结论；SIL/HIL/shadow/canary 分别列出未覆盖物理、安全和自主范围。not_run、not_applicable、failed 与 passed 分开，页面不能把未执行层显示成灰色通过。

Fault matrix 在 replay/SIL 注入 duplicate、reorder、delay、loss、queue full、engine slow、NaN、contract mismatch、restart 与 telemetry pressure；HIL 再验证真实 driver/controller/clock/power；shadow 对生产观察分布测 freshness 和 resource；canary 只覆盖批准 task/area/speed/session。每个 fault 有 expected transition，偏离即失败，而不是以最终“没撞”判通过。

Telemetry schema 自身版本化，consumer 不认识字段时不能丢关键 safety/deadline event。Metrics 指定 unit、clock、histogram buckets、cardinality 和 aggregation window，避免高基数 ID 压垮系统。Trace sampling 对 incident、reject、miss、rollback 全保留，对正常路径可采样；采样策略不得使 tail failure 消失。Dashboard 只是视图，原始 event ledger 是证据源。

Release 审批分 model、platform、controls、evaluation、safety 和 operations。每个角色只签其范围，批准事件引用 evidence bundle 和允许环境。Canary 未通过不能扩大；active 版本 immutable，配置 hot change 创建新 release。Registry 原子更新 active pointer，client 通过 epoch 观察切换，部分节点失败时保持旧 active 或整体回滚，不能形成无声明混合版本。

Rollback drill 在发布前从 registry 解析 LKG，验证 artifact 可用、兼容 target hardware、controller binding 和 safety interface；模拟切换、drain、queue clear、state reset、handshake、probe 和流量恢复，测量恢复时间。若新版本已改变 cache/memory/schema，坏版本产生的状态隔离并由 manifest 处理。rollback 失败时进入独立安全状态和人工响应。

完成定义要求从 controller command 反向重建 capture 与 bundle，也能从 incident 正向追踪 detection、fallback、rollback 和验证。若只有漂亮 latency 图而没有 raw trace、如果 response 无法关联 observation、或 LKG 依赖丢失，状态仍是 evidence-missing。没有目标硬件与真实负责人签署时，所有频率、阈值、端口和动作保持占位。

网页与模板通过静态审计只表示 deployment design ready，不表示系统已部署、已实时或已安全。后续真实实现必须在目标硬件上重新跑 parity、tail/soak、fault matrix、HIL/shadow/canary 与 rollback drill，并由下一页安全契约给出最终授权；结果以新 evidence release 回填，不能修改原设计记录冒充既有验证。

发布前进行双向可追溯审查：从 active pointer 解出每个 artifact、contract、approval 和 verification；从任一 command 追到 active epoch、request、observation、adapter 与 controller ack。若其中一条依赖运行目录、人工记忆或未版本化配置，发布门禁失败。环境变量和 feature flag 也必须展开到 deployment config hash。

Rollback drill 覆盖 server 仍活着但输出错误、server crash、network partition、controller reject 激增、thermal miss、telemetry 丢失和 safety signal。每种触发由不同 detector 发起，但切换遵循相同原子流程。Drill 测 detection、decision、drain、switch、probe 与恢复各段时间，并确认坏版本 action/state 不跨越边界。

Incident 包含影响 session/trial、first/last event、bundle、症状、cause confidence、safety/physical outcome、fallback/rollback、数据隔离和后续复核。未知 cause 允许保留，不能为了关闭工单选最像的模块。修复后以新 candidate 和故障复现集验证，不原地把 failed release 改回 approved。

Observability 自身有 SLO：关键 event 完整率、clock quality、trace join 成功率、metric drop、log queue age 和 storage availability。若无法证明关键 command 与 safety event 已记录，系统可以继续安全控制的范围由安全契约决定，但不得继续扩大 canary 或生成完整证据 claim。

最终完成记录列出所有未测硬件、冷路径、负载、故障、fallback 和 safety authorization。网页模板中的 placeholder、虚构 ID 与空阈值不会被转换成部署默认；实现者填入事实后重新生成 bundle/hash 和 evidence release。只有目标硬件上的全链 trace、故障注入、回滚演练与负责人签署齐全，才可称指定范围部署已验证。

上线评审应按一条完整 sample path 演算，而不只逐模块打勾。选择 normal、stale、missing sensor、slow inference、invalid output、controller reject、safety veto、bundle switch 和 rollback 九种场景，从 capture event 开始逐步写出 ID、timestamp、owner、queue state、decision 与终态。任何场景出现无 owner 的转换、无法关联的日志或依赖“系统通常会处理”的步骤，都回到契约修订。

配置漂移检测比较 registry 中批准的 deployment config 与进程实际 resolved config，包括环境变量、feature flags、QoS、thread/affinity、power mode、engine profile、sampling、queue 和 fallback。比较结果在 readiness 与周期审计中产生 hash；发现 drift 时根据字段重要性 not_ready、degraded 或 quarantine。不能让运维临时修改保留到下一次启动而没有版本事件。

可用性设计还要覆盖依赖失效：DNS/registry/auth、time sync、model store、telemetry store、controller service 和 safety channel 分别规定启动、运行中与恢复行为。控制路径不能因日志或模型仓库短暂不可用而无限阻塞，但若 contract、clock 或 safety authority 无法确认，则不能继续发新动作。依赖恢复后重新验证 identity 和 session，不假设旧连接仍可信。

Canary 比例不是唯一限制，还要限制 robot、task、workspace、速度、时间窗、并发 session、operator 与累计 action budget。扩大任一维度都需要上一阶段证据和批准。监控门禁按 success、reject、stale、deadline、queue、controller、safety、thermal 和 incident 分轴，平均成功不能抵消安全或时序越界。达到 stop 条件后自动收缩暴露面，但重新扩大必须人工或预授权流程确认。

Rollback 之后要验证“旧行为真的恢复”：加载 LKG hashes，确认 processor/stats/adapter/protocol/scheduler/controller binding 一致，queue/history/cache 已清，新的 session epoch 生效，golden probe 与最小闭环检查通过。只看到 server 重新 ready 不能结束 incident。坏版本期间采集的 observation、memory、cache、metrics 和训练候选数据按 lineage 隔离，避免污染后续 release。

每次发布最终形成 deployment evidence card：允许范围、bundle、目标硬件、real-time class、关键 rates、端到端 latency 与 freshness、资源/热边界、验证层级、fallback、LKG、safety interface、已知缺口和审批。卡片中 not_measured 与 unknown 保持原样，不用零或模型文档值填充；当硬件、driver、controller、site 或负载改变时，复用结论前重新评估适用范围。

完成状态至少区分 design_ready、static_verified、replay_verified、sil_verified、hil_verified、shadow_verified、canary_approved 和 active_approved。网页制作只能达到前两者中的文档层，不能自行提升真实系统状态。所有未关闭项有负责人、证据要求、过期时间与复核记录；例外到期自动失效，并阻止后续扩大部署范围。

运行班次交接不能只说“服务正常”。交接卡列 active bundle、session 数、控制器模式、最后一次健康探针、时钟质量、队列水位、最近 deadline miss、拒绝动作、fallback、温度功耗、未关闭 incident 与 LKG 可用性。接班者逐项确认，不从上一班次的口头描述推断状态；交接失败时停止扩大任务范围，并保留当时快照。

状态快照区分可恢复与必须清空的部分。模型权重、只读 processor 和批准配置可以恢复；observation history、在途请求、未提交动作 suffix、controller transaction、临时 cache 和 session capability 通常要按 manifest 丢弃或重建。恢复工具不得复制未知来源的内存镜像。每个状态字段声明 owner、序列化格式、bundle 兼容范围、过期条件和回滚处置。

维护与校准会改变系统身份。相机重装、工具更换、关节零点修正、gripper 磨损、controller 参数、驱动或固件升级都触发 compatibility review；即使模型文件不变，也可能需要新 calibration、adapter、golden fixture 与 HIL 证据。运维记录绑定设备身份和生效时间，使 incident 能判断使用的是维护前还是维护后的物理配置。

供应链更新采用隔离构建与可重复产物：依赖锁、编译器、engine builder、容器基础、驱动和模型制品都有来源与摘要。安全补丁不能绕过行为回归；紧急修复可缩短审批时间，但必须保留风险接受、有限范围、回滚与补测期限。发现制品撤回、许可证或漏洞问题时，registry 能列出受影响 bundle、active session 和历史证据。

自动化只能执行已批准的确定动作，例如隔离 failed candidate、把 active 指针回到已验证 LKG、阻止新 session 或收集 incident bundle。涉及机器人重新使能、解除安全停止、改变物理限制、选择未知 fallback 或扩大 canary 的决定，需要相应 authority。自动化请求和结果都是事件，重复执行保持幂等，失败不会留下半切换状态。

系统退役同样需要契约：停止接收新请求，drain 或取消在途工作，确认 controller 进入批准状态，撤销凭据，归档 bundle/evidence，按保留期处理日志与媒体，并更新 registry 为 retired。退役版本不得因旧 client 重连而重新 active；如需复现历史结果，在隔离环境加载并使用新的 session 与权限。

最终证据审查采用保守原则：缺少 p99、冷启动、过载、时钟、controller ack、queue 切换、热稳定、故障注入或 rollback drill 中任一关键项，都只能声明对应部分未验证。团队可以继续进行离线研究或缩小范围的受控测试，但不能把缺口折算成假定通过，也不能依赖“未发生事故”证明拒绝、降级和恢复路径正确。

容量规划不能只按平均任务估算。分别计算单 session 峰值、目标并发、故障重试、日志突发、模型切换时双份制品和 rollback 预留；CPU、GPU、内存、显存、网络、磁盘与电源都保留安全余量。达到容量边界前由 admission 明确拒绝，不能等到 OOM、swap、热降频或网络排队破坏 deadline 后再由重启恢复。

变更评审需要给出“为什么行为保持不变”或“哪些行为预期改变”。依赖升级、编译 flags、硬件、量化、预处理、QoS、queue、sampling 与 controller 参数分别提供差异、受影响路径和验证集。纯运维变更若触碰任一强契约，也视为新 deployment candidate。无法证明无影响时采取有影响假设，而不是跳过回归。

远程服务的断连与重连状态机要显式：检测连接失效，阻止新动作，处理在途 response，进入批准 fallback，创建新 transport 与 session epoch，重新握手、同步时钟并做 functional probe，最后才恢复请求。网络恢复本身不代表策略和 controller 仍处于兼容状态；重连不得把断连前 chunk、sequence 或 reference state带回新会话。

多人和多机器人共用平台时，审计资源、公平性与隔离。一个 session 的高优先级不能无限饿死其他任务，优先级反转和抢占成本要测；跨 session 的图像、prompt、cache、normalization 和 action 绝不串线。共享 engine 故障要能隔离影响范围，若不能，则所有依赖 session 同时进入一致的降级或停止状态。

灾备不仅保存模型文件，还保存 registry、签名、依赖、配置、adapter、stats、协议、controller binding、LKG 与审计事件。恢复演练在隔离环境验证摘要、权限和兼容性，并确认不会把已撤回或 quarantined 版本重新激活。备份与恢复策略由真实系统另行批准；本网页只定义所需证据，不自动创建备份。 变更窗口必须同时记录允许进入的版本集合、冻结开始与结束时刻、值班角色、观测期、停止条件和撤销路径。窗口开始前先锁定 registry revision、部署清单摘要、依赖镜像摘要与 LKG 指针，再核对正在运行的实例是否全部来自同一批准集合；若发现漂移，先停止变更并解释差异，不能用“顺便升级”消除证据。窗口内每个步骤只改变一个可归因变量，步骤间保留最短观测期；任何 deadline、freshness、queue age、fallback rate 或 controller reject 越过批准阈值，都按预先写定的 abort plan 撤销。冻结期不是禁止调查，而是禁止未经批准的新行为进入控制链。

跨区网络、时间同步、证书、DNS、对象存储、registry 和遥测后端都属于部署依赖，而不是 Policy Server 之外的“环境问题”。依赖清单要注明 owner、超时、缓存寿命、降级模式和失效传播方向。网络分区时，边缘实例只能在租约、摘要、兼容矩阵与本地安全门禁仍有效的范围内继续；时间源不可信时，不得伪造 freshness；遥测后端不可用时，系统应限制继续运行的证据窗口，超过窗口后进入安全不可用，而不是无限积压。依赖恢复后先做身份、时钟和序列连续性复核，再解除隔离。

证据链还要防止“日志存在但不可相信”。每个发布事件、握手结果、请求摘要、动作门禁、回滚决策和人工确认都绑定单调序号、可信时间来源、artifact digest 与配置 revision；跨进程转存保留来源和校验值，权限分离保证执行者不能单独改写验收记录。出现缺口、重复、乱序或摘要不一致时，报告必须显式标记未知区间，禁止用插值或后写说明冒充原始事实。保留期限和访问控制由真实组织审批，本页只规定验证时需要证明证据连续、可追溯且能与控制结果对齐。

实时服务的可用性目标不能凌驾于安全语义。SLO 至少分别描述请求成功、端到端 deadline、动作新鲜度、有效控制周期与安全 fallback；单纯返回 HTTP 成功不代表控制可用。若维持服务会消费过期观测、复用过期动作、绕过门禁或失去实际执行反馈，正确结果是安全不可用：拒绝新会话、清空危险队列、维持批准的 hold/stop 状态并向值班人暴露原因。恢复条件必须是可机器检查的联合谓词，而不是“看起来稳定”。

最终独立复核应由未执行本次变更的角色，把需求、实现摘要、Golden/Replay 结果、SIL/HIL/Shadow/Canary 证据、告警记录、回滚演练与未决缺口串成同一条可审计链。任何未决项都写明影响面、临时护栏、责任人和到期时间；无法证明不影响控制语义的缺口视为阻断项。只有当版本身份唯一、契约一致、实时预算有余量、故障注入符合预期、回滚可达且安全页的授权仍有效时，才关闭变更窗口。关闭记录不是永久许可；依赖、硬件、控制器、策略或安全规则任一项变化，都重新触发相应验证阶梯。

必须明确拒绝的错误表述。

  • “6 Hz 模型可以控制 6 Hz 机器人”错误；必须说明测量边界、chunk、controller 和全链时延。
  • “平均 80 ms，所以满足 100 ms deadline”错误；需 tail、jitter、miss count 和负载条件。
  • “实时就是低延迟”错误；实时关注 deadline 和可预测性。
  • “ROS 2 是实时系统”过度；OS、Executor、QoS、callback、内存、I/O 和代码路径都需验证。
  • “reliable QoS 更安全”不一定；重传可能增加陈旧与队列，需按消息语义选择。
  • “queue 不丢数据最好”错误；控制观测往往宁可丢旧保新，动作则必须有顺序和失效规则。
  • “远程推理只多一个网络 RTT”错误；还含序列化、上传、服务排队、下载和重连。
  • “服务返回成功就执行”错误；先核对 session、request、observation、contract、expiry、shape、finite 和 action semantics。
  • “异步能消除推理延迟”错误；它隐藏部分等待，但引入预测—执行错位和队列语义。
  • “队列里还有动作就无需 fallback”错误；动作可能基于过期观测或已失效目标。
  • “action chunk 越长越不易饿队列”不完整；同时增加开放环暴露和过时风险。
  • “最新 response 覆盖旧 chunk”不完整；需要 committed prefix、切换点和连续性策略。
  • “client resend 是安全的”错误；推理请求可做幂等，动作命令不能无条件重放。
  • “量化总能减小延迟”错误；硬件、kernel、校准和 quant/dequant 开销会改变结果。
  • “编译后模型语义相同”未经验证；需 golden、离线、SIL/HIL 和闭环回归。
  • “warm-up 后不必测冷启动”错误；重启、profile/shape change 和 cache eviction 都可能恢复冷路径。
  • “batching 提升性能”不等于单机器人延迟改善；收集 batch 本身可增加 queue delay。
  • “GPU 利用率越高越好”错误；可能牺牲 p99、功耗、热稳定和故障隔离。
  • “health check 200 即 ready”错误；ready 还要求 artifact/contract 绑定、warm-up 与下游连接。
  • “回滚等于加载旧权重”错误；必须原子恢复整套 bundle 并清空不兼容状态。
  • “日志越详细越可观测”错误；同步日志可能扰乱 deadline，且原始图像/指令有隐私。
  • “SIL 通过即可上真机”错误；还需 HIL、shadow、受控 canary 与安全批准。
  • “fallback 默认保持上一动作”危险；delta 与 absolute 语义不同，fallback 必须由控制/安全所有者明确。
  • “模型服务拥有紧急停止”错误；独立安全功能不能依赖同一模型进程存活。
