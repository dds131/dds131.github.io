数据集构建与数据质量分析

HDF5 与三路 MP4 的原始形态、转换为 LeRobot v2.1 的完整流程、以首次张开夹爪为基准的起点裁剪、包装加运行时替换的零侵入改造手法，以及指令与实测差异的定量归因

← 项目主页 ·数据集与数据质量 ·模型训练 ·真机部署 ·动作块平滑 ·效果与失败分析

本页从转换器拿到的输入开始，回答三个问题：原始数据是什么形态、 为什么要转成 LeRobot 格式以及转的过程中做了什么、这份数据本身可不可信。

原始数据的采集环节（VR 手柄位姿到关节角的逆解、110 Hz 指令下发、 HDF5 与 MP4 的对齐落盘、失败恢复数据的补采闭环）属于上游项目， 见 VR 遥操作 RM75 · 数据管线，本页不重复。

一、原始数据的形态

1.1 目录结构

一次采集会话（session）产出一个目录，目录内一条 episode 对应一个 HDF5 文件 与三个同名 MP4 文件：

<in_dir>/
  20260812_054806_pick_cube/          ← 一次采集会话
    meta.json                         ← 机器人型号、帧率、相机名、有效与废弃条数
    episode0000.hdf5                  ← 一条轨迹的全部低维信号
    episode0001.hdf5
    ...
    video/head_camera/episode0000.mp4     ← 全局视角
    video/arm_camera/episode0000.mp4      ← 腕部视角
    video/third_camera/episode0000.mp4    ← 第三视角（2026-08-13 起启用）

图像不存在 HDF5 里，而是外部的三个 MP4。转换器读 HDF5 拿低维信号、 用 OpenCV 解码 MP4 拿图像，并强制校验 视频帧数 == 轨迹长度 T，不等直接抛异常。 这条硬校验的价值在于：图像与动作一旦错位一帧，模型学到的就是「看到 A 的时候做 B」， 而这种错误在训练日志上完全看不出来。

1.2 HDF5 内部的字段

字段 形状与类型 含义
observations/qpos (T, 8) float32 前 7 维是关节实测角（单位：度），第 8 维是夹爪实测开口，归一化到 0–1 的连续量
action (T, 8) float32 前 7 维是关节下发指令角（度），第 8 维是夹爪指令
timestamp (T,) float64 采集时刻，可选
属性 fps 30 采样帧率
属性 arm_dof 7 RM75-B 是七自由度冗余臂
属性 joint_unit deg 关节角单位是度，不是弧度
属性 camera_names 三路相机名 与 video/ 下的子目录名一一对应

state 与 action 的第 8 维不是同一种量。 qpos[:,7] 是夹爪实际张开了多少（连续测量值）， action[:,7] 是下发给夹爪的档位指令（离散值）。 两者语义不同、量纲不同，这一点贯穿后面的裁剪判据、归一化统计与部署侧的解码逻辑。

1.3 夹爪指令是三个离散档位

对 2026-08-13 那一批数据（data_2026_8_13_1，593 条 episode、390,362 帧）逐帧统计 action[:,7]，取值只有三个：

0.0　夹紧183,650 帧　47.05%
0.5　半开27,615 帧　7.07%
1.0　全开179,097 帧　45.88%

这三个档位在真机上分别对应：夹紧（力控，夹持力 600）、半开（张开 25 度）、 全开（张开 50 度）。注意 1 是「开」而不是「抓取」，与直觉相反， 这个约定在部署侧的夹爪解码里也必须保持一致。

0.5 档最初被当成过渡态处理（老版转换器会把夹爪二值化，把 0.5 归到某一侧）， 第六节的统计推翻了这个判断，因此新版保留三个档位。

1.4 同一条 episode 的三个视角

下面三段是同一条 episode（20260812_054806_pick_cube 的 episode0000） 的三路相机原片，时长同为 25.87 秒、分辨率同为 640×480、帧率同为 30 fps。 三路必须严格同源同长，否则「三视角」这个说法不成立。

head_camera　全局视角，看得到料框与凹槽的相对位置
arm_camera　腕部视角，随夹爪运动，看得清工件姿态
third_camera　第三视角，补齐前两路的遮挡盲区
第三路相机是 2026-08-13 才加上的。加它的直接动机是：两路配置下腕部相机在 下降抓取阶段会被工件与夹爪本体挡住，全局相机又看不清工件的细微姿态。 消融实验的结果见真机部署一页—— 在 0828 权重 step 40000 的离线评测里（52 个样本），第三路一旦置黑，动作误差会放大到 5.48 倍； 三路之间的相对排序见部署页第七节 E 条（另一轮测量，绝对倍率不可与前者直接比较）。

二、转换为 LeRobot v2.1

2.1 为什么要换格式

openpi 的训练侧数据接口是 LeRobot 数据集。直接沿用自有的 「HDF5 加三个 MP4」有三个问题：

  1. 随机访问代价高。 训练是逐帧随机采样的，MP4 必须顺序解码到目标帧； 一次训练步要取 256 个样本，落在 256 条不同 episode 的不同时刻上。
  2. 没有统一的元数据契约。 openpi 的 transform 链依赖固定的列名与 特征声明（observation.images.*、observation.state、action）， 自有格式没有这层描述。
  3. 归一化统计无处安放。 分位数归一化需要在全量数据上先跑一遍统计， LeRobot 的 meta/ 目录是这批统计的标准落点。

2.2 转换流水线

转换流水线。读取与解码是 I/O 与 CPU 密集的，用线程池并行；写盘由主线程按 先进先出串行执行，保证产出顺序与串行版逐字节一致。最多同时有 workers + 1 条 episode 在飞。1393 条 episode 的完整转换约 117 分钟。

2.3 features 定义

特征键 dtype shape 说明
observation.images.head_camera image (224,224,3) 全局相机
observation.images.arm_camera image (224,224,3) 腕部相机
observation.images.third_camera image (224,224,3) 第三视角
observation.state float32 (8,) 7 关节实测角（度）加夹爪实测开口
action float32 (8,) 7 关节指令角（度）加夹爪档位指令

LeRobot 另外自动并入五个默认字段：timestamp、frame_index、episode_index、 index、task_index。

转换器不写入自己的 timestamp。 LeRobot 会按 fps 生成等间隔时间戳， 而真实采集的帧间隔有抖动；把真实 dt 传进去会触发 LeRobot 的 check_timestamps_sync 校验失败。这里让它按 30 fps 规则生成， 时间信息的真值保留在原始 HDF5 里，训练本身也不使用绝对时间戳。

2.4 图像为什么是 letterbox 而不是拉伸

resize_with_pad：先等比缩到 224×168，再在上下各补 28 行黑边凑成 224×224，不做非等比拉伸。拉伸会改变工件的表观宽高比，而 U 形件 的可抓方向恰恰由它的长短边决定，形变会直接干扰抓取姿态的判断。 这份实现是 openpi 官方 resize_with_pad 的 numpy 与 OpenCV 复刻， 部署侧用的是同一份逻辑——两侧预处理一旦不一致，模型看到的就是分布外输入。

2.5 图像为什么内嵌进 parquet 而不是编码成视频

LeRobot 支持两种图像存储：dtype: "video"（另存 MP4，读时解码） 与 dtype: "image"（PNG 字节内嵌进 parquet）。本项目选后者， 所以产出的数据集没有 videos/ 目录，total_videos 为 0。

选内嵌 PNG 的理由

  • 训练是逐帧随机采样，parquet 行内直读一帧的代价是常数；视频要顺序解码到目标帧
  • 无损，不引入视频编码带来的块效应与色度子采样误差
  • 数据加载器不依赖视频解码库，多进程 worker 更稳定

代价

  • 体积大：1393 条 episode 共 163.7 GB，同等内容视频编码只需几 GB
  • 转换耗时长：约 117 分钟，其中大部分花在 PNG 编码上
  • 写入期需要磁盘临时空间存中间 PNG

这是一个明确的空间换时间取舍：训练要跑十万步、每步取 256 个样本， 数据加载不能成为瓶颈；而 163.7 GB 落在本地 NVMe 上是可以接受的。

2.6 分片与索引

  • 一条 episode 一个 parquet：data/chunk-{chunk:03d}/episode_{index:06d}.parquet
  • chunks_size = 1000，即每 1000 条 episode 归入一个 chunk 目录。 1393 条被分成 chunk-000（0–999）与 chunk-001（1000–1392）
  • codebase_version = "v2.1"，fps = 30，robot_type = "rm75"
  • 全局 index 连续无断号，episode_index 从 0 到 1392 无空洞

三、起点裁剪

3.1 问题

人在 VR 里开始遥操作时，第一个动作通常不是伸手，而是先把夹爪张开。 在此之前的若干帧里，机械臂停在原位、夹爪闭合，画面与动作都没有任务信息。 这些帧数量不固定（实测 t0 有 25 种不同取值，最小 4 帧、中位 11 帧、最大 38 帧）， 所以不能用固定帧数裁剪，必须逐条自动判定。

3.2 判据与流程

t0 = 第一个满足 action[t, 7] >= 0.5 的 t          # 首次出现「张开」指令
t0 = min(t0 + extra, T - 1)                        # extra 为可配的额外保留量
若 t0 == 0        → 原样返回，不做任何切片
若 t0 > 200       → 抛异常（裁得太多，数据可能有问题）
若 T - t0 < 60    → 抛异常（剩得太少，这条 episode 没有价值）
否则：qpos / action / timestamp / 三路图像 一律从 t0 起同步切片

阈值 0.5 与夹爪档位判据用的是同一个常数，保证「判定张开」与「落盘取值」自洽。 切片之后还有两道自检：七路数据长度必须一致、裁后首帧的 action[0,7] 必须仍满足 张开判据。两道护栏（裁太多、剩太少）都选择抛异常而不是静默跳过， 因为静默跳过会让一条坏数据以「看起来正常」的方式进入训练集。

3.3 效果与交叉验证

项目 数值
触发裁剪的 episode 598 / 1394
丢弃帧数 11,479 / 871,409 = 1.32%
裁后最短 episode 230 帧
附带发现 11 个人工清单里没列出的 session 也需要裁，其中 4 个 t0 均值 65–99 帧（裁掉 15%–18%）

一个不依赖裁剪代码本身的交叉验证。 对早一批数据（593 条）比较裁剪前后的夹爪取值分布： 0.0 档恰好少了 2,171 帧，而 0.5 与 1.0 两档 一帧未动。总账 390,362 − 2,171 = 388,191，与数据集实际帧数吻合。

这条验证的意义在于：它从「结果的统计性质」独立地证明了裁掉的全部是 张开指令之前的闭合段，既没有多切、也没有少切，而不需要去读裁剪函数的实现。

另有一组逐像素的对齐验证：抽 9 条 episode，在首帧、中间帧、末帧三个时刻， 把数据集里的三路图像与原始 MP4 的第 t0 + t 帧逐像素比对，平均绝对差 全部为 0.0000；作为反证，被裁的 7 条如果拿数据集首帧去比原始第 0 帧， 差值是 1.55–2.78；三路之间两两比对差值 41–56，确认它们确实是三个不同视角 而不是同一路的副本。

四、零侵入的改造手法

三相机、夹爪三状态、起点裁剪这三件事都是本项目新增的需求， 而转换器的九个已有模块此前已经跑通并产出过多批数据。

采用的做法是「包装加运行时替换」：新写一个入口脚本，它先正常 import 原有模块， 然后在运行时就地替换掉模块里的函数对象与容器内容。因为 Python 的 import 拿到的是同一个模块对象， 所有已经 import 过这些名字的模块会自动看到替换后的行为，不需要逐个改调用方—— 这也正是下面第三处必须「就地修改」而不能整体重新赋值的原因。相比 fork 一份改， 它的好处是原文件保持可验证的未改动状态，回退等于不加那几个开关。

具体到本项目，这个入口只替换三处行为，九个已有文件一个都不改。 转换前后对这九个文件做 md5 比对，逐字节未变。

替换点 做什么 开关
read_episode → read_episode_trimmed 读完 episode 立即按 t0 裁头 --trim_gripper_open（默认开）
validate → validate_3state 夹爪合法取值判据由 {0,1} 改为 {0,0.5,1} --gripper_3state
IMG_KEYS / CAM_SRC 就地追加第三路相机 让下游所有模块都看到三路而不是两路 --cameras3

为什么第三处必须「就地」修改而不能整体重新赋值。 各模块用的是 from common import IMG_KEYS, CAM_SRC，绑定的是同一个 list 与 dict 对象。如果在入口里写 common.IMG_KEYS = [...]， 只会让入口自己的名字指向一个新对象，其它模块仍持有旧的两路列表—— 结果是产出一个静默少一路相机的数据集，而转换过程不会报任何错。

因此追加之后立刻做一次对象同一性自检， 确认入口看到的和各模块看到的是同一个对象，不是则直接退出。 这类失败必须在第一分钟暴露，而不是在 117 分钟之后靠人工目视发现。

validate_3state 的实现方式同样是保守的：先调用原版拿到全部体检项， 再只替换夹爪那一项的判据重算结论，其余四项（形状、有限性、 state 夹爪连续、action 为绝对量）一项不减。

--gripper_3state 1 会自动向下游注入 --binarize_gripper 0， 避免两个开关互相矛盾时产生难以察觉的错误组合。

五、数据质量：指令与实测的差异是什么

这一节回答一个必须回答的问题：action 与 state 之间差着的那部分， 是数据噪声，还是有物理含义的量？

分析对象是最终在用的 ruierman_lerobot_3cam_rawact_0828， 随机抽 100 条 episode（固定随机种子）共 61,729 帧 / 2,058 秒。

结论先行：这个差异几乎全部是时间延迟，不是数据质量问题。 下面给出三条彼此独立的证据。

5.1 逐关节偏差：没有系统性误差

单条 episode 的指令与实测叠加。两条线几乎重合，可观察到的差异只在快速段。
差值随时间的变化。差值的包络与关节速度的包络高度一致，这是延迟的典型特征。

七个关节的差值均值全部落在 ±0.09 度以内。 如果存在标定误差、零位偏移或单位换算错误，均值会呈现固定方向的偏置， 实际没有。差值的标准差在 0.70–1.78 度之间，关节 7（腕部回转）最大。

5.2 移位实验：残差降 66.7%

把实测序列整体后移 k 帧再与指令比对，逐 k 计算残差：

残差随移位帧数的变化。七条曲线全部在 k = 1 至 2 处取到谷底，呈清晰的 V 形。
关节 差值均值 差值标准差 最佳移位 对齐后残差 降幅 相关系数
J1 −0.0845 1.0181 1 帧 / 33 ms 0.2769 64.0% 0.919
J3 −0.0057 0.6999 1 帧 / 33 ms 0.1959 63.3% 0.911
J7 −0.0222 1.7804 2 帧 / 67 ms 0.4352 67.0% 0.924
七关节平均 ±0.09 内 0.8855 1.7 帧 / 57 ms 0.2926 66.7% 0.907

两条独立证据指向同一个结论：

  • 谷底位置一致。 七个关节都在 1–2 帧处取到最小残差，对齐后残差下降 66.7%。 如果差异来自随机噪声，移位不会让残差系统性下降。
  • 误差与速度强相关。 corr(|误差|, |速度|) = 0.907。 稳态误差（如摩擦、重力补偿不足）与速度无关； 只有 误差 ≈ 速度 × 延迟 这个模型能解释这么高的相关性。

数量级也能对上：七关节合成速度的中位数是 21.11 度每秒， 乘以 0.0667 秒约等于 1.41 度，与实测的 0.70–1.78 度标准差同一量级。

57 ms 是遥操作链路加伺服响应的固有物理延迟（VR 采样、网络、逆运动学求解、 指令下发、伺服执行、编码器回读），不是采集质量问题。

5.3 末端口径的复核

关节空间的结论需要在笛卡尔空间独立复核一次，因为七自由度冗余臂的 关节误差与末端误差之间不是简单的线性关系。

末端工具中心点的跟随分析。指令轨迹与实测轨迹几乎完全重合，差异表现为沿轨迹方向的相位滞后。
指标 数值
末端位置误差中位数 3.644 mm
末端姿态误差中位数 0.661 度
其中可归因于时间延迟的比例 96%（指令领先占 98.2%）
真正跟不准的部分 约 1.3 mm
端到端延迟的三种估计 关节法 57 ms / 末端平移法 67 ms / 末端速度回归 44 ms
综合最佳估计 约 40 ms（高速段底噪最小时的收敛值）
速度跟随比 / 总位移比 0.9828 / 0.9828（机械臂完整走完了指令路径）

末端误差比法兰误差大（速度越高比值从 1.064 升到 1.344）， 但两者的等效延迟完全相同（39.6 ms 对 39.7 ms）。 这说明末端多出来的那部分误差来自姿态误差乘以 0.195 m 力臂的几何放大， 不是额外的延迟。

分析过程中遇到的一个统计陷阱。 按 state 的速度分档统计误差比， 得到的趋势是 1.12 递减到 0.71；按 action 的速度分档，趋势是 0.89 递增到 1.06—— 方向完全相反。这说明它是分档带来的选择偏差，不是物理现象。 比较两个分布时不能按其中之一分档，这条教训已写进分析脚本的注释。

5.4 速度分布：运动快而短促

单关节 3.18–6.93 30.18–85.65 231–484 13%–20%

三点值得注意：

  • 中位与 95 分位差近一个数量级，说明运动是「快而短促」的， 大部分时间在慢速对准、少数时间在快速转移。
  • 关节 7 最快（95 分位 85.65 度每秒），它同时也是误差最大的关节—— 这是同一件事的两面，不是两个独立问题。
  • 指令的最大值集中在 157.09 度每秒，这是指令端的限幅； 实测出现的 247–484 度每秒是差分噪声（单帧编码器跳变被 30 倍帧率放大）， 判断真实速度应看 95 分位而不是最大值。

157.09 度每秒因此是动作空间的实际上界，部署侧的速度限幅可以据此设定。

六、夹爪：一个隐式的触觉传感器

1,057 次夹爪指令跳变后的开口响应。三档指令各自的稳态开度分布与到达 90% 的用时。

6.1 响应特性

指令 次数 稳定开度中位 标准差 到达 90% 用时
1.0 全开 243 0.5245 0.0896 8 帧 / 267 ms
0.0 闭合 279 0.2005 0.1816 7 帧 / 233 ms
0.5 半开 535 0.4598 0.2139 10 帧 / 333 ms

夹爪响应需要 233–333 ms，比关节的 57 ms 慢 4 至 6 倍。 一个动作块覆盖 1.667 秒，夹爪的响应就要占掉其中约六分之一。 这条数据是动作块平滑 一页里「离散档位绝不做加权融合」这条设计的直接依据。

6.2 合不到底的那 58.4%

279 次闭合指令里有 163 次（58.4%）开口停在 0.05 以上，没有合到底。 这不是故障，而是夹爪被工件挡住了——开口值直接反映了被夹处的厚度， 曲线在 0.20、0.28、0.34 三处出现平台，对应工件不同部位的厚度。

由此得到一个免费的能力：state[7] 是一个隐式触觉传感器。 发出闭合指令后如果开口合到底（接近 −0.02），说明什么都没夹到； 停在某个平台，说明夹住了对应厚度的部位。 模型在训练时能看到这一维，因此它具备习得「抓空后重试」这一行为的条件。

6.3 半开档是双峰分布，不是过渡态

最初的判断是「0.5 只是从闭到开的过渡值，可以合并掉」。 对 629 个 0.5 连续段做段长统计后，这个判断被推翻：

段长 占段数 占时长 性质
≤ 3 帧 73.6% 仅 17.3% 真正的过渡态
≥ 15 帧 17.6% 77.8% 明确的保持，中位 1.10 秒，最长 3.30 秒

保持段的开度是 0.2787 ± 0.0147（111 段里有 99 段落在同一个直方图区间）， 比 0.0 闭合档（标准差 0.1479）确定得多，是一个高度可重复的机械档位。 100 条 episode 里有 99 条至少出现过一次；111 个保持段里有 96 个属于 0.0 → 0.5（保持约 1.1 秒）→ 1.0 的释放序列——这正是「先松一点让工件落稳、 再完全张开」的操作习惯。

方法论上的自省。 段长的中位数是 2 帧、均值是 8.0 帧，相差 4 倍。 这个差距本身就是强烈的偏斜信号，最初「只看中位数就下结论」是错的。 双峰分布不能用中位数概括，这条已成为本项目所有统计分析的固定检查项。

保留三个档位因此是有依据的，而不是「多留一档没坏处」。 代价是引入一个混淆源：0.5 保持时的开度 0.2787 与「闭合但被工件挡住」 的中位 0.2408（覆盖 0.19–0.34）高度重叠，单看 state[7] 难以区分 「半开保持」与「夹住工件」，需要结合 action[7] 的档位一起判断。

八、一条从失败反推出的设计约束：同一观测不能对应两种动作

前面七节讨论的都是「这批数据是什么样」。这一节讨论的是下一批数据该怎么采—— 它不是从统计里得出的，而是从真机上的一次跳步失败反推出来的。

8.1 π0.5 的推理没有记忆

一次推理的输入只有当前这一时刻的三路图像、8 维本体状态和一条固定的语言指令， 输出是未来 50 步的动作块。块与块之间不传递任何隐状态，也没有「现在执行到第几阶段」 的计数器；上一个块做过什么，对下一个块的推理没有任何影响。 换句话说，策略是一个无记忆的单步条件映射：给定同一组（图像，状态，语言）， 它给出的动作分布永远是同一个，与走到这里的路径无关。

这带来一个直接的后果：

如果数据集里存在两段样本，其图像、本体状态、语言指令几乎相同， 标注动作却指向不同的任务阶段，那么模型在该观测处学到的就是一个多峰分布。 上线时它无法用「我刚才做过什么」来消歧，只能从多个峰里采样： 轻则随机跳过一个阶段，重则在两个阶段之间反复摆动、原地循环，任务推不下去。

本项目实际踩到的例子是「放入凹槽」与「从凹槽取出」这两个阶段—— 两者都是「夹爪夹着工件悬在凹槽上方」，观测几乎重合， 策略因此会跳过放槽直接入盒。录像与完整归因见 效果与失败分析第 6.6 节。

8.2 四条采集规范

由此反推出的、下一轮采集应当遵守的约束：

  1. 每个阶段在观测上必须可区分。 任务分解出的各个阶段，要在图像内容或本体位形上 有明显、稳定、可见的差异。若两个阶段物理上就长得一样，就人为把它们拉开—— 例如放槽前后走明显不同的过渡位姿，让「去程」与「回程」在关节空间里不重合。
  2. 单条 episode 内的动作风格要单一。 同一条数据里不要混入多种做法 （不同的接近路径、忽快忽慢的速度习惯、中途改变主意的重试）。 风格混杂等于人为加宽了同一观测下的动作分布，让本来单峰的地方也变成多峰。
  3. 相邻阶段的差异要足够大。 判据很朴素：拿一帧观测出来，人自己能不能一眼看出 「这是第几步」。人看不出来的地方，模型同样看不出来。
  4. 区分不了就把区分信息显式加进条件。 如果几何上无论如何都无法拉开， 就不要指望策略自己推断：补一路能看到「凹槽是否已被占用」的相机视角， 或把阶段编码并入条件输入，或把单条长指令拆成分阶段指令由外部状态机切换。
边界说明：这四条是从单个失败现象反推出的设计经验，没有做过消融验证。 要证实它，需要构造一版「阶段位形刻意错开」的数据集重新训练并做真机对照， 本轮没有做。写在这里是作为下一轮采集的规范，不是已验证的结论。 与之配套的执行侧参数（每个动作块实际执行多少步，太短易摆动、太长精度差）见 动作块平滑第 8.3 节。
