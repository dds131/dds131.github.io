知识库首页 /VLA 总览 /DexGraspVLA /高层规划器与目标抽象

DexGraspVLA 的高层规划器不是一个与控制器联合训练的策略网络，而是通过 OpenAI 兼容接口调用的现成视觉语言模型。它把自由形式提示拆成四类问答：选择下一目标、定位目标、判断抓取结果、判断整条提示是否完成。真正进入低层感知链的是边界框；SAM 将框变成初始掩码，Cutie 再维持目标身份。

4项 VLM 子任务，对应公开代码的四个 task_name
0项 DexGraspVLA 专用规划器参数更新
149 / 150独立边界框评测中的正确数
89.6%96 个长程场景的全任务成功率

先区分三个版本边界。 论文除长程任务外的实验使用 Qwen-VL-Chat；长程任务使用 Qwen2.5-VL-72B-Instruct。当前公开 README 与规划器代码以可替换模型接口为主，部署示例指向 Qwen2.5-VL-72B。不能用当前仓库默认方案反向改写论文中其他实验的模型设置。

一、规划循环：四项任务在什么时候发生

论文给出模块职责，公开 inference.py 则揭示了实际调用顺序：系统在第一次抓取前先检查提示是否已经完成；若未完成，才进入目标选择与抓取循环。

flowchart TB
  P["用户提示 + 初始头部图像"] --> C0["④ 提示完成核验"]
  C0 -->|"已完成"| E["结束"]
  C0 -->|"未完成"| I["① 提出下一条物体级抓取指令"]
  I --> B["② 预测目标边界框"]
  B --> S["SAM 生成当前目标的初始掩码"]
  S --> T["Cutie 在控制执行中传播掩码"]
  T --> G["③ 抓取结果核验：当前头部图 + 腕部图"]
  G --> R["脚本化放置/复位序列"]
  R --> C1["④ 提示完成核验"]
  C1 -->|"未完成"| I
  C1 -->|"已完成"| E

图中“脚本化放置/复位”不是 VLM 或扩散控制器生成的动作。论文明确说成功抓取触发脚本化放置，之后复位；公开脚本在每次控制尝试结束后都会调用固定的 right_finish_reset() 序列。

1.1 论文流程与当前源码并非完全同粒度

论文把结果核验概括为规划器“监控控制器执行”。当前公开脚本实现得更具体：当末端高度超过阈值时，后台循环调用抓取结果核验；一次 True 会结束当前控制尝试，连续三次 False 也会结束并复位。这里的“三次”是同一次执行过程中的连续核验结果，不是论文表格里的 Ours@3 三次独立抓取尝试。

Figure 2 在规划器回路旁标出 1 Hz，但论文正文和公开脚本没有把四类任务统一实现成固定 1 Hz 调度。因此不能据此声称每秒完整运行一次四项 VLM 子任务。

二、四项子任务：输入、输出与失败影响

子任务 视觉输入 其他输入 输出 当前脚本中的调用位置
① 指令提出 初始头部图 + 当前头部图，均经工作区预处理 用户提示 一句物体级自然语言指令 每轮抓取开始
② 边界框预测 当前头部图，经工作区预处理 ① 的指令 bbox_2d、label、description SAM 初始化之前
③ 抓取结果核验 当前完整头部图 + 当前腕部图 ① 的指令 推理文本中的 True/False 控制器执行期间，末端超过高度阈值后
④ 提示完成核验 初始头部图 + 当前头部图，均经工作区预处理 用户提示 推理文本中的 True/False 首次抓取前及每轮尝试后

2.1 指令提出：决定“下一步抓谁”

prompt 要求只选一个当前可见目标，并描述颜色、形状和相对位置。它还写入了四条启发式：优先右侧再到中间和左侧，避开被阻挡或包围的物体，避免导致其他物体倾倒，并满足用户提示。

这些规则是作者写入 prompt 的任务先验，不是从 2,094 条示范中学出的规划策略。它们有助于论文中的右臂桌面设置，但并非普适原则：若机器人安装方向、工作空间或任务代价改变，“从右到左”可能不再合适。

同时查看初始图和当前图，可以帮助模型判断哪些目标已经从桌面移除；但这仍是基于图像差分与语义推理的启发式判断，不是显式的物体清单或状态机。

2.2 边界框预测：把指令落到像素区域

输出结构为：

{
  "bbox_2d": [x1, y1, x2, y2],
  "label": "简短名称",
  "description": "外观与位置描述"
}

调用方只读取 bbox_info['bbox_2d']；名称和描述主要用于响应解释与日志。对宽为 $W$、高为 $H$ 的图像，一个有效框至少应满足

\[0\le x_1<x_2<W,\qquad 0\le y_1<y_2<H.\]

prompt 要求坐标在图像范围内，并要求目标不可见时不要猜。然而当前代码没有显式的空目标协议，也没有检查坐标顺序、范围或最小面积；因此 prompt 约束不能等同于运行时保证。

2.3 抓取结果核验：判定目标是否被抓住

这是唯一同时使用头部与腕部图像的子任务。prompt 要求结合“目标是否仍在桌面”和“手中是否稳固持有目标”给出布尔判断。两个视角可以减少单视角歧义，但论文没有对这一子任务做独立的受控准确率评测，也不能保证遮挡、相似物体或空抓时判断可靠。

更重要的是，它与低层控制器在同一尝试中表现出的重抓不是同一机制：VLM 核验决定何时结束当前尝试；重抓则发生在滚动动作块和新观测构成的低层闭环中，其因果归因仍需谨慎。详见⑥ 推理闭环与现象。

2.4 提示完成核验：决定是否停止整条任务

此任务比较初始与当前头部图像，要求只考虑可见三维物体：相关物体全部移除时返回 True，仍有相关物体时返回 False。原页面把它误写成只有五行且缺少输出约束；论文 v5 与当前源码实际上都包含判断规则、布尔输出格式和示例。

它在第一次抓取前也会运行，因此空桌面或已经完成的指令可以直接结束。其主要风险是错误的 True 会让主循环立即停止；错误的 False 则会继续进入目标选择，而当没有合法目标时，当前接口又缺少明确的“无目标”返回类型。

三、边界框为什么有用，以及它没有证明什么

论文把自然语言的“域方差”转换为格式一致的边界框，并将其称为 domain-invariant affordance。这里应把格式不变与统计不变分开理解。

3.1 确实成立的接口优势

低带宽空间接口不同措辞最终都变为四个图像坐标；低层控制器无需编码语言 token。
能直接驱动 SAM边界框提供目标的大致范围，SAM 负责转成像素级掩码。
模块可替换只要新规划器继续输出同一坐标约定，就可更换 VLM，而不必重训低层控制器。
故障容易定位目标选择、框选、分割、跟踪和动作执行可分别记录与检查。

3.2 “域不变”不能按字面理解

边界框 $\mathbf b=(x_1,y_1,x_2,y_2)$ 仍取决于相机视角、分辨率、裁剪区域、目标遮挡以及 VLM 的定位能力。环境变化若使 VLM 框错目标，域偏移仍会沿接口传到下游。论文没有测量训练域与测试域的边界框分布差异，也没有做“语言、点提示、框提示、直接掩码”等接口的受控消融。

因此，论文结果支持“边界框是一个有效且格式统一的任务接口”，但不支持以下更强结论：

  • 边界框完全不含域相关信息；
  • 框提示一定优于点提示或其他目标表示；
  • 仅靠边界框就造成了全部泛化提升；
  • 低层控制器因此不再需要处理视觉域变化。

四、从工作区图像到逐帧掩码

4.1 工作区预处理

论文说明，指令提出、边界框预测和提示完成核验只需要桌面工作区，因此保留相关区域并将其余像素填白。当前公开 preprocess_img 没有改变图像尺寸，而是保留原图的

\[h\in[0,\lfloor0.6H\rfloor),\qquad w\in[\lfloor0.4W\rfloor,\lfloor0.9W\rfloor)\]

区域，其余位置设为 255。比例是当前机器人相机视角下的硬编码配置，不应当直接迁移到其他相机或安装位姿。抓取结果核验没有走这个预处理函数，而是使用完整头部图和完整腕部图。

这一步能屏蔽桌外干扰，但不能称为把域差异“归零”：保留区域中的背景、光照、遮挡和物体外观仍会变化。

4.2 SAM：每个新目标重新播种

边界框在当前抓取轮次的起始时刻 $t_0$ 提示 SAM，得到二值掩码

\[\mathbf m_{t_0}\in\{0,1\}^{H\times W\times1}.\]

公开实现启用 multimask_output=True，并选择 SAM 自评分数最高的候选。初始化前会清空 Cutie 记忆；因此长程任务每换一个目标都会重新执行“VLM 出框 → SAM 分割 → Cutie 播种”，不是整条用户提示只运行一次 SAM。

4.3 Cutie：在本轮控制中维持目标身份

第一帧把 SAM 掩码和 object id 写入 Cutie；之后每帧只输入新图像，由 Cutie 的记忆机制输出当前掩码 $\mathbf m_t$。这种时序跟踪避免每帧重新调用 VLM/SAM，也减少相似物体之间的目标跳变。

但当前脚本没有掩码质量检测、漂移检测或本轮内的 SAM 重初始化。若 Cutie 漂移，错误掩码会直接进入控制器，通常要等当前尝试结束、下一轮重新出框时才会清空记忆。论文的 149/150 定位评测只测 VLM 边界框，不测 SAM 分割质量或长时间跟踪漂移。

HTTP httpx.HTTPTransport(retries=1) 缓解一次瞬时连接失败 没有任务级重试或回退策略
JSON parse_json 后交给 json_repair.loads 修补代码围栏、逗号或括号等格式问题 不校验字段、坐标范围、框面积或目标可见性
布尔值 小写响应后先查 true，再查 false 实现简单 同时包含两词时可能误判，也未强制最终答案位置
日志 base64 图像在文本日志中替换为占位符，图像另存 避免日志膨胀并保留调试证据 不构成隐私或数据保留策略

当前布尔解析尤其需要注意：它不是结构化输出解析，而是字符串包含判断。若推理文本同时出现 true 和 false，代码会优先返回 True。更稳健的实现应使用严格 schema，例如只接受 {"success": true}，并对缺字段、双值、非法坐标设置重试或安全停止。

README 的自部署示例使用 vLLM 0.7.3，在一台 8×A800 服务器上占用四张卡承载 Qwen2.5-VL-72B，并以 7B 模型做 speculative decoding。它说明该规划器可部署，但不构成端到端延迟基准；论文没有报告四项 VLM 调用各自的延迟分布。

六、实验证据应该怎样读

6.1 长程任务：评测完整串联系统

四类提示各测试 24 个随机杂乱场景，共 96 个任务。除“清空桌面”含三个未见物体外，其余场景有 3–4 个未见物体，其中两个与提示相关。

指标 Clear table Green objects Bottles Food 汇总
全任务成功率 95.8% 87.5% 91.7% 83.3% 89.6%
成功任务中每个目标平均尝试数 1.09 1.14 1.09 1.19 1.12
指令提出准确率 100.0% 92.6% 94.3% 88.1% 94.3%
边界框准确率 98.7% 98.2% 98.1% 98.3% 98.4%

这些分项的样本单位和条件依赖并不相同，不能简单把百分比相乘来重建 89.6%。全任务成功要求所有必要阶段最终完成，而且成功任务可能对同一目标尝试多次。

6.2 独立边界框评测：149/150 的真实含义

条件 正确/测试数 准确率
无干扰：白桌、白光 29/30 96.7%
背景干扰：标定板或彩色桌布 60/60 100.0%
光照干扰：台灯或迪斯科灯 60/60 100.0%
汇总 149/150 99.3%

每种具体场景布置 5 个杂乱场景，每场 6 个随机物体。评测者为每个物体提供描述其外观和位置的文字提示，再检查预测框是否紧密包围目标。

这项实验强有力地支持 VLM 在所测干扰下的条件式定位能力，但有四个边界：

  1. 输入提示由评测者给出，不是子任务①自动生成，因此没有测“指令提出 → 框选”的级联误差。
  2. “紧密包围”没有给出 IoU 阈值，判定规则不够适合独立精确复现。
  3. 只覆盖五种桌面/光照场景，不能推导任意开放环境下都是 99.3%。
  4. 没有置信区间、重复模型采样或不同 VLM 的对照。

七、创新点、故障传播与改进方向

7.1 这一层真正的贡献

  • 把开放式提示拆成四个可记录、可替换、可分别评测的 VLM 子任务；
  • 用边界框把语言规划和像素级控制连接起来，再由 SAM/Cutie 维持目标身份；
  • 将初始—当前图像对照用于目标选择和终止判断；
  • 在长程真机任务与受干扰定位场景中给出分项结果。

Qwen、SAM、Cutie 和 OpenAI 兼容服务本身都不是本文提出的。论文也没有做规划器接口的完整消融，因此创新应表述为模块编排与接口设计，而不是新的视觉语言模型或已被单独证明最优的目标表示。

7.2 关键故障链

故障 可能后果 当前系统可能发现吗
指令提出选错目标 抓取与用户意图不符的物体 完成核验可能发现任务仍未完成，但已移走的错误物体无法恢复
框选错误或坐标非法 SAM 得到错误/空掩码 结果核验有机会判为失败；代码没有框级校验
SAM 分割错误或 Cutie 漂移 控制器追踪错误区域 没有本轮内显式漂移检测，通常到下一轮才重新初始化
抓取核验假阳性 提前结束当前尝试并执行固定复位序列 后续完成核验可能继续任务，但不保证识别这次误判
完成核验假阳性 提前终止整条用户任务 主循环没有更高层复核
完成核验假阴性 在无合法目标时继续规划 prompt 要求不猜，但接口没有安全的“无目标”分支

7.3 优先改进方案

  1. 为四项任务定义 JSON Schema，并在进入机器人控制前验证字段、枚举、坐标和置信度。
  2. 增加 no_target、uncertain 与 retry 状态，避免把所有异常压成布尔值。
  3. 对边界框做越界裁剪、面积阈值和 SAM 空掩码检查；必要时请求 VLM 重试。
  4. 为 Cutie 增加掩码面积突变、目标消失和跟踪置信度监控，在本轮内触发重新分割或安全停止。
  5. 分别记录四项调用延迟、重试次数与失败类型，才能定位 72B 规划器的真实时延瓶颈。
  6. 增加端到端规划评测：让①自动提出指令，再评②定位，以覆盖级联误差。
