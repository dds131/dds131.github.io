两个层级不能按数字直接对齐。论文中的 18 维和 700k 步描述论文实验；openpi 中的 32 维和 TrainConfig.num_train_steps=30_000 是固定源码版本里的类级默认值，具体配置可以覆盖。训练步数还必须结合全局 batch、初始化权重和数据采样方式解释。

一、训练系统全景与本页边界

先把一次训练更新放回完整链路：

flowchart LR
  A["数据集<br/>任务与机器人混合"] --> B["平台变换<br/>动作语义统一"]
  B --> C["Normalize<br/>统计量与模式"]
  C --> D["模型变换<br/>图像·分词·补零"]
  D --> E["compute_loss<br/>Flow Matching"]
  E --> F["全局范数裁剪"]
  F --> G["AdamW + 学习率日程"]
  G --> H["可选 EMA"]
  H --> I["检查点<br/>参数 + norm stats"]

本页重点解释数据配方、统一宽度、归一化、优化器、EMA、LoRA、后端差异与检查点契约。Flow Matching 损失推导见子页 ②；四段数据变换的执行顺序见子页 ④；实验结果与推理延迟见子页 ⑥。

二、两阶段训练

论文把训练分成目标不同的两段，这一点与大语言模型的做法一致。

预训练目标是让模型见到尽可能多的任务，并且每个任务内部覆盖多样的行为。论文明确指出，正是这些「多样但质量较低」的数据让模型具备从错误中恢复、应对高度变化情形的能力。
后训练目标是让模型在目标任务上熟练而流畅地执行。这一阶段的数据要求相反：应当体现一致且流畅的策略，而不是追求多样。

2.1 预训练的数据配方

论文第五节给出的一手数字：

项 数值 说明
开源数据混合权重 9.1% 指训练混合中的抽样占比，不是原始文件大小占比；含 OXE、Bridge v2、DROID
开源数据的特点 1 到 2 个相机、2 到 10 Hz 控制 频率低、相机少，但物体与环境覆盖广
自采数据 903M 个时间步 其中单臂 106M、双臂 797M
任务数 68 论文强调其「任务」定义比常见做法宽得多
机器人构型 7 种 含单臂、双臂、以及完整与非完整约束的移动操作机

论文特别提醒了「任务」这个词的口径：它说的一个任务是一整类复杂行为，例如「清理餐桌」这一个任务就包含把各式餐具杯子送进回收箱、把各种垃圾丢进垃圾桶。这与「把杯子拿起来」「把盘子拿起来」算作两个任务的常见做法完全不同，因此实际行为的丰富程度远超 68 这个数字给人的印象。

数据不平衡的处理：把每个「任务—机器人」组合记为 $g$，样本数记为 $n_g$。论文令组合的抽样概率与 $n_g^{0.43}$ 成正比，即

\[p_g=\frac{n_g^{0.43}}{\sum_j n_j^{0.43}}.\]

因此大组合的总抽样概率仍然更高，但只按次线性速度增长。若组合内部均匀抽样，单个样本被抽到的概率与 $n_g^{-0.57}$ 成正比：大组合中的每个样本相对降权，小组合中的每个样本相对升权。这比“样本越多，组合权重越小”更准确。

2.2 两个阶段的规模差距

这是本页第一处需要显式区分两层数字的地方。

  论文实验 openpi 固定源码版本
训练步数 主模型 700k 步；另有 160k 步版本用于与基线比较 TrainConfig 类默认 30k；具体配置有 10、20k、30k、100k 等
初始化 VLM 从 PaliGemma 初始化，动作专家从随机参数开始，再做跨本体预训练 由 weight_loader 或 PyTorch 权重路径决定
典型用途 大规模跨本体预训练与论文实验 同时包含推理配置、微调示例、DROID 训练示例和调试配置
num_train_steps=30_000 只是类级默认值，不能单独定义训练阶段。仓库的 LIBERO 微调示例确实从基础检查点开始，但部分推理配置沿用 NoOpWeightLoader，其他训练配置也会覆盖步数。比较训练规模时至少要同时报告全局 batch、更新步数、初始化方式和数据混合；粗略的样本抽取次数为 num_train_steps × batch_size，但它仍不等于独立轨迹数或有效数据覆盖率。

2.3 后训练需要多少数据

论文报告其下游任务从约 5 小时到 100 小时以上。这个数字描述论文中的机器人、示教质量与任务定义，不能直接换算成新平台的最低采集量。估算自己的数据需求时还要考虑任务成功率、场景覆盖、恢复行为、控制频率和动作块重叠；更稳妥的做法是先用小规模数据建立学习曲线，再决定是否继续采集。

三、跨本体的统一动作空间：18 与 32

读到 D = 18 与 D = 32 时，先确认版本和语境：18 是论文数据混合采用的统一状态/动作宽度，32 是当前 Pi0Config.action_dim 的默认模型宽度。32 不是所有 openpi 模型和配置都必须使用的常数。

3.1 两个数字各自的来源

  论文的 18 openpi 的 32
它是什么 论文跨本体数据采用的统一向量宽度 Pi0Config 的默认状态/动作张量宽度
怎么来的 双臂 12 + 双夹爪 2 + 全向底盘 3 + 升降躯干 1 = 18 Pi0Config.action_dim 的默认值；具体配置可覆盖
出处 论文第五节原文 models/pi0_config.py
可否改 是该论文训练配方的选择，不是架构常数 是配置项；增大时会改变投影层形状与 checkpoint 兼容性

论文把状态和动作统一到数据混合中的最大宽度，低维机器人尾部补零，缺失图像槽位则显式标为无效。openpi 同样使用固定宽度接口，但代码只表明默认值是 32，并没有把“为了长期预留余量”写成设计结论；后者至多是合理解释，不应作为已证实事实。

因此读到这两个数字时，正确的问法不是「谁写错了」，而是：这是论文里的模型配置，还是当前 openpi 的软件接口配置？同一类问题在时间方向约定上也出现过，处理方式一样——先确认对方在讲哪一层。时间方向那一条见子页 ③。

3.2 补零与掩码发生在哪

在 openpi 里，补零不在模型中，而是数据侧的一个变换：

# src/openpi/transforms.py
class PadStatesAndActions(DataTransformFn):
    """Zero-pads states and actions to the model action dimension."""
    model_action_dim: int

    def __call__(self, data):
        data["state"] = pad_to_dim(data["state"], self.model_action_dim, axis=-1)
        if "actions" in data:
            data["actions"] = pad_to_dim(data["actions"], self.model_action_dim, axis=-1)
        return data

三条要点：状态与动作一起补；补在尾部（pad_to_dim 用 np.pad 右填零）；模型收到的已经是补齐好的张量。相机缺失则走另一条路——用 image_masks 在注意力里屏蔽，详见子页 ① 第 4.1 节。

补零维度不会被损失掩掉。若某个填充动作维 $a_d=0$，训练时仍有 $x_{t,d}=t\epsilon_d$、$u_{t,d}=\epsilon_d$，模型要学习把这一路噪声积分回零。JAX 又在固定的 $D$ 个动作维上取均值，因此真实自由度越少，有效维度在总损失中的相对权重越低。这是统一接口的工程折中，不宜简单称为“无害”；完整推导见子页 ② 第 11.2 节。

四、归一化：默认模式、统计量与 checkpoint 契约

归一化同时影响预训练权重看到的输入尺度、微调目标的数值范围和推理时动作的反变换。模式、统计量与动作语义必须作为一个整体核对。

4.1 两种模式

transforms.py 的 Normalize 支持两种归一化，由一个布尔开关选择：

模式 公式 输出范围
z-score \((x - \mu) / (\sigma + 10^{-6})\) 不设限，取决于分布
分位数 \((x - q_{01}) / (q_{99} - q_{01} + 10^{-6}) \times 2 - 1\) 把 1% 到 99% 分位映射到 \([-1, 1]\)

分位数模式对离群值更稳健：极少数异常大的动作不会把整体压扁，代价是超出 1% 到 99% 区间的值会落在 \([-1, 1]\) 之外。

4.2 哪个模型用哪一种

答案在一行代码里：

# src/openpi/training/config.py
use_quantile_norm=model_config.model_type != ModelType.PI0,

在默认的 DataConfigFactory 路径中，π0 使用 z-score，π0.5 与 π0-FAST 使用分位数归一化。这是工厂默认规则，不是不可覆盖的模型定律；最终口径以具体 DataConfig.use_quantile_norm 和 checkpoint 资产为准。

风险不只是“训练和推理是否使用同一公式”，还包括是否与基础 checkpoint 的输入分布一致。如果从 π0 基础权重微调，却把数据改成 π0.5 的分位数口径，模型起点看到的尺度会发生变化；即使训练损失可以下降，也不能据此证明表示口径兼容。检查时同时核对 use_quantile_norm、asset_id 和实际加载的 norm_stats.json。

4.3 统计量的生成与一致性

归一化统计由 scripts/compute_norm_stats.py 在平台变换之后、模型归一化之前统计 state 与 actions，默认遍历数据集，也可用 max_frames 抽样。结果存为 norm_stats.json。RunningStats 流式累计均值与平方均值，并用 5000 个分箱的直方图近似 1% 与 99% 分位数，因此不需要把整个数据集同时放进内存。

训练与推理必须使用同一资产口径。 z-score 反变换会把均值补 0、标准差补 1；分位数反变换则只变换统计量覆盖的前缀维度，把额外尾部维度直接拼回。两条路径都在避免把模型填充维误映射成机器人动作，但 z-score 分支还包含 $10^{-6}$ 项，不能把“原样返回”理解成数学上的严格恒等。

若某一维几乎不变化，std 或 q99 - q01 会很小，归一化值可能被放大。排查动作幅度异常或训练发散时，应依次核对统计文件、归一化模式、动作单位与绝对/增量语义，并检查每一维的 std、q01 和 q99；不要仅凭“方向大致正确”锁定单一原因。

4.4 训练期图像增强

preprocess_observation(..., train=True) 还会执行图像增强：非腕部相机先做 95% 随机裁剪、缩放回原尺寸和约 ±5° 旋转，所有视角再做亮度、对比度与饱和度扰动；推理时不启用这些随机变换。它们是 openpi 训练实现的一部分，但不是论文贡献。复现时若自行绕过 compute_loss(..., train=True) 的标准路径，应确认没有意外关闭增强，也不要把推理端设置为训练模式。

五、优化器与学习率调度

以下先解释 training/optimizer.py 与 TrainConfig 的类级默认值。具体训练配置可以覆盖它们，例如 pi05_libero 使用不同的 batch、预热、峰值学习率和 EMA 衰减。

5.1 AdamW

# src/openpi/training/optimizer.py
@dataclasses.dataclass(frozen=True)
class AdamW(OptimizerConfig):
    b1: float = 0.9
    b2: float = 0.95
    eps: float = 1e-8
    # Changing this to 0 can cause out-of-memory errors for some reason, so we set it to a negligible value.
    weight_decay: float = 1e-10
    clip_gradient_norm: float = 1.0

三处值得注意：

二阶动量 0.95 而非 0.999大模型训练里常见的取法。更短的二阶动量窗口让优化器对梯度尺度的变化响应更快，代价是估计噪声更大。
权重衰减近似为零但不等于零取 1e-10 而不是 0。上游注释只记录“设为 0 曾导致显存不足”，没有给出机制解释；应把它视为该实现的兼容性约束，而不是 π0 的算法结论。
梯度裁剪按全局范数 1.0在 optax 链里排在 AdamW 之前。若阈值为 c，裁剪可写成 g' = g · min(1, c / ||g||₂)，再由 AdamW 处理。

5.2 余弦衰减加预热

# src/openpi/training/optimizer.py
@dataclasses.dataclass(frozen=True)
class CosineDecaySchedule(LRScheduleConfig):
    warmup_steps: int = 1_000
    peak_lr: float = 2.5e-5
    decay_steps: int = 30_000
    decay_lr: float = 2.5e-6

设步数为 $s$、预热长度 $W=1000$、总衰减边界 $T=30000$。学习率从 $\eta_0=2.5\times10^{-5}/1001\approx2.5\times10^{-8}$ 线性升到峰值；第 1000 步到第 30000 步按余弦下降，之后保持终值。decay_steps 包含预热阶段，不是预热结束后再额外衰减 30000 步：

\[\eta(s)= \begin{cases} \eta_0+(\eta_{\max}-\eta_0)\dfrac{s}{W}, & 0\le s<W,\\[6pt] \eta_{\min}+\dfrac{\eta_{\max}-\eta_{\min}}{2} \left[1+\cos\left(\pi\dfrac{s-W}{T-W}\right)\right], & W\le s<T,\\[6pt] \eta_{\min}, & s\ge T. \end{cases}\] 
flowchart LR
  A["步 0<br/>约 2.5e-8"] --> B["线性预热<br/>1000 步"]
  B --> C["峰值 2.5e-5"]
  C --> D["余弦衰减<br/>至第 30000 步"]
  D --> E["终值 2.5e-6"]

5.3 训练长度与学习率边界要共同设计

decay_steps 的默认值 30000 与 num_train_steps 的默认值 30000 是相等的，但它们是两个独立的字段。

关系 实际行为 何时合理
num_train_steps < decay_steps 在余弦曲线到达终值前停止 快速试验或有意提前停止
num_train_steps = decay_steps 最后一步附近到达终值 默认配方
num_train_steps > decay_steps 后续阶段保持 decay_lr 有意进行低学习率收尾时可以采用

因此不是“两个字段必须永远相等”，而是修改训练长度时必须重新确认期望的学习率轨迹。应在日志中记录学习率，并明确最后一段是提前停止、刚好退火完成，还是低学习率平台期。

5.4 权重来源

JAX 路径由 weight_loader 决定初始化方式：

  • NoOpWeightLoader：保留模型刚创建的参数；它也是 TrainConfig 的类默认值，并不只服务调试配置。
  • CheckpointWeightLoader：加载完整模型检查点；LoRA 微调时允许补入新建的 LoRA 参数。
  • PaliGemmaWeightLoader：只覆盖 VLM 主干中能匹配的参数，动作专家及其他新增参数保留随机初始化。

具体微调示例必须让模型家族与基础检查点一致，例如 pi0_libero 对应 pi0_base、pi05_libero 对应 pi05_base。训练入口会校验参数树、形状和 dtype；π0 与 π0.5 的结构不同，错配通常会在初始化阶段报错。PyTorch 路径则读取 pytorch_weight_path/model.safetensors，不使用同一套 JAX weight_loader 加载流程。

5.5 保存、恢复与选择检查点

JAX 检查点同时保存三类内容：可恢复训练的 train_state、供推理加载的 params，以及包含归一化统计的 assets。启用 EMA 时，推理 params 取 EMA 参数；未启用时取当前训练参数。save_interval 决定保存频率，管理器通常只保留最新检查点，同时保留步数能被 keep_period 整除的里程碑。

resume=True 用于恢复同一次训练的参数、优化器状态和步数；weight_loader 则是在新训练开始前初始化模型，两者不能混为一谈。标准训练脚本没有用训练损失自动挑选“最佳真机策略”的逻辑，最终选择仍应依赖独立评估，而不是默认最后一步一定最好。

六、EMA

JAX TrainConfig.ema_decay 的类默认值是 0.99。每次参数更新后，代码执行

\[\bar\theta_t=\beta\bar\theta_{t-1}+(1-\beta)\theta_t.\]

当 $\beta=0.99$ 时，$1/(1-\beta)=100$ 是近似时间尺度，不是“最近 100 步等权平均”；权重半衰期约为 $\ln 2/(-\ln 0.99)\approx69$ 步。EMA 通常让导出的参数随训练步变化得更平滑，但效果仍需用任务评估验证。

官方低显存 LoRA 示例关闭 EMA：

# src/openpi/training/config.py
# Turn off EMA for LoRA finetuning.
ema_decay=None,

这是一项显存权衡，不是 LoRA 的数学要求。README 也把禁用 EMA 列为 JAX 训练显存不足时的可选措施，因为训练状态需要额外保存一份参数树。

标准 JAX 检查点流程在启用 EMA 时会自动把 ema_params 写入供推理使用的 params 项，同时保留可恢复训练的状态；因此使用官方保存与加载路径时，不需要手工“切换到 EMA”。只有绕过该流程、直接导出训练状态时，才需要确认拿到的是哪组参数。固定提交中的 PyTorch 训练不支持 EMA。

七、LoRA 与冻结策略

Pi0Config 的两个 variant 字段各自可以换成带 _lora 的版本，对应配置在 gemma.py 中：VLM 专家使用秩 16、缩放 16，动作专家使用秩 32、缩放 32。LoRA 不直接训练完整矩阵 $W$，而是学习低秩增量：

\[W'=W+\frac{\alpha}{r}BA,\qquad A\in\mathbb{R}^{r\times d_{\mathrm{in}}},\quad B\in\mathbb{R}^{d_{\mathrm{out}}\times r}.\]

这里 $r\ll\min(d_{\mathrm{in}},d_{\mathrm{out}})$，所以可训练参数和优化器状态显著减少；秩与缩放是工程超参数，不属于 π0 的核心算法创新。

冻结哪些参数由 get_freeze_filter() 按两个 variant 的取值推出。使用时有一条硬性要求：传给 freeze_filter 的那个 Pi0Config 必须与 model 字段用同一组 variant，官方注释专门提醒过。写法是把同样的参数再构造一次：

# src/openpi/training/config.py，pi0_libero_low_mem_finetune 节选
model=pi0_config.Pi0Config(paligemma_variant="gemma_2b_lora",
                           action_expert_variant="gemma_300m_lora"),
...
freeze_filter=pi0_config.Pi0Config(
    paligemma_variant="gemma_2b_lora", action_expert_variant="gemma_300m_lora"
).get_freeze_filter(),
ema_decay=None,

两处写同样的参数看起来冗余，但这正是容易出错的地方：只改了 model 而忘了改 freeze_filter，冻结范围就会与实际模型对不上。

上述冻结与 LoRA 流程属于 JAX 训练入口。固定提交中的 PyTorch 训练脚本不支持 LoRA，也不会应用这套 freeze_filter；选择后端前应先确认所需能力。

八、显存与省显存手段

README 给出以下单卡估算。它们不是硬件保证；模型变体、batch、序列长度、后端、驱动和编译缓存都会改变峰值显存。

用途 显存下限 示例显卡
推理 大于 8 GB RTX 4090
LoRA 微调 大于 22.5 GB RTX 4090
全量微调 大于 70 GB A100 80GB / H100

JAX 路径常用的省显存手段：

  • 调整 JAX 预分配比例。XLA_PYTHON_CLIENT_MEM_FRACTION=0.9 允许 JAX 预分配更多显存，可能避免默认 75% 上限造成的 OOM，但会减少同卡其他进程可用空间，不能称为“无副作用”。
  • 分片参数。用 fsdp_devices 在单机多卡间切分模型状态，并在分片组之间做数据并行；通信会增加，固定提交的 JAX 训练不支持多机。
  • 禁用 EMA。减少一份参数树的训练状态，但需要重新验证导出权重的稳定性。
  • 使用 LoRA。减少可训练参数和优化器状态，是官方面向约 24 GB 单卡的方案；实际可行性仍取决于 batch、模型变体和运行环境。

十一、哪些是知识重点，哪些才是创新点

论文方法贡献跨本体数据混合、预训练与后训练的数据质量分工，以及 VLM 与 Flow Matching 动作专家的联合训练，是理解 π0 的主线。
模型接口设计把不同机器人的状态与动作装入固定宽度张量，并用显式图像槽位和 mask 统一观测接口，是多本体训练得以落地的重要条件。
工程实现归一化、AdamW、余弦日程、EMA、LoRA、FSDP 和检查点管理决定训练是否稳定、能否在现有硬件运行，但它们本身不是 π0 独有的算法创新。

最值得保留的判断方式是：先问一条结论属于论文方法、模型数据契约，还是固定代码版本的默认配置。只有第一类可以直接讨论“论文创新”；第二类要结合张量形状理解，第三类则必须带上版本、配置名和后端。
