系统架构与控制链路

VR 遥操作 RM75 机械臂的分体式进程架构、逆运动学选型、三层安全约束与夹爪控制链路

← 项目主页 ·系统架构 ·数据采集与保存 ·工程问题记录

一、为什么是四个进程

整套系统在运行时是四个独立进程 + 一个浏览器监控页，而不是一个大程序。这个划分不是设计洁癖，是被三条硬约束逼出来的。

约束一：高跟随模式要求指令间隔不超过 10 ms。 机械臂用 CAN-FD 高跟随透传时，控制器不再对每个目标做自己的平滑与阻尼，跟手感大幅提升，代价是指令流必须连续——一旦间隔超标，控制器会按自己的保护逻辑收尾。

约束二：Python 的 GIL 是每进程一把。 实测表明，在 110 Hz 主循环所在的进程里哪怕只增加一个纯 Python 后台线程，循环周期的中位数就会从 9.15 ms 涨到 14.20 ms（正好等于解释器默认的线程切换间隔）；加到三个线程时中位数 20.27 ms、最坏 90.98 ms。最反直觉的是，一个只做小 numpy 数组运算的线程也是 14.20 ms——开销全在 Python 对象层，而不是计算本身。相机抓帧加视频编码的负载远大于此，放进主循环必然击穿 10 ms 红线。

约束三：底层 SDK 有两个不可重入的全局状态。 机械臂的建连接口非幂等，重复建连会导致应答串包、读到坏数据、最终抱闸；VR SDK 是进程内全局状态，一个会话里只能有一套。所以采集进程绝不能自己连机械臂、也绝不能初始化 VR SDK。

三条合起来只有一个解：拆进程。

进程 职责 关键约束
夹爪守护 接收 UDP 指令，转成 ROS 2 Action 发给工控机 单槽串行，支持抢占
夹爪状态回传 订阅 /joint_states，把夹爪真实角度以 50 Hz 回传 跑在 ROS 2 的 conda 环境里
遥操作 唯一持有机械臂连接与 VR SDK；110 Hz 主循环；每帧广播状态包 主循环里不做任何会阻塞的事
数据采集 订阅状态包，30 Hz 抽样，写 HDF5；再派生一个独立的相机进程 不连机械臂、不初始化 VR、不加载 JAX

关键设计是：采集端并不知道自己在和另一个进程说话。它拿到的是一个接口完全一致的「假 loop 对象」——由状态包解出的字段拼装而成，同时扮演主循环、位姿源、机械臂后端、夹爪枢纽四个角色。因此录制器的代码一行都不用改，它原有的十几组离线单测继续有效，双进程产出的 HDF5 与单进程完全同构。

实测遥操作进程加上广播之后，主循环最坏单帧 1.7–1.8 ms，与不广播时没有差异；采集进程因为不加载 JAX 和 GPU，秒开，崩了重启也不影响机械臂。

二、从手柄到关节：一帧里发生了什么

坐标系映射

VR 头显给出的位姿在头显坐标系下，需要旋转到机械臂基座系。官方给的旋转矩阵在本工位实测下 Z 轴对、X/Y 反——现场相对官方标定姿态绕竖直轴转了 180°。左乘一个绕 Z 的 180° 旋转即修正，使得「手柄向右 → +Y、向上 → +Z、向前推 → +X」符合直觉。底座朝向若再变，只需再乘一个绕 Z 的旋转，不动其他任何代码。

离合式重定位

只有握住右手握把时机械臂才跟随，松开立即停止。松开再握 = 重新锚定：把当前手的位姿记为新的参考帧，机械臂不会跳。这让操作像用鼠标一样可以「抬起—放下」分段进行，不受人手臂物理活动范围的限制。

输入端低通

改成高跟随后，控制器原本「顺便」滤掉 VR 噪声的阻尼没有了，真机开始抖。解法是在噪声进入逆解之前先滤一道——实测在输入端滤比在关节端滤有效得多，降抖约 78%。

逆运动学：为什么从厂商方案换到 PyRoki

维度 厂商内置数值逆解 PyRoki
原理 黑盒 开放的最优化框架，每一项「愿望」都是可调代价项
自碰撞规避 不透明 显式的软代价 + 硬约束，裕量可精细标定
冗余处理 不可控 显式的「贴上一帧 + 偏 home」，行为可预测
可调性 几乎不可调 每个代价项的权重都能改
代价 快、无额外依赖 需要 JAX，单解 20–90 ms

换的动机很实际：厂商逆解在近身姿态和冗余处理上不透明，出了问题没法调；PyRoki 把一切摊开成可调的代价项。20–90 ms 的单解耗时靠异步 worker 化解——主循环提交请求后立刻取「当前最新可用解」，永不阻塞，代价是 1–2 帧滞后。

替换的正确性做了三重交叉验证：与厂商正解对比，基座系位置差均值与标准差均小于 1e-6 m，旋转角差 0.0011°；与厂商逆解对拍，关节角最大差 5.04°、均值 1.45°（七自由度冗余臂肘部解法不同，但末端一致，反而互证两者都对）；真机首解与实测关节角差 0.012°。

性能上踩过一个坑：自碰撞距离计算最初没做 JIT 编译，每帧 37 ms，把主循环直接拖到 25 Hz；加上 JIT 后降到 3.5 ms，回到当时的 50 Hz。（这是**引入异步 CAN-FD 后端之前**的阶段，那时主循环还受制于每帧一次阻塞式读关节；后来把读关节改成后台轮询加缓存，主循环才提到 110 Hz。）另外 JIT 首次编译要十几秒到几十秒，必须在进入控制回路前完成预热，否则第一帧就会卡住触发看门狗。

陈旧解门控

异步逆解带来一个隐蔽风险：松开握把或执行回位期间主循环不再调用求解，worker 里留着的是几秒前的旧解；再握把时它会被当成「新解」取出来用。曾经因此发生过握把瞬间七个关节全部朝旧位形跑飞 13.65° 的事故——准确地说，陈旧解决定了跑飞的方向，跑飞的量级另有原因（滤波器重置时把上一帧速度置成了空值，导致首帧逃逸限加速度约束），两层叠加才酿成事故，详见工程问题记录第 1 条。

解法是加时间门控：取解时若距上一次求解超过 0.1 秒就丢弃，保持不动、等两三帧新解出来再动。

三、安全层：三层限速加一次单帧钳制

144 °/s关节限速
1000 °/s²限加速度
8°单帧最大步长
0.03 / 0.01 / 0.002 m自碰撞三层裕量

第一层：限速 144 °/s。 RM75 的 j1/j2 额定速度只有 180 °/s（j3–j7 为 225），必须取最受限的。再打八折是被真机事故反推出来的：把指令限速设成 180 °/s 时，高跟随模式下真机会冲过指令——j1 实际冲到 211.6 °/s，超额定 17.6%，伴随电流飙升（j2 达 17.3 A，而按铭牌功率折算的连续额定电流约 4.2 A——伺服电机瞬时电流高于连续额定属正常，但这个倍数已经明显偏高）、撞限位、抱闸。乘 0.8 之后真机峰值约 169 °/s，回到额定的 94%。

第二层：接近限位时按刹车曲线降速，允许的速度上限取 √(2·a·剩余行程)——即「以当前减速能力，剩这么点行程最多还能跑多快」。这里不能用线性降速：刚进入降速区那一瞬所需的减速度可能高达 1380 °/s²，超过第三层的上限，会被拦住导致速度收不下来，反而冲出限位。

第三层：限加速度 1000 °/s²。 曾经出过这样的事故——自碰撞门连续拒解四秒后突然放行，速度从 0 瞬间跳到 82.7 °/s，折合约 9000 °/s²，直接抱闸。

这三层有一个共同的关键技巧：整体等比缩放，而不是逐关节截断。把整个关节增量向量除以「最大分量与上限之比」，关节空间的运动方向完全不变——机械臂「减速但不改道」。逐关节截断会让各关节比例变化，导致末端路径拐弯、抖动。实测等比缩放后方向余弦为 1，偏离直线 3.7e-16。

安全层另有一道粗糙但确定的单帧钳制：任何一帧的关节变化不超过 8°，这一层用逐关节截断，与滤波器的等比缩放互补。

自碰撞三层防线

软代价（裕量 0.03 m）→ 硬约束（0.01 m）→ 求解后安全门（0.002 m）。

调参过程有两条血泪经验：硬约束裕量要大——降到 0.001 会引发拒解震荡进而抱闸；安全门可以小——在全关节空间随机采样 8000 组构型做过一次实测，各档阈值下都没有出现「真碰撞被漏放」（0/8000）。这是抽样结果、不是理论保证，但足以说明把阈值调小换来的主要是更少的误拦。

早期这两个值是耦合在一起的（忽略阈值写成「硬约束 + 1e-3」），一改硬约束就连带改了安全门，怎么调都不对。修法是彻底拆开成两个独立参数。中途还因为一次基于「固定其余关节」的错误扫描而下调了阈值，引发过两次真机抱闸掉使能事故。

四、六层包装式改造

整套系统在上游内核之上叠了六层，每一层都是新增文件，用子类继承或运行时替换接入，上游代码一个字都没改。

层 加了什么
遥操作内核（上游） 主循环、VR 位姿源、机械臂后端、安全层
+ PyRoki 逆解层 七自由度约束逆解、三层限速滤波、键盘回位、异步 CAN-FD 后端
+ 闭环安全层 陈旧解门控、滤波器零速度重置、安全回位
+ 加速度平滑层 目标接近提前减速、坏读数多帧一致性重锚
+ 夹爪层 三段扳机判定、UDP 指令通道
+ 底座偏航层 绕 Z 的坐标修正
+ 数据采集层 状态广播、录制状态机、相机进程、五个运行时补丁

每层入口脚本用「只解析自己关心的参数、其余原样透传给下一层」的方式串起来，因此任何一层都能单独摘掉回退。

五、夹爪链路

夹爪走一条完全独立的通道，不占用机械臂的控制回路。

指令方向：遥操作进程读右手扳机 → 三段判定 → UDP 发给夹爪守护进程 → 转 ROS 2 Action → 工控机执行。三段的阈值是扣到底才夹（≥0.95）、松到底才全开（≤0.05），中间为半开。

阈值经历了 0.6/0.3（两态）→ 0.8/0.2（三态首版）→ 0.95/0.05（调灵敏度）三轮。加三态时踩了个坑：原来的 0.3~0.6 是「保持原状态」的死区，改成三态后中间那段本身成了一个状态，两个边界就变成了硬分界——扳机停在阈值附近会在两个状态间反复跳，而每次夹紧服务端要约 0.5 秒判稳，夹爪就来回抽搐。解法是两个边界各留 0.05 的迟滞。

反馈方向：一个独立的 ROS 2 进程订阅 /joint_states，把夹爪真实角度以 50 Hz 经 UDP 回传给采集端，写进数据集。失联超过 0.5 秒就记 NaN 并计数降级步数，不静默用期望值顶替。

六、回位

按键盘 h/o 或按下左手摇杆可让机械臂回到 home 位形或零点。回位走的是纯关节插值加梯形速度规划，不经过逆解。

这套速度规划最初有三个缺陷，导致关节加速度超设定上限 1.7–2.1 倍（实测 15 个距离组合里 13 个超标，最坏 820 °/s² 对 400 的上限）：减速途中判据会重新跳回加速分支产生锯齿；起刹晚一帧，等判据成立时其实已经刹不住了；落位时速度从一个不小的值直接归零。修正后 15 个组合全部落回上限内，末段速度单调递减，常用场景耗时只增加 1%。

修这个问题时自己制造过一个新 bug：为了处理落位突降，一开始写成「直接把速度压到目标值」，结果把 1.14 °/s 一步压到 0.32 °/s，凭空造出 90 °/s² 的新跳变。正确做法是**限制降幅**，而不是限制绝对值。

七、两个 conda 环境，不能合并

系统跑在两个互斥的 Python 环境里：

  • ROS 2 环境：ROS 2 Humble + rclpy，numpy 1.26.4 —— 跑夹爪守护与状态回传。
  • 遥操作环境：JAX + PyRoki + h5py + OpenCV，numpy 2.3.5 —— 跑遥操作、数据采集、回放与全部离线测试。

两个环境的 numpy 版本互斥，这是它们必须分开、不能合并的根本原因。具体故障是：如果在遥操作终端里误载入了 ROS 2 的环境脚本，numpy 1.26.4 会被塞进 PYTHONPATH，JAX 随即报错，整条真机链路全废。

还有一个容易踩的点：目录归属不等于环境归属——夹爪状态回传脚本虽然放在数据采集目录下，但它导入 rclpy，必须跑在 ROS 2 环境里。
