专题总览 5 模型谱系 6 训练与适配 7 长时序任务

训练产物不是“一个 loss 降下来的权重文件”，而是与数据、目标、参数所有权、优化状态、评测证据和回滚关系绑定的候选策略版本。拿到候选基座和新机器人后，第一步不是运行脚本，而是冻结输入 checkpoint、数据 release、目标路由、可训练范围、停止与选择规则。

  • 一次训练阶段是可追溯对象。 输入、数据、目标、参数、优化状态、停止规则和输出缺一不可。
  • 比例不能混写。 原始数据占比、目标采样概率、实测 batch 频率、loss 权重与梯度贡献是五个不同量。
  • 冻结必须可验证。 learning rate 为零不能替代 autograd、optimizer、mode、buffer 与 serialization 检查。
  • 最低离线 loss 只能筛候选。 它不能替代闭环 rollout、旧能力保持、延迟和安全门禁。
  • 发布必须可撤销。 approved、active、superseded、rolled_back 与 takedown 是不同状态。

本页只设计研究和受控评测的证据链，不下载权重、不运行训练或推理、不连接机器人、不执行部署。偏好优化、在线强化学习与 reward model 属于 RLT/RLHF-VLA 分支，不会被普通 SFT 名称掩盖。

先定义训练生命周期，而不是先运行脚本

六类阶段术语

| 术语 | 本页定义 | 典型输入 | 典型输出 | 不能推出 | | — | — | — | — | — | | VLM pretraining | 图像/文本等通用多模态预训练 | 大规模非机器人多模态数据 | VLM 权重与处理器 | 已具备低层控制 | | robot foundation pretraining | 跨任务/本体机器人数据上的策略基础训练 | VLM 或随机初始化、机器人数据 | 通用机器人策略基座 | 适合目标机器人 | | Co-training | 同一阶段联合抽样多个 source/objective | 异构 web、机器人、高层语义、低层动作样本 | 共享或分路参数更新 | 原始数据拼接即可 | | SFT / target adaptation | 用带监督目标数据适配目标域 | 基座 + 目标机器人数据 | 目标域候选权重 | 必须全参数更新 | | post-training | 基座后的统称，可含 SFT、偏好、RL、蒸馏 | 基座与额外反馈 | 后训练候选 | 等同 RL | | continual adaptation | 多个时间顺序 release 上持续更新并保持能力 | active/base + 新旧 release | 版本链和保持证据 | 简单继续训练即可 |

术语卡必须写“数据/目标维度”和“参数更新维度”正交。SFT 说明监督形式，LoRA 说明参数化方式，两者不能互相替代。

训练阶段七元组

页面把阶段定义为：

Stage = (Init, DataRelease, ObjectiveRouting, ParameterOwnership, OptimizerState, StopRule, Output)

每项至少包含：

  1. Init：checkpoint identity、hash、model config、加载策略。
  2. DataRelease：不可变 release ID、split、fingerprint、license。
  3. ObjectiveRouting：样本类型→可用 label→loss→权重→denominator。
  4. ParameterOwnership：trainable/frozen/generated/merged 参数和 buffer。
  5. OptimizerState：optimizer、scheduler、scaler、EMA、step 与 RNG。
  6. StopRule：预算、异常、安全、offline gate，不以单一 loss plateau 替代闭环选择。
  7. Output：训练 checkpoint、weights-only export、evidence bundle 与 lineage。

任一项为 unknown 时可以做研究探索，但不得写“可复现”“可恢复”或“可发布”。

阶段 DAG 而非覆盖式目录

推荐版本关系：

immutable_base → stage_run → candidate_checkpoint → evaluated_candidate → approved_release → active_release

旁路状态：

  • rejected：未通过预注册门禁，不删除证据。
  • quarantined：制品、数据、许可证或安全证据不完整。
  • rolled_back：曾激活后撤回，保留原因和替代版本。
  • superseded：被新批准版本替代，不等于失败。
  • takedown：因安全、许可证、数据撤回等停止使用。

文件名“latest”“best”“final”不得成为唯一版本身份；页面要求稳定 run ID、step、hash 和父节点。

三种 checkpoint 产物

| 产物 | 内容 | 用途 | 常见错误 | | — | — | — | — | | training checkpoint | 模型、optimizer、scheduler、scaler、EMA、step、RNG、sampler/cursor 等 | 中断恢复与审计 | 只保存 weights 却称 resume | | weights-only export | 推理所需权重和模型配置 | 评测、转换或下游初始化 | 缺 tokenizer/norm/assets | | deployment bundle | 权重、processor、prompt、I/O contract、norm、runtime manifest、签名/哈希 | 后续受控部署 | 未经批准就由训练目录直接加载 |

本页只设计 deployment bundle 字段，不生成 bundle。

停止规则与选择规则分开

  • 停止规则回答“这个 run 何时停止产生新 checkpoint”。
  • 选择规则回答“已产生的哪些 checkpoint 进入更昂贵评测”。
  • 发布规则回答“哪个 evaluated candidate 可以成为 approved/active”。
  • 回滚规则回答“出现何种信号时退回哪个已知版本”。

不得把 early stopping、best validation loss、best rollout 和 approved release 写成同一个状态。

生命周期验收要落到证据，而不是命名。 在训练启动前，先为七元组逐项生成不可变 run manifest：所有外部引用解析为 release ID 与摘要，所有默认值展开，所有空字段保留为显式 unknown。manifest 的内容摘要成为 run ID 的组成部分；后续任何数据、路由、可训练范围或停止条件变更，都创建新的 stage 节点，不能在原目录里覆盖配置继续跑。

建议把阶段 DAG 做成追加式事件账本。每条事件至少包含 event_id、父状态、目标状态、触发原因、操作者或批准者、时间、输入和输出摘要。重复提交同一事件应保持幂等；越级转换、父制品不存在或摘要不匹配时应 fail closed。这样既能回答“当前 active 是谁”，也能沿父边重建它为何被批准。

停止原因也要分类保存：预算耗尽、预注册步数完成、数值异常、数据耗尽、基础设施中断、离线安全门禁触发、人工终止分别使用稳定枚举。completed 只说明 run 不再产生 checkpoint，不代表最后一个 checkpoint 最好，更不代表获得发布资格。中断时还要记录最后一个一致 step、最后一个落盘 checkpoint 与尚未提交的 accumulation 状态。

每个候选的最小证据包应同时包含 run manifest、配置展开结果、代码与依赖摘要、数据 release、参数所有权快照、逐源统计、异常事件、checkpoint 清单及选择状态。训练日志是时间序列证据，manifest 是身份契约，两者不能互相替代。若账本与制品目录冲突，以可验证摘要和批准记录为准，并把冲突升级为 quarantine，而不是猜测“最新文件”。

在真正使用算力前，可以做一轮“不训练验收”：解析配置、枚举数据 release、构造路由表、加载初始化资产、列出参数组、演算停止与输出路径，但不执行优化步骤。该验收的输出应足以让另一位审阅者判断七元组是否闭合，并提前发现默认值漂移、路径指向可变目录、候选覆盖和回滚目标缺失。

权限边界也属于生命周期契约。数据负责人可以批准 release，模型负责人可以批准候选进入评测，机器人与安全负责人决定是否进入受控闭环；这些角色可以由同一组织承担，但批准事件不能被训练进程自行生成。服务账号只获得写入当前 run 目录、登记候选和读取已批准输入的最小权限，不应能够改写 base、历史评测或 active 指针。权限失败、凭据过期和存储不可用都应进入停止分类，并保证失败前已提交的 checkpoint 仍可验证。

一次合格的阶段评审不是“配置看起来合理”，而是审阅者能从 manifest 复算关键事实：输入摘要是否与父节点一致，数据与目标是否闭合，所有可训练参数是否有 owner，停止条件是否能被机器判定，输出是否有唯一落点。评审结论写成 pass、conditional pass 或 fail；conditional pass 必须列出截止状态与补证材料，不能在条件尚未闭合时把候选推进为 approved。

初始化与预训练：从哪组权重开始

三种启动语义

Scratch。

随机或规则初始化全部需要训练的参数。必须记录 initialization seed、模块初始化方式和未从基座继承的能力。适合架构探索或有充分机器人预训练预算的情形；不能把“没有旧偏置”写成“更好”。

Initialize / warm start。

从 VLM、机器人基座或之前权重加载可兼容参数，建立新的 run。optimizer、scheduler、step 和数据 cursor 可重新初始化。必须记录 missing/unexpected keys 和有意重置的模块。

Exact resume。

恢复同一 run 的训练语义。除模型参数外，至少核对 optimizer、scheduler、scaler、EMA、global step、RNG、distributed sampler、数据 cursor、gradient accumulation 与代码/配置。无法恢复这些状态时，应称“从 checkpoint 重新初始化新 run”，不能称 exact resume。

初始化兼容矩阵

加载前必须进行 fail-closed 检查：

| 契约 | 检查对象 | 不匹配处理 | | — | — | — | | 架构 | model family、层数、hidden size、action head/expert | 明确迁移规则；默认拒绝静默加载 | | tokenizer | 词表、special token、action token 范围 | 重建映射或拒绝；不得按索引猜 | | vision processor | resize、crop、颜色、归一化、相机顺序 | 生成差异报告并重新验证 | | prompt/template | system/user 模板、任务字符串、占位符 | 固定版本；不得静默改变 token 边界 | | observation schema | 图像、状态、历史长度、mask | adapter 必须有版本和测试 | | Action ABI | 维度、顺序、坐标、absolute/delta、单位、频率 | 不兼容时禁止直接加载 action head | | normalization | q01/q99、mean/std、per-dim mask、asset ID | 与训练数据 release 绑定 | | embodiment/task IDs | 枚举、索引、unknown | 未知值默认拒绝而不是映射 0 | | PEFT state | base hash、target modules、rank、merge 状态 | base 不一致时拒绝合并 | | runtime assets | code commit、dependency、precision | 进入评测前锁定 |

页面展示两种结果：

  • compatible：所有强契约一致，有可验证 hash。
  • migration_required：存在显式转换与验证计划。
  • incompatible：Action ABI、family 或关键资产无法安全映射。
  • 不使用模糊的“基本兼容”。

VLM 初始化与机器人预训练

初始化决策要回答：

  1. VLM 带来哪些视觉/语言表征，哪些低层控制能力尚不存在？
  2. 新 action head/expert 如何初始化，是否先单独预热？
  3. 视觉、语言、状态和 action 模块分别更新还是冻结？
  4. 机器人数据是否足够覆盖目标视角、状态与控制分布？
  5. web/VLM 能力是否需要 retention suite？
  6. 基座许可证、权重使用条款和数据来源是否允许目标用途？

页面不得暗示“大 VLM 初始化必然优于小模型或 scratch”。比较必须配对数据、计算、参数更新范围和闭环协议。

机器人基础预训练与目标域适配

基础预训练追求跨任务/本体可复用表示；目标域适配追求特定机器人和任务上的闭环能力。两者必须分别记录：

  • 数据覆盖与 unit；
  • 任务/本体条件；
  • action adapter 和 normalization；
  • 目标函数与可用标签；
  • 参数范围；
  • 输出 checkpoint；
  • 选择协议；
  • 保持/迁移证据。

目标域数据若已进入基座预训练，不得将训练集近乎完美的 action accuracy 当作独立泛化；必须登记数据重叠和 contamination。

新模态与新本体的四种选择

  1. 映射到已有 slot：仅在语义、几何和 mask 契约可证明等价时。
  2. 增加 projector/stem：保留共享主干，但必须初始化并验证新模块。
  3. 增加 per-embodiment head/adapter：隔离接口差异，增加路由和版本成本。
  4. 重新设计主干：只在已有接口无法表达时，视为新 architecture/version。

全零占位不是新增模态方案。每个 slot 必须有 value + availability_mask + source + missing_reason。

模型特定示例框

示例框必须带“不是通用默认”徽标：

  • OpenVLA 官方实现同时提供 LoRA 与全量微调入口；全量路线的计算与分布转移假设不能外推到其他模型。
  • openpi 配置展示 full 与 LoRA/freeze filter 路线；checkpoint family、config、资产与 normalization 必须匹配，且不同实现后端支持范围可能不同。
  • π0.5 论文的分阶段目标与异构样本是模型特定设计；精确步数与 loss 系数留在 π0.5 页。
  • SmolVLA 的冻结 VLM、训练 action expert 是一种资源/遗忘取舍；不是所有小数据任务的默认最优解。
  • GR00T N1 的跨本体预训练和单本体 post-training 提供遗忘案例；具体冻结组件与比例留在模型页。
  • X-VLA 的 staged adaptation 与 soft prompt 是实例；zero learning rate、缺少 optimizer state 的 checkpoint 等陷阱用作审计提示。

初始化报告应把“成功加载”拆成四层：制品可读取、张量名可映射、接口契约兼容、行为基线可复现。许多框架在 strict=false 下仍能返回模型对象，但 missing keys 可能正好位于 action expert，unexpected keys 也可能说明加载了错误 family；因此报告必须列出每一个未匹配参数，并按“预期新增、允许迁移、必须拒绝”分类，不能只展示数量。

Scratch、warm start 与 exact resume 的公平比较需要同一数据 release、等价有效更新预算、相同候选保存频率和同一闭环选择协议。若 warm start 更快到达某离线阈值，应同时报告总计算和最终闭环表现；若 scratch 使用更多步数或不同数据，它回答的是另一问题。对于 exact resume，还应在一个小型固定批次上比较中断前后的下一步 loss、采样索引和参数摘要，明确分布式执行中哪些差异被允许。

迁移不是一次 load_state_dict。任何 tokenizer 扩展、相机顺序变化、状态维度重排、动作头替换或 normalization 更新，都要生成迁移清单：源字段、目标字段、转换函数、不可逆信息、单元测试、迁移前后摘要和批准人。新增参数要记录初始化分布与 seed；丢弃旧参数要说明它为何不再参与行为；复用名称但改变语义应视为不兼容，而不是“形状相同即可”。

新模态验收至少包含三组反例：真实值且 mask 为真、占位值且 mask 为假、故意构造的值与 mask 冲突。路由器必须对冲突给出确定错误，而不是把它送入主干。新本体还要对 task/embodiment ID 的 unknown 路径做测试，确认不会落到索引 0，也不会错误复用另一机器人的 action adapter 或归一化资产。

所有外部基座都需要开放制品记录：来源页面、版本或 commit、文件摘要、许可证版本、获取日期、原始模型卡、处理器资产和已知限制。页面只引用这些记录，不把“公开可下载”当作许可结论。若后续撤回某个数据或权重来源，lineage 查询应能列出所有受影响候选并阻止其继续 promote。

初始化后还应保存一组不涉及训练的行为指纹：固定预处理输入、关键中间张量的 shape/统计、动作输出 schema、参数与 buffer 摘要。它不用于证明任务能力，而用于区分“权重相同但 processor 不同”“加载成功但 action head 未恢复”“同一 checkpoint 在不同 runtime 下数值漂移”。指纹输入不得包含敏感数据，并需与模型版本一起维护；架构有意变化时新建指纹版本，不能覆盖旧基线。

Exact resume 的确定性应按现实边界表述。单设备固定 kernel 可能做到下一步近似一致，分布式通信、数据 worker 或非确定算子则可能只保证统计等价。报告要列出 deterministic flags、允许容差与已知非确定源，并通过短窗口对照判断 loss、梯度和采样是否偏离。无法做到逐位一致不等于不能恢复，但若连数据 cursor、step 与 scheduler 都无法对齐，就不能用“硬件噪声”解释语义断裂。

Co-training：数据、目标、条件与缺失模态怎样路由

五个经常被混用的比例

页面必须用同一示例同时显示：

  1. raw_storage_fraction：落盘样本占比。
  2. target_sample_probability：采样器期望概率。
  3. empirical_batch_frequency：实际 batch/样本频率。
  4. loss_weight：目标函数前的显式系数。
  5. gradient_contribution：考虑有效 token、尺度、mask、accumulation 后的实测更新影响。

若第 i 类样本抽样概率为 p_i、有效标签数为 n_i、loss 权重为 λ_i，其梯度贡献不等于 p_i 或 λ_i；至少记录：

g_i = || ∇_θ (λ_i · L_i / denominator_i) ||

该式用于诊断，不暗示只凭梯度范数就能决定最佳配比。

分层采样设计

推荐先定义 hierarchy：

source_family → dataset/release → embodiment → task → episode/window

每层写：

  • unit：episode、step、window、token 或 pair；
  • base size 与有效 size；
  • target probability；
  • replacement 与 exhaustion 行为；
  • temperature/cap/floor；
  • per-epoch 或 per-step 重新采样；
  • distributed worker 的确定性；
  • 实测频率和置信区间/偏差。

采样器必须输出审计日志，不能只记录配置值。

混合 batch 与交替 batch

| 策略 | 优点 | 风险 | 必须记录 | | — | — | — | — | | mixed batch | 同步更新共享参数；吞吐可能更稳定 | padding/mask 复杂、目标尺度混合 | 每样本 route、有效 denominator | | homogeneous microbatch | 模态/shape 简单，便于统计每源梯度 | 更新顺序和 accumulation 影响 | microbatch 顺序与合并规则 | | round-robin | 可控覆盖 | 小源过采样、周期性偏差 | 周期、exhaustion、shuffle | | stochastic source per step | 期望简单 | 短窗口方差大 | seed、实测频率 | | curriculum/stage switch | 可逐步解冻或加目标 | 阶段切换引入分布突变 | 边界 checkpoint 与验证 |

页面不推荐唯一策略；要求能重构“哪个参数在何时接收哪类梯度”。

Objective routing 表

每类样本必须明确：

| 字段 | 示例含义 | | — | — | | sample_type | web_vqa / robot_action / high_level_subtask / target_robot | | available_modalities | image、language、state、action | | availability_mask | 每个 slot 是否真实存在 | | available_labels | text target、action target、subtask target | | active_objectives | LM、action BC、flow、auxiliary | | loss_weight | 显式数值与 schedule | | denominator | valid token / action dim / sample | | gradient_targets | trunk、projector、action expert、adapter | | stop_gradient | 哪条路径不反传 | | logging_key | 独立 loss、count、grad norm | | failure_policy | 缺 label、未知 ID 或 shape 错误时拒绝/隔离 |

不能用一个总 loss 曲线替代分路统计。

任务与本体条件

条件可以进入：

  • 自然语言 prompt；
  • learned task/embodiment ID embedding；
  • soft prompt；
  • per-embodiment stem/head；
  • action adapter 和 normalization asset；
  • router/gating。

每种方式必须回答：

  1. ID 的权威枚举来自哪里？
  2. train/eval 是否使用同一映射？
  3. unknown ID 是拒绝、fallback 还是明确 zero-shot route？
  4. 条件是否泄漏测试身份或场景标签？
  5. 条件是否参与归一化和 action decode？
  6. 新本体添加后旧 ID 是否保持稳定？

不得用数组位置或目录排序隐式生成永久 ID。

缺失模态处理

缺失模态必须区分：

  • 未采集；
  • 传感器故障；
  • schema 不适用；
  • 被 augmentation/dropout 主动遮蔽；
  • 因隐私/许可证不可用；
  • 对该 objective 不需要。

处理选项：

  • 固定占位值 + 显式 mask；
  • learned missing token；
  • route 到不依赖该模态的子图；
  • modality dropout 训练；
  • 拒绝该样本。

不得仅靠 NaN、全零或空字符串让模型自行猜。mask 还要进入 attention/目标 denominator，并测试“有值但 mask=false”和“缺值但 mask=true”的错误路径。

防止信息泄漏

  • 动作目标 token 不得从输入侧穿过错误 attention mask。
  • 未来帧、未来状态和 episode 终止不得泄漏给因果策略。
  • normalization 统计只从允许的训练 split 计算。
  • target task ID 不得编码 test-only 场景答案。
  • teacher plan 或 privileged state 若只在训练使用，必须声明推理时替代来源。
  • augmentation 必须保持图像、状态、动作和 mask 的时序/几何一致。
  • co-training 的 web 文本若含 benchmark answer，需登记 contamination 风险。

采样与梯度诊断

至少按 source/objective 记录：

  • requested 与 realized sample counts；
  • dropped/invalid/masked counts；
  • valid token/action counts；
  • loss 均值、方差和分位数；
  • gradient norm；
  • 共享参数上的梯度 cosine 或冲突信号；
  • throughput、padding 比例和 OOM/retry；
  • 每类数据的有效 wall-clock 占用。

梯度冲突只作为诊断。页面不得把 PCGrad、loss rescaling 或 gradient surgery 写成默认解；任何介入都要通过配对消融和闭环保持验证。

采样配置之外，还要保存逐步事件流或可聚合的等价记录。单条记录至少能恢复 source family、dataset release、embodiment、task、episode/window、worker、采样概率、是否 replacement、是否被丢弃及其原因。审计时先比较 requested、drawn、valid 和 optimized 四个计数；只有最后一个真正进入了某个 objective 的 denominator。这样可以区分“配置比例没生效”“样本被 schema 拒绝”和“样本存在但没有可用标签”。

denominator 是 Co-training 最容易被隐藏的放大器。语言 loss 可能按有效 token 平均，动作 loss 可能按 action dimension、chunk 或 sample 平均；padding、可变 horizon 与缺失维度会改变每类样本的有效权重。每个 objective 应记录 numerator、denominator 与显式系数，并在聚合前保留 source 切片。只看最终标量无法判断小数据源被过度放大还是被大量 padding 稀释。

mixed batch 的正确性需要逐样本 route 单元测试：同一 batch 内的 web 样本不得触发 action loss，机器人样本缺少文本目标时不得生成伪 LM 标签，辅助目标只能更新声明的模块。homogeneous microbatch 或梯度累积还要固定合并顺序和缩放规则，验证拆成两个 microbatch 与等价大 batch 在允许误差内产生一致更新。

task、embodiment、dataset 与 normalization 的 ID 应来自带版本的权威 registry。训练配置引用语义 ID，加载时再解析为稳定索引，并保存解析结果；禁止用文件排序、首次出现顺序或 worker 局部枚举生成永久映射。registry 新增条目只能追加或显式迁移，旧索引变化会使已有 checkpoint 的条件语义失效。

缺失模态注入是必要的压力测试。对每一种 missing reason，构造“缺值且正确 mask”“有占位但关闭 attention”“故障值被隔离”的样本，检查 loss denominator、attention、缓存和日志是否一致。modality dropout 必须使用独立的 augmentation 标志，不能伪装成传感器故障，否则真实故障率和训练增强率会混在同一统计中。

信息泄漏排查应从 batch 构造追到 attention 与缓存：随机打乱未来动作、遮蔽 teacher plan、替换 test-only task ID、只用 train split 重新计算 normalization，并检查输出是否按预期变化。若移除一个理论上不可见的字段却显著改变结果，先 quarantine 该路由，而不是继续调 loss 权重。

梯度诊断最终要回答“谁在更新共享参数”。按 source/objective 采样梯度范数与 cosine 时，记录采样频率、参数子集和精度；与 realized frequency、有效 denominator、吞吐和 optimizer step 对齐。发现冲突后，先排除单位、mask、标签和数据质量问题，再做权重或梯度手术消融，并用同一闭环协议验证是否真的改善。

可以用一张小型对账表快速发现比例错觉：配置要求源 A/B 的目标概率为 70/30，事件流却显示 drawn 为 68/32、valid 为 60/40、optimized 为 45/55，同时 B 的每样本有效 action 数更高。此时不能声称“训练采用 70/30 混合”；报告应分别保留四层频率、denominator 和梯度贡献，再定位 A 的 schema 丢弃或 mask 是否异常。任何重新加权都从新的假设和配对实验开始，而不是事后把 observed 结果重新命名为目标比例。

路由测试应覆盖正例、负例和组合例。正例证明每种合法 sample type 激活预期 objective；负例证明缺标签、未知 ID、非法 shape 和冲突 mask 被拒绝；组合例证明 mixed batch 中每个样本只贡献允许的分子与分母。测试还要比较单样本运行与混合运行的对应 loss，防止 batch-level 条件误把一个样本的模态可用性广播给整批数据。新 source 接入时先通过这组测试，再允许进入真实采样器。

每次 run 都生成机器可读清单，至少包含：

  • parameter name；
  • module/owner；
  • base/new/adapter/generated；
  • trainable boolean；
  • requires_grad；
  • optimizer group；
  • learning rate / weight decay；
  • dtype；
  • parameter count；
  • load source；
  • save destination；
  • merge status；
  • expected gradient；
  • observed gradient norm。

页面显示四个汇总：

  1. total parameters；
  2. requires-grad parameters；
  3. optimizer-owned parameters；
  4. observed-updated parameters。

冻结语义的五项检查

  1. Autograd：冻结参数是否 requires_grad=false，是否有意保留输入梯度。
  2. Optimizer：冻结参数是否完全不在 optimizer group；zero LR 不作为唯一证明。
  3. Mode：模块处于 train 还是 eval；dropout、BatchNorm 等行为是否预期。
  4. Buffers：running stats、EMA、quantization calibration 等是否变化。
  5. Serialization：保存/加载是否保留冻结/adapter/merge 关系。

测试需要在一个受控 step 前后比较参数和 buffer hash，并允许明确列出的非参数状态变化。

LoRA、Adapter 与合并状态

LoRA manifest 至少记录：

  • base checkpoint hash；
  • target module pattern；
  • matched module list；
  • rank、alpha、dropout；
  • trainable bias/embedding/head；
  • adapter dtype；
  • merged/unmerged；
  • merge tool/version；
  • merge 前后数值校验；
  • 多 adapter 的选择/组合规则。

Adapter manifest 还记录 insertion point、bottleneck 和路由。soft prompt 记录 prompt length、ID mapping 和初始化。

不得把“adapter 文件很小”当作独立可运行；没有正确 base 和 processor 时它不是完整策略。

资源预算拆分

显存/内存至少拆成：

  • 基座参数；
  • 可训练参数的梯度；
  • optimizer states；
  • activations 与 attention；
  • EMA/target copy；
  • batch、sequence、image resolution 和 action horizon；
  • distributed/sharding/quantization overhead；
  • dataloader/prefetch。

PEFT 通常减少可训练参数和 optimizer state，但不会自动消除主干前向、激活或数据成本。若训练需要梯度穿过冻结主干到早期可训练模块，激活保留仍可能很高。

选择决策树

  1. 先检查 Action ABI/模态是否可表达；不可表达则先改接口，不靠 LoRA 修补。
  2. 若新数据少且需强保持，先试隔离 head/adapter/LoRA，并设 retention gate。
  3. 若域差主要在视觉/语言或本体接口，针对相关模块做 partial unfreeze 消融。
  4. 若大分布转移且有足够数据/计算，可评估 full fine-tuning，但必须加强保持与回滚。
  5. 若多本体共享基座，优先显式 per-embodiment adapter/head 与稳定路由，而不是让一个隐式 ID 承担全部差异。
  6. 任一路线都用 matched budget 和相同闭环 protocol 比较，不能只比 trainable count。

阶段式解冻

阶段式方案必须写出每个边界：

  • Stage A：新增 head/projector 预热；
  • Stage B：加入 LoRA/Adapter 或部分解冻；
  • Stage C：必要时更广范围联合更新；
  • 每次切换重新声明 optimizer、scheduler、EMA、loss routing 和数据 mixture；
  • 边界 checkpoint 独立保存并评测；
  • 不在同一日志中静默改变 trainable set。

阶段式训练不是必然更好；它只是把参数变化和证据分段，使失败更容易定位和回滚。

参数所有权快照应在三个时点生成：加载后、optimizer 构造后、第一次有效更新后。第一份证明初始化来源，第二份证明 optimizer 实际拥有谁，第三份用参数与 buffer 摘要证明谁真的变化。声明 trainable 却没有梯度、进入 optimizer 却没有更新、声明 frozen 但 buffer 改变，都要形成差异项而不是被汇总百分比吞掉。

冻结测试不只看参数值。固定输入下分别运行 train/eval mode，检查 dropout、BatchNorm、EMA、量化标定、缓存与随机增强；完成一个 optimizer step 后比较参数、buffer 和 optimizer state。允许变化的对象采用白名单，任何未列出的变化使候选进入 quarantine。这样才能区分“数学上没有梯度”和“运行时行为保持不变”。

LoRA 与 Adapter 的身份是 base 摘要加目标模块清单再加自身权重。合并前后要在固定输入上做数值对照，并保存容差、精度、merge 工具版本和反合并能力；多 adapter 还要测试错误路由和 unknown route。若部署端只拿到 adapter 文件却解析不到唯一 base，加载必须失败，不能搜索一个“看起来相近”的本地权重。

资源报告应区分峰值设备内存、主机内存、持久存储、训练吞吐与评测延迟。PEFT 的参数文件较小，不代表激活、视觉编码或 action chunk 推理便宜。比较 head-only、LoRA、partial 和 full 时，应统一图像分辨率、序列长度、batch 定义、precision、checkpointing 与分布式策略，否则“节省百分比”不可解释。

matched-budget 消融至少给两种视图：相同 wall-clock/设备预算下谁更好，以及相同有效 optimizer step/样本预算下谁更好。两种排序可能不同，必须同时保留。每个候选沿用相同数据 release、selection rollout 和 retention suite；若某路线因 OOM 改小 batch，还要重新声明 accumulation、denominator 与学习率规则。

阶段式解冻的边界应像新的 stage 一样验收。切换时保存边界 checkpoint、更新参数所有权表、重建 optimizer groups、声明 scheduler 是否重启并验证旧状态是否兼容。不得在一个长 run 里通过配置热更新静默增加可训练层，否则无法把收益或遗忘归因到具体阶段。

最先修复的始终是接口表达能力。如果新机器人动作语义、单位或时序不能被现有 Action ABI 表达，任何 PEFT 方法都只能拟合错误编码；如果模态路由遗漏有效信号，扩大可训练范围也不会恢复信息。只有接口和数据契约通过反例测试后，参数效率比较才有意义。

序列化验收要覆盖未合并与已合并两条路径。未合并路线重新加载 base 加 adapter 后，应重现固定输入输出和 ownership；已合并路线要证明目标权重包含预期增量，同时不再错误加载同一 adapter 两次。转换为不同 precision、分片或部署格式时，每一步都生成父子摘要与数值对照。若转换工具丢失 processor、normalization 或 prompt 资产，即使权重张量一致，也只能标为不完整 export。

参数差异报告应从模块汇总下钻到异常名单：预期变化模块给出变化范数和占比，冻结模块给出最大差异，新增与删除参数给出来源说明，buffer 单独列示。仅以全局 hash 不同无法定位问题，仅以若干抽样参数相同也无法证明冻结。对于共享 embedding、tied weights 或量化参数，要显示别名关系和物理存储，避免同一更新被重复计数或漏记。

Checkpoint 选择与遗忘评估：离线 Loss 不是闭环表现

五层证据漏斗

  1. 完整性：hash、配置、加载、NaN、shape、asset、license。
  2. 离线门禁：分路 loss、held-out prediction、校准、数据切片。
  3. 仿真闭环：固定环境版本、seed、任务、扰动和控制接口。
  4. 受控真机：小范围、限速、人工接管、停止条件、硬件状态。
  5. 保持/安全：旧任务、本体、语言/视觉能力、延迟、干预和失败类型。

较低层失败时，不进入更昂贵或更危险层。较高层通过不能倒推较低层数据/许可证完整。

数据划分角色

| 集合 | 用途 | 是否可反复看 | 是否可用于选择 | | — | — | — | — | | train | 优化参数 | 是 | 不独立选择 | | validation | 诊断、early stopping、候选筛选 | 有限、需记录 | 可用于预注册离线门禁 | | selection rollout | 比较候选的闭环集合 | 有限、固定协议 | 可 | | retention suite | 检查旧能力 | 每版固定 | 可作为否决门禁 | | final test | 最终报告 | 只在冻结后 | 不得回流选择 | | safety challenge set | 风险/故障门禁 | 受控 | 可否决，不作为性能加分 |

当 selection rollout 被频繁用于调参时，它已成为 validation，应建立新的 final test。

Candidate pool

  • 按预定 step/epoch/compute interval 保存，而非看到好曲线后临时加密。
  • 同时保存阶段边界、异常前后和最佳离线门禁候选。
  • 每个 candidate 绑定同一 run manifest、父 checkpoint 和代码。
  • 候选数量与 rollout 预算事先限定。
  • 损坏、不兼容或证据不全候选直接 quarantine。
  • 不让“last”自动进入发布评测。

选择协议

选择前冻结：

  • candidate list；
  • environment/robot version；
  • task and scene list；
  • trial/seed；
  • initialization/reset；
  • operator/intervention policy；
  • success/partial/failure definition；
  • latency/safety metrics；
  • aggregation；
  • tie-break；
  • safety veto；
  • missing/aborted trial 处理。

若 safety、success、retention 与 latency 冲突，优先展示 Pareto front 和硬门禁，不用任意加权总分隐藏取舍。

离线指标的适用边界

可以用于：

  • 检查训练是否发散；
  • 比较相同数据/目标/denominator 下的候选；
  • 定位某 source、task、action dimension 的异常；
  • 筛除明显失败 checkpoint。

不能单独推出：

  • rollout success；
  • recovery；
  • compounding error；
  • real-time feasibility；
  • collision/limit safety；
  • OOD robustness；
  • 旧能力保持；
  • 人类可接受性。

训练集 action accuracy 接近 100% 还可能意味着数据重叠或记忆，并非泛化。

闭环指标最小集合

  • task success 与 partial completion；
  • safety-conditioned success；
  • intervention / emergency stop；
  • failure taxonomy；
  • recovery 与重试；
  • action/replan/command latency；
  • jitter、deadline miss、queue/staleness；
  • horizon/time-to-complete；
  • ID/OOD 分轴；
  • old/new task 分轴；
  • robot/scene/object/operator 分层；
  • trial、seed、置信区间或不确定性。

具体 benchmark 和统计计算由统一评测页维护，本页只要求选择报告引用同一 protocol ID。

遗忘与迁移矩阵

定义适配前 checkpoint B 和适配后 candidate C。对每个旧能力切片 k 记录：

Retention_k = Metric(C, k) - Metric(B, k)

方向需按指标定义；对 failure/latency 等越低越好的指标不得直接沿用同号。至少报告：

  • forward transfer：新任务相对从零或简单基线的收益；
  • backward transfer / retention：旧任务变化；
  • worst-slice retention；
  • safety regression；
  • language/vision grounding probe；
  • calibration 与置信行为；
  • compute/storage/runtime delta。

均值不替代 worst slice。门禁应按关键旧能力和安全切片逐项判断。

遗忘缓解选择

| 方法 | 适用假设 | 代价 | 必须验证 | | — | — | — | — | | rehearsal/replay | 可保留代表性旧数据且许可允许 | 存储、采样、隐私 | replay 覆盖和新旧权重 | | regularization/EWC 类 | 参数重要性估计有意义 | 额外状态、塑性降低 | 新任务收益与保持取舍 | | distillation | 可运行 teacher/base | 计算、teacher 偏差 | 蒸馏目标不压制必要新行为 | | adapter/head isolation | 任务/本体可可靠路由 | 模块增长、路由错误 | unknown 与跨任务共享 | | partial freeze | 基座表征足够 | 容量限制 | 域差切片是否改善 | | mixture rebalance | 遗忘来自新旧数据失衡 | 采样复杂 | 实测梯度与闭环 | | periodic re-pretraining | 能重建统一 release | 高成本 | lineage、许可、全套回归 |

EWC 作为持续学习方法的一手例子，不被写成 VLA 默认；具体方法需要模型和任务证据。

回归定位顺序

  1. 复核评测环境/机器人/processor 是否变化。
  2. 复核 Action ABI、normalization 和 task/embodiment route。
  3. 对比 base 与 candidate 的参数/buffer diff。
  4. 对比新旧 source 的实际采样和有效 label。
  5. 对比 per-source loss/gradient 与数据质量。
  6. 在固定 candidate 上做模块/adapter on-off。
  7. 只改变一个变量做配对回退实验。
  8. 无法定位时停止 promote，保留证据，不用继续训练掩盖故障。

候选池必须在看到结果前预注册生成规则。保存间隔、阶段边界、最大候选数、离线淘汰条件和闭环预算写入 selection manifest；训练结束后只能按规则解析候选，不得因为某条曲线“看起来漂亮”临时加入额外 checkpoint。若因异常需要追加候选，应开新一轮选择并记录变更原因，避免选择偏差被藏在文件挑选中。

train、validation、selection rollout、retention 与 final test 的使用事件要记账。每次查看、调参或人工复核都会消耗独立性；当 selection 集被用于改变模型或门禁，它就应降级为 validation，并为最终报告冻结新的集合。报告不仅列 split 名，还列 release、去重规则、污染检查和访问次数。

离线门禁的边界要通过反例说明：较低 action MSE 可能来自高频静止段，较高 token accuracy 可能来自数据重叠，平均 loss 改善可能掩盖稀有安全动作退化。因此按任务、场景、动作维度、速度区间、缺失模态和 OOD 状态切片，并与简单基线比较；但这些结果仍只负责筛除明显失败，不替代闭环。

闭环试验中缺失、人工中止与基础设施失败不能被悄悄从分母删除。协议要规定各类 trial 的重试上限、计分方式与敏感性分析，并保留原始事件。若候选更容易触发保护停机，简单重试会系统性美化它；若硬件故障与候选无关，也要在盲化条件下按统一规则裁决。

遗忘评估同时报告平均变化、worst slice、置信区间和门禁结论。旧任务集合需要固定版本，并包含新适配最可能影响的视觉、语言、动作与本体切片；只测总体成功率可能漏掉低频但关键的安全退化。若 base 与 candidate 的 runtime 或处理器不同，还应先做兼容对照，避免把环境差异误判为遗忘。

缓解方法必须对应可证伪假设：认为数据失衡导致遗忘，就对 mixture 做配对调整；认为共享参数漂移，就比较冻结、隔离 adapter 或正则；认为接口改变，就修复 adapter 与 normalization。每项缓解都同时评估新任务收益与旧能力保持，不能只证明 retention 变好而忽略塑性丢失。

回归定位按“环境—接口—参数—采样—梯度—模块”顺序推进，每一步产出 diff 和结论。定位失败不是继续搜索最好 checkpoint 的理由，而是阻止 promote 的证据。修复后使用新 run ID 和新的 candidate pool 重做门禁，不能把修复后的结果附到旧候选身份上。

选择报告为每个候选保留一行证据索引，而不只列最终冠军：完整性状态、离线门禁、闭环任务结果、retention worst slice、延迟、安全事件、缺失 trial、证据链接和淘汰理由都要可追溯。最终选择若依赖硬门禁，明确哪一项具有否决权；若在多个合格候选间使用 tie-break，规则必须在试验前冻结。没有唯一赢家时可以保留 Pareto 集，并说明后续需要补哪类证据。

不确定性不能只在均值后附一个区间。trial 数、独立 seed、场景层级、机器人个体和操作者可能形成相关结构；报告应声明统计单位以及是否把重复尝试当作独立样本。小样本结果用于风险控制时，应采用保守门禁并展示原始计数。缺失或中止的敏感性分析至少给出乐观、预注册和保守三种处理，让审阅者看到结论是否依赖某一种分母选择。

持续适配：版本、批准、回滚与方法分流

持续数据闭环

active policy → logged episode → triage → labeled/reviewed data → immutable release → candidate run → offline/sim/real evaluation → approval → next active policy

每条 episode 必须带：

  • policy version/hash；
  • robot/config version；
  • task/scene；
  • observation/action schema；
  • operator/intervention；
  • outcome/failure；
  • consent/license/provenance；
  • time；
  • inclusion/exclusion reason。

active policy 产生的数据不能直接无版本流入正在运行的训练 job。

数据 release 与反馈污染

  • 评测轨迹进入训练前必须结束当前 selection cycle，并创建新 release。
  • 人工挑选“困难失败”要记录选择机制，避免把报告集隐式变为训练集。
  • 自动采集的成功/失败分布不代表真实任务分布。
  • 人类接管轨迹要区分 policy action、human action 和 control ownership。
  • 删除/撤回数据要能定位受影响 checkpoint。
  • replay 数据若许可证或保留期变化，必须触发 lineage 审计。

版本状态机

允许转换：

  • created → training → candidate
  • candidate → evaluated | rejected | quarantined
  • evaluated → approved | rejected
  • approved → active
  • active → superseded | rolled_back | takedown
  • rolled_back → investigated

禁止：

  • training checkpoint 直接 active；
  • rejected/quarantined 直接 active；
  • 无批准人和证据 hash 的 candidate active；
  • 覆盖旧 active 制品而不保留 rollback target。

Promote 门禁

至少要求：

  1. 制品 hash 和加载自检通过。
  2. 数据/代码/配置/许可证 lineage 完整。
  3. offline、simulation、受控 real-world 证据满足适用层级。
  4. 新任务指标达到预注册目标。
  5. 关键旧任务和安全切片未越过退化阈值。
  6. runtime latency/资源满足下游预算。
  7. 安全、模型、数据和机器人负责人完成授权。
  8. rollback target 已存在并通过加载演练。
  9. 监控、takedown 和人工接管责任明确。

本页不提供真实阈值；由目标系统负责人在后续评测/部署/安全页填写。

Rollback 不是复制旧文件

回滚 manifest 必须含：

  • from version；
  • to version；
  • trigger；
  • approver；
  • artifact hashes；
  • runtime/processor/I/O contract；
  • normalization and adapter assets；
  • compatibility check；
  • stateful component handling；
  • verification protocol；
  • data produced during bad version 的隔离规则；
  • incident link；
  • reactivation criteria。

若部署涉及外部 controller、queue、memory 或 planner，仅回退 VLA weights 可能不恢复旧行为；这些依赖由后续页面补齐。

Shadow、Canary 与真机边界

  • shadow：候选读取日志/观测但不下发动作；可测一致性和延迟，不证明闭环。
  • simulation canary：有限 seed/task 运行；受 sim fidelity 限制。
  • hardware-in-loop：验证 I/O、时序和限制器；不等于自主真机任务。
  • controlled real canary：小范围、限速、隔离区域、人工接管和停止规则。
  • broader rollout：只有安全页批准后讨论；本页不执行。

“canary”不是自动安全许可，而是一种缩小暴露面的发布阶段。

方法分流

继续监督适配适合：

  • 有可信 demonstrations/labels；
  • 行为目标可由监督信号表达；
  • 主要问题是域适配或接口变化；
  • 闭环探索不是必要条件。

转 RLT 相关专题时：

  • 目标需要在线交互、价值估计或策略改进；
  • 需要显式 MDP、reward、replay、critic 与在线系统；
  • 额外真实交互和安全授权成立。

转 RLHF-VLA 相关专题时：

  • 信号来自成对偏好、排序、轨迹反馈或 reward model；
  • 需区分 RM/PPO、直接偏好与连续轨迹路线；
  • 需要处理偏好偏差、reward hacking 和在线反馈版本。

RLT/RLHF-VLA 是相关分支，不是本页线性下一课，也不是 SFT 自动升级。

一个新机器人方案的最小闭环

最终工作示例用空值而不是虚构数字：

  1. 冻结 Robot/Action ABI 与数据 release。
  2. 选择基座并完成兼容矩阵。
  3. 建立 head-only/PEFT/full 的小规模 matched-budget 候选。
  4. 记录分层采样和 objective routing。
  5. 生成参数所有权和训练 checkpoint。
  6. 以 offline gate 淘汰损坏或发散候选。
  7. 用固定仿真/受控真机 protocol 比较 Pareto 候选。
  8. 运行旧能力 retention suite。
  9. 形成 evidence bundle 与批准记录。
  10. 绑定 rollback target 后才进入后续部署设计。
  11. 将新反馈冻结为下一 release，而非覆盖当前实验。
  12. 若监督信号不足，再显式转入后训练专题。

持续闭环中的反馈首先进入版本化收件箱，而不是训练集。triage 记录来源策略、控制所有权、失败标签置信度、重复/近重复、隐私与许可状态；审核后才进入不可变 data release。对同一 episode 的标签修订创建新 revision，并保留旧值和理由，使后续能够解释某个候选为何见过特定反馈。

人工接管轨迹必须逐时刻区分 policy command、human command、限制器输出与机器人实际执行结果。只有这样才能判断动作标签代表专家示范、纠正信号还是被安全层裁剪后的行为。控制权不明的轨迹可用于故障分析，但默认不能作为干净监督数据进入下一 release。

版本状态转换采用幂等事件：同一请求重复提交不重复激活，过期批准不能覆盖新 active，所有状态更新都校验 expected current state。active 指针与制品本身分离，切换指针前验证目标 bundle 的摘要、processor、I/O contract、normalization 和依赖；切换失败时保持旧 active，不留下半发布状态。

回滚演练应在发布前完成，而不是事故后第一次尝试。用隔离环境从 registry 解析 rollback target，验证完整加载、接口握手、状态清理和最小行为探针，并测量恢复时间。演练还要覆盖新版本已写入缓存、planner memory、queue 或数据 schema 的情况，确认回退权重后不会继续消费不兼容状态。

shadow 只能证明候选能在旁路读取观测并满足部分延迟要求；simulation canary 受环境保真度限制；HIL 验证接口和时序；受控真机 canary 才观察有限闭环行为。每一层都要定义进入、退出、停止、人工接管与数据隔离规则，上一层通过不自动授予下一层权限。

方法分流记录“为什么监督适配仍足够”或“为什么需要新的反馈范式”。如果问题是数据缺口、Action ABI、模态路由或本体适配，先修复这些基础；只有在目标确实依赖交互式策略改进、偏好或 reward 时，才转到 RLT/RLHF-VLA，并创建新的目标、风险和授权契约，不能在 SFT run 中暗中加入在线更新。

最终可审计版本应能回答七个问题：它从哪个 base 来、看过哪些 release、哪些参数改变、为何选中、旧能力如何变化、谁批准激活、遇到何种信号回到哪个版本。任一答案只能靠口头记忆或“latest”目录恢复时，网页应把状态标记为证据不完整，而不是发布完成。

发布前演练应模拟三类触发：指标缓慢越界、明确安全事件、制品或许可证紧急撤回。三者的检测来源、授权路径和恢复时限不同，但最终都要解析到完整 rollback target 并冻结问题版本产生的新数据。演练结束保存开始时间、触发信号、决策、指针切换、验证结果和未解决项；若只能手工复制文件、找不到旧 processor 或需要临时询问版本号，演练判定失败。

回滚完成不等于事件关闭。问题版本保留 rolled_back 身份，其相关数据、日志和候选进入调查隔离；旧版本恢复 active 后还要确认监控、数据 schema、缓存和外部控制器恢复到兼容状态。后续若修复并重新训练，应从明确父节点创建新候选，通过完整门禁，而不是把原版本重新标为 approved。这样版本链既保留失败历史，也避免不可审计的“原地修好”。

页面的完成定义也应机器可核对：六个阶段契约均有稳定 ID，所有候选均能追到父 base 和数据 release，参数变化与 optimizer 所有权一致，selection report 引用固定协议，active 与 rollback target 都能解析为完整 bundle。若只缺真实阈值或批准签名，可以标记为待系统负责人填写；若缺数据来源、Action ABI、normalization 或父权重摘要，则属于结构性缺口，不能以“后续补充”绕过。

最后做一次反向演练：从 active 版本出发，不查看训练目录名称，只依靠 registry 和证据索引重建 processor、prompt、输入输出契约、参数制品、归一化和评测结论；再从任一数据 release 出发，查询它影响了哪些 run、candidate 与 active 历史。两条查询都闭合，才说明训练与持续适配形成了真正可审计的版本图。任何孤立节点、可变外链或无法验证的摘要都进入缺口清单，并在下一次 promote 前关闭。

审计结论还要区分“页面设计完成”和“真实系统已验证”。本页能够冻结字段、状态和证据格式，但没有真实数据、训练运行、仿真、HIL 或机器人结果时，相应值必须保持未填写；示例不能伪装成测量。后续实施者填入事实后，应再次运行完整性检查，并由对应责任人签署。这样既让页面成为可执行蓝图，又不会把文档完备性误报为模型或系统已经安全可用。

完成记录同时列出仍待外部系统提供的事实、责任角色与解除条件；只有这些条件被真实证据关闭，相关状态才可从“设计就绪”提升为“已验证”。
