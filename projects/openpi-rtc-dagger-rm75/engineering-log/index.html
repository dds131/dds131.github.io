工程迭代：问题、根因与修复

OpenPI RTC + DAgger RM75 的相机契约、状态机、异常清理、实时记录、尾部采样与环境边界复盘

项目概览 RTC 复现与接管 纠正数据 数据与训练 安全与验证 工程迭代 论文与路线
ROOT CAUSEREGRESSIONEVIDENCE LEVEL

“代码改了”“历史测试通过”和“问题已消除”不是同一件事。

每项工程修复都按症状、因果链、改动、证据等级与残余风险记录；本轮新增只读源码与日志复核，把已能复算的问题升级为量化证据，未重新运行的机器人/训练测试仍保持原级别。

一、先统一状态口径

状态 严格含义 本页如何使用
需求记录已修复 项目文档记录了根因、代码改动和当时的测试结果 可以复述，但必须标明本轮未复跑
已缓解 设计降低了风险，但缺少目标环境、长时间或压力证据 用于三相机热路径、尾部采样等问题
待复验 当前挂载范围内没有对应源码/环境或本轮没有执行回归 不能显示成绿色“当前通过”
已只读复核 从目标源码、配置或原始日志直接核对并可重新计算 支持对应历史运行的机制与数字；不等于本轮重新运行机器人/训练
已验证 指定 commit、配置、输入与日志在目标环境重新执行并通过 本轮网页构建属于此类；历史训练/真机日志不因此变成本轮新实验

工程日志不能只写“已优化”。最小证据单元应包含：issue ID、受影响版本、最小复现输入、预期/实际结果、根因、补丁位置、回归用例、artifact 摘要、执行日期与残余风险。

三、案例 E1：相机“键名正确”仍可能静默错

推理入口的 rename_map 把数据集原始键映射到模型槽位。初版把模型槽位反写进新数据集，会造成 feature 集与参考库不同。修复的核心不是再堆一张硬编码字典，而是让参考集 schema 成为转换时真相源。

但结构回归只能证明“字段可读”：

  • schema 测试：键、shape、dtype、fps、robot_type；
  • 物理语义测试：遮挡单台相机，确认 raw key 与真实设备；
  • 像素测试：颜色顺序、旋转、裁剪与宽高比；
  • 时序测试：图像、状态和最终命令的时间戳偏差。

只有第一项通过时，状态应写成“schema 兼容”，不能写成“相机数据完全正确”。

四、案例 E2：继承复用必须保留组合语义

项目记录表明，初版 start/Home 路径直接触发了内部行为，却绕过基类公开事件入口。局部看“同一个函数最终被调用”，全局却缺少状态迁移、计时器、队列与清理副作用，出现 RTC 接块为零和守卫回退。

修复原则是让子类发出基类理解的公开事件，而不是复制或直调内部动作。回归至少覆盖：

  1. 事件前置条件与非法相位拒绝；
  2. 状态、队列 epoch 和计时器变化；
  3. start → 收块 → soft stop → handoff → TELEOP；
  4. 保存/丢弃后回 IDLE；
  5. Home 作为主动运动命令的权限、路径与完成条件；
  6. 基类升级后的契约测试。

本页保留 super().handle_key(...) 作为项目文档中的修复线索；在未读取对应 commit 源码前，不据此断言当前实现仍完全一致。

五、案例 E3：异常清理是事务，不是改一个 phase

软件异常收口至少涉及五类状态：会话 phase、RTC 队列/在途结果、控制参考、录制缓冲和资源线程。只把 phase 改回 IDLE 会留下旧动作或脏数据；先自动保存再清理又会把未确认数据写进训练集。

更稳妥的顺序是：禁止新策略动作 → 进入定义的故障/保持状态 → 失效旧队列 → 停止录制并隔离未保存临时段 → 有序释放资源。恢复到可启动状态还需要显式复位，不能因异常处理函数返回就自动继续运动。

物理急停和断电不受这个软件事务保证。下次启动必须扫描临时目录，识别未完成写入，并要求人工决定恢复、隔离或删除；不能把残留文件自动并入正式纠正库。

六、案例 E4：热路径“更轻”不等于满足实时预算

110 Hz 的名义周期约为

\[T_c=\frac{1}{110}\approx9.09\ \mathrm{ms}.\]

三路 224×224 RGB、uint8 图像若以 30 Hz 完整复制，仅像素载荷速率就约为

\[R_{\mathrm{img}} = \frac{30\times3\times224\times224\times3}{2^{20}} \approx12.9\ \mathrm{MiB/s},\]

60 秒约 775 MiB，尚未计 Python 对象、数组元数据、原始相机分辨率与编码缓冲。因此“只 copy”是合理降风险，但不是零成本。

代表性真机记录已经补上第一组运行时数字：10 个连续 ACTIVE 段内有 20,338 个有效周期，P50/P95/P99/P99.9 分别为 9.092/9.379/9.638/10.063 ms，最大 11.161 ms，有效频率 109.999 Hz，未观察到大于 1.5 倍目标周期的间隔。这说明该次会话的发送节拍稳定，但日志没有计划 deadline 或 lateness，不能据此报告 deadline miss=0。

回归仍应覆盖真三相机、最长允许 episode、磁盘慢写和日志开启条件下的内存峰值。若未来改后台编码，队列必须有界；满队列时是丢帧、停止录制还是结束会话，需要显式策略，不能让无限积压反向拖垮控制。

七、案例 E5：尾部修复必须落在采样起点

最小 60 帧、完整恢复和坏段回退有助于数据质量，却不会自动消除动作块 padding。对于 $H=50,T=60$，完整未来窗口起点只有 $T-H+1=11$ 个。

“训练侧丢最后 49 帧”若被实现为先裁短 episode，再从裁短后的尾部继续取窗口，padding 仍会出现。正确含义是过滤最后 49 个样本起点；另一条可接受路径是证明 padding mask 从数据加载器一直传到损失并真实屏蔽这些位置。两者都需要训练侧单元测试，本轮页面审计没有执行。

八、案例 E7–E8：采集吞吐与训练吞吐都要量化

在线 DAgger 的优势是状态由当前策略真实诱导，但当策略成功率已经较高时，操作者的大部分时间会花在成功 rollout 和等待上。工程优化不是取消在线接管，而是把已知失败簇转成可重复的定向恢复模板，批量采集后再用较低频率的在线 DAgger 审计未知失败。两类数据必须保留不同的 collection_mode，分别报告每小时有效 episode、失败簇覆盖和真实策略可达率；否则高吞吐数据可能只是更容易摆放的数据。

训练侧也不能用一句“JAX 更快”结束决策。现有历史日志统一到 optimizer-step 后：8-GPU JAX 为 5.676 s/step、45.10 samples/s、约 5.64 samples/s/GPU；4-GPU PyTorch 为 11.812 s/step、21.67 samples/s、约 5.42 samples/s/GPU。聚合吞吐相差 2.08×，GPU 数也相差 2×，单 GPU 粗归一仅约 4.1%。未来仍需锁定同一数据 manifest、模型、可训练参数、dtype、有效 batch、GPU 和步数，再分别记录首次编译、预热后 samples/s、峰值显存、损失/梯度一致性与端到端时间。若训练用 JAX、部署用 PyTorch，还要把权重转换与固定输入动作误差纳入总成本。

九、案例 E9–E10：时间段和延迟域混淆会制造假结论

跨段差分的问题不是一个统计细节。旧分析器先保留所有 ACTIVE 帧，再对结果整体 np.diff；一旦中间经历 WAIT_FIRST_CHUNK，两个相隔很久的段端点会成为“相邻样本”，产生假的超大速度、加速度和 jerk。正确顺序是先按原始状态与时间连续性切段，再在每段内部求导，最后按有效样本数汇总。本轮控制周期和 RTC 记录复算均使用该口径，旧分析器文件本身尚未修改。

LPF 群延迟误入 RTC d 是另一个时钟域错误。双级 EMA 的约 55 ms 群延迟描述“指令经过低通后机械臂响应变慢”，RTC 的 $d$ 描述“观测到动作块返回之间过去了多少 30 Hz 策略步”。把前者加给后者，会让冻结前缀领先真实时间轴，ss1.0 下触发首步偏差连续拒块。源码当前已从 _d_est 移除该补偿；输出 LPF 仍可保留，但只作为下游命令平滑。

这两个案例共享同一原则：任何延迟或差分指标都必须先标注它属于观测、推理、策略动作、伺服发送还是物理响应时间轴，不能因单位都是“秒”就相加。

十、被拒绝、暂缓或保留的替代方案

拒绝：两套下发循环

RTC 与 VR 各自写硬件会破坏单写者，切换瞬间的最后写入者和夹爪命令都不可审计。

有条件启用：JAX 训练后转 PyTorch

大规模数据下优先实测 JAX；只有稳态吞吐收益覆盖编译、转换和双框架维护成本，且参数、统计、固定输入与 rollout 等价回归通过后，才进入部署链。

不选：采集端安装训练栈

会扩大实时环境依赖与变更面，却不改善控制；保留原始包并在训练域可重复转换更容易审计。

拒绝：只录几帧纠正

缺少从偏离状态恢复到任务完成的后半段，并显著增加动作块尾部受 padding 影响的窗口。

拒绝：无摘要覆盖式复制

无法区分完整文件、半包和误版本；接收必须先到临时落点并校验，再切换。

保留：有界后台编码

可降低停止阶段等待，但必须先定义队列上限、背压、丢帧标记和异常恢复。

十一、回归记录还缺什么

记录项 为什么需要
commit / 依赖锁定 确认测试针对哪个实现，而非同名脚本
配置与设备条件 速度、相机分辨率、fps、模型和硬件会改变结果
最小复现与预期断言 让根因和修复可重复，而不是只留“成功”日志
原始日志与 artifact 摘要 证明结果没有在转述中被改写
性能分位数与资源峰值 平均值会掩盖控制周期长尾与内存峰值
当前复跑状态 明确历史记录、页面审计和目标环境验证的差别

十二、知识点、重点与工程创新

知识点

  • 状态机组合语义与公开事件契约
  • schema 兼容与物理传感语义
  • 异常清理事务与崩溃恢复
  • 实时周期分位数、内存带宽和有界背压
  • 采集吞吐、失败簇覆盖与框架训练吞吐

本页重点

  • 历史回归不得写成本轮复验
  • 尾部保护作用于样本起点
  • Home 与物理急停不属于普通 abort 清理
  • 每个修复保留可复现证据和残余风险

工程创新点不是“改动最少”本身，而是把差异面限制在可审计边界：公开事件扩展、单写者、临时数据隔离、参考 schema 驱动和分层 manifest。最小改动只有在不绕过状态语义、能独立回归和能成套回滚时才有价值。

十三、仍存风险与下一轮重点

  1. 在目标 commit 上重跑所有历史回归，并为结果生成证据包。
  2. 用真 VR 核对按键名、阈值、去抖与离合方向。
  3. 在真三相机最长 episode 下复验现有控制周期分位数，并补记录内存峰值与计划 deadline。
  4. 在训练侧证明最后 49 个起点被过滤，或 padding mask 被损失消费。
  5. 用纠正保持集和旧任务保持集决定 source sampling，而不是凭帧比例猜权重。
  6. 比较定向恢复与在线 DAgger 的每小时有效 episode、失败簇覆盖和真实策略可达率。
  7. 在锁定版本上完成同 GPU 数的 JAX/PyTorch 等条件基准与跨框架部署回归。
  8. 把连续段差分逻辑正式合入分析器，并使旧报告标注是否受 gap-diff 影响。
  9. 用相同 checkpoint 和固定延迟比较 RTC 与执行侧动作平滑，避免把主观观感写成算法等价。
工程结论：“最小改动”是可验证性策略，不是少写代码的竞赛。若少改一行的代价是绕过基类状态、复制隐含契约或缺少回归 artifact，差异面反而更难定位和回退。
