openpi-RLT ⑥：安全、实时性与工程问题闭环

以现象、根因、修复和量化验证为主线，复盘七维 delta、相机争用、周期卡顿、JAX 显存、FAULT、交还回退和 Replay 污染

总览 三阶段 RL-Token 运行架构 E-2 / F / G L4 在线训练 工程修复 结果与归因
SafetyRealtimeData semantics

真机在线 RL 的失败不只来自模型：动作单位、相机所有权、共享内存、显存抢占和数据语义，都可能制造“像算法问题”的假象。

本页只记录已经形成证据闭环的工程问题。每一项都按“现象 → 机制 → 干预 → 验证”阅读；只修掉现象而没有独立验证，不算闭环。

五类风险

ACTION

动作表征

七维 delta、夹爪绝对量、单位换算、首点锚与正则权重。

VISION

相机与共享状态

Frame bus 所有权、陈旧帧、FAULT 时间戳与跨进程一致性。

TIMING

控制时序

块边界、周期卡顿、Actor 等待、交还回退与夹爪同步。

RESOURCE

显存与数值环境

JAX 预分配、Actor 退 CPU、IK 后端与依赖隔离。

REPLAY

数据语义

HUMAN 来源、空介入、坏段回溯、journal 截断与更新预算。

闭环的证据标准

1 · 现象先把“卡、抖、停训”变成频率、延迟、计数或数据比例。
2 · 机制用日志、离线复现或消融找到能解释现象的具体机制。
3 · 干预一次只改与机制对应的单位、状态机、内存写序或资源配置。
4 · 验证既查目标指标，也查回归项；“不再报错”不等于任务成功。

指标 数值 口径

这些数字说明大多数循环接近 110 Hz，同时存在少量长尾。由于日志没有调度器 deadline 计数器，表中的阈值统计不能包装成经过定义的“deadline miss 率”。

插值、过滤、平滑与轨迹约束

当前链路不是一个离线全局轨迹优化器，而是“VLA / Actor 动作块 → 时间插值 → chunk 安全过滤 → 110 Hz 命令过滤 → 单帧 IK / 碰撞约束”的分层组合。

1. 动作块安全过滤的固定顺序

rm75_safe_filter.py 对候选 chunk 依次执行：

  1. 非有限值用前一目标替换；首点异常时用当前关节状态。
  2. 相邻关节目标每步最大变化限制为 10°，内部保留 $10^{-3}$ 的裕量。
  3. 首点必须在当前姿态 10° 内，然后重新执行逐步跳变限制。
  4. 应用 RM75 软限位：原始范围为 [-178,-130,-178,-135,-178,-128,-360]° 到 [178,130,178,135,178,128,360]°，再向内收 5°；同时约束第四关节绝对值不小于 10°。
  5. 对整个 chunk 复验；若任一条件仍失败，不局部拼接，而是整块保持当前姿态。
  6. 夹爪量化到 {0, 0.5, 1}。

“整块回退”是重要安全语义：它避免一半来自新计划、一半来自旧计划的混合轨迹通过校验。

2. 110 Hz 命令过滤的作用与参数

参数 / 逻辑 当前值 作用
输入低通 alpha 0.30 抑制上游目标的高频变化
命令 EMA alpha 0.25 平滑最终下发目标
关节速度上限 144 °/s 对整个位移向量做同比例缩放，保留方向，不逐关节硬裁剪
关节加速度上限 1,000 °/s² 同比例限制速度增量

软急停使用五次 smootherstep 速度包络沿原方向减速，状态机、抢占条件和 Replay 丢弃语义见在线训练页。因此普通 EMA、靠近软限位的制动和软急停是三种不同机制，不能合并成一个“平滑”。

3. IK 与碰撞约束的计算量

当前 IK 首次编译记录为 3.60 s，热路径单次求解约 3.7 ms；模型启用 18 对自碰撞对、4 项 cost 和 2 项不等式约束。首次编译必须在进入实时控制前预热，否则 3.60 s 编译暂停会直接破坏控制时序。热路径耗时只是 IK 求解器本身，不包含 VLA 推理、网络、相机或机械臂通信。

4. 为什么当前回到 legacy，而不是继续 blend

最新控制日志记录 smooth mode=legacy，并保留 $E=2,V=1$；smootherstep、最大跳变 2° 的 blend 配置存在，但当前未启用。两轮历史 A/B 给出了撤回原因：

试验 legacy / 原 blend 行程 原 blend 窗口状态 延迟补偿版相对 legacy 高频与导数结果        
A/B-1 20.30° / 3°，行程损失 85% expired 21、no-window 0 行程 20.61°，差约 1% $ dq $ p95 −9.2%，$ d^2q $ p95 −37.3%，但 9–12 Hz 能量 40.18 → 60.66
A/B-2 20.54° / 6°，行程损失 71% expired 21、no-window 1 行程 20.69° $ dq $ p95 +2.4%，$ d^2q $ p95 +46.2%，9–12 Hz 能量 9.08 → 53.24

原 blend 因窗口过期造成明显欠执行；延迟补偿恢复了行程，却在两轮中都放大 9–12 Hz 能量，第二轮连速度和加速度分位数也恶化。因此当前选择 legacy 是量化回退结论，不是“blend 已优化完成”。这也是本项目对轨迹优化的边界：现有系统做局部时间插值、约束与滤波，没有证据支持把它描述为全局最优轨迹规划。

四项被新证据推翻的解释

早期解释 证据为何不支持 更正后的结论
“epoch 太多导致晃动” 同一抖动表象同时包含单位错配、执行等待和 Actor 原始输出三类量 先分解数据尺度、执行链路与策略输出；不能把训练轮数当成总根因
“IK 新解供给不足导致周期卡顿” 1.045 s 周期峰与 GPU 争用同步；改 CPU 后峰消失 根因是控制侧 JAX IK 与 π0.5 的周期性 GPU 资源竞争
“相机本身不稳定触发 FAULT” 离线 writer/reader 即可复现全零时间戳，修写序后脏读归零 根因在 frame bus 共享内存一致性，不在相机硬件
“Prompt 漏掉了取出阶段” 训练指令已经包含最终移入箱子的完整动作链 真正缺口是阶段词与 stage_id 条件，以及把 RLT 施加到整条长任务
这些更正的共同原则是：一个解释只有在能预测指标变化、并经针对性干预验证后，才从“假说”升级为“根因”。

单位错误为什么危险

上游正则作用于六个弧度制关节，本项目的物理动作是七个关节、以度表示。这里有两次换算，不能把它们混成一个倍率：

  1. 只处理六关节“弧度 → 度”，系数从 10 变成 0.020269；直接照搬 10 会比这一步的等价系数大约 493.4 倍。
  2. 再把第七关节纳入均值正则，系数从 0.020269 变成 0.014415；这是均值分母与尺度统计改变带来的 1.406 倍调整。

因此，10 与最终 0.014415 的数值比约为 693.7，而不是 493。真正需要保持的是总正则强度：

\[0.014415 \times 263.7545 \approx 3.802 \approx 10 \times 0.3802.\]
边界：0.014415 表示“在七关节度制下与上游总正则强度等价”，不是“已经证明的真机最优值”。更大的 0.020269 虽让验证集拟合改善 0.061°，却令 BC 正则惩罚增加约 43%，G 闸优势仅 1/3148；证据不足以宣称更优。

同名 JAX，两个不同故障

故障 发生位置 表象 根因与干预
接管期周期卡顿 控制侧 IK 与 π0.5 推理 约每 1.045 s 出现一次长停更 PyRoki/JAX IK 与模型抢 GPU；IK 转 CPU，限制预分配
Actor 走走停停 在线 Actor 服务 请求等待、hold 增多 Actor 无法取得预期显存而退 CPU；关闭默认预分配并限制显存比例

两项问题都与 JAX 内存策略有关，但进程、路径和可观测指标不同，不能用一次修复的 A/B 结果替代另一项验证。

Actor 资源竞争：一次典型 A/B

Actor wait · 修复前273.3 ms
Actor wait · 修复后36.4 ms
hold · 修复前53.1%

JAX 默认预分配让在线 Actor 无法获得显存并退到 CPU，表面表现是“策略抖动、走走停停”。补齐显存限制后，等待和 hold 恢复到健康范围，抖动约降 35%。

执行链路修好后，Actor 的符号翻转率仍约为 VLA 的 2.83 倍，运动帧占比仍只有 13.4%（纯 VLA 对照为 71.2%）。这条残差证据把“资源故障导致的抖动”和“策略本身不够平滑”分开了；任务仍失败，不能把链路修复写成算法收益。

接管期周期卡顿

卡顿最初被解释成“新解供给不足”，但取证显示 1.045 秒周期峰来自 JAX IK 与大模型争用 GPU。预分配一度达到 12.2 GB，而 IK 实际只需约 270 MB；将 IK 固定到 CPU 并限制 JAX 预分配后：

指标 修复前 修复后
新解事件的 1.045 s 自相关 0.751 −0.021
solve_ms 最大值 114.6 ms 17.0 ms
超过 50 ms 的停更帧 352（4.94%） 0

FAULT 的根因更正

跨进程读者偶尔看到全零时间戳，导致 age 被计算成系统运行时间并触发相机 FAULT。最终根因不是抽象的“相机不稳定”，而是 frame bus 的共享内存元数据头在写入时短暂暴露中间态。

复现离线 writer/reader 复现：880 万次读取里出现 107,460 次脏读。
写序用一次切片更新，按 active → timestamp → sequence 的次序提交。
去抖单次异常不立刻 FAULT；连续 3 次异常才升级，真实断流仍能被捕获。
双验证离线脏读 107,460 → 0；随后 67 分钟实机运行 0 FAULT。

数据质量也是安全

没有动作的 HUMAN 块会让 Actor 学到“接管时保持不动”；做错的人工纠正会把错误动作当作优质监督。位移阈值加第七路 Grip 过滤前者，带审计记录的丢段键处理后者。二者职责不同：自动门只判断“有没有操作”，不能判断任务语义“做得对不对”。

同样，截断 Replay journal 如果不同步复位 global_step，会让 Learner 认为更新预算已经完成，表现为“程序都在但不再训练”。一次现场数据中，所需更新数是 21,545，而旧 global_step 已到 73,410，因而待更新量被算成 0。修复不是盲目重启，而是将 journal、20,000 更新目标与计数基线一致地重置。

在线监视必须同时看 Replay 总量、目标更新数、global_step 和实际 UTD。任何一项单独“在增长”都不能证明训练语义正确。

交还不是一个按键事件

HUMAN → BASE 的切换同时跨越 planner、目标缓存、当前观测和夹爪状态。只改变 source 会把旧计划或旧夹爪值带回 BASE，造成反向回退或张爪掉件。完整切换需要：

  1. HUMAN 期间暂停生成新的 BASE plan；
  2. 交还时用当前观测刷新 proxy；
  3. 软清理 pending plan 与上一个目标，同时保留并同步真实夹爪状态；
  4. 经过短暂冷却后再允许 BASE 重新规划。

专项压力测试记录了 144 次快速交还、0 次反向回落；夹爪同步后，该切换路径的掉件也消除。这个结论只覆盖切换安全，不代表完整任务成功。

诊断与收工命令

本页仍不公开“一条命令直接让机械臂运动”的入口，但以下离线检查与项目内收工工具是理解故障闭环所必需的：

RLT_ONLINE=<OPENPI_RLT_ONLINE_RM75_DIR>
RUN="$RLT_ONLINE/tools_e2"
PY_CONTROL=<CONTROL_PYTHON>

bash "$RLT_ONLINE/tools/run_offline_tests.sh"
bash "$RLT_ONLINE/control_side/run_control_side_selftest.sh"
"$PY_CONTROL" "$RUN/e16_argv_check.py"

bash "$RUN/e2_cleanup.sh" --verify-only
bash "$RUN/e2_cleanup.sh" --orphans
bash "$RUN/e2_cleanup.sh" --verify-only
命令 / 参数 作用 能排除什么，不能排除什么
run_offline_tests.sh 跑补丁、Replay、Learner 与工具的离线回归。 能发现代码级回归；不能发现相机、编码器或物理反馈故障。
run_control_side_selftest.sh 用假后端检查策略代理、动作闸、超时和控制契约。 能检查 AUTO/TELEOP 的 executed_action 语义；dryrun 的 state 等于刚下发动作，不能证明真实 next observation 对齐。
e16_argv_check.py 只解析 E-1.6 启动参数，不开相机、不连 VR、不启动硬件。 能发现 source/backend/频率等参数拼错；不能证明设备可用。
--verify-only 只读取端口、相机、GPU 与共享内存残留状态。 适合开跑前和收工后复查；通过不代表任务成功或现场已清场。
--orphans 清理由本项目规则识别出的孤儿进程。 只在正常退出顺序完成后使用；它不能代替先 flush journal/checkpoint，也不得扩成宽泛杀进程命令。

固定排障顺序是：先正常停机与 --verify-only，再清本项目孤儿；之后分别检查端口与资源，最后才回到代码。这样能避免把陈旧进程、共享内存或显存残留误诊为新的算法错误。

六条工程方法论

  1. 每个修复必须配可观测指标。
  2. dryrun 不能证明真实编码器、相机或物理反馈相关的性质。
  3. 安全整形器兜底不等于 Actor 原始输出安全。
  4. 启动配置必须锁定动作维度、单位、后端和显存口径，不能依赖进程默认值。
  5. 被新证据推翻的解释必须显式更正，不能作为“多个可能根因”永久保留。
  6. “工程链路已稳定”与“学习算法有效”必须分开验收。
本页不提供能直接启动真实硬件的命令。完整操作流程保留在本地只读运行手册；网页只公开设计、证据和相对模块职责。
