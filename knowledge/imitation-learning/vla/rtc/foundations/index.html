  • 共同基础：对 action ABI 或实时链路不确定时，先看动作空间与动作表示和实时部署接口。
  • 安全边界：本文的公式是时序建模工具，不是真机调度参数，也不构成硬实时、稳定性或安全证明。真实系统还必须有 Runtime、policy I/O contract 与独立安全层。

RTC 的第一个正确性条件不是某条 guidance 公式，而是每个观测、动作和动作块都能映射到同一个物理控制 tick；否则算法正确也会执行错时间的动作。

  • 区分 wall clock、control tick 与生成时间，并按顺序记录九类关键事件。
  • 把新旧动作块映射到同一绝对 tick，识别过期、已提交、软重叠与自由后缀。
  • 导出 Guided 与 Training-Time 共用的 branch contract，再按 checkpoint 与训练条件选择路线。

三种时间域与九个事件

三种时间域不能写成一个 time

wall clock · T_mono

单位为 ns、ms 或 s，由 monotonic clock 所有。它用于计算 duration；人类可读 UTC 只能辅助跨日志关联，不能替代单调时钟做耗时差。

control tick · k

整数 tick，由 controller/runtime 所有。它必须与 control_session_id 一起解释；控制器重启后，单独比较整数没有意义。

generative time · tau

Flow/Diffusion 的无量纲时间或离散采样步，由 policy sampler 所有。它不能与控制 tick 相加，也不能当成机器人已经运动的时间。

flowchart LR
  M["monotonic wall clock<br/>T_mono · duration"] -. "event timestamp" .-> K["control tick<br/>k + control_session_id"]
  K -. "request / target mapping" .-> P["policy sampler"]
  P --> G["generative time tau<br/>solver trajectory"]
  G -. "output becomes ready" .-> M

图 1｜三种时间域。 单调时钟测持续时间，控制 tick 定位物理调度，tau 只描述采样器内部演化；虚线是带 contract 的映射，不表示这些量可以直接相加。

九个事件构成最小可审计链

| 顺序 | 事件 ID | 必填时间或标识 | 不能误读为 | | —: | — | — | — | | 1 | observation_captured | mono + tick + observation ID | 数据已经进入模型 | | 2 | inference_started | mono + tick + frozen observation ID | 相机曝光时刻 | | 3 | delay_prediction_bound | mono + d_hat + predictor version | 事后实测延迟 | | 4 | chunk_ready | mono + tick + chunk ID | 新块已经可以执行 | | 5 | chunk_validated | mono + contract/shape/finite 结果 | safety 已放行 | | 6 | chunk_merge_committed | mono + 保留/替换 index range | 首动作已经派发 | | 7 | chunk_first_dispatched | mono + k_switch + controller seq | 动作已经物理完成 | | 8 | controller_ack | mono + controller seq | 世界状态已经达到目标 | | 9 | execution_feedback | mono + sensor/control tick | 原始 proposal 未被 safety 改写 |

时钟与日志规则

  • duration 使用 monotonic clock；UTC 可附在同一事件上，但不参与 duration 计算。
  • 跨进程或跨主机时记录 clock_domain、同步方法与不确定度，禁止把两个来源不明的时间戳直接相减。
  • tick rate 变化、丢 tick、controller pause 和 session restart 都是事件，不可用连续整数静默补齐。
  • 时间戳缺单位或 epoch 时标记 unknown；不要根据数值位数猜单位。
  • tau 只进入 sampler trace，不进入机器人事件轴。
event_trace_record:
  event_id: "<one-of-nine-events>"
  monotonic_time: "<value-with-unit>"
  clock_domain: "<monotonic-source>"
  control_session_id: "<opaque>"
  control_tick: "<int-or-null>"
  request_id: "<opaque>"
  authority_epoch: "<int>"

该模板只冻结字段与验证语义，不是可部署配置；opaque ID 不得替换成凭证、人员身份或原始敏感图像。

从一条 trace 回答四个不同问题

“模型什么时候算完”“新块什么时候可用”“控制器什么时候收到”“机器人什么时候产生反馈”是四个问题。第一问由 chunk_ready 回答；第二问至少要等 chunk_validated 与 chunk_merge_committed；第三问看 chunk_first_dispatched/controller_ack；第四问只能由 execution_feedback 和平台语义回答。若一条日志只有 request start 与 response end，它最多证明某段软件耗时，不能证明动作在正确 tick 被派发。

事件顺序也不是简单的单请求串行链。多个 request 可能并发，旧块可能跨越多个新请求继续供给，某个 ready chunk 也可能因 contract 失败被拒绝。因此每个事件至少绑定 session_id/request_id/chunk_id 中适用的键，并携带 authority_epoch。审计时先按 session 与 request 建因果关系，再把 dispatch 序列投影到 control tick；不能只按 wall-clock 排序后假设相邻行属于同一动作块。

对缺失事件采用显式状态：not_observed 表示采集系统没看到，not_applicable 表示该路径确实没有，rejected_before_event 表示流程提前终止。三者不能都写 null。只有这样，分析者才能区分日志缺口、设计分支与真正故障，也才能解释为什么某个 chunk_ready 没有后续 dispatch。

动作块、长度与动作 ABI

从 observation anchor 到 target tick

在观测/请求 anchor tick k_obs 上，策略产出长度为 H 的动作块：

\[A^{(k_{\mathrm{obs}})}= \left[a^{(k_{\mathrm{obs}})}_0,\ldots,a^{(k_{\mathrm{obs}})}_{H-1}\right].\]

若 policy contract 没有另行声明，本站采用半开索引 i in [0,H)，并把局部位置映射为：

\[k_{\mathrm{target}}=k_{\mathrm{obs}}+i.\]

这不是所有策略的天然真理。采用 future offset、history center、camera exposure center 或 action-latency compensation 的模型必须在 contract 中修改映射。尤其不能默认 index 0 一定表示 observation tick 的“下一步”。

七个核心量各有所有者

| 符号 | 站内定义 | 单位 | 所有者 | 不是 | | — | — | — | — | — | | H | policy 一次预测的动作数 | action steps | policy/checkpoint | 执行完整块的承诺 | | s_plan | 配置的计划执行/切换跨度 | control ticks | scheduler | solver steps | | s_run | 两次相关 anchor 在 trace 中实际相隔 tick | control ticks | runtime trace | 隐藏 jitter 的固定常数 | | delta_meas | 指定测量边界内的连续实测延迟 | time | monotonic trace | 无边界的“总耗时” | | d_meas | 延迟期间实际经过的完整控制 tick | control ticks | event/tick trace | 下一次预测值 | | d_hat | 调度决策前冻结的预测 delay | control ticks | predictor/scheduler | 事后真值 | | n_flow | 一次生成的数值采样步数 | solver steps | policy sampler | execution steps | | R | 新旧块在绝对时间上可对应的长度 | action steps | alignment | queue depth |

论文初次引用时可写裸 s 与 d，但必须立即映射到 s_plan/s_run/d_hat/d_meas。日志、接口、模板与伪代码不使用语义不明的裸 s、d、n。queue_depth、committed_count 与 valid_suffix_count 另行记录，也不复用为 s。

参数名不能跨来源直接等同

论文、Kinetix 示例、LeRobot 当前文档与本站 contract 可能用相近名字表达不同区间。阅读实现时先根据事件、单位和索引范围判断语义，再建立版本化映射；看到 execution_horizon 不能直接断言它等于论文的 s。

概念 论文符号 实现中可能出现的名字 本站冻结名
chunk length H chunk size / prediction horizon chunk_size_H
planned execution spacing s execute horizon / replan stride planned_stride_s
measured spacing Algorithm 1 中运行时 s=t elapsed steps / stride measured_stride_s_run
overlap window H-s prefix attention / execution horizon overlap_length_R
predicted delay d_hat delay estimate / queue estimate predicted_delay_d_hat
measured delay d inference delay ticks measured_delay_d
solver steps n 或实现自定义 flow steps / denoise steps solver_steps_n_flow

表中的“可能出现”不是 API 承诺。每条映射要绑定仓库、commit/tag、配置路径与检查日期，并说明它代表配置意图、trace 实测还是派生量。若同一字段在不同版本改变含义，保留两条带版本记录，不把历史数据按新定义重解释。

任何实现字段只有在单位、起止事件、半开区间和 owner 都匹配时，才可写入本站冻结字段。无法确认时使用 source-specific 原名并标记待验证；这比填入看似标准但语义错误的 s_run 或 d_meas 更安全，也避免后续 Guided、Training-Time 与 Runtime 在同名字段上实际讨论不同系统。

Action ABI 先于任何对齐

新旧块要么具有相同 action_abi_hash，要么经过有版本和 hash 的 adapter 转换到同一比较空间。至少核对：

  • batch、sequence、action dimension 与维度名称/顺序；
  • absolute、delta、velocity 或 torque 语义；
  • reference frame、unit、normalization/statistics；
  • gripper/tool mapping、padding/mask 与 controller consumer；
  • target tick convention、时间戳含义与 offset。

shape 相同不能证明 ABI 相同。delta action 若相对各自 inference-start state 定义，两个数值相同也可能指向不同物理目标；比较前必须重锚定。详细 ABI 规则归公共动作表示页。

ABI 不一致时先停止比较

常见错误是看到两个张量都是 [H,M] 就逐元素求差。比如旧块第 0–5 维可能是 joint position，新块同样六维却是末端 delta；又或者两者都是 pose，却分别位于 base frame 与 camera frame；再或者 gripper 的 0/1 编码方向相反。此时“平滑差值很小”没有物理含义，继续构造 prefix 只会把错误藏进 mask。

adapter 必须说明输入/输出 ABI、坐标变换来源、统计量版本、可逆性以及离散字段的处理方式。转换失败、frame transform 过期、维度名缺失或 normalization hash 不匹配时，候选块应标为 rejected，而不是退化成按位置猜测。旧、新块都完成转换后，再计算 absolute tick 对应与动作差；转换前后的 artifact reference 应保留，方便追溯误差来自策略还是 adapter。

action ABI 还要回答 consumer 语义。相同的 position setpoint，在控制器把它解释为立即目标、插值端点或带 deadline 的轨迹点时，会形成不同执行结果。RTC 只对齐候选动作及其时序，不替代 controller contract；没有 consumer、rate、hold/timeout 与 acknowledgement 定义，就不能声称两个块已经“无缝”交接。

从连续延迟到调度 delay

两个测量边界必须分名

默认模型生成延迟从 inference_started 测到 chunk_ready：

\[\delta_{\mathrm{meas}}= T(\text{chunk\_ready})-T(\text{inference\_started}).\]

调度若关心“观测何时变成可合并动作”，还应测：

\[\delta_{\mathrm{usable}}= T(\text{chunk\_merge\_committed})-T(\text{observation\_captured}).\]

二者不能都叫 inference latency。预处理、传输、排队、postprocess、adapter 与 validation 是否被包含，必须写进 measurement manifest。

论文离散量与 scheduler policy 分开

在固定控制周期 Delta t 的简化条件下，论文型离散量可以写成：

\[d_{\mathrm{meas}}= \left\lfloor\frac{\delta_{\mathrm{meas}}}{\Delta t}\right\rfloor.\]

实际跨过的 tick 应优先由事件 tick 差计算。若工程采用 ceil、最近整数或额外裕量，这是 scheduler policy，必须记录 rounding mode 与 margin，不能改称论文原定义。固定周期不成立时，使用实际 tick/时间戳，不用平均频率反推每一个样本。

延迟链路可分解、可定位

| 组件 | 起点 → 终点 | 至少记录 | | — | — | — | | sensor age | exposure/measurement → observation captured | sensor clock、同步不确定度 | | preprocessing | captured → inference request ready | crop/resize/tokenize 版本 | | queue wait | request ready → model starts | device/server queue 与负载 | | model compute | model starts → model output | warm/cold、n_flow、device mode | | postprocess | output → chunk validated | unnormalize、adapter、finite/shape check | | merge | validated → merge committed | lock/queue epoch、保留与替换范围 | | dispatch age | target/observation → first dispatched | k_switch、staleness | | ack | dispatch → controller ack | controller seq、timeout |

平均值只能描述中心位置。调度审计至少报告 p50、p95、p99、max、deadline miss、cold-start/warm-up 与负载条件，且保留各分位数的测量边界。

测量清单要能复现数字

一次延迟报告应同时冻结 software revision、checkpoint/processor/adapter hash、执行设备与模式、请求 batch、输入形状、n_flow、队列策略、并发度、采样窗口和排除规则。仅写“平均推理 80 ms”无法判断是否包含预处理、是否混合冷启动，也无法换算成可靠的 tick。若页面引用外部数字，必须保留原作者的边界与硬件语境，不能直接搬成本站的部署保证。

异常样本不得为了图表整齐而静默删除。timeout、cancelled request、shape rejection、clock reset 和负 duration 各自计数；负 duration 通常说明 clock domain 或事件关联错误，不应取绝对值。分位数按请求计算时，要说明被拒请求是否纳入；按控制 session 汇总时，要避免长 session 用样本数完全淹没短 session。

从连续时间转为 tick 时，还需验证观测到派发之间是否跨越 controller pause 或 rate change。若跨越，floor(delta/Delta t) 与实际 tick 差可能不同；此时 event tick 是主记录，连续 duration 用于解释链路，二者都保留而不强行改成一致。d_hat 的质量则用误差分布和 miss rate 评估，不能只比较均值。

d_hat 是带版本的预测，不是事实

d_hat 可以来自 recent max、rolling quantile、mode/hardware profile、conservative fixed bound 或 compile/warm-up state machine。这里不推荐数值，只要求记录 predictor version、输入窗口、输出时刻、prediction error 与 miss。d_meas > d_hat 时交给 Runtime 的超时/降级策略，不能静默缩短已提交前缀，也不能回写历史预测使 trace 看似命中。

Temporal Ensembling 聚合同一绝对未来时刻

Temporal Ensembling 先把不同请求对同一绝对未来 tick 的预测配准，再按声明的权重聚合。它不是“取两个数组同一局部 index 做平均”，也不是生成过程中的 prefix conditioning。ACT 的具体实现属于 ACT；这里仅保留通用比较轴。

RTC 的差别在于：Guided 分支把旧块信息注入推理期采样，Training-Time 分支把 prefix/delay conditioning 学入 checkpoint；两者共享本页的问题模型，但条件注入点不同。

比较基线时保持输入、时钟与失败口径一致

公平比较不是只换方法名。各基线应使用同一 observation/target convention、Action ABI、controller 消费规则、负载窗口和安全 gate，并分别记录等待、过期、拒绝、deadline miss 与 fallback。同步方法若由底层 hold 上一目标，等待期仍有控制输出；朴素异步若裁掉前缀，统计时不能把被裁位置计作有效预测；RTC 若额外执行 VJP，也必须把其计算纳入同一延迟边界。

Temporal Ensembling 的缓存键应至少包含绝对 target tick、control session 与 ABI/authority epoch。按局部 index 聚合会把不同物理时刻混在一起；跨接管 epoch 聚合则会把 policy proposal 与人工或 safety 动作混在一起。权重随预测年龄、请求时刻或其他量变化时，要写出方向和归一化规则，并明确没有预测的 tick 如何处理。

“轨迹更平滑”只是一项现象指标。还要分别观察 fresh-observation reactivity、任务结果、动作/速度/加速度跳变、过期率、超时、拒绝和安全介入。平滑可能来自对新观测反应变慢，抖动也可能来自合理避障修正；任何单一曲线都不能替代带事件语义的闭环解释。

将新旧块对齐到同一绝对 tick

两块只有映射到物理 tick 后才能比较

旧块 anchor 为 k_old，新块 anchor 为 k_new：

\[A^{\mathrm{old}}[j]\mapsto k_{\mathrm{old}}+j, \qquad A^{\mathrm{new}}[i]\mapsto k_{\mathrm{new}}+i.\]

同一物理 tick 的索引满足：

\[k_{\mathrm{old}}+j=k_{\mathrm{new}}+i, \qquad j=(k_{\mathrm{new}}-k_{\mathrm{old}})+i.\]

若两次 anchor 相隔 s_run=k_new-k_old，则 A_new[i] 对应 A_old[s_run+i]；在相同 target convention 下，旧块能提供的最大对应长度为 R=H-s_run。

过期不等于 committed，proposal 不等于 executed

若 k_ready=k_new+d_meas，则局部 i<d_meas 的 nominal target tick 已过期。它们不能再次 dispatch；若 trace 证明旧块对应动作确已或将执行，可以作为条件前缀。若 safety gate 改写动作，条件应引用实际 committed/executed action，而不是模型原始 proposal。authority 从 policy 切到 human、fallback 或 safety 后，也不能继续把旧 policy 计划冒充实际动作。

i_switch=d_meas 只是理想起点

理想首个可派发索引是 i_switch=d_meas。真实系统还要计入 validation/merge 所跨 tick、queue 中不可撤销动作、controller lookahead、transport batching、插值和 missed/deferred tick。因此 Runtime 必须记录实际 i_switch 与 k_switch，不能只从模型 latency 推测。

半开区间消除 off-by-one

  • chunk index：[0,H)；expired prefix：[0,d)；
  • overlap reference：[0,H-s)；soft region：[d,H-s)；free suffix：[H-s,H)；
  • 测试至少覆盖 delay 0、1、H-s=d、d>H-s 与 d>=H；
  • controller contract 要声明 a_i 是在 tick k+i 派发的 setpoint，还是覆盖 [k+i,k+i+1) 的命令。

absolute joint/pose 在 frame 与 unit 一致时可按同一 target tick 比较；delta action 需要重锚定；velocity/torque 的重复与保持有不同累计物理效果；带 timestamp 的 trajectory 优先用内嵌时间；离散 gripper event 通常不适合平均或插值。

对齐 worksheet 先算 tick，再决定动作

每次切换可以按固定顺序完成一张静态 worksheet：先记录 old/new chunk_id 与 anchor；再列出每个局部 index 的 nominal target tick；用 event trace 标出 ready、validated、merge 与实际 dispatch；随后把旧块同 tick 的 proposal、committed、实际 dispatched/feedback 分列；最后才计算 hard、soft 与 free 区域。这样能把“模型想做什么”“队列承诺什么”“控制器收到什么”分开。

以上图的虚构值为例，k_old=100、k_new=103、H=8，所以 s_run=3 且 R=5。新 i=0..4 分别对应旧 j=3..7；如果 d_meas=2，新 [0,2) 的 nominal tick 103、104 已过期，理想切换从 i=2、tick 105 开始。新 i=5..7 没有旧块对应位置，属于 free suffix。此例只验证索引，不给出真实控制频率或动作值。

若 queue 已提交到 tick 106，模型延迟仍为 2，也不能回到 tick 105 派发；实际 k_switch 至少推到 107，相应 i_switch 也要更新。若新块只覆盖到 110，但不可撤销队列把切换推到 111，则 valid suffix 为空，Runtime 应拒绝或降级，而不是循环新块最后一个动作。由此可见，d_meas 决定过期的最低界，committed boundary 可能进一步缩短可用后缀。

不同动作类型还影响“旧动作可作为条件”的证据。position target 可引用已提交 setpoint，但 feedback 可能表明尚未到达；velocity/torque 需要结合实际持续时间；delta action 必须知道起始状态；离散事件要防止重复触发。对齐表应记录 condition 使用 proposal、committed 还是 feedback，以及选择理由，不能统一称为 executed prefix。

可行域与 hard/soft/free 三段

d <= s <= H-d 的前提与推导

只在以下简化条件下讨论裸 H/s/d：固定块长与控制周期；一次相关推理在 d tick 内结束；新旧 anchor 相隔 s；旧块覆盖 H tick；忽略 validation/merge/controller 的额外延迟；单一相关 worker 不在上次推理前再启动；两块 Action ABI 与 target convention 一致。

若推理开始不早于旧 anchor，需要 d<=s；若旧块要覆盖到新块 ready，需要 d<=H-s。合并得到：

\[d\le s\le H-d.\]

这是简化调度可行性，不是任务成功率、稳定性、安全或 hard real-time 证明。任何前提被破坏都要回到事件 trace 与 Runtime contract，而不是继续套公式。

三段同时编码时间事实与条件语义

| 标记 | 半开区间 | 时间/authority 状态 | Guided 解释 | Training-Time 解释 | | — | — | — | — | — | | A · hard/expired prefix | [0,d) | nominal target 已过期；是否 committed 另证 | 强条件，典型权重 1 | clean prefix condition | | B · soft overlap | [d,H-s) | 未执行，但旧块有对应计划 | 声明的衰减权重 | 是否条件化由训练设计声明 | | C · free suffix | [H-s,H) | 旧块没有对应目标 | 权重 0 | postfix prediction/loss |

退化情形必须显式测试

| 条件 | 预期结果 | | — | — | | d=0 | hard prefix 为空；soft overlap 仍可存在 | | H-s=d | soft overlap 为空，只剩 hard 与 free | | s=H | overlap 为空；若 d>0，右侧可行域不成立 | | d>s | 原单 worker 启动假设不成立，需要并发或其他调度 | | d>H-s | 旧块在新块 ready 前耗尽，进入明确降级 | | H-s-d<0 | 配置非法，不构造负长度 mask | | d>=H | 新块返回时所有 nominal positions 已过期 | | variable control rate | 不用固定 Delta t，按实际事件/tick 对齐 | | skipped tick | 记录 gap，不按连续整数补齐 | | authority change | 用实际 authority 与 executed action 重建 prefix |

Foundations 只冻结 Soft Mask 的最小约束：hard prefix 上 W_i=1；soft overlap 内满足声明的范围与非增规则；free suffix 上 W_i=0；shape 能与动作块广播；NaN/Inf 直接拒绝。具体函数、beta、VJP 与 clipping 归 Guided。Training-Time 是否复用相同 soft region 也不能由本页自动规定。

可行、退化与不可行要用不同状态

配置检查不应只返回布尔值。feasible_under_assumptions 表示当前数值满足简化不等式且前提经确认；degenerate_but_defined 表示某段为空但区间仍合法，例如 d=0 或 H-s=d；infeasible_for_this_scheduler 表示旧块覆盖不足或启动约束被破坏；unknown_due_to_missing_trace 表示无法确认实际 s_run/d_meas。unknown 不能自动当 pass，也不能为了继续流程被填成预测值。

当 d>H-s 时，可选措施属于 Runtime/系统设计：延长经过验证的覆盖、改变调度、降低请求频率、切换 fallback 或进入 safe state。Foundations 不替任何平台选择动作。尤其不能简单把 d clip 到 H-s，因为这会让 mask 看似合法，却隐藏新块返回前旧队列已经耗尽的事实。

对 variable rate 与 skipped tick，区域可以在 index space 中保持半开写法，但过期判定仍要用目标时间与事件 trace。若 policy 输出带时间戳的 trajectory，H-s 不再足以表达真实重叠；应构造 timestamp intersection，并在 branch contract 里声明 alignment mode，而不是把不等间隔轨迹强塞进固定 tick 公式。

Contract 不变量

  1. old/new action_abi_hash 相同，或显式记录 adapter version/hash 与转换前后空间。

Contract 生命周期与拒绝路径

contract 在请求创建时先冻结版本、ABI、clock domain、anchor 与 d_hat；此时 k_ready/d_meas 保持 null。结果返回后追加 ready 事件和实测字段，再做 schema、shape、finite、range、authority epoch 与 region coverage 检查。只有全部通过才生成新的 immutable contract hash 并交给分支或 Runtime。更新不是原地覆盖历史记录，而是保存前后版本的父子关系。

拒绝原因应是稳定枚举，例如 abi_mismatch、clock_domain_unknown、authority_epoch_changed、invalid_region、non_finite_action、no_valid_suffix 或 deadline_miss，同时允许附带不含敏感数据的解释。调用方不得把所有拒绝归成 model failure，因为许多问题来自日志、adapter、queue 或 controller contract。

branch 输出必须回显输入 hash、branch mode 与 compatibility evidence。Guided 不能只写“普通 checkpoint 可用”，而要证明 sampler 可迭代、梯度路径与 dtype/device 合法；Training-Time 不能只凭模型名称推断 prefix conditioning，而要有训练配置与 checkpoint metadata。证据不足时 compatibility=unknown，候选不得进入 merge。

Runtime 对候选的任何裁剪、重锚定、fallback 或 safety 修改都产生新的 provenance 记录。这样复盘时可以区分算法输出、运行时变换与最终派发，也能在不保存原始敏感观测的情况下重建决策链。

三个消费者各负其责

  • Guided 消费旧块 reference/committed action、三段范围、comparison space、iterative sampler、dtype/device；产出 guided candidate、guidance trace 与数值健康信息，不负责 queue merge。
  • Training-Time 消费 delay support、clean prefix、per-token condition/mask、postfix target/loss 与 checkpoint compatibility；产出 trained checkpoint contract 与 compatible inference input，不负责 queue merge。
  • Runtime 接收任一分支的 candidate、provenance、预测/实测 delay、committed boundary、valid suffix、mode health 与 reject reason；它负责 validation、merge、dispatch、timeout 与 fallback，Safety 保留最终执行 gate。

适合已有兼容 iterative Flow/Diffusion checkpoint、无法或暂不重训练、能够承担 VJP/guidance compute，并有离线数值验证能力的情况。

应交付：mask/target/VJP/beta 语义、clipping 与稳定性记录。

Training-Time Action Conditioning

适合可修改训练样本与 loss、checkpoint 明确训练了 prefix/delay conditioning、部署 delay 在支持范围内，并能验证训练/部署一致性的情况。

应交付：delay distribution、prefix mask、postfix loss 与 checkpoint contract。

进入 Training-Time Action Conditioning

无法判断 checkpoint 能力时，选择结果应是“先做 contract 缺口审计”，不是猜测支持。两页都学习属于深入路线；Runtime 使用 merge_policy:any，不要求两个分支全部完成，也不把 Training-Time 写成 Guided 的后继。

| 决策问题 | Guided | Training-Time | 证据不足时 | | — | — | — | — | | 可否修改训练流程 | 不要求 | 必须可控训练数据与 loss | 记录 owner，不猜 | | checkpoint 条件 | compatible iterative sampler | 明确训练过 prefix/delay conditioning | 标记 compatibility unknown | | 主要新增成本 | VJP/guidance 与数值检查 | 训练、数据构造与一致性验证 | 先完成成本清单 | | delay 范围 | 受推理与 runtime contract 约束 | 还受训练支持范围约束 | 测量分布，不外推 | | 关键交付 | guidance trace、mask、clipping | training contract、prefix/postfix loss | contract 缺口审计 |

选择记录应引用 checkpoint/code/processor/adapter hash、证据来源版本与验证日期。若两条路线都满足，可以分别做离线候选评估，但进入 Runtime 时仍需明确本次 request 的单一 branch mode，避免把两套条件化无意叠加。若两条都不满足，则退出算法选择并修补基础 contract，而不是用平滑滤波冒充 RTC。

完成检查与返回路径

本页完成检查

读者应能在不猜测的前提下填写或标记 unknown：

  • H/s_plan/s_run/d_hat/d_meas/n_flow/R 的单位与所有者；
  • observation、start、prediction-bound、ready、validated、merge、dispatch、ack、feedback 九事件；
  • old/new anchor 与 local index 到绝对 tick 的映射；
  • proposal、committed、dispatched、executed/feedback 的区别；
  • [0,d)、[d,H-s)、[H-s,H) 三段；
  • d<=s<=H-d 的全部简化前提与至少四个失效条件；
  • Action ABI hash、adapter hash 与 target convention；
  • Guided、Training-Time 或 unknown reason 的选择记录。

完成本页不等于可以真机运行。下一阶段仍要经过所选算法分支、Runtime 的异步队列与失败策略、policy I/O contract、独立 Safety gate 和现场 risk acceptance。

最小审计产物

本页的验收产物是六份可静态复核的记录：notation manifest、event trace schema、chunk alignment worksheet、feasible-region worksheet、branch handoff contract 与 branch choice record。每份记录都应有版本、hash、owner、输入证据和 unknown/reject 状态；没有真实设备数值也可以完成结构审计。

审阅者应从任一 dispatch 反向追到 merge、validation、candidate、request 与 observation，从任一 candidate 正向看到 accepted、rejected 或 expired。若链路在中途断开，结论只能是“证据不足”，不能用连续曲线或视频观感填补。真实部署还要把这些记录接入 incident trace、safe state 与人在回路 authority，但那些执行策略不在本页定义。

验收时再做一次独立交叉检查：由未参与填写的人随机选择一个正常样本和一个拒绝样本，重新计算 index 到 tick 的映射、区间并集与 contract hash。如果复算结果依赖口头解释、临时脚本状态或未保存的配置，产物仍不完整；应把缺失证据写回 worksheet，而不是在结论中省略。
