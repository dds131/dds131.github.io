π0 的架构可以用论文里的一句话概括：它被实现为一个单一的 transformer，带有两套权重（也就是两个专家），每个 token 被路由到其中一个专家，而两套权重只通过 transformer 的自注意力层发生交互。

这句话每一个分句都有具体的实现含义。本页把它拆到可实现的粒度：两套权重分别算什么、为什么不同宽度仍能联合注意力、信息究竟在哪些算子中交换、论文的缓存设计与固定源码实现有何差别，以及多步 Flow Matching 推理为何要求动作专家保持轻量。

2048 / 1024两个专家的宽度
256每路相机的图像 token 数
867默认配置下的最大槽位数
3因果掩码的块数
816 : 51prefix 与 suffix 最大槽位数
π0 架构的核心事实来自论文 arXiv:2410.24164v4 的正文第四节与附录 A-B，以及 openpi commit 215abfb；第十节的跨版本对比另参考 π0.5 论文。论文用于说明方法与设计意图，固定源码快照用于说明可复核的公开实现；两者不一致时正文会并列标出。若使用更新的 openpi，应先核对配置、张量形状与缓存路径是否发生变化。

一、本页在专题中的位置

总览页 给出了整条链路的形状与去向，回答的是「数据从哪进、到哪出、中间变成什么形状」。本页回答的是下一层问题：这些形状是怎么算出来的，以及为什么必须是这样。

本页刻意不讲的内容：Flow Matching 为什么是生成式的、速度场的数学定义、时间步分布的形式，这些属于子页 ②；论文与源码的时间方向差异属于子页 ③；逐函数的源码走读属于子页 ④。本页只在需要时引用它们的结论，不重复论证。

二、PaliGemma：π0 的视觉-语言底座

论文明确说明，选用 PaliGemma 是出于便利性与它相对较小的体量（这对实时控制有用），并强调这套框架兼容其他预训练 VLM。因此，PaliGemma 是 π0 的具体底座，而不是方法成立的唯一选择。架构层面的关键增量是机器人状态与动作的输入输出通路、动作专家，以及 Flow Matching 动作生成。

更准确地说，PaliGemma 包含 SigLIP 视觉编码器和 Gemma 解码器式 Transformer 主干，并不是 CLIP 那样彼此独立的对称双塔。π0 继承视觉编码器、词嵌入与 VLM 主干，再增加机器人专属模块。

2.1 SigLIP 视觉塔：图像如何变成 token

源码里视觉塔的实例化参数是 variant="So400m/14"、pool_type="none"、num_classes 设为 VLM 主干的宽度。这三个参数各自决定了一件事。

变体串的两半So400m 决定网络规模：宽度 1152、深度 27、MLP 维度 4304、16 个注意力头。斜杠后的 14 是 patch 的边长。
patch 边长决定 token 数输入分辨率固定为 224 乘 224，于是每边切出 224 除以 14 等于 16 个 patch，全图 16 乘 16 等于 256 个 token。
不做池化pool_type 取 none，表示不把这 256 个 token 汇聚成一个全局向量，而是逐 token 输出。视觉信息以序列形式进入 Gemma 主干，后续自注意力可以访问不同图像区域。
输出宽度对齐num_classes 被设成主干宽度 2048，作用是把视觉塔的 1152 维输出投影到与语言 token 相同的嵌入空间。

在论文发布配置与固定提交中，输入会预处理为 224 乘 224，对应固定的 16 乘 16 patch 网格和可学习位置编码。若要换分辨率，不能只改输入张量，还需要同时处理 patch 网格与位置编码；这属于改模型配置，而不是现有 checkpoint 的即插即用能力。

2.2 Gemma 主干与词嵌入

语言侧沿用 Gemma 2B 的词表与嵌入。指令文本经分词后查嵌入表，得到与图像 token 同宽度（2048）的向量。π0 的语言 token 上限是 48。

主干本身的源码配置为：宽度 2048、深度 18、MLP 维度 16384、8 个查询头、1 个键值头、头维度 256。论文附录把 num_heads 写成 18，但 18 实际是层数；openpi 源码与 Gemma 规格均为 8，因此本页采用源码值。

「1 个键值头」意味着 Gemma 2B 用的是多查询注意力：8 个查询头共享同一组键与值。这对 π0 是一个额外的便宜——推理时要缓存的 prefix 键值只有单头的量，而不是八头的量。论文在描述这套配置时也点明了多查询注意力这一点。

2.3 late fusion：视觉编码器怎样接入 Gemma

论文说明 π0 遵循标准的 late fusion VLM 配方：图像编码器把图像观测投影到与语言 token 相同的 2048 维空间，随后二者沿序列轴拼接并进入 Gemma 主干。这与「另建交叉注意力，让解码器读取视觉编码器输出」不同。这里说的是 prefix 内部的图像与语言 token：它们使用同一套 VLM 专家权重并在同一自注意力中交互；机器人 state 与动作 token 随后会走另一套、更窄的专家权重。

  VP --> VTK["256 个图像 token<br/>宽度 2048"]

三、双专家：一个 Transformer，两套权重

这是 π0 架构里最核心、也最容易误解的一点。论文自陈这个结构受 Transfusion 启发：Transfusion 在一个 Transformer 中对连续输出使用 Flow Matching、对离散输出使用交叉熵。π0 借用了“连续 token 与语言模型主干共存”的思路，并进一步给机器人专属的 state 与动作 token 单独配一套权重。这里的交叉熵描述的是 Transfusion 的配方；π0 论文给出的机器人训练目标是动作 Flow Matching 损失，不能据此推断它同时对语言 token 计算交叉熵。

3.1 常见的两种误读

误读 为什么不对
PaliGemma 后面接了一个 Transformer 解码器，用交叉注意力读取 VLM 的输出 根本没有交叉注意力。所有 token 在同一条序列上做一次自注意力，动作 token 与图像 token 之间是普通的注意力关系，不是解码器读取编码器的关系
动作专家是个层数更少的轻量网络 层数完全相同，都是 18 层。两个专家的权重在每一层都并存，逐层交替计算

正确的心智模型是：prefix 与 suffix 在逻辑上组成最长 867 个槽位，但隐藏状态始终保持为两个不同宽度的数组；每一层先分别投影，再把头几何一致的 Q/K/V 沿 token 轴拼接，完成一次联合自注意力，最后按原分段切回各自通路。跨专家信息交换发生在联合注意力的打分、归一化和 value 聚合中，不只是 softmax 的某一瞬间。

3.2 交互到底发生在哪一步

源码里的一个 Transformer block 按下面的顺序执行。注意哪些步骤是按专家分开做的，哪些是合起来做的。

步骤 分开还是合并 说明
注意力前的归一化 分开 每个专家一个 pre_attention_norm
计算查询、键、值 分开 每个专家用自己的投影权重，从各自宽度映射到相同的头几何
沿 token 轴拼接 Q/K/V 合并 只拼投影后的 Q/K/V；不同宽度的原始隐藏状态不直接拼接
RoPE、缩放与注意力打分 合并 计算跨专家的 \(QK^\top/\sqrt{256}\)，并施加分块掩码
softmax 与 value 聚合 合并 对完整 key 轴归一化，再用注意力概率加权 \(V\)；跨专家信息在这里写入输出
按 token 段切回 分开 联合注意力输出按 prefix / suffix 的原长度切开
注意力输出投影 分开 每个专家用自己的输出投影，分别回到 2048 与 1024
残差、前馈前归一化、前馈网络、残差 分开 每个专家一套，前馈网络使用自己的 MLP 维度

也就是说，两个专家共享的是联合自注意力的计算域，而不是参数：归一化、Q/K/V 投影、输出投影和 FFN 都各有一套权重；投影后的 Q/K/V 才进入同一个注意力算子。论文所说的「两套权重只通过自注意力层交互」，对应的是从跨专家打分到 value 聚合的完整链路。

不同宽度为什么还能联合注意力？设默认最大长度为 \(L_v=816\)、\(L_a=51\)：

\[X_v^{(\ell)}\in\mathbb{R}^{B\times L_v\times 2048},\qquad X_a^{(\ell)}\in\mathbb{R}^{B\times L_a\times 1024}.\]

两段隐藏状态不直接拼接。每个专家先用自己的权重投影：

\[Q_e\in\mathbb{R}^{B\times L_e\times 8\times256},\qquad K_e,V_e\in\mathbb{R}^{B\times L_e\times1\times256}.\]

随后令 \(Q=[Q_v;Q_a]\)、\(K=[K_v;K_a]\)、\(V=[V_v;V_a]\)，只在 token 轴上拼接，并计算

\[A=\operatorname{softmax}\!\left(\frac{QK^\top}{\sqrt{256}}+\widetilde M\right),\qquad Z=AV.\]

其中 \(\widetilde M\) 在可见位置取 0、屏蔽位置取负无穷。由于采用多查询注意力，单组 K/V 会共享给 8 个查询头。\(Z\) 再按 \(L_v/L_a\) 切开，经两个专家各自的输出投影分别回到 2048 与 1024 维。

3.3 源码强制的三条约束

因为 Q/K/V 要沿序列轴拼成一条，两个专家的头几何必须完全一致，否则拼不起来。源码在注意力模块的开头用三条断言把这件事钉死：

# src/openpi/models/gemma.py，Attention.__call__ 开头
# all experts must share the same head dim, num heads, and num kv heads for self-attention to work
assert all(config.head_dim    == self.configs[0].head_dim    for config in self.configs)
assert all(config.num_heads   == self.configs[0].num_heads   for config in self.configs)
assert all(config.num_kv_heads == self.configs[0].num_kv_heads for config in self.configs)

对照两个变体的实际配置，可以看清哪些必须相同、哪些是自由的：

配置项 gemma_2b gemma_300m 是否必须相同
width 2048 1024 否
mlp_dim 16384 4096 否
depth 18 18 是（两套权重要逐层并存）
num_heads 8 8 是（断言强制）
num_kv_heads 1 1 是（断言强制）
head_dim 256 256 是（断言强制）

论文的表述与此完全一致：「由于两个专家只在自注意力层交互，width 与 mlp_dim 不必在专家之间匹配。」反过来说，头几何则必须匹配。

留意多查询注意力里的维度并不对称：动作专家的 Q 有 8 个头，总维度为 8 乘 256 等于 2048；K 与 V 各只有 1 个头，总维度分别为 256，并共享给 8 个查询头。value 聚合后的结果重新具有 8 乘 256 的头维度，再由动作专家自己的输出投影映射回 1024。不能把 Q、K、V 都简称为“升到 2048 维”。

3.4 与 Mixture of Experts 的区别

论文把这个设计描述为「类比于一个有两个混合元素的 mixture of experts」。下面比较的是典型的稀疏、门控式 MoE，并非所有 MoE 变体都必须满足这些特征：

路由方式典型稀疏 MoE 用可学习 router 选择专家；π0 则按模态固定分流：图像与语言走 VLM 专家，state 与动作走动作专家。它没有可学习 router 的选择不稳定，但固定路由也限制了参数共享方式。
负载均衡典型稀疏 MoE 常用负载均衡损失，避免 token 集中到少数专家。π0 的 token 数由输入结构决定，不需要为这两个固定分支增加该损失。
专家关系典型 MoE 的候选专家常采用同构设计。π0 的两套权重异构且职责固定：VLM 专家继承预训练权重，动作专家从零初始化，二者宽度也不同。

正因为这些差别，用 Mixture of Transformer Experts（MoT） 来称呼这种「按模态固定分流、逐层两套完整权重、只共享注意力」的结构，比直接叫 MoE 更贴切。

3.5 与编码器—解码器结构有何不同

π0 论文没有给出“为什么不采用编码器—解码器”的完整消融，因此不能把某一种动机写成作者已经证明的结论。根据实际计算图，可以确认三点差别：

  1. π0 不新增交叉注意力模块，而是在每一层让动作查询直接读取该层的图像与语言 K/V。
  2. prefix 继续沿用 PaliGemma 的自注意力路径，更直接地复用预训练参数。
  3. 动作表示逐层接触 VLM 中间表示，而不是只依赖一个固定的编码器输出接口。

这些特点解释了当前设计怎样复用预训练 VLM，但不意味着编码器—解码器只能读取最后一层，也不意味着其他架构必然破坏预训练权重。事实上，论文的 π0-small 基线就采用了动作专家交叉注意观测编码器输出的结构。

四、token 序列是怎么拼的

逻辑序列分为 prefix 与 suffix 两段，分别由 embed_prefix 与 embed_suffix 构造。二者共享 token 顺序、位置编号和注意力掩码，但由于隐藏宽度分别是 2048 与 1024，源码不会把原始 embedding 拼成一个同宽张量，而是以两个数组送入双专家主干；进入注意力后，Q/K/V 才沿 token 轴拼接。

段 内容 数量 走哪套权重 构造方式
Prefix 图像 token 每路 256，默认 3 路共 768 VLM 专家 逐路过 SigLIP，输出按序拼接
Prefix 语言 token 最多 48 VLM 专家 分词后查 Gemma 嵌入表
Suffix state token 1 动作专家 本体状态经一个线性层投影
Suffix 动作 token 50 动作专家 含噪动作与时间步融合后得到

把默认配置代进去：prefix 最长 768 加 48 等于 816，suffix 是 1 加 50 等于 51，整条序列最长 867 个 token。

4.1 相机路数不足时怎么办

模型认的是固定的相机键名（一路底座视角加左右两路腕部视角）。实际机器人相机路数不足时，缺失的那一路仍然会占据 256 个 token 的位置，但其 input_mask 被置为假，注意力计算时被屏蔽。

这个设计的好处是序列长度固定、计算图形状不变；代价是缺失的相机仍然占用计算，以及一个很隐蔽的失效模式：自建数据集若相机键名写错，那一路会被当作缺失而静默屏蔽，模型不会报错，只是看不见那个视角。

这是复现 π0 时踩坑概率最高的问题之一。现象是训练损失正常下降、真机行为却像少了一个视角——因为模型确实少了一个视角。排查方式是打印实际进入模型的 image_masks，而不是检查数据集里有几个相机。

五、机器人专属输入的编码

prefix 侧沿用 PaliGemma 的既有通路，没有新东西。真正新增的是 suffix 侧的四个小模块。

5.1 状态：一个 token，也补齐到 32 维

本体状态经一个线性层投影成一个 token。两个细节值得单独说。

第一，为什么只占一个 token。 π0 把整个连续状态向量一次线性投影为单个 token，表示紧凑，序列开销也最小。能否缓存并不取决于 state 是一个还是多个 token，而取决于这些 token 是否依赖每步变化的含噪动作：只要 state 自成一块且不能看动作，即使有多个 state token，理论上同样可以缓存。

论文正是按这个理由设计三块掩码；但要区分设计允许与源码已经实现。固定提交的 sample_actions 只预计算并缓存图像与语言 prefix，每个积分步仍会重新调用 embed_suffix，因此 state_proj、state token 及其在动作专家中的 K/V 都会重算。

第二，状态的输入维度也是 action_dim。 默认配置中，状态投影层与动作投影层的输入维度都是 32；官方数据变换会把不同本体的状态和动作映射、补齐到这一统一维度。

# src/openpi/models/pi0.py，Pi0.__init__ 中
self.action_in_proj = nnx.Linear(config.action_dim, action_expert_config.width, rngs=rngs)
...
self.state_proj     = nnx.Linear(config.action_dim, action_expert_config.width, rngs=rngs)

迁移到新本体时，状态与动作必须使用训练配置约定的维度、语义顺序、归一化统计和 padding 规则。最后一维不是 32 通常会在线性层直接触发形状错误；更隐蔽的风险是张量已经有 32 维，但关节顺序、有效维或归一化口径错误，此时程序可能正常运行而语义已经错位。

5.2 含噪动作：每步一个 token

含噪动作块的形状是 50 行 32 列，经一个线性层投到动作专家的宽度，得到 50 个 token——动作块里的每一步对应序列上的一个 token。这一点决定了动作块天然就是一个序列对象，注意力可以直接建模步与步之间的关系。

论文另外指出，动作专家内部使用完全双向的注意力掩码，所有动作 token 互相可见。这与语言模型的因果掩码不同：动作块是一次性整体生成的，不存在「第 10 步还看不到第 30 步」的约束。

5.3 时间步编码：怎样覆盖 0 到 1

流匹配的时间步是一个标量，用正弦余弦编码展开成向量。源码的调用是：

# src/openpi/models/pi0.py，embed_suffix 中
# embed timestep using sine-cosine positional encoding with sensitivity in the range [0, 1]
time_emb = posemb_sincos(timestep, self.action_in_proj.out_features,
                         min_period=4e-3, max_period=4.0)

设编码维度为 \(D=1024\)，对 \(j=0,\ldots,D/2-1\)，源码先生成几何间隔的周期

\[P_j=P_{\min}\left(\frac{P_{\max}}{P_{\min}}\right)^{j/(D/2-1)}, \qquad P_{\min}=0.004,\quad P_{\max}=4,\]

再计算

\[\phi(\tau)=\left[\sin\frac{2\pi\tau}{P_0},\ldots,\sin\frac{2\pi\tau}{P_{D/2-1}}, \cos\frac{2\pi\tau}{P_0},\ldots,\cos\frac{2\pi\tau}{P_{D/2-1}}\right].\]

当 \(\tau\in[0,1]\) 时，最短周期通道约经历 250 个周期，最长周期通道约经历四分之一个周期。多尺度频率共同提供局部敏感度与全局变化，不能只用“最大周期更小”来解释可分辨性。这组范围是固定提交针对 0 到 1 时间区间采用的具体配置。

5.4 动作与时间的融合

含噪动作的表示与时间步的表示拼接后，过一个两层 MLP。论文附录给出的公式与源码逐项对应：

\[\text{token} = W_3 \cdot \mathrm{swish}\!\left( W_2 \cdot \mathrm{concat}\left( W_1 \cdot a^{\tau}_{t'},\; \phi(\tau) \right) \right)\]
论文符号 源码符号 形状
\(W_1\) action_in_proj 32 到 1024
\(\phi\) posemb_sincos 标量到 1024
\(W_2\) action_time_mlp_in 2048 到 1024
\(W_3\) action_time_mlp_out 1024 到 1024

拼接之所以是 2048 维，是因为动作表示与时间表示各 1024 维接在一起。融合之后，每个动作 token 都携带了「这一步的含噪动作是什么」与「现在处在去噪路径的哪一点」两份信息。

这条拼接路线是 π0 的做法。π0.5 改成用 adaRMSNorm 把时间步注入每一层的归一化，动作 token 本身不再携带时间信息——那一页有完整的机制对比，本页不展开。

六、分块因果注意力掩码

这是整个架构里工程价值最高的一个设计，论文正文只用一句话带过，细节在附录。

6.1 三个块

论文把序列划成三个块：图像与语言合为第一块，状态自成第二块，含噪动作为第三块。块内双向，块间因果——每个块内部的 token 互相可见，但任何块都看不到它之后的块。

源码用一个布尔数组 ar_mask 标记块的起点，其构造完全对应上述划分：图像与语言的全部位置为假，状态位置为真，动作块的第一个位置为真、其余 49 个为假。为真表示「这个 token 开启一个新块，此前的 token 看不到它」。

6.2 论文给出的三条理由

附录 A-B 对这个划分给了三条独立的理由，逐条都值得展开。

理由一：保护预训练表示第一块装的正是 PaliGemma 预训练时见过的那两种模态。禁止它注意到后面的块，是为了尽量减小相对于 VLM 预训练的分布漂移——如果让图像语言 token 去注意机器人状态与含噪动作这些预训练期从未出现过的输入，它们的表示就会偏离预训练时的分布，继承来的语义知识随之打折。
理由二：状态具备缓存条件论文明确写道，state 不随流匹配积分步改变；禁止它注意动作块后，其 K/V 在算法上可以跨积分步复用。固定提交尚未利用这项优化，而是每步重算整个 suffix。
理由三：动作需要完整上下文最后一块对应含噪动作，它可以注意到整条输入序列。动作生成需要用到全部可用信息，因此不对它设任何限制。

把论文设计与固定实现分开看，结论才准确：论文把 observation 的 K/V 视为可缓存条件，其中包括 state；commit 215abfb 只先运行并缓存图像与语言 prefix，之后每个积分步用 51 个 suffix query 读取这份缓存，同时重算 1 个 state token 和 50 个动作 token。若完全取消 observation 缓存，最大配置下每步将重新处理完整的 867 个槽位，而不是 817 个。

论文在 RTX 4090 上报告图像编码 14 毫秒、观测前向 32 毫秒、十次动作前向合计 27 毫秒。这些数字是端到端阶段耗时，不能简单等同为“VLM 专家耗时”和“动作专家耗时”；它们说明缓存观测、重复运行动作侧是低延迟推理的核心组织方式。

6.3 源码怎么实现

实现相当精巧，只有两行有效代码。用 ar_mask 的累加和作为块编号，再比较两两之间的块编号大小：

# src/openpi/models/pi0.py
def make_attn_mask(input_mask, mask_ar):
    mask_ar = jnp.broadcast_to(mask_ar, input_mask.shape)
    cumsum = jnp.cumsum(mask_ar, axis=1)          # 每个 token 属于第几块
    attn_mask = cumsum[:, None, :] <= cumsum[:, :, None]   # 只能看块号不大于自己的
    valid_mask = input_mask[:, None, :] * input_mask[:, :, None]  # 屏蔽 padding
    return jnp.logical_and(attn_mask, valid_mask)

ar_mask 每遇到一个真值，累加和就加一，于是同一块内的 token 拿到相同块号，下游块的编号更大。令 \(r_i\) 为 ar_mask、\(c_i=\sum_{k\le i}r_k\)、\(m_i\) 为有效输入 mask，则查询位置 \(i\) 能否看到键位置 \(j\) 可写成

\[M_{ij}=m_i m_j\,\mathbf{1}[c_j\le c_i].\]

因此块内编号相同而双向可见，后面的块可以读取前面的块，反向则被屏蔽。π0 三块在块级别对应

\[\begin{bmatrix} 1&0&0\\ 1&1&0\\ 1&1&1 \end{bmatrix},\]

其中行是 query、列是 key。

这个写法的通用性也值得一提。源码的文档串里举了三个例子：全真数组给出纯因果注意力，前若干位为假、其余为真给出 prefix-LM 注意力，而 π0 用的是分块形式。同一个函数用不同的 ar_mask 就能表达这一整类掩码，不需要为每种模式单写一个实现。

七、位置编码：两层，不要混在一起

这条序列上其实有两套位置信息，作用范围完全不同，混淆它们会导致对架构的误解。

层次 作用范围 机制 说明
视觉塔内部 单张图像的 256 个 patch 之间 patch 位置编码 告诉视觉塔某个 patch 在图上的哪个格子。这也是输入分辨率必须固定的原因之一
主干 最长 867 个槽位的逻辑序列 旋转位置编码 作用于查询与键；position id 由有效 mask 的累积和生成，而非固定槽位编号

训练时主干使用 \(p_i=\sum_{k\le i}m_k-1\) 生成 RoPE position id；推理时 suffix 的起点是 prefix 的有效 token 数。因而 867 是最大槽位数，不是每个样本的有效 token 数，也不是固定的最大位置编号。语言 padding 和缺失相机仍占张量槽位，但会被注意力 mask 屏蔽，也不会推进后续有效 token 的位置编号。

另外要与位置编码彻底区分开的是流匹配时间步编码。它同样使用正弦余弦函数，但编码的是去噪路径进度，与 token 的序列位置无关；在 π0 中，它通过融合 MLP 进入动作 token，而不直接作用于注意力打分。

一句话记法：位置编码决定「相隔多远」，注意力掩码决定「能不能看见」，时间步编码决定「去噪走到哪了」。三者互不替代。需要补底座的话，见位置编码与注意力机制两页。

八、动作专家为什么只有 300M

这是 π0 架构里最值得单独讲的一条因果链，因为它展示了一件事：网络规模不总是由表示能力决定的，也可能由部署约束反推出来。

8.1 计算量的不对称

固定提交的 openpi 推理先运行一次 VLM prefix 以建立 KV cache，随后运行十次 suffix 前向。state 虽然值不变，但仍包含在每步重建的 suffix 中。因此两个专家承担的计算模式明显不对称。

固定提交的推理阶段 图像与语言 prefix suffix（state + 动作）
最大槽位数 816 51
主干前向次数 1 默认 10
KV 复用 固定源码已缓存 固定源码未缓存；state 也随每步重算
论文阶段耗时 观测前向 32 毫秒，不能简单等同于 VLM 专家 十次动作前向合计 27 毫秒

动作专家每次只处理 51 个 suffix 槽位，却要默认运行十遍。若它采用与 VLM 主干相同的 2048 宽度和 16384 MLP，重复前向的成本会显著增加。论文因此明确把缩小动作专家归因于推理加速；至于具体延迟增长比例，需要以实际硬件和实现测量，不能仅凭参数量断言“成倍”增长。

8.2 缩的是宽度，不是深度

论文的原话是：为了加速推理（推理需要动作专家的多次前向），我们把动作专家缩小到宽度 1024、MLP 维度 4096，参数量约 300M。

注意缩的是哪两个量。宽度从 2048 减半到 1024，MLP 维度从 16384 缩到四分之一的 4096——而深度仍然是 18 层，一层不少。

为什么不减层数？因为两个专家的权重是在同一批 Transformer block 里逐层并存的：第 k 层里，前 816 个 token 走 VLM 专家第 k 层的权重，后 51 个走动作专家第 k 层的权重。源码对此有一条直接的断言，位置在多专家主干的构建处：

# src/openpi/models/gemma.py，Module.setup 开头
# all experts must have the same depth
assert all(config.depth == self.configs[0].depth for config in self.configs)

在 commit 215abfb 的逐层一一配对实现中，深度不一致会在模块构建阶段触发断言；头维度、查询头数与 KV 头数也被注意力模块的断言固定。它们是该固定实现与对应 checkpoint 的约束，不是所有双专家架构的数学定理。理论上可以另行设计跳层、非对称层数或公共注意力投影，但那已经属于修改主干结构。

因此，在不修改 openpi 主干代码、保持预训练 VLM 配置不动的前提下，动作专家最直接的缩放自由度是 width 与 mlp_dim。论文采用 1024 和 4096，既保留 18 层逐层交互，又降低多次 suffix 前向的成本。

把证据充分的因果链串起来：Flow Matching 默认需要十次 suffix 前向 → 重复执行的动作专家必须控制成本 → 在当前逐层配对实现中保持相同深度与头几何 → 通过减小 width 与 mlp_dim 得到约 300M。论文明确给出的动机是推理加速；它没有证明“动作本身简单”，也没有证明 300M 是所有实现中的唯一规模。

8.3 参数量的构成

论文给出的总账是：PaliGemma 约 30 亿参数，动作专家新增约 3 亿且从零初始化，合计约 33 亿。动作专家从零初始化这一点值得留意——它不继承任何预训练权重，其全部能力来自机器人数据的训练。这也解释了为什么 π0 需要大规模的跨本体预训练阶段：VLM 侧有互联网知识打底，动作侧则是白纸一张。

9.3 参数量是怎么算出来的

上表的参数量不是抄来的，是按各模块的配置直接累加。核算方法写在这里，便于复核与在改配置后重算。

# 每层参数量（两个专家用同一套公式，只是宽度与 MLP 维不同）
#   FFN 是 GeGLU：gating_einsum 形状 (2, width, mlp)，linear 形状 (mlp, width)
FFN  = 2 * width * mlp + mlp * width          # = 3 * width * mlp
#   注意力：q (H, width, hd)、kv (2, KV, width, hd)、out (H, hd, width)
ATTN = H * width * hd + 2 * KV * width * hd + H * hd * width
每层 = FFN + ATTN          总计 = depth * 每层

# 代入 gemma_300m：width=1024, mlp=4096, depth=18, H=8, KV=1, hd=256

FFN = 3 * 1024 * 4096 = 12,582,912
ATTN = 8*1024*256 + 2*1*1024*256 + 8*256*1024 = 4,718,592
每层 = 17,301,504 x18 = 311,427,072 -> 约 311.4M

# 代入 gemma_2b：width=2048, mlp=16384, 其余相同

FFN = 3 * 2048 * 16384 = 100,663,296
ATTN = 8*2048*256 + 2*1*2048*256 + 8*256*2048 = 9,437,184
每层 = 110,100,480 x18 = 1,981,808,640 -> 约 1.98B

# SigLIP So400m/14：width=1152, depth=27, mlp=4304, heads=16

patch 卷积 = 14 * 14 * 3 * 1152 = 677,376
位置编码 = 256 * 1152 = 294,912
每层 = 4*1152*1152 + 2*1152*4304 = 5,308,416 + 9,916,416 = 15,224,832
27 层 = 411,070,464
输出头 = 1152 * 2048 = 2,359,296
合计 = 414,402,048 -> 约 414.4M

# π0 自己新增的五个线性层（pi05=False 分支；pi05=True 走的是另一组）

state_proj / action_in_proj / action_out_proj 各 32 * 1024 = 98,304
action_time_mlp_in = 2048 * 1024 = 2,097,152
action_time_mlp_out = 1024 * 1024 = 1,048,576
合计 = 3,244,032 -> 约 3.24M

# 以上全部只数权重，不含偏置，也不含 RMSNorm 与 LayerNorm 的缩放参数

动作专家 18 层主要矩阵算得 311,427,072，与 gemma.py 的 # 311M params 注释吻合。这验证了动作专家块的公式和口径；它不能反向证明 SigLIP、词嵌入与全模型的其他估算也必然正确，因此下表仍把各项标为本站核算。

把各块加起来与论文口径对照：

组成 参数量 来源
SigLIP 视觉塔 约 414.4M 本站按 So400m 配置核算，见上
Gemma 词嵌入表 约 526.6M 257152 乘 2048
Gemma 2B 主干 18 层 约 1981.8M 本站核算，见上
动作专家 18 层 约 311.4M 本站核算，与源码注释一致

9.4 一次前向的完整形状追踪

把上面各模块串起来，按默认最大配置追踪一次训练前向的张量形状。这里假设三路相机槽位、语言 padding 到 48、动作 horizon 为 50；这些是张量槽位形状，实际有效 token 数由 mask 决定。批大小记作 \(B\)。

步骤 张量 形状
输入图像（每路） 原图 \(B \times 224 \times 224 \times 3\)
视觉塔输出（每路） 图像 token \(B \times 256 \times 2048\)
三路拼接 图像 token \(B \times 768 \times 2048\)
语言嵌入 语言 token \(B \times 48 \times 2048\)
prefix 拼接 prefix \(B \times 816 \times 2048\)
状态投影 state token \(B \times 1 \times 1024\)
动作投影 动作表示 \(B \times 50 \times 1024\)
时间编码并广播 时间表示 \(B \times 50 \times 1024\)
拼接后过融合 MLP 动作 token \(B \times 50 \times 1024\)
suffix 拼接 suffix \(B \times 51 \times 1024\)
注意力掩码 布尔矩阵 \(B \times 867 \times 867\)
主干输出（suffix 侧） suffix 表示 \(B \times 51 \times 1024\)
取末 50 个并投影 速度场 \(B \times 50 \times 32\)

最后一步需要注意：主干输出的 51 个 suffix token 里，只有末尾 50 个被取出来算速度场，第一个 state token 的输出被丢弃。state token 的作用是作为条件被动作 token 注意到，它自身的输出表示没有监督目标，也不参与损失。

训练式完整前向的最大注意力掩码形状为 \(867 \times 867\)：它在同一逻辑序列上定义 token 间可见性，但不意味着存在一个统一的 \(867\times width\) 隐状态张量。推理时 prefix KV 已缓存，每一步的 query 只有 51 个 suffix 槽位，因此实际使用的完整 mask 是 \(B\times51\times867\)。

把 9.1 的总图、第 3.2 节的单层展开与本表对照，π0 的网络就完整了：总图给模块与连接，单层图解释联合注意力，本表给每一步的张量形状。三者的口径一致，都是默认配置下的同一次前向。若要改配置（例如换 action_dim 或相机路数），按 9.3 的公式重算即可，形状表里受影响的是 32、768、816、867 这几个数。

十、与 π0.5 在架构上的差别

π0.5 在同一份源码里由一个布尔开关控制，架构层面的差别集中在 suffix 侧。这里只列差在哪，机制见 π0.5 页。

项 π0 π0.5
状态的进入方式 连续向量经线性层投成 suffix 里的一个 token 离散化后并入语言 token，属于 prefix
时间步的注入方式 与动作表示拼接后过融合 MLP 经时间 MLP 后作为 adaRMSNorm 的条件注入各层归一化
语言 token 上限 48 200
suffix 的构成 1 个 state token 加 50 个动作 token 仅 50 个动作 token
视觉塔、主干、双专家结构 相同 相同

需要区分“机制延续”和“分块完全相同”。π0.5 仍沿用双专家与受限注意力的思想，但 state 已并入 prefix；当前 openpi 只实现 π0.5 的 Flow Matching 动作头，因此实际是“含 state 的 prefix + 连续动作”两块，而不是 π0 的“图像语言 + state + 动作”三块。π0.5 论文中的完整混合训练还包含 FAST 动作 token，并用额外可见性约束避免连续动作读取真值离散动作。故本页的双专家原理可迁移理解，具体 token 分组与掩码必须回到对应版本核对；这里不对 π0.6 作无来源的概括。
