本页的知识点、创新点与重点

1 个结构主开关 pi05
2 处五个检查点中真正含 pi05 分支
6 个官方 pi05_* 配置（含推理配置）
0 处compute_loss 中的交叉熵项
数据侧状态离散化的实际发生位置
两套PyTorch 实现（openpi 自带与 LeRobot）
200 / 48pi05 / pi0 默认最大 prompt 长度
本页最重要的两个认识。其一，状态离散化不在模型前向里：ModelTransformFactory 配置 TokenizePrompt 是否传入状态，真正的 np.digitize 位于 PaligemmaTokenizer.tokenize()；pi0.py 只接收已组成的 token 序列。其二，compute_loss() 的外层代码没有 pi05 条件分支，公开 π0.5 路径只计算流匹配误差；论文组合目标中的文本交叉熵没有出现在这条实现路径上。

一、本页在专题中的位置

本页负责代码事实：文件在哪、函数怎么走、开关控制了什么、配置取什么值。不负责解释这样设计的原因——那是 ② 与 ③ 的职责。

本页沿用 π0 的部分，不重讲。make_attn_mask、embed_prefix 的函数骨架、流匹配训练与显式 Euler 采样、prefix KV cache 的复用，都由两种配置共用。注意“共用外层函数”不等于内部张量完全相同：embed_suffix() 仍会依据 pi05 改变 token 与时间条件注入方式。

二、读码地图

2.2 一张图：两条调用链与五个检查点

下图把训练与推理两条调用链并排画出，并用 ★ 标出第四节逐个检查的五个位置。只有构造函数与 embed_suffix() 含真正的 pi05 条件分支；其余三处的价值在于确认外层代码没有分支。灰底为数据侧，色框为模型侧。

2.3 建议的阅读路径

先看开关，再看它控制了什么，最后看配置怎么用它。

  1. pi0_config.py 全文（仅一百余行）——把 pi05 开关及其联动的两个默认值看清楚；
  2. pi0.py 的 Pi0.__init__ ——看 pi05 分支创建了哪些层、没创建哪些层；
  3. pi0.py 的 embed_suffix ——看运行时 token 与时间条件如何分流；
  4. transforms.py 的 TokenizePrompt，再跟到 tokenizer.py 的 PaligemmaTokenizer.tokenize ——前者决定是否传状态，后者真正执行分箱；
  5. training/config.py 的 ModelTransformFactory ——ModelType.PI05 走哪条数据变换；
  6. training/config.py 的六个 pi05_* 配置与 optimizer.py ——参数是怎么更新的。

三、Pi0Config 逐字段

字段 默认值 含义与注意点
dtype "bfloat16" JAX 主干与视觉编码器的矩阵计算/嵌入 dtype；PyTorch 训练另有独立精度配置
paligemma_variant "gemma_2b" VLM 专家变体；另有 gemma_2b_lora
action_expert_variant "gemma_300m" 动作专家变体；另有 gemma_300m_lora
action_dim 32 模型内部动作宽度；较低维数据由变换补齐，不能直接当作每个平台的物理自由度数
action_horizon 50 动作块步数；六个 pi05 配置里被改成 10 / 15 / 16 的情况见第六节
max_token_len None → 见下 由 __post_init__ 按 pi05 决定
pi05 False 结构主开关；控制模型类型、suffix 结构与 AdaRMS，状态是否离散输入仍可另改
discrete_state_input None → 见下 由 __post_init__ 默认跟随 pi05；模型本身不读它，只被数据变换工厂读取
pytorch_compile_mode "max-autotune" 仅 PyTorch 路径使用

__post_init__ 里有两处联动，是整份配置最需要记住的地方：

if self.max_token_len is None:
    object.__setattr__(self, "max_token_len", 200 if self.pi05 else 48)
if self.discrete_state_input is None:
    object.__setattr__(self, "discrete_state_input", self.pi05)

两处联动都是「未显式指定时才生效」。因此 discrete_state_input 可以与 pi05 拆开——pi05_libero 就显式设成了 False。这个组合的后果是反直觉的，见第六节 6.2。

另外，源码注释里关于 discrete_state_input 的那句话值得原样记住：这个配置项不被模型直接使用，而是由 ModelTransformFactory 读取。它决定的是数据怎么变换，不是网络怎么搭。

pi05 还决定模型类型枚举：model_type 属性在 pi05 为真时返回 ModelType.PI05，否则返回 ModelType.PI0。这个枚举是数据变换分流的依据。

四、五个函数检查点：两处真分支、三处共享路径

4.1 Pi0.__init__：创建了哪些层

两个分支创建的层不同，这是后续一切差异的根源。

层 pi0 分支 pi05 分支 说明
action_in_proj 有 有 含噪动作块到动作专家宽度的线性投影
action_out_proj 有 有 动作专家输出到速度场的线性投影
state_proj 有 无 连续状态到一个 suffix token 的线性投影
action_time_mlp_in / _out 有 无 动作与时间步拼接后的融合 MLP
time_mlp_in / time_mlp_out 无 有 时间步单独过的 MLP，输出 adaRMS 条件向量

主干的构造也随开关改变：

llm = nnx_bridge.ToNNX(_gemma.Module(configs=[paligemma_config, action_expert_config],
                                     embed_dtype=config.dtype, adarms=config.pi05))
llm.lazy_init(rngs=rngs, method="init",
              use_adarms=[False, True] if config.pi05 else [False, False])

列表两项分别对应 VLM 专家与动作专家。只有动作专家开启自适应归一化。

4.2 embed_prefix：函数内没有 pi05 分支

这一点常被误解。embed_prefix 的代码里没有任何 self.pi05 判断：它照常把各路图像过视觉编码器、把 tokenized_prompt 过词嵌入，然后拼接。

换句话说，embed_prefix() 不区分状态整数与普通文字。π0.5 的状态之所以进入 prefix，是因为数据侧把它拼进 prompt；对模型而言，它只是更长的一串 token。这也解释了为什么 pi05 默认预留 200 个位置，而 pi0 默认是 48；若显式覆写配置，代码并不会强制两者必须取这两个数。

4.3 embed_suffix：运行时 token 与条件注入在这里分流

函数返回四个值：token、输入掩码、自回归掩码、以及 adarms_cond。两个分支的走法：

步骤 pi0 分支 pi05 分支
状态 token state_proj(obs.state) 作为 suffix 第一个 token，ar_mask 追加 True 跳过，suffix 里没有状态 token
动作 token action_in_proj(noisy_actions) 同左
时间步嵌入 posemb_sincos(timestep, ...)（两分支相同） 同左
时间步如何使用 沿特征维与动作 token 拼接，再过 action_time_mlp_in → swish → _out 过 time_mlp_in → swish → time_mlp_out → swish
返回的条件向量 adarms_cond = None adarms_cond = time_emb

两个分支共用的时间步嵌入调用是：

time_emb = posemb_sincos(timestep, self.action_in_proj.out_features,
                         min_period=4e-3, max_period=4.0)

一处容易读漏的连带后果。pi0 的 suffix 是「1 个状态 token + action_horizon 个动作 token」，pi05 则只有动作 token，所以动作 token 的位置与 suffix 掩码长度相差一位。再加上两种配置创建的 MLP 与归一化参数不同，检查点不能只靠改一个布尔值就假定完全兼容。官方几个微调示例加载同架构的 pi05_base 或 pi05_droid；代码没有证明“位置差一位”是其唯一原因。

4.4 compute_loss：外层无 pi05 判断，目标只有流匹配

这是整份源码里最需要如实记录的一点。函数体中没有任何 self.pi05 判断，末尾返回的是：

v_t = self.action_out_proj(suffix_out[:, -self.action_horizon:])
return jnp.mean(jnp.square(v_t - u_t), axis=-1)

其中 u_t = noise - actions，x_t = time_expanded * noise + (1 - time_expanded) * actions，时间采样为：

time = jax.random.beta(time_rng, 1.5, 1, batch_shape) * 0.999 + 0.001

没有交叉熵项，没有 FAST 动作 token，没有文本 logits 上的损失。论文 Eq. (1) 的离散项在这条路径上不存在。这与官方 README 的说明一致：该仓库对 π0.5 的训练与推理目前只支持流匹配头。完整差异清单与成因见 ⑦ 论文与实现的差异及推理期现象。

这里的 mean(..., axis=-1) 只沿动作维求均值，函数返回形状仍是“批次 × 动作时域”；更外层训练代码再聚合它。图中简写成 MSE，不能误读成该函数已经把 batch 与 50 个时间步全部平均成一个标量。

前向调用把条件向量按专家分派：

(prefix_out, suffix_out), _ = self.PaliGemma.llm(
    [prefix_tokens, suffix_tokens], mask=attn_mask, positions=positions,
    adarms_cond=[None, adarms_cond])

第一项恒为 None（VLM 专家不接受调制），第二项在 pi05 下才非空。

4.5 sample_actions：调度骨架共享，suffix 仍按配置分流

默认 num_steps=10，dt = -1.0 / num_steps，从 time = 1.0 出发用显式 Euler 更新。循环条件 time >= -dt/2 用来抵抗浮点误差；默认情况下执行 10 次，从噪声端积分到动作端。prefix 只前向一次以填充 KV cache，之后每一步重算 suffix。sample_actions() 本身不判断 pi05，但它调用的 embed_suffix() 会判断，因此只能说调度与缓存骨架共享，不能说两种配置的完整计算完全相同。

源码注释明确说明：实现采用扩散文献中常见的方向，\(t=1\) 是噪声、\(t=0\) 是目标分布，并指出这与 π0 论文的记号相反。

这条注释直接说明了 openpi 的时间方向与 π0 论文相反，而 π0.5 论文沿用的是与 π0 论文一致的方向（\(\mathbf{a}^{\tau,\omega}=\tau\mathbf{a}+(1-\tau)\omega\)，即 \(\tau=1\) 为真实动作）。两套约定的完整代换关系见 ③ 两阶段训练与组合损失，π0 侧的完整讨论见 π0 · 时间方向约定与推理期现象。

五、状态离散化的数据侧调用链

模型前向里找不到 256 档分箱，因为调用链是：ModelTransformFactory 为 PI05 创建 TokenizePrompt → TokenizePrompt 依据 discrete_state_input 决定是否传入 state → PaligemmaTokenizer.tokenize() 真正执行 np.digitize。数值分箱位于 src/openpi/models/tokenizer.py：

if state is not None:
    # This is the Pi05 format, where the state is part of the discrete language input.
    discretized_state = np.digitize(state, bins=np.linspace(-1, 1, 256 + 1)[:-1]) - 1
    state_str = " ".join(map(str, discretized_state))
    full_prompt = f"Task: {cleaned_text}, State: {state_str};\nAction: "
    tokens = self._tokenizer.encode(full_prompt, add_bos=True)
else:
    # This is the Pi0 format, where the state is part of the continuous action expert input.
    tokens = self._tokenizer.encode(cleaned_text, add_bos=True) + self._tokenizer.encode("\n")

对归一化范围内的状态，代码用步长 \(2/256=1/128\) 的边界把每一维映射到整数 0–255。它没有在 tokenizer 内先裁剪：输入恰在 \([-1,1]\) 时得到合法 256 档；小于 −1 的值可能得到 −1，大于 1 的值饱和到 255。因此这里隐含依赖上游归一化/裁剪，不能把“256 档”误解成对任意实数都自动安全。

是否传入 state，由 training/config.py 的 ModelTransformFactory 和配置项共同决定：

ModelType 数据变换中的分词器 备注
PI0 PaligemmaTokenizer(max_token_len) 不传状态
PI05 PaligemmaTokenizer(max_token_len) + discrete_state_input=... 仍是 PaliGemma 分词器
PI0_FAST TokenizeFASTInputs(FASTTokenizer(...)) 只有这一条路径使用 FAST 分词器
这张表回答了一个高频困惑：论文说 π0.5 用 FAST 分词器，为什么 pi05=True 的训练路径里看到的是 PaliGemma 分词器？因为在当前公开仓库里，FAST 分词器只服务于 PI0_FAST 这个模型类型，π0.5 这条路径不经过它。这不是读错，而是公开实现与论文完整配方的范围差异，详见 ⑦。

超长时的行为也在这个函数里：先记录 warning，再直接截断到 max_token_len，不会主动抛错。这意味着状态串或长指令可能在尾部被静默舍弃；频繁出现 warning 时应增大长度或检查 prompt，而不是假定模型拿到了完整输入。

6.1 逐项差异

配置名 模型参数 batch 训练步数 学习率调度 EMA 权重来源 / 用途
pi05_aloha pi05=True（其余默认，action_horizon=50） 默认 默认 默认 默认 —（推理配置）

pi05_droid_finetune pi05=True、action_dim=32、action_horizon=16 32 20k 默认 默认 pi05_droid

五点值得注意：

  • action_horizon 有四种取值：默认 50、pi05_droid 的 15、pi05_libero 的 10、两个 DROID 微调配置的 16。不存在一个「π0.5 的块长」，它按平台与数据集设定。
  • pi05_aloha 与 pi05_droid 位于源码的 Inference configs 分组；表中的默认 batch、步数、优化器并不表示官方用这些值训练了对应发布权重。
  • pi05_libero 是唯一显式改 EMA 的这六项配置；它和 pi05_full_droid_finetune 都显式创建 CosineDecaySchedule，但二者令 peak_lr 与 decay_lr 同为 5e-5，所以 warmup 后学习率保持不变。“使用名为 CosineDecaySchedule 的类”不等于数值上真的发生余弦下降。
  • pi05_droid_finetune 的权重来自 pi05_droid 而不是 pi05_base，且其数据配置里特意复用 DROID 原始的归一化统计量，源码注释写明「微调时要复用原始 DROID norm stats」。
  • pi05_full_droid_finetune 的 warmup 只有 1k，而 pi05_libero 是 10k。两者的训练步数分别是 100k 与 30k，warmup 占比相差很大。

6.2 pi05_libero 那个反直觉的组合

pi05=True 却把 discrete_state_input 关成 False，结果不是「退回 π0 的状态走法」，而是：

通路 在这个组合下的状态
进 prefix（语言侧） 关闭——TokenizePrompt 不把状态写进 prompt
进 suffix（动作侧） 也不存在——pi05=True 时 Pi0.__init__ 根本没有创建 state_proj

两条模型输入通路同时关闭，因此这个配置的策略前向不以本体状态为条件，只以图像、指令、含噪动作与时间变量生成速度场。代码事实到此为止：仓库没有通过消融证明为什么 LIBERO 可以这样设，也不能由这一例推出真机任务不需要本体状态。迁移配置时，应依据任务是否存在视觉不可辨的关节/末端状态做验证。

八、PyTorch 路径

先澄清一个常见混淆：与 π0.5 相关的 PyTorch 实现有两套，不是一套。

  1. openpi 自带的 src/openpi/models_pytorch/，与 JAX 版共用同一份 Pi0Config 与同一个 pi05 开关；
  2. Hugging Face LeRobot 的 π0.5 实现，是另一套独立的代码库与类名体系。

把两者的文件组织与类名混为一谈是常见错误。本页只讲第一套。

openpi 自带的 PyTorch 实现与 JAX 版在 pi05 分支上的处理是同构的——同样读 config.pi05，同样按 use_adarms=[False, True] if self.pi05 else [False, False] 构造主干，同样在 pi05 下不建 state_proj。

官方 README 列出的已知限制（截至 2026-10-08）：

项目 PyTorch 路径是否支持
π0-FAST 模型 不支持
混合精度训练 不支持
FSDP 全分片数据并行训练 不支持
LoRA 训练 不支持
训练期 EMA 权重 不支持

README 同时说明：PyTorch 实现已在 LIBERO 基准上验证过推理与微调；JAX 检查点可用 examples/convert_jax_model_to_pytorch.py 转换；推理 API 与 JAX 版一致，只需把检查点路径指向转换后的模型。

这里的“混合精度不支持”需要按 README 的术语理解：PyTorch 训练可以选择全 bfloat16（默认）或全 float32，但尚不支持“参数/梯度 float32、部分计算 bfloat16”这种 JAX 默认的混合精度方案；不能误写成 PyTorch 训练只能使用 float32。

九、读码时容易踩的四个坑

现象 真实原因
在 pi0.py 里找不到状态的 256 档离散化 数据变换把状态传给 tokenizer.py，后者执行分箱；模型只收到 token（第五节）
在 compute_loss 里找不到论文的交叉熵项 公开仓库的 π0.5 路径只有流匹配头，不是读错（第 4.4 节，成因见 ⑦）
pi05=True 却看到 PaliGemma 分词器 FAST 分词器只服务 PI0_FAST 模型类型（第五节）
把 action_horizon 当成 π0.5 的固定属性 六个官方配置里有 50 / 15 / 16 / 10 四种取值（第 6.1 节）
