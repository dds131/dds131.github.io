知识库 / 强化学习 / 评估与可复现性
Independent runs · uncertainty · reproducible evidence

训练出一条曲线，不等于证明一种算法

强化学习结果同时受初始化、探索轨迹、环境随机性、实现、调参预算和 checkpoint 选择影响。本页把“跑分”升级为可审计的证据链：先固定问题、预算和选择规则，再用独立 run 与正确的统计层级回答结论是否稳定。

1 个主单位独立训练 run，而非 evaluation episode
3 层隔离训练、选择、最终测试
4 类视角中心、区间、分布、失败
12 项测试防止统计与选择泄漏

最小证据契约：对预先声明的任务、交互预算和主指标，运行若干独立训练重复；使用与训练隔离的评估随机性；按正确层级聚合；同时报告 point estimate、置信区间、原始 run、失败数、environment steps 与 wall-clock；不得用同一批最终测试结果反复调参或挑 checkpoint。

1. 为什么强化学习评估特别难

监督学习常在固定测试集上评估一个已训练模型；RL 的模型会改变数据分布，而每次动作又影响之后能观察到什么。一个最终分数混合了至少六类变化：

  1. 网络初始化与优化器随机性；
  2. 探索动作导致的轨迹分叉；
  3. 环境转移、reset 与观测噪声；
  4. replay 抽样、并行调度和非确定性算子；
  5. 超参数、实现细节与 wrapper；
  6. 训练中选择 checkpoint 的规则。

因此，单 seed 的漂亮曲线只能证明“这次运行发生过”，不能估计算法通常会怎样。

flowchart LR
  SPEC["预注册<br/>任务·预算·指标"] --> RUNS["独立训练 runs"]
  RUNS --> SELECT["仅用 validation<br/>调参与选 checkpoint"]
  SELECT --> TEST["冻结方案<br/>独立 test evaluation"]
  TEST --> EST["聚合估计<br/>CI · IQM · profile"]
  EST --> CLAIM["结论<br/>效果·成本·失败"]
  RUNS -. "配置、日志、版本" .-> AUDIT["可复现清单"]
  TEST -. "原始 episode 数据" .-> AUDIT

前置阅读：强化学习初探、MDP与环境 API、终止截断与时间边界。后续所有算法页的实验结论都应遵守本页协议。

2. 先固定术语与统计对象

名称 本页定义 常见误用
episode 从 reset 到任务终止或采样截断的一条交互序列 把 100 个 episode 当 100 次独立训练
evaluation 冻结参数后执行的一组 episode 边评估边继续更新归一化统计
checkpoint 某个训练步保存的参数及其全部运行状态 只保存网络、不保存 wrapper/normalizer
run 从初始化开始的一次完整训练重复，包含独立随机流 改个整数 seed，但复用完全相同的随机数据
seed bundle 初始化、环境、动作空间、replay、评估等随机流的记录 只调用一次全局 seed()
task 环境 ID、版本、参数、wrapper、目标与预算共同定义的问题 只写“MuJoCo”或“Atari”
trial/config 一组超参数及其训练 runs 把挑中的最好配置当唯一尝试

独立性在 run 层判断。 同一 run 的 100 个 evaluation episode 共享同一套训练参数，能更精确估计这个 checkpoint 的期望表现，却不能代替 100 个独立训练 seed。把 episode 数当 seed 数会产生伪重复（pseudoreplication）和过窄区间。

2.1 层级结构

典型数据层级是：

\[\text{algorithm} \rightarrow \text{task} \rightarrow \text{training run} \rightarrow \text{checkpoint} \rightarrow \text{evaluation episode}.\]
  • episode 在 checkpoint 内嵌套；
  • checkpoint 在同一 run 内相关；
  • run 才承载训练随机性；
  • task 是多任务聚合的分层单位；
  • 环境版本与硬件后端可能构成额外层级。

若问题是“部署这个固定 checkpoint 的回报是多少”，episode 是抽样单位；若问题是“重新训练这个算法通常如何”，run 是主要抽样单位。先写清 estimand，再选择 bootstrap 单位。

3. 随机性不是一个整数

一个可审计 run 至少记录：

  • 参数初始化 seed；
  • 训练环境与每个 vector worker 的 seed；
  • action space / exploration RNG；
  • replay sampler、minibatch shuffle 与 augmentation RNG；
  • evaluator 的独立 seed 集；
  • 数据集版本与顺序；
  • 框架确定性开关、算法与算子后端；
  • 并行 actor 数及调度策略。
seed_bundle = {
    "init": 1101,
    "train_env": [2101, 2102, 2103, 2104],
    "exploration": 3101,
    "replay": 4101,
    "augmentation": 5101,
    "eval_env": [9101, 9102, 9103],
}

相同 seed 不保证跨硬件、驱动和并行调度逐位复现；不同 seed 标签也不自动保证随机流独立，例如两个 run 可能误用同一个 replay 采样器状态。固定离线数据集本身不必然破坏各 run 在初始化/优化随机性上的条件独立，但这些 run 只能估计“给定该数据集”的训练变异，不能覆盖重新采集数据集带来的不确定性；固定 procedural level 集同理。可复现性声明应区分：

  • exact replay：同一平台逐位一致；
  • numerical reproducibility：数值在容差内一致；
  • statistical reproducibility：独立复跑得到兼容的分布与结论。

4. 训练回报不等于独立评估回报

训练日志混有探索、参数更新、非平稳归一化和不断变化的策略。正式评估应：

  1. 冻结模型参数、目标网络和归一化统计；
  2. 使用独立 evaluator 与独立 seed；
  3. 关闭只为收集数据而加入的 exploration noise；
  4. 保留目标部署策略本身定义的随机性；
  5. 固定 episode 数、最大时长和边界语义；
  6. 同时记录 return、length、success、安全与约束指标。

“关闭噪声”不是强制把所有 stochastic policy 改成 argmax。若声称部署的是随机策略，就应按它的分布评估；若部署的是 deterministic mean action，则评估 mean action。评估策略必须与声明对象一致。

训练流

允许探索、更新 running statistics、写 replay；用于优化，不作为最终无偏测试。

validation 流

用于调参、early stopping 与 checkpoint 规则；一旦反复查看，它就不再是 test。

test 流

冻结所有选择后只执行约定次数；用于最终报告，不回流到开发决策。

5. 单任务、多 seed 的最小报告

对 run \(i\) 的 \(E\) 个独立评估 episode，先计算 run-level 均值：

\[\bar R_i=\frac{1}{E}\sum_{e=1}^{E}R_{i,e}.\]

再在 \(N\) 个独立训练 run 上聚合：

\[\bar R=\frac{1}{N}\sum_{i=1}^{N}\bar R_i.\]

最低限度同时给出：

  • 每个 run 的 \(\bar R_i\) 和 episode 数；
  • run 间 mean、median 和置信区间；
  • 原始散点，而不只是一条柱；
  • 成功/失败 run 数及预先定义的失败处理；
  • 最终性能、完整 learning curve、environment steps；
  • wall-clock、硬件与资源消耗。

mean 回答期望结果，median 描述典型位置；两者可能在灾难性失败或重尾分布下差异很大。不能选择更好看的那个而不解释。

5.1 成功率、约束率与稀有事件

若 episode 指标是成功/失败，先在每个 run 内计算

\[\hat p_i=\frac{1}{E_i}\sum_{e=1}^{E_i}\mathbb 1[\mathrm{success}_{i,e}],\]

再按 estimand 聚合 run。直接把所有 episode 池化会让 episode 更多的 run 获得更大权重，并把共享 checkpoint 的 episode 误当成独立训练重复。若问题只是“这个固定 checkpoint 的成功率”，episode-level binomial interval 可以回答；若问题是“重新训练算法后的成功率”，必须保留 run 层，并可用分层 bootstrap 或合适的层级模型同时传播 run 与 episode 变异。

安全违规等稀有事件还要报告事件数、暴露量（episode、小时、米数或动作数）和区间。有限测试中观察到 0 次事件不等于真实风险为 0，不能只给点估计。

6. 置信区间与 bootstrap

置信区间表达估计的不确定性，而不是“真实均值有 95% 概率落在这个已算出的频率学区间里”。在重复抽样解释下，95% 构造程序长期覆盖参数约 95%。

6.1 单任务：在 run 层重采样

def bootstrap_run_mean(run_scores, rng, draws=10000):
    estimates = []
    n = len(run_scores)
    for _ in range(draws):
        sample = rng.choice(run_scores, size=n, replace=True)
        estimates.append(sample.mean())
    return percentile(estimates, [2.5, 97.5])

这段代码对 \(\bar R_i\) 重采样，而不是把所有 episode 打散。若还要传播每个 checkpoint 的 episode 误差，可用分层 bootstrap：先抽 run，再在抽中的 run 内抽 episode。

6.2 多任务：保持 task 分层

多任务得分矩阵常写为：

\[X\in\mathbb R^{A\times T\times N},\]

其中 \(A\) 是算法、\(T\) 是 task、\(N\) 是 run。stratified bootstrap 在每个 task 内重采样 runs，再对任务聚合，避免样本多的 task 无意中获得更大权重。

bootstrap 不能修复设计错误。三个高度相关的“seed”、被挑过的 checkpoint、泄漏的测试集或选择性删除失败 run，即使生成 10000 次 bootstrap 也不会变成可靠证据。run 很少时，区间本身也可能非常不稳定，必须披露原始点。

6.3 配对与非配对比较必须使用不同重采样单位

若算法 A、B 预先以同一 task instance、初始状态集或 common random numbers 形成真实配对，应先构造 run-level 配对差值，并在每个 task 内重采样配对单元；不能把 A、B 两列分别独立抽样后破坏协方差。若没有可辩护的一一对应，则按非配对设计处理。仅使用相同整数 seed 标签不自动形成配对，配对依据和丢失配对的处理规则都要写进 manifest。

7. IQM、performance profile 与 optimality gap

跨许多 task 时，仅看平均归一化分数可能被少数极端 task 支配；仅看 median 又可能对有限样本低效。推荐把多个视角一起报告。

7.1 Interquartile Mean

对某一算法，把它在各 task、各 run 的规范化分数汇总、排序，取中间 50% 求均值：

\[\operatorname{IQM}(X)= \operatorname{mean}\left( X_{25\%\ldots 75\%} \right).\]

IQM 对极端值比 mean 稳健，同时比只取单个中位点利用更多数据。它不是任意“先对每个 task 求 median 再平均”；聚合顺序必须与所用实现、论文协议一致。若各 task 的有效 run 数不同，直接池化会让 run 更多的 task 权重更大；应修复缺失、使用明确的等 task 权重估计器，或把不等权作为 estimand 的一部分公开。

7.2 Performance profile

对“分数越大越好”的规范化分数 \(Z\)：

\[F(\tau)=\Pr(Z>\tau).\]

横轴是阈值 \(\tau\)，纵轴是超过阈值的 run-task 比例。整条曲线能显示低端失败、典型区间和高端尾部，而一个均值不能。

7.3 Optimality gap

给定目标阈值 \(\tau^\star\)，可定义：

\[\operatorname{Gap}_{\tau^\star} = \mathbb E\left[\max(\tau^\star-Z,0)\right].\]

越小越好。\(\tau^\star\)、归一化和是否裁剪都必须声明；否则不同报告里的“optimality gap”不可直接比较。

统计量 主要回答 不能单独回答
mean 随机 run-task 的期望分数 是否被异常高分支配
median 典型中间位置 近半任务失败的严重程度
IQM 中间 50% 的稳健整体水平 最差尾部和具体 task
performance profile 各阈值的超过比例 单个简洁排序
optimality gap 距离目标还有多远 目标阈值是否合理
probability of improvement A 优于 B 的概率型摘要 改进幅度与资源代价

8. 学习曲线、AUC 与 sample efficiency

只报告训练结束时刻会掩盖学习速度、早期崩溃和预算选择。设在环境步 \(x_k\) 的评估分数为 \(y_k\)，梯形积分：

\[\operatorname{AUC} = \sum_{k=0}^{K-1} \frac{y_k+y_{k+1}}{2} (x_{k+1}-x_k).\]

若要比较不同预算，应再明确除以的横轴区间与分数归一化；AUC 的单位和端点必须相同。

8.1 不等长曲线

  • 预先固定公共 evaluation grid；
  • 只在实际覆盖区间内插值，不向训练结束后外推；
  • 因崩溃提前结束的 run 不能静默丢失；
  • 画均值/中位数线时，同时给 run-level 区间；
  • 平滑只用于显示，统计量从未平滑原始值计算。

8.2 横轴不止一种

横轴 优点 必须补充
environment transitions 最接近样本效率 action repeat、并行 env 与 reset 计数
agent decisions 适合控制策略调用成本 每个决策跨多少 simulator steps
raw frames Atari 等像素基准常用 frame skip / action repeat
gradient updates 显示优化强度 update-to-data ratio
wall-clock 体现真实吞吐 硬件、并行度、评估时间
energy/cost 体现资源代价 计量范围与基础设施

不同 frame skip 下“100 万 environment steps”可能代表不同数量的原始帧和物理时间；不同控制频率下“1000 episodes”也不是相同交互量。至少同时报告 transitions、agent decisions、模拟/真实时间与 wall-clock。

9. 多任务归一化必须可逆、可审计

常见线性归一化：

\[z_{a,t,r} = \frac{x_{a,t,r}-L_t}{U_t-L_t},\]

其中 \(L_t\) 是低参考，\(U_t\) 是高参考。必须公开：

  • 每个 task 的 \(L_t,U_t\) 数值和来源；
  • 高分是否更好；
  • 是否 clip 到 \([0,1]\)；
  • 参考分数是否来自同一环境版本；
  • \(U_t=L_t\) 时如何处理。

禁止静默修补分母为零。 若 \(U_t=L_t\)，该 task 的归一化未定义；应修正参考、改用有意义的尺度，或把 task 标记为不可聚合并报告。用极小 epsilon 偷换分母会制造任意巨大分数。

原始分数必须与归一化分数一起提供。归一化方便聚合，但会继承参考策略的误差、版本漂移与尺度选择。

10. 超参数选择是一部分实验预算

比较算法 A、B 时，不能给 A 100 个配置、每个 5 seeds，却只给 B 一个默认配置、1 seed。公开以下预算：

  • 搜索空间及先验/采样分布；
  • 搜索算法；
  • 每个配置的训练预算；
  • 筛选阶段与确认阶段的 seeds；
  • 总 environment interactions、GPU/CPU hours；
  • 选择指标和 tie-breaking；
  • 被尝试的全部配置及失败数。
flowchart LR
  DEV["开发任务与少量 seeds"] --> SEARCH["公平搜索预算"]
  SEARCH --> RULE["冻结超参数<br/>冻结 checkpoint 规则"]
  RULE --> CONFIRM["新训练 seeds"]
  CONFIRM --> TEST["held-out test episodes / tasks"]

“论文 baseline 的默认参数”不一定对当前代码、环境版本和预算公平；但无限制地为新方法调参、不给 baseline 同等机会，同样不公平。应预先选择并披露资源对称规则。

11. Checkpoint 选择与 winner’s curse

若每隔 10k steps 评估一次，然后从 100 个 checkpoint 中挑最高分，并把同一批 episode 的最高分当最终结果，就把评估噪声也优化进去了。

可靠规则可选：

  1. 固定最后 checkpoint：最简单，但需定义训练失败；
  2. 预注册步数 checkpoint：按先验预算选定；
  3. validation 选择，test 重评：用 validation seeds 选择后，在新 episode/seeds 上评估；
  4. 窗口平均：预先声明末尾若干 checkpoint 的 run-level 平均；
  5. 独立选择器：用开发任务选全局规则，再冻结到测试任务。

checkpoint 不是独立训练样本。把同一 run 的 100 个 checkpoint 当 \(N=100\)，会同时违反独立性并引入 best-of-many 偏差。最终 test 不能参与 early stopping。

12. 环境、wrapper 与 benchmark 版本

实验配置必须足以重建真正的 MDP/POMDP 与观测处理：

  • environment ID、包版本、ROM/资产 hash；
  • game mode、difficulty、sticky action；
  • observation resize、frame stack、reward clipping；
  • action repeat、frame skip、控制频率；
  • reset 分布、初始状态、最大时长；
  • terminated / truncated 处理；
  • action scaling、mask、安全过滤器；
  • simulator precision、solver 与随机扰动。

Atari 的 deterministic 与 sticky-action 协议、不同 no-op reset、life-loss 处理和 frame skip 会改变结果；不能只写算法名和游戏名。机器人环境还要记录控制周期、仿真步长、延迟和安全 reset。

环境边界的统一语义见环境 API、终止截断与时间边界。

13. 资源、公平性与 wall-clock

同样的 environment steps 不等于同样的计算：

  • model-based 方法可能每步做大量规划；
  • off-policy 方法的 update-to-data ratio 不同；
  • 大规模并行可缩短 wall-clock，却增加总资源；
  • evaluation、数据预处理与仿真初始化也消耗时间；
  • 真实机器人需要计入 reset、人工干预和停机时间。

建议最少报告：

类别 字段
交互 transitions、episodes、agent decisions、action repeat
优化 gradient updates、batch size、UTD ratio
计算 CPU/GPU/accelerator 型号与数量、显存、精度
时间 训练、评估、仿真/reset、总 wall-clock
资源 峰值内存、可选能耗/云成本
并行 env 数、actor/learner 数、同步方式

样本效率、计算效率和时间效率是三个问题。某算法可用更少数据却花更多 GPU 时间；结论应按应用约束分别陈述。

14. 失败 run、缺失数据与异常值

失败不是天然的“工程噪声”。NaN、显存溢出、策略崩溃、环境卡死和安全终止都可能是方法稳定性的一部分。

在实验前定义：

  • 什么算算法失败、基础设施失败和无效任务；
  • 是否允许重跑，最多几次；
  • 重跑是否使用同一 seed；
  • 失败 run 在主指标中的分数/删失规则；
  • 缺失 checkpoint 的曲线如何处理；
  • 异常值规则是否与算法标签无关。

推荐同时提供：

  1. intention-to-evaluate 主分析：包含所有已启动且符合协议的 run；
  2. valid-only 敏感性分析：只含成功 run，但明确分母；
  3. failure rate、失败类型和时间点；
  4. 原始数据与剔除理由。

错误做法 运行 10 个 seeds，删除 3 个崩溃 run，然后写“7 seeds 的均值”，却不说明原计划和失败比例。这会系统性高估稳定性。

15. 显著性、实际重要性与多重比较

小 p-value 不说明收益大，也不说明部署值得。结论应同时给出：

  • effect size 与原始单位差异；
  • uncertainty interval；
  • 预先定义的最小实际重要差异；
  • probability of improvement 或配对差值；
  • 样本、计算、延迟与安全代价。

只有在任务、初始化或环境随机流有明确一一对应且配对在协议中预先声明时，才使用 paired analysis。仅仅把两个算法都叫“seed 0”不构成配对。

若对许多 task、指标、checkpoint 和算法对反复检验，偶然显著概率上升。应声明主比较，区分探索性分析，并在需要时采用多重比较控制或层级模型。

16. 曲线与图表的诚实呈现

  • 轴从哪里开始要有理由，不截断轴夸大差异；
  • 颜色、线型和图例在所有图中一致；
  • 置信带注明统计单位和构造方法；
  • 原始 run 用淡线或散点保留；
  • smoothing window、插值规则、evaluation interval 写在图注；
  • 对数轴、归一化、裁剪和缺失值必须显式；
  • 表格不能只加粗赢家而省略不确定性。

每个时间点各做一次 pointwise 95% CI，不等于整条曲线以 95% 概率被带包住。若声称“整个训练过程都更好”，需要 simultaneous band、预注册的曲线摘要（如 AUC），或明确限制结论。

下面的伪代码只检查协议结构，不替代人工审查：

REQUIRED = {
    "algorithm.code_commit",
    "environment.id",
    "environment.package_version",
    "environment.wrapper_stack",
    "randomness.train_seed_bundles",
    "randomness.eval_seeds",
    "budget.train_environment_transitions",
    "evaluation.episodes_per_checkpoint",
    "evaluation.checkpoint_rule",
    "evaluation.primary_metric",
    "evaluation.confidence_interval",
    "resources.hardware",
    "missing_data.rerun_rule",
}

def audit_manifest(cfg):
    errors = []
    for key in REQUIRED:
        if lookup(cfg, key) in (None, "", []):
            errors.append(f"missing: {key}")

    if overlaps(train_seeds(cfg), eval_seeds(cfg)):
        errors.append("train/eval seed overlap")
    if cfg["evaluation"]["checkpoint_rule"] == "best_on_test":
        errors.append("checkpoint leakage")
    if normalization_denominator_is_zero(cfg):
        errors.append("undefined normalization")
    if not cfg["missing_data"]["report_failed_runs"]:
        errors.append("failed runs hidden")
    return errors

结果表的 schema 也应验证：

20. 发布前报告模板

20.1 问题与协议

  • task、环境版本、wrapper、终止/截断；
  • train/validation/test 隔离；
  • 主指标、次指标、预算和 checkpoint 规则；
  • 超参数搜索空间与总预算；
  • 独立训练 runs 数和 seed bundle。

20.2 结果

  • 每 task、每 run 原始结果；
  • mean、median、IQM 与 95% CI；
  • performance profile / optimality gap；
  • learning curve、AUC 与最终值；
  • environment transitions、wall-clock、硬件；
  • failure count 与敏感性分析。

20.3 复现资产

  • code commit、diff hash、依赖锁文件；
  • 全部配置、seed、命令与日志；
  • 原始 episode 级数据和 schema；
  • 聚合与绘图脚本；
  • 环境资产、数据集和 benchmark 版本。

一句结论应该能还原为一条查询。 例如：“在 10 个独立训练 runs、冻结 final checkpoint、每 run 50 个 held-out evaluation episodes 下，算法 A 在 12 个 task 的 IQM 为……，95% stratified bootstrap CI 为……，失败 1/10，总交互……，总 wall-clock……”。缺少其中关键限定时，结论往往比证据更强。

21. 常见错误与定位

现象 常见根因 优先检查
区间异常窄 把 episode 当独立 training run bootstrap 单位与层级
复跑排名改变 seeds 少、重尾、调参过拟合 原始 run、IQM、CI、搜索预算
测试分数远高于部署 best-checkpoint/test leakage selection/test 是否隔离
曲线末端只剩好 run 崩溃 run 被丢弃 不等长曲线与 status 字段
algorithm A 的 step 更少但更慢 计算量或并行度不同 wall-clock、UTD、硬件
多任务均值被一项支配 归一化或重尾异常 原始分数、profile、IQM
同 seed 配对后显著 seed 标签并非共同随机数 是否存在真实一一对应
结果无法复现 环境/wrapper/资产漂移 manifest、lockfile、hash
评估分数抖动很大 episode 少或 evaluator 仍更新 eval 冻结与 episode CI
报告只有成功 runs 选择性缺失 planned N、failure rule

调试顺序：先核对统计对象与数据 schema → 核对 train/validation/test 隔离 → 核对环境步与时间口径 → 重算原始 run-level 指标 → 再检查 bootstrap、IQM 与图表。

22. 与其他页面的职责边界

  • 本页：统一 run、评估隔离、统计聚合、不确定性、选择与复现协议；
  • 环境边界页：统一 seed、终止、截断、auto-reset 和时间口径；
  • 各算法页：保留算法特定损失、诊断量与 ablation；
  • 离线强化学习：补 dataset split、行为策略与 OPE 特有问题；
  • 多智能体页面：补跨 agent、对手池与共同随机数；
  • 机器人/人类介入页面：补 intervention、真实时间、安全事件与人力成本；
  • VLA/概率契约页面：补 token、log-prob 与动作变换的一致性指标。

本页定义的是证据协议，不是“选择一个统计库就完成评估”。任何工具输出都必须回到实验问题、抽样单位和数据生成过程解释。

23. 练习

  1. 构造 3 个 training runs、每个 100 个 evaluation episodes，比较错误 episode-level bootstrap 与正确 run-level bootstrap 的区间宽度。
  2. 对含一个灾难失败的 8 个分数手算 mean、median 与 IQM，解释三者各自隐藏什么。
  3. 模拟从 50 个 noisy checkpoints 中选最大值，再用新 episodes 重评，观察 winner’s curse。
  4. 让两个算法具有相同 environment steps、不同 UTD ratio，比较 sample efficiency 与 wall-clock efficiency。
  5. 给一张含缺失 run 和不同 frame skip 的结果表写 manifest audit rules。
  6. 用相同 task 数据画 mean 柱状图和 performance profile，比较能否看见低端失败。

  5. Sutton & Barto, Reinforcement Learning: An Introduction, 2nd ed.——return、策略评估、抽样与 RL 基础定义。

论文中的“推荐”不是脱离任务的硬性定律：任务数量、run 数、配对结构和风险目标不同，估计器也可能不同。不可省略的底线是：声明 estimand、保持数据隔离、在正确层级量化不确定性、公开选择与失败，并让结论可由原始数据重算。
