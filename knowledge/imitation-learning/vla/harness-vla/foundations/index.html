知识库 · 机器人模仿学习与 VLA · VLA · Harness VLA · 基础概念与方法边界
  • 本页身份：编排系统基础，不是模型架构、训练配方或机器人部署说明。
  • 中心问题：Planner、Harness runtime、Registry、Executor、Frozen VLA、Environment、Memory、Verifier 与 Safety 各自拥有什么状态和权限？
  • 安全边界：GoalVerdict 与 SafetyDecision 是两条独立 authority；任务成功不能解除 actuator inhibit。
  • 当前范围：只读教学模板；不运行模型、服务、评测、仿真或机器人，不提供真机默认参数。

Harness 不是模型的一层，而是使模型输出能够被约束、执行、观察、验证和停止的系统边界。开始判责前必须先区分 Agent Harness、Robotic Harness 与 Learning/Training Harness。

三种 Harness：先确定讨论对象

三义矩阵

术语 包围对象 主要职责 必然训练参数吗 典型失败
Agent Harness Planner / LLM / VLM tool schema、context、Memory、权限、turn loop、trace、retry 否 tool 错选、上下文污染、权限越界
Robotic Harness policy 与 physical system observation adapter、primitive dispatch、controller、feedback、verdict 否 frame/单位错、超时、执行错误、反馈错位
Learning / Training Harness 可训练组件 data、batch、Loss、backward、optimizer、checkpoint、evaluation 通常是 梯度、数据、checkpoint 或配方错误

Harness VLA 使用前两类责任。底层 checkpoint 的训练属于第三类，但它不在 Harness deployment loop 的同一条梯度图中。遇到“Harness 学到了什么”，依次问：改变的是 model_parameters、runtime_state、planner_context 还是 persistent_memory；更新是否由 Loss/backward/optimizer 产生；变化是否跨 run 持久化且有 revision；evaluation 是否允许该变化。

只有梯度路径实际更新该组件参数，才能称为该组件的梯度训练。Memory 提交、缓存刷新、prompt 变化、预算递减和动作队列变化都不是 Loss。页面主张使用四类标签：原论文事实、官方实现事实、本站解释、工程建议。

九个系统对象与责任边界

九对象教学抽象

本站用 H = (Π, Ω, P, X, F, E, M, V, S) 进行跨论文与实现判责：Π Planner，Ω Harness runtime/orchestrator，P Primitive Registry，X Executor/Toolkit/dispatcher，F Frozen VLA backend，E Environment/controller interface，M Memory provider，V Goal/post-condition verifier，S Independent safety authority。这不是论文原式，也不是 RPent 类图。

flowchart TD
  T["task + ObservationEnvelope"] --> PI["Π Planner"]
  M["M Memory provider"] -->|scoped view + receipt| PI
  PI --> O["Ω Harness runtime"]
  P["P Primitive Registry"] -->|versioned schema| O
  O --> X["X Executor / Toolkit"]
  X --> F["F Frozen VLA backend"]
  X --> E["E Environment / controller"]
  F --> E
  E --> V["V Post-condition / Goal verifier"]
  S["S Independent safety authority"] -->|permit / inhibit / safe state| X
  V -->|verdict evidence| O
  O -->|trace + next turn| PI

图 1｜九对象责任图。 等价文本：任务与观测进入 Planner；Memory 只返回有 receipt 的 scoped view；Registry 给 Harness 版本化 schema；Harness 经 Executor 调用 analytic primitive 或 Frozen VLA；Environment/controller 返回物理反馈；Verifier 判断后置条件/目标；Safety 独立许可、拒绝或进入 safe state。

对象 主要输入 → 输出 可变状态 不拥有的权限
Π Planner task、observation、memory view、schema → PrimitiveCall / planning status context / history 不直接写 actuator，不拥有 safety permit
Ω Harness runtime config、call、budget、service state → validated dispatch、trace、lifecycle run state / budget / turn index 不伪造 goal truth，不越过 Safety
P Registry definitions、version → schema、capability metadata versioned registry 不执行动作，不接受未注册类型
X Executor validated call → PrimitiveResult、execution trace in-flight execution 不决定任务语义成功
F Frozen VLA local observation、prompt、policy contract → action chunk inference cache；参数冻结 不拥有全局任务分解或 actuator gate
E Environment/controller permitted command → observation、controller feedback、native state physical/sim state 不根据 Planner 文本自报成功
M Memory scoped query、phase、identity → memory view + receipt exploration 可提交；evaluation 只读 不绕过 scope、revision、provenance
V Verifier task spec、state/evidence → GoalVerdict / PostConditionVerdict verifier state 不替代 safety authority
S Safety state、limits、fault、command → permit/inhibit/safe state safety state 不由 Planner、Memory、benchmark override

审计顺序

sequenceDiagram
  participant O as Observation / Memory
  participant P as Planner
  participant H as Harness / Registry

图 3｜Typed turn。 SafetyDecision 与 GoalVerdict 位于独立泳道：前者决定命令能否进入执行链，后者判断指定任务谓词是否成立。Planner finish、tool ok 或 primitive completed 都不能替代任一 authority。

ObservationEnvelope 至少含 observation_id、captured_at_monotonic、sensor/frame/calibration versions、RGB/depth/proprioception availability、task/episode/turn ID 与 freshness。PrimitiveCall 至少含 call/registry/primitive ID、kind、arguments、units/frames、preconditions、budget、requested postconditions、planner identity 与 memory receipt IDs。

PrimitiveResult 至少记录 accepted/rejected/started/completed/timed_out/aborted/faulted、executor/controller identity、起止时间、observed effects、trace IDs 与 fault code。GoalVerdict 记录 predicate version、true | false | unknown、evidence、verifier owner 与时间；SafetyDecision 记录 permit/inhibit/safe_state、policy version、reason、owner 与 re-arm requirement。

事件 只证明什么 不证明什么
schema validation passed 参数类型和字段满足 registry 动作可达、正确或安全
tool returned ok 工具协议没有报告错误 primitive 后置条件成立
primitive completed executor 到达其终止状态 task goal 成立
Planner finish Planner 不再请求 tool verifier 接受或环境成功
GoalVerdict true 指定谓词在给定证据上成立 物理执行满足全部安全要求

与邻近方法的边界

对象 主要改变 参数可能更新 运行时核心 与 Harness VLA 的关系
层级策略 高/低层 policy 决策结构 可以 option / skill selection 可充当 Planner 或 primitive policy，但不自动提供权限、Memory、审计与 verifier
Behavior Tree / task planning 显式任务结构与控制流 通常否 tree / search / execution monitor 可作编排后端；Harness 还规定 tool、Memory、反馈与模型接口
Task-and-Motion Planning 离散任务与连续运动联合求解 通常否 feasibility / search 可生成 analytic 部分；不等于 VLA-backed primitive runtime
VLA 后训练 policy parameters / distribution 是 SFT / Flow / RL / preference objective 可先训练再接入 Harness
RTC action chunk 时间协调 依分支 async queue / chunk conditioning 可位于 vla_act 内部或执行边界
RLT online RL policy / critic update 是 reward、critic、replay、deployment 与 non-gradient Memory 编排不同
RLHF-VLA human preference / feedback alignment 是或直接偏好更新 preference、reward、policy optimization 可改策略；不等于 planner trace Memory
Training Harness 优化流水线 是 data、Loss、optimizer、checkpoint 训练组件，不负责 deployment orchestration

判断标准不是“有没有高层和低层”，而是系统是否显式定义 tool contract、Memory scope、turn feedback、verdict、权限、trace 与安全交接。若问题只发生在动作块边界和推理延迟，优先评估RTC；若目标是更新策略参数，比较RLT或RLHF-VLA。

能力上限、必要条件与停止规则

必要条件不是成功保证

对必须调用 vla_act 的任务，令 G 为正确 grounding，R 为 Registry 可表达任务，A 为 analytic/staging 可达，L 为冻结 VLA 具备局部接触技能，V 为目标可验证，B 为预算足够，Q 为 Safety 允许，Y 为任务成功。本站解释性必要条件为：

Y ⇒ G ∧ R ∧ A ∧ L ∧ V ∧ B ∧ Q

这不是论文定理，也不表示右侧同时成立就必然成功，更不能把边际概率直接相乘。Harness 不能绕过缺失技能、不可达状态、不可验证目标、预算或安全限制。

flowchart LR
  G["G grounding"] --> Y["Y candidate success"]
  R["R registry expressible"] --> Y
  A["A staging reachable"] --> Y
  L["L local skill exists"] --> Y
  V["V verdict observable"] --> Y
  B["B budget available"] --> Y
  Q["Q safety permits"] --> Y
  Y -. "necessary, not sufficient" .-> N["verified task success"]

图 5｜能力必要条件。 七项都是候选成功的必要门，但不是充分条件；任一缺失都应转入诊断、修复、训练或停止，不得用无限重试掩盖。

任一条件成立就停止自动重试并进入 safe action / escalation：相同 failure signature 达到上限；observation 过期或 calibration/version 不匹配；staging 不能满足 precondition；局部技能受控重试后无进展；verifier 为 unknown 且证据无法补齐；safety inhibit、硬件 fault、碰撞/力/速度限制触发；budget 耗尽；Memory/Registry/policy contract hash 漂移；失败不可逆或下一次更危险；owner 未定义或审计链缺失。

禁止把 unknown 当 success、改变目标定义、放宽安全阈值或无限重试。若底层局部技能不存在，应补数据或训练；若 controller/hardware fault 存在，应由相应 owner 修复，而不是继续 Planner 调参。

候选条件

  • 局部 VLA 接触技能已可靠；主要失败来自重绑定、空间变化、组合、staging 或局部恢复。
  • 小型固定 Registry 可表达任务，每个 primitive 有可观察后置条件。
  • Memory 可版本化、隔离、验证和冻结；Planner latency 与任务尺度兼容。

  • controller 与 Safety owner 独立，失败和重试不累积不可接受风险。

    </div>

反例与禁用条件

  • 稳定分布内任务由直接 VLA 已可靠完成，或固定流程用状态机/behavior tree 更透明。
  • 唯一问题是 action chunk 时序、局部技能缺失或需要策略参数更新。
  • task predicate 不可验证，只能依赖自然语言自报成功。
  • schema/frame/unit/controller/calibration 未冻结，权限不可限制，Memory 无来源或跨评测污染。

  • strict hard real-time、不可逆失败、危险重试或独立安全层缺失。
