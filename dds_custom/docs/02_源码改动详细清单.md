
| 问题                 | 回答                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **这行代码的作用**   | 定义站点的绝对根地址。Jekyll 在构建时用它拼出所有需要绝对 URL 的地方                                                                                           |
| **具体影响哪些产物** | `sitemap.xml` 里每个 `<loc>`；`feed.xml`（RSS）里每篇文章的链接；每个页面 `<head>` 里的 `<link rel="canonical">`；Open Graph 的 `og:url`（社交平台分享预览用） |

| **为什么是这个值**   | GitHub 用户主页站的域名由 GitHub 固定分配，格式是 `https://<用户名>.github.io`。用户名是 `dds131`，所以是 `https://dds131.github.io`                           |
| **怎么做的**         | `02_patch_config.sh` 用 `sed -i -E` 做行首锚定的精确替换，替换前先 `grep` 确认当前值确实是上游默认值，不符合就报错中止                                         |
| **做得怎么样**       | ✅ 成功。`diff -u` 确认只改了这一行的这一处，行尾注释原样保留                                                                                                  |

### 1.2 改动 ②：`baseurl`

**位置**：第 22 行

```diff
- baseurl: /al-folio # the subpath of your site, e.g. /blog/. Leave blank for root
+ baseurl: # the subpath of your site, e.g. /blog/. Leave blank for root
```

| 问题                       | 回答                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **这行代码的作用**         | 定义站点在域名下的**子路径前缀**。al-folio 的模板里所有资源引用都写成 `{{ site.baseurl }}/assets/...`，构建时 `{{ site.baseurl }}` 被替换成这里的值                            |
| **两种站点形态的取值**     | 用户主页站（仓库名 == `<用户名>.github.io`）：路径是 `/`，**必须留空**；项目站（仓库名任意）：路径是 `/<仓库名>/`，**必须填 `/<仓库名>`**                                      |
| **为什么本项目要留空**     | 仓库名 `dds131.github.io` 精确等于 `<用户名>.github.io`，GitHub 判定为用户主页站，站点根路径就是 `/`                                                                           |
| **不改的后果（严重）**     | 所有资源 URL 会变成 `/al-folio/assets/css/main.css`，而文件实际在 `/assets/css/main.css` → **全站 CSS、JS、图片、字体 100% 404**。页面能打开，但完全没有样式，是一堆黑色纯文字 |
| **为什么保留空行而不删除** | al-folio 官方 `docs/INSTALL.md` 明确写明「leave `baseurl` empty (do NOT delete it)」。Jekyll 中「键不存在」与「键存在但值为空」的行为不同，删掉会出问题                        |
| **怎么做的**               | `sed` 的匹配模式 `'^baseurl: /al-folio '` 末尾特意带一个空格，只删掉值 `/al-folio`，把后面的注释文字完整保留下来。保留注释是有意为之 —— 日后看到这行能立刻明白它为什么是空的   |
| **做得怎么样**             | ✅ 成功且已实测验证。部署后抓取首页提取全部资源链接，**19 个资源全部返回 200，零 404**                                                                                         |
| **风险等级**               | **改错风险最高的一处**（配错就是全站崩），但已通过实测验证正确                                                                                                                 |

### 1.3 改动 ③：`exclude` 新增 `dds_custom/`

**位置**：第 228 行（插入到 `  - docs/` 之前）

```diff
    - docker-compose-slim.yml
+   - dds_custom/
    - docs/
```

| 问题                        | 回答                                                                                                                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **这个配置的作用**          | `exclude` 是一个路径列表，列出 Jekyll 构建时要**完全忽略**的文件和目录                                                                                                                                                                                             |
| **为什么要加**              | `dds_custom/` 是本项目新增的自定义目录，里面是 shell 脚本和中文 Markdown 文档，属于「项目工程资料」，不是「网站内容」                                                                                                                                              |
| **不加的后果**              | ① `dds_custom/docs/*.md` 会被 Jekyll 当成网页渲染，出现在最终站点里（比如 `https://dds131.github.io/dds_custom/docs/01_技术路线与实现方案/`）；② 更严重的是，文档里写了大量 Liquid 语法示例（`{{ }}`、`{% %}`），Jekyll 会尝试解析它们，很可能直接导致**构建失败** |
| **为什么插在 `docs/` 之前** | 该列表原本是按字母序排列的。`dds` 与 `docs` 比较：`d`=`d`，第二个字符 `d` < `o`，所以 `dds_custom/` 应排在 `docs/` 前面。保持有序便于日后查找和维护                                                                                                                |
| **怎么做的**                | `sed '0,/^  - docs\/$/s\|...\|...\|'`。地址范围 `0,/pattern/` 限定只替换**第一次**出现，防止文件别处若也有 `  - docs/` 被误改；替换内容里用 `\n` 插入换行实现「在某行之前插入一行」                                                                                |
| **事后校验**                | `sed` 即使没匹配到任何内容也返回 0（成功），所以脚本里必须再 `grep` 一次确认真的插进去了，否则会静默失败                                                                                                                                                           |
| **做得怎么样**              | ✅ 成功。构建产物 `gh-pages` 分支中确认没有 `dds_custom/` 目录                                                                                                                                                                                                     |
| **风险等级**                | 极低。只影响构建时的文件筛选                                                                                                                                                                                                                                       |

**验证命令**：

```bash

  'grep -n "dds_custom/" /workspace/project_files/dds_web_projection_1/al-folio/_config.yml'
```

### 1.4 改动 ④：`include` 新增 `.nojekyll`

**位置**：第 219 行

```diff
- include: ["_pages"]
+ include: ["_pages", ".nojekyll"]
```

| 问题                                 | 回答                                                                                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **这个配置的作用**                   | `include` 与 `exclude` 相反，它强制 Jekyll **处理那些默认会被忽略的文件**                                                                                                                         |
| **Jekyll 默认忽略什么**              | GitHub 官方文档明确写明：「By default, Jekyll doesn't build files or folders that... Start with `_`, `.`, or `#`」。即以下划线、点号、井号开头的文件和目录默认被跳过                              |
| **为什么这一行是必需的，不是可选的** | 新增的 `.nojekyll` 以点号开头，属于默认被忽略的范畴。如果只创建文件而不加进 `include`，Jekyll 构建时会直接跳过它，它就**不会被复制进 `_site/`**，也就传不到 `gh-pages` 分支 —— 等于白加了一个文件 |
| **原有的 `_pages` 为什么在里面**     | 同理，`_pages/` 以下划线开头，上游把它加进 `include` 才能让 Jekyll 处理其中的页面。这也说明本次改动是**沿用上游既有的机制**，不是引入新花样                                                       |
| **怎么做的**                         | 因为 `include` 的值里含有 `[`、`]`、`"` 等正则元字符，脚本先用一个内嵌 `sed` 把它们全部转义，再交给外层 `sed` 做整行替换。`grep` 判断时用 `-F`（固定字符串模式）而非正则                          |
| **做得怎么样**                       | ✅ 成功。部署后 `https://dds131.github.io/.nojekyll` 返回 200，证明它确实被复制进了产物并发布出去                                                                                                 |
| **风险等级**                         | 极低。只是多复制一个 0 字节文件到构建产物                                                                                                                                                         |

**验证命令**：


## 二、新增文件：根目录 `.nojekyll`

| 项                               | 内容                                                                                                                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **路径**                         | `<仓库根>/.nojekyll`                                                                                                                                                                                              |
| **内容**                         | 空文件（0 字节）。它的作用完全由「这个文件存在」这一事实决定，内容无关紧要                                                                                                                                        |
| **目的**                         | 让 GitHub Pages **原样发布** GitHub Actions 已经构建好的产物，不要再跑一遍自带的 Jekyll                                                                                                                           |
| **官方依据**                     | GitHub 官方《Configuring a publishing source》：外部 CI 通常「把构建产物提交到 `gh-pages` 分支」并且「包含一个 `.nojekyll` 文件」，此时 GitHub「会检测到该分支不需要构建步骤」，直接进入部署                      |
| **解决的实际问题（有实测证据）** | Pages 的 `build_type` 是 `legacy`，会对已构建好的产物再跑一遍内置 Jekyll。Jekyll 丢弃下划线开头的目录，而 al-folio 的产物根目录有 `_pages/`。**实测 `/_pages/dropdown/` 返回 404；加上 `.nojekyll` 后恢复为 200** |
| **附带收益**                     | 官方文档写明「使用 `GITHUB_TOKEN` 的 workflow 产生的提交不会触发 Pages 构建」。`deploy.yml` 正是用 `GITHUB_TOKEN` 推 `gh-pages` 的，所以补齐前每次都要手动调 API 触发 Pages 构建。补齐后实测能自动触发并完成部署  |
| **与上游设计的关系**             | al-folio 的 `_config.yml` 第 243-245 行本就有 `keep_files: [CNAME, .nojekyll]`，说明上游**预期该文件存在**并主动保护它，只是从未真正创建过。本次是**补齐上游缺口**，不是违背上游设计                              |
| **为什么不能放进 `dds_custom/`** | 该文件必须位于**发布站点的根目录**才有效，这是 GitHub 的硬性规则，无法通过目录组织规避。这是本项目唯一一个放在 `dds_custom/` 之外的新增文件                                                                       |
| **创建时间**                     | 2026-07-30 13:54:32 UTC                                                                                                                                                                                           |
| **执行工具**                     | `dds_custom/scripts/03_add_nojekyll.sh`                                                                                                                                                                           |
| **做得怎么样**                   | ✅ `/_pages/dropdown/` 从 404 变为 200；`/.nojekyll` 返回 200；全站 20 项回归测试 0 失败                                                                                                                          |

## 三、新增目录 `dds_custom/` 及其全部文件

**设计原则**：所有新增内容集中在这一个目录下，与 al-folio 上游代码完全隔离，

**为什么它不会影响网站**：已加入 `_config.yml` 的 `exclude` 列表（见改动 ③），Jekyll 构建时完全忽略。

```
dds_custom/
├── README.md                          # 目录总览与快速开始
├── _config.yml.original.bak           # 修改前的原始 _config.yml（自动生成）
├── docs/                              # 5 份说明文档
│   ├── 01_技术路线与实现方案.md
│   ├── 02_源码改动详细清单.md          # 本文件
│   ├── 03_部署操作手册.md
│   ├── 04_GitHub官方要求对照.md
│   └── 05_问题与排查记录.md
└── scripts/                           # 4 个可执行脚本
    ├── 00_env_proxy.sh
    ├── 01_backup.sh
    ├── 02_patch_config.sh
    └── 03_add_nojekyll.sh
```

**脚本共同的设计约定**（4 个脚本全部遵守）：

| 约定                | 说明                                                                     |
| ------------------- | ------------------------------------------------------------------------ |
| `set -euo pipefail` | 出错立即停止 / 引用未定义变量报错 / 管道任一环节失败即失败。防止半截状态 |
| **幂等**            | 可重复执行，已完成的部分自动跳过，不会重复施加改动                       |
| **路径硬编码**      | 不接受外部传入路径，避免误操作到别的目录                                 |
| **执行前校验**      | 修改前先确认当前内容符合预期，不符合就报错中止，绝不在未知状态下乱改     |
| **执行后校验**      | 修改后再确认一次真的改成功了（`sed` 未匹配时也返回 0，必须二次确认）     |
| **可回滚**          | 有修改行为的脚本都提供 `--restore` 或 `--undo` 参数                      |
| **不含任何凭据**    | 所有脚本均不包含 token、密码。PAT 只通过 `docker exec -e` 环境变量传入   |
| **详细注释**        | 每个脚本头部有完整的目的/原理/用法/回退说明，关键代码行有逐行注释        |

### 3.2 `scripts/01_backup.sh`

| 项                                     | 内容                                                                                                                                                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **行数**                               | 215 行（含注释）                                                                                                                                                                                         |
| **目的**                               | 在每个里程碑留下可精确回退、可逐行比较的快照                                                                                                                                                             |
| **解决的问题**                         | ① 改坏了要能退回去；② 要能说清「到底改了什么」；③ 源目录整个损坏也要能救                                                                                                                                 |
| **代码做了什么（6 个步骤）**           | ① 初始化独立快照 git 仓库（幂等）；② `find` 清空快照工作区但保留 `.git`；③ `tar` 管道复制源文件（排除 `.git`）；④ `git commit`（内容无变化则跳过）；⑤ 快照仓库打 annotated tag；⑥ 源仓库也打同名 tag     |
| **为什么建独立快照仓库而不是复制目录** | al-folio 自带的 `.git` 有 354 MiB。每个里程碑复制一份整目录，磁盘迅速膨胀，且多份副本之间没法用 git 工具比较。独立快照仓库只跟踪工作区文件（约 55 MiB），多个里程碑共享 git 对象存储，增量存储、体积可控 |
| **为什么源仓库也打 tag**               | 两者互补：源仓库 tag 零额外空间、`git diff <tag>` 最方便，但与源目录同生共死；独立快照库占空间，但源目录被误删时仍能恢复。所以两个都做                                                                   |
| **为什么快照排除 `.git`**              | 快照的目的是保存**内容**，不是保存上游提交历史。上游历史在源仓库已有一份，且公开可从 GitHub 重新获取，没必要再存一份 354 MiB                                                                             |
| **`rm -rf` 的安全性**                  | 作用域严格限定在硬编码的 `${SNAP}`（快照仓库目录），**永远不会碰源目录**。源目录全程只被 `tar` 读取，不写不删。且 `set -u` 保证路径变量为空时脚本会直接报错退出，不会变成 `rm -rf /`                     |
| **为什么用 `tar` 管道而不是 `cp -r`**  | ① `tar` 的 `--exclude` 能可靠排除 `.git`，`cp` 没有 exclude 选项；② `tar` 完整保留权限、符号链接、时间戳；③ 管道方式不产生中间临时文件                                                                   |
| **为什么先清空再拷贝**                 | 只覆盖的话，源目录里已删除的文件会残留在快照里，导致快照不能精确反映当时的真实状态                                                                                                                       |
| **做得怎么样**                         | ✅ 成功建立 7 个里程碑快照，快照仓库 133 MB，源仓库同步 7 个 tag                                                                                                                                         |
