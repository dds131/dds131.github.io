一、本页在专题中的位置

前五页讲的是这个模型怎么造出来的。本页只回答一个问题：把它落到自己的机器和机器人上，要付多少代价、怎么选。

1.4%Table 1 中 LoRA 的可训练参数占比
59.7 GBSigLIP-only 变体、batch 16 的 LoRA 实测
约 8 倍论文报告的 LoRA 算力节省
7.0 GBTable 2 中 int4 推理显存
10 – 150论文所测新本体任务的演示条数
适用范围。 本页分析的是 2024 年原始 OpenVLA 论文及其参考实现，重点是理解微调、量化和部署的证据边界。官方仓库后来推荐 OFT：相对原始逐 token OpenVLA，它面向更高频率、动作分块和连续动作做了专门优化。因此，下文约 6 Hz 的吞吐和 Table 1、Table 2 的资源数字应视为原始 OpenVLA 基线，不是当前所有 OpenVLA 系方法的性能上限。
先统一实验口径。 论文脚注 4 明确说明，§5.3 和 §5.4 使用的是较小的 OpenX 数据混合，以及只含 SigLIP、不含 DINOv2 的较小模型。也就是说，Table 1 与 Table 2 适合比较同一实验内的微调策略和量化精度，不能直接代表最终发布的双视觉编码器权重，也不能脱离 batch、硬件、软件版本和并行方式推导通用显存门槛。

二、五种微调策略的定义

论文对五种策略的定义写得很明确（层一，§5.3）：

策略 解冻范围
全量微调 微调期间更新所有权重
仅最后一层 只微调 Transformer 主干的最后一层与 token 嵌入矩阵
冻结视觉塔 冻结视觉编码器，微调其余全部权重
三明治微调 解冻视觉编码器、token 嵌入矩阵与最后一层三者
LoRA 低秩适配，取多个秩值，作用于模型的全部线性层

注意「仅最后一层」与「三明治」的训练范围差别在于后者额外解冻视觉编码器。在这组实验中，两者的成功率点估计相差 31.8 个百分点；这是特定任务与训练设置下的观察值，不是跨任务固定不变的“视觉塔代价”。

这五项是论文的消融定义，不是当前 vla-scripts/finetune.py 提供的五个现成开关。2026-09-16 核对的脚本直接提供 LoRA、4-bit 量化 LoRA，以及关闭 LoRA 后的 DDP 全参数路径；“仅最后一层、冻结视觉塔、三明治”需要另行设置 requires_grad 或使用相应训练配置。对于旗舰 7.5B 模型的全量微调，官方文档推荐原生 train.py + FSDP，而不是用 DDP 在每张 GPU 上复制完整模型。

以下为论文 Table 1 原表转录（层一，§5.3）。表注说明：平均成功率与标准误差由每种方法 33 次 rollout 在选定的 Franka-Tabletop 任务上计算得出；带星号的显存数字是用 FSDP 分片到 2 张 GPU 上的结果。

这张表要横着读，三列一起看才能得出结论：

成功率维度全量微调与 LoRA 秩 32 的点估计分别为 69.7% 和 68.2%，相对报告的标准误差很接近；论文据此将 LoRA 描述为匹配全量微调。由于没有报告显著性或等效性检验，这里不能进一步声称二者在统计上等价。
参数维度跨度达 74 倍：全量 7,188.1 百万，LoRA 秩 32 只有 97.6 百万。三明治 914.2 百万，比 LoRA 多近十倍。
显存维度与参数量并不同序。显存还受激活、优化器、临时工作区与分片方式影响；特别是带星号的两行采用双卡 FSDP，不能把表中总量直接当成单卡需求。
冻结参数不等于切断反向传播。「仅最后一层」同时训练 token 嵌入矩阵；为了得到嵌入矩阵的梯度，梯度仍需经过中间的冻结 Transformer 层。冻结这些层能省去其参数梯度与优化器状态，但不能简单写成“不必穿过这些模块、无需保留激活”。该策略为何在此实现中最低，只能归因于参数梯度、优化器状态、激活保存策略和具体实现的共同作用，论文没有提供逐项显存分解。

四、冻结视觉塔的实验结果与证据边界

机制论证属 子页 ① 网络架构与 Prismatic 主干，本页只补量化幅度并指出一个容易被忽略的对照。

论文在 §3.4 给出的判断是：先前关于 VLM 的工作发现训练期冻结视觉编码器通常带来更高性能，直觉上冻结能更好地保留互联网规模预训练学到的鲁棒特征；但在 VLA 训练中，微调视觉编码器对性能至关重要，作者推测预训练视觉主干可能没有捕捉到场景中关键部位足够细粒度的空间细节（层一）。

把 Table 1 的两行放在一起，可以看出这句话的分量：

对照 成功率 差值
全量微调 69.7 ± 7.2% 基准
冻结视觉塔 47.0 ± 6.9% 低 22.7 个百分点

在这项受控消融中，训练策略的关键差别是视觉塔是否参与微调，成功率点估计相差 22.7 个百分点。这支持“视觉表示也需要适配机器人数据”的结论；但 22.7 是有限任务和 rollout 下的实验估计，不应被写成换到任何本体都固定损失 22.7 个百分点。

Table 10 的说明还将所有可比试验汇总为：冻结视觉塔平均成功率 46.7%，微调视觉塔为 80.0%。这一汇总同时受不同基座和可比任务范围影响，适合支持方向性结论，不是发布版 OpenVLA 的绝对性能。 这张表的口径必须先说清楚。 表头自身写明两个基座是 SigLIP ViT-SO 224px 与 LLaVa v1.5 7B 复现版，都不是最终发布的双编码器 OpenVLA。因此这两组数字用于支持「微调视觉塔优于冻结」这一定性结论在不同基座上都成立，不能当作发布模型自身的性能。

六、三明治微调：省在哪、为什么仍不如 LoRA

三明治微调解冻视觉编码器、token 嵌入矩阵与最后一层。把它与相邻两种策略对照：

对照 成功率 可训练参数（百万） 显存
仅最后一层 30.3 ± 6.1% 465.1 51.4 GB
三明治（加解冻视觉塔） 62.1 ± 7.9% 914.2 64.0 GB
LoRA 秩 32 68.2 ± 7.5% 97.6 59.7 GB

从仅最后一层到三明治，额外解冻视觉塔后成功率点估计提高 31.8 个百分点，与前述视觉塔消融方向一致。相对 LoRA 秩 32，三明治的可训练参数约多 9.4 倍、报告显存高 4.3 GB，成功率点估计低 6.1 个百分点；论文未报告显著性检验，因此不应把这 6.1 个百分点解释成已证明的稳定差距。

一种可能的解释，而不是由表格直接证明的机制：三明治只更新视觉塔、嵌入矩阵和最后一层，LoRA 则把低秩增量分布到全部线性层，因此后者能在更多层上进行小幅协调。Table 1 证明的是两种策略在该设置下的结果差异，不能单凭结果表确定内部机制。

七、LoRA：秩、作用范围与 1.4% 的核算

论文对 LoRA 的三条结论（层一，§5.3）：

  • 作用于模型的全部线性层；
  • 在论文比较的秩 32 与秩 64 中，成功率点估计相同，因此作者推荐默认取 32；
  • LoRA 在匹配全量微调性能的同时，只训练模型 1.4% 的参数。

第三条可以用 Table 1 直接算回（本页推算）：

\[\frac{97.6}{7{,}188.1} = 1.358\% \approx 1.4\%\]

分子是 LoRA 秩 32 的可训练参数，分母是同表「全量微调」那一行的可训练参数。两者一致，论文的 1.4% 与表内数据自洽。

秩 32 与秩 64 的参数量分别为 97.6 与 195.2 百万，成功率点估计均为 68.2%，显存相差 0.8 GB。因此，在本实验比较的两个秩中没有观察到提高到 64 的收益，选择 32 更经济；这不能外推为所有任务和数据规模下“秩都不重要”。

为什么 Table 1 与发布权重参数量不同？ Table 1 的全量微调参数为 7,188.1 百万，发布权重实测总参数约 7,541.2 百万，相差约 353 百万。脚注 4 已确认 Table 1 使用 SigLIP-only 变体；发布版额外包含约 303 百万参数的 DINOv2 分支，融合后的投影层结构也不同。因此 DINOv2 能解释差额的主要部分，但不能把全部 353 百万都简单归给 DINOv2。可靠结论仍是：Table 1 的绝对参数与显存属于较小变体。

八、微调阶段的显存构成

本节给出概念分解，论文只报告总显存，没有测量各分项；因此不能用下式反推出精确占比。
\[M_{\text{train}} \approx M_{\text{weights}} + M_{\text{grad}} + M_{\text{optimizer}} + M_{\text{activations}} + M_{\text{workspace}} + M_{\text{fragmentation}}\]

LoRA 只训练 97.6 百万参数，为什么仍需要 59.7 GB？因为“可训练参数”只直接影响其中一部分：

组成 主要影响因素 LoRA 下的含义
模型权重 参数量、精度、量化、分片 未量化时仍要加载完整基座权重
参数梯度 可训练参数及其精度 只为 LoRA 参数和其他解冻参数保存
优化器状态 可训练参数、优化器类型 LoRA 的主要节省来源之一
激活 batch、序列长度、网络深度、检查点策略 梯度仍穿过全网络，不能随参数占比同步降到 1.4%
临时工作区与碎片 算子、CUDA、分配器和并行方式 不由参数量比例直接决定
LoRA 的可训练参数约为全量微调的 1.4%，不等于显存降到 1.4%。若只按 Table 1 的报告总量计算，59.7 GB 相对 163.3 GB 约下降 63.4%；但后者采用双卡 FSDP，而 LoRA 是单卡口径，所以该比例只能描述表内报告值，不能直接解释为每张 GPU 的节省比例或通用硬件需求。

降低显存时，通常应先减小每卡 batch 并增加梯度累积，再评估激活检查点、量化 LoRA、CPU offload 或多卡分布式。具体收益取决于实现，必须在目标软件栈上实测峰值显存。

当前 HF 微调脚本中的有效全局 batch 应按

\[B_{\text{global}} = B_{\text{per-rank}} \times N_{\text{accum}} \times N_{\text{ranks}}\]

计算；实验目录名只编码了前两项，使用 DDP 时不能据目录名反推出全局 batch。该脚本也没有在非边界 micro-batch 使用 DDP no_sync()，所以每次 backward() 仍会通信：梯度累积可以降低单次显存，但不会按累积倍数消除 all-reduce 成本。

保存与停止计数还有实现边界：gradient_step_idx % save_steps == 0 在每个 micro-batch 后判断，grad_accumulation_steps > 1 时同一个 step 可能重复进入慢速保存/LoRA 合并；停止条件同样在 micro-batch 级判断，会多算一次随后丢弃的 backward，而累积为 1 时会实际执行 max_steps + 1 次更新。稳健实现应只在 optimizer.step() 后递增唯一的 global_step，再按它保存和停止。脚本保存的 processor 与模型/adapter 也不含 optimizer、scheduler、RNG 和数据位置，因此是推理权重快照，不是可逐步复现的断点续训状态。

这里的量化微调具体是 4-bit QLoRA：load_in_4bit=True、NF4、BF16 compute，并强制启用 LoRA；LoRA 目标为 all-linear，默认 r=32、alpha=min(r,16)、dropout 0。它不是 Table 1 中未量化 LoRA 资源数字的同义词，显存与效果必须单独测量。

十二、推理吞吐与控制频率

论文正文明确给出的推理侧数字只有一组（层一，§3.5）：OpenVLA 以 bfloat16 载入时推理需要 15 GB 显存，在单张 NVIDIA RTX 4090 上运行速度约为 6 Hz（未使用编译、投机解码或其他推理加速手段）。

这张图要横着读三件事。以下三条均为按图读取，即从上方嵌入的柱状图中肉眼读出，论文正文与表格都没有给出这些逐 GPU 的数值，因此本页不转录具体读数、只描述形态。其一，RTX 4090 的 bfloat16 一栏约为 6，与 §3.5 正文所述「RTX 4090 上约 6 Hz」相符，可以拿它当读图的标尺。其二，8 比特在多数 GPU 上都是三者中最低的一栏；这与论文在附录 D.4 中提出的假设一致——该假设认为 8 比特量化所用运算导致推理速度下降（层一），完整证据链见子页 ⑦。其三，2080Ti 一组是图中唯一的反例，其 8 比特一栏高于 bfloat16 一栏。论文正文与图注都没有解释这一反例，本页也不代为推测原因。可验证的下一步是查该型号所属 GPU 架构对 INT8 与 BF16 两种数据类型的硬件支持差异，但这属于本专题范围之外的硬件问题。就部署而言，可以保守地记住一条：量化能否带来加速是随 GPU 型号变化的，不要把某一张卡上的结论跨卡照搬。

Figure 6 显示 bfloat16 与 int4 在 RTX 4090 和 H100 上吞吐较高，并指出现代推理框架还有进一步优化空间。需要更正论文图注的一处硬件名称：RTX 4090 属于 Ada Lovelace，H100 属于 Hopper，不能把两者都归为 Ada Lovelace。标有黑桃符号的条目表示模型需要分片到两张 GPU 才能装下。

约 6 Hz 只是 RTX 4090 上模型生成动作的吞吐，不能直接等同于机器人闭环频率。端到端延迟至少应写成：

\[T_{\text{e2e}} = T_{\text{capture}} + T_{\text{encode}} + T_{\text{upload}} + T_{\text{queue}} + T_{\text{preprocess}} + T_{\text{inference}} + T_{\text{download}} + T_{\text{dispatch}}\]

因此，5 Hz 控制周期为 200 ms。只有在 batch=1、稳态、串行服务且没有排队，并且“6 actions/s”的测量口径可近似为单请求服务率时，取倒数才得到约 167 ms/动作、约 33 ms 名义余量；它不是论文测得的 p50/p99 单请求延迟。相机、网络、排队和抖动都可能耗尽余量，必须实测完整链路。

本体 控制频率 能从 6 Hz 得出的结论
Franka-Tabletop 5 Hz 非阻塞 名义吞吐略高，但必须实测完整链路的 p50、p95、p99 延迟后才能判断是否稳定跟上
Franka-DROID 15 Hz 非阻塞 原始逐 token 策略无法为每个控制周期提供新动作，需要明确低层控制器如何处理动作间隔
“非阻塞”只表示低层控制器不会停下来等待模型，不能据此假定它必然重复上一个动作。控制器可能保持绝对目标、重复增量、插值轨迹或使用内部伺服目标；这些语义必须从机器人接口确认。重复 delta action 与保持绝对位姿的风险完全不同。

十四、HuggingFace 推理接口

发布权重通过 HuggingFace AutoClass 接口加载。下面是一个强调输入契约与版本固定的模板；MODEL_REVISION 应替换为经过审核的模型仓库提交哈希：

model_id = "openvla/openvla-7b"
model_revision = "<PINNED_MODEL_REVISION>"
instruction = "pick up the red cup"

processor = AutoProcessor.from_pretrained(
    model_id, revision=model_revision, trust_remote_code=True
)
vla = AutoModelForVision2Seq.from_pretrained(
    model_id,
    revision=model_revision,
    attn_implementation="flash_attention_2",   # 可选，需要 flash_attn
    torch_dtype=torch.bfloat16,
    low_cpu_mem_usage=True,
    trust_remote_code=True,
).to("cuda:0")

# 仅适用于这里的 openvla/openvla-7b（Pure In/Out 模板）
prompt = f"In: What action should the robot take to {instruction.lower()}?\nOut:"
inputs = processor(prompt, image.convert("RGB")).to("cuda:0", dtype=torch.bfloat16)
action = vla.predict_action(**inputs, unnorm_key="bridge_orig", do_sample=False)

五处必须正确的地方：

项 要求 原因
模型与代码 revision 固定并记录 main 会变化；模型与远程实现必须成对复现
trust_remote_code 仅对已审核 revision 开启 它会执行模型仓库提供的 Python 代码，不只是读取权重
提示模板 与训练模板一致 空格、换行和前后缀都会改变 token 序列
指令大小写 直接 HF 路径要自行小写化 官方部署脚本会在内部小写化，直接调用不会代做
unnorm_key 选择当前本体和动作定义对应的统计键 它决定动作维数与反归一化尺度；自定义模型的键集合并不固定为 25 个

模板不能跨模型族照搬：openvla/openvla-7b 使用上面的 Pure In/Out 格式，而 v01 变体使用带 system prompt 的 Vicuna USER/ASSISTANT 格式。官方服务通过路径名是否含 v01 来分支，这只是示例约定；生产系统应由固定配置声明 prompt builder，不能靠可任意改名的路径字符串猜模型族。

不存在的 unnorm_key 通常会触发校验错误；更危险的是选择了一个确实存在、但属于错误本体或动作定义的键，此时程序可能正常返回动作，却使用错误的维数、分量顺序或数值尺度。部署前应把键名、动作维数、单位、坐标系、delta/absolute 语义和夹爪约定一起写入接口契约，而不是只检查数组形状。

微调后的反归一化统计量还有“双来源”风险：finetune.py 把新数据统计另存为 dataset_statistics.json，但保存权重时不会自动把它同步进 config.norm_stats。官方 deploy.py 只有在 openvla_path 是本地目录时才读取旁路 JSON 并覆盖 vla.norm_stats，且本地目录缺少该文件会在启动时失败；从 Hub 标识加载时则继续使用模型配置里的统计量。发布微调模型时应把权重、processor 与 JSON 成套保存，最好同时同步 model.norm_stats 和 model.config.norm_stats，加载后再核对键、维数与分量语义。

do_sample=False 只关闭随机采样，并不保证输出一定是动作 token。两版 predict_action() 都把 max_new_tokens=D 当作上限，然后直接截取整段序列末尾的 D 个 id；代码没有断言实际生成了恰好 D 个新 token，也没有对完整词表施加动作区间硬掩码。生产封装应验证 new_token_count == D 和每个 id 的合法性；若 EOS 提前终止或出现普通文本 token，应拒绝该动作，而不是让解码裁剪把异常静默变成端点动作。

上面的模板显式传了 revision；官方 deploy.py 与 finetune.py 的默认 from_pretrained(..., trust_remote_code=True) 并没有这样做，LoRA 合并时重新加载基座也未固定 revision。若直接传 Hub 模型名，必须修改脚本，让 processor、训练模型和合并用基座都使用同一审核过的 commit，并记录解析后的 SHA；或改用已固定的本地快照。固定 HF 实现还期望 transformers==4.40.1、tokenizers==0.19.1，并仅接受 timm 0.9.10/0.9.11/0.9.12/0.9.16，不能只记录模型名。

十五、远程推理服务

论文提出把 GPU 推理放在远端，从而降低机器人端的算力要求。官方 vla-scripts/deploy.py 给出的具体实现是同步 HTTP POST /act：客户端提交图像、指令和可选的 unnorm_key，服务端完成一次推理后返回一次动作。机器人可以连续发请求，但这不是 WebSocket 或 gRPC 意义上的流式协议。

该脚本适合演示接口，不是可直接暴露到机器人网络或公网的生产服务。它没有内置认证、TLS、限流、请求大小限制、有界队列和动作安全校验；异常处理还会把内部异常统一转成字符串 "error"。同步路由也没有为单个 GPU 模型提供串行化锁，多个请求可能同时进入推理并造成显存峰值、乱序返回或不可控排队。生产封装至少需要：

  • 认证、TLS 与网络访问控制；
  • 图像尺寸、类型、编码和请求体大小校验；
  • 用单消费者或显式 semaphore 串行化单模型 GPU 推理，并设置有界队列、deadline、request_id、过期丢弃、限流及明确的 429/503 错误码；
  • revision 和依赖版本固定；
  • 动作维数、有限值、幅度、速度和工作空间校验；
  • 时间戳、过期动作丢弃、watchdog 与安全停止；
  • p50、p95、p99 延迟、队列长度、错误率和动作年龄监控。

模型推理不一定永远是最大延迟项：弱网络、并发排队、图像编码或冷启动都可能成为瓶颈，应按第十二节的端到端公式实测，而不是只记录模型吞吐。

源码虽然在无 CUDA 时选择 CPU device，但仍默认请求 FlashAttention 2 和 BF16；这不构成可靠的 CPU fallback。非 CUDA 部署必须显式选择兼容的 attention 实现与 dtype，并独立验证性能和数值。异常响应也应改为结构化 4xx/5xx；不能返回通常仍带 HTTP 200 的普通字符串 "error"。

十六、LIBERO：可复现的微调基准

真机评测依赖硬件、场景布置和控制栈，复现成本高且难以标准化。论文因此补充了 LIBERO 仿真实验（层一，附录 E.1），为不同方法提供更一致的比较条件。

基准构成。 LIBERO 含四个任务套件，每个套件 10 个任务、每个任务 50 条人工遥操作演示：

套件 考察什么
LIBERO-Spatial 物体相同、布局不同，考察空间关系理解
LIBERO-Object 布局相同、物体不同，考察物体类型理解
LIBERO-Goal 物体与布局相同、任务目标不同，考察面向任务的行为知识
LIBERO-Long（即 LIBERO-10） 长时程任务，物体、布局与任务都多样

论文中的 OpenVLA 使用 LoRA r=32，并且为四个 suite 各自独立训练一个策略，不是把四套件联合训练成一个模型。复现比较时必须保留这一实验单位。

五步数据处理（层一，附录 E.1，这是复现该实验的关键）：

步 处理
1 把演示重新渲染为 256 × 256 像素。原始数据是 128 × 128，直接上采样画质很差，因此改为用存储的动作在仿真中重新步进并保存渲染图像
2 滤除全部空操作动作，即平移与旋转分量接近零且不改变夹爪状态的动作
3 训练与测试时把第三人称图像旋转 180 度，因为在作者硬件上 LIBERO 环境返回的图像是倒置的
4 重放并剔除失败演示。结果移除了 LIBERO-Spatial 500 条中的 68 条、LIBERO-Object 的 46 条、LIBERO-Goal 的 72 条、LIBERO-Long 的 121 条
5 所有方法只使用静态第三人称相机图像，不使用数据集另外提供的腕部相机图像
LIBERO 的处理是按动作语义识别并过滤全部 no-op；Bridge 的处理则针对已知的首帧零动作。二者都在避免无效监督，但触发条件和覆盖范围不同，不应视为完全相同的规则。第 4 步还说明“演示文件”不等于“成功轨迹”：LIBERO-Long 重放后剔除了 121/500，即 24.2%。

结果（层一，Table 12）：每种方法在每个套件上评测 3 个随机种子，每个种子 500 次，共 1,500 次 trial。不同套件难度不同，因此除平均成功率外，还应看跨套件平均排名。

OpenVLA 的平均成功率和平均排名均第一，但只在四个套件中的两个取得最高成功率：LIBERO-Object 由 Diffusion Policy 领先，LIBERO-Goal 由 Octo 领先。这支持“整体迁移能力较均衡”，不支持“OpenVLA 在每类任务上都最好”。仿真中的平均领先幅度小于论文真机实验。作者推测原因是 OpenVLA 只在真实机器人数据上预训练，存在仿真—现实域差异；但这不是单变量消融结论，因为两个评测还同时改变了任务、数据和协议。

十七、部署侧换本体检查清单

以下项目应在离线回放、shadow mode、低速限幅和人工监护下逐级验证，再允许策略直接控制机器人。

检查项 最低要求
版本 固定模型 revision、远程代码 revision 和依赖版本
显存 在目标硬件按真实 batch 和并行方式实测，并保留运行余量
微调 默认从 LoRA r=32 开始；显存不足先调 batch 与梯度累积
视觉塔 论文结果支持默认参与适配；若冻结，必须在目标任务重新验证
图像输入 校验相机来源、RGB 顺序、尺寸、裁剪、朝向、时间戳和延迟
动作契约 固定维数、分量顺序、单位、坐标系、delta/absolute 与夹爪语义
反归一化 校验 unnorm_key、统计量版本以及动作上下界
模型产物 权重、processor、dataset_statistics.json 与 config 中统计量保持一致
生成输出 验证新 token 数等于动作维数，且每个 token 都属于合法动作区间
控制周期 测量端到端 p50、p95、p99 延迟和动作年龄，不只看模型 Hz
控制器 明确阻塞/非阻塞及两次策略更新之间的保持、重复或插值行为
安全限制 关节、工作空间、速度、加速度、夹爪力和碰撞限制均在模型外执行
失效处理 超时、断网、异常值、GPU OOM 和服务错误进入可验证的安全状态
人员安全 提供 watchdog、硬件急停、人工接管，并先以低速和小工作空间验证
数据质量 重放演示，区分成功、失败和 no-op；不要假定所有演示都有效

论文足以确认 §5.2 中 OpenVLA 等方法使用相对位置控制，但不能据此推出每个 7 维分量的顺序、旋转表示、单位和夹爪极性。完整动作 ABI 必须来自对应数据 transform 与机器人客户端的固定版本；不能只凭 unnorm_key 名称或数组长度反推。

十八、本页易误解点清单

常见说法 是否成立 正确表述
LoRA 把显存降到 1.4% 不成立 1.4% 是可训练参数占比；显存还包含权重、激活和工作区
可训练参数越少显存一定越低 不成立 显存还取决于梯度路径、batch、检查点、精度与分片方式
提高 LoRA 秩一定能提升性能 不成立 本实验的秩 32 与 64 点估计相同，不能外推到所有任务
冻结视觉塔固定损失 22.7 个百分点 不成立 22.7 是特定消融的点估计，不是跨任务常数
Table 10 是发布模型的性能 不成立 其基座是 SigLIP ViT-SO 与 LLaVa 复现版，只支持定性结论
int4 在任何设备都优于 int8 不成立 只在论文特定硬件、实现和控制协议下观察到这一结果
OpenVLA 在所有微调任务上都最好 不成立 窄域单指令任务上 Diffusion Policy 更强，见第十节
6 Hz 模型吞吐等于 6 Hz 闭环控制 不成立 还需计入采集、网络、排队、预处理与动作下发
unnorm_key 选错一定会报错 不成立 不存在的键会报错；存在但语义错误的键可能静默地产生错动作
do_sample=False 就保证动作合法 不成立 它只关闭随机采样；仍需检查生成长度、早停和 token 区间
五种论文策略都有现成脚本开关 不成立 当前 HF 脚本直接暴露的是 LoRA/量化 LoRA/全参数路径
LIBERO 的演示都是成功的 不成立 重放后 LIBERO-Long 剔除了 500 条中的 121 条
全量微调需要和预训练同等算力 不成立 预训练 64 卡 14 天，全量微调 8 卡 5 – 15 小时
官方 REST 示例可直接用于生产 不成立 它缺少认证、限流、严格校验、监控和机器人安全保护
