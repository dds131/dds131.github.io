VLA 总览/DexGraspVLA/高层规划器与目标抽象

① PLANNER · EVENT-DRIVEN VLM · BBOX PRODUCER

Planner 不是与低层控制器联合训练的策略网络。它把用户提示拆成四项事件级 VLM 任务，维护当前 instruction 与两类完成状态，并把“当前目标位于哪一帧的哪个 bbox”交给下一页。

返回专题总览下一知识点：② 目标感知与跟踪相关：③ 观测编码器与 DiT
4 个 task_nameevent-drivenbbox ≠ maskstatic analysis only

自由形式提示先被转成当前物体级 instruction，再落到当前头部图像的二维框。抓取执行期间，另一个 VLM 任务监控当前目标是否抓住；在第一次抓取前和每次固定复位后，第四项任务判断整条用户提示是否完成。Planner 的价值在于把语义目标、空间目标与任务状态显式化，而不是直接产生动作。

0已报告的 Planner 专用微调任务
149 / 150独立 bbox 评测正确数
86 / 96四类长程提示的完整任务成功数

阅读边界。 本页只解释 Planner 状态机、四项任务、bbox 生产者合同和静态风险；SAM 初始化、Cutie 传播与 mask 质量归 ② 目标感知与跟踪，动作闭环与线程安全归 ⑥ 推理闭环，完整数值表归 ⑦ 实验。

二、事件状态机：第一次抓取前先核验完成状态

固定脚本的静态顺序是：保存用户提示和初始工作区图；先判断提示是否已经完成；未完成才提出当前 instruction、预测 bbox 并交给 Perception；控制器执行期间后台核验抓取结果；一次 attempt 结束后执行固定放置/复位，再判断整条提示是否完成。下图是本站对固定脚本的状态抽象，不是论文发布的形式化状态机。

stateDiagram-v2
  [*] --> PromptCaptured
  PromptCaptured --> CompletionPrecheck
  CompletionPrecheck --> Finished: true
  CompletionPrecheck --> InstructionProposal: false
  InstructionProposal --> BoundingBoxPrediction
  BoundingBoxPrediction --> PerceptionHandoff
  PerceptionHandoff --> ControllerExecuting
  ControllerExecuting --> AttemptEnded: true / three-false / timeout / manual
  AttemptEnded --> ScriptedReset
  ScriptedReset --> CompletionCheck
  CompletionCheck --> Finished: true
  CompletionCheck --> InstructionProposal: false
  Finished --> [*]

文本回退： 捕获提示 → 首次完成预检；若已完成则结束，否则依次生成 instruction 与 bbox → 交给感知页 → 控制器执行并由后台核验 → 当前 attempt 因成功、连续三次 False、超时或人工条件结束 → 固定放置/复位 → 再次完成核验；未完成时重新选择目标。

这个顺序包含三个容易误读的边界：初始完成核验发生在第一次抓取之前；instruction 一定先于 bbox；bbox 后只发生感知交接，本页不越过 Page112 直接连接 Architecture。

三、四项 VLM 任务与统一请求信封

固定 task_name、输入、输出与触发事件
任务 视觉/文本输入 输出 触发

四项任务还需要分别记录输入版本和决策作用域。Instruction 与 Completion 关联整条 user prompt，BBox 关联当前 instruction 和一张确定的头部 frame，Outcome 则关联当前 controller execution 及同一时刻的头/腕图。若只保存最终字符串而丢失这些角色，离线检查将无法判断错误来自目标选择、空间定位、视觉核验还是时序错配。统一信封的目的不是把四项任务合并，而是在保持语义分离的同时建立可追踪的证据链。

四、Instruction 与 Completion：选择目标、判断整条提示

4.1 Instruction Proposal

Task①读取用户提示、初始工作区图和当前工作区图，产生一句当前物体级抓取 instruction。初始—当前图对照有助于推断哪些目标已从桌面移除，但公开接口没有显式物体清单或持久化符号状态。

prompt 写入四条任务先验：优先右侧再到中间和左侧、避开被阻挡或包围的目标、避免碰倒其他物体、满足用户提示。这些是作者手写规则，不是从 2,094 条控制示教中学出的 Planner 参数；“从右到左”也不是可跨机器人安装方式照搬的普适原则。

4.2 Prompt Completion Check

Task④比较初始与当前工作区头部图，并读取原始用户提示。它在第一次抓取前和每个 attempt 的固定复位后调用：空桌面或已完成提示可以在首轮直接结束。假阳性会提前终止整条用户任务；假阴性会继续目标选择，而固定接口缺少明确 no_target 恢复分支。它与只判断当前目标的 Grasp Outcome 是两个独立布尔语义，不能共用状态。

因果与训练边界。 论文没有报告 Planner 专用微调，也没有证明这些 prompt 规则来自机器人示教。它们是对通用 VLM 的任务编排；Planner 的可替换接口不等于更换模型后性能等价。

五、BBox：格式统一的空间接口，不是 mask 或抓取位姿

Task②读取当前工作区头部图和 Task① instruction，期望输出 bbox_2d: [x1,y1,x2,y2]、label 与 description。固定调用方只读取 bbox_info['bbox_2d']；后二者主要用于解释或日志。bbox 是 Planner→Perception 的唯一强制空间 payload，既不是像素 mask，也不是抓取位姿。

对白填充后仍保持原尺寸的宽 W、高 H 图像，约定左上角为原点，x 向右、y 向下；最小有效条件是：

\[0\le x_1<x_2\le W,\qquad 0\le y_1<y_2\le H.\]
现有事实与建议 guard 必须分开
层 字段或条件 证据状态
固定响应 bbox_2d、label、description 调用方只消费 bbox_2d
坐标合同 frame id、W/H、单调时间戳、xyxy 本站明确化的交接要求
建议 guard 数值/有限、顺序、范围、最小面积、当前帧 工程建议；固定调用点未完整实现
空目标 no_target 或等价 variant 固定接口缺失

论文称 bbox 是 “domain-invariant affordance”。有证据支持的是：四坐标提供一致格式、把自由语言与低层控制器解耦、可作为分割提示。没有建立的是：bbox 在统计上与域无关、总优于点或直接 mask、单独造成全部泛化增益，或让控制器不再面对视觉域偏移。相机、裁剪、遮挡、定位模型和 instruction 质量仍会改变 bbox；论文也没有提供 language vs point vs bbox vs direct mask 的受控消融。

六、图像预处理、模型身份与时钟边界

Instruction、BBox 与 Completion 使用桌面工作区头部图：固定 preprocess_img 保持原图尺寸，只保留行区间 [0,floor(0.6H)) 与列区间 [floor(0.4W),floor(0.9W))，其余像素填 255。Grasp Outcome 不走这一步，而是使用完整头部图和完整腕部图。比例是当前相机与安装位姿的硬编码常量，不是跨相机几何真理，也不能消除保留区域内的背景、光照和遮挡差异。

七、Outcome、attempt 与固定复位：三个计数层级

Grasp Outcome 是唯一同时读取完整头部图与腕部图的 Planner 任务。固定代码在后台 daemon thread 中，当末端高度超过 height_threshold 后发起核验；循环末尾 sleep(0.1) 只是轮询间隔，不证明 VLM 请求达到 10 Hz。一次解析为 True 会结束当前 controller execution；连续三次解析为 False 也会结束并进入固定复位。论文没有给该子任务独立受控准确率。

“连续三次 False”与 Ours@3 不是同一个计数器
计数器 样本单位 作用
consecutive_failed_attempts 同一次 controller execution 内的连续核验结果 阈值 3；结束当前 attempt 并复位
Ours@k 每个测试最多允许的独立抓取 attempt；k∈{1,2,3} 实验协议；attempt 内策略自身 re-grasp 不另计
低层 re-grasp 同一 attempt 内动作闭环行为 不等同于 VLM False 次数，也不增加 Ours@k

论文概括“成功抓取触发脚本化放置并复位”；固定 run_planner 则在每次 execute_grasping() 返回后调用 right_finish_reset()，不只覆盖成功路径。序列依次为：移动到右侧 placement joint、打开左右手、经过 right return-medium joint、回到 right initial joint。它既不是 VLM 生成，也不是扩散控制器生成；本页只用它切分 attempt，硬件安全与并发语义由 Inference/Source Code 负责。

八、解析路径、typed failure 与 fail-closed 目标

固定客户端通过 OpenAI-compatible API 得到文本；传输层只配置一次 HTTP retry。JSON 路径先清理代码围栏，再交给 repair parser；这能修补格式，却不等于字段 schema、坐标范围或语义有效。布尔路径把响应转为小写，先查 true、再查 false，所以同一响应同时含两词时会优先 True。所有 VLM 输出都应作为不可信输入。

失败类型是建议的可观测接口，不是当前实现已具备的保障
类别 类型 建议处理
传输/响应 ENDPOINT_UNAVAILABLE、REQUEST_TIMEOUT、EMPTY_RESPONSE 不得压成业务 False
JSON/字段 JSON_PARSE_FAILED、REQUIRED_FIELD_MISSING 保留原文引用并拒绝下游
bbox BBOX_NONFINITE、BBOX_OUT_OF_RANGE、BBOX_DEGENERATE 验证 frame 与范围，fail closed
布尔/目标 BOOLEAN_AMBIGUOUS、NO_VALID_TARGET 不把歧义或无目标当作普通 False
时序 STALE_IMAGE、FRAME_MISMATCH 拒绝陈旧或跨 frame payload

工程目标应是：无法证明 bbox、frame 或终止判定有效时，在进入 Perception 或执行动作之前 fail closed。当前固定实现并未完整实现上述 taxonomy；本页也不提供绕过校验的运行按钮。

诊断记录还应保存失败发生在哪个状态、是否发出下游 payload、采用了何种恢复动作，以及恢复后是否换用了新的 frame/request id。这样才能区分“模型回答不确定”“解析器接受了无效结构”“过期结果覆盖新状态”和“有效 handoff 在感知阶段失败”。其中重试、请求人工确认、安全停止或重新规划只是候选策略；没有统一置信度与风险预算时，不应默认自动重试总比停止更安全。

九、并发共享状态：只能登记静态风险

固定脚本中相机捕获、机械臂控制、手部控制、键盘监听、抓取结果核验、执行时限监控六类线程并行。Outcome daemon 读取 current_instruction、当前头/腕帧、in_post_run 与连续失败计数；静态审计未看到完整的 attempt id、frame id、request id、deadline 关联。

晚到响应旧核验结果可能在状态切换后返回；这是静态可见风险，不是已复现故障。
重叠核验同一 attempt 的后台请求若缺少唯一关联，可能难以判定哪个结果仍有效。
陈旧帧头/腕图与 instruction 若无 frame/request 关联，时间一致性无法仅靠变量名证明。
状态竞态in_post_run 与失败计数跨线程读写的运行性质需要后续动态验证。

本页没有 import 或运行项目，因而不能声称这些风险实际发生，也不能给出发生率。运行时深入分析、停止条件和安全控制边界分别链接 Inference 与 Source Code 页面。

十一、Planner→Perception 强交接合同

Planner 完成后只签发“目标 instruction + bbox + 产生该 bbox 的头部 frame + provenance”，不生成初始 mask。Page112 必须验证 frame/bbox，调用 SAM 得到首帧 mask，清空并播种 Cutie，维护跨帧目标身份，并拥有 mask 质量、漂移、消失和重新初始化的失败语义。目标发生变化时必须回到 Planner 产生新的 handoff。
