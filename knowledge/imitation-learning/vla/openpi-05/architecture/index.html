π0.5 的网络与 π0 不是两个模型。论文 Appendix E 的原话是「两个 transformer 的维度与 π0 相同」，openpi 里两者共用同一个 Pi0 类、同一份 compute_loss，差别由一个布尔开关 pi05 控制。这个开关只切换两件事，源码注释把它们写得很干脆：本体状态改走离散语言 token 而不再是 suffix 里的连续输入；动作专家改用 adaRMSNorm 注入流匹配时间步。

本页要做的是把这两句话拆到可实现的粒度，并说清第三件不在注释里、但决定了整个训练配方能否成立的事：六段式注意力掩码如何让两种动作表示互相看不见。

`num_heads` 这一行是本页记录的唯一一处论文与源码不一致。论文 Appendix E 写 num heads=18，openpi 写 num_heads=8。本页不替任何一方断定对错，只陈述两件可核验的事：其一，可运行、可加载官方权重的产物是 openpi；其二，该值在两个专家之间必须相同，理由见下一小节。完整的「论文与实现差异」清单归本专题子页 ⑦。

为什么有些配置可以不同、有些必须相同

src/openpi/models/gemma.py 的 Attention.__call__ 开头有三条断言，把答案写死了：

assert all(config.head_dim      == self.configs[0].head_dim      for config in self.configs)
assert all(config.num_heads     == self.configs[0].num_heads     for config in self.configs)
assert all(config.num_kv_heads  == self.configs[0].num_kv_heads  for config in self.configs)

原因在紧随其后的那一行：两个专家各自算完 Q/K/V 之后，代码做的是

q, k, v = (jnp.concatenate(y, axis=1) for y in zip(*qkvs, strict=True))

沿序列轴拼接。也就是说自注意力不是「VLM 算一遍、动作专家再算一遍」，而是两边的 Q/K/V 拼成一条长序列后联合做一次注意力。拼接要求除序列长度以外的所有轴对齐，于是 num_heads、num_kv_heads、head_dim 三项必须一致。

还有第四项约束写在别处：gemma.py 的 Module.setup 开头断言 depth 也必须相同。这解释了一个容易被误解的现象——动作专家并不是一个「层数更少的小模型」，它和 VLM 一样是 18 层，小只小在 width（2048 降到 1024）与 mlp_dim（16384 降到 4096）上。原因同样是联合注意力：两个专家必须在每一层同步参与同一次注意力计算，层数对不齐就无法逐层配对。

而 width 与 mlp_dim 可以不同，是因为它们只出现在各自专家的投影矩阵里。q 投影的形状是 (num_heads, width, head_dim)：输入宽度是本专家的 width，输出宽度是共享的 head_dim。VLM 用 2048 → 8 × 256，动作专家用 1024 → 8 × 256，两者投影出来的 Q 形状相同，因此能拼。

注意一个容易被二手讲解写错的推论：num_heads × head_dim 不必等于 width。动作专家是 8 × 256 = 2048，而它的 width 是 1024。注意力的内部宽度与残差流的宽度在这里是解耦的，`attn_vec_einsum` 再把 (num_heads, head_dim, width) 投回 1024。

num_kv_heads 取 1 是什么意思：多查询注意力与 KV cache 的账

上表里 num_kv_heads = 1 这一行容易被当成又一个无关紧要的配置项划过去，但它决定了整个架构最依赖的那件事——prefix 的 KV cache 有多大。

gemma.py 的 Attention.__call__ 里对 Q 与 KV 走的是两条不同的分支。当 num_kv_heads 与 num_heads 不相等时（π0.5 正是这种情况，8 与 1），Q 与 KV 由两个独立的 einsum 产生：

q_einsum  = Einsum(shape=(config.num_heads,     config.width, config.head_dim))   # 8 个头
kv_einsum = Einsum(shape=(2, config.num_kv_heads, config.width, config.head_dim)) # 1 个头，K 与 V 各一份
q      = q_einsum("BTD,NDH->BTNH", x)
k, v   = kv_einsum("BSD,2KDH->2BSKH", x)

随后 Q 被重排成「KV 头 × 组」两级，再与那唯一的一个 K 头做点积：

q      = einops.rearrange(q, "B T (K G) H -> B T K G H", K=self.configs[0].num_kv_heads)  # K=1, G=8
logits = jnp.einsum("BTKGH,BSKH->BKGTS", q, k)

也就是说：8 个查询头共享同一组 K/V。这是多查询注意力（Multi-Query Attention）——分组查询注意力在 num_kv_heads = 1 时的极端情形。

它省下了多少

KV cache 只需缓存 K 与 V，而 K/V 的头数是 1 而不是 8，缓存直接小到八分之一。按本页第十节的默认配置（prefix 长 968、head_dim = 256、depth = 18、dtype 为 bfloat16）把账算一遍：

量 计算 结果
单层单个张量（K 或 V） \(968 \times 1 \times 256 \times 2\) 字节 约 0.47 MiB
单层 K 与 V 合计 \(\times 2\) 约 0.95 MiB
18 层合计（每个样本） \(\times 18\) 约 17 MiB
若改成 8 个 KV 头（对照） \(\times 8\) 约 136 MiB

上表是按源码常量直接算出的，不是论文或仓库给出的数字，仅用于说明量级差异；实际显存占用还取决于批大小、是否做分片等因素。

为什么这件事对 π0.5 尤其要紧

一般语言模型里 KV cache 的压力来自「序列越生成越长」。π0.5 的情形不同——它的 prefix 长度是固定的，但那份 cache 要在十步积分里被反复读取。于是省 KV 头带来的收益体现在两处：

  • 显存：动作专家每步都要拿全部 prefix 的 K/V 做注意力，cache 必须常驻；
  • 访存带宽：十步积分意味着同一份 cache 被反复读取。多查询注意力把相对于 8 个 KV 头的读取量压到八分之一；这通常有利于降低带宽压力，但是否成为端到端瓶颈仍取决于硬件、批大小与实现，不能在没有性能剖析时断言“必然访存受限”。

把本页几处结论连起来看，会发现它们指向同一个目标：

设计 在哪一节 对「十步积分」这件事的作用
掩码让信息单向从 VLM 流向动作专家 第五节 prefix 表示不依赖 suffix，cache 可以复用
state 从 suffix 迁到 prefix 第四节 十步里恒定不变的量进入可缓存的 prefix；官方 π0.5 推理不再每步重算它
动作专家只有 300M 本节 要重算十遍的那部分参数量最小
num_kv_heads = 1 本节 被读十遍的那份 cache 体积最小

四条设计的作用并不相同：掩码决定 prefix cache 能不能复用；state 的位置决定这个不变量是否进入 cache；动作专家规模影响每步 suffix 的计算量；KV 头数影响 cache 的存储与读取量。不能把后两项都概括成“复用成本”。

需要说明两点边界。其一，多查询注意力不是 π0.5 的创新，它来自 Gemma 本身的架构选择，π0 与 π0.5 共用同一份 get_config，此处只是把它对本页主题的意义讲清楚。其二，第二节开头那三条 assert 要求两个专家的 num_kv_heads 必须相同——在 π0.5 里这意味着动作专家也是单 KV 头，它与 VLM 专家的 K/V 沿序列轴拼接后才能做联合注意力。

300M 动作专家与重复推理开销

prefix 在一次动作采样中只编码一次，而 suffix 随十步积分反复计算。因此，较小的动作专家确实会降低重复部分的计算量；但论文与仓库没有把“为何选 300M”归因于这一点，也没有给出不同动作专家规模的单变量消融。把它理解为与推理结构相匹配的工程效果是合理的，不能写成作者已经证明的设计动机。完整的计算路径在 π0 专题子页 ①，π0.5 继承了这一双专家取舍。

四、state 为什么从连续 suffix 移到离散 prefix

这是两处改动里更容易被低估的一处。它看起来只是换了个位置，实际改变的是 state 在整个模型里的角色。

改动的确切内容

src/openpi/models/tokenizer.py 的 PaligemmaTokenizer.tokenize 在传入 state 时走 π0.5 格式：

discretized_state = np.digitize(state, bins=np.linspace(-1, 1, 256 + 1)[:-1]) - 1
state_str = " ".join(map(str, discretized_state))
full_prompt = f"Task: {cleaned_text}, State: {state_str};\nAction: "
tokens = self._tokenizer.encode(full_prompt, add_bos=True)

π0 格式则完全不同：只把指令文本编码后接一个换行 token 作为「答案起点」，state 根本不进语言侧。

对应地，src/openpi/models/pi0.py 的 embed_suffix 用一个 if not self.pi05 把 state token 整段跳过；__init__ 里 state_proj 这个线性层在 pi05=True 时根本不会被创建。

三条结构性收益

  • 输入接口更接近 VLM 的 token 形式。 π0.5 的完整论文配方会在同一训练阶段采样图文、网页与机器人等不同数据源，但论文没有要求每个 minibatch 都同时包含纯图文样本和机器人样本。把 state 写进文本 prefix 后，机器人样本不再额外依赖一个连续 state suffix token；不过不同样本的目标、掩码和模态仍然不同，不能说它们的“前向路径完全一致”。还要区分：公开 pi0.py 的 pi05=True 路径只实现连续动作流匹配，并未实现论文中的纯文本训练分支。
  • state 参与 prefix 的语义融合，而不只是给动作解码器一个数值条件。 在公开实现中，图像 token、指令 token 与离散 state token 都位于 embed_prefix 生成的同一双向注意力块，因此当前本体状态可以影响 prefix 表示。论文 Appendix E 的完整掩码也把 proprioceptive state 放在 full-prefix mask 内。
  • state 进入可复用的 KV cache。 state 在十步积分里恒定不变，放在 prefix 意味着它只被编码一次。π0 虽然把 state 单列为 suffix 的第一个注意力块，但公开 sample_actions 每个欧拉步都会重新调用 embed_suffix 并重算该 state token；公开实现只缓存图像与语言 prefix。π0.5 才真正把 state 移到这份缓存中。

代价：256 档量化，且归一化口径成为硬约束

源码把 np.linspace(-1, 1, 257)[:-1] 作为 256 个分箱阈值，即阈值从 \(-1\) 到 \(1-\frac{2}{256}=0.9921875\)。对位于预期归一化范围内的值，np.digitize(...)-1 产生 0–255：\(-1\) 映射到 0，达到最后一个阈值及以上的值映射到 255。论文没有解释 256 这个数的来源；能确认的权衡是，档数越少量化越粗，档数越多则整数表示与词元占用可能增加。

真正需要警惕的是归一化口径与边界行为。论文 Section IV-C 写明动作数据按各维度的 1% 与 99% 分位数归一化到 \([-1,1]\)；公开 transforms.Normalize 和 tokenizer 都没有额外裁剪。因此边界不是对称饱和：低于 \(-1\) 的值经 np.digitize(...)-1 会得到 -1，而高于最后一个阈值的值都会得到 255。若大量样本越界或挤在边界，若干 state 维度的分辨率会静默塌缩，策略可用的本体信息随之减少；但这不等于模型必然“完全看不见状态”，更不等于“开环执行”——图像与指令仍在闭环条件中。现象与排查归本专题子页 ⑦。

论文并没有给出一个单独的 state-tokenization 消融来证明「这个改动本身提高了多少成功率」。因此可以明确说它让结构与训练范式更统一，但不能说论文已证明它独立贡献了某个百分比的性能。

一个直接推论：discrete_state_input 关掉之后，state 就没有任何入口了

上面两条源码事实合起来会导出一个后果，值得在这里点明——因为它不是假想，pi05_libero 出厂配置就是这样。

state 在 π0.5 里只有两条可能的入口，而它们分别由两个独立的开关控制：

入口 由谁控制 pi05=True 且 discrete_state_input=False 时
走 suffix，经 state_proj 成为一个连续 token pi0.py 的 if not self.pi05 关闭——pi05=True 使这段被整体跳过，且 state_proj 根本不会被创建
走 prefix，离散化后拼进 prompt 文本 transforms.py 的 TokenizePrompt.discrete_state_input 关闭——该标志为假时传入 state=None，tokenize 转而走 π0 格式，prompt 里没有 State: 那一段

两条路同时断开，本体状态就完全进不了模型。这不是「退回 π0 的状态走法」——π0 的走法是第一行那条，而 pi05=True 已经把它关掉了。

为什么官方配置会这么设。pi05_libero 确实显式写了 discrete_state_input=False。本站只陈述这个组合的机制后果，论文与仓库都没有解释这样设的理由，因此不对「LIBERO 上是否应当去掉本体状态」下判断。完整的配置对照与后果分析在 ⑥ OpenPI 源码剖析 第 6.2 节，它也被收进 ⑦ 差异与推理期现象 的反直觉现象清单；本页只负责说清「入口为什么只有两条、又怎么被同时关上」。

五、注意力掩码：六段结构与两种动作表示的信息隔离

这一节是本页的核心，也是最容易被二手讲解略过的部分。π0.5 的训练配方要求模型同时用两种方式表示动作：FAST 离散 token 走交叉熵，连续动作 token 走流匹配。两者放在同一条序列里，如果互相可见，就会发生信息泄漏——预测 FAST token 时可以偷看连续动作，反之亦然，任务全部退化。

论文 Appendix E 给出了完整的掩码规则，并配了一张示意图：

把图和 Appendix E 的文字对齐，规则可以逐段写死：

查询段（行） 能看到 看不到 依据
图像 token 全部 prefix（图像、Prompt、State） FAST token、动作专家 token 「A full prefix mask is used on images, prompt tokens, and proprioceptive state」
Prompt token 同上 同上 同上
State token 同上 同上 同上
FAST 动作 token 全部 prefix，以及自身之前的 FAST token 动作专家 token 「FAST action tokens attend to this prefix and auto-regressively on previous action tokens」
动作专家 embedding 全部 prefix，以及彼此（块内双向） FAST 动作 token 「attend to the prefix and to one another, but do not attend to FAST action tokens to avoid information leakage」

三条结论可以从这张表直接读出：

  • 信息单向从 VLM 流向动作专家。 论文原话是「no VLM embedding attends to the action expert」。这是 prefix 的 KV cache 能在十步积分中复用的前提：prefix 的表示不依赖任何 suffix 内容，因此十步里它一字不变。
  • FAST 段内部是因果的，动作专家段内部是双向的。 前者是自回归解码的要求（生成第 k 个 token 时不能看到第 k+1 个），后者是流匹配的要求（整块动作一次性并行输出，块内不存在先后）。图中 FAST 那一块的三角形与动作专家那一块的实心方块，画的就是这个差别。
  • 两种“方向”不要混为一谈。 跨专家的条件流是 VLM prefix → 动作专家的单向关系；FAST token 与连续动作专家 token 之间则是相互不可见。两条动作表示各自以 prefix 为条件，不构成前后相接的预测链。

openpi 里对应的是哪一段代码

需要如实说明：开源 openpi 的 pi05=True 路径上没有 FAST token 那一段（原因见子页 ⑦）。能在源码里核对的是「prefix 双向、suffix 对 prefix 单向」这半张掩码，由 ar_mask 与 make_attn_mask 实现。

embed_prefix 给图像与语言 token 的 ar_mask 全部填 False；embed_suffix 给动作段填 [True] + [False] * (action_horizon - 1)。make_attn_mask 的规则是：

cumsum = jnp.cumsum(mask_ar, axis=1)
attn_mask = cumsum[:, None, :] <= cumsum[:, :, None]

即「累计 mask_ar 小于等于自身的 token 可见」。True 起一个新块，块内所有 token 的 cumsum 相同因而互相可见；后一块能看到前一块，前一块看不到后一块。所以：

  • prefix 全 False → cumsum 恒为 0 → prefix 内部全可见（双向）。
  • 动作段首个 True 让 cumsum 跳到 1 → 动作段能看到 prefix，prefix 看不到动作段；动作段内部 cumsum 相同 → 块内双向。
对照 π0 分支会更清楚：π0 的 embed_suffix 先加一个 state token 且 ar_mask 取 True，再加动作段又取一次 True，于是 π0 是三块（prefix / state / 动作），π0.5 是两块（prefix / 动作）。分块因果掩码的通用机制与三条设计理由见 π0 专题子页 ①，本页不重讲。

六、时间步注入：从拼接到 adaRMSNorm

两种做法的确切形式

π0 的做法是在进入 Transformer 之前把时间步混进 token 表示：

\[\text{token}_k \;=\; \mathrm{MLP}\Big(\big[\,W_{a}\,a^{\tau}_{k}\;;\;\phi(\tau)\,\big]\Big), \qquad k = 1,\dots,H\]

也就是把时间嵌入沿特征维复制 H 份、与每个动作 token 拼接，再过 action_time_mlp_in（输入宽度是 2 × width）、swish、action_time_mlp_out。

π0.5 改成条件调制。论文 Appendix E 给出时间步 MLP 的形式：

\[c(\tau) \;=\; \mathrm{swish}\Big(W_2\cdot \mathrm{swish}\big(W_1\cdot \phi(\tau)\big)\Big), \qquad W_1, W_2 \in \mathbb{R}^{w\times w}\]

openpi 的 embed_suffix 与之逐字对应：time_mlp_in → swish → time_mlp_out → swish，产物作为 adarms_cond 传给主干。动作 token 本身则只过一个线性层 action_in_proj，不与时间拼接。

然后在动作专家的每一层，c(\tau) 通过自适应 RMSNorm 起作用。src/openpi/models/gemma.py 的实现是：

\[[\,\text{scale};\ \text{shift};\ \text{gate}\,] \;=\; W_{\text{mod}}\, c(\tau), \qquad \hat{x} \;=\; \mathrm{RMSNorm}(x)\cdot\big(1+\text{scale}\big) + \text{shift}\]

而 gate 不作用在归一化上，它作用在残差分支上：

def _gated_residual(x, y, gate):
    if gate is None:
        return x + y
    return x + y * gate

每个 Block 里取两次：一次在 pre_attention_norm（自注意力子层之前），一次在 pre_ffw_norm（前馈子层之前），各自产出一份 gate 用于对应子层的残差。整条注入通路画出来是这样：

其一，调制参数是逐层独立的，不是全模型共享一份。 gemma.py 里 18 层由 nn.scan 生成，variable_axes 取 {"params": 0}，意味着参数沿层数轴堆叠、每层各有一份。于是动作专家一共有 \(18 \times 2 = 36\) 组 scale/shift/gate，另加最终归一化 final_norm 的一组（它同样接收 adarms_cond，但代码取返回值的第 0 项，丢弃了它的 gate，只用 scale 与 shift）。

其二，gate 的落点不在归一化上而在残差加法上。这个区别看起来细微，却是下一节那个结论的全部来源。

为什么要这样改

角度 拼接方案（π0） 调制方案（π0.5）

底层理由在于流匹配本身：不同 τ 上网络面对的输入分布差异极大。 \(\tau\) 接近噪声端时输入几乎是纯高斯，接近数据端时输入几乎就是真实动作。要用同一组权重覆盖整条路径，网络必须能按 \(\tau\) 切换行为。归一化层的 scale/shift 恰好是「按条件重标定整层激活分布」的最小手段——这套构造来自 DiT 的 adaLN，π0.5 把它从扩散 Transformer 搬到了动作专家上。

同样要如实说明：论文没有给出 adaRMSNorm 与拼接方案的单变量消融。因此「它提供了更深层、更显式的时间步条件化」是可核验的结构事实，但不能声称论文已证明它独立贡献了多少泛化提升。

七、零初始化：动作专家的 Transformer 块从恒等映射起步

这一点需要精确到“哪一部分恒等”。零初始化作用于每个自适应 RMSNorm 产生的 scale、shift 与 gate，并不把整个端到端动作专家置零或变成恒等函数。

调制矩阵 \(W_{\text{mod}}\) 的实现是：

modulation = nn.Dense(x.shape[-1] * 3, kernel_init=nn.initializers.zeros, dtype=dtype)(cond)
scale, shift, gate = jnp.split(modulation[:, None, :], 3, axis=-1)

kernel_init 取 zeros，偏置默认也是零初始化，因此在训练第 0 步：

\[\text{scale} = \text{shift} = \text{gate} = 0\]

代入上面两式：

  • 归一化退化为 \(\hat{x} = \mathrm{RMSNorm}(x)\cdot(1+0)+0 = \mathrm{RMSNorm}(x)\)，与普通 RMSNorm 一致；
  • 残差退化为 \(x + y\cdot 0 = x\)，也就是该子层的输出被完全丢弃。

第二条比第一条强得多。它意味着在后训练第 0 步，动作专家的每一个注意力残差分支与前馈残差分支都被旁路，因此 18 个 Transformer 块的堆栈对动作流是恒等映射。不过，端到端动作专家并非恒等：action_in_proj、时间条件 MLP、最终 RMSNorm 与 action_out_proj 仍然执行。最终调制头的 scale/shift 为零时，最终归一化退化为普通 RMSNorm；它不是恒等运算。

由此可确认的是：随机初始化的注意力与前馈分支在第 0 步不会写回残差流，随后随着 gate 学习而逐步接入；但输入/输出投影仍是随机初始化并参与计算，因此不能说“随机权重根本不参与计算”。论文 Section IV-D 只陈述动作专家在后训练开始时随机初始化，没有把零初始化明确写成作者采用随机初始化的原因；这里给出的是源码机制解释，不是论文已经验证的因果结论。

这条只在 pi05=True 时成立。π0 分支的 adarms_cond 为 None，RMSNorm 走普通分支、返回的 gate 是 None，_gated_residual 退化成 x + y——π0 的 Transformer 块没有这种由零 gate 造成的恒等起点。

这里要把事实与推论分开。论文 V-D 陈述的事实是「π0 始终使用动作专家」（π0 always uses the action expert）；论文并没有说 π0 之所以不能推迟引入动作专家，是因为缺少这个恒等起点。本页能确证的结构事实是：零 gate 屏蔽了动作专家各层随机注意力/前馈更新，并不屏蔽整个动作预测路径，也不能据此保证训练“一定不会崩”。至于 π0 的设计为何如此，论文未述，本站不推测。

归属于哪一点差异 涉及的模块 性质
差异一：状态从连续 suffix 迁到离散 prefix 状态离散化、prompt 拼接 改动（都在数据侧，模型代码不变）

这个计数的口径需要说明，否则会含糊。上表按职能分行，不是按源码对象分行——「状态离散化」与「prompt 拼接」同属 PaligemmaTokenizer.tokenize 一个函数，按源码对象算则是一个。按职能算是「17 中有 6 个不同」，按源码对象算是「16 中有 5 个不同」。两种算法的结论一致：改动集中在状态表示与时间步条件化两处，主干未动。

另外两行的「新增」也需限定：RMSNorm 与 _gated_residual 这两个函数本身两个分支共用，只是 π0 下 cond 与 gate 恒为 None、分别退化为普通 RMSNorm 与普通残差。说它们是「π0.5 新增」，指的是这条通路在 π0.5 才被启用，不是说源码里多了两个函数。

9.3 放大一层：视觉编码器内部

上面两小节把视觉编码器整个画成了一个方框。但「一张 224×224 的图怎么变成 256 个 token」（三路相机合起来才是 prefix 里的 768 个），是整条链路里唯一一处分辨率与 token 数直接挂钩的地方，值得单独拆开。

先说归属：这一整节讲的模块，π0.5 一个都没有改。视觉编码器完全继承自 π0，而 π0 这一侧又原样来自 PaliGemma —— 包括下面要讲的 pool_type="none" 这个关键选择。本节之所以仍然展开，是因为分辨率 → token 数 → prefix 长度 → KV cache 这条链路的起点在这里，而 §9.1 与 §9.2 都只把它画成一个方框。视觉侧本身的原理不在本专题重讲，见 π0 · 网络架构与双专家。

这一小节与 §9.1 的关系。§9.1 那张图里「SigLIP So400m/14 → pool_type=none → 256×2048」这一个方框，展开来就是本小节的七行。两处的数字必须能对上：每路 256、三路 768、加 200 语言 token 得 968，这个 968 贯穿 §9.1、§10 的形状追踪与 §2 的 KV cache 账。

一个容易被忽略的连锁关系：图像分辨率直接决定 KV cache 大小。token 数是 \((224 / 14)^2 = 256\)，若把输入分辨率提到 448，token 数变成 \((448/14)^2 = 1024\)，三路就是 3072，prefix 长度从 968 涨到 3272——§2 里算过的 KV cache 会按同一比例放大。

但这件事不是改个数字就能做的。分辨率在 openpi 里由 models/model.py 的 IMAGE_RESOLUTION = (224, 224) 定下，它经 Pi0Config.inputs_spec 进入 fake_obs，再由 img.lazy_init 把位置嵌入的形状固定为 (1, 256, 1152)。换成 448 之后这份预训练的位置嵌入就对不上了，必须插值或重训。也就是说，分辨率不是一个可以自由调的推理期参数，而是与预训练权重绑定的结构常量。

π0.5 论文与 openpi 都没有做过分辨率消融，以上只陈述这条结构性依赖与它的约束，不对「提高分辨率是否更好」下任何判断。
