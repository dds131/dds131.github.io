知识库 · 机器人模仿学习与 VLA · RTC · Training-Time RTC
  • 必读前驱：先完成 RTC Foundations，能够用绝对 tick、Action ABI 与 authority epoch 定义部署可得 prefix。
  • 范围：本页只拥有训练样本、逐 Token 时间、后缀 Loss、checkpoint capability 与 trained sampler；训练平台配方、异步队列和安全执行不在本页。
  • 流程边界：页面不运行训练、模型、仿真或机器人，不给出真实路径、账户、设备参数或可执行命令，不上传，也不自动备份。

Training-Time RTC 在训练时随机模拟 delay，把将由旧块执行的动作 prefix 作为干净条件，只学习生成 postfix；推理时因此不需要 Guided VJP，但必须使用学过该条件接口的兼容 checkpoint。

  • 构造每样本不同 delay、三轴清晰且无 future leakage 的训练 batch。
  • 区分 prefix/postfix、padding/channel mask 与四种 Loss 归一化口径。
  • 用 capability manifest 验证 trained checkpoint，并把 proposal 交给 Runtime 而非直接 dispatch。

Training-Time 分支：把 prefix 条件移到训练

四张方法边界卡

Clean Prefix

prefix 直接位于动作端。训练来自 ground truth，部署来自 actual committed/dispatched 动作；二者存在 exposure gap。

Per-Token Time

同一 chunk 内 prefix 时间为 1，postfix 时间为基础 tau。模型接口必须支持 [B,H] 时间语义。

Postfix Loss

prefix 只作条件，不参与预测误差；仍须与 dataset validity、padding 和 action-channel mask 合成。

Trained Mode

在线不做 Guided VJP，但它不是普通 checkpoint 的运行时开关，也不代表整个系统零额外成本。

相比基础 Flow 的三个改动

  1. 每个样本采样训练 delay d_train_b，让一段动作成为部署时可获得的条件。
  2. 为动作时间轴构造 tau_token[B,H]：prefix 置 1，postfix 保留基础 Flow 时间。
  3. Loss 只监督有效 postfix，并把 mask、广播轴和分母口径写入 manifest。

模型参数仍通过基础训练器常规反向传播更新；方法没有发明新 optimizer，也不要求额外训练一个独立 RTC 网络。但输入接口、time embedding broadcast、batch collator、Loss 和 checkpoint capability 都发生了可验证变化，不能概括成“架构完全不改”。

与 Guided 平行，不是升级链

Guided 用既有兼容 iterative policy 在推理期做 VJP，Training-Time 则先训练 prefix/delay conditioning。它们共享 Foundations 的时间与动作 contract，但不共享 checkpoint 要求。Training-Time 不是 Guided 的“下一代”，Guided 也不是 trained 模式的必需前置；二者从 Foundations 等权分叉，并在 Runtime 以 merge_policy:any 汇合。

“消除 inference-time overhead”只指不再执行 Guided 的 reverse-mode VJP。prefix 对齐、逐 Token 时间、hard overwrite、shape/finite 验证、queue 与 provenance 仍有成本，系统级 latency 仍需测量。

训练条件必须对应部署时真正可得的信息

方法成立的关键不是把数组前几项设成干净动作，而是这些动作在部署时确实已经由旧块提供并被 Runtime/authority 承诺。训练样本若使用未来 demonstration action，却在真实部署的同一时刻尚未可知，就形成 target leakage；离线 Loss 会很好看，在线模型却依赖不存在的条件。每个 prefix 位置都要关联 nominal target tick 和 availability rule。

Training-Time 分支也不自动获得更强 reactivity。它学习在给定 clean prefix 后生成 postfix；prefix 越长，可供新 observation 改变的 horizon 越短。连续性、fresh-observation 反应、任务成功与 safety intervention 必须分开评测。训练 support 覆盖某个 delay 只说明模型见过该条件，不证明闭环一定稳定或安全。

在线不做 VJP 可能降低单次 sampler 计算，但新 checkpoint 的模型结构、time embedding 或前缀处理也可能改变前向成本。编译、memory、prefix overwrite、processor 和 queue latency 都要在相同 measurement boundary 下比较；不能把论文里的算法性省略翻译成“零 RTC 成本”。

这一页最终交付的是训练/推理能力 contract，不是训练配方。具体 batch size、learning rate、epoch、device mesh、checkpoint path 与机器人参数必须由项目自己的训练和部署文档拥有，并有独立风险审查。

训练样本：干净 prefix 与带噪 postfix

Batch 轴、动作轴和通道轴先分清

训练动作 A 与噪声 epsilon 的 shape 都是 [B,H,M]：B 是 batch，H 是动作时间，M 是动作通道。基础 Flow 时间 tau 为 [B]，每样本模拟 delay d_train 为 [B] integer。任何 reshape、broadcast 或 gather 都要标明影响哪一轴。

对每个样本 b：

\[P_{b,i}=\mathbf 1[i<d_b], \qquad Q_{b,i}=\neg P_{b,i}.\]

其中 P/Q shape 为 [B,H]。prefix、postfix 与 overlap 不同：prefix 是新块局部 [0,d_train)；postfix 是 [d_train,H)；overlap 是 Foundations 中按绝对 tick 得到的旧/新块共同区域，Training-Time 方法不会自动把整个 overlap 都作为条件。

逐 Token 时间和输入构造

\[\tau_{b,i}^{\mathrm{token}} = \begin{cases} 1,&i<d_b,\\ \tau_b,&i\ge d_b, \end{cases}\] \[X_{b,i,m} = (1-\tau_{b,i}^{\mathrm{token}})\epsilon_{b,i,m} + \tau_{b,i}^{\mathrm{token}}A_{b,i,m}.\]

因此 prefix 恰为 clean action X=A，postfix 留在普通 Flow 路径。训练时的 clean prefix 来自 ground truth；部署时来自旧 policy 的 committed/dispatched 动作，可能带模型误差、safety rewrite、controller clipping 与状态偏差。二者不能被称为同一分布。

Mask 合成顺序与空样本拒绝

D_valid[B,H] 表示数据时刻是否真实存在，C_valid[B,M] 或 [M] 表示动作通道是否有效。最终元素 mask 为：

\[L_{\mathrm{mask},b,i,m} = Q_{b,i}\land D_{\mathrm{valid},b,i}\land C_{\mathrm{valid},b,m}.\]

prefix mask 不能替代 padding mask；padding 也不能被当成“已知前缀”。组合前检查 shape/dtype，组合后计算每样本与全 batch 的有效 postfix 时刻/元素计数。分母为零的样本或 batch 返回 typed data error，不能加 epsilon 掩盖数据错误。

Collator 输出要可逆到单样本事实

Batch collator 常把可变长度样本 pad 到共同 H，这里最容易把 d_train、H_valid 和全局 H 混在一起。对每个样本先在未 padding 坐标中验证 0<=d_b<H_valid_b，再 pad A/epsilon/D_valid；prefix/postfix mask 仍按局部有效长度生成。若先按 batch 最大长度采 delay，短样本可能得到空 postfix。

记录 sample_id -> batch row、原始长度、采样 delay、mask digest 与随机数流，使任一 batch row 都能脱离 batch 复算。数据增强、subsequence crop 或 time shift 若改变有效长度，必须发生在 delay sampling 前或明确重算 mask；不能裁剪动作后继续沿用旧 d_train。

三轴 permutation tests 能抓住静默广播错误：交换 batch row 时所有同属记录一起交换；交换动作时间时需要同步交换 action、token time 与 time mask；交换 channel 时同步交换 action 与 channel validity，但不改变 prefix boundary。若只交换一个 tensor 仍不报错，说明 contract 检查不足。

训练日志默认保存 digest、计数和受控 artifact reference，不复制敏感视频、语言指令或完整动作。需要抽样可视化时使用经过授权、脱敏并与数据 release 绑定的制品，页面不提供实际数据导出路径。

  sample_id: "<opaque>"
  chunk_shape: "[B,H,M]"
  d_train: "<int-per-example>"
  prefix_mask_ref: "<artifact-ref>"

部署可得性与 future leakage

训练 prefix 中的每个位置都必须在对应部署时刻可由旧块 actual/committed provenance 提供。不能把新 observation 后才知道的 future action、完整示范后缀、未来状态或任务结果塞进条件。泄漏测试应基于事件与绝对 tick，而不只看数组 index。

训练 ground-truth prefix 比部署的 policy-generated prefix 更干净，会形成 exposure gap。可选的扰动、rollout prefix、safety-modified prefix 或混合数据都属于方法迁移，必须有版本化分布与单独实验；不能把它们写成论文默认。任何增强都不能破坏 Action ABI 或让训练看到部署不可获得的信息。

Exposure gap 要拆成四种来源

第一是数值误差：部署 prefix 来自模型、量化、adapter 与 controller，未必等于 demonstration。第二是状态误差：即使命令相同，机器人反馈状态和 observation 也可能因动力学、延迟或扰动不同。第三是 authority 误差：safety/human/fallback 可能改写旧动作。第四是分布误差：训练 delay、任务、硬件和负载与部署不同。四类 gap 的缓解和 owner 不同，不能只加统一噪声。

若采用 rollout-generated prefix，应记录生成 policy/checkpoint、环境/数据版本、是否经过 safety rewrite、失败样本是否保留，以及 rollout 与监督后缀的因果关系。若使用 teacher action 加人工噪声，要说明噪声空间、相关结构和截断；独立高斯扰动不一定模拟真实 controller 或 policy error。

数据切分也要防跨轨迹泄漏。来自同一 episode 的 prefix/postfix 窗口若被分散到 train 与 validation，会让指标高估泛化；同一机器人 session 的重复片段也可能泄漏环境状态。split manifest 至少绑定 episode、task、robot/config 与时间范围，具体匿名化规则由数据治理文档定义。

prefix 长度与 task phase 可能相关：长 delay 样本如果主要来自复杂场景或 cold-start，简单重采样会同时改变任务分布。delay sampler 应在允许范围内考虑分层或权重记录，报告 q_train(d|context) 是否近似独立，避免把条件偏差误当成 RTC 效果。

逐动作 Token 时间与模型接口

“无需新参数”不等于接口不变

需要分三层描述：参数结构可能复用原网络；输入 shape 从 batch scalar time 扩展为 per-token [B,H]；conditioning 路径必须让不同动作 Token 收到各自 time embedding。若实现把一个 [B] 时间强制广播给所有位置，trained prefix 语义并未实现，即使模型仍能前向。

| 接口项 | 目标 shape | 检查 | | — | — | — | | action/noise/input | [B,H,M] | batch、时间、通道顺序固定 | | base tau | [B] | finite，位于声明区间 | | d_train | [B] integer | 0<=d_b<H_valid_b | | tau_token | [B,H] | prefix=1，postfix=tau_b | | time embedding | [B,H,E] 或等价 | 各 Token 条件不被再次塌缩 | | prefix/postfix mask | [B,H] | 不沿 batch 错播 | | channel validity | [B,M] 或 [M] | 只沿时间轴广播 | | velocity output | [B,H,M] | 与 target、mask 对齐 |

参数兼容性测试

用同一 checkpoint 做三个静态/微型测试：全部 Token 共用相同 time 时，新接口输出应在声明容差内匹配基础接口；改变单个 Token time 时，至少对应 conditioning 路径发生可观测变化；交换 batch 样本或 action index 后，输出按同样 permutation 变化。若模型架构允许跨 Token attention，局部 time 改变可影响其他位置，但不能被完全忽略。

还要验证 dtype/device、padding 位置、编译 shape、不同 H 的支持策略与 mixed precision。checkpoint loader 应检查 capability manifest，而不是看到 tensor keys 能加载就宣称兼容。参数 shape 相同只能说明权重可放入网络，不证明它学过 prefix conditioning。

Time embedding 不能在主干入口后被意外塌缩

一些实现先生成 [B,H,E] time embedding，却在与 observation 融合前做 mean/pool，最终仍退化为单一 batch time。接口测试要在模型内部可观测点确认 Token 差异仍存在，而不只检查输入 tensor shape。若 attention/MLP 通过共享权重处理 Token，差异可以传播，但不能在无声明的 reduction 中消失。

padding Token 的 time 值本身没有训练语义，但必须 finite，并由 D_valid 阻止进入 Loss；attention mask 还要避免 padding 影响有效 Token。RTC prefix mask 不能替代 attention padding mask。两者若合并为同一 bool，模型可能把 clean prefix 当成不可见 padding，从而完全学不到条件。

可变 horizon 有三种策略：固定 H 并 padding、按有限 shape bucket 编译、或显式支持动态 shape。manifest 要声明其中一种及支持集合。把训练过 H=H0 的 checkpoint 直接用于更长 chunk，即使 positional encoding 能运行，也属于 out-of-capability，必须单独验证。

兼容性回归应保存基础模式和 trained 模式的对照：全 Token 同 time、d=0、单 Token time perturbation、batch permutation、time-axis permutation、全 padding rejection 与 mixed precision。每项都有 tolerance 和设备条件；不允许只凭 loss 能下降判定接口正确。

Flow 速度目标与论文符号审计

站内主约定由路径导数决定

本页沿用 tau=0 噪声、tau=1 动作：

\[X^\tau=(1-\tau)\epsilon+\tau A, \qquad \frac{\mathrm dX^\tau}{\mathrm d\tau}=A-\epsilon.\]

因此监督速度 U=A-epsilon，正向 Euler 从 noise 走向 action。prefix Token 处于 tau_token=1，但是否对其计算 target 并不影响 Loss，因为 prefix 被 postfix mask 排除；实现仍应让所有张量 finite，不能用 NaN target 依赖乘零消失。

论文 v2 的内部符号不一致

论文 v2 Equation (2) 的印刷符号与 Equation (1) 路径导数、Algorithm 1 及固定 Kinetix commit 使用的方向不一致。页面把这记录为“同一版本内部不一致”，而不是未经作者确认的勘误定论。复现采用哪一方向，必须同时列路径、target、sampler 更新和固定代码证据。

不能只凭变量名 t、noise 或 velocity 猜方向。其他代码库若用 t=1 噪声、t=0 动作，epsilon-A 可能在其反向参数化下正确；把该符号单独复制到本站正向 tau 约定才会出错。

三项解析测试与 evidence note

  1. 端点：代入 0/1，确认分别得到 noise/action。
  2. 导数：对插值式求导，与 target 完全一致。
  3. 一步方向：常速度解析样本做 Euler，距离 action 端应按预期变化。

Sign 错误会怎样暴露

如果在正向 tau 路径上误用 epsilon-A，最小常速度例子会从动作端反向移动，训练 target 与 sampler update 的方向相冲。实际大模型可能仍因其他实现细节出现 loss 下降，所以“能训练”不是符号正确的证据。端点、解析导数和一步 Euler 测试必须独立于训练曲线存在。

对 per-token time，prefix 处 tau=1 的 target sign 即使被 Loss mask 排除，也会经过前向计算。若实现计算中出现除以 1-tau 等端点表达，prefix 可能生成 inf/NaN 并污染其他 Token。测试要确认被 mask 的位置在 reduce 前仍 finite；不能依赖最后乘零。

代码映射时同时记录 path function、target construction、sampler step、time adapter 与注释。只查看变量 flow 或 velocity 的名字没有证据力。若固定代码与论文新版后来一致，应新建审计版本并保留旧结论，不直接覆盖历史 run 的语义。

公式审计结论使用 scope：paper-v2 + fixed-commit + noise0_action1。换论文版本、commit 或 time convention 后必须重新运行；这个 scope 也进入 checkpoint capability，避免模型与推理器各自采用不同方向却共享同一标签。

后缀 Loss、Mask 与归一化

Elementwise error 与公开实现口径

定义元素误差：

\[L_{\mathrm{raw},b,i,m} = \left(V_{\theta,b,i,m}-U_{b,i,m}\right)^2.\]

论文 Algorithm 1 与固定 Kinetix 实现使用 shape [B,H,1] 的时间 mask，乘法广播到 M，但分母只统计有效动作时刻：

\[\mathcal L_{\mathrm{global\mbox{-}timestep}} = \frac{ \sum_{b,i,m}L_{\mathrm{raw},b,i,m}L_{\mathrm{mask},b,i,m} }{ \sum_{b,i}\left(Q_{b,i}\land D_{\mathrm{valid},b,i}\right) }.\]

若 channel mask 存在，分子会少若干通道，而上述分母未自动调整；因此分母语义、channel handling 与 zero-denominator policy 都必须进入 manifest。

四种不能混称的归一化

| 口径 | 分母 | 样本权重效应 | 备注 | | — | — | — | — | | global valid timestep | 全 batch 有效 postfix 时刻数 | postfix 长的样本贡献更多时刻 | 固定公开实现核心口径 | | per-example timestep | 每样本先除自身有效时刻，再 batch 平均 | 每样本等权 | 空 postfix 样本须拒绝 | | per-element | 有效 postfix 标量元素数 | 动作维变化时尺度更直观 | 与源码相差通道尺度 | | explicit weighted | 另有 sample/time/channel weight | 由声明权重决定 | 属于方法迁移，需单独验证 |

当所有样本的 M 固定且无 channel mask 时，timestep 与 element 均值相差常数 M，但学习率、梯度裁剪和其他 Loss 权重都会受影响，不能说完全等价。改变归一化后必须产生新 training run record，不能仍标成固定实现复现。

用一个两样本 worksheet 复算分母

设 batch 中两个虚构样本的有效 postfix 时刻数分别为 2 和 6，动作维都是 4。global-timestep 分母是 8，分子包含 32 个标量误差；per-element 分母是 32；per-example 则先各除以 2 与 6，再对两样本取平均。若每个标量误差相同，三个 Loss 只差可预测尺度；若误差和 postfix 长度相关，它们的梯度方向也可能不同。

加入 channel mask 后情况更明显：若第一个样本只有 2 个有效通道，global-timestep 分母仍按 2 个时刻统计，等价于降低该样本分子规模；per-element 会按 4 个有效元素统计。哪一种是预期必须由 manifest 决定，不能让 broadcasting 与 reduction API 隐式选择。

Sample weight 应在明确层级应用。若权重针对整条样本，应先完成该样本规定的归一化再乘；若权重针对时间或通道，则进入元素 mask/weight。把 [B] 权重直接广播到 [B,H,M] 后又用未加权分母，会改变整体尺度。每种路径用手工小张量计算 oracle。

Loss report 除总值外还应给有效样本数、postfix 时刻数、元素数、按 delay 分桶的分子/分母、zero/near-zero count 与梯度范数。这样才能区分优化异常、mask bug 和 delay 分布变化，避免只看一个平均标量。

Loss property tests 不依赖大模型

用全零 target/预测、全一固定误差和手写小张量即可验证 reduction。全一误差下，global-timestep Loss 应等于有效通道数的相应和；per-element 应为 1；per-example 每个非空样本的贡献相等。改变无效 padding 或 prefix 位置的 error，结果必须不变；改变任一有效 postfix 元素则按可计算幅度变化。

梯度 oracle 也应覆盖 mask。对线性 V_theta=w*X 的单参数模型，手算不同 normalization 的 dL/dw，再与 autodiff 对照。这样能区分 forward Loss 数值偶然正确、backward broadcasting 却错误的情况。有限差分只用于测试，不能替代正式训练反向传播。

全 padding、全 channel invalid、d=H_valid、非有限 target/prediction、负 sample weight 与非整数 delay 都必须在 reduction 前拒绝。若某个 sample 被过滤，report 要保存过滤原因和原 batch size；不能静默丢弃直到分母非零。

与其他任务 Loss 组合时，先报告各自未加权值、权重、加权值和梯度范数，再求和。RTC postfix Loss 尺度改变会改变多任务平衡；只调 learning rate 不一定能恢复，必须把组合口径写入 training run lineage。

d=0、padding 与空 postfix

d=0 时输入和 mask 语义退化为普通 Flow，但若基础 Loss 用全元素均值，数值尺度仍与 timestep 归一化不同。d_train 必须满足 0<=d_b<H_valid_b，保证每样本至少一个有效 postfix 时刻；所有位置 padding、channel 全无效或合成后分母为零都要拒绝 batch。

Dataset padding、RTC prefix、channel validity、sample weight 各有独立来源。推荐顺序是先验证各 mask shape/dtype，再构造布尔有效集合，再应用显式 float weight，最后计算分子/分母。不能把 NaN error 乘零后期待消失，也不能用小 epsilon 把空 batch 变成零 Loss。

Batch 聚合改变梯度尺度

不同 d_b 让每样本 postfix 长度不同。global 口径会让长 postfix 样本贡献更多 element；per-example 口径则让极短 postfix 样本也与长样本同权，可能放大高 delay 样本。二者都可研究，但要与 delay sampling distribution 一起报告，否则无法知道梯度偏重来自采样频率还是归一化。

梯度路径与记录

梯度只经有效 postfix Loss 返回 policy 参数；prefix 没有直接预测误差，但作为输入条件仍会影响网络表示和 postfix 输出。冻结层、optimizer、learning rate、weight decay、warmup、clip、precision 与随机种子都属于 training run lineage，不能归因为 RTC 方法固定要求。

Delay 支持范围与训练分布

分清训练 support、预测值和实测值

d_train 来自训练分布；d_hat 是部署请求前冻结的预测/保守 bound；d_meas 是结果返回后的实测 tick。三者可以数值相同，却不能共用一个字段。checkpoint capability 声明训练 support 集合，Runtime 用 d_hat 做调用门禁，再用 d_meas 判断实际 valid suffix 与是否 out-of-support。

分布必须写集合，不只写 maximum

固定 Kinetix commit 的一种分布在整数集合 {0,...,D-1} 上对小 delay 指数加权；论文其他示例使用均匀分布。它们是实验/实现选择，不是所有机器人必须照搬的唯一分布。随机整数 API 的 upper bound 可能是 exclusive，自然语言“0 到 D”却容易被读为 inclusive，因此 manifest 直接列 support set 或精确定义 max_delay_exclusive。

| 分布/策略 | 作用 | 风险 | 必须记录 | | — | — | — | — | | uniform support | 每个 delay 等概率 | 可能低估常见小 delay 或长尾 | 精确集合、seed | | exponential-to-small | 小 delay 权重更高 | 长 delay 样本稀少 | 未归一化权重与归一化结果 | | empirical histogram | 拟合观测部署分布 | 受采集偏差与未来漂移影响 | 数据窗口、硬件/负载范围 | | tail-upsampled | 提高长尾覆盖 | 改变平均梯度与任务权重 | upsample 规则与 loss normalization | | curriculum | 逐阶段扩 support | lineage 更复杂 | 每阶段 support、checkpoint parent |

从 wall clock 到 control ticks

训练 support 必须绑定 control rate、rounding policy、measurement boundary 与 hardware/load mode。同一个毫秒延迟在不同控制频率下对应不同 tick；固定 D 不能脱离这些字段迁移。实际跨 tick 优先从 Foundations 事件 trace 得到，不用平均频率替代每次观测。

训练/验证/测试 delay 数据要防止信息泄漏。选择 q_train(d) 可使用训练期已批准的部署画像，但最终评测窗口与未来 incident 不应反向调参。若部署硬件或负载改变，先标记 distribution shift，再决定追加训练或拒绝，不把新直方图静默并入旧 checkpoint claim。

Out-of-support 是显式状态

d_hat 不在 support 时，trained mode 不应启动并希望模型外推；Runtime 可以选择 compatible Guided、fallback 或 safe state，但策略由部署 contract 决定。d_meas 事后越界时，本次 proposal 即使 finite 也要标记 out-of-support，不能把任务偶然成功当成 capability 扩展证据。

Support 内也不等于分布内

一个 delay 可能位于 support 集合，却在训练中概率极低；单纯 range check 看不出这一点。capability manifest 应同时提供 support 与 probability/bin count，Runtime/评测可标记 in_support_low_evidence。这不是立即拒绝的通用规则，但必须让 owner 看到模型正在使用稀疏证据区域。

support 还受 H、control rate、task/hardware mode 与 measurement boundary 约束。d=4 在两个控制率下代表不同 wall-clock 时长，在不同 H 下也留下不同 postfix。迁移时不能只复制整数集合；要验证整个 delay contract 和剩余有效 horizon。

选择 q_train 的证据顺序

先从已批准的系统 trace 得到 delay 分解和置信区间，再按目标 ODD、硬件、负载、warm/cold 模式分层；随后确定训练要覆盖的 support 与每个 bucket 最低证据量；最后才选择 uniform、empirical、tail upsample 或 curriculum。不能先挑一个方便分布，再只收集能证明它合理的数据。

经验直方图并非天然最佳。常见状态可能占满训练预算，让关键长尾几乎不出现；过度上采样长尾又会降低普通状态质量。decision record 应写目标函数：拟合频率、保证最小 coverage、强调 deadline 附近或分阶段扩展，并与 chosen Loss normalization 一起审查。

每个 delay bucket 至少报告样本数、task/robot/context 覆盖、prefix/postfix 长度、有效元素数和 validation 指标。只有样本数没有内容多样性，可能是同一 episode 的重复窗口；只有平均指标则会掩盖某个 delay 彻底失败。

重新训练扩大 support 时，旧 checkpoint capability 不自动升级。新 run 继承 parent，但产生新 support hash、数据 lineage、评测与 release。Runtime allowlist 只有在新 bundle 完成验证后才切换，并保留旧 bundle 作为可回滚制品。

部署漂移通过版本化窗口记录：p50/p95/p99/max、deadline miss、cold/warm state、queue load 与 mode。若新尾部超出训练范围，先把 capability claim 缩小或门禁升级，再决定扩数据和继续训练。不能用线上失败样本自动回灌而跳过隐私、数据质量和 train/test 隔离。

out-of-support 的事件仍要进入 incident/metrics，但不得把 rejected proposal 当成模型预测质量样本。否则后续统计会混入从未执行的候选或把 fallback 成功归给 trained policy。评测表必须保留 branch、gate decision 和最终 authority。

失败、取消、恢复训练与继续微调都产生新记录，不原地改写已发布 manifest。训练成功也只证明 run 结束，不证明闭环质量；capability status 要结合接口测试、support gate 与评测证据。

Lineage 必须能回答五个问题

审阅者应能从 checkpoint 反查：它从哪个 parent 开始；使用哪版数据与 split；采用哪种 sample/time/Loss contract；在哪个 code/processor/optimizer 环境训练；哪些评测支持当前 capability。任何一项 unknown 都应保留，不用模型文件名、目录时间或人工记忆补全。

resume 与 fine-tune 不同。resume 继续同一 run 的 optimizer/scheduler 状态，也要记录中断点、数据游标和环境变化；fine-tune 创建新目标或数据分布，必须是新 lineage 节点。若从普通 checkpoint 开始训练 prefix capability，parent 本身不能被回写成 trained-capable。

发布 checkpoint 时把权重 hash、processor、normalization、Action ABI、time convention、support 与 Loss normalization 绑定为不可变 bundle。只替换 processor 或统计量就会改变模型输入语义，应创建新 release，而不是保持相同 capability hash。

回滚选择一个已验证旧 bundle，不通过删除新文件或覆盖 latest 指针来隐藏失败 run。实验、候选与正式 release 使用不同状态；只有正式 release 才能进入部署 allowlist，且仍需 Runtime contract 检查。

Trained 推理与 Prefix 重写

Runtime 输入必须来自实际旧动作

trained sampler 读取 Foundations handoff：request/observation、old actual action reference、old/new anchor、Action ABI、normalization、authority epoch、H/M/s_run/d_hat、checkpoint capability 与 contract hash。旧块先按绝对 tick join 到新块坐标，只有有效 [0,d_hat) prefix 被使用；不能把未经处理的完整旧块按局部 index 直接切片。

训练用 ground truth prefix，部署用 policy-generated committed/dispatched prefix。若 safety/controller 改写动作，target 应引用修改后 record；若 authority epoch 变化、clock session 不明、ABI/normalization 不匹配或 d_hat 超 support，返回 typed rejection。

每步重新覆盖 prefix 的伪代码

function TrainedSample(policy, observation, handoff, rng):
    require checkpoint_capability verified and compatible
    require contract/hash, action ABI, normalization and authority current
    require d_hat inside checkpoint delay support
    prefix, validity, source_ticks = align_actual_actions_by_absolute_tick(handoff)
    require valid prefix exactly covers [0,d_hat)

    X = normal(rng, shape=[H,M], dtype=policy.sample_dtype)
    for k in 0 .. n_flow-1:
        tau = time_grid[k]
        X[0:d_hat] = prefix[0:d_hat]
        tau_token[:] = tau
        tau_token[0:d_hat] = 1
        V = policy_velocity(observation, X, tau_token)
        require shape(V)=[H,M] and all_finite(V)
        X = X + step_size[k] * V
        record metadata-only step trace

    if output_contract_requires_exact_prefix:
        X[0:d_hat] = prefix[0:d_hat]
    require shape(X)=[H,M] and all_finite(X)
    return TrainedProposal(branch="training_time", contract_hash=handoff.contract_hash,
                           checkpoint_capability_hash=capability_hash,
                           delay_support_hash=support_hash,
                           action_chunk_ref=artifact_ref)

每次 policy evaluation 前覆盖 prefix，确保模型看到 clean condition；Euler update 仍可能改动全部位置，所以最后一步之后 prefix 未必逐元素不变。RTC Runtime 会跳过已过期 prefix；若下游 API 要求完整返回块的 prefix 精确不变，可以在循环后再覆盖，但必须标作 output contract 增强，不改称论文核心算法。

每步 trace 验证 hard condition 真的存在

sampler step 至少记录 tau、prefix overwrite 前后差异、token-time digest、velocity/postfix norm、finite status 与 capability/contract hash。prefix overwrite 后，X[0:d_hat] 必须在容差内等于 source；policy evaluation 后可以产生全长 velocity，但下一 step 前再次覆盖。这样能定位 prefix 漂移发生在模型 update、adapter 还是 overwrite 漏失。

不建议默认记录完整 action payload；digest、范围、范数和受控 artifact reference 足以做多数一致性审计。若为数值复现保存中间 tensor，必须绑定数据治理、保留期限和访问权限，不能写入普通应用日志。失败 trace 也要保存首个异常 step，而不是只留下最终 non-finite。

time grid、step size、solver 与 n_flow 作为 sampler capability 一起保存。即使 checkpoint 支持 per-token time，更换 solver 也可能改变分布与 prefix 最终漂移；不能把同一 trained checkpoint 在任意积分器上的行为都归入原验证范围。

输出 closure 检查包括 shape [H,M]、所有元素 finite、branch、checkpoint/support hash、authority epoch、prefix source digest 和 step count。任一项失败，整块 rejected；不删掉异常通道继续返回，也不把最后一个 finite 中间状态冒充完成结果。

输出仍是 proposal/postfix

Runtime 在 ready 后用 d_meas、merge 时刻、queue committed boundary、authority 与 safety gate 重算 valid suffix。d_meas 可能大于 d_hat，导致更多位置过期；trained conditioning 不替代 stale check，也不保证 support 内 proposal 一定可派发。

status=rejected 时 action ref 必须为空。取消、resource limit、non-finite、capability mismatch、alignment gap、authority stale 与 out-of-support 分别使用稳定 failure code；算法层不自动 retry，也不决定 hold/repeat/stop。

Prefix 重写有三个常见误区

第一，只在循环开始前覆盖一次。首个 Euler update 会改动 prefix，后续模型看到的不再是 clean condition；正确流程是在每次 policy evaluation 前重写。第二，把 prefix time 设成基础 tau，这让模型把已知动作当成带噪 Token。第三，把完整 old chunk 写入 [0,d_hat) 而不做绝对 tick join，可能把错误时刻的动作当条件。

最后一次 update 后是否再覆盖取决于 output contract。RTC 通常不会派发过期 prefix，所以数值漂移不一定影响执行；但下游若计算完整块 hash、continuity metric 或期待 exact prefix，循环后覆盖能避免歧义。无论选择哪种，都在 sampler record 写 final_prefix_overwrite=true/false，不能依赖调用方猜测。

d_meas>d_hat 时，训练条件只覆盖较短 prefix，而 Runtime 实际还要跳过更多位置。只要剩余 suffix 有效且 support/contract 允许，proposal 可能仍可使用；若 d_meas>=H 或越过训练/部署门禁，则 reject。算法不能在结果返回后重新生成更长 prefix 而忽略 deadline 与新 observation。

取消与 supersession 在 step 边界检查。旧 request 被新 observation 取代后，即使计算完成也返回 stale，不进入 merge；中间 sample 仅作受控诊断。自动 retry 要创建新 request、冻结新 contract 和 authority，不能复用旧 proposal ID。

只有既有 checkpoint 且无法重训练时，Guided 更可能可行；能控制训练、部署 delay 有稳定证据、吞吐又不允许 VJP 时，Training-Time 值得评估。两者都需要同一 Foundations contract 和 Runtime，不应以“新/旧”“高级/初级”排序。

切换分支必须改变 capability 证据

同一 UI 里的 mode toggle 不能替代算法证据。切到 trained 时必须选择有 prefix capability 的 checkpoint、support 和 Loss lineage；切到 guided 时要验证 iterative sampler、VJP、mask 与 coefficient。共同的 Action ABI/Runtime contract 可以复用，但分支特有字段不能残留或静默默认。

比较两条路线要固定 observation、task、controller、safety、Action ABI、solver 与基础 checkpoint lineage，并同时测 model compute、VJP/overwrite、end-to-end usable latency、valid suffix、task outcome 和 safety intervention。只比 forward time 会漏掉 queue 与验证；只比成功率会漏掉额外计算和风险。

两条路线都可失败。Guided 可能数值不稳定或太慢；trained 可能 exposure gap、support drift 或 checkpoint 不兼容。Runtime 的 fallback 图应基于已验证能力与当前状态，而不是把另一分支假定为永远可用；两者都不可用时应进入声明的 safe path。

从 request 到 feedback 的状态链

request created 时冻结 observation、d_hat、checkpoint capability、support、contract 和 authority；sampler started/ready 分别记录实际开始与结果时刻；Runtime validated/merge committed 再决定 valid suffix；dispatch/ack/feedback 由 controller 事件完成。任何阶段都不能用后一个状态回写覆盖前一个状态。

ready 之前若 authority、checkpoint allowlist、processor 或 Action ABI 版本变化，job 标 stale。ready 之后若 d_meas、queue committed boundary 或 safety gate 使 suffix 无效，proposal 标 rejected/expired。两种拒绝原因不同：前者说明 request 上下文失效，后者说明结果不再可用；监控和重试策略也应区分。

若 Runtime 选择 alternate Guided branch 或 fallback，新 request 使用新 branch record 与 proposal ID，不能把 trained failure code 丢掉，也不能让 fallback 成功覆盖原失败。事件链保留最终 authority，便于 Experiments 按“提出者、接纳者、执行者”归因。

feedback 进入下一轮 prefix provenance 时，需要说明它是 command echo、controller state 还是物理传感状态。它们时延与语义不同，不能统一命名 executed action。缺少可对齐反馈时，使用 committed/dispatched source 并保留 evidence scope，不伪造更强事实。

本页交付 sample contract、token-time/mask worksheet、sign audit、Loss normalization record、delay support manifest、training lineage、checkpoint capability、trained sampler record 与 Runtime handoff。每份制品都有版本、hash、owner、证据 scope 与 unknown/rejected 状态；不能只交一个 checkpoint 文件。

审阅者随机选择一个 d=0、一个中间 delay、一个接近 support 上界和一个非法样本，手算 prefix/postfix、token time、有效 mask 与 Loss 分母；再从 ready proposal 反查 checkpoint、run、数据 release 和 source prefix。任何链条依赖口头解释、临时 notebook 状态或未保存配置，都不能称为可复现。

可安全复用的是符号、schema、检查表和证据边界；不可直接复用的是论文/实现示例 delay、训练 epoch、optimizer、控制率或设备阈值。后续构建若暴露公式渲染、窄屏、SVG ID 或链接问题，只修正展示与 contract 一致性，不扩展到实际训练或真机执行。

最终结论必须同时列出适用范围与失败出口：checkpoint 只在声明的 Action ABI、时间方向、horizon、delay support、processor 和 evaluation protocol 下具备 trained capability；超出任一范围时状态回到 unknown 或 rejected，由 Runtime 选择已验证替代路线。不能因为文件可加载、单个离线 Loss 下降或一次任务成功，就扩大 capability claim。所有待定项保留到后续证据补齐，不用默认值填空。

交付者还需明确谁有权改变 support、发布新 checkpoint、批准部署 allowlist 和触发回滚；这些 owner 与审批记录属于 capability 的一部分。缺少责任人或回滚制品时，即使数学与静态测试全部通过，也只能停留在研究候选状态，不能进入受控部署路径。 所有范围缺口、失败样本、未知状态和待验证假设必须保持可见，并进入下一轮复核记录。

发布前的四层复核

数据层检查 split、future leakage、padding/channel validity、delay sampling 与 exposure gap；数学层检查 token time、path/target sign、Mask 与 Loss 分母；制品层检查 checkpoint lineage、processor/ABI/normalization 和 capability；系统层检查 d_hat/d_meas、authority、Runtime handoff 与 Safety。四层分别记录，不用一个“训练通过”勾号代替。

结论状态使用 verified、verified_with_scope、pending_version_lock、not_applicable 与 rejected。论文方法可在 v2 scope 下 verified；LeRobot main 行为只能 pending_version_lock；没有真实测量的系统吞吐必须 pending，不能因静态公式正确而写成“实时”。

负面空间也要审阅：没有把 Kinetix 数值写成通用配方，没有把 ordinary checkpoint 当 trained，没有把 d=0 Loss 称为数值完全相同，没有把 support 内写成安全保证，没有把 proposal 写成 executed，也没有提供真实命令、账号、路径、端口或设备参数。

交付报告列源 hash、覆盖稿 hash、正式 patch hash、专页 checker、全量回归和未完成的构建/浏览器验收。所有 unknown/rejected/pending 项保持可见，不为追求全绿删去失败样本、缩小检查范围或改写来源结论。
