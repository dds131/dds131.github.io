“训练轮次”采用什么口径

两份日志最可靠的共同口径是 optimizer step/update：

  • JAX：75,610 个 optimizer steps；
  • PyTorch：100,000 个 optimizer updates；
  • 两者 global batch 都是 256；
  • 页面不补写统一 epoch，因为数据采样、重复方式和日志没有形成可直接等价的 epoch 证据。

若面试官追问 epoch，应先给出数据集有效样本定义、采样器和每步消费样本数，再换算；不能用 raw frames 直接除以 batch。

三、JAX 是否更快

聚合吞吐比：

[ \frac{45.10}{21.67}\approx2.08. ]

但 GPU 数量也是 8 对 4，正好相差 2 倍。按 GPU 数量粗归一：

[ \frac{5.64}{5.42}\approx1.041, ]

即约 4.1%。此外混合精度、实现、编译、并行方式、GPU 拓扑、运行日期和系统负载并未锁定。

正确结论：现有条件下，8-GPU JAX 聚合吞吐为 45.10 samples/s，4-GPU PyTorch 为 21.67 samples/s；不能据此声称“JAX 框架本身快 2.08 倍”。

四、训练指标怎样回答

  • loss 下降说明优化过程收敛，但不能替代真机成功率。
  • nonfinite_skip=0 说明所记录的 JAX 运行没有触发非有限值跳步，不是所有 checkpoint 都可安全部署。
  • step time 分位数描述训练性能长尾，不能与 182.6 ms 的动作块推理耗时混用。
  • 训练完成量按 optimizer step 统一，不能把 PyTorch micro-step 和 optimizer update 混算。
  • checkpoint 选择还需要旧任务保持集、新失败保持集、部署固定输入回归和真机 trial；这些结果当前缺失。

五、50 步动作窗口和尾部 padding

现有数据契约使用动作窗口 (H=50)。若短 episode 长度 (T=60)，不含 padding 的合法起点只有：

[ T-H+1=11. ]

受 padding 影响的起点比例为 (49/60\approx81.7\%)，所有窗口位置中的 padding 比例为 (49/120\approx40.8\%)。因此聚合时应比较有效窗口数，而不是只比较 raw frames；正确做法是过滤非法起点或证明 mask 被损失函数消费，不能简单裁掉文件尾部后破坏图像、状态和动作对齐。

六、DAgger 量化边界

待验证 当前没有同等级的 DAgger 纠正会话数据包、接管频率、保存率、再训练前后成功率和旧技能保持率。本页只展示基础数据管线与基础训练历史，不把它们包装成 DAgger 训练结果。

七、等条件训练基准应怎样补

未来比较必须锁定：

  1. 同一数据 manifest、模型结构与可训练参数；
  2. 同一 dtype、global batch、GPU 数量和训练步数；
  3. 首次编译时间与预热后 samples/s 分开；
  4. 峰值显存、loss/梯度一致性和端到端时间；
  5. JAX→PyTorch 权重转换耗时与固定输入动作误差；
  6. checkpoint、配置、norm、数据集和 trial 的血缘绑定。
面试一句话：我把训练轮次统一到 optimizer step：JAX 8 卡完成 75,610 步、119 小时，PyTorch 4 卡完成 100,000 次更新、328 小时；聚合吞吐差 2.08 倍，但卡数也差 2 倍，所以只报告条件和结果，不做框架因果结论。
