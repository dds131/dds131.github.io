先证明接口满足算法前提，再复用开源代码

仓库名不能证明数学接口兼容。可靠的集成要同时锁定 commit、模型、动作头、算法和环境，并让不满足条件的组合在训练前显式失败。

本页定位：这是工程映射与验收指南，不是可直接复制运行的安装脚本。仓库能力按 2026-10-10 查阅到的官方 README、代码和项目页整理；上游变化后必须重新核对锁定版本。

一、先把“支持”分成三个等级

  • 直接复用：上游已经提供对应模型、算法或运行路径；仍要锁 commit 并复现实验。
  • 经 Adapter 复用：数学结构或调度组件可借鉴，但数据、动作、环境或安全语义必须转换。
  • 自行实现与验证：上游没有提供这一职责，不能用项目名或相似函数名代替。
项目 截至审校日的官方能力快照 在 RLHF-VLA 中的合理位置 不能据此默认成立
OpenVLA 原始离散 action-token VLA；官方仓库还列出 FAST tokenizer 与 OFT continuous-action 路径 基座、预处理、微调、推理与特定 action head 的 adapter 所有 checkpoint 都有同一种动作表示；现成人类反馈、PPO 或真机安全闭环
OpenPI π₀、π₀.₅ 为 flow-based VLA；π₀-FAST 为自回归 VLA。官方仓库当前说明 π₀.₅ 训练/推理仅支持 flow-matching head Flow 或 FAST 基座、LeRobot 数据映射、训练/推理与 policy server 整个仓库都能提供 token log-prob；Flow Matching loss 就是策略 log-prob
APO 面向自回归 VLA 的人类辅助 Action Preference Optimization 官方实现 binary desirability、接管/纠正类别、平衡采样和自适应加权的参考实现 普通 chosen/rejected pair；通用 PPO/Flow/在线 RL 平台
GRAPE 基于 OpenVLA 的 GCPG 与 trajectory-wise preference optimization 同初态轨迹配对、TPO-LoRA、迭代 rollout 的参考实现 偏好一定来自人；任意 batch/多机配置都已支持
OpenRLHF 面向 LLM/VLM 与 agentic RL 的 RM、DPO、PPO 等训练和分布式编排 actor/reference/reward/critic 生命周期、Ray/训练编排思想，经 adapter 使用 机器人控制时钟、环境 step、proprio、action chunk、安全接管已原生对齐
RLinf 官方列出 embodied/VLA RL、在线与真实机器人路径，并持续增加 π₀/π₀.₅、π₀-FAST、SAC-Flow 等特定组合 rollout、资源调度、特定模型—算法—环境组合的直接或适配式复用 任意 VLA、任意反馈算法、任意机器人即插即用；完整人工标注产品
Uni-RLHF 官方仓库主要提供通用反馈标注平台；训练数据与 baseline 在关联项目中 反馈 UI、标注工作流和传统 RL 反馈设计参考 原生 VLA schema、视频—动作同步或生产部署链路
RLIF 用 intervention decision 作为 reward signal 的 off-policy RL 方法 人工介入事件、replay 与 off-policy actor/critic 路径 pairwise RLHF；必须直接模仿接管动作；VLA 专用实现
版本敏感：“支持某模型”必须展开成 repository commit + model/checkpoint + action head + algorithm + environment 五元组。README 的最新能力不能反向证明旧 checkpoint 或本地 fork 具备同样接口。

二、总体架构：上游仓库不直接互相依赖

flowchart TB
  SRC[Pinned upstream repositories] --> BR[Bridge package]
  ROB[Robot / simulator] --> RT[Runtime & safety layer]
  UI[Label / intervention UI] --> STORE[Immutable episode & feedback store]
  RT --> STORE
  BR --> CAP[Policy capability gate]
  STORE --> BATCH[Canonical batches]
  CAP --> ALG[DPO · APO · TPO · PPO · Flow RL · RLIF]
  BATCH --> ALG
  ALG --> CKPT[Artifact manifest + checkpoint]
  CKPT --> GATE[Replay · Sim · Shadow · Controlled real gates]
  GATE --> RT

桥接层只负责显式转换，不静默修改上游语义。机器人运行时、安全层和反馈系统也不应因为训练框架升级而被一起替换。

建议为每次实验保存 source pin manifest：

sources:
  openvla:
    repository: https://github.com/openvla/openvla
    commit: <full-sha>
    dirty_patch_sha256: <sha256-or-none>
    submodules: <locked-shas>
artifacts:
  policy_checkpoint_sha256: <sha256>
  processor_sha256: <sha256>
  normalization_sha256: <sha256>
  schema_version: <semantic-version>
runtime:
  image_digest: <immutable-digest>
  accelerator_stack: <recorded-version-set>
licenses:
  code: <license>
  weights_and_data: <separately-reviewed>

只记 branch 名或 latest 不可复现；只记代码 commit 也不够，因为 processor、动作统计和 checkpoint 仍可能漂移。

三、统一数据契约：字段名之外还要固定语义

3.1 Condition 与 Episode

Condition
  episode_id, step_id, task_id, scene_id
  images[camera_id]: tensor, timestamp, calibration_id
  language: raw_text, tokenizer_id
  proprio: tensor, timestamp, frame, unit
  history_mask, event_time

Episode
  condition[]
  action[]
  outcome: success, cost[], intervention[], termination
  lineage: behavior_policy, processor, reward, safety_config

必须说明相机坐标系、机器人坐标系、物理单位、控制频率和时钟来源。视频帧与动作按 episode_id + step_id + timestamp 对齐，不能依赖文件名排序。

3.2 ActionBatch：三个动作不能混成一个

ActionBatch
  proposed_action   # 模型原始输出
  commanded_action  # 坐标变换、限幅、安全过滤后送给控制器
  executed_action   # 由控制/状态日志确认的实际执行量
  frame, unit, normalization_id
  chunk_horizon, valid_mask, execution_mask
  distribution_info
  policy_artifact_id, safety_config_id, timestamps

其中 distribution_info 还要声明概率对应的随机变量，例如 action token、pre-squash latent、整个 action chunk 或生成路径。若行为策略只对 proposed token 给出概率，就不能把 safety-filtered executed action 直接代入重要性比率。

3.3 FeedbackRecord 不只一种

反馈结构 最小字段 典型算法
Pairwise preference condition_id、chosen_id、rejected_id、tie/invalid、来源与置信度 DPO、TPO、奖励模型
Binary desirability sample_id、desirable/undesirable、来源类别、类别权重 KTO、APO 式目标
Intervention/correction input time、延迟窗口、接管开始/结束、human action、原因码 APO 数据构造、RLIF、DAgger 类方法
Scalar/language score/text、量表、指南版本、解析器版本 奖励模型或审计辅助

APO 不应被预处理成普通 chosen/rejected pair 后再宣称“复现 APO”；GRAPE 的 GCPG 排序也不应被描述成人类偏好。

3.4 ArtifactManifest

每个训练 batch 和部署包都应能追溯到：

  • behavior/current/old/reference policy 的不可变 artifact ID；
  • processor、action tokenizer、normalization 和相机标定；
  • reward model、labeler、release evaluator 与 guideline；
  • dataset manifest、split/group key、schema migration；
  • safety config、runtime image digest、代码 commit 与补丁哈希。

四、Policy Adapter 要有能力协商，而不是只有同名函数

下面是本专题建议的概念接口，不声称任何上游仓库原生实现这些方法：

@dataclass(frozen=True)
class PolicyCapabilities:
    autoregressive_action_tokens: bool
    exact_action_log_prob: bool
    trajectory_or_path_log_prob: bool
    flow_matching_target: bool
    value_head: bool
    supports_teacher_forcing: bool

class PolicyAdapter(Protocol):
    def encode_condition(self, batch) -> ConditionBatch: ...
    def sample(self, condition, *, rng) -> PolicyOutput: ...
    def score_action(self, condition, action) -> LogProbOutput: ...
    def supervised_loss(self, batch) -> LossOutput: ...
    def export(self, manifest) -> DeploymentArtifact: ...
    def capabilities(self) -> PolicyCapabilities: ...

score_action 不支持时必须明确报错，不能返回零、负 MSE 或未校准的相似度来“凑接口”。sample 还要返回 RNG/采样配置、动作空间、mask、生成元数据和对应 artifact ID。

4.1 自回归 action token 的可评分条件

若动作序列 z_{1:L} 与物理动作的编码固定，则一个 action chunk 的对数概率可写为

\[\log \Pi_\theta(a\mid h) =\sum_{\ell=1}^{L}m_\ell \log p_\theta(z_\ell\mid h,z_{<\ell}),\]

其中 $m_\ell$ 只选择实际动作 token。语言 token、padding 和未执行后缀都不能进入该和式；tokenizer、离散化、chunk 长度和 normalization 也必须与 rollout 时一致。

4.2 Flow Matching loss 不是自动可用的 log-prob

典型 Flow Matching 训练目标形如

\[\mathcal L_{FM} = \mathbb E_{t,x_0,x_1} \left[ \left\|v_\theta(x_t,t,h)-u_t(x_t\mid x_1)\right\|_2^2 \right].\]

它是速度场回归目标，并不自动等于 $-\log\pi_\theta(a\mid h)$。若某算法需要归一化密度、生成路径概率、critic 或特定重参数梯度，就必须实现并验证那些接口；不能仅把负 Flow MSE 填进 DPO/PPO 的 log-ratio。

五、算法启动前的 Capability Gate

算法路径 必须满足 不满足时
Token DPO / TPO current/reference 能对同一动作 token teacher-force；pair 条件一致；mask 正确 停止训练，不能用序列 loss 冒充偏好比率
APO 自回归 action token；binary desirability/类别；reference；与论文一致的平衡采样和自适应权重 不得改成普通 DPO pair 后仍称 APO
PPO rollout sampling；behavior log-prob；current re-score；old/reference 冻结；critic；终止/截断 mask 历史数据不得无修正混入 on-policy buffer
Flow supervised / reward-weighted regression flow target、time/noise sampler、动作与 execution mask 只能声称优化代理目标，不能声称精确 policy ratio
Flow RL 所选算法明确要求的路径/密度、critic、重参数或 off-policy 接口 逐项补齐或更换算法
RLIF-style intervention event/reward、replay buffer、off-policy actor/critic、安全执行链路 不能用 pairwise 数据管线替代

配置校验应在加载大模型或启动机器人之前执行，并打印缺失 capability 与其数学原因。

六、五条最小落地路径

6.1 自回归 VLA + DPO/TPO

  1. 锁定具有可 teacher-force 动作 token 的 current/reference。
  2. 按同一 condition 构造 chosen/rejected；轨迹偏好还要保持任务和初态可比。
  3. 验证 token span、padding、未执行 chunk 与 reference 冻结。
  4. 先用合成样本检查 loss 和梯度方向，再跑 LoRA 小批量过拟合。
  5. 用 held-out pair margin 只做训练诊断，最终看仿真与受控闭环。

GRAPE 官方实现可作为 OpenVLA TPO-LoRA 参考。其当前 README 说明训练以 batch size 1、单 GPU为主，chosen/rejected 轨迹一一对应、来自同任务且初态一致；这些是该实现快照，不是 TPO 的普遍硬件定律。

6.2 自回归 VLA + APO

APO 路径使用人类辅助交互形成的 binary desirability，而不是普通成对偏好：

  1. 记录正常、介入前风险、人工纠正等来源类别及其时间边界。
  2. 复现官方代码对应的类别定义、平衡采样、reference score 和自适应动作回归权重。
  3. 检查离散 token 得分与连续动作 L1 权重的 detach/归一化位置。
  4. 分类别报告样本量、loss、成功率与安全事件，避免多数类掩盖纠正样本。
  5. 只有目标、数据和实现都一致时才称“APO”；否则写成自定义 binary-feedback objective。

6.3 VLA + Reward Model + PPO

这一条需要完整新增 rollout collector、奖励模型、critic、reference KL、on-policy buffer 与环境生命周期。通用 OpenRLHF 可提供 actor/reference/reward/critic 和分布式编排参考，但机器人侧仍要实现：

  • 多相机、proprio、控制频率和 episode 状态；
  • action chunk 的生成、逐步执行与中途截断；
  • safety layer 修改动作后的语义；
  • done、timeout、intervention、abort 的 bootstrap mask；
  • rollout worker 与 learner 之间的 policy artifact 一致性。

验收时必须重算 rollout batch 的 behavior log-prob，并在 current=old 时检查 ratio 接近 1。

6.4 OpenPI / Flow VLA 路径

先识别具体模型头：π₀/π₀.₅ flow 与 π₀-FAST autoregressive 不能共用同一假设。对 flow head，优先从官方监督训练/推理接口建立可复现基线，再选择明确支持 Flow policy 的算法，例如经验证的 reward-weighted flow、Flow RL 或 residual/off-policy 路径。

“可以生成连续动作”不等于“可以直接跑 PPO”；“能算 Flow Matching loss”也不等于“能算 DPO 所需 log-ratio”。每个候选算法都要在 capability gate 中写出真实梯度和概率对象。

6.5 RLIF-style 人工介入 RL

  1. 记录何时介入、介入持续区间与行为策略，不只保存 human action。
  2. 将 intervention decision 映射成论文定义的 reward signal。
  3. 使用与该方法匹配的 off-policy replay、actor 与 critic。
  4. 将安全接管职责与训练 reward 分开：接管保证当下执行安全，reward 只影响后续学习。
  5. 对照 intervention rate、任务成功、成本与无人工评估，不能只优化“少触发接管”。

七、上游代码怎样分工

层 可直接复用 必须 Adapter 通常需要自研
Base policy 锁定模型的官方加载、微调、推理 observation/action mapping、processor、normalization 目标机器人驱动与安全控制
Preference algorithm APO/GRAPE 的论文对应路径 自有 schema、mask、分布式 batch、评估 新反馈类型或新 action head 的数学目标
RL orchestration OpenRLHF/RLinf 的已支持训练和调度组件 环境 RPC、episode 生命周期、artifact sync 物理故障恢复与实验室运行规则
Feedback Uni-RLHF UI 思路、RLIF/APO 的信号结构 视频/动作同步、guideline、审计字段 生产权限、隐私、仲裁和事故流程
Deployment 上游导出/serving 能力 latency、watchdog、model manifest 独立硬安全层、灰度和真实回滚策略

OpenRLHF 现在覆盖的模型和 RL 算法比早期版本更广，但“支持 VLM”仍不意味着机器人 action chunk 与环境状态已经对齐。RLinf 的官方能力也在快速增长，应优先复用它已明确支持的四元组；对未列组合仍按新集成处理。

八、Bridge package 建议目录

rlhf_vla_bridge/
  manifests/        # source pins, artifacts, schema migrations
  schemas/          # condition, action, feedback, outcome
  policies/         # openvla, openpi and other adapters
  capabilities/     # algorithm requirements and fail-closed checks
  rewards/          # RM, task reward, cost and calibration

  rollout/          # sim/real collectors and policy synchronization

这是一种职责边界，不要求搬运或重排上游仓库。优先使用薄 adapter、配置和 contract test；必须修改上游时，把补丁单独保存并记录哈希。

九、测试顺序：先测语义，再测吞吐

9.1 数据与动作

  1. 图像、proprio、动作的时间戳、step ID 与 calibration 对齐。
  2. action normalization 编码/解码往返误差在容差内。
  3. proposed → commanded → executed 的变换与 mask 可追溯。
  4. done、timeout、intervention、abort 的 termination/bootstrap 组合逐项覆盖。
  5. 先 group split，再生成 pair/window；同一 episode 增广不得跨集合。

9.2 数学与梯度

  1. 小动作词表上，token log-prob 与 brute-force 枚举一致。
  2. current=reference 时 DPO/APO score difference 为零；current=old 时 PPO ratio 为 1。
  3. 交换 chosen/rejected 后偏好 loss 的方向反转。
  4. pad、语言 token、未执行 chunk 不改变 action objective。
  5. Flow adapter 请求 exact log-prob 时必须失败，除非已实现并通过密度测试。
  6. reference、old 与 evaluator 参数不在 optimizer 中，且跨 worker hash 一致。

9.3 系统与部署

  1. 单进程结果与分布式结果在容差内一致，pair 不被跨 rank 拆错。
  2. rollout manifest 中的 behavior policy 与实际 worker 权重哈希一致。
  3. checkpoint 恢复后 optimizer、scheduler、RNG、replay cutoff 和数据游标一致。
  4. 导出前后相同输入、预处理和随机种子产生一致分布或容差内动作。
  5. policy、processor、normalization、safety config 任一不匹配时拒绝启动。

十、分阶段验收，避免“一次拼全栈”

阶段 最小产物 通过条件
A：单模型基线 锁定 commit/checkpoint 的官方推理或 SFT 官方或自定义小任务可复现，输入输出语义明确
B：Adapter 契约 CanonicalBatch、capability 与 contract tests shape、单位、mask、概率对象和 lineage 全通过
C：小数据算法 合成数据 + 小批量过拟合 loss 数值有限、方向正确、冻结边界正确
D：离线评估 held-out pair、replay、校准与分层报告 无数据泄漏；指标含样本量与不确定性
E：仿真闭环 固定 seed/task suite 的 candidate/champion 比较 成功与成本同时过门，能复现实验
F：真实系统 shadow → 受限灰度 → 扩大部署 延迟、安全、人工接管和停止规则均过门

任何阶段失败都回到最近的契约层定位，不通过扩大 GPU 数量掩盖语义错误。

十一、复现、许可与供应链清单

  • 仓库 URL、完整 commit SHA、tag、submodule SHA、dirty patch hash。
  • 数据 manifest、group split、schema version、迁移脚本和删除/更正记录。
  • checkpoint、processor、tokenizer、normalization、相机标定和 safety config 哈希。
  • 容器 image digest、Python/CUDA/PyTorch/JAX、GPU/驱动边界和确定性设置。
  • 训练配置、优化器、scheduler、RNG state、恢复点与评估协议。
  • 代码、模型权重、基础模型、数据集分别审查许可证；开源代码许可证不自动覆盖权重与数据。
  • 保存依赖锁文件与软件物料清单；任何本地补丁都单独记录。
  • 凭据、机器人地址和内部网络配置只在运行时 secret/config 中出现，不进入网页、示例、日志、模型卡或 Git 历史。

十二、知识点、重点与工程设计价值

12.1 知识点

  • 仓库能力由 commit、模型、动作头、算法和环境共同确定。
  • Pairwise preference、binary desirability、intervention reward 是不同训练契约。
  • Token、Gaussian、Flow 等动作生成方式对应不同概率与梯度接口。
  • Canonical schema 要固定随机变量、坐标系、单位、时间和 artifact lineage。

12.2 重点

  • 能采样不等于能求 log-prob；Flow Matching loss 不能冒充 policy likelihood。
  • unsupported 必须 fail closed，不能用占位值让训练继续。
  • 通用 RLHF 编排、embodied rollout、反馈 UI 与硬安全层不能相互替代。
  • 开环 loss/动作误差只是诊断，最终需要分层闭环门禁。

12.3 工程设计价值及边界

  • Capability-aware adapter 能把数学前提变成机器可检查的启动条件。
  • CanonicalBatch 与 ArtifactManifest 让训练、评估和部署共享同一证据链。
  • Contract tests 能提前发现 mask、概率对象、版本漂移与分布式错配。
  • 以上是本专题的工程综合设计，不主张发明 adapter/schema/门禁概念，也不保证任意上游组合都能工作。
