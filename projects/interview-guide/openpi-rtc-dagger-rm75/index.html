03 · REAL-TIME & CORRECTION

把实时动作执行和失败纠正组织成同一条可审计闭环

RTC 解决高延迟动作块的连续生成与执行，人工门控数据聚合解决策略进入失败状态后的数据分布问题；本项目的重点是把两者连接起来，同时保留严格的安全和证据边界。

一、30 秒定位

基于既有 π0.5 与 VR 系统，设计一个“策略自主运行—操作者接管恢复—只保存有效纠正窗口—转换聚合—再训练—重新部署”的闭环。RTC 负责在推理延迟下处理已承诺动作前缀和新动作块；人工门控负责采集策略真实失败分布上的专家动作。两者只改变候选目标来源，最终必须经过同一安全链和唯一发送点。

本页主线：RTC 和 DAgger 处在两个不同的闭环：RTC 管“动作块怎样在推理延迟下连续到达执行器”，DAgger 管“策略访问到失败状态后怎样获得专家纠正”。项目的工程难点是让两条闭环共用会话状态、数据契约和安全下发链，而不是把两个名词并列起来。

二、先看现场视频：能证明什么，不能证明什么

正确结论：两段视频支持定性观察，不构成严格配对 A/B。现有部署观察是 RTC 更平滑、稳定、较不易晃动；异步推理加动作块交叉淡化在机器人快速运动时仍容易晃动。要形成量化结论，仍需锁定 checkpoint、初始条件、任务文本、速度、安全参数与重复 trial。
为什么没有添加“DAgger 效果视频”：现有资产里没有独立的 DAgger 接管—保存—再训练—回部署视频。复用普通遥操作素材会把“人工能恢复”误写成“DAgger 闭环有效”，因此本页不这样做。

三、为什么 RTC 和 DAgger 不能混为一件事

部分 解决的问题 不负责什么
RTC 高延迟推理、动作块已承诺前缀、连续滚动生成与执行 不判断任务是否做错，也不自动产生专家纠正
DAgger 在当前策略诱导的状态分布上获得专家标签，缓解行为克隆分布偏移 不负责动作块实时连续性，也不天然保证安全
人工门控方案 操作者判断风险并接管，形成 corrections-only 数据 未实现风险模型与阈值学习时，不能称为完整 HG-DAgger

四、目标闭环与 RTC 核心机制

1 · 自主执行RTC 根据当前观测和已承诺前缀持续提供候选动作。
2 · 人工接管操作者通过 VR 切换候选目标来源，底层安全链不切换。
3 · 纠正记录记录经过安全约束后真正发送的命令，并保存接管窗口与 provenance。
4 · 转换聚合校验相机、state/action、时间窗口和样本身份，再并入训练数据。
5 · 再训练回传以旧任务保持集和新失败保持集共同验收 checkpoint，再进入部署门控。

图：RTC 维持自主执行的动作连续性；人工接管产生 corrections-only 数据，经校验、聚合和再训练回到下一轮部署。

RTC 到底在处理什么

设动作块长度为 $H$，策略动作频率为 $f_a$，实测端到端推理延迟为 $T_{infer}$。新块返回时已经过去的策略步数是

\[d_{real}=\left\lceil T_{infer}f_a\right\rceil , \qquad A_{usable}^{new}=A^{new}[d_{real}:H].\]

因此 RTC 的索引必须建立在策略动作频率上，不能把 110 Hz 伺服下发频率或 30 Hz 纠正记录频率代入。若 $d_{real}\ge H$，整块已经过期，应拒绝并进入保守路径，不能从索引 0 重放。

量 作用 本项目怎样确定 常见误用
$H$ / chunk_size 一次预测覆盖的策略动作步数 从 checkpoint 配置读取 部署时为了“更稳”单独改长
$f_a$ RTC 索引的时间基准 从训练数据和运行时动作语义锁定 误用 110 Hz 或 30 Hz
inference_delay 已经过期、需要跳过的前缀步数 端到端延迟乘 $f_a$ 后向上取整 只统计 GPU forward，不算排队和预处理
execution_horizon 旧块参与一致性约束的窗口 在满足实现版本约束后离线扫描 当成“两次推理间固定执行步数”
queue_threshold 剩余动作低于阈值时触发下一次产块 由延迟分布、块长和安全余量确定 直接照抄 execution horizon
guidance / schedule 控制新旧块重叠区的约束强度与衰减 固定版本后先离线验证有限值和响应性 把官方起始示例当成 RM75 最终值

Hard、Soft、Free：同一个新块里有三种时间责任

新观测到达策略时，执行器不会暂停等待。RTC 因此不是把两段轨迹做一次普通插值，而是先明确“哪些动作已经成为事实、哪些未来动作需要保持连续、哪些位置可以服从最新观测”。

Hard prefix · 已承诺区推理期间已经执行或不可撤销的前缀。它由真实经过的延迟步数决定，新结果不能回写这一段。
Soft prefix · 重叠约束区尚未执行、但旧计划已经覆盖的未来区间。RTC 用 guidance 与 schedule 约束新旧计划的一致性，同时保留对新观测的响应。
Free suffix · 自由生成区越过重叠窗口后的新计划，主要服从最新观测与任务条件，补充后续动作。
\[ \hat d=\left\lceil \hat T_{infer}f_a\right\rceil,\qquad 0\le \hat d\le K<H,\qquad d_{real}<H \]

其中 $\hat d$ 是发起请求前用于组织前缀的预测延迟步数，$d_{real}$ 是结果返回后按真实端到端延迟计算的步数，$K$ 是 execution_horizon。两者不能混用：预测值用于构造请求，真实值用于决定返回块还有多少可用动作。若 $d_{real}\ge H$，唯一正确的结论是“整块过期”，而不是降低索引后继续播放。

在明确经过前缀条件训练的 trained 模式中，还必须同时满足当前实现版本给出的约束：

\[ d_{\max}^{train}\le K\le H-d_{\max}^{train}, \qquad queue\_threshold\ge d_{\max}^{train}. \]

普通 Flow/VLA checkpoint 应先使用 guided；只有训练时明确做过 prefix conditioning，才有依据选择 trained。模式不是一个可随意互换的部署开关。

关键参数怎样读、怎样调

参数 准确作用 起始值与确定方法 调错后的可见后果
rtc.mode 选择运行时引导或训练过的前缀条件路径 普通 checkpoint 用 guided；trained 需训练证据 模式与 checkpoint 不匹配，不能假定输出语义仍正确
execution_horizon=K 定义旧计划参与一致性约束的重叠窗口 官方示例从 10 步开始；实际值需结合 $H$、延迟和离线扫描确认 太小易在块边界突变；太大可能压制对新观测的响应
max_guidance_weight 控制 Soft prefix 的最大一致性引导强度 10-flow-step 官方示例从 10.0 开始；不是 RM75 已验证最优值 太小约束不足；太大可能过度追随旧计划甚至数值不稳
prefix_attention_schedule 决定一致性约束沿前缀怎样衰减 先测 EXP，再与 LINEAR 比较 ONES 约束最强；ZEROS 接近硬截断，不能只凭名字选
inference_delay 离线复现中模拟已经流逝的策略步数 对预处理、传输、排队、推理、后处理全链路计时，再用 $\lceil Tf_a\rceil$ 只量 GPU forward 会系统性低估过期前缀
queue_threshold 队列剩余量达到阈值时提前请求下一块 根据 P95/P99 延迟、$H$ 和安全余量确定 太小会下溢停顿；太大会堆积陈旧动作
fps rollout 的策略动作频率，也是 RTC 步索引基准 与训练数据及 action 语义一致 写成 110 Hz 发送频率会让延迟换算和块时长全错
chunk_size=H checkpoint 一次生成的动作步数 从 checkpoint 配置读取并锁定 部署侧单改会破坏训练—推理契约
flow inference steps 扩散/流模型的推理迭代数，直接影响延迟 变更后重新测全链路延迟并重标 RTC 参数 迭代数变了却沿用旧延迟，Hard prefix 会错位
debug 输出中间诊断信息 只用于离线或短时受控测试 放入约 110 Hz 的热路径可能改变时序本身

先离线复现：命令与每个参数的责任

下面是当前 LeRobot RTC 数据集评估入口的结构化复现命令。尖括号必须替换为本轮锁定的真实工件；示例值只提供起点，不代表 RM75 的最终调参结果。

python examples/rtc/eval_dataset.py \
  --policy.path=<PINNED_CHECKPOINT> \
  --dataset.repo_id=<PINNED_REFERENCE_DATASET> \
  --rtc.mode=guided \
  --rtc.execution_horizon=10 \
  --rtc.max_guidance_weight=10.0 \
  --rtc.prefix_attention_schedule=EXP \
  --inference_delay=<MEASURED_DELAY_IN_POLICY_STEPS> \
  --device=cuda \
  --output_dir=<RTC_DEBUG_OUTPUT_DIR> \
  --seed=<FIXED_SEED>
命令参数 本轮必须记录的内容 它不代表什么
--policy.path checkpoint、配置和归一化统计的不可变标识/摘要 只有目录名不能证明实际权重相同
--dataset.repo_id 与模型兼容的观测、动作 schema 和统计 数据能加载不等于相机身份、单位正确
--rtc.mode=guided 对普通 checkpoint 使用运行时引导路径 不是“已经训练过 RTC”
--rtc.execution_horizon=10 官方示例起点 10 步，随后扫描并记录结果 不是固定推理周期，也不是通用最优值
--rtc.max_guidance_weight=10.0 10-flow-step 配置的官方起始示例 不是速度、加速度或 RM75 已验收值
--rtc.prefix_attention_schedule=EXP 指数衰减的前缀注意日程 不能替代与 LINEAR 的对照
--inference_delay 以策略步表示的端到端实测延迟，整数且向上取整 不是毫秒，也不是单次 GPU forward
--device=cuda 选择本次评估的计算设备 不保证结果更快，也不改变 action 频率
--output_dir 独立保存本次诊断输出，避免覆盖前轮 不是训练 checkpoint 目录
--seed 固定可控随机源以便复查 不保证跨设备、跨版本完全逐位一致

离线通过条件不是“命令能退出”：同一观测、checkpoint、预处理和 seed 下，输出必须为有限值；Hard/Soft/Free 的长度、索引与时间轴必须一致；命令、commit、解析后的配置和输出摘要必须一起归档。

再接 rollout：官方入口与本项目私有链路要分开说

lerobot-rollout \
  --strategy.type=base \

  --inference.type=rtc \
  --inference.rtc.mode=guided \
  --inference.rtc.execution_horizon=10 \
  --inference.rtc.max_guidance_weight=10.0 \
  --inference.rtc.prefix_attention_schedule=EXP \
  --inference.queue_threshold=<MEASURED_QUEUE_THRESHOLD> \
  --fps=<POLICY_ACTION_FPS> \
  --task=<FIXED_TASK_TEXT> \
  --duration=<BOUNDED_SECONDS> \
  --device=cuda \
  <ROBOT_AND_CAMERA_SPECIFIC_ARGUMENTS>

--strategy.type=base 只表示官方入口中的自主 rollout；本项目的人工纠正由私有 DaggerRunner 会话层负责，不能把两者说成同一个参数。首次真机必须给 --duration 有界时长；机器人、相机、端口和标定参数只能来自受控配置，不能从网页补写。

现有记录只确认了私有调用链中的两个事实：client/dagger_runner.py 继承 RTCRunner，RTC 服务加载本轮 pretrained_model_ema。当前网页工作区没有私有实现和 --help 输出，因此这里只保留可核对的结构，不虚构参数名：

<RTC_SERVER_ENTRY> --ckpt <ROUND_N_CHECKPOINT>/pretrained_model_ema
<PROJECT_PYTHON> client/dagger_runner.py <LOCKED_PROJECT_ARGUMENTS>

从离线到真机的八道门

冻结工件记录 commit、checkpoint、配置、norm、任务文本、相机映射、单位、$H$、$f_a$ 与 seed。
建立双基线保留同步无 RTC 与异步无 RTC 两条基线，避免把异步收益误记到 RTC。
测全链路延迟覆盖预处理、传输、排队、推理和后处理，至少保留 P50/P95/P99/max。
固定输入离线测锁定观测、旧动作块和 seed，检查数值、分区长度与索引。
假队列故障注入不连机械臂，主动制造慢推理、整块过期、下溢和旧 generation 晚到。
只读与低速真机先验证 state/action/相机身份，再经过既有安全链做有限时长、低速测试。
接入人工事务验证软停、队列失效、VR 重新离合、保存/丢弃和安全后的真实动作记录。
锁定协议 A/B固定 checkpoint 和初始条件，重复比较四组方案并记录任务与实时性指标。

五、面试重点：三条工程原则

1. 单写者安全不变量

自主模式与人工模式只能改变“目标由谁产生”，不能各自拥有一套机械臂发送通道。两种候选动作都要通过同样的限位、限速、步长、夹爪和故障约束，再由唯一发送点下发；记录器保存的是安全链之后的真实命令。这样才能避免接管瞬间的双写竞争和数据—执行不一致。

2. 纠正数据不能只有一个 intervention 标记

需要区分原始观测、候选动作、实际发送动作、操作者接管区间、有效训练窗口和样本来源。corrections-only 数据中 100% intervention 只说明该小库全部来自人工窗口，不等于合并数据集的采样比例或训练损失权重。

3. 已知失败和未知失败用两条数据路线

已知失败可以通过场景驱动的定向恢复示教提高吞吐；在线低频接管则用于发现策略真实访问到的未知失败，并校验定向数据是否覆盖实际分布。前者高效但不自动继承 DAgger 的分布保证，后者更接近 DAgger 语义但真机成本更高。

当前部署观察：RTC 部署的运动更加平滑、稳定，机械臂不容易晃动；仅靠异步推理后的动作块交叉淡化，在机器人快速运动时仍容易晃动。该结论是现场观察，不是已经锁定 checkpoint、任务条件和重复次数的受控 A/B。

六、接管不是一个按键，而是一段受约束事务

IDLE → AUTO → SOFT_STOP → HANDOFF → TELEOP 是会话层相位，不是底层控制器全部状态。它把“谁有权产生候选目标”“队列是否仍有效”“是否允许记录”拆开，使一次接管可以被逐步验证，而不是靠一个布尔变量瞬间切换。

相位 允许的动作来源 必须完成的条件 禁止事项
IDLE 仅安全保持 无活动 episode，发送线程保持已知安全目标 不消费历史 RTC 队列
AUTO RTC 候选动作 generation 与当前会话一致，动作新鲜、长度有效且通过安全链 人工与策略不能同时写硬件
SOFT_STOP 状态化的减速/保持参考 停止发起新 RTC 请求，旧 generation 失效，持续经过限速/限加速度 不能直接把速度目标跳到零后撤销安全链
HANDOFF 安全保持 队列清空、确认停稳、VR 重新离合、记录事务就绪 不能沿用接管前 VR 参考或旧动作块
TELEOP VR→IK 候选动作 Grip=1、已 armed、活动 episode；仍通过同一安全链 Grip 松开时不能继续移动或记录

四个运行角色为何必须解耦

策略产块异步生成动作块；返回时携带 generation，只能进入仍有效的会话。
唯一发送线程约 110 Hz 读取当前候选，经状态化安全函数处理后向硬件发送。
纠正采样线程约 30 Hz 对齐观测、图像与安全后动作；频率不同于策略步和伺服步。
事件驱动会话层管理接管、保存、丢弃、故障与返回 AUTO，不承担高频硬件写入。

设测量状态为 $x_t=[q_t,w_t]$，其中 $q_t$ 是 7 关节实测角，$w_t$ 是连续夹爪开口；命令为 $u_t=[q_t^{cmd},c_t]$，其中 $c_t\in{open,hold,close}$ 是离散夹爪命令。所有来源共享同一个带内部历史 $h_t$ 的安全函数：

\[ (u_t,h_{t+1})=\mathcal S(r_t,x_t,h_t),\qquad r_t\in\{r_t^{RTC},r_t^{VR},r_t^{hold}\}. \]

保持参考应写成 $r_t^{hold}=[q_t,c_{t-1}^{safe}]$：关节保持当前实测位置，夹爪保持上一条安全命令。不能直接把 $x_t$ 当命令发送，因为连续开口测量 $w_t$ 与离散命令 $c_t$ 不是同一种语义。

一次接管与返回的完整事务

接管触发会话从 AUTO 进入 SOFT_STOP，递增 generation；从这一刻起，旧异步结果即使晚到也不再可用。
停止并排空停止新 RTC 请求，让状态化安全链减速，清空尚未执行的旧动作，等待停稳条件成立。
重建人工参考进入 HANDOFF 后以当前机械臂位姿重建 VR 离合，避免手柄坐标跳变直接映射成机械臂跳变。
门控记录进入 TELEOP 后，只有 Grip=1 且 armed、有活动 episode 时，才发送并记录人工纠正。
结束纠正Grip 松开只保持、不记录；操作者显式选择 save 或 drop，不能把所有试探动作自动入库。
返回自主稳定保持、清空/失效旧状态，用最新观测创建新 generation；新块通过新鲜度、长度与安全检查后才回 AUTO。
\[ record_t=TELEOP_t\land ARMED_t\land Grip_t\land ACTIVE\_EPISODE_t. \]

记录器必须位于 $\mathcal S$ 之后，保存真正送往唯一发送点的 $u_t$，而不是策略、IK 或 VR 的原始候选 $r_t$。这样离线训练标签才与真机实际执行契约一致。

关键失败模式：如果只把模式变量从 TELEOP 改回 AUTO，晚到的旧 generation 或接管前队列可能重新生效，把机械臂拉回已经失效的轨迹。模式切换必须同时更新相位、队列、在途请求和记录事务。

七、纠正数据为什么要分开“状态、候选与实际动作”

字段 正确语义 不能替代什么
observation.state (8,) 7 个实测关节角 + 连续夹爪开口 不是本周期动作命令
action (8,) 安全链后实际发送的 7 关节目标 + 夹爪命令编码 不是 VR 原始位姿，也不保证机器人恰好到达
三路相机 224 × 224 的头部、臂部、第三视角 shape 相同不能证明物理相机身份正确
intervention 当前帧来自人工接管 不是成功标签，也不会自动成为 loss 权重
provenance checkpoint、来源 trial、采集路线和失败类型 不能只用 episode 文件名推断来源

corrections-only 小库中保留帧可以全部是 intervention，但聚合训练集的 intervention 比例取决于各来源帧数，训练采样权重又取决于采样器或损失是否显式读取该字段。三者不能混成同一个“人工数据比例”。

在线接管与定向恢复：都能采数据，但证据不同

路线 初始状态从哪里来 优势 必须承认的限制
在线接管 当前策略在真实 rollout 中到达的状态 最接近 DAgger 的策略诱导分布，能发现未知失败 真机成本高；需要在风险扩大前完成软停和接管
定向恢复 人工布置或从失败库重建的已知错误状态 同一失败类型可高吞吐采集，便于覆盖恢复方向 可能缺少原始速度、接触、队列和历史观测上下文，不能自动等同严格 DAgger

实践中以定向恢复库覆盖已知失败，以低频在线接管做分布审计。每个 episode 至少保存 collection_mode、failure_type、initialization_method、source_trial_id、policy_checkpoint 与 was_policy_reached，否则后续无法判断“策略自己走到的失败”和“人为摆出的失败”各占多少。

为什么 H=50、T≥60 仍会产生大量尾部 padding

训练一个长度为 $H$ 的 action window 时，episode 尾部不足的部分常被末动作补齐。对长度为 $T$ 的 episode，受 padding 影响的起点比例和所有窗口位置中的 padding 比例分别为

\[ \rho_{touch}=\frac{\min(T,H-1)}{T},\qquad \rho_{pad}=\frac{H-1}{2T}\quad(T\ge H). \]

本项目数据契约记录的 $H=50,T=60$ 代入后，$\rho_{touch}=49/60\approx81.7\%$，$\rho_{pad}=49/120\approx40.8\%$。因此“episode 至少 60 帧”不等于有很多完整动作窗口：不含 padding 的合法起点只有

\[ \mathcal I_{valid}=\{t\mid0\le t\le T-H\},\qquad \lvert\mathcal I_{valid}\rvert=T-H+1=11. \]

正确处理是在 sampler 中过滤起点并报告有效窗口数 $M$，而不是简单裁掉每个文件的末尾；后者会同时破坏图像、状态、动作和事件时间轴。独立校验还要检查三路图像能解码、字段 shape/dtype、时间戳单调、intervention 区间与 save/drop 结果一致。

八、从纠正包到下一轮部署：数据账本必须闭合

原始采集包的职责是保存可追溯事实：frames.npz + mp4 + meta。转换后的训练数据是另一个域，不能一边采集一边原地覆盖。第 $i$ 轮聚合应视为保留重复样本身份的多重集合拼接：

\[ D_i=D_0\uplus D_{corr}^{(1)}\uplus\cdots\uplus D_{corr}^{(i)}. \]

这里使用 $\uplus$ 而不是普通集合并集，是因为同一场景的不同时间帧、重复纠正和来源身份都不能被无声去重。报告人工数据贡献时，应先比较各来源的有效窗口数 $M$，再说明 sampler 或 loss 的显式权重；只报 raw frames 会被短 episode 的 padding 扭曲。

六步闭环与每步的验收物

冻结原始包结束 episode 后显式 save/drop；保存 manifest、文件摘要和采集 checkpoint，原始包只读归档。
转换训练域按锁定的相机身份、state/action 语义与归一化约定生成标准数据，不覆盖采集源。
独立校验重新打开产物，检查视频、帧数、dtype/shape、有限值、时间戳、intervention 与 provenance。
物理聚合重新编号 episode，合并 base 与各轮 correction，重算统计并按有效窗口数出具来源账本。
有限步训练从锁定起点训练固定步数，同时监控原任务保持集与新失败保持集，不用训练 loss 代替任务验收。
工件化回传把权重、配置、norm、manifest 和摘要作为一个 bundle；先停旧服务，再整包切换，失败则整包回滚。

训练轮次更准确的表达是一个有限过程，而不是“聚合后自动得到最优策略”：

\[ \theta_i=Train_K(\theta_{start},D_i,c_i,\xi_i), \]

其中 $K$ 是有限训练步数，$c_i$ 是锁定配置，$\xi_i$ 是本轮随机状态。2026-10-08 的记录把“从最佳任务 checkpoint 全量微调”列为当前基线，文档中的约 5k–20k 步是待扫描预算，不是已经执行的默认值；2026-10-09 记录的 foundation base、约 50k 步属于后续比较路线，不能倒写成已完成基线。

十、怎样验证 RTC 收益而不把观感当结论

验证应依次通过：固定 commit/checkpoint 与数据统计、离线数值路径、假队列与延迟故障注入、只读真机状态、低速受限真机、锁定协议的配对 A/B。最终至少比较“无 RTC/无执行侧平滑、仅异步、仅 RTC、RTC + 执行侧平滑”，同时记录成功率、任务时间、块边界 jerk、deadline miss、队列下溢和人工接管率。

配对组 RTC 执行侧平滑 该组回答的问题
A · 同步基线 关 关 同步等待新块时的任务表现与边界抖动是多少
B · 仅异步 关 关 单独把推理放到异步链路后，排队和块交接带来什么变化
C · 仅 RTC 开 关 前缀约束和延迟处理本身带来什么变化
D · RTC + 执行侧平滑 开 开 生成侧连续性与发送侧约束叠加后的最终表现

四组必须使用同一 checkpoint、任务文本、初始条件分层、速度/安全参数和 trial 规则；B 与 A 的差异只允许来自预先定义的异步链路。任务指标记录成功率、完成时间和人工接管率；实时性指标记录端到端延迟分位数、deadline miss 与队列下溢；运动指标记录块边界 jerk 或等价的锁定统计。没有这些控制条件，视频只能留在“现场观察”列。

代表性问题—根因—验证

问题 根因 需要的验证
新块返回后从头播放 没按真实延迟裁掉过期前缀 注入慢推理，确认新块从 $d_{real}$ 开始；整块过期时拒绝
接管后旧动作重新生效 generation、队列和会话相位没有原子失效 在 HANDOFF/TELEOP 期间让旧请求晚到，确认不能入队
记录数据与真机执行不一致 在安全链之前记录候选动作，或存在第二发送点 对比 stored action 与唯一发送点日志
RTC 看起来更顺，但任务收益不明 checkpoint、速度或平滑配置没有锁定 配对 trial；定性视频与统计表分开呈现
定向恢复数据很多，却覆盖不到真实失败 人工摆出的状态缺少速度、接触与队列上下文 用低频在线接管审计失败簇和 provenance 分布

常见追问

  • 为什么当前不直接宣称完整 HG-DAgger？ 因为尚未验证基于模型不确定性的风险度量和接管阈值；当前准确名称是 human-gated / DAgger-inspired。
  • 为什么 RTC 比交叉淡化更稳定？ 交叉淡化只处理新旧块接缝；RTC 在生成阶段显式处理已承诺前缀和推理延迟。当前只有现场观察，仍需受控 A/B 才能量化。
  • 已知失败和未知失败怎样兼顾？ 定向恢复库提高已知失败采集吞吐，在线低频接管发现遗漏分布；聚合时保留两种 collection mode。
  • 最重要的安全不变量是什么？ RTC 与 VR 只生成候选参考，安全链和硬件写权限始终只有一份。

十一、面试讲述方式

建议的 2 分钟讲述顺序

问题（约 20 秒）：π0.5 一次输出动作块，但真机推理存在端到端延迟；等待新块会停顿，旧块从头重放又会执行过期动作。同时，纯行为克隆一旦进入示教外状态，错误会继续积累。

RTC（约 40 秒）：我把返回块拆成 Hard、Soft、Free 三段。Hard 是推理期间已经承诺的动作，用 $d_{real}=\lceil T_{infer}f_a\rceil$ 裁掉；Soft 用 execution horizon、guidance 和 schedule 约束新旧计划一致；Free 响应最新观测。整块过期就拒绝，不从索引 0 重放。

人工纠正闭环（约 40 秒）：接管不是换一个布尔值，而是 AUTO→SOFT_STOP→HANDOFF→TELEOP 的事务：旧 generation 失效、软停、清队列、重新离合，再让 VR 候选进入与 RTC 相同的安全链。只在 TELEOP、armed、Grip 和 active episode 同时成立时记录安全后真实命令。

数据与结论（约 20 秒）：纠正包独立校验后按有效 action window 聚合，再做有限步训练和整包回滚。视频中可定性观察到 RTC 更平滑稳定、较不易晃动；快速运动时仅异步加交叉淡化仍容易晃，但统计收益必须由锁定协议四组 A/B 给出。

如果有 5 分钟：按证据展开，不按名词堆砌

时间 展示对象 重点讲什么
0:00–0:40 两段现场视频 先说可见现象，再主动说明不是锁定变量的配对 A/B
0:40–1:50 闭环图 + RTC 公式 解释策略步时间轴、Hard/Soft/Free、整块过期拒绝和三个频率不能混用
1:50–2:40 参数与命令 挑 execution_horizon、guidance、schedule、delay、queue threshold，说明值从哪里来以及误用后果
2:40–3:35 五相位状态机 沿一次接管与返回讲 generation 失效、软停、清队列、重离合和单写者安全链
3:35–4:25 数据契约 + padding 解释实测 state、实际发送 action、provenance，以及 H=50/T=60 为何只有 11 个完整起点
4:25–5:00 聚合闭环 + 验证阶梯 说明六步账本、bundle 回滚、四组 A/B 指标，并以当前证据边界收尾
建议收尾句：“我没有把 RTC、交叉淡化和 DAgger 混成一个效果描述：RTC 处理生成时的延迟与前缀一致性，执行侧平滑约束真实下发，人工纠正解决失败状态上的监督缺口；三者通过同一状态机、数据契约和验证协议连接。”

十二、注意边界

  • 没有不确定性风险模型与阈值学习时，应称 human-gated / DAgger-inspired，不称完整 HG-DAgger。
  • 训练 loss、dry-run 通过和动作平滑观感都不能替代真机任务指标。
  • RTC、DAgger、HG-DAgger 的算法贡献来自原论文；本项目可主张的是 RM75 上的系统组织与审计方法。
  • 当前网页工作区未定位到需求中列出的完整同名实现，页面不能替代源码、commit、日志和运行记录。
