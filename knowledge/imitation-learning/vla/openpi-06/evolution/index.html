0 个π0.6 / π*0.6 的官方检查点
2 个openpi 上相关的公开 issue
6 个本页记录的社区复现项目
π0 / π0.5六个项目当前文档化的可运行策略底座

本页要建立的判断有三条。其一，π0.6 继承 π0.5 的双专家、流匹配、分层子任务与知识隔离框架；论文主文强调的升级集中在模型规模和预训练数据，模型卡还记录了 metadata 条件与文本因果注意力。因而它不是完全不变，也不是从零另造一套网络。其二，截至 2026-10-08，官方 openpi 仍未公开 π0.6 / π*0.6 检查点或 RECAP 训练实现，仓库名或配置名中的 pi06 不能当作官方来源证明。其三，本页所列六个社区项目都覆盖 RECAP 的一部分，但其文档化、可运行的策略路线均从公开的 π0 / π0.5 权重出发；能否称作“复现”，必须继续核对价值模型、优势标签、条件丢弃、CFG 和迭代控制，而不能只看项目名。

一、四代的关系可以写成两个式子

\[\pi_{0.6} \approx \pi_{0.5}\text{ 的核心框架} + \text{Gemma 3 4B} + \text{860M 动作专家} + \text{扩展的多平台数据} + \text{metadata 与文本因果掩码}\] \[\pi^{*}_{0.6} = \pi_{0.6} + \text{价值函数} + \text{优势条件} + \text{RECAP 迭代后训练}\]

这里的“加号”表示概念上的差异分解，不是可直接执行的模型合成。第一式仍是监督式基座训练，没有引入任务回报；第二式才加入由执行结果训练的价值函数、优势标签和迭代数据闭环。

本专题其余七个子页都遵循同一条口径：与前两代相同的机制只指出、不重讲。这一节把这些「只指出」的部分集中起来。

3.2 论文主文枚举的三项升级，以及模型卡补充的差异

论文第五节把 π0.6 相对前代的改进概括为三点，且都属于规模或数据层面：

# 改动 性质
i 预训练数据集增补来自多个机器人平台的额外数据 数据
ii 基座 VLM 换为 Gemma 3 4B 规模
iii 动作专家增至 860M 规模

模型卡把 π0.6 作为通用基座直接进行 out-of-box 评测，并报告它在这一设置下优于对照。这说明作者希望减少任务特定微调依赖；它不等于“任何新任务都不再需要微调”，也不是对所有部署条件的保证。

模型卡还写明了两处设计上的差异，它们不在论文的三点之列：一是 prompt 中可选的 metadata；二是文本 token 之间用因果注意力——π0 与 π0.5 的 prompt 都属于双向注意力的前缀，π0.6 的写法是「保持图像 token 之间的双向注意力，但文本 token 之间用因果注意力」。模型卡没有说明后者的原因，对照细节见子页 ①第五节与第八节。

更稳妥的结论是：论文主文强调规模和数据升级，模型卡另有注意力掩码与条件输入差异；公开材料没有给出一套脱离 π0.5 核心框架的全新拓扑。因此，“完全没变”和“完全重做”都过度简化了演进关系。

四、官方开源到什么程度

2026-10-08 再次复核，Physical Intelligence 的官方仓库 openpi 的 README 仍只列出三个基座检查点：

模型 检查点路径 说明
π0 gs://openpi-assets/checkpoints/pi0_base 流匹配基座
π0-FAST gs://openpi-assets/checkpoints/pi0_fast_base 自回归基座
π0.5 gs://openpi-assets/checkpoints/pi05_base 用知识隔离训练的升级版

其中没有 π0.6 或 π*0.6 的检查点，也没有 RECAP 的训练实现。

README 另有两条与本专题直接相关的说明：

  • 该仓库目前对 π0.5 的训练与推理只支持流匹配头。也就是说，子页 ②讲的那条 FAST 离散动作分支，在公开实现里并不完整。
  • 专家检查点中的 π0.5-DROID 注明使用知识隔离训练。这与模型卡把评测对照设为「用知识隔离训练的改进版 π0.5」是一致的。

六、复现的边界：哪些被复现了，哪些没有

要判断一个项目复现到了什么程度，最有效的办法是把 π0.6 与 π*0.6 拆成组件，逐项去问。下表左列是组件，右列是有一手证据的现状。

组件 官方是否公开 社区现状（有一手证据的部分）
π0.6 基座检查点（Gemma 3 4B 加 860M 动作专家） 否 六个项目的 README 中均未见。qrafty-ai/pi-openpi 的检查点表把 π0.6 一行标为 coming soon，而该行的说明是「π0.5 加 RECAP 训练、使用冻结主干」
π0.6 基座预训练流程 否（模型卡只给规格，不给配方） 六个项目的 README 中均未见。与 Gemma 3 4B 主干相关的只有三处自述：qrafty-ai/pi-openpi 列有三个归在「True Pi0.6」下的配置，注明需要大规模数据；exla-ai/fla 的 Gemma 3 4B 配置标为未测试（Untested）；hzm8341/pi0.6 把升级到 Gemma 3 4B 主干列为未完成的待办项
知识隔离训练流程 部分：openpi 的 π0.5-DROID 注明用它训练 exla-ai/fla 标注为以「Pi0/Pi0.5 冻结主干配方」支持；qrafty-ai/pi-openpi 自述「冻结 VLM 主干、只训练动作专家」。★ 两者都是冻结主干，与官方做法不同，见表后说明
FAST 离散动作分支 部分：openpi README 注明 π0.5 目前只支持流匹配头 hzm8341/pi0.6 自述其 RECAP 损失目前只包住流匹配一项，子任务文本预测与 FAST 离散动作似然列在待办项中；其余项目未核实
分布式价值函数（201 分箱） 否 hzm8341/pi0.6 自述其 value 是 progress-based proxy；ybpy/pistar 记录了 VLM 价值模型训练；Destiny000621/RECAP 已明确采用 SigLIP-So400m + Gemma3-270M 和 201 分箱 C51 风格价值头，但冻结方式等仍是项目自己的工程选择；RLinf 文档给出独立价值模型配置
优势计算与二值化 否 hzm8341/pi0.6 自述离线版基础实现已完成；ybpy/pistar 的 README 含「VLM 推理并标注 adv_ind」一节
优势条件策略训练 否 多个项目自述包含。RLinf 的文档化配方把负样本作为无条件样本、正样本用于正条件，并另设 10% 无条件概率；这与论文对正/负二值条件及 30% 条件丢弃的描述并不相同，属于近似实现而非逐式等价
真机 rollout 与人工介入闭环 否 hzm8341/pi0.6 自述其 CLI「还不会自动完成真实 rollout、value model 训练和 VLA 训练调用」；ybpy/pistar 的 README 含「真机 DAgger rollout 与数据采集」一节；Destiny000621/RECAP 自述记录的是在真实硬件上实际运行的流水线，其采集侧的 DAgger 会话（自主、暂停、纠正三种阶段）由另一个仓库 limb 完成

★ 表中「知识隔离」一行需要特别说明：社区所说的「支持知识隔离」，与官方 π0.6 的做法不是一回事。

exla-ai/fla 与 qrafty-ai/pi-openpi 的 README 都是用冻结 VLM 主干来实现的——主干参数整体不更新，只训练动作专家。而官方 π0.6 的知识隔离，按模型卡原文是「视觉-语言主干预测 FAST 动作 token 与共训练样本，动作专家的梯度不回流主干」——主干在训练全程持续更新，只是流匹配那一路的梯度被截断。

两者的共同点是「流匹配梯度不进入主干」；差别在于主干能否继续从 FAST 动作 token 与其他共训练样本中更新。整体冻结会同时切断这些更新，而官方知识隔离只截断流匹配通路。完整对照见子页 ②第五节「与冻结主干的本质区别」。

因此，读到社区项目「支持知识隔离」时，不能等同于复现了官方 π0.6 的训练方式。

由此可以得到本页最重要的一条判断：

本页所列六个项目都没有提供“官方 π0.6 基座”。截至复核日，官方既未发布该检查点，也未公开足以重建同一基座的完整数据与训练配方。社区项目可以从头训练自定义的 Gemma 3 配置，也可以从 π0 / π0.5 暖启动；但只有后者在这些项目的当前文档化、可运行路线中得到明确支持。更准确的概括是：

\[\text{当前文档化路线} \approx \pi_0\text{ 或 }\pi_{0.5}\text{ 基座} + \text{各项目对 RECAP 的实现或近似}\]

七、复现时容易走偏的几个点

7.1 仓库名或配置名里的 pi06 不代表论文的 π0.6

这是最容易误判的一处。一个名为 pi06_* 的训练配置，其底座可能仍是 pi05_base。首先应检查初始化权重，再检查主干、动作专家和数据配方。官方没有发布 π0.6 检查点，所以声称“加载官方 π0.6 权重”的路线不成立；但社区仍可能从头训练自定义的 Gemma 3 模型，不能反过来断言所有可运行实现都必然从 π0 / π0.5 出发。

这不是推测，三个项目的 README 里都能直接看到：

例一：Destiny000621/RECAP 的配置表。 README 把注册的十个配置（训练与推理成对）称为「pi0.6 configs」，并写明它们全部共用 Pi0Config(pi05=True, pistar=True)。表中五个训练配置的初始权重（Init weights）一栏：pi06_yam_vial_30fps 与 pi06_yam_vial_30fps_lora 是 pi05_base，其余三个是 SFT 检查点；而 README 对该 SFT 检查点的说明是「pi0.5 warm-start checkpoint」。名字叫 pi06，底座是 π0.5。

例二：qrafty-ai/pi-openpi 自己列的对照表。 这个项目在 README 里把两种方案分成了两行（原表照录，只翻译了表头）：

方案（README 原文） VLM 主干 动作专家 所需数据 README 的建议
Pi0.5-based Gemma 2B（冻结） 300M 约 10 万帧 推荐
True Pi0.6 Gemma 3 4B 860M 数百万 仅在有大规模数据时

项目自己推荐的是第一行——基于 π0.5 预训练权重、冻结主干、只训练动作专家。第二行「真正的 π0.6」的规格与官方模型卡一致（Gemma 3 4B、860M），但官方从未公开其权重。

同一份 README 的配置清单也按这两行分组：pi06_multi、pi06_aloha_sim、pi06_libero、pi06_base_lora 四个配置归在「Pi0.5-based」一组之下，只有名字中带 gemma3 的三个配置归在「True Pi0.6」一组。配置名以 pi06 开头，并不说明它属于哪一组。

两点提醒。其一，上表是 qrafty-ai/pi-openpi 的 README 自述，「约 10 万帧」「数百万」这类数据量是该项目的估计，不是官方数据。其二，该表第一行的「Gemma 2B」指的是 PaliGemma 3B 的语言塔，与本站的记录一致：PaliGemma 3B 由 SigLIP So400m/14 视觉塔与 Gemma 2B 语言塔组成（见本页第二节对照表与 π0.5 · 网络架构与结构差异），两种写法只是统计范围不同。

例三：exla-ai/fla 的 pi06 配置。 README 的模型总览表中，「pi06 configs」一行的参数量标为 2.7B，与同表中 π0.5 的 2.7B 相同；「实验性」一表把这类配置标为冻结主干（frozen backbone），第五节的两个自测数字所用的 pi06_multi 即属此类。与此同时，README 在「需要社区贡献」一表中把 Gemma 3 4B 配置标为未测试（Untested）。三处自述合起来说明：这里的 pi06 配置并不具备 π0.6 的规格（Gemma 3 4B 主干加 860M 动作专家）——仅 Gemma 3 4B 主干一项的参数量就已超过 2.7B。

7.2 论文未公开的量不能靠实现反推

本专题各页已逐处标注了论文未给出的量，汇总如下：

未公开的量 相关页
失败代价常数的取值 ④
经验回报离散到分箱的具体分配方式 ④
分箱上下界与各箱代表值 ④
损失乘子 α 的取值（论文以 30% 条件丢弃替代它）；各实验所用引导强度的具体值（附录 E 只举例中等范围 1.5 到 2.5） ⑤

社区实现中这些位置上出现的具体数值，是各自的工程选择。它们可能合理、可能有效，但不能当作论文原文引用。

7.3 几个容易被简化掉、但会改变算法的细节

细节 若简化会怎样 出处
每轮从预训练检查点重训，而非续训上一轮 得到的是另一个算法，其多轮行为与论文结果不可直接对照 ③ 第九节
预训练期用 \(N = T\)、后训练期用 \(N = 50\) 会改变优势的时间尺度；两种写法概念上都需比较动作前后的价值，但实际推理开销取决于是否批量计算和复用结果 ⑤ 第二节
论文预训练优势公式的求和下标 附录印为从 0 到 T 的整段回报，但主文通式从 t 开始；静默改写会掩盖歧义，应对照官方代码或作者说明 ⑤ 第二节
30% 的条件丢弃 若不训练可靠的无条件分支，就无法按论文方式做 CFG；仍可训练正条件策略，但不是同一目标 ⑤ 第八节
人工纠正强制置为正 纠正动作将按阈值划档，部分会进入负档，不再全部作为正样本被模仿 ⑤ 第五节
失败轨迹完整保留 删除失败轨迹会损失已采集的失败状态覆盖与结果监督；论文未做该消融，不能断言价值函数将完全失效 ⑥ 第 9.1 节
