一、本页在专题中的位置

前四个子页按知识点解释机制，本页按文件、参数共享边界与调用关系回答三个问题：核心创新落在哪些类和参数上，训练与推理实际怎样执行，以及迁移到新机器人时哪些接口必须保持一致。

99.14%普通文件体积来自 SoftFold ROS 工作区
3647纳入统计的自有 Python 物理行
3185vendored Florence-2 物理行
3调用链
31Handler 注册键
核验基线：官方仓库提交 6bc2513f5f1cbec715cc668b414392a6cae5c671、论文 v1 与 checkpoint 配置修订 c1c4a64a7e03ac5b95c468bf1578f3d03651b53b。源码定义该提交的可执行行为，论文说明设计意图与实验设置，README 只给示例，checkpoint 配置定义具体模型实例；四者不能互相替代。

1.1 先抓住创新主线

X-VLA 不是简单地“给 Florence-2 接一个动作头”。源码中的关键设计是：大部分主干跨本体共享，少量输入、输出与提示参数按 domain 私有化。domain_id 因而不是普通标签，而是选择私有参数的路由键。

层级 代码落点 是否按 domain 私有 作用
Soft prompt soft_prompt_hub 是 为每个 domain 生成提示 token；它们在位置编码之后追加到序列尾部
动作编码 action_encoder 是 将动作、状态与时间嵌入投影到共享隐空间
动作解码 action_decoder 是 将共享隐状态映射回对应 domain 的动作向量
多模态特征投影 vlm_proj、aux_visual_proj use_hetero_proj=True 时是 分别适配主视角图文特征与辅助视角视觉特征
Transformer 主干 blocks、norm、位置编码 否 在不同本体之间共享主要表征与推理能力
数据与动作适配 Handler、action_slice、action-space registry 工程接口 将异构文件格式、时间尺度与动作布局整理成统一模型输入

前三项及可选的异构视觉投影是跨本体参数化的核心；FastAPI、Accelerate、LoRA、普通注册表和 vendored Florence-2 是重要工程基础设施，但不应与模型创新混为一谈。

domain 私有参数不等于 domain 私有动作空间。action_space 只在构造模型时按 config.action_mode 创建一次；动作维数、损失、预处理与后处理对整份模型都是全局的。domain_id 只选择 soft prompt、动作编码器/解码器以及可选的异构特征投影，并不会切换 ee6d、joint 或 auto。跨本体训练成立的前提，是各 Handler 已把原始控制量映射到同一模型侧表示。

关键结构性事实：forward_vlm 在循环外只调用一次，随后每一步只重复动作 Transformer，因而避免重复执行 Florence-2。这是降低迭代开销的重要结构因素，但不是低延迟的充分证据；实际延迟还取决于采样步数、24 层主干、float32 部署、硬件、图像预处理与通信。动作空间行为也必须分开理解：ee6d、joint 清零夹爪输入并在输出端做 sigmoid；agibot_ee6d 不修改输入输出；auto 只补齐、裁剪动作，不会补齐 proprio。

实际递推式

源码先固定一份高斯噪声并令初始预测为零：

\[x_1\sim\mathcal N(0,I),\qquad a^{(0)}=0.\]

对 \(k=K,K-1,\ldots,1\) 依次计算

\[t_k=\frac{k}{K},\qquad x_{t_k}=t_kx_1+(1-t_k)a^{(K-k)}.\]

令 \(m\) 为整份模型共享的 action_mode，\(P_m\) 与 \(Q_m\) 分别表示该动作空间的预处理和后处理。每轮真正执行的是

\[(\tilde s_k,\tilde x_{t_k})=P_m(s,x_{t_k}), \qquad a^{(K-k+1)}=F_\theta(\tilde x_{t_k},t_k,o,l,\tilde s_k,d),\]

循环结束后再计算

\[a_{\mathrm{out}}=Q_m\!\left(a^{(K)}\right).\]

其中 ee6d 与 joint 的 \(P_m\) 每轮都会清零夹爪输入，auto 会补齐动作宽度，agibot_ee6d 的预处理则是恒等映射；\(Q_m\) 负责 sigmoid、裁剪或恒等输出。每一步都复用同一个 \(x_1\)，新预测直接替换旧预测，没有速度积分或步长累加；最后一次网络调用发生在 \(t=1/K\) 而不是 \(t=0\)。因此更准确的名称是“固定噪声条件下的迭代自精化”，不是 ODE 求解。

    action_space.dim_action             -> dim_action               # ee6d 为 20
    getattr(action_space, "dim_proprio",
            dim_action)                 -> dim_proprio              # ee6d 未定义，回退到 20
Florence2ForConditionalGeneration(
    config.florence_config)             -> self.vlm
    del vlm.language_model.model.decoder                            # 删掉解码器
    del vlm.language_model.lm_head                                  # 删掉词表头
SoftPromptedTransformer(
    hidden_size=config.hidden_size,
    multi_modal_input_size=projection_dim,                          # 取自 florence_config
    depth / num_heads / mlp_ratio / num_domains
    dim_action=dim_action, dim_propio=dim_proprio,
    len_soft_prompts / dim_time / max_len_seq / use_hetero_proj
)                                       -> self.transformer

七个要点：

  • 动作空间先于主干构造，因为模型侧 dim_action 与 dim_proprio 决定私有投影形状。只有模型侧宽度改变时才会产生形状不兼容：例如 joint 为 14 维；ee6d、agibot_ee6d 与默认 auto(max_dim=20) 可保持 20 维，但动作语义和损失仍可能不兼容。
  • multi_modal_input_size 不是独立配置项，它取自 florence_config 的 projection_dim。改 Florence 的规模会连带改变主干两路视觉投影的输入维。
  • 构造参数实际拼写为 dim_propio。这是固定源码中的接口拼写；若在自定义构造代码中按常见写法传 dim_proprio，会成为未知关键字。模型内部注释与张量语义仍指 proprioception。
  • dim_proprio 用 getattr 带默认值取；动作空间未定义它时，状态输入宽度默认等于动作宽度。这只规定模型期待的张量宽度，不保证坐标顺序、单位或物理语义同构。
  • auto 模式有两个未校验前提。它只补齐动作、不补齐 proprio，因此状态宽度必须已经等于 max_action_dim；同时必须满足 real_action_dim ≤ max_action_dim，否则 _pad_to_model_dim 会构造负长度 padding。这两种配置错误都会在运行期失败。
  • max_len_seq 不是 Transformer 的总 token 上限。源码在追加 soft prompt 之前检查并截取位置编码，因此它只约束动作、主视角图文与辅助视角 token 的合计长度；实际送入 24 层主干的长度还要再加 len_soft_prompts。
  • domain 槽位有硬边界。所有 DomainAwareLinear 与 soft_prompt_hub 都以 num_domains 构造，因此必须满足 \(0\le d<\texttt{num\_domains}\)。新增超出范围的 id 不能只改字典，还要扩展配置与 checkpoint 中相应 embedding 的第一维。

四、两个注册表，失败模式正好相反

这是本页最值得单独记住的一条结构性事实。同一个 robot_type 字符串会被两个不同的注册表分别查一次，而它们查不到时的行为完全相反。

注册表 在哪 查不到时 后果
Handler 注册表 _REGISTRY domain_handler/registry.py 抛 KeyError，并提示「把它加进 _REGISTRY」 首次从该数据源取样时失败，错误较容易定位
Domain id 映射 DATA_DOMAIN_ID datasets/domain_config.py 静默返回 0（.get(robot_type, 0)） 程序可能继续运行，但数据会使用 0 号槽位的 prompt 与动作投影 
# datasets/domain_handler/registry.py —— 严格查表
def get_handler_cls(dataset_name: str) -> Type[DomainHandler]:
    """Strict lookup: require explicit registration."""
    try:
        return _REGISTRY[dataset_name]
    except KeyError:
        raise KeyError(f"No handler registered for dataset '{dataset_name}'. ...")
# datasets/dataset.py —— 静默回退
sample["domain_id"] = torch.tensor(DATA_DOMAIN_ID.get(robot_type, 0))
两种漏配要分开。完全没有登记 Handler 的类型会在首次取样时抛出异常；只有已经登记 Handler、却漏写 domain id 的类型才会静默使用 0。后一种情况下训练可能继续且损失下降，但样本实际选择了 0 号私有参数。更稳妥的实现应让两处都严格查表，并在送入模型前验证 0 ≤ domain_id < num_domains。

_REGISTRY 在核验提交中有 31 个注册键，指向 17 个具体 Handler 类；DATA_DOMAIN_ID 也有 31 个键，且两者键集合完全一致。因此静默回退是新增类型时的接口风险，不是当前 31 个已注册类型存在漏配的证据。多个键可以共享同一类，例如四个 robomind-* 都指向 RobomindHandler；“注册键数、具体类数、实现文件数”不能混为一谈。

一处小瑕疵：get_handler_cls 的异常信息写的是「Add it to _REGISTRY in datasets/domains/registry.py」，但仓库里没有 datasets/domains/ 这个目录，实际路径是 datasets/domain_handler/registry.py。照着报错信息去找会找不到文件。这属于目录改名后遗留的旧路径。

4.1 采样权重使用的是第三套键

DATA_WEIGHTS 不是按 robot_type 查，而是按 self.metas 的键 n 查。普通 meta 以 dataset_name 为键；LeRobot v2.1 meta 却以通常是路径的 root_path 为键。也就是说，Handler、domain id 与采样权重实际使用三套可能不同的名字。

这会让 LeRobot 数据悄悄绕过声明权重。例如 meta 内的 robot_type="AGIBOT" 可以正确命中 Handler 和 domain 15，但若 n 是数据根路径，DATA_WEIGHTS.get(n, 1.0) 就不会命中 "AGIBOT": 0.4，而会回退到 1.0。应把三类标识显式规范化为一个稳定 dataset key，或分别使用清晰命名的字段并做严格校验。
元数据键还必须唯一。InfiniteDataReader.__init__ 直接执行 self.metas[dataset_name] = meta 或 self.metas[root_path] = meta。目录中两个 meta 产生同一键时，后读文件会静默覆盖先读文件，而不是合并轨迹；多源训练启动前应同时检查键的语义、唯一性和最终归一化权重。

五、接一个新平台要动哪几个文件

按文件组织（子页 ② 第十一节按相机配置组织、子页 ④ 第十节按踩坑概率组织，三者互补）。

顺序 文件 / 对象 必须确认或修改 漏掉后的结果
0 checkpoint 配置、action_hub.py 选定全局动作表示、状态宽度，确保新 id 小于 num_domains 形状不兼容、embedding 越界，或损失语义错误

新增 domain 槽位必须区分“预留行”和“扩容”。若新 id 仍在 checkpoint 已有的 num_domains 范围内，张量形状无需扩展，但公开脚本不会替你重新初始化这行 prompt、action encoder/decoder 或异构投影，必须显式决定它们的起点。若新 id 超出范围，则只改配置会造成 embedding 第一维与旧权重不匹配；应扩展张量、保留旧行并初始化新增行，再检查加载报告。复用一个正在使用的 id 虽可避免扩容，却会让两个数据域共享同一组私有参数；除非这是有意设计，否则会发生语义碰撞。

此外，当前模型一次只能持有一个全局 action_space。若新平台的原始动作维度、夹爪含义或损失类型不同，必须先在 Handler 中映射到现有公共表示，或修改 action_hub.py 与模型配置；仅增加 domain id 不足以支持任意异构动作空间。

5.1 Handler 有两族，实现工作量差别很大

base.py 里有两层类：抽象基类 DomainHandler 与它的 HDF5 子类 BaseHDF5Handler。 格式、坐标语义、相机顺序和时间口径与现有实现完全一致时，可以让新注册键复用已有 Handler；否则才应新建实现。当前共有 8 个 Handler 实现文件、17 个具体类，按继承关系分成两族：

族 继承自 需要实现 实现文件 / 具体类数
HDF5 族 BaseHDF5Handler build_left_right、index_candidates 4 个文件 / 13 个类
自定义读取族 DomainHandler 完整的 iter_episode 4 个文件 / 4 个类

数据能整理成约定的 HDF5 结构时，接入成本更低。 BaseHDF5Handler 提供图像和指令读取、时间插值、候选帧遍历、静止段过滤、语言增强，并应用由 InfiniteDataReader 创建后传入的图像变换；子类至少实现轨迹构造与候选索引两个钩子。

自定义读取族需要自己产生与训练入口兼容的样本。必须保持的不变量是：返回 abs_trajectory、图像张量及其 mask、语言指令；确保状态与动作的坐标、单位、排列和模型侧宽度一致；并在进入模型前经过 action_slice。时间窗口、重采样、缺失视角补齐也必须与目标 checkpoint 的训练口径一致；静止段过滤和语言增强则是训练策略，应按数据性质决定，而不是无条件照抄。

5.2 build_left_right 是 HDF5 族的核心

对 HDF5 族，build_left_right 返回两组绝对轨迹、时间戳、标称采集频率与 qdur 预测跨度；自定义读取族则在各自 iter_episode 中定义时间语义。不同 Handler 即使都输出 30 个动作锚点，也未必覆盖相同物理时域；AGIWorld 甚至按帧片段的归一化坐标插值，没有统一的秒级 qdur。迁移时必须核对目标 checkpoint 看到的时间口径，逐 Handler 数值和片尾缩窗边界见子页 ④ 第 3.2 节。

注意 DATA_WEIGHTS 与 DATA_DOMAIN_ID 是两个独立的字典。单一数据源缺少采样权重时，回退到 1.0 后归一化结果仍为 1；多源训练则必须核对运行时 key 是否真正命中目标权重。DATA_DOMAIN_ID 不应依赖默认值，必须显式登记并校验范围。

六、论文、README 与固定实现的主要差异

本专题前四个子页已经分别论证论文、README 示例与固定实现之间的边界。本节只汇总声明、可执行行为和代码位置，便于读者定位；完整机制与证据仍以对应子页为准。

第 4 项对应的实际采样可写为

\[u\sim\mathcal U(0,1),\qquad i=0,\ldots,B-1,\qquad t_i=(u+i/B)\bmod(1-10^{-5}).\]

其中 \(B\) 是 batch size。同一批样本共享随机偏移 \(u\)，所以各 \(t_i\) 不是独立同分布；分层排列使批内覆盖更均匀，但模数小于 1 又带来极小的边界偏差。

正确的核对原则是：论文用于理解设计意图和报告的实验设置，源码用于确定该提交的可执行行为，README 用于理解示例命令，checkpoint 配置用于确定具体模型实例。出现差异时应同时标注对象和版本，不能笼统地说“所有数值以代码为准”。

6.1 论文差异之外，还要看到这些工程风险

下面各项不一定与论文冲突，但会直接影响训练正确性、可复现性或部署输入，不能混入上一张表后遗漏掉。

风险 源码事实 影响 / 正确理解
分布式数据重复 dataloader 未传给 accelerator.prepare，InfiniteDataReader 也未按 rank 或 worker 显式分片 不同随机种子不保证样本互斥；多进程有效数据量不能按 world size 直接推算
元数据键覆盖 多个 meta 以相同 dataset_name 或 root_path 写入 self.metas 后读文件覆盖先读文件；必须在采样前断言键唯一并核对实际轨迹数

主视角被硬编码为第 0 槽 forward_vlm 只把 image_features[:, 0] 与文本送入 Florence；其余视角走辅助视觉分支 相机顺序不是可交换集合；第 0 槽缺失但其他槽有效时，主图文流会接收零图像特征
缺失视角没有主干 mask 有效性只用于决定哪些图像进入 DaViT，而且“至少一张有效”的检查针对整个 batch 而非每个样本 补零 token 经有偏置投影后仍参与动作主干；同一 batch 中个别样本全缺图也不会被前置检查单独拦截
use_proprio 不是有效开关 配置被保存，但前向仍始终接收并使用 proprio 不应把 false 解读为已经支持无状态输入
auto 配置缺少校验 只补齐动作，不补 proprio，也没有检查 real_action_dim ≤ max_action_dim 状态宽度不等或真实动作更宽会在运行期触发形状/负 padding 错误
两个 prompt 长度字段 配置同时有 len_soft_prompts 与 soft_prompt_length 构建主干只使用前者；后者是疑似遗留字段，修改它不会改变 prompt 长度
零长度 prompt 不能直接训练 len_soft_prompts=0 时主干不创建 soft_prompt_hub，但两个训练入口的优化器无条件访问该属性 前向支持“无 prompt”，官方训练入口却会在构建优化器时 AttributeError；需把该参数组改为条件创建
无限遍历采用递归委托 _iter_one_dataset 末尾 yield from 自身 每完成一次数据源遍历就增加一层委托，长期训练宜改成显式循环
Accelerate 官方支持为 IterableDataset 构造分片包装。因此这里能下的结论是“当前代码没有显式分片保证”，而不是“IterableDataset 不应交给 prepare”。

七、易误解点核对表

读这份仓库时最容易形成的错误印象，逐条对照：

  • 看到 Florence2ForConditionalGeneration 不等于模型会生成文本。构造后 decoder 与 lm_head 立刻被 del 掉，只保留 encoder。
  • config.json 里的 decoder_layers: 12 不代表运行时有这 12 层。照配置估参数量会偏大。
  • 看到 num_domains: 30 不等于用了 30 个数据源。那是槽位上限，预训练实际用 7 个。
  • domain_id 不会自动选择动作空间。它只索引 domain-aware 参数；整份模型仍共用一个 action_space、动作宽度和损失约定。
  • soft prompt 在序列末尾，但没有自己的绝对位置编码。源码先给动作、主视角图文和辅助视角 token 加 pos_emb，然后才拼接 prompt；它仍可通过双向自注意力影响前面的动作 token。
  • action_hub.py 注册了四个动作空间，不是六个。franka_joint7 与 so101_bimanual 只存在于 LeRobot 移植版。
  • image_mask 不会传给动作主干。它只筛选送入 DaViT 的有效图像；缺失视角的占位特征仍会经过有偏置的投影并参与后续注意力。
  • 不同 rank 和 worker 的随机种子不等于数据分片。它们可能降低采样序列完全相同的概率，但不保证样本不重叠。
  • get_handler_cls 的报错路径是旧的，写的是 datasets/domains/，实际在 datasets/domain_handler/。
