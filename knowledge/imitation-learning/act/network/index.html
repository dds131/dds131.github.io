子页 ④ 回答的是「为什么这样设计网络」：DETR 的集合预测思想、action query 与 object query 的类比边界、多相机特征为什么沿宽度维拼接、四套位置编码为什么分工不同。本页回答的是另一个问题——这个网络本体到底由哪些模块构成，它们如何被装配起来，训练时又是如何被驱动的。

ACT 的策略网络是一个名为 DETRVAE 的 nn.Module。在标准 backbone 路径下，它直接注册 14 个子模块和 1 个持久 buffer；为便于阅读，后文会把 transformer 容器展开成 encoder 与 decoder 两项。这里必须区分“顶层直接注册成员”和递归展开后的全部 PyTorch 模块，后者远不止 15 个。本页逐项说明这些成员的类型、权重形状、参数量和数据流位置，再回答三个结构性问题：模块如何组合、任务损失能到达哪些参数、超参数决定哪些张量维度。

14 + 1直接子模块 + 持久 buffer
83.9Mrequires_grad 注册参数
2 条有/无目标动作的前向路径
4 + 7 + 4主干 encoder / decoder / CVAE encoder 层数
5 + 1后验专用模块 + buffer
1 + 6未接损失的头 + 零任务梯度层
本页最需要记住的三条：ACT 的视觉主干只建了一份，多路相机复用同一组权重，因此固定块长时参数量与相机数无关，但计算量、激活显存和 encoder 序列长度都会增长；DETRVAE 内部有两个互相独立的 Transformer encoder，一个融合当前观测，一个估计 CVAE 后验；固定提交虽然构造 7 层 decoder，却在动作头前取返回栈的 [0]，所以动作预测只依赖第 1 个 decoder layer，后 6 层执行前向但没有任务损失信号。

1.1 方法贡献、继承组件与实现遗留

类别 内容 应如何理解
ACT 的方法贡献 动作分块、Temporal Ensembling、以 CVAE 建模示范动作块 这是论文提出并通过实验讨论的核心方法
继承或改写 ResNet-18、DETR-style Transformer、FrozenBN、Joiner、二维正弦位置编码 属于已有视觉与 DETR 组件，不能记作 ACT 独创

固定提交的实现遗留或风险 输入维度硬编码 14、is_pad_head 未监督、只采用第一 decoder layer、--masks/--dilation 兼容性问题 这些是源码事实或静态推断，不应包装成方法创新

官方图中的元素 源码中对应什么 说明

4.1 Backbone 与 FrozenBatchNorm2d

主干由 torchvision.models.resnet18 构造，但传入了两个非默认参数。

backbone = getattr(torchvision.models, name)(
    replace_stride_with_dilation=[False, False, dilation],
    pretrained=is_main_process(), norm_layer=FrozenBatchNorm2d)
num_channels = 512 if name in ('resnet18', 'resnet34') else 2048
pretrained=is_main_process()在官方单进程入口中 get_rank() 返回 0，因此会加载 ImageNet 预训练权重；真正的分布式环境中非主 rank 的实参为 False，不能概括成任何情况下都直接加载。
norm_layer=FrozenBatchNorm2d把 BatchNorm 的 weight、bias、running_mean、running_var 四个量全部改为 register_buffer。它们进 state_dict，但不是 nn.Parameter，因此不在优化器中、也不参与参数量统计。
num_channels = 512ResNet-18 与 ResNet-34 的 layer4 输出 512 通道，更深的变体是 2048。ACT 用的是 512，这个数字随后被 input_proj 读取。

冻结 BatchNorm 的直接后果是主干的归一化统计量在训练全程保持不变。固定预训练统计量通常有利于小批量视觉训练，但这是一般工程解释；论文没有提供 FrozenBN 消融，不能把它写成作者验证过的因果结论。论文所说的“每个任务从头训练”也应理解为不复用其他机器人任务的完整策略，而不是 ResNet 的所有参数都随机初始化。

这里有一处容易误读的源码细节：BackboneBase.__init__ 接收了 train_backbone 参数，但用于冻结浅层的那段循环被整段注释掉了。

# for name, parameter in backbone.named_parameters(): # only train later layers
#     if not train_backbone or 'layer2' not in name and 'layer3' not in name and 'layer4' not in name:
#         parameter.requires_grad_(False)

因此 train_backbone = args.lr_backbone &gt; 0 这个判据虽然被计算出来并一路传进 BackboneBase，却不产生 requires_grad=False 的冻结行为。ResNet-18 除 BatchNorm 外的卷积参数都保留 requires_grad=True，并进入独立的优化器参数组；在官方正 lr_backbone 配置下会更新，若用户把该组学习率设为 0，则仍不会产生优化器更新。

4.2 ResNet-18 的内部结构：stem 与四个 stage

第 4.1 节讲的是 ACT 对主干做了什么改动，本节打开主干本身。ACT 直接调用 torchvision.models.resnet18，没有改动它的层结构，因此这里描述的就是 ResNet-18 的原始结构，只是标出了 ACT 实际用到的那一段。

ResNet-18 是本页唯一直接实例化的 torchvision 预训练网络，但并非只有它来自外部设计：Transformer、FrozenBN、Joiner 与位置编码主要继承或改写自 DETR。官方 ACT 实现把动作分块 CVAE、latent/proprio 条件注入、动作 query 与控制执行方式组合为一条完整策略；这不表示其中每个组件或接线都由论文单独首创。ResNet-18 有 11,166,912 个注册参数、约占全网 13.31%；本节展开它，是为了说明图像如何从 (B,3,480,640) 变成 (B,512,15,20)，而不是把基础主干误记为 ACT 的独创模块。

结构全图。 ResNet-18 由一个 stem（前置下采样）和四个 stage（layer1 到 layer4）组成，每个 stage 含 2 个 BasicBlock，合计 \(4 \times 2 \times 2 + 1 = 17\) 个卷积层，加最后的全连接层共 18 层带权重的层——这就是名字里 18 的来源。图中虚线框内的两个模块在 ACT 中不存在，原因见第 4.4 节。

「卷积层数」有两个口径，下面的表用的是后一个，容易混淆，先说清楚：主路径卷积 17 个（conv1 一个，加四个 stage 各 2 块 × 2 卷积共 16 个），这 17 个加上最后的 fc 才是名字里的 18；但 layer2、layer3、layer4 的首块各自还带一个 downsample 里的 1×1 卷积，算上它们全网共 20 个卷积层。下表合计的 11,166,912 覆盖的是全部 20 个——其中主路径 17 个占 10,994,880，三个 downsample 占 172,032（分别是 8,192、32,768、131,072）。命名用 17，参数量用 20，两者不能混着引用。

stem 与 layer1 常被混为一谈，但职责不同：stem 负责前置下采样，用 7×7 卷积和池化把空间尺寸降到 \(1/4\)；四个 stage 负责继续提取特征并逐步增加通道。不能仅凭层数少就断言 stem 计算代价很低，因为首层仍作用在最高分辨率上。注意 layer1 既不降采样也不改通道，真正“通道翻倍、边长减半”的只有 layer2 到 layer4。

4.3 BasicBlock：残差块的两条路径

上一节把四个 stage 当作整体看，本节打开 stage 里重复出现的那个单元。ResNet-18 与 ResNet-34 用的是 BasicBlock，ResNet-50 及更深用的是 Bottleneck，两者不能混谈——第 4.4 节的 --dilation 问题正是踩在这个区别上。

一个 BasicBlock 有两条并行路径，输出是二者相加后再过一次激活：

flowchart TB
  X["输入 x<br/>(B, C_in, H, W)"] --> MAIN["主路径"]
  X --> SIDE["捷径 shortcut"]
  subgraph MAINP["主路径：两个 3x3 卷积"]
    MAIN --> A1["conv1<br/>3x3，stride s，pad 1，bias=False<br/>C_in 到 C_out"]
    A1 --> A2["bn1"]
    A2 --> A3["relu"]
    A3 --> A4["conv2<br/>3x3，stride 1，pad 1，bias=False<br/>C_out 到 C_out"]
    A4 --> A5["bn2"]
  end
  subgraph SIDEP["捷径：二选一"]
    SIDE --> S1["情形一：恒等<br/>identity = x，无参数"]
    SIDE --> S2["情形二：downsample<br/>1x1 卷积 stride s + bn<br/>C_in 到 C_out"]
  end
  A5 --> ADD["相加 out += identity"]
  S1 --> ADD
  S2 --> ADD
  ADD --> R2["relu"]
  R2 --> Y["输出<br/>(B, C_out, H/s, W/s)"]

捷径走哪一条，由一行源码决定。 在 _make_layer 里：

if stride != 1 or self.inplanes != planes * block.expansion:
    downsample = nn.Sequential(
        conv1x1(self.inplanes, planes * block.expansion, stride),
        norm_layer(planes * block.expansion),
    )

判据是「形状对不上就补一层」：只要空间尺寸要变（stride != 1）或通道数要变（inplanes != planes），恒等捷径就无法与主路径输出相加，必须插一个 \(1\times1\) 卷积把 \(x\) 变形到目标形状。反之形状本来就一致时，捷径不带任何参数。

ResNet-18 的 8 个 BasicBlock 按这条判据分成两类：

位置 stride 通道 in 到 out 捷径 为什么
layer1[0] 1 64 到 64 恒等 形状完全一致
layer1[1] 1 64 到 64 恒等 形状完全一致
layer2[0] 2 64 到 128 downsample 尺寸减半且通道翻倍
layer2[1] 1 128 到 128 恒等 首块已完成变形，其后各块形状稳定
layer3[0] 2 128 到 256 downsample 尺寸减半且通道翻倍
layer3[1] 1 256 到 256 恒等 同上
layer4[0] 2 256 到 512 downsample 尺寸减半且通道翻倍
layer4[1] 1 512 到 512 恒等 同上

规律是：每个 stage 只有第一个块改变形状，其余块都是等形状的恒等残差块。 这也解释了上一节参数表里 layer1 为什么比其他 stage 少一项——它整个 stage 都没有 downsample。

三个容易被略过的实现细节：

所有卷积都是 bias=Falseconv3x3 与 conv1x1 两个工厂函数都写死了这一项，这是 torchvision ResNet 的结构事实。原始 BatchNorm 的仿射项可吸收前置卷积偏置；但 ACT 的 FrozenBN 已把 weight 与 bias 固定为 buffer，因此不能再解释成“后层有可学习偏置”。参数核算只计卷积权重的直接原因是这些卷积确实没有 bias 参数。
降采样发生在 conv1 而不是 conv2源码注释写明 Both self.conv1 and self.downsample layers downsample the input when stride != 1。主路径的第一个卷积与捷径的 1×1 卷积用同一个 stride，两条路径才能在末端对齐。
相加发生在第二个 bn 之后、最后一个 relu 之前残差分支的顺序是 conv-bn-relu-conv-bn，与捷径相加之后才过最后一个 relu，即整体为 conv-bn-relu-conv-bn-加-relu。这是原始 ResNet 的 post-activation 写法，特征是激活位于相加之后。需要与之区分的是 pre-activation 变体（He 等 2016 的 Identity Mappings）：它把 bn 与 relu 整体移到残差分支前面（分支变成 bn-relu-conv-bn-relu-conv），并且取消相加之后的激活，使捷径成为一条完全无阻的恒等通路。两者的差别是分支结构的重排，不是把某一个 relu 挪个位置。 ACT 用的是 torchvision 的实现，即 post-activation。
和本页第七节的 Transformer 层对照时，只能作残差连接这一一般原则的类比。BasicBlock 是一条双卷积分支加捷径；Transformer encoder layer 则串联注意力残差与 FFN 残差，并包含 LayerNorm 和 dropout，二者拓扑并不一一对应。残差与归一化的先后顺序见子页 ⑩ Transformer 层内实现。

4.4 ACT 取用这个主干带来的三处后果

前两节讲的是 ResNet-18 本身。本节讲 ACT 把它装进 Backbone 之后，有哪三件事与单独使用 torchvision.models.resnet18 不同。这三条都能直接影响复现。

后果一：avgpool 与 fc 被物理剔除，不是被绕过。 IntermediateLayerGetter 的构造过程是按 named_children() 顺序逐个收进一个 ModuleDict，收满就 break：

layers = OrderedDict()
for name, module in model.named_children():
    layers[name] = module
    if name in return_layers:
        del return_layers[name]
    if not return_layers:
        break
super().__init__(layers)

ACT 走的是 return_layers = {'layer4': "0"}（见第 4.5 节），所以循环在收进 layer4 之后立刻终止，avgpool 与 fc 从未被加入这个 ModuleDict。它们不在 state_dict 里、不在 parameters() 里、也不占显存。说「ACT 只是不调用分类头」是不准确的——那个分类头在 ACT 的模型对象中根本不存在。

这条正好能把参数量对上。torchvision 为 resnet18 声明的权重规模是 11,689,512，而本页第十三节给主干记的是 11,166,912，差 522,600。差额的来源可以逐项核对：

项 参数量 在 ACT 中的去向
全部卷积权重 11,166,912 保留 requires_grad=True；官方正学习率配置下更新
全部 BatchNorm 的 weight 与 bias 9,600 被 FrozenBatchNorm2d 改成 buffer，不再是参数
fc 的 weight 与 bias 513,000 被 IntermediateLayerGetter 剔除，不存在
合计 11,689,512 与 torchvision 声明值一致

BatchNorm 那 9,600 的构成：全网 BN 通道数合计 \(64 + 256 + 640 + 1280 + 2560 = 4800\)（依次为 bn1、layer1 到 layer4，含三个 downsample 里的 BN），每个通道有 weight 与 bias 两个参数，故 \(4800 \times 2 = 9600\)。

这条核对的价值在于：它同时验证了第 4.1 节的 FrozenBatchNorm2d、本节的 IntermediateLayerGetter 截断、以及第十三节的参数量表三者相互自洽。任何一处理解错了，这三个数就对不上。复现时如果打印出来的主干参数量不是 11,166,912，说明这三处之一没按 ACT 的方式配置。

后果二：冻结的是归一化统计量，不是卷积层。 这一点第 4.1 节已从「冻结浅层的循环被整段注释掉」的角度说过，这里补上结构侧的对照：FrozenBatchNorm2d 只影响 BN，而 BN 在 ResNet-18 里分布在每个卷积之后——17 个卷积层配 17 个 BN，加上三个 downsample 里的 BN 共 20 个。它们全部退出优化器，但 20 个卷积层一个不少地参与训练（17 个主路径卷积加 3 个 downsample 的 1×1 卷积，口径见第 4.2 节）。

因此「ACT 冻结了视觉主干」是一个常见但错误的说法。准确的表述是：归一化统计量冻结，卷积权重全部可训练，只是走一个单独的低学习率参数组（见第 10.4 节）。

后果三：--dilation 这个开关在默认主干上不可用。 Backbone.__init__ 把它一路传给 torchvision：

backbone = getattr(torchvision.models, name)(
    replace_stride_with_dilation=[False, False, dilation], ...)

三元组的第三位对应 layer4，所以这个开关的语义是「把 layer4 的 stride 2 换成空洞卷积」，使输出分辨率从 \(15\times20\) 变成 \(30\times40\)，视觉 token 数从 300 涨到 1200（单相机口径）。听起来是个现成的提分旋钮，但在 ResNet-18 上它会直接抛异常。链条是这样的：

步 位置 发生了什么
1 _make_layer(dilate=True) self.dilation *= stride 使 dilation 变为 2，同时把 stride 置回 1
2 该 stage 的第一个块 传入的是 previous_dilation，仍为 1，构造正常
3 该 stage 的其余块 传入 dilation=self.dilation，即 2
4 BasicBlock.__init__ if dilation > 1: raise NotImplementedError("Dilation > 1 not supported in BasicBlock")

BasicBlock 明确不支持空洞卷积，只有 Bottleneck 支持。因此 --dilation 只在 --backbone resnet50 及更深的变体上可用，而 ACT 的默认主干是 resnet18。

默认配置不触发--dilation 是 action='store_true'，默认 False，官方参考命令没有传它。它是默认未启用且与 ResNet-18 不兼容的遗留开关；换成支持 dilation 的 Bottleneck 主干后仍可使用，因此不应绝对称为“死开关”。
但复现时会踩到想加大视觉分辨率的人很自然会去试这个开关，得到的是一个看起来与自己改动无关的 NotImplementedError。两条可行的路：其一，调大输入图像尺寸——下采样倍数仍是 32，但输入变大则输出特征图同比变大；其二，先换成 Bottleneck 类主干（resnet50 及更深）再打开这个开关——注意换主干本身不改变分辨率（同样是 32 倍下采样），它的作用是让 --dilation 变得可用。单换主干而不开开关，分辨率不会有任何变化。
本站没有实机验证上述链条是从 torchvision 与 ACT 两处源码推出的，本站未在容器中跑过 --dilation 来触发该异常。引用时请按「源码推断」对待。

4.5 IntermediateLayerGetter 与 return_layers 

if return_interm_layers:
    return_layers = {"layer1": "0", "layer2": "1", "layer3": "2", "layer4": "3"}
else:
    return_layers = {'layer4': "0"}

return_interm_layers = args.masks。官方参考命令不传 --masks，默认走 else 分支：只取 layer4 的输出，且丢弃 avgpool 与 fc。返回值是一个只含一项的 OrderedDict。

这里还有一个默认路径之外的兼容性风险：若用户打开 --masks，features 会按 layer1 到 layer4 返回四项，而 DETRVAE.forward() 仍固定取 features[0]，即 64 通道的 layer1；input_proj 却仍按 backbones[0].num_channels=512 构造。按源码静态分析，两者会发生通道不匹配。因此该开关不能在当前 ACT 接线中直接启用。

这一点直接解释了 DETRVAE.forward 里那个容易误读的索引：

features, pos = self.backbones[0](image[:, cam_id]) # HARDCODED
features = features[0] # take the last layer feature

features[0] 取的是「唯一被返回的那一层」，不是「第一个相机」。相机的循环在外层，索引变量是 cam_id；而 self.backbones[0] 里的 [0] 才是「共享的那一份主干」，源码注释 # HARDCODED 标的就是这里。

4.6 PositionEmbeddingSine

构造参数PositionEmbeddingSine(hidden_dim // 2, normalize=True)，即 num_pos_feats = 256，行方向与列方向各 256 维，拼成 512 维。
temperature = 10000与原始 Transformer 的正弦编码同一常数。
normalize = True全一 mask 下，累计坐标从 1 开始，离散位置约为 1/H' ... 1 与 1/W' ... 1，再乘 scale = 2π；不是严格包含 0 的闭区间。这样可把不同特征图的坐标范围缩放到相近尺度，但不代表编码与采样分辨率完全无关。
无可训练参数纯函数式计算，不出现在 state_dict 中。

一处实现细节值得记住：该模块用 not_mask = torch.ones_like(x[0, [0]]) 构造全一掩码，x[0] 取批内第 0 个样本、[0] 取第 0 个通道并保留该维，因此 not_mask 的形状是 \((1,\, H',\, W')\)，输出的位置编码 batch 维恒为 1。这正是主干侧在 Transformer.forward 中需要对 pos_embed 做 repeat(1, bs, 1) 的原因。

4.7 Joiner 

class Joiner(nn.Sequential):
    def __init__(self, backbone, position_embedding):
        super().__init__(backbone, position_embedding)
 
    def forward(self, tensor_list):
        xs = self[0](tensor_list)
        out = []
        pos = []
        for name, x in xs.items():
            out.append(x)
            pos.append(self[1](x).to(x.dtype))
        return out, pos

Joiner 是一个两元素的 nn.Sequential，把主干与位置编码打包成一个对象，一次调用同时返回特征与对应的位置编码。build_backbone() 最后把 num_channels 外挂到 Joiner 实例上，使得 DETRVAE 可以直接读 backbones[0].num_channels。

DETRVAE.backbones 是一个 nn.ModuleList，但里面只有一个元素。这个细节决定了参数名以 backbones.0. 开头，进而决定了第 10.4 节的参数组归属。

4.8 input_proj 

self.input_proj = nn.Conv2d(backbones[0].num_channels, hidden_dim, kernel_size=1)

1×1 卷积在空间维上不做任何混合，等价于对每个空间位置独立做一次线性变换。它把主干输出的 512 通道投影到 Transformer 的隐维度 512。

两点需要说准：

它作用在展平之前调用顺序是 input_proj(features) 然后才 cat 与展平，输入是四维特征图 (B, 512, 15, 20) 而不是 token 序列。论文附录 C 的详细架构图则画成先展平再过 linear layer；图号会随论文版本变化，因此这里按“附录 C 详细架构图”引用。只要每个空间位置共享同一个线性映射，且两步之间没有插入非线性或归一化，1×1 卷积与展平后的逐 token Linear 在数学上等价。源码写法还明确了投影发生在多相机拼接之前、且所有相机共用同一个 input_proj。
当前配置下输入输出通道相同512 到 512 看似冗余，但保留这一层解耦了主干与 Transformer：换成 ResNet-50（2048 通道）或改 hidden_dim 时，这一行都不需要改。

4.9 一路相机的形状链

ResNet-18 layer4 输出 \((B,\, 512,\, 15,\, 20)\) 空间尺寸缩小 32 倍，\(480/32 = 15\)，\(640/32 = 20\)

五、状态与隐变量注入的三个模块

除视觉之外，encoder 的输入序列还有两个 token：一个来自机器人当前关节位置，一个来自隐变量 \(z\)。它们由三个模块产生。

5.1 input_proj_robot_state 

self.input_proj_robot_state = nn.Linear(14, hidden_dim)

把 14 维关节位置投影成一个 512 维 token。这里的 14 是写死的字面量，不是 state_dim 变量。

这是迁移到其他机器人时的首要兼容性风险：build() 里的 state_dim 只用于构造 action_head，三个输入侧投影层仍把 14 写成字面量。修改机器人维度时必须分别核对 qpos 维度、目标动作维度和输出动作维度，不能只改一个变量。

5.2 latent_out_proj 

self.latent_out_proj = nn.Linear(self.latent_dim, hidden_dim)  # 32 到 512

把 32 维隐变量投影成一个 512 维 token。它属于策略的 latent 条件输入支路，而不是后验 encoder 的专用部分，因此有无目标动作时都会执行。无目标动作的 rollout 路径把 latent_sample 置为全零张量，但仍需经过这层线性变换。

由此产生一个精确的结论：无目标动作时，该投影输出不是零向量，而是这层线性变换的偏置向量。它先作为主 Transformer encoder 序列第 0 个输入 token，随后通过 encoder memory 间接影响 decoder；不能说 decoder 直接接收该 token。

5.3 additional_pos_embed 

self.additional_pos_embed = nn.Embedding(2, hidden_dim) # learned position embedding for proprio and latent

两个可学习的位置嵌入，专供序列最前面那两个非视觉 token。视觉 token 用的是 2D 正弦编码，这两个 token 没有空间位置可言，因此改用可学习嵌入。

拼接发生在 Transformer.forward 中：

additional_pos_embed = additional_pos_embed.unsqueeze(1).repeat(1, bs, 1) # seq, bs, dim
pos_embed = torch.cat([additional_pos_embed, pos_embed], axis=0)
 
addition_input = torch.stack([latent_input, proprio_input], axis=0)
src = torch.cat([addition_input, src], axis=0)

由 torch.stack 的实参顺序可以确定：序列第 0 位是 latent token，第 1 位是 proprio token，第 2 位起才是视觉 token；相应地 additional_pos_embed.weight[0] 配 latent、[1] 配 proprio。

源码中这一行的注释写作 learned position embedding for proprio and latent，措辞顺序与张量实际顺序相反。以 torch.stack 的实参顺序为准。这个差别在正常使用中不产生任何影响，但在调试时如果按注释去索引某一行嵌入，会取错对象。

六、CVAE 后验编码支路：5 个模块与 1 个 buffer

这条支路从「数据集目标动作块加当前关节位置」估计近似后验并采样隐变量 \(z\)。目标动作可以来自真实遥操作，也可以来自仿真脚本示范。源码判据是 actions is not None：训练和带标签验证都会进入；无目标动作的 rollout/部署则跳过。概率含义与部署时取零的理由见子页 ③ CVAE 与隐变量 z。

遥操作数据采集：这条支路的输入从哪来

视频展示真实遥操作示范的来源；仿真脚本生成的目标动作也会进入同一后验支路。rollout 时未来目标动作不可用，因此不能运行这条后验编码路径。

6.1 五个子模块与一个持久 buffer

cls_embednn.Embedding(1, 512)，512 个参数。用法与 BERT 的 [CLS] 一致：放在序列首位，让它通过注意力聚合整段序列的信息，最后只取它的输出表示。
encoder_action_projnn.Linear(14, 512)。逐时刻作用于动作块，把 (B, H, 14) 变成 (B, H, 512)，即 H 个动作 token。
encoder_joint_projnn.Linear(14, 512)。把当前关节位置变成 1 个 token。
pos_table注册为 buffer 的固定正弦编码表，形状 (1, H+2, 512)。不是参数，但进 state_dict。
encoder由 build_encoder() 单独构造的 4 层 TransformerEncoder。与主干 encoder 超参相同、对象与权重完全独立。
latent_projnn.Linear(512, 64)。一次性产出 mu 与 logvar，各占输出的前 32 与后 32 维。

6.2 两个 qpos 投影层的对照

input_proj_robot_state 与 encoder_joint_proj 是全网最容易混淆的一对：同为 nn.Linear(14, 512)、同样处理 qpos；前者两条路径都执行，后者只在有目标动作的后验路径执行，而且两者参数完全独立。

6.3 pos_table 是 buffer，不是参数

self.register_buffer('pos_table', get_sinusoid_encoding_table(1+1+num_queries, hidden_dim))

三点后果：

不占参数量它不是 nn.Parameter，不进优化器，sum(p.numel() for p in model.parameters()) 统计不到它。
但进 state_dictregister_buffer 默认 persistent=True，它会被保存进 checkpoint。形状为 (1, H+2, 512)，H 为 90 时是 47,104 个浮点数。
改 chunk_size 会破坏 checkpoint 兼容因为形状随 num_queries 变化，用不同 chunk_size 训练的 checkpoint 无法直接 load_state_dict，会报形状不匹配。同一问题也出现在 query_embed 上。

另外，前向中写的是 pos_embed = self.pos_table.clone().detach()。pos_table 本身已经是 requires_grad=False 的 buffer，clone().detach() 在语义上是冗余的，其净效果是每次前向多做一次 \((H+2) \times 512\) 的拷贝。这不影响正确性。

6.4 CVAE encoder 与主干 encoder 是两个独立对象

def build_encoder(args):
    d_model = args.hidden_dim # 256
    dropout = args.dropout # 0.1
    nhead = args.nheads # 8
    dim_feedforward = args.dim_feedforward # 2048
    num_encoder_layers = args.enc_layers # 4 # TODO shared with VAE decoder
    normalize_before = args.pre_norm # False
    activation = "relu"
 
    encoder_layer = TransformerEncoderLayer(d_model, nhead, dim_feedforward,
                                            dropout, activation, normalize_before)
    encoder_norm = nn.LayerNorm(d_model) if normalize_before else None
    encoder = TransformerEncoder(encoder_layer, num_encoder_layers, encoder_norm)
 
    return encoder

这个函数自己 new 了一个 TransformerEncoderLayer，再包进 TransformerEncoder。它与 build_transformer() 内部构造的主干 encoder 没有任何共享。源码注释里的 shared with VAE decoder 指的是超参数取值相同（都用 args.enc_layers），不是权重共享。

代码中的行尾注释 # 256 与 # 2048 是从 DETR 继承下来的默认值备注；论文与官方 README 参考配置传入 512 与 3200。源码通过命令行接收这两个值，并不强制固定，复现时应以实际参数为准。

由 normalize_before = False 还能推出一个容易被忽略的事实：encoder_norm 为 None，即两个 encoder 的末尾都没有额外的 LayerNorm。decoder 那边则是无条件创建 decoder_norm。三处 norm 的取值对照见子页 ⑩ Transformer 层内实现 第八节。

6.5 这条支路产出什么

序列构造与前向的完整代码：

action_embed = self.encoder_action_proj(actions)          # (bs, H, 512)
qpos_embed = self.encoder_joint_proj(qpos)               # (bs, 512)
qpos_embed = torch.unsqueeze(qpos_embed, axis=1)         # (bs, 1, 512)
cls_embed = self.cls_embed.weight                        # (1, 512)
cls_embed = torch.unsqueeze(cls_embed, axis=0).repeat(bs, 1, 1)
encoder_input = torch.cat([cls_embed, qpos_embed, action_embed], axis=1)
encoder_input = encoder_input.permute(1, 0, 2)           # (H+2, bs, 512)
cls_joint_is_pad = torch.full((bs, 2), False).to(qpos.device)
is_pad = torch.cat([cls_joint_is_pad, is_pad], axis=1)   # (bs, H+2)
pos_embed = self.pos_table.clone().detach()
pos_embed = pos_embed.permute(1, 0, 2)                   # (H+2, 1, 512)
encoder_output = self.encoder(encoder_input, pos=pos_embed, src_key_padding_mask=is_pad)
encoder_output = encoder_output[0]                       # 只取 CLS 位
latent_info = self.latent_proj(encoder_output)           # (bs, 64)
mu = latent_info[:, :self.latent_dim]
logvar = latent_info[:, self.latent_dim:]
latent_sample = reparametrize(mu, logvar)                # (bs, 32)
latent_input = self.latent_out_proj(latent_sample)       # (bs, 512)

其中 cls_joint_is_pad 是两列常量 False，保证 CLS 与 qpos 这两个位置永远不被 padding 掩码屏蔽。这是 CVAE encoder 与主干 encoder 的一处关键差别：CVAE encoder 有 key padding mask，主干 encoder 完全没有掩码。掩码形参在三处的完整取值追踪见子页 ⑩ Transformer 层内实现 第十节。

七、序列主干：transformer 内部的两个对象

self.transformer 是一个 Transformer 对象，它内部只有两个子模块加一次参数初始化。

encoder_layer = TransformerEncoderLayer(d_model, nhead, dim_feedforward,
                                        dropout, activation, normalize_before)
encoder_norm = nn.LayerNorm(d_model) if normalize_before else None
self.encoder = TransformerEncoder(encoder_layer, num_encoder_layers, encoder_norm)
 
decoder_layer = TransformerDecoderLayer(d_model, nhead, dim_feedforward,

7.3 query_embed 与 tgt

query_embednn.Embedding(num_queries, hidden_dim)，即 H 行 512 列的可学习参数表。真实机器人展示的 H=90 口径下是 46,080 个参数；仿真示例的 H=100 下是 51,200 个。
tgt不是模块，是 torch.zeros_like(query_embed) 生成的常量张量。它没有参数、不出现在 state_dict 里，每次前向重新生成。

这两者的关系是 DETR 式 decoder 最容易被讲错的一点：decoder 的输入是全零张量 tgt，query_embed 是以 query_pos 的身份在每一层注意力中被加到 query 上的。论文正文把 query 描述为固定正弦嵌入，而官方源码用的是 nn.Embedding，这处论文与源码的差异记录在子页 ⑧ 实验、消融与局限 第 5.2 节；设计意图与并行解码的论证在子页 ④ DETR-style Transformer 第八节；零值在第一层如何传播的代数推演在子页 ⑩ Transformer 层内实现 第七节。

7.4 hs 的形状与那个 [0]

build_transformer() 里 return_intermediate_dec=True 是硬编码的，因此 decoder 返回全部 7 层的输出：

位置 形状 说明
TransformerDecoder 返回 \((7,\, H,\, B,\, 512)\) 7 层堆叠，seq-first
Transformer.forward 末尾 transpose(1,2) \((7,\, B,\, H,\, 512)\) 转成 batch 在前
DETRVAE.forward 取 [0] \((B,\, H,\, 512)\) 索引层维，取第 1 个 decoder layer 的输出

这里的 [0] 索引层维而不是元组，取的是第 1 个 decoder layer 经共享末尾 LayerNorm 后的输出。这不是无关紧要的返回格式细节，而会改变有效网络深度。

固定提交的重要实现行为：动作头只读取第一层中间输出，因此第 2 到第 7 个 decoder layer 虽然继续执行、占用算力并计入 checkpoint，却不影响 a_hat。它们对 L1/KL 的任务梯度为零；这与 is_pad_head 完全未接入损失、梯度为 None 不同。若忠实复现官方 checkpoint，应保留 [0]；若改成最后一层 [-1] 或增加逐层辅助损失，应视为架构修复并重新训练。

八、两个输出头

hs 同时进入两个线性头。

8.1 action_head 

self.action_head = nn.Linear(hidden_dim, state_dim)   # 512 到 14
a_hat = self.action_head(hs)                          # (B, H, 512) 到 (B, H, 14)

nn.Linear 只作用在最后一维，因此同时把 \(H\) 个位置的 512 维表示映射成 14 维动作。\(H\) 个动作位置采用非自回归并行解码，不按时间顺序逐个生成；但 query 会在 decoder self-attention 中相互交换信息，因此不是彼此独立的 \(H\) 次回归。

这是全网唯一使用 state_dim 变量的模块。第 5.1 节提到的三个输入侧投影层写的都是字面量 14，只有这里跟着 state_dim 走。

8.2 is_pad_head 

self.is_pad_head = nn.Linear(hidden_dim, 1)   # 512 到 1
is_pad_hat = self.is_pad_head(hs)             # (B, H, 512) 到 (B, H, 1)
return a_hat, is_pad_hat, [mu, logvar]

这个头的设计意图是预测动作块中哪些位置是 padding。但在 policy.py 里：

l1 = (all_l1 * ~is_pad.unsqueeze(-1)).mean()
loss_dict['l1'] = l1
loss_dict['kl'] = total_kld[0]
loss_dict['loss'] = loss_dict['l1'] + loss_dict['kl'] * self.kl_weight

is_pad_hat 被接收后再未出现在任何一行里。由此产生一条完整的因果链：

环节 结果
输出未进入 loss 该头不在反向图中
loss.backward() 之后 is_pad_head.weight.grad 为 None
AdamW 遍历参数时 对 grad is None 的参数直接跳过，连解耦权重衰减也不施加
训练结束 从头训练时保持初始化值；恢复训练时保持 checkpoint 载入值
保存 checkpoint 它仍然出现在 state_dict 里，仍计入 n_parameters 的打印值
自查方法：有目标动作并执行一次反向传播后，policy.model.is_pad_head.weight.grad 应为 None；action_head.weight.grad 通常应为非 None 的张量，不能要求每个元素必然非零。未监督的 padding 头不参与官方动作损失，其输出没有学习意义；这是遗漏还是保留接口，源码与论文没有给出作者结论。

十、两条前向路径与梯度去向

同一个 DETRVAE 对象有两条前向路径，判据只有 actions is not None。变量名虽然叫 is_training，它却不读取 self.training：带目标动作的训练和验证都会走后验路径；无目标动作的 rollout 走零潜变量路径。train() / eval() 仍独立控制 dropout 等层的行为，不能与这里的分支混为一谈。只要传入非空 actions，即使处于 eval() 或 inference_mode()，重参数化仍会随机采样 \(z\)；eval() 只改变 dropout 等模块的模式，不会自动把 \(z\) 设为 0。

10.3 梯度可达性

总损失是两项之和：

\[\mathcal{L} = \mathcal{L}_{1} + \beta \cdot D_{\mathrm{KL}}\]

两项在计算图中的起点不同，因此能回传到的模块集合也不同。

backbones 是 否 KL 只依赖 mu 与 logvar，与图像无关
input_proj 是 否 同上
input_proj_robot_state 是 否 主干侧的 qpos 投影

decoder.layers[1:7] 任务梯度为零 否 在当前 PyTorch 计算图与官方损失下继续前向计算，但不影响被选择的 hs[0]
query_embed 是 否

两条结论：

decoder.layers[1:7] 与 is_pad_head 的优化器行为不同。前者仍位于 decoder 返回栈的计算图中，未被选择的切片反向传播零信号，PyTorch 通常会为其物化数值全零但非 None 的梯度，因此 AdamW 仍可能施加解耦权重衰减；后者不是 loss 的祖先，梯度为 None，AdamW 会跳过。是否物化零梯度可用一次实际训练步打印 grad is None 与 grad.abs().max() 复核。

KL 项直接到达 5 个模块它对视觉主干、主 Transformer 与动作头没有直接梯度；但调整 kl_weight 会改变后验、latent 输入及与 L1 的联合优化轨迹，仍可能间接影响动作重建和最终策略性能。
L1 项能穿过重参数化reparametrize 写成 mu + std * eps，其中 eps 不带梯度而 mu 与 std 带，因此 L1 的梯度可以经 latent token 回流到整条 CVAE 支路。这正是重参数化技巧要解决的问题，推导见子页 ③ 第 4.7 节。

十一、超参数如何决定每个张量的维度

九个结构超参各自控制网络的不同部分。下表按「控制哪些模块」「出现在哪些形状里」「改动是否破坏 checkpoint 兼容」三列整理。这里的“不兼容”默认指在原模型类中使用 load_state_dict(strict=True) 时存在键或形状冲突；非严格加载、参数迁移或改写模型不属于这一口径。超参的数值从哪来、哪些被覆盖，见子页 ⑥ 训练目标与超参 第八节。

超参 本文引用配置 控制哪些模块 出现在哪些张量形状里 改动后旧 checkpoint
hidden_dim 512 两个 encoder、decoder、投影、嵌入与输出头；不改变 ResNet-18 本体 多数 token 与 Transformer 中间张量的最后一维 不兼容

三条需要说准的结论：

state_dim 只触达 action_head其余三个输入投影仍硬编码 14。qpos 维度错误会在两个 qpos 投影处失败，目标动作维度错误会在 encoder_action_proj 处失败；若只改输出维而监督仍为 14，则可能在 L1 处报形状错误；若维度恰好满足广播规则，也可能发生静默广播。不能只依赖运行时报错，必须分别核对状态维与动作维。
固定 H 时 camera_names 不改变参数量主干只建一份、循环复用；相机数影响序列长度、算量和输入视角语义，但不改变 state_dict 参数形状。
nheads 不改变参数量，但会改变函数多头注意力的 in_proj_weight 形状是 (3d,d)，与头数无关；只要新头数整除 d，旧权重形状可以载入，但通道分组与缩放因子已经变化，不能称为语义兼容。

十二、单相机与四相机两套口径对照

官方仓库同时支持仿真（单路 top 相机）与真机（四路相机）。下表比较的是两套有文档依据的联合配置：官方仓库仿真示例采用单相机、\(H=100\)；官方项目页真实机器人展示采用四相机、\(H=90\)。因此表中的差异不能全部归因于相机数：encoder 长度主要由相机数决定，query 参数与 CVAE 长度由 \(H\) 决定，decoder 算量同时受二者影响。

注意力 score 容量按序列长度平方增长理论 score 张量从 22.3 MiB 增至 352.7 MiB，接近 16 倍；实际峰值还取决于注意力实现、精度、是否保存权重与反向缓存，不能据此断言总显存瓶颈。
口径声明：上表的显存数字只计算单个 encoder self-attention 内部逐头 score 张量的名义容量（形状为 batch 乘头数乘 S 乘 S，按 fp32 计），不含其他激活、反向缓存、优化器状态或框架额外拷贝。融合注意力、混合精度或重计算实现不一定显式保留同形状张量，因此这个数字只用于比较量级，不是实际峰值，也不是跨实现通用的显存下界。

两套口径下 state_dict 的形状差别只有两项：query_embed.weight 分别为 \((100,\,512)\) 与 \((90,\,512)\)，pos_table 分别为 \((1,\,102,\,512)\) 与 \((1,\,92,\,512)\)。这是 \(H\) 不同造成的；相机名称和顺序不进入 state_dict，但会改变输入契约与拼接后的视角语义。

若要只观察相机数的影响，应固定 \(H\)。此时注册参数量、query 与后验序列长度均不变；只有视觉 token 数、主 encoder 长度、cross-attention memory 长度、算量与激活容量随相机数变化。

十三、参数量核算

13.1 三条解析式

Transformer 层内的参数量可以完全解析地写出来。记 \(d\) 为 hidden_dim、\(f\) 为 dim_feedforward。

多头注意力（nn.MultiheadAttention 把 Q、K、V 三个投影打包成一个 in_proj_weight，再加一个输出投影）：

\[P_{\mathrm{MHA}} = \underbrace{3d^2 + 3d}_{\text{in\_proj}} + \underbrace{d^2 + d}_{\text{out\_proj}} = 4d^2 + 4d = 1{,}050{,}624\]

前馈网络：

\[P_{\mathrm{FFN}} = \underbrace{df + f}_{\text{linear1}} + \underbrace{fd + d}_{\text{linear2}} = 2df + f + d = 3{,}280{,}512\]

LayerNorm：

\[P_{\mathrm{LN}} = 2d = 1{,}024\]

由此得到两种层的参数量：

\[P_{\text{enc-layer}} = P_{\mathrm{MHA}} + P_{\mathrm{FFN}} + 2P_{\mathrm{LN}} = 4{,}333{,}184\] \[P_{\text{dec-layer}} = 2P_{\mathrm{MHA}} + P_{\mathrm{FFN}} + 3P_{\mathrm{LN}} = 5{,}384{,}832\]

decoder 层比 encoder 层多一个注意力子层与一个 LayerNorm，因此多出约 105 万参数。逐层结构的完整拆解见子页 ⑩ Transformer 层内实现 第十三节。

13.2 视觉主干的口径

ResNet-18 的参数量不能直接用 torchvision 的公开数字，需要做两步扣减：

步骤 数值 理由

13.5 四条结论

固定 H 时参数量与相机数无关相机数本身不改变任何参数形状；83.9M 内随 H 变化的只有 query_embed。
完整 decoder 是最大的注册单体它有 7 层，encoder 有 4 层，即层数多 75%；每层还多 cross-attention 与一个 LayerNorm。但当前输出只依赖第 1 层，44.9% 是注册占比而非有效深度贡献。
约五分之一的注册参数在无目标动作路径不执行具体是 CVAE encoder、cls_embed 和三个后验投影层，共 17.38M；不要把 cls_embed 称为投影层。
与论文表述的关系论文原文写的是 around 80M parameters。本页按源码逐模块解析核算得 83.9M。两者在论文给出的精度内一致，本页不把任何一方当作错误；引用时应注明口径。

十四、CNNMLP 基线的模块对照

官方仓库里还有一个 CNNMLP 类，作为不使用 Transformer 与动作分块的对照基线。静态结构对照可以说明模块、参数量和输入契约差异，但不能单独证明性能收益；性能结论必须结合相同实验条件下的结果。

14.1 模块构成

其中 action_head 从未在 forward 中被调用：前向最后一行是 a_hat = self.mlp(features)，动作直接由 mlp 产生。这与 DETRVAE 里的 is_pad_head 属于同一类情况——已创建、已计入参数量、但不参与计算。

14.2 768 这个数字的来源

mlp_in_dim = 768 * len(backbones) + 14 里的 768 是硬编码的。它的来历是：480×640 输入经 ResNet-18 得到 15×20 特征图，再过三个 kernel_size=5 且无填充的卷积，空间尺寸依次变为 11×16、7×12、3×8，通道数降到 32，因此展平后每路相机得到 \(32 \times 3 \times 8 = 768\) 维。

这意味着 768 隐含了 480×640 的输入分辨率假设。换分辨率时，CNNMLP 会在 mlp 第一层发生形状不匹配；DETRVAE 没有固定展平维度，通常无需修改全连接输入形状，但视觉 token 数、注意力算量、激活显存、位置采样与数据分布都会随分辨率变化，不能概括为“不受影响”。

14.3 三处结构分歧

维度 ACT（DETRVAE） 基线（CNNMLP） 差异的含义
视觉主干 建 1 份，多路共享 每相机各建 1 份 共享权重减少参数并鼓励各视角使用同一特征映射；是否形成通用表示需额外分析
多相机融合 拼成 token 序列，由注意力显式融合 各路展平、拼接后由全连接层混合 两者都能产生跨视角交互；差别在显式位置相关注意力与固定布局全连接的归纳偏置
输出 \(H\) 步动作块，并行产生 单步动作（policy.py 里只取 actions[:, 0] 作监督） 这是动作分块与单步回归的根本分界，见子页 ②
损失 L1 加 KL MSE 基线没有隐变量，也就没有 KL 项
