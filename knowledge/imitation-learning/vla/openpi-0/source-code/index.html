一、读码地图：仓库全貌

先建立职责边界。文件大小会随注释和新配置变化，不能用来判断概念重要性；真正稳定的是“谁定义接口、谁装配数据、谁执行模型”。

目录 作用 与 π0 的关系
src/openpi/models/ JAX 模型定义、配置与共享模块 pi0.py、pi0_config.py、gemma.py、siglip.py
src/openpi/models_pytorch/ PyTorch 模型实现 接口相近，但损失形状、训练入口与设备计时需单独核对
src/openpi/training/ 训练配置、数据加载、优化器、检查点 配置在这里，是读码的实际入口
src/openpi/policies/ 推理封装与机器人平台输入输出适配 部署时主要修改这里
src/openpi/transforms.py 通用数据变换 补零、归一化、分词、缩放都在这一个文件里
src/openpi/shared/ 归一化统计、下载、图像工具、类型标注 normalize.py 是训练与推理必须一致的那份口径
src/openpi/serving/ WebSocket 策略服务端 机器人侧通过它连模型
scripts/ 训练、服务、归一化统计等入口脚本 JAX 与 PyTorch 训练入口分开

按职责定位核心文件：

文件 先看什么 关键问题
training/config.py 一个具体的 TrainConfig 与对应 DataConfigFactory 数据从哪里来、如何变换、加载哪个检查点
training/data_loader.py transform_dataset、create_data_loader 四段变换的真实执行顺序
models/pi0_config.py 字段默认值、model_type、inputs_spec 模型形状与 π0/π0.5 分支
models/pi0.py __init__、embedding、loss、sampling JAX 训练与采样主路径
models_pytorch/pi0_pytorch.py forward、sample_actions PyTorch 与 JAX 的边界差异
policies/policy_config.py create_trained_policy 推理变换、权重和 norm stats 如何装配
policies/policy.py infer 单次策略调用的边界与计时口径
transforms.py Normalize、TokenizePrompt、PadStatesAndActions 数据契约如何落地
建议先选一个具体配置，沿 TrainConfig → DataConfig → transform_dataset → Pi0Config → Pi0 追踪。这样先确定输入键、归一化、动作维度和 checkpoint，再读模型中的张量变换，不会把某个数据集或 π0.5 的分支误当成通用机制。

二、四条阅读路径

按目的分流，不要试图从头到尾通读。

路径甲：我想搞懂 π0 的网络先读 pi0_config.py 的形状约束，再读 pi0.py 的初始化、embedding、loss 与 sampling，最后进入 gemma.py 的 Attention 和 Block。若使用 PyTorch，再逐项对照 models_pytorch/pi0_pytorch.py。
路径乙：我想在自己的数据上微调先读 training/config.py 里的 pi0_libero，再定位它引用的 DataConfigFactory、机器人变换与 norm stats。复制示例后必须修改配置名、数据键、动作语义、资产标识和 checkpoint，不能只替换 repo_id。
路径丙：我想把模型部署到真机先 policies/policy.py 的 infer，再 policies/policy_config.py 的 create_trained_policy，然后看 policies/ 下与自己平台最接近的那个适配文件，最后 scripts/serve_policy.py 与 serving/websocket_policy_server.py。
路径丁：我想改训练循环JAX 先看 scripts/train.py 的 main、init_train_state、train_step；PyTorch 看 scripts/train_pytorch.py。修改优化器、EMA 或日志通常在训练脚本完成，修改噪声、目标速度或损失则要进入模型实现。
pi0_libero 的注释较完整，适合作为配置阅读起点；旁边的 pi0_libero_low_mem_finetune 演示 LoRA 微调，并把 ema_decay 设为 None。这只是示例组合，不代表所有 LoRA 任务都应机械复用相同数据变换与训练超参。

三、三条调用链

本页的核心。三条链是三个观察视角，并不彼此独立：TrainConfig、DataConfig 与 Pi0Config 同时连接训练、模型构建和推理。修改公共配置时必须沿三条链一起检查。

3.1 训练链

flowchart TB
  CLI["命令行：scripts/train.py"] --> CFG["training/config.py<br/>按名字取出 TrainConfig"]
  CFG --> DL["training/data_loader.py<br/>create_data_loader"]
  DL --> RT["repack_transforms<br/>键名重排"]
  RT --> DT["data_transforms<br/>机器人相关变换"]
  DT --> NM["Normalize<br/>用 norm_stats"]
  NM --> MT["model_transforms<br/>缩放 分词 补零"]
  MT --> BATCH["批数据"]
  CFG --> INIT["init_train_state<br/>建模型 建优化器 载权重"]
  INIT --> STEP["train_step"]
  BATCH --> STEP
  STEP --> LOSS["model.compute_loss<br/>见 models/pi0.py"]
  LOSS --> PRE["preprocess_observation<br/>尺寸检查 mask 与训练增强"]
  PRE --> EMB["embed_prefix + embed_suffix"]
  EMB --> OBJ["Flow 速度目标与 MSE"]
  OBJ --> GRAD["求梯度 应用更新 EMA"]
  GRAD --> CKPT["training/checkpoints.py<br/>按 save_interval 存盘"]

四个要点：

数据管线有四段repack_transforms、机器人相关的 data_transforms、归一化、model_transforms 依次执行；详细内容集中在第七节。
补零发生在数据侧PadStatesAndActions 属于 model_transforms，模型收到的状态和动作已经补到配置的 action_dim。
模型内部仍有预处理compute_loss 随后调用 preprocess_observation(train=True) 做尺寸检查、图像 mask 和随机增强。四段数据变换不是进入网络前的全部步骤。
外层循环与目标函数分开优化器、EMA、日志通常在训练脚本；噪声、时间、速度目标和损失定义在 compute_loss。

3.2 推理链

flowchart LR
  ROBOT["机器人侧<br/>packages/openpi-client"] --> WS["serving/websocket_policy_server.py"]
  WS --> INFER["policies/policy.py<br/>Policy.infer"]
  INFER --> IT["input_transform<br/>复用核心数据与模型变换"]
  IT --> B["加批维度"]
  B --> SA["model.sample_actions<br/>见 models/pi0.py"]
  SA --> UB["去批维度"]
  UB --> OT["output_transform<br/>反归一化 切回真实维度"]
  OT --> OUT["动作块返回机器人侧"]

Policy.infer 决定单次策略调用的边界。下面保留与计时和变换有关的主干；JAX 与 PyTorch 在批处理、随机数和设备转换上有不同分支：

# src/openpi/policies/policy.py，省略后端分支后的主干
inputs = self._input_transform(inputs)
inputs = add_batch_and_move_to_backend(inputs)
observation = Observation.from_dict(inputs)
start_time = time.monotonic()
actions = self._sample_actions(rng_or_device, observation, **sample_kwargs)
model_time = time.monotonic() - start_time
outputs = remove_batch_and_copy_to_host({"state": inputs["state"], "actions": actions})
outputs = self._output_transform(outputs)
outputs["policy_timing"] = {"infer_ms": model_time * 1000}
infer_ms 只包围 sample_actions，不含输入输出变换、主机与设备之间的数据搬运以及网络传输，也不是端到端机器人延迟。JAX 路径在结束计时前没有对结果调用 block_until_ready()，可能主要统计异步派发而低估设备执行时间。PyTorch CUDA 通常也应使用 CUDA Event 或显式同步；不过当前采样循环用设备标量判断 Python while 条件，可能引入隐式同步，不能仅凭代码断定偏差方向。正式基准应分别按后端预热并同步，因此这里的 infer_ms 只能视为实现中的粗略调用区间。

另一个细节：infer 也接受可选的 noise 参数，并会在噪声是二维时自动补上批维度。这是子页 ③ 第 6.3 节说的「固定噪声即可复现」在部署侧的入口。

3.3 模型构建链

flowchart TB
  TC["TrainConfig.model<br/>一个 Pi0Config 实例"] --> CREATE["Pi0Config.create"]
  CREATE --> INIT["Pi0.__init__"]
  INIT --> GC["gemma.get_config<br/>取两个专家的配置"]
  INIT --> LLM["gemma.Module<br/>configs 传入两个配置"]
  INIT --> IMG["siglip.Module<br/>So400m/14"]
  INIT --> PROJ["动作投影与时间条件层<br/>π0 五层，π0.5 四层"]
  TC --> MTF["ModelTransformFactory<br/>按 model_type 分支"]
  MTF --> TRANS["对应的一组数据变换"]
  DIR["checkpoint_dir"] --> DETECT{"根目录有 model.safetensors?"}
  DETECT -->|是| PT["load_pytorch<br/>PyTorch"]
  DETECT -->|否| JAX["restore params/<br/>JAX Orbax"]
  PT --> POLICY["Policy"]
  JAX --> POLICY

关键点有两个。第一，Pi0Config 同时进入模型与数据两条装配路径：create() 决定网络结构，ModelTransformFactory 则读取 model_type、max_token_len、action_dim 与 discrete_state_input 生成模型变换。原始 π0 有 state_proj、action_in_proj、两层 action-time MLP 与 action_out_proj；π0.5 不建 state_proj，改用两层 time MLP 为 adaRMSNorm 生成条件。改配置时必须同时检查参数形状与数据表示。

第二，部署后端由 checkpoint 内容选择。create_trained_policy() 检查根目录是否存在精确文件名 model.safetensors：存在时走 PyTorch load_pytorch()，否则从 params/ 恢复 JAX/Orbax 参数树；两种文件同时存在时优先 PyTorch，两者都不存在时则在后续加载阶段失败。源码 docstring 一处写成 model.safensors，正文应以实际检查的 model.safetensors 为准。未显式指定 PyTorch 设备时，入口优先使用可用 CUDA，否则使用 CPU。

这只是权重布局到后端的路由，不会识别 π0、π0.5 或 π0-FAST 家族；模型家族仍由 train_config.model 决定，权重形状必须匹配。该固定提交的通用 load_pytorch() 实际构造 PI0Pytorch，不能据此推断 π0-FAST 也具有可用的 PyTorch 后端。归一化统计默认从同一 checkpoint 的 assets/<asset_id> 加载。

四、pi0_config.py：旋钮清单

本节字段只描述 π0 与 π0.5 共用的 Pi0Config；π0-FAST 使用独立的 Pi0FASTConfig，不能机械套用本表。

字段 默认值 在代码里控制什么
dtype "bfloat16" 传给 Gemma 的 embedding dtype 与 SigLIP 的矩阵计算 dtype；不表示所有中间量和损失都强制为 bfloat16
paligemma_variant "gemma_2b" 取哪一组 VLM 专家配置；带 _lora 的变体会启用低秩分支
action_expert_variant "gemma_300m" 取哪一组动作专家配置
action_dim 32 模型动作宽度、输入输出规格与补零目标；π0 的 state_proj 也使用它，π0.5 不创建 state_proj
action_horizon 50 动作块长度，也是连续动作序列和噪声张量的时间维；不要与 π0-FAST 的离散 token 数混为一谈
max_token_len 48（pi05 开则 200） 非图像 token 序列上限；π0 主要是 prompt，π0.5 还可能包含离散化状态
pi05 False 模型类型开关，见第六节
discrete_state_input 跟随 pi05 模型本身不直接读取；ModelTransformFactory 用它决定分词器是否把状态写入 prompt token
pytorch_compile_mode "max-autotune" 只影响 PyTorch 分支

配置类还提供 get_freeze_filter()，按两个 variant 是否包含 lora 生成冻结规则。LoRA 微调时必须让冻结规则与实际模型使用同一组 variant，否则可能冻结错误的参数集合。

action_dim 是模型张量宽度，不等于机器人自由度。保留预训练 checkpoint 的 32 维时，原始状态和动作维度都必须不超过 32，再由 PadStatesAndActions 补齐；该变换只补短，不会把过长输入安全截断。若增大 action_dim，投影层形状随之改变，原始 checkpoint 通常不能无条件加载。输出端还要由平台变换显式切回真实动作维度。

每个取值「为什么是这个数、配错了会怎样」在总览页的速查表与子页 ① 里已给出，本页不重复。

五、pi0.py：关键函数与张量契约

__init__、posemb_sincos 和观测预处理同样重要；下面五项是训练与采样的关键接口，不是“整个模型只有五个函数”。记批大小为 $B$，prefix 长度为 $P$，动作块长度为 $H$，模型动作宽度为 $D$，VLM 专家宽度为 $E_v$，动作专家宽度为 $E_a$。默认两个专家的宽度不同，不能用一个 $E$ 混写。

函数 主要输入 主要输出 调用关系与边界
make_attn_mask input_mask [B,N]、块起点 mask_ar [N] 或 [B,N] [B,N,N] 布尔矩阵 训练前向一次；采样时 prefix 一次、每个积分步的 suffix 再一次
embed_prefix 图像、图像 mask、语言 token token [B,P,E_v] 与两个 mask 属于 VLM 专家流；采样时其 K/V 被缓存
embed_suffix 状态、含噪动作 [B,H,D]、时间 [B] π0 为 [B,H+1,E_a]，π0.5 为 [B,H,E_a] 属于动作专家流；π0 额外包含连续状态 token
compute_loss RNG、观测、动作 [B,H,D] JAX 为 [B,H] 内部在动作维取均值；由 JAX train_step 继续聚合
sample_actions RNG、观测、步数、可选噪声 [B,H,D] 动作块 [B,H,D] 从噪声端积分到数据端；由 Policy.infer 调用

默认 gemma_2b 的 $E_v=2048$，gemma_300m 的 $E_a=1024$。两个 hidden-state 张量不会直接沿序列维拼接；各专家先用自己的 Q/K/V 投影映射到共同的注意力头几何，再沿 token 轴联合计算注意力，最后经各自输出投影回到原宽度并进入各自 MLP。固定配置中二者同为 18 层、8 个查询头、1 个 K/V 头且 head dimension 为 256，因而能够同步交换信息而不要求 hidden width 相同。

make_attn_mask 先对块起点标记累积。令 $c_i$ 表示截至位置 $i$ 的块起点累计值，查询位置 $i$ 能看见键位置 $j$ 的条件为：

\[M_{ij}=m_i\land m_j\land[c_j\le c_i].\]

所以 mask_ar 不是“允许注意”的普通布尔 mask，而是“是否开启新注意力块”的标记。这个定义同时表达双向 prefix、块间因果关系和 padding 屏蔽。

三条结构性观察：

联合序列不等于张量直接拼接训练时，prefix 与 suffix 在注意力位置轴上构成同一条逻辑序列，但仍以两个不同宽度的专家张量 [prefix_tokens, suffix_tokens] 传入；拼接的是 mask 与位置语义。sample_actions 则先跑 prefix 建立 K/V cache，再在循环里只跑 suffix。
缓存只覆盖 prefix图像与语言在积分循环外计算一次；状态、时间与含噪动作属于 suffix。原始 π0 的连续状态 token 因此会随 suffix 在每个积分步重新计算，不能说“全部观测都被缓存”。
共享 embedding 减少实现漂移训练与推理复用 embed_prefix 和 embed_suffix，但数据变换、缓存路径与后端数值仍需分别测试；代码复用降低风险，不等于自动保证完全一致。

JAX 的训练路径使用

\[x_t=t\varepsilon+(1-t)a,\qquad u_t=\varepsilon-a,\]

并返回

\[L_{b,h}=\frac{1}{D}\sum_{d=1}^{D}\left(v_{\theta,bhd}-u_{bhd}\right)^2.\]

PyTorch forward 则以 reduction="none" 返回 [B,H,D]，外层训练代码再归约；因此不能把 JAX 的 [B,H] 接口描述成两个后端完全相同。补零维度也没有 loss mask：若该维真实动作 $a_d=0$，仍有 $x_{t,d}=t\varepsilon_d$、$u_{t,d}=\varepsilon_d$，模型学习把该噪声维积分回零。这些维度不是“没有训练目标”，但真实自由度少于 $D$ 时，有效维度在固定 $D$ 维均值中的相对权重会降低。

六、模型家族共存，但代码共享边界不同

这一节解决最常见的读码错误：π0 与 π0.5 共用主类，π0-FAST 则是独立实现，不能把“同一仓库”误读成“三个模型共用一套代码”。

6.1 问题在哪

models/ 目录同时住着三个模型：π0、π0.5、π0-FAST。其中 π0 与 π0.5 共用同一个 Pi0Config 与同一个 Pi0 类，靠一个布尔字段 pi05 切换；π0-FAST 则是独立的 pi0_fast.py 与 gemma_fast.py。

后果是：随手打开 pi0.py 读到的每一段代码，都可能是 π0.5 的分支。例如 embed_suffix 里就有两条路：

# src/openpi/models/pi0.py，embed_suffix 节选
if not self.pi05:
    # π0：状态作为 suffix 里的一个连续 token
    state_token = self.state_proj(obs.state)[:, None, :]
    ...
if self.pi05:
    # π0.5：时间步走 adaRMSNorm，不与动作拼接
    ...
else:
    # π0：时间步与动作表示拼接后过 MLP
    ...

研究原始 π0 时，必须确认 pi05 为 False，否则很容易把 π0.5 的离散状态与 adaRMSNorm 写成 π0 的机制。

6.2 配置名里带 pi0 不等于它是 π0

配置名称只是人类约定，不能作为模型类型的可靠判据；例如 pi0_fast_droid 以 pi0_ 开头，却使用独立的 FAST 模型。配置数量也会随上游新增配置和动态展开项变化，本页不再把某个快照的数量当成知识点。

模型家族 权威判据 状态条件 动作生成
π0 Pi0Config(pi05=False)，model_type=PI0 state_proj 连续状态 token 位于 suffix 连续 Flow Matching
π0.5 Pi0Config(pi05=True)，model_type=PI05 通常由 tokenizer 写入 prompt；是否写入还受 discrete_state_input 控制 连续 Flow Matching，时间经 adaRMSNorm 注入
π0-FAST Pi0FASTConfig，model_type=PI0_FAST 状态量化后写入双向文本 prefix；动作由 FAST tokenizer 编码为自回归 postfix 离散动作 token，自回归解码

6.3 判断一个配置属于哪个模型

  • 第一步看配置类。Pi0FASTConfig 是 FAST；Pi0Config 再进入下一步。
  • 第二步看 model_type 或 pi05。pi05=True 是 π0.5，否则是原始 π0。
  • 第三步校验 checkpoint。weight_loader 应与模型家族和参数形状一致，但自定义或恢复训练可以使用不同路径，所以 checkpoint 只能交叉验证，不能反推模型类型。
  • 不要用名称或 action_dim 分类。action_dim 是可配置的张量宽度；7、8、32 都不是任何家族的充分条件。

6.4 一个反直觉的细节

discrete_state_input 默认跟随 pi05，但可以单独覆盖。pi05_libero 就是这么做的：

# src/openpi/training/config.py
model=pi0_config.Pi0Config(pi05=True, action_horizon=10, discrete_state_input=False)

这两个字段控制不同位置：discrete_state_input=False 使 TokenizePrompt 不把状态交给 tokenizer；pi05=True 又使 embed_suffix 跳过只属于 π0 的 state_proj。因此在这份实现中，pi05_libero 的状态既不进入离散 prompt，也不走 π0 的连续状态通路；除 batch 形状等外围用途外，状态不作为模型条件。不能把“字段可以覆盖”误解成“自动退回 π0 的另一条状态路径”。π0.5 的完整机制见 π0.5 页。

七、数据管线与模型内部预处理

先区分两层：DataConfig 装配的是四段数据管线；进入 compute_loss 或 sample_actions 后，模型还会调用 preprocess_observation。把两层混成一句“预处理”会遗漏训练增强，也容易误判训练—推理差异。

数据管线段 配置字段 典型内容 何时执行
一 repack_transforms 把数据集的键名改成模型认的名字 最先
二 data_transforms 机器人相关变换，如相对动作与绝对动作互转 归一化之前
三 归一化 Normalize，读 norm_stats 中间
四 model_transforms π0/π0.5：缩放、分词、补零；FAST：状态与动作 token 化 最后

ModelTransformFactory 按模型类型给出第四段。在该工厂生成的 π0 与 π0.5 输入列表中，结构上的直接差别是 π0.5 额外把 discrete_state_input 传给分词器；模型内部仍有状态 token 与 adaRMSNorm 等差异，不能据此说两个模型“只差一个参数”：

# src/openpi/training/config.py，ModelTransformFactory.__call__ 节选
case _model.ModelType.PI0:
    return Group(inputs=[InjectDefaultPrompt(...), ResizeImages(224, 224),
                         TokenizePrompt(PaligemmaTokenizer(max_token_len)),
                         PadStatesAndActions(action_dim)])
case _model.ModelType.PI05:
    return Group(inputs=[InjectDefaultPrompt(...), ResizeImages(224, 224),
                         TokenizePrompt(PaligemmaTokenizer(max_token_len),
                                        discrete_state_input=...),
                         PadStatesAndActions(action_dim)])
对默认 π0/π0.5，模型内部的 preprocess_observation 要求 base_0_rgb、left_wrist_0_rgb、right_wrist_0_rgb 三个键存在，必要时再次缩放并补边。train=True 时，非腕部视角还会做 95% 随机裁剪、恢复尺寸和 ±5° 旋转，所有视角都会做颜色扰动；推理时不做这些随机增强。通常 ResizeImages(224,224) 已满足尺寸要求，模型内部 resize 只是检查与兜底。 Observation.from_dict 要求整个 image_mask 字典存在；“缺少 mask 时默认补 True”仅指该字典中缺少某个已有图像键的 mask 项。π0-FAST 是家族例外：它调用预处理时传入 observation 的实际图像键列表，而不是 π0/π0.5 的固定三键集合。PyTorch 也有独立的 preprocess_observation_pytorch；它覆盖相同类别的 resize、mask 与训练增强，但随机数和算子实现不同，不保证逐像素等价。

推理策略复用 DataConfig 中的机器人变换、归一化和模型变换，但前置 repack 可以由 create_trained_policy 的调用方单独提供；输出侧还按逆序执行模型输出变换、反归一化、机器人输出变换和 repack 输出。因此更准确的说法是“共享核心变换定义”，不是逐项完全相同。归一化统计的具体口径见子页 ⑤ 训练流程与优化配置。

八、易误解点核对表

前三个子页与本页累计得到的结论，汇总成一张表。每条只给正确说法与出处，不重复论证。

常见说法 准确说法 出处
π0 是 VLM 后接一个完全独立的动作解码器 VLM 专家与动作专家有各自参数，在同步 Transformer 层的联合自注意力中交换信息；MLP 等参数仍按专家分开 子页 ①
动作专家一定比 VLM 专家层数少 默认 gemma_2b 与 gemma_300m 变体层数同为 18，主要差在宽度与 MLP 维度；换 variant 后应重新核对 子页 ①
只有动作补零到 32 维 状态与动作都由 PadStatesAndActions 补到模型宽度 本页第七节
补零维度会被 loss mask 排除 Flow Matching 路径没有该 mask；填充动作维仍接收噪声并参与固定 D 维均值 本页第五节
0.999 与 0.001 是“截断采样” 代码执行 t = 0.999z + 0.001，这是仿射缩放；它避开 t=0，但不是 rejection 或 clip 子页 ②
论文时间与源码时间必有一个写错 令论文变量 τ=1−t 时，时间方向与速度符号一起改变；必须比较完整变量映射，不能只比较箭头方向 子页 ③
推理 10 步就是机器人执行 10 步 10 是生成一个完整动作块的数值积分步数，不是环境控制步数 子页 ③
pi0_fast_droid 是 π0 的普通配置 它使用 Pi0FASTConfig，属于离散 token 与自回归解码路线 本页第六节
pi05_libero 的状态回退到 π0 连续路径 两条状态输入都被关闭；状态不作为该模型配置的条件输入 本页第 6.4 节
infer_ms 是端到端或准确模型延迟 它不含变换与传输；JAX 未等待结果，PyTorch 还可能有隐式同步，均应另做后端基准 本页第 3.2 节
阅读讲解材料时，优先核对模型家族判据、状态路径、损失归约、时间变量映射和设备计时口径。只对上函数名而没有追踪张量形状与条件分支，仍可能得到错误结论。

九、知识重点与创新点如何定位

不要把“配置数量多”“多个模型共用一个类”当成算法创新。应把 π0 的贡献、推理实现、仓库工程和后续家族演进分开：

π0 算法贡献视觉—语言专家与动作专家保留各自参数和宽度，却在同步 Transformer 层中通过联合注意力交换信息；整段连续动作由条件 Flow Matching 生成，而不是离散成语言 token。
π0 推理效率图像与语言 prefix 的 K/V 在积分循环外建立并复用，每一步只重算包含状态、时间与含噪动作的 suffix。边界是“prefix 缓存、suffix 重算”，不是“全部观测缓存”。
openpi 工程设计Pi0Config、DataConfig、transform factory、权重格式与 Policy 把模型形状、平台语义、归一化和部署装配连接起来；这是重要工程能力，但不是论文算法贡献。
后续模型演进π0.5 改变状态表示与时间条件方式，π0-FAST 改用离散动作 token。它们适合用于理解仓库分支，但不应倒写成原始 π0 的创新。

十、迁移到自己机器人时要动哪些地方

按改动顺序列出，每条给出文件位置。具体的训练超参与显存分档属于子页 ⑤，本节只给结构。

  • 相机键与缺失视角。默认 π0/π0.5 要求三个规范图像键存在；缺失视角应由平台适配器创建尺寸正确的零图并设置 image_mask=False。π0-FAST 按 observation 的实际图像键预处理，必须按所用家族和平台适配器分别核对，不能把固定三键规则推广到所有模型。
  • DataConfig。以接近的平台配置为模板，修改唯一配置名、repo_id、asset_id、键重排、动作语义、默认 prompt 和机器人输入输出变换。不要只替换数据集地址。
  • 状态与动作规格。对 π0/π0.5，状态与动作由 PadStatesAndActions 补到 action_dim，超过目标宽度时不会自动安全截断；改变宽度还会造成投影层与 checkpoint 形状不兼容。π0-FAST 的标准模型变换不调用该补零器，状态和训练动作直接进入 FAST tokenizer，action_dim 与 action_horizon 还用于动作 token 反解，因此必须单独核对 tokenizer 与真实控制规格。
  • 归一化统计。按训练配置运行 scripts/compute_norm_stats.py，确认 checkpoint 中的资产目录、asset_id 和推理加载口径完全一致。
  • 推理侧适配。输入变换负责规范键名、图像布局和动作语义；输出变换必须显式反归一化、恢复绝对/增量动作语义，并把模型宽度切回真实控制维度。
  • 模型、后端与权重。先用配置类和 pi05 判定模型家族，再校验 checkpoint。部署入口以根目录是否存在 model.safetensors 选择 PyTorch，否则尝试恢复 params/ 中的 JAX 参数；改变 action_dim、variant 或 LoRA 结构后，还要检查全部参数形状与冻结规则。
  • 端到端验证。分别做训练 batch 形状检查、固定噪声的重复推理、动作单位与范围检查，以及带设备同步的稳态延迟测试；JAX 和 PyTorch 后端应分别验证。
