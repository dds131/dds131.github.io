一、已确认的服务端命令结构

源码确认

<RTC_PYTHON> server/serve_lerobot_rtc_policy.py \
  --ckpt <PINNED_CHECKPOINT> \
  --which pretrained_model_ema \
  --schedule EXP \
  --max-guidance-weight <LOCKED_WEIGHT> \
  --execution-horizon 30 \
  --device cuda \
  --warmup 2
参数 作用 调节影响 面试边界
--ckpt 选择 checkpoint 根目录 改变模型、配置和归一化统计来源 目录名不能替代权重摘要与配置校验
--which pretrained_model_ema 选择 EMA 权重目录 决定服务端实际加载哪组参数 不能只说“加载了最新模型”
--schedule EXP 配置 RTC 前缀引导的衰减日程 改变重叠区的一致性分布 需与 LINEAR 等配置离线比较
--max-guidance-weight 限制 guided RTC 的最大修正强度 太小约束不足；太大可能压制新观测或数值不稳 页面不补造本轮未锁定的具体值
--execution-horizon 30 定义旧计划参与 soft mask 的重叠范围 更大通常更平滑，也可能更迟钝 不等于完整块长 50
--device cuda 选择推理设备 影响可用实现和性能 不保证任何固定耗时
--warmup 2 正式服务前进行两次预热 降低首次请求冷启动影响 不是训练轮次

二、已确认的客户端命令结构

源码确认

<CONTROL_PYTHON> client/lerobot_rtc_runner.py \
  --head-dev <HEAD_CAMERA> \
  --arm-dev <ARM_CAMERA> \
  --third-dev <THIRD_CAMERA> \
  --policy-url <LOCAL_RTC_SERVICE> \
  --rate 110 \
  --infer-latency-steps auto \
  --speed-scale 1.0 \
  --chunk-exec-steps 25 \
  --exec-horizon 30 \
  --max-accel 2500 \
  --max-vel 240 \
  --max-first-step-deg 20 \
  --lpf-fc 5 \
  --lpf-order 2 \
  --record \
  --record-tag <RUN_TAG>

三、时间与队列参数

参数 已确认作用 当前值意味着什么 调错后的表现
--rate 110 唯一发送线程目标频率 名义周期约 9.091 ms；实测有效 109.999 Hz 太低降低时间分辨率；太高压缩 CPU/I/O 预算
--infer-latency-steps auto 用近期实测整数延迟步的滑窗最大值预测冻结前缀 对延迟长尾更保守 低估会重放过期语义；不能把 LPF 延迟加进来
--speed-scale 1.0 按比例加快或放慢 30 Hz 动作时间轴 保持原时间尺度 改变播放速度、触发频率和单位时间噪声
--chunk-exec-steps 25 走过 25 个策略动作步后触发重推理 稳态名义约 1.2 次/s 太小请求更频繁；太大增加队列下溢风险
--exec-horizon 30 客户端传给 RTC 服务的重叠约束终点 与服务端 horizon 对齐 太大可能过度追随旧计划；太小块边界更突变
符号陷阱：完整模型块长是 50 个 30 Hz 动作步；chunk_exec_steps=25 是重推理触发阈值；exec_horizon=30 是 soft-mask 衰减终点。三者不能都写成“动作块长度 H”。

四、运动与平滑参数

参数 作用 直接影响 不能声称什么
--max-accel 2500 限制安全链输出加速度变化 值越小越保守，也更易产生跟随滞后 不是实测平均加速度
--max-vel 240 限制安全链输出速度 值越小峰值速度越低 不是机器人一直以 240 运行
--max-first-step-deg 20 限制新块首步相对当前状态的最大偏差 拦截明显发散或错位块 不替代全块有限值和逐路点检查
--lpf-fc 5 设置 7 关节 EMA 低通截止频率 越低去高频更强、相位滞后更大 不修改 RTC 推理延迟步
--lpf-order 2 使用双级 EMA 比单级抑制更强，同时增加滞后 夹爪不经过该滤波

这些数值应按源码帮助中定义的单位解释；公开页不把参数上限改写成实际速度、制动距离或安全认证。

五、记录参数与量化闭环

  • --record：在真实 send() 路径记录实际发送命令、实测关节与接块事件。
  • --record-tag：为该次运行提供可追踪标签。
  • 退出后形成 frames.csv 和 events.json，支持控制周期、推理耗时、延迟步和队列事件复算。
  • 记录器必须保持轻量；图像编码和磁盘慢写不能侵占约 9.1 ms 的控制周期预算。

六、官方复现入口与私有 DAgger 入口要分开

现有面试总览中的 examples/rtc/eval_dataset.py 和 lerobot-rollout 是官方 RTC 复现结构；上面的两个入口是本项目已定位的 RTC 服务和 RM75 控制链。它们不能混写成同一个脚本。

待验证 历史需求记录中出现过 client/dagger_runner.py，但本轮没有定位到与 RTC 同等级的实现和 --help 输出。因此不添加私有 DAgger flags，也不把占位符包装成可运行命令。

面试一句话：我不会只报参数值，而是说明每个参数控制哪条时间轴、改变后影响连续性还是响应性、验证时观察什么，以及它为什么不能被误解成实测速度或性能结论。
