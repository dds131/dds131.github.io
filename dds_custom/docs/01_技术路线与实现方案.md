## 一、al-folio 与 GitHub Pages 的工作原理

### 1.1 al-folio 是什么

al-folio 是一个基于 **Jekyll**（Ruby 编写的静态站点生成器）的学术主页主题。

- 内容源：`_pages/`（独立页面）、`_posts/`（博客）、`_projects/`（项目）、`_news/`（新闻）、`_bibliography/`（文献 BibTeX）、`_books/`、`_teachings/`
- 模板层：`_layouts/`（页面骨架）、`_includes/`（可复用片段）、`_sass/`（样式）
- 总配置：`_config.yml`
- 构建命令：`bundle exec jekyll build`，产出纯静态站点到 `_site/`

al-folio 依赖大量第三方 Jekyll 插件（见 `Gemfile`）：`jekyll-scholar`（文献）、`jekyll-imagemagick`（图片处理）、`jekyll-minifier`、`jekyll-paginate-v2`、`jekyll-toc`、`jekyll-jupyter-notebook` 等，共 20 余个。

### 1.2 GitHub Pages 是什么

GitHub Pages 是 GitHub 提供的静态网站托管服务。它有两种工作模式：

| 模式 | 说明 |
| --- | --- |
| **内置 Jekyll 构建**（`build_type: legacy`） | GitHub 拿到指定分支的内容后，自己跑一遍 Jekyll 再发布 |
| **直接发布** | 分支内含 `.nojekyll` 文件时，GitHub 原样发布，不做任何处理 |

### 1.3 二者结合的关键矛盾

**GitHub Pages 的内置 Jekyll 只支持一个固定的、很短的插件白名单**（`jekyll-coffeescript`、`jekyll-default-layout`、`jekyll-gist`、`jekyll-github-metadata`、`jekyll-optional-front-matter`、`jekyll-paginate`、`jekyll-readme-index`、`jekyll-titles-from-headings`、`jekyll-relative-links` 共 9 个），官方明确写明「GitHub Pages cannot build sites using unsupported plugins」。

al-folio 用的插件几乎全部不在白名单里。

**结论：绝对不能让 GitHub Pages 直接去构建 al-folio 的源码分支。**

本项目实测印证了这一点：在把发布源设为 `main` 分支的阶段，`pages build and deployment #2` 构建失败。

### 1.4 正确的做法

在**别处**用完整的 Ruby 环境把站点构建好，只把**构建产物**交给 GitHub Pages 发布：

```
main 分支（源码）
   │
   │  GitHub Actions（完整 Ruby 3.3.5 + Node 20 + Python 3.13 + imagemagick 环境）
   │  执行 bundle exec jekyll build + purgecss
   ▼
gh-pages 分支（构建产物 _site，含 .nojekyll）
   │
   │  GitHub Pages 原样发布
   ▼
https://dds131.github.io/
```

## 二、三种可选技术路线与选型理由

### 方案 A：源码上传，GitHub Actions 云端构建 ★ 已采用

把源码推到 GitHub，由仓库自带的 `.github/workflows/deploy.yml` 在 GitHub 的云端 runner 上构建，产物推到 `gh-pages` 分支。

| 维度 | 评价 |
| --- | --- |
| 对容器环境的改动 | **零**。容器里只需要 `git`，不装任何 gem、npm 包、系统库 |
| 构建环境一致性 | **最高**。完全由上游 workflow 定义，与 al-folio 官方一致 |
| 网络要求 | 构建跑在 GitHub 云端，与国内网络无关；本地只需能 push |
| 缺点 | 本地看不到预览；改一次要等 3~5 分钟 |

### 方案 B：容器内本地构建，只推 `_site`

在容器里 `bundle install` + `npm ci` + `apt install imagemagick` + `pip install nbconvert`，本地构建后只把 `_site/` 推到 `gh-pages`。

| 维度 | 评价 |
| --- | --- |
| 对容器环境的改动 | **很大**。要装 30+ 个 gem（含需编译的 nokogiri）、Node 包、系统库 |
| 风险 | 走代理下载量大，失败点多；与「尽量不改环境」的要求直接冲突 |
| 优点 | 可离线预览 |

### 方案 C：A + B 混合

线上走 A，另外在容器里装依赖用于本地 `jekyll serve` 预览。

**选型结论：采用方案 A。**

理由：
1. 用户明确要求「尽量不修改环境」「只做最小的修改」，方案 A 对容器零改动
2. 方案 A 的构建环境由上游 workflow 保证，复现度最高，最符合「复现该项目」的目标
3. 方案 B 的依赖安装是最大的失败风险源，收益（本地预览）却不是本次的核心目标
4. 方案 A 跑通后，若后续确实需要本地预览，随时可以再补方案 B，两者不冲突

## 三、站点形态的选择

GitHub Pages 有两种站点形态，**由仓库名唯一决定**：

| 形态 | 仓库名要求 | `url` | `baseurl` | 访问地址 |
| --- | --- | --- | --- | --- |
| 用户/组织主页站 | **必须**是 `<owner>.github.io` | `https://<owner>.github.io` | **留空** | `https://<owner>.github.io/` |
| 项目站 | 任意 | `https://<owner>.github.io` | `/<仓库名>` | `https://<owner>.github.io/<仓库名>/` |

### 选型过程中排除的一个陷阱

最初提供的仓库是 `dds131/dds-1-github.github.io`。这个仓库名**看起来**像主页站（结尾有 `.github.io`），但 GitHub 判定主页站的唯一条件是 **仓库名 == `<用户名>.github.io`**，而用户名是 `dds131`，不等于 `dds-1-github`。

因此该仓库会被判定为**项目站**：
- 实际地址是 `https://dds131.github.io/dds-1-github.github.io/`
- `baseurl` 必须填 `/dds-1-github.github.io`
- 若误按主页站把 `baseurl` 留空，**全站 CSS/JS/图片会全部 404**

最终改用 `dds131/dds131.github.io`，仓库名与用户名精确匹配，是标准的**用户主页站**，`baseurl` 留空。

## 五、关键设计决策

### 5.1 为什么必须改 `_config.yml` 而不能用叠加配置绕开

Jekyll 支持 `--config a.yml,b.yml` 做配置叠加，理论上可以把自定义配置全放在 `dds_custom/` 下，完全不碰 `_config.yml`。

但上游 `.github/workflows/deploy.yml` 第 100 行执行的是**裸的** `bundle exec jekyll build`，不带 `--config` 参数。要用叠加配置就必须修改这个 workflow 文件。

**权衡**：改 `_config.yml` 的 3 行 **vs** 改 CI workflow 文件。后者更底层、影响面更大（workflow 一旦改错，整个部署链路瘫痪）。因此改 `_config.yml` 才是真正的最小改动。

### 5.2 为什么需要 `.nojekyll`

见 [`04_GitHub官方要求对照.md`](04_GitHub官方要求对照.md)。简述：

- Pages 发布源为分支时，默认会对该分支内容再跑一遍内置 Jekyll
- Jekyll 默认丢弃以 `_`、`.`、`#` 开头的文件和目录
- al-folio 的构建产物根目录含 `_pages/`，因此被丢弃（实测 `/_pages/dropdown/` 返回 404）
- 加上 `.nojekyll` 后 GitHub 原样发布，问题消失（实测恢复为 200）

### 5.3 PAT 的安全处理

推送需要认证。常见做法是把 token 写进 remote URL（`https://user:token@github.com/...`），但这会让 token **永久留在 `.git/config` 里**。

本项目采用的做法：

```bash
docker exec -e GH_TOKEN='<token>' <容器> bash -lc '
  git -c credential.helper="!f(){ echo username=dds131; echo password=$GH_TOKEN; };f" \
      push https://github.com/dds131/dds131.github.io.git main:main'
```

- token 只存在于**进程环境变量**中
- 不写入 `.git/config`，不出现在 remote URL
- 不出现在命令行 argv（`ps` 里看不到）
- 不落任何文件；本目录下所有脚本和文档均不含 token
- 用完即散，容器里不留痕迹

### 5.4 为什么用显式 refspec `main:main`

本地仓库有 3 个备份 tag（`al-folio.v1.0.0.*` 等），它们是**纯本地的回退锚点，不应该出现在 GitHub 上**。用显式 refspec `main:main` 而不是 `git push --tags` 或 `--follow-tags`，可以确保只推分支、不推 tag。
