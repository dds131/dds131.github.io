知识库 · 机器人模仿学习与 VLA · RTC · Runtime
  • OR 合流：可从 Guided Inpainting 或 Training-Time RTC 进入本页；二者是平行 proposal 分支，不要求同时完成。
  • 范围：本页拥有调度、队列、提交、下发、ack/feedback、故障状态与 trace；不重新推导 VJP，不重复训练 Loss，也不把运行时写成新动作生成算法。
  • 执行边界：页面只给契约、伪记录和验证设计，不运行模型、训练、仿真、服务或机器人，不提供真机阈值、私有地址、凭据或可执行部署命令。

RTC Runtime 不生成第三种动作策略；它把 Guided 或 Training-Time 产生的 proposal 放进同一个时序、队列、权限和安全契约中，决定接受、丢弃、提交、下发或降级。

  • 用五条 lane、事件 ledger 与四种 delay 解释“异步推理”和“动作连续”为什么不是同一件事。
  • 按绝对 tick 裁掉过期动作，以 snapshot → validate → compare-and-commit 实现不阻塞控制线程的发布。
  • 把 lifecycle、inference job 与 queue 三个正交状态机、typed reason、dispatch gate 和 trace 组合成可验证的 Runtime contract。

Runtime 是合流与执行所有者

Runtime 接受 proposal，不接管方法身份

Guided 分支在推理期用旧块连续性引导生成；Training-Time 分支用兼容 checkpoint 生成以旧 prefix 为条件的 postfix。它们输出的都只是候选动作块 proposal。Runtime 不改变分支的数学含义，也不把两种结果混成匿名数组：每个 envelope、queue entry、commit、dispatch 与 trace 都保留 branch=guided|training_time，以便回答“这一条命令由哪种能力产生、经过了哪些 gate、为何被接受”。

merge_policy:any 表示任一兼容分支都可进入共享 Runtime，而不是先 Guided 再 Training-Time，也不是两者必须同时成功。Runtime 的职责始于 branch adapter 之后：统一 schema、时钟、Action ABI、normalization、authority、generation、过期裁剪、安全验证与 controller 交接。若 proposal 不满足公共契约，Runtime 应拒绝并写 typed reason，不能猜测、补零或偷偷换分支。

异步推理不自动等于 RTC 连续性

普通 async inference 只说明请求和返回没有阻塞调用方。它可以返回过期动作、覆盖新任务、在 reset 后写回旧结果，或让队列耗尽。RTC 连续性还要求：控制线程按 Delta_ctrl 推进；推理期间仍有有效 runway；返回块与当前绝对 tick 对齐；过期 prefix 被裁掉；提交是原子的；下发继续经过 authority、安全与 controller gate。因此“放到后台线程”只是拓扑变化，不是系统正确性证明。

Proposal owner

Guided/Training-Time 生成候选块并提供分支证据；它们不能直接把数组写进 controller。

Runtime owner

在绝对 tick 上验证、裁剪、原子替换队列，维持 generation 与 provenance。

Safety owner

决定命令接受、改写、拒绝与 fallback；队列平滑不能替代安全判定。

Controller owner

接收下发并产生 ack；applied feedback 是后续事实，不由 ack 代替。

三层动作事实不能塌缩

模型空间 proposal 是 policy 输出，可能仍在归一化坐标或需要 adapter；postprocessed command 已完成反归一化、frame/unit 变换和必要约束；applied feedback 是 controller/robot 实际执行后的观测事实。三层必须有各自引用和 hash。proposal 被 commit 不代表已 dispatch，dispatch 被 ack 不代表物理上 applied，安全层改写后的 command 也不能继续冒充原 proposal。

Runtime 页面因此不声明“无缝即安全”。动作值连续可以改善视觉或控制平滑，却不证明 collision、joint/velocity limit、workspace、human stop 或 controller health 合格。fallback 的 owner 和 policy reference 必须来自 Safety/机器人控制契约；queue underflow 不能在本页擅自解释成 hold-last。

控制/推理双线程与事件 Ledger

五条 lane 比“两线程”更接近真实责任边界

实现上可能只有两个 OS thread，也可能跨进程，但系统语义至少包含五条 lane：Sensor/Control 产生观测并消费下一 tick；Runtime Queue 保存已提交命令；Inference 对快照生成 proposal；Safety 审核待下发命令并拥有降级政策；Controller 接收、确认并产生 applied feedback。把 Safety 与 Controller 隐入控制线程会让 ack、改写与 fallback 失去独立证据。

Event Ledger 是跨线程唯一可审计的时间账本

wall clock 用于人类日志，不能决定队列顺序；调度使用单调时钟与控制 tick。定义 Delta_ctrl 为目标控制周期，k 为不回退的绝对控制 tick。至少区分 k_obs（观测归属）、k_new（proposal 局部 index 0 的目标 tick）、k_ready（推理结果可见）、k_commit（成功替换队列）和 k_dispatch（命令交给 controller）。若外部时间戳回退或跳变，记录 clock_discontinuity，不让 wall time 倒流重排动作。

每个 tick 的 ledger 记录计划时间、实际唤醒、skipped tick、消费的 queue generation、chunk/local index、authority epoch、safety verdict、dispatch/ack/feedback 引用。控制循环晚醒两个周期时，不应通过“数组只加一”假装中间 tick 存在；ledger 明确标出 skipped tick，并让下一绝对 tick 参与过期裁剪。时间换算规则本身也需要版本和 hash，避免升级 rounding 方式后历史 trace 无法复算。

论文 Algorithm 1 与生产增强分层

论文事实 RTC Section 4.3 的 Algorithm 1 让 GetAction 每个 control period 被调用：在 mutex 内更新最新 observation、递增 t、通知 condition variable，然后返回 A_cur[t-1]。InferenceLoop 等待 t>=s_min，启动时取 s=t，用 A_cur[s:H] 作为 leftover，以有限延迟 buffer 的最大值预测 delay；模型推理在锁外完成。线程返回后再次加锁，把实测 t 写入 delay buffer，并令 t=t-s 后发布新块。

工程增强 生产映射还需要 absolute tick、reset/authority epoch、queue generation、ABI/contract hash、safety/controller 状态和完整端到端计时。论文变量 t 是算法中的离散执行计数，不应被扩写成所有 transport、ack 与 feedback 的事实；工程记录应保留论文语义，同时另立 ledger 字段。

统一 Proposal Envelope 与分支 Gate

先过公共 gate，再进入分支 gate

公共 gate 与生成方法无关：schema/version 可解析；request/proposal ID 唯一；episode、reset epoch、authority epoch 和 task version 未变化；observation freshness 合格；shape 为 [H,M] 且所有数值 finite；Action ABI、normalization、policy I/O contract 与 capability hash 匹配；snapshot generation 仍可比较；absolute tick join 可计算；safety validator 可用；proposal 未被更新请求 supersede。任一步失败都返回 typed reason，且 rejected/discarded 记录不保存动作 payload 引用。

Guided gate 额外验证 mask schedule/digest、旧块 applied provenance、VJP finite 与配置过的 underprediction 接受规则。裁剪必须按 d_meas，不能因 d_hat 较小就执行已经过期的 prefix。Training-Time gate 验证 checkpoint 明确声明 per-token time、clean-prefix/postfix capability、支持范围 d_train_max 与 compatible manifest；普通 checkpoint 不得靠运行时布尔开关冒充 trained mode。

Accepted · 公共 gate 与所选 branch gate 均通过

Runtime 仍须按绝对 tick 计算有效后缀，并在 compare-and-commit 时复核 generation/epoch；gate 通过不是立即 dispatch。

Stale epoch · reset 或 authority 已变化

无论 Guided 还是 Training-Time 都以 stale_reset_epoch 或 authority_changed 丢弃。旧 job 可以完成计算，但不能提交。

Fully expired · i_start 大于等于 H

返回 proposal_fully_expired，valid ranges 与 generation_after 为 null；不把最后一项重复填满 runway。

Guided under-predicted · d_meas 大于 d_hat

记录 delay_underpredicted。是否仍有足够有效 horizon 需由显式接受策略决定，不能静默忽略预测误差。

Training-Time prefix outrun · d_meas 大于 d_cond

返回 trained_prefix_outrun 并丢弃，因为模型只被条件化到更短 prefix，超出部分不是可证明的连续条件。

Delay out of support · d_meas 大于 d_train_max

返回 delay_out_of_support。即使数组还有 postfix，也不能声称 checkpoint 学过该条件范围。

调度、Backpressure 与延迟预算

单 in-flight 与 latest-wins 是清晰的默认基线

控制线程从不等待模型。它在 queue 低于 low-watermark 时发布 inference intent；scheduler 保持最多一个 in-flight job。job 运行期间到达的新 observation 只替换 pending observation slot，形成 latest-wins，而不是无限堆积推理请求。当前 job 完成后，若 runway 仍低或 pending observation 更新，再创建下一快照。这样 backpressure（下游处理不过来时主动限制上游积压）是显式策略，而不是靠内存最终耗尽。

多 worker 可能提高吞吐，却会产生乱序 ready、额外 GPU contention 与更多 generation conflict；除非任务证明收益并定义 selection policy，否则 inference_workers:1 更容易审计。即使单 worker，也必须处理“旧 job 返回时新的 reset/authority/task version 已发生”。结果是否过期由 epoch/generation 比较决定，而不是由完成顺序或 thread ID 决定。

触发条件不应只有固定 s_min。工程 scheduler 可综合 queue runway、预测延迟、observation freshness、job 状态与 cooldown，但每个阈值都属于版本化 runtime manifest。页面只解释结构，不给真机默认数值。若低水位频繁触发而 job 尚未完成，计数一次 backpressure event，不创建重复请求；若 runway 已不足以覆盖预计端到端时延，则进入明确 degraded/fallback 路径。

四种 delay 各回答一个问题

$$ d_{wall}=\left\lceil\frac{T_{e2e}}{\Delta_{ctrl}}\right\rceil, \qquad i_{start}=\max(0,k_{next}-k_{new}). $$
  • d_hat：delay predictor 给生成分支的输入，回答“预计会消耗多少 tick”。
  • d_cond：proposal 实际采用的连续性条件长度，回答“模型对多长 prefix 作了承诺”。
  • d_wall：由选定端到端 wall-time 边界换算的诊断值，回答“物理时间约跨了多少控制周期”。
  • d_meas：ledger 中从 snapshot/目标起点到当前 next tick 的实际已消费控制 tick，回答“提交时究竟该裁多少”。

d_meas 决定裁剪；d_hat 与 d_cond 决定分支 gate；d_wall 用于解释延迟预算和时钟异常。四者可以相等，但不能因常见相等就合并字段。模型自身的生成时间参数（例如 flow/diffusion time）是算法坐标，不进入 queue delay。

选定统计分位数后，把 capture、preprocess、model、postprocess、validate、commit、transport 的同口径分量相加得到 T_e2e，再除以 Delta_ctrl 向上取整得到 d_wall。将 d_wall 与当前 queue runway 比较，只能提示“在该分位样本下预算覆盖/超出”，不能自动生成部署参数。

延迟预算边界要写在测量定义中

只计 model forward 会系统性漏掉 capture、预处理、adapter、验证、锁竞争与 transport；从用户 wall clock 跨机器测量又可能引入未同步时钟。首选同进程 monotonic clock 标记边界；跨进程则用 trace span 与经过验证的 clock relation，并把不确定度写入记录。每个分位指标必须同时给样本数、时间窗口、branch、runtime/model/version 和 warm/cold 条件。

动作队列、Absolute Tick 与过期裁剪

队列条目由绝对 tick 主键连接

一个 queue entry 至少包含 absolute_tick、chunk_id、local_index、branch、queue_generation、command reference、proposal provenance、authority epoch 与 task version。索引 0 只有在绑定 proposal_start_tick=k_new 后才有物理含义。当前控制线程下一次要消费的 tick 为 k_next，proposal horizon 为 H，则有效局部起点：

$$ i_{start}=\max(0,k_{next}-k_{new}), \qquad \mathcal I_{valid}=[i_{start},H). $$

若 0<=i_start<H，局部 index i_start 对应 k_next，后续条目的 absolute tick 严格递增且不重复；若 i_start>=H，整块已经过期，返回 proposal_fully_expired。不要把 H-1 重复下发，也不要把数组向左挪后仍沿用旧 k_new。若裁剪后长度小于 min_valid_horizon，返回 valid_horizon_too_short，是否降级由 runtime/safety policy 决定。

replacement 不是数组整体覆盖

提交时从 k_next 开始构造新队列，确认 head tick 正好等于当前 next tick，尾部严格连续。旧 generation 中已消费、已 dispatch 或被 authority 接管的条目不可被回写。尚未消费的旧尾部是被替换、拼接还是保留，只能按版本化 queue policy 执行；RTC 的共享基线应显式记录 replacement semantics，而不能靠容器 clear()+extend() 猜测。

动作值还要经过 Action ABI 与 normalization 检查。关节顺序、frame、unit、rate/position/velocity 语义和 adapter 版本任一不匹配，都在入队前拒绝。shape [H,M] 正确并不代表语义正确。若 safety 会逐 tick 改写 command，每条 entry 同时保留 proposal ref、postprocess ref 和 safety verdict ref，不能把改写值覆盖回模型 artifact。

Property invariants

对任意 H,k_new,k_next，property test 应覆盖负差、零差、边界 H-1、恰好 H 和远大于 H：有效范围非空当且仅当 0<=i_start<H；fully expired 当且仅当 i_start>=H；committed ticks 严格递增、无重复；replacement 后 head tick 等于提交瞬间 next tick；拒绝结果没有 action ref；每次成功 commit 的 generation 单调增加；reset/authority change 后的旧 proposal 永不 commit；branch/task label 与每个 entry 同步。

Snapshot、锁边界与原子提交

Snapshot → validate → compare-and-commit

推理线程短暂按固定顺序取得 observation_state 与 action_queue 锁，复制不可变 Runtime Snapshot，然后立即释放。模型和 branch adapter 在锁外运行。返回后先做不依赖共享可变状态的 schema/finite/hash 验证，再以固定锁顺序读取当前 epoch、authority、task 和 generation；只有都与 snapshot 兼容，且绝对 tick 裁剪成功，才一次性写入新 queue、generation 和 commit record。

compare-and-commit（比较后提交）意味着“我当初看到的前提现在仍成立才写入”。它避免慢 job 覆盖新队列。generation 是单调代次，不是队列长度：队列被 clear 后又 refill 到相同长度，长度比较会误认为没变化，这就是 ABA——状态从 A 变到 B 又看似回到 A。单调 generation/epoch 让相似表象仍可区分。

Control Tick、Dispatch、Ack 与安全层

Control tick 只做有界、可预测工作

每次 tick：推进 ledger；读取当前 authority/reset/task；检查 queue head 的 absolute tick 与 generation；若无有效条目则报告 queue_underflow 并把控制权交给已配置 fallback owner；对命令做 frame/unit/finite/ABI 与 deadline 检查；调用 Safety 获得 accepted/modified/rejected verdict；向 Controller adapter 发送；记录 pending ack；最后更新 observation/feedback 引用并在需要时触发低水位 inference intent。任何步骤都不能同步等待模型。

若 queue head 小于当前 tick，逐项标记 expired/skipped 后再寻找当前 tick，不把迟到动作补发；若 head 大于当前 tick，说明存在 gap，不能假设未来动作适用于现在。skipped_tick 与 deadline_miss 应区分：前者是 ledger 中控制 tick 跨越，后者是特定命令未在 deadline 内下发。外部时钟不单调则用 clock_discontinuity 隔离，不重写 absolute tick 历史。

Dispatch gate

dispatch 前至少验证：absolute tick 等于 current tick；queue generation 仍是当前；reset/authority epoch 与 task version 匹配；Action ABI、frame、unit 与 controller capability 匹配；command finite；Safety validator 可用并返回明确 verdict；controller session、watchdog 与 human authority 状态允许；deadline 未过。任何一项失败都不发送原命令，并记录 owner 与恢复条件。

Safety modified 不是失败，但产生新的 command reference 和 provenance edge；rejected 进入安全契约定义的 fallback。Runtime 不自行选择 hold-last、zero 或 stop。某些系统 hold-last 可能危险，另一些系统 zero 也可能危险，所以页面只要求 fallback manifest 指向经审查的安全控制器。

失败状态机、降级与恢复

三个状态机正交，不压成一个“运行/失败”开关

Lifecycle 描述 runtime 是否 booting、ready、paused、degraded、stopping；Inference Job 描述 idle、snapshot、running、ready、rejected/cancelled；Queue 描述 empty、healthy、low、underflow、invalidated。三者可组合：例如 lifecycle=ready、job=running、queue=low 是正常压力状态；lifecycle=degraded、job=idle、queue=underflow 则由 fallback 接管。把它们压成一个 enum 会制造组合爆炸，也难以指出谁负责恢复。

恢复不是把状态位改回 ready

恢复需证明触发条件消失，并从新快照建立干净代次。reset/authority/task change 后，即使旧 inference 随后成功，也只能被丢弃；不能“补交”。从 degraded 回 ready 前至少检查 monotonic clock、Safety、controller session、manifest/ABI、queue head tick、epoch/generation 与 trace sink。若策略允许 retry，必须有次数/时间预算和 jitter 记录，防止 retry storm 加重 backpressure。

pause 时冻结新的 proposal commit 还是清空 queue，要由 lifecycle contract 定义；resume 增加 epoch 或新 generation，避免暂停前 job 在恢复后写回。shutdown 首先停止新 snapshot，然后使 in-flight 结果不可 commit，再按 controller/Safety contract 完成队列处置。异常路径与正常路径共享同一事件 ledger，不能只在日志文本里写“已恢复”。

Observability、Trace 与隐私

Trace 必须能连接请求、动作与反馈

最小 join keys 包括 trace_id/request_id/proposal_id/commit_id/dispatch_id，以及 observation_id,episode_id,absolute_tick,chunk_id,local_index。每个 span 还带 branch、runtime/model/contract/ABI hash、reset/authority epoch、snapshot/current queue generation、四种 delay、valid range、reason、safety verdict、controller status 与 feedback ref。没有这些连接，仅凭线程日志时间顺序无法证明哪次推理影响了哪一 tick。

日志中的 status 必须与 state machine 一致：proposal ready、committed、dispatched、acked、feedback observed 是不同事件。跨进程 trace 若采样，需要保证错误、降级、reset、authority change 与 safety intervention 不被普通采样率丢弃；健康高频 tick 可以聚合，但必须保留可复算计数与抽样政策版本。

指标按分布报告，不只报平均值

延迟指标覆盖 capture/pre/model/post/validate/commit/transport/e2e，以及 d_hat,d_cond,d_wall,d_meas 的误差分布；queue 指标覆盖 runway、low-watermark、underflow、expired/short proposal、generation conflict；freshness 覆盖 observation age 与 superseded request；control 覆盖 tick jitter、skipped/deadline miss、dispatch/ack/feedback；safety 覆盖 accepted/modified/rejected 与 fallback duration；concurrency 覆盖 in-flight、lock wait、backpressure 和 cancelled result。

任何 P50/P95/P99/max 都同时报告样本量、时间窗口、版本、branch、任务分层和 cold/warm 条件。不同窗口的 P99 不可直接相减，平均 latency 也不能替代 tail。d_hat-d_meas 需要方向：正值是保守预测，负值是 underprediction。成功率与连续性指标需在 Experiments 页面解释，本页只定义观测契约。

默认最小化与脱敏

默认不记录原始图像、完整语言指令、真实地址/端口、凭据、设备 ID、私有 checkpoint 路径、高频完整动作 payload 或 PII。使用 opaque ID、不可逆 hash、shape/finite/digest、聚合统计和受访问控制的 artifact reference。需要调试 payload 时走单独授权、短期保留、审计访问与删除流程，不能因为 debug=true 绕过治理。

动作本身也可能泄露任务、设备或人类行为。trace 只需证明 ABI、范围和 provenance 时，保存 hash、统计与受控引用即可。错误消息不得回显 secret 或完整请求；第三方 telemetry 需确认数据边界。页面示例全部使用占位符，不包含可连接服务的真实标识。

四条端到端验收叙事

静态字段正确只是最低门槛。发布前应让审阅者沿着同一组 opaque ID，从 observation 一直走到 feedback，再故意改变时序和 authority，确认系统不是“正常路径看起来能跑、异常路径靠猜”。以下叙事不提供真实阈值或设备动作，而是规定事件次序、可见状态和反证条件；每条都可以映射为 deterministic scheduler 的模型测试与人工 trace walkthrough。

场景一：健康 Guided proposal 在控制持续推进时提交

控制线程在绝对 tick k0 捕获 observation，queue runway 触发低水位事件。scheduler 取得包含 reset/authority/task/generation 的 snapshot，并标记 branch=guided。推理在锁外运行；这段时间 control 连续消费旧 generation，每个 tick 仍经过 Safety 与 Controller。proposal 在 k_ready 到达后先过公共 gate，再核验 Guided mask、旧块 provenance 与 VJP finite。Runtime 从当前 k_next 计算 i_start，而不是复用启动时数组 index。

若有效 horizon 足够，compare-and-commit 在一个临界区内把 generation 从 g 增至 g+1，commit record 写明 local/absolute half-open range。下一 control tick 只能看到完整的新 generation 或完整的旧 generation，不得看到一半旧尾部加一半新头部。Safety 若接受，dispatch 产生独立 ID；Controller ack 后仍保持 feedback 为空，直到实际反馈事件抵达。验收证据是 ledger 中绝对 tick 连续、无重复，旧块与新块的边界可按 provenance 复算，而不是动作曲线“看起来平滑”。

反证包括：control thread 在 model span 中出现等待；proposal ready 即被标记 applied；d_hat 被写进 measured delay；Safety modified 的值仍指向原 command hash；ack 事件提前填充 feedback。任一出现都说明状态层级被压缩，应阻断发布。

场景二：Training-Time proposal 被实际 delay 追过

兼容 checkpoint 声明 d_cond 和训练支持上界。推理开始时预测值可能较小，但返回前出现 latency spike，ledger 显示 d_meas>d_cond。即使 i_start<H 且数组还有若干非过期位置，Runtime 也必须返回 trained_prefix_outrun：这些位置是基于较短 clean prefix 生成，不能因为 shape 仍合法就声称连续性条件成立。若同时 d_meas>d_train_max，trace 可以附加 out-of-support 诊断，但 primary reason 的优先级要由版本化 reason policy 固定。

discard 记录的 generation_after、valid ranges、commit tick 与 action ref 均为空。queue 继续消费原有条目；若 runway 到达低水位，scheduler 不并发堆积同类 job，而是更新 latest pending observation。若随后 underflow，fallback owner 接管，不能从 proposal 的最后一个位置合成 hold-last。恢复需要新快照落在 checkpoint capability 与 runtime budget 的共同支持域内，并形成新的 request/proposal ID；不得把原 proposal 改写 metadata 后重试提交。

该场景同时验证三个容易混淆的事实：数组未完全过期不等于方法条件仍有效；预测误差不等于实际裁剪量；fallback 可维持系统受控状态却不代表任务动作仍由 VLA 提供。

场景三：推理期间发生 reset 与 authority 转移

在 job 运行时触发 episode reset，reset_epoch 单调增加，旧 queue 被失效；随后 human authority 接管并增加 authority epoch。旧 job 即便正常完成、数值 finite、horizon 足够，也要先因 epoch 不一致被丢弃，不能进入 Safety 试探性审核。取消底层计算可以节省资源，但取消回调可能延迟或失败，所以正确性必须由 compare gate 保证。

当 control 权限交还 policy 时，Runtime 从当前 episode、authority、task 与空/新 queue 状态创建全新 snapshot。旧 observation、leftover、condition variable 唤醒和 pending request 均不得跨 epoch 复用。trace 用旧 request 的 stale_reset_epoch/authority_changed 与新 request 的健康路径形成可见分界，审阅者能证明没有“同 ID 复活”。

这个测试应再加入 ABA：reset 后 queue 清空，再填入与 reset 前相同长度的 fallback 条目。若实现只比较长度、head index 或数组地址，旧 proposal 可能错误提交；只有单调 reset epoch、authority epoch 与 queue generation 联合比较才能拒绝。恢复完成的证据不是 lifecycle 被人工设回 ready，而是新代次的 Safety、controller、clock、ABI 与 trace sink 自检全部通过。

场景四：dispatch 后 NACK，反馈又超时

已提交 command 在 deadline 内通过 Safety，但 Controller 返回 NACK。Runtime 记录 controller_nack，不得把 queue pop 当成 applied，也不得用 ack 字段的存在表示成功。若协议随后没有给出可关联 feedback，独立计时器产生 feedback_timeout；二者可以出现在同一 dispatch 的事件链上，但不能互相覆盖。Safety/Controller contract 决定是否停止、切 fallback 或重新建立 session，Runtime 只执行已版本化的处置并保留 owner。

若 NACK 后仍有后续 queue 条目，它们不自动安全：controller session、authority 或 Safety verdict 可能已失效。恢复流程应重新验证 session capability、清理或隔离旧 generation、建立新的 dispatch sequence，并确认 observation/feedback tick 归属。任何把未确认命令算作“已执行 prefix”送入下一 Guided/Training-Time 条件的实现，都会污染 continuity provenance。

验收时还要故障注入 Safety gate unavailable。预期结果是未审核命令不下发，reason 为 safety_gate_unavailable，fallback 由 Safety owner 接管；绝不能为了减少 underflow 指标而绕过验证器。该负例比成功 dispatch 更能证明系统边界真实存在。

兼容性与发布矩阵

Runtime release 不是只冻结一个容器版本。至少联合固定 runtime manifest、branch capability、model/checkpoint、Action ABI、normalization、policy I/O contract、Safety rules、Controller adapter、clock conversion 和 queue policy。任一 hash 改变都应形成新兼容性行；“同一模型名”或“shape 没变”不足以复用旧结论。测试报告按组合记录 pass/fail/unsupported，而不是把 unsupported 当 failure 混入成功率。

“已兼容”也有范围：它只覆盖报告中的 branch、task class、runtime/controller 版本和测试窗口。硬件负载、网络拓扑、camera pipeline 或 Safety policy 改变后，旧 P99 与 queue runway 结论不能自动外推。发布清单应明确哪些变化允许复用静态验证，哪些必须重跑性能/故障实验，哪些需要重新做风险评审。

发布判定与可回滚边界

发布 gate 至少分四层。第一层是结构与 contract：schema、graph、hash、ABI、模板和来源完整。第二层是确定性逻辑：absolute tick、裁剪、generation、epoch、锁顺序和 reason property tests 全通过。第三层是受控系统证据：相同版本下的 tail latency、queue runway、连续性、controller 与 Safety fault injection 达标。第四层才是任务/风险审查；它由独立实验与安全流程拥有，不能因前三层通过就写“生产可用”。

回滚对象是完整兼容组合，不是只降级模型文件。若 runtime 已改变 queue semantics，而 checkpoint 回到旧版，混合组合可能从未验证。回滚 manifest 应绑定 runtime、branch capability、ABI/normalization、Safety/controller adapter 和 trace schema，并说明进行中的 job、已提交 queue 与 authority 如何处置。回滚期间旧 generation 不得跨版本继续提交；必要时增加 epoch 并按安全契约重建队列。

阻断条件包括：任何 source baseline 被意外修改；双前驱/双后继图不再精确；控制 tick 可能等待模型；拒绝记录保留动作 payload；reset/authority 后旧 job 可写回；Safety 不可用仍能下发；ack 被当作 applied；P99 缺少样本量/窗口；trace 暴露原始敏感数据。不存在这些反证仍不等于效果成立，只表示 Runtime contract 具备进入 Experiments 与固定版本 Source Code 审阅的资格。

审阅者的复算路径

先从 dispatch record 的 absolute tick 与 generation 反查 commit，再由 valid absolute range 还原 proposal 的 local index；用 k_next-k_new 独立计算 i_start，核对 d_meas 与裁剪一致。随后检查 snapshot/current epoch、authority、task 与 generation 比较，确认 commit 没跨越 reset 或 ABA。再检查 branch gate：Guided 的预测包络与 VJP/mask provenance，或 Training-Time 的 d_cond/d_train_max capability。

接着从 command ref 分离模型 proposal、postprocess 与 Safety modified 值，确认 dispatch verdict、controller status 和 feedback 都是独立事件。最后查看性能聚合是否能回到同一版本/branch/window 的 trace 样本，并验证脱敏策略没有为了审计而保存完整动作或图像。任何 join 断裂都应标记证据不足，而不是用临近日志行或人工记忆补齐。

这条复算路径也是最小文档测试：新成员不读实现内部变量，只凭 manifest、schema、ledger 和固定版本映射，应能回答“哪次观测触发了哪种分支、候选块为何被裁、哪几项被提交、Safety 是否改写、Controller 是否确认、反馈是否到达、失败由谁恢复”。如果回答依赖某位作者口头说明，契约仍不完整。

常见误判与审计问答

“动作曲线没有跳变，是否证明 RTC 正确？” 不能。平滑可能来自旧队列持续执行、Safety 限幅、Controller 滤波，甚至只是可视化降采样。正确性先由 absolute tick、provenance、generation 和 epoch 证明；连续性质量再由 Experiments 的同口径指标证明。反过来，一次任务所需的快速合法转向可能在曲线上不平滑，也不能仅凭外观判为失败。

“proposal 在 deadline 前 ready，是否必然能提交？” 不能。ready 只结束 inference span；其后仍有公共/分支 gate、当前 generation 比较、有效 horizon、Safety 可用性与 commit 临界区。deadline 还必须写明属于 inference ready、queue commit 还是 controller dispatch。不同边界共用一个 latency 名称，会把调度问题误诊成模型问题。

“queue 还有条目，为什么要触发 inference？” scheduler 依据 runway 与延迟分布提前补充，而不是等 empty 才行动。low-watermark 是触发信号，不是安全证明；它与 d_hat、branch support、observation freshness 和单 in-flight 状态联合判断。若每个 tick 都因 low 重复创建 request，说明 backpressure 未实现。若永远等 underflow 才请求，异步线程也无法提供连续性。

“同一数组 shape 是否足以证明 adapter 兼容？” 不足。相同 [H,M] 可以代表不同 channel 顺序、frame、unit、控制模式或 normalization。Action ABI hash 和 contract hash 必须匹配；golden vector 应覆盖每个通道、正负方向、边界与 round-trip。Runtime 不允许用截断、pad、重新排序猜测修复未知 ABI，因为这种修复可能数值 finite 却物理错误。

“为什么 reset、authority 与 task version 要分开？” reset 表示 episode/状态重建，authority 表示谁有下发权，task version 表示语义目标。它们可能独立变化：human 接管不一定 reset；任务语言修订不一定改变 controller authority；传感器重置也不一定更换任务。分开的单调 epoch/hash 能给出精确 reason 与 owner，也避免一次变化被另一个字段偶然掩盖。

“为什么 rejected record 不能保留动作引用？” 一方面避免未通过 finite、ABI 或隐私 gate 的 payload 进入长期制品；另一方面保证下游不会把“有 action ref”误认成可执行证据。必要诊断保存 schema、shape、digest、统计与受控短期引用，由专门权限流程管理。commit/dispatch/apply 的引用链只从成功 gate 建立。

“latest-wins 会不会丢掉重要 observation？” 它明确丢弃尚未创建 snapshot 的旧 pending observation，以限制积压；已经创建的 snapshot 仍用 request ID 可追踪。是否允许跳过某类事件由上游任务/安全 contract 决定：急停或 authority 变化不是普通 observation，必须走独立高优先级通道。latest-wins 不能被用来吞掉 reset、安全事件或 Controller 故障。

“Safety modified 后还能用于下一次连续性条件吗？” 可以或不可以，取决于分支 contract 需要 committed、dispatched 还是 applied provenance。关键是引用真实层级并记录 freshness，绝不能把修改后的命令伪装成原 proposal。若 feedback 尚未到达，系统只能声明已 dispatch/acked 的事实，不能提前声称 applied prefix；能力不足时应拒绝该连续性条件或进入有定义的保守路径。

最小证据包与所有权交接

一次 Runtime 审阅的最小证据包包含：冻结来源清单与访问日期；页面/实现 baseline hash；graph/front-matter 检查；runtime 与 branch capability manifest；ABI、normalization、contract 与 clock 版本；属性/并发/故障注入报告；按版本和 branch 分层的 latency/queue/control/safety 指标；脱敏 trace 样例；已知限制和 unsupported 组合。证据包只保存引用与摘要，不复制受限数据或凭据。

Runtime 团队负责证明“候选块被正确对齐、验证、提交和记录”；模型团队负责分支 capability 与 proposal 质量；Safety 团队负责 verdict、fallback 与恢复条件；Controller 团队负责协议、ack/feedback 和设备侧状态；实验团队负责连续性、reactivity、任务成功与统计效力。某个团队可以实现多个组件，但证据 owner 仍需分开，以免模型指标替代系统正确性，或队列稳定替代安全审查。

交接到 Experiments 时输出的是可测假设和 trace schema，不预写结果；交接到 Source Code 时输出的是固定版本映射和待核对符号，不假装滚动仓库永久一致。两条路线都可能发现 contract 缺口并返回 Runtime 修订，因此导航是同权分叉而不是瀑布式“先代码后实验”。只有当缺口通过新版本 manifest、测试与证据关闭，原 blocked/unsupported 行才可更新。

最终完成定义是：页面身份和图关系精确，内容边界没有越权；所有关键状态与动作层级可区分；正常、迟到、reset/authority、NACK/Safety 故障均能产生确定 reason 和 owner；审阅者能从脱敏记录独立复算裁剪与提交；源文件保持只读且正式补丁可严格应用。它不宣称某套真实系统已经安全部署，也不把教学模板直接转成运行参数。

审阅结论还要区分“检查通过”“证据不足”和“明确失败”。检查通过仅限被测版本与范围；证据不足不会自动转成通过，需要补齐 trace、版本或样本；明确失败则保留反例、reason 与 owner，直到新版本关闭。这样的三值结论能防止缺失数据被统计为零故障，也避免一次健康演示覆盖未测试的并发和恢复路径。
