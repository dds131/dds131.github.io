工程问题记录

抱闸、抖动、延迟、断流、回位——十一个真实问题的现象、取证、根因与量化效果

← 项目主页 ·系统架构 ·PyRoki 逆解器 ·数据采集与保存 ·工程问题记录

这一页记录的是控制回路上真实发生过的问题。每一条都按「现象 / 根因 / 解法 / 效果」四段写，尽量给出当时实测的数字——包括那些最后证明我判断错了的排查过程，因为走错的那一段往往比结论更有用。

先分清四种“停止”

“松开离合”“恢复数据软急停”“正常退出”和“Ctrl+C 紧急停止”在代码里是四条不同路径。把它们混成一个词，会直接误判第 10、11 条问题：

操作/状态 发送链行为 是否规划减速 适用目的
正常遥操作松开右手握把 当前正式配置停止产生新的跟随命令；曾试过 0.2 秒、约 22 帧重发末帧，但真机无改善，已从推荐命令移除 否；重发相同位置也不是减速轨迹 离合与重新锚定，不等于急停
恢复会话 SOFT_STOP 左手握把 ≥80% 持续 100 ms 后触发；0.25 秒内沿原规划时间轴减速，110 Hz 发送不断，随后保持冻结点并交给人工 是；继续经过状态化滤波、限速和限加速度 模型控制到人工接管的平滑交接；不是硬件安全急停
终端 e 走完整收尾：停止、恢复终端、断开连接、打印统计 按正常退出流程 无故障时的推荐退出方式
Ctrl+C 优先发送紧急停止、断连并硬退出，跳过可能阻塞的其余收尾 不等待普通收尾完成 真正需要立刻停止时；代价是终端回显可能来不及恢复

诊断时也要选对开关：--backend dryrun 只跑计算链而不驱动真机，适合方向和状态机检查；正式低开销运行使用 --no-log，若要查“主循环很快但实际发送断流”的问题，应单独启用 --send-gap-csv <文件> 记录真实发送间隔，而不是只看单帧计算耗时。

1. 回位之后一握手柄，机械臂立刻抱闸锁死

现象
按键盘回位键让机械臂回到 home 位之后，再握 VR 手柄，机械臂立刻抱闸掉使能、锁死。这是整个项目里最严重的一个问题。
取证
逐帧分析真机记录的 CSV：握把上升沿那一帧，指令要求的速度是 164 °/s（折合约 18000 °/s²），七个关节全部朝回位之前的旧位形跑飞 13.65°。
根因（两层串联）
第一层决定了跑飞的方向：逆解是异步 worker，松握把和回位期间主循环不再调用求解，worker 里留着的是几秒前的陈旧解，再握把时被当成新解取出来用。
第二层决定了跑飞的量级：滤波器重置时把「上一帧速度」置成了空值，使得首帧逃逸了限加速度约束。
用独立的物理验算交叉印证：164 °/s 以 1000 °/s² 刹停需要 13.4°，与实测的 13.65° 吻合——根因坐实。
解法
第一层加陈旧解时间门控：取解时若距上次求解超过 0.1 秒就丢弃，保持不动、等两三帧新解。第二层把重置时的「上一帧速度」置为 0 而不是空值（实质就是一行）。两处都用「子类继承 + 覆盖」实现，既有代码零修改。
效果
144.0 °/s、跑飞 13.65° → 0.00 °/s、跑飞 0.00° 真机 2026-07-20 实测抱闸消除。
（这里的 144.0 °/s 与上面取证里的 164 °/s 不是笔误：164 是真机 CSV 里记录到的实际值，144.0 是离线复现该场景时复算出来的指令速度——离线复现受限速层约束、封顶在 144 °/s，真机则因高跟随下会冲过指令而更高。两者指向的是同一次事故。）值得一提的是：只修第二层，跑飞峰值就从 13.65° 降到 0.74°——这说明量级上真正起决定作用的是那一行。

2. 偶发的单帧坏读数把机械臂顶到抱闸

现象
与回位无关的随机抱闸。
根因
真机的关节读数偶尔会串包（TCP 应答错位），导致单帧关节角跳变 29°。而当时的重锚路径无条件信任读数并绕过全部限幅，于是一帧就下发了 29.8° 的阶跃。
解法
把「单帧超阈值就重锚」改成「连续 3 帧一致才重锚」，期间保持不动、一个字节都不下发。
效果
单帧坏读数不再引发抱闸 保留了一个开关可以关掉这道门控用于对比。

3. 每段运动的起停时刻剧烈抖动

现象
手柄从一个位姿移到另一个位姿时，机械臂在起步和停止的瞬间剧烈抖动。单测实测：对 40° 阶跃过冲 5.712°，速度方向折返两次。
根因
手柄停下后指令仍以 144 °/s 冲向目标，直到只剩 5.24° 时平滑器才开始要求减速——而这时需要 3960 °/s² 的减速度，远超 1000 的上限，于是被限加速度拦住。实际需要 14.8° 才刹得住，却只剩 5.24°，结果冲过目标约 10°，再被反向拉回，来回振荡。
解法
增加「目标接近提前减速」：距目标小于 14.8° 时整体同比例降速，从物理上保证刹得住。更远的地方跟手性能零代价。
效果
过冲 5.712° → −0.0000° 起停平滑，可单独回退。

4. 跟手慢 → 快 → 抖 → 稳：三步走

现象一：跟手慢
根因是用了低跟随模式透传，控制器对每个目标做自己的平滑与阻尼。解法：改高跟随。
现象二：高跟随要求透传周期 ≤10 ms，主循环超标
根因：主循环每帧都要走一次 TCP 读关节角，实测 p50 6.5 ms、p95 13 ms、最坏 21.8 ms——单这一次阻塞读就吃爆了 10 ms 预算。
解法：新增一个异步 CAN-FD 后端，继承原后端只覆盖「读关节」和连接管理，用后台守护线程以 50 Hz 轮询、存进带锁缓存，主循环只读缓存。
效果
最坏单帧 17 ms → 0.2 ms 主循环回到 1–3 ms，100 Hz / ≤10 ms 达标。
这次改造还有个意外收获：轮询线程记下的「关节真实测量时刻」后来成了整个数据采集系统的帧对齐锚点。另外，速度和加速度必须在轮询线程内按真实时间差分——如果放在 110 Hz 主循环里对 50 Hz 的缓存做差分，会得到「假零值 + 跳变」的伪速度。
现象三：去掉阻尼后真机开始抖
根因：低跟随的阻尼原本「顺便」滤掉了 VR 的位姿噪声。解法：在噪声进入逆解之前先做一道输入端低通——实测比在关节端滤有效得多。效果：降抖约 78%。

5. 顿挫的真凶不在代码里

现象
真机遥操作时机械臂顿挫、卡一下、然后朝目标快速冲过去。
排查
逐项排除了可视化、日志、机械臂通信、平滑算法——都不是。最后把 VR 端的数据到达情况单独记下来，真相才浮出水面。
根因
是 VR 头显与手柄的无线链路在冻结。 161.4 秒内、在握把持续按住的期间，发生了 14 次超过 100 ms 的数据冻结，最长一次 520 ms；VR 数据的平均到达率只有 85.8 Hz，而主循环跑在 110 Hz —— 意味着 20.6% 的帧读到的是旧数据。冻结恢复那一帧的位姿跳变达 61.6 mm，而正常帧间跳变只有 1.64 mm。
解法
硬件层面：改用路由器组建局域网，让头显与主机在同一个有线局域网内通信，实测稳定得多。（Type-C 转网口走网线也是一种可行方案，本项目最终采用的是路由器组网。）软件层另外提供了关闭可视化、关闭日志两个降延迟开关。
效果
顿挫消除 这条的教训比修复本身更值钱：盯错指标会一直修错地方。

6. 「最差单帧耗时」是一个误导性指标

现象
单独跑遥操作一切正常，一旦同时开数据采集就容易抱闸，日志里的逆解失败计数持续递增。
排查过程（两步都很有意思）
第一步先用逐文件哈希比对确认八十个源文件全部没被改动，排除「代码被改坏了」。教训：版本控制只能证明文件没变，证明不了运行时行为没变。
第二步做对照实验，跑 110 Hz × 4000 帧：纯遥操作最差单帧中位 0.7 ms，加广播 1.0 ms，加相机与录制 1.1 ms，超过 10 ms 的次数全部为 0。这个量级根本解释不了抱闸。
根因
指标本身错了。 主循环有四条「不发送」的出口（未握把 / 逆解未及时出解 / 安全层拒解 / 急停），因此它可以每帧只花 0.3 ms，却连续几十帧一个字节都不发。而高跟随的硬要求是「指令到达间隔 ≤10 ms」，不是「单帧耗时 ≤10 ms」。
采集为什么会加剧：逆解 worker 是同进程的 JAX 线程，采集带来的 GIL 竞争推迟了它出解，触发陈旧解门控丢弃，于是断流。
GIL 实测（24 核）：无竞争时周期 p50 9.15 ms；加一个纯 Python 线程变成 14.20 ms（正好等于解释器默认切换间隔）；加三个变成 p50 20.27 / 最坏 90.98 ms。最反直觉的是，加一个只操作小 numpy 数组的线程同样是 14.20 ms——开销全在 Python 对象层。而会主动释放 GIL 的阻塞 IO 线程、大矩阵运算线程则完全没有影响。
解法
① 把数据采集拆成独立进程（GIL 是每进程一把）；② 新增一个下发监视器，包装发送接口测真实的指令间隔 p50/p95/最大值与超标次数，直接给出「健康 / 零星断流 / 断流严重」的结论；③ 提供可选的指令流保活线程，用绝对时基按固定节拍补发。
效果
保活离线实测：最长间隔 36.5 ms / 8 次超标 → 9.2 ms / 0 次 主循环卡顿 30 ms 的场景下从 39.1 ms / 4 次降到 9.1 ms / 0 次。
诚实说明：这不是硬实时保证，所以保活默认关闭。

7. 从单进程走到四进程

触发
更早的一次尝试留下了实测记录：为了把诊断数据落成 CSV，在 110 Hz 主循环里加了一个后台写线程，最差单帧就从 7.2 ms 涨到 12.1 ms，直接击穿高跟随的 10 ms 红线，方案当场撤回。而相机抓帧加视频编码的负载远大于那个写线程。
根因
除了 GIL，还有两条更硬的约束：机械臂建连接口非幂等（重复建连 → 应答串包 → 坏读数 → 抱闸），VR SDK 是进程内全局状态。所以采集进程绝不能自己连机械臂、也不能初始化 VR SDK。
解法
拆成四个进程，遥操作进程作为唯一数据源每帧广播 128 字节定长包。采集端用一个「接口完全一致的假 loop 对象」承接，同时扮演主循环、位姿源、机械臂后端、夹爪枢纽四个角色——录制器代码一行都不用改，原有的十几组离线单测继续有效，双进程产出的 HDF5 与单进程完全同构。
效果
加广播后主循环最差单帧 1.7–1.8 ms，与不广播无差异 采集进程秒开、崩了重启不影响机械臂。
附带的一条教训
单进程版本后来被停用了，原因很能说明问题：干跑测试显示它能正常启动、能录三路相机、日志一切正常，但悄悄少了四个修复——因为三相机改造是通过共享配置自动继承的，而那四个修复是在分体版入口里挂载的。日志里没有它们的标记，这是唯一能看出来的线索。

8. 回位的速度规划有三个缺陷

现象
机械臂快到 home 位时不平顺、有顿挫。离线仿真跑出的末段速度序列出现反弹（…12.27 → 9.73 → 13.36 → 10.82 → 6.81 → 0.00），且从 6.8 °/s 直接归零。最大加速度 749 °/s²，是设定上限 400 的 1.9 倍；15 个距离组合里 13 个超标，最坏 820。
根因（三条独立）
A 减速途中会重新加速——判据每帧重算刹车距离，减速时刹车距离按速度平方缩小而剩余行程只线性缩小，某几帧就会跳回加速分支，形成锯齿。
B 起刹晚一帧——判据用的是当前速度，而加速段速度还在涨，等判据成立时其实已经刹不住了。
C 落位速度突降——剩余不足一帧行程时步长被截断，反推出的速度仍然很高，下一帧直接归零。
解法
新建一个接口完全兼容的规划器在运行时替换掉原有的，上游零修改。四处改动：刹车锁存（一旦减速绝不回加速分支——回位是点到点单调逼近，中途没有回加速的物理理由）；爬行下限防减速过头停死；前瞻起刹（用「再加速一帧后的速度」算刹车距离，只要再加速一帧就会刹不住，这一帧就立刻减速）；落位限降幅。另加一道防过冲硬钳位。
效果
15 个组合全部落回 400 °/s² 上限内 末段速度单调递减无反弹；常用场景（回位 70.5°）耗时只增加 1%（2.89 s → 2.92 s）。上游三套原版单测无回归。
修的过程里自己制造过一个新 bug
处理「落位速度突降」时，第一版写成「直接把速度压到目标值」，结果把 1.14 °/s 一步压到 0.32 °/s，凭空造出 90 °/s² 的新跳变。正确做法是限制降幅，不是限制绝对值。

9. 回位距离越小，越容易出问题

现象（用户报告）
回到 home 之后过一小会儿再按握把，机器人会突然朝其他方向动一下，然后才开始跟随手柄。
根因链
① 回位走的是纯关节插值，算出目标后直接下发，完全绕过了指令滤波器；② 回位结束时两边的状态分了家——主循环记录的指令是 home，而滤波器内部的状态还停在回位开始之前；③ 滤波器只在输入与内部状态偏差超过 15° 时才重置；④ 回位距离小于 15° 时这个条件不成立，于是新的目标从一个陈旧位置起算。
所以回位距离越小越容易出问题——这一点非常反直觉。实机验证完全吻合：大于 15° 的回位不跳，小于 15° 的回位跳。
一个「对了一半」的初始猜测
最初怀疑是「缓冲区里有没发完的旧指令」。事实是：透传是位置流、控制器端没有指令队列，所以缓冲区没问题；但「过时的状态」确实存在，它在软件端的滤波器里。
解法
松手期间持续把滤波器同步到真机当前位形（每帧判断「未握把 且 不在回位中 且 未急停」就同步），开销约 10 μs/帧。
为什么不是「按下握把时同步一次」
实施前专门讨论过，有三个理由否掉：① 那样只用握把那一帧的读数，若正好赶上串包就会同步到错误位置并下一帧立刻下发，等于绕过了问题 2 里的多帧一致性门控；② 治不了「松手期间被外力挪动机械臂」的情况；③ 时序上也别扭。
反过来，在当前方案下串包读数是无害的——松手期间一个指令都不下发，链条断在第三步。
效果
握把首帧偏差 → 0，零跳变 干跑冒烟中记录到「同步前最大偏差 134.07°」——这个数字直接量化了不修的话握把瞬间会跳多少度。

10. 松手瞬间机械臂硬停（离线有效，真机无效）

现象
松开右手离合键时机械臂立刻停下，关节冲击很大，像硬急停一样。
根因
离合出口是「直接返回」——本帧起一个字节都不再下发，指令流戛然而止，控制器按自己的保护逻辑收尾。需要澄清的是：软件端既没有调急停、也没做减速规划，它「什么都没做」，这正是问题所在。
解法
松手后继续以主循环节拍重发最后一帧已批准的指令若干秒。实现上有个硬要求：全程零 sleep——这段逻辑跑在 110 Hz 主循环里，睡 0.2 秒等于让控制回路卡死 22 帧。测试里用语法树扫描源码验证确实没有任何休眠调用，并冻结时钟调用 5000 次反证它没有自走时钟。
效果（如实记录）
离线有效：最大断流 394 ms → 193 ms，重发帧数 22 ≈ 0.2 秒 × 110 Hz，21 条离线用例全通过。
真机实测 ❌ 感受不到改善，松手冲击依旧。因此已从推荐命令中移除，代码保留但默认关闭——不加参数时与改造前逐字节相同。
一个未经验证的推测：重发的是相同的位置指令，控制器本来可能就保持在该位置；也就是说「断流」未必是真机冲击的主因，真正的冲击可能来自控制器固件内部的收尾逻辑或伺服环对「目标不再更新」的响应——这些都在软件层之外。

11. Ctrl+C 之后终端不回显

现象
退出遥操作后终端打字看不见字符，每次都要盲打命令恢复。
根因
键盘回位功能需要关闭终端回显，正常退出时会在收尾流程里恢复。但 Ctrl+C 走的是急停信号处理器：发急停 → 断开连接 → 硬退出，跳过所有收尾逻辑。（用干跑后端时不注册这个处理器，回显就能正常恢复——这解释了为什么只有真机模式才出现。）
为什么不去掉硬退出
这不是 bug，是有意的安全设计：Ctrl+C 意味着「出事了，立刻停」，最高优先级是让急停马上生效。若走正常退出流程，后面还有 VR SDK 关闭、日志落盘、渲染线程回收……任何一步卡住或抛异常都可能拖延甚至阻断急停。硬退出保证急停发完立刻死。
所以正确思路不是去掉它，而是另外提供一条干净的退出路径。
解法
新增一个 e 键：拦到它就抛出中断异常，被主流程接住，走完整的八步收尾。既有文件零修改；上游对未知键直接返回，所以其他按键原样转交。
效果
e 键 = 正常结束（回显自动恢复），Ctrl+C = 紧急停止 分工写进了操作手册。离线实测 e 键会执行完整的收尾链路（停机、恢复终端、断连、打印统计），而 Ctrl+C 只做前两步。
