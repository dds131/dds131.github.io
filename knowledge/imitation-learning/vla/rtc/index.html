RTC 是运行时方法，不是新模型

首屏结论

首屏固定中心句：

RTC 不是 π 系列的新版本，也不是新的视觉语言主干；它处理的是动作分块策略在推理延迟存在时，怎样一边继续执行旧块，一边生成并对齐新块。

紧接三张边界卡：

| 层级 | 产物 | RTC 是否拥有 | | — | — | — | | VLA / action policy | 基于观测与任务条件生成动作块 | 否；RTC 消费兼容策略 | | RTC | 跨块条件、时间对齐、异步生成与队列交接 | 是 | | controller / safety | frame 转换、限幅、伺服、碰撞与安全停止 | 否；必须独立存在 |

方法身份

正文只保留以下定义：

  • entity_type=runtime；
  • 原始 guided RTC 是 inference-time 条件生成；
  • training-time RTC 把 prefix conditioning 学入 checkpoint；
  • 两者共享时间语义和 runtime，不共享相同 checkpoint 要求。

不在首屏出现具体任务数、性能百分比或参数值。首屏不得使用“下一代 VLA”“π0.7 的专属能力”“零成本实时”等措辞。

动作块为何在延迟下失配

最小符号

Overview 只介绍三项，不展开完整推导：

| 符号 | 最小含义 | 详细责任页 | | — | — | — | | H | 一次预测的动作块长度 | Foundations | | s | 计划执行/切换跨度 | Foundations | | d | 端到端推理延迟对应的控制步数 | Foundations / Runtime |

允许保留一条概念公式：

\[\text{new chunk ready at } t+d,\qquad \text{its first } d \text{ slots are already stale}.\]

d <= s <= H-d 只作为“在论文离散假设下的可行性提示”展示；完整前提、离散化和边界推导链接 Foundations。

三个问题

以三卡显示：

  1. 等待：同步生成时机器人可能停顿或沿栈定义的 fallback 行为运行。
  2. 过期：异步结果返回时，基于旧观测生成的新块前缀已经错过其时间位置。
  3. 模式切换：两个独立生成的合法块可能来自不同策略模式，直接拼接或逐元素平均可能无效。

禁止误读

  • action chunk 不等于 open-loop 执行完整 H 步；
  • inference delay 不等于单个 GPU kernel 时间；
  • temporal ensembling 不等于 RTC；
  • smooth interpolation 不等于条件分布内轨迹；
  • 队列中“还有动作”不等于动作仍新鲜、有效或安全；
  • RTC 不使用推理期间尚未进入模型的新观测，除非另有显式 streaming/closed-loop 机制。

  participant Q as Old chunk / queue
  participant P as Policy inference
  C->>Q: consume actions during delay d
  P->>P: generate new chunk from observation at t
  P-->>Q: result ready at t+d

图 2｜推理延迟造成的时间错位。 后台推理期间旧块继续被消费；新块返回时，其开头对应的时间位置已经过去，不能当作全新前缀直接执行。

对齐不是把两段向量接起来

新块的可用区间必须由 observation timestamp、request/session、预测起点、实际返回时间和 controller 已提交索引共同决定。Runtime 先确定旧块哪些动作已经执行、哪些已承诺但尚未执行、哪些仍可替换，再把新块中时间位置已经过去的 stale prefix 排除。任何估算延迟 d_hat 与实测 d 的差异都保留在 trace 中；不能为了让边界看起来连续而移动时间戳或把旧动作重标成新动作。

块交接还必须保留 provenance。每个 candidate、prefix、suffix 和最终 dispatch 都关联 checkpoint、RTC mode、contract hash、observation ID、generation/epoch 与来源 branch。任务、prompt、机器人模式、reference state 或 authority 变化时，旧 generation 失效；晚到 response 不能覆盖新会话。Reset 同时清理 queue、condition cache 和未完成 request，并等待 controller/authority 确认，不只是把数组置空。

连续性指标与闭环反应指标应分开。位置或速度跳变小，只说明交接局部平滑；若 candidate 仍基于旧观测，它可能平滑地继续错误方向。报告同时显示 boundary discontinuity、observation/action age、deadline miss、committed prefix、任务结果与安全事件。只有在这些字段绑定同一 trial、硬件和控制契约时，才能判断 RTC 改善的是生成连续性、系统吞吐，还是实际任务反应。

Guided 与 Training-Time 两条路线

选择表

| 维度 | Guided RTC | Training-Time RTC | | — | — | — | | 条件进入 | 推理期采样过程 | 训练时 prefix conditioning，推理时硬前缀/兼容条件 | | checkpoint | 普通兼容 flow/diffusion checkpoint | 必须是相应训练的兼容 checkpoint | | 推理额外成本 | VJP/guidance 计算 | 避免 guided backward path，但仍有模型和 runtime 成本 | | 主要可调项 | overlap、mask schedule、guidance clip/weight | delay sampling、最大训练 delay、prefix/postfix mask | | 主要风险 | 强引导数值不稳定、动作/时间错位 | 未训练 checkpoint、部署 delay 超出训练支持 | | 适合情形 | 已有 checkpoint、无法重训练、需要实验性接入 | 可控制训练、需要降低 guided 推理开销 | | 详细页 | Guided Inpainting | Training-Time Action Conditioning |

“更快”“更好”“drop-in replacement”必须带论文/实现范围，不放无条件勾叉。

并行而非串行

图中两条边必须从 Foundations 同时发出：

Foundations
  ├─ Guided Inpainting
  └─ Training-Time Action Conditioning

Guided 页与 Training-Time 页互不写入对方的 prerequisite_page_ids、prev_page_ids 或 next_page_ids。两页都进入 Runtime，Runtime 使用 merge_policy:any。

可组合边界

允许正文说明某些研究/实现可能组合两类条件，但必须标记为方法迁移或具体实现事实。不能因为两个名称都含 RTC 就假设：

  • trained checkpoint 仍需要 guided VJP；
  • guided checkpoint 自动支持 trained prefix；
  • 两者的 mask、delay 或 queue 配置完全同义；
  • 同一参数名在论文、Kinetix 与 LeRobot 中具有相同定义。

policy contract

本页的 policy_io_contract_id 为 null。任何真机 RTC 实例必须引用非空制品，至少绑定：

  • observation/action schema；
  • frame、unit、absolute/delta；
  • normalization 与 inverse transform；
  • prediction/execution horizon；
  • model sampling steps；
  • control/inference/execution rate；
  • controller consumer；
  • checkpoint/code/processor/adapter hash；
  • RTC mode 与配置版本；
  • safety interface version/hash。

缺失时只能称“概念说明”“论文复现计划”或“离线实现审计”，不得称“可部署 RTC 配置”。

latency contract

必须区分：

  • sensor age；
  • preprocessing；
  • request serialization/network；
  • queue wait；
  • model compute；
  • postprocess；
  • queue merge；
  • action age at dispatch；
  • controller acknowledgement。

平均延迟不能替代 p95/p99、jitter、deadline miss、queue starvation 和 cold-start。d_hat 是调度预测，d 是实测对齐量；字段名与单位必须显式。

安全边界

RTC 可以改变动作候选如何生成和拼接，但不能拥有：

  • 最终 actuator authority；
  • 独立 collision/force/workspace gate；
  • protective/emergency stop；
  • 现场 risk acceptance；
  • 故障后的自动 re-arm；
  • 人员接管权限定义。

所有真机入口同时链接 vla-foundations-safety。安全页要求的 ODD、safe state、watchdog、authority 和 incident trace 优先于 RTC 的连续性目标。

证据范围、开放问题与完成标准

必须保留的六条边界

  1. guided 的“不重训练”有兼容策略和正确接口前提。
  2. trained 的“无 inference-time guidance overhead”不等于零推理成本。
  3. 跨块连续不等于使用了推理期间的新观测。
  4. 吞吐和任务成功必须与 hardware、delay、chunk、controller、trial protocol 一起报告。
  5. 官方仿真仓库不等于完整真机栈；LeRobot 当前实现不等于原论文规范。
  6. RTC 不替代低层控制、独立安全层或人在回路 authority。

开放问题卡

只列问题，不给虚假答案：

  • 连续性与 fresh-observation reactivity 怎样共同优化？
  • relative action、absolute action 与重锚定怎样保持物理语义？
  • 训练 delay 分布怎样覆盖部署 tail latency？
  • guided 和 trained 在统一 compute/latency budget 下如何公平比较？
  • queue merge 在 task/prompt 改变、reset 和故障时如何保持 provenance？
  • RTC 与 world model、streaming policy、high-rate small policy 怎样组合？
  • 何时应拒绝生成而非继续平滑旧轨迹？

2026 年后续方法可作为 related reading，必须单列日期、主张和差异，不进入 RTC 原论文事实框。

事实、实现与迁移的证据边界

原始 RTC

可由原始论文 Real-Time Execution of Action Chunking Flow Policies 支持的主张：

  • RTC 是 inference-time 算法，用于动作分块策略的平滑异步执行。
  • 原始方法把会在推理期间执行的动作冻结，并将剩余动作视为条件补全。
  • 论文面向兼容的 diffusion/flow action chunking policy，并主张不需重新训练。
  • Guided Inference 在采样步骤中加入基于误差和 VJP 的 guidance。
  • Soft Mask 把完整重叠区纳入不同强度的一致性约束。
  • 论文给出 Kinetix 动态任务和 π0.5 真机双臂任务的实验，但数字必须随协议一起引用。
  • 论文承认 guided 方法增加额外计算开销。

不能由原始论文直接支持的主张：

  • 任意 VLA 或任意离散动作 token 模型都可无修改使用。
  • RTC 自动修复错误 frame、unit、normalization 或 relative-action anchor。
  • 论文算法提供 OS/网络/驱动层硬实时保证。
  • 连续轨迹已经满足碰撞、力、速度、工作空间或安全认证要求。
  • 所有机器人都应使用相同 H/s/d/beta。
  • 论文公开仓库包含完整 π0.5 真机部署栈。

Training-Time Action Conditioning

可由 Training-Time Action Conditioning for Efficient Real-Time Chunking 支持的主张：

  • 方法在训练时模拟 inference delay，并直接对 action prefix 条件化。
  • 目标是避免 inference-time inpainting 的额外计算。
  • 论文声称无需修改模型架构或机器人 runtime，但仍需相应训练数据构造与 checkpoint。
  • 论文在仿真和 π0.6 真机任务上比较 training-time 与 inference-time RTC。
  • “drop-in replacement”是作者在其条件下的结论，不是任意 checkpoint 的兼容承诺。

必须明确：

  • trained 模式不能用于未以相应 prefix/delay 条件训练的 checkpoint。
  • 训练延迟范围是契约的一部分；部署时延超出支持范围必须拒绝、降级或重新训练。
  • 训练时知道的 committed prefix 不能泄露部署时不可获得的未来动作。
  • 去掉 VJP 开销不等于整个端到端控制链没有延迟或 jitter。

LeRobot 与其他实现

  • LeRobot 当前 main 文档同时描述 guided 与 trained 模式，属于官方项目的当前实现事实，不是 RTC 论文定义。
  • main 会变化；任何字段名、默认值、支持模型和队列行为都必须绑定 tag 或 commit。
  • LeRobot 当前实现中的 thread、reset epoch、relative-action re-anchoring、queue threshold 与错误处理只能在 Source Code/Runtime 页作为固定版本实例。
  • Physical Intelligence 的 real-time-chunking-kinetix 仓库说明其定位是论文仿真实验实现；不得写成完整真机部署参考。
  • GitHub issue、第三方教程和演示只作为问题线索或复现补充，不能升级为官方事实。
  • 2026 年后续实时动作分块研究可列入“研究边界/相关方法”，但不得倒写成 2025 RTC 原论文组件。
