训练页同时回答“怎样训、训多快、为什么停、怎样证明它真的在学习”

最终 0828 训练使用 JAX 原生参数分片，不是 PyTorch FSDP2；计划 100,000 步，实际在 75,610 步人工停止。训练没有因 OOM、崩溃或非有限值守门退出。

一、实际 8 卡训练命令

cd "$OPENPI"
V="$OPENPI/.venv/bin/python"
export CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
export WANDB_MODE=disabled
export XLA_PYTHON_CLIENT_MEM_FRACTION=0.85
CKPT="/path/to/checkpoints"
LOG="/path/to/train.log"

setsid nohup "$V" -u scripts/train.py pi05_rm75_rawact_3cam \
  --exp-name rm75_3cam_pi05_0828 \
  --num-train-steps 100000 \
  --lr-schedule.warmup-steps 2000 \
  --lr-schedule.peak-lr 2.5e-5 \
  --lr-schedule.decay-steps 100000 \
  --lr-schedule.decay-lr 2.5e-6 \
  --log-interval 10 --save-interval 1000 --keep-period 1000 \
  --num-workers 32 \
  --fsdp-devices 8 --batch-size 256 \
  --no-wandb-enabled --overwrite \
  --checkpoint-base-dir "$CKPT" \
  > "$LOG" 2>&1 < /dev/null &
参数 实际值 面试中要解释的作用
配置位置参数 pi05_rm75_rawact_3cam π0.5、三相机、8 维 state/action 与对应变换链
--num-train-steps 100,000 优化上限，不代表最终实际完成步数
warmup / peak LR 2,000 / 2.5e−5 降低全参训练初期冲击，再进入峰值学习率
decay steps / LR 100,000 / 2.5e−6 衰减时间尺度与计划总步数一致
--log-interval 10 聚合输出 loss、nonfinite_skip、param_norm 等
--save-interval 1,000 每 1,000 步保存 checkpoint
--num-workers 32 数据解码和预取并行度
--fsdp-devices 8 JAX mesh 参数分片轴，不是第三方 FSDP2
--batch-size 256 全局 batch；每步覆盖更多样本并降低梯度方向噪声
XLA 显存比例 0.85 为驱动和运行时留出显存余量

二、训练速度分布

训练日志统计进度率来自日志中的平滑 rate: x s/it，用于描述分布和长尾；不是 75,610 个原始单步内核计时点。

样本数 35,678 32,051

P50 5.4 s/step 5.4 s/step
P95 6.9 s/step 6.8 s/step

全局 batch 256、75,610 步累计处理约 19.4 M 个 batch elements；按 859,154 帧计算约 22.53 epoch。这里的 epoch 是推导量，不是训练程序直接打印值。

三、checkpoint 保存停顿

75 次保存 mean P50 P95 P99 max
训练主线程阻塞 63.92 s 61.52 s 86.63 s 106.83 s 120.89 s
异步保存完整历时 200.46 s 201.55 s 237.65 s 241.85 s 242.57 s

共保留 75 份、约 3.1 TB。“主线程阻塞”解释附近 step 为什么变慢；“异步完整历时”描述后台写盘任务寿命，两者不能相加后再当成单步耗时。

四、怎样证明训练健康

指标 起点 终点 / 结果
loss 0.0748 0.0006，最低 0.0005
grad_norm 0.5697 0.0119
param_norm 1802.39 1813.21
param_norm_all 4789.23 4793.26
nonfinite_skip — 7,562 个日志点全为 0

不能只看 loss。本项目曾遇到 loss 仍打印但参数范数冻结的故障。运行健康至少同时看 loss 是否有限并下降、nonfinite_skip 是否为 0、param_norm 是否在足够长窗口内变化。

五、三轮实验怎样解释

训练 数据 batch / GPU step 40,000 等效 epoch 总训练耗时 真机结果
0814 733 ep / 472,842 帧 24 / 4 卡（卡数来自配置默认，日志未记录） 2.03 58.4 h 64%
0825 1,407 ep / 867,770 帧 24 / 4 卡 1.11 约 27 h 约 10%
0828 1,393 ep / 859,154 帧 256 / 8 卡 11.92 119 h 12 min 92%

0825 与 0828 数据规模接近，batch 24→256 是当前证据最强的主要因素；但 0825 的 decay_steps 为 50,000，另外两轮为 100,000，没有完成严格单变量实验。因此不能把 82 个百分点全部归因于 batch。

六、复杂问题的解决

现象 诊断证据 处理
28° 失效权重 相机文件夹物理语义装反，shape 仍合法 重新核对 USB 物理口、逻辑槽位和三个 mask
loss 变成 inf 正式环境下复现，并用 param_norm 冻结判定未学习 保留逐步日志和 40 步快速判定；num_workers=0 只作规避，不作修复
0825 数据增加但真机下降 相近数据规模下 batch、decay schedule 和等效 epoch 不同 改用 batch 256、decay 100,000，并保留因果边界
step 70,000 真机退化 离线训练误差仍下降 checkpoint 由统一真机协议选择，不按末点或最低训练 loss 选择
一句话回答：最终训练不是“跑了 75,610 步”这么简单；我用步耗时分布、checkpoint 停顿、参数范数和非有限值守门证明训练过程健康，再用统一真机协议决定使用 step 40,000。
