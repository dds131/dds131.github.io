安全不是模型说“安全”，而是每个危险都有边界、检测、独立防护、责任人、已验证安全状态、恢复门槛和可追踪证据；模型只能提出候选意图与动作，最终执行权必须经过与模型故障域分离的确定性安全链。

  • 这是教育性系统规格，不是安全认证或现场批准。 任何真机操作都由现场合格人员按设备、应用、组织流程和适用标准手动发起。
  • 先定义系统、ODD 与危害。 detector、模型分数或 stop 名称不能替代风险分析。
  • 任务成功与安全成功是两个轴。 被安全层拦截的危险候选也必须计数。
  • 模型输出永远是候选。 VLA、VLM、reward model、LLM judge 或人工 UI 都不能绕过最终确定性 gate 与独立安全功能。
  • 没有通用安全数值。 本页不给速度、力、距离、停止时间、SIL、PL 或恢复阈值。

本页不执行模型、仿真、故障注入或机器人动作，不提供真实 IP、端口、凭证、设备序列号、人员身份、动作值和启动命令，不修改只读源站，不上传，也不自动备份。

安全案例、系统边界与 ODD

风险术语

| 术语 | 本页工作定义 | 不应混同 | | — | — | — | | hazard | 可能造成 harm 的潜在来源或条件 | 已经发生的 failure | | hazardous situation | 人、资产或环境暴露在 hazard 中的情形 | 仅模型输出异常 | | harm | 人身、财产、环境、权利或业务造成的实际损害 | 低 success | | risk | harm 的严重性与发生/暴露/可避免性等因素的组合 | 单一 confidence | | failure | 系统未按要求执行功能 | 必然导致 harm | | unsafe behavior | 违反安全 requirement 的行为或状态 | 任务失败 | | safety goal | 高层不可接受风险的约束主张 | 实现细节 | | safety requirement | 可分配、可验证的约束或功能 | 泛泛“要安全” | | safety mechanism | 实现 requirement 的技术/流程措施 | 证据本身 | | verification evidence | 支持 requirement 已按范围实现的可复查材料 | 未绑定版本的截图 | | residual risk | 已实施措施后仍存在并明确接受/处置的风险 | 被隐去的风险 | | safe state | 对特定 hazard/场景经评估后风险可接受的状态 | 通用零动作 | | degraded mode | 限制能力、ODD 和持续时间的批准运行模式 | 任意 fallback | | safety case | claim—argument—evidence 及边界/残余风险集合 | 功能清单 |

ODD 与 OOD

  • ODD（operational design domain）描述被批准运行的环境、任务、人员、机器人、工具、载荷、照明、通信、速度/力、维护和组织条件。
  • OOD（out-of-distribution）描述输入、状态、任务或输出相对训练/校准/验证分布的偏离。
  • ODD 内也可能出现 ML OOD，例如批准场地内出现训练未见的物体。
  • ODD 外也可能被 detector 误判为 ID。
  • 进入 ODD 是运行授权判断；OOD detector 是风险信号之一。两者都不能替代确定性约束。
  • 页面 UI 必须把两个缩写展开显示，避免只靠颜色或上下文区分。

Safety envelope

安全 envelope 至少由以下集合的交集定义：

\[\mathcal{S}_{\mathrm{allow}}(x,t) = \mathcal{S}_{\mathrm{joint}} \cap \mathcal{S}_{\mathrm{workspace}} \cap \mathcal{S}_{\mathrm{kinematic}} \cap \mathcal{S}_{\mathrm{contact}} \cap \mathcal{S}_{\mathrm{collision}} \cap \mathcal{S}_{\mathrm{tool/payload}} \cap \mathcal{S}_{\mathrm{human}} \cap \mathcal{S}_{\mathrm{authorization}}.\]

这只是接口表达，不宣称各集合可由简单几何或单一阈值精确计算。每个 predicate 都需要传感器依赖、单位、frame、版本、owner、最大年龄、故障响应和验证范围。

风险信号与执行许可

页面不把风险压成无解释的单分数。若为了排序使用聚合信号：

\[r_t = f(r_t^{\mathrm{valid}}, r_t^{\mathrm{ood}}, r_t^{\mathrm{unc}}, r_t^{\mathrm{semantic}}, r_t^{\mathrm{motion}}, r_t^{\mathrm{runtime}}),\]

则必须说明：

  • 各分量的定义、单位、范围与缺失处理；
  • f 是策略，不是物理真理；
  • 阈值版本与校准集；
  • 单个低风险信号不得覆盖 deterministic violation；
  • detector failure 本身有 fail-safe 行为；
  • risk score 只能请求 allow/clarify/refuse/takeover/stop，最终 authority 仍由安全链仲裁。

六条系统不变量

  1. No bypass：任何 policy、planner、reward、human UI 或远程服务都不能绕过最终 deterministic gate 和独立安全功能。
  2. Single authority：任一时刻最多一个已确认 authority 向 controller 提交命令；候选来源可多，actuator writer 只能一个。
  3. Fresh evidence：所有用于执行许可的 observation、state、human command、predicate 与 heartbeat 都在批准 freshness 内。
  4. Fail bounded：任何检测到或合理预期的关键故障都有预定义、经验证且有界的 safe-state transition。
  5. No silent recovery：严重故障、急停或 authority ambiguity 后不得自动恢复运动；复位、重验证和重新授权分开。
  6. Traceable consequence：candidate action、filter decision、executed command、controller ack、authority 和 safety event 能以时间一致的 ID 关联。

可靠性、可用性与安全

| 概念 | 关注 | 典型指标 | 本页限制 | | — | — | — | — | | reliability | 在条件和时间内持续完成功能 | failure rate、MTBF、success continuity | 高可靠也可能稳定执行危险功能 | | availability | 需要时可提供服务 | uptime、ready ratio、repair time | 安全拒绝会降低 availability 但可能正确 | | safety | 不可接受风险得到控制 | safe success、unsafe execution、hazard exposure | 不能由 uptime 或 task success 推导 | | resilience | 受扰后维持/恢复受控服务 | degraded duration、recovery time | 恢复必须重新满足安全条件 | | security | 防止未授权改变/泄露/滥用 | access、integrity、attack detection | 具身系统安全与 cyber risk 相互影响 | | privacy | 管理人与环境数据处理风险 | minimization、retention、access | 不能为审计无限期保留所有原始数据 |

系统边界

边界图至少包含：

  • 人：操作员、监护人、旁观者、维护人员、数据主体、远程支持；
  • 机器人：本体、驱动器、控制柜、制动、末端工具、夹具、载荷、能源；
  • 环境：工作区、围栏、门、地面、障碍、工件、照明、噪声、温湿度；
  • sensing：相机、力/力矩、关节、触觉、接近、人检测与时间同步；
  • AI plane：VLM/VLA、planner、memory、reward/judge、processor、adapter；
  • runtime plane：client/server、网络、queue、scheduler、logger、artifact registry；
  • control plane：action gate、trajectory/controller、single writer；
  • safety plane：safety PLC/controller、watchdog、interlock、protective stop、e-stop；
  • procedure：启动、交班、维护、复位、事件和变更管理；
  • 外部依赖：电源、网络、时间源、身份、云服务、远程工具。

每条跨边界接口注明：数据/能量/命令方向、owner、信任等级、最大年龄、权限、故障行为和审计 ID。

ODD manifest

ODD 不是一句“室内桌面操作”，至少覆盖：

| 维度 | 最小字段 | | — | — | | 机器人/工具 | 本体、自由度、工具、夹具、payload 范围、控制模式、软件/固件版本 | | 任务 | 允许任务、禁止任务、对象类别、接触类型、预计持续时间 | | 空间 | 工作区、禁区、动态区、人员位置、遮挡、地面/支撑 | | 物理 | 速度/力/能量相关条件、温度、易碎/尖锐/液体/带电对象 | | 感知 | 相机角色、视野、照明、最小质量、遮挡、传感器健康 | | 通信 | 本地/远程、deadline、loss/jitter 范围、断连策略 | | 人 | 允许接近、监护职责、培训、视线、接管设备、最大负荷 | | 生命周期 | 上电、启动、执行、暂停、维护、重启、恢复、停用 | | 组织 | owner、approver、值班、事件联系人、变更权限 | | 排除项 | 未批准本体、工具、载荷、公共环境、儿童/动物等 | | 退出条件 | ODD violation、health failure、uncertainty、权限缺失、事件 |

页面提示：具体阈值不在公共页给出；模板使用占位符，并要求风险评估与硬件验证。

Hazard 分析

按生命周期而非只按正常运行组织 hazard：

  1. 运输/安装；
  2. 上电与初始化；
  3. 模型/配置加载；
  4. 自动执行；
  5. 人机协作或接管；
  6. 暂停/停止；
  7. 故障和恢复；
  8. 清洁/维护/换工具；
  9. 数据导出与远程支持；
  10. 退役。

Hazard category 至少包括：

  • crushing、shearing、impact、entanglement、puncture；
  • unexpected motion、gravity drop、tool release、payload ejection；
  • collision、workspace intrusion、unstable support；
  • thermal、electrical、chemical、stored energy；
  • wrong object/person/target、unsafe task、goal drift；
  • privacy、unauthorized observation、identity/location exposure；
  • cyber takeover、prompt injection、malicious tool call；
  • workload、mode confusion、authority ambiguity；
  • loss of sensing、communication、compute、controller；
  • maintenance bypass、misconfiguration、stale calibration；
  • common-cause and cascading failure。

Safety case 结构

每个顶层 claim 下必须展示：

claim → context/assumption → argument → requirement → mechanism → verification → evidence → limitation → residual risk → owner/approval

证据等级不可混淆：

从边界声明到可审查主张

安全案例的第一步不是列出模型功能，而是给系统画一条可以争辩的边界。边界内写清谁能改变能量、运动和权限，边界外写清系统依赖什么、依赖失效时由谁发现。相机、网络或云服务即使由第三方维护，只要其失效会改变执行许可，就不能从分析中消失；它应作为外部实体进入接口表。每条接口同时描述正常流、反向反馈、时间要求、信任来源和断开语义。否则“服务不可用”会在运行时被多个模块各自解释，形成没有 owner 的危险间隙。

ODD manifest 需要把允许条件写成可观测事实。比如“人员受控”必须落到角色、可见范围、进入检测、授权状态和退出条件；“光照正常”必须绑定能验证的感知质量与失效处理；“网络稳定”必须绑定上一页定义的 freshness、deadline 与会话完整性。无法在线观测的条件只能作为启动前检查或组织假设，不能伪装成实时 predicate。每项假设还要注明证明方式、有效期和失效后的保守处理。排除项与退出条件和允许项同等重要，因为系统最容易在边界刚被越过时继续沿用旧许可。

Hazard 分析使用“原因—危险状态—暴露—伤害”链，而不是把 failure 名称直接当作 hazard。相机冻结是原因；机器人在有人接近时继续根据旧图像运动是 hazardous situation；挤压或冲撞才是可能的 harm。相同原因在不同工具、载荷或姿态下可能对应不同伤害与安全状态，因此故障码不能一对一机械映射为某个 stop。反过来，一个 hazard 也可能由模型幻觉、坐标系错误、控制器模式错误或人工误操作等多条因果路径触发，要求 defense-in-depth 覆盖不同故障域。

每条 safety goal 应拆成可验证、可分配的 requirement。需求文本说明受保护对象、触发条件、允许反应窗口、期望状态和适用 ODD；mechanism 说明由谁实现，verification 说明怎样观察正确与错误行为，evidence 绑定 artifact、配置、测试与结果摘要。若只能证明检测而不能证明物理停止，就把 limitation 明写出来，不把检测日志升级为风险已经降低。Residual risk 必须有具名角色接受或继续处置，并设置复审日期；“团队已知”不是责任闭环。

合成审计例：不代表现场结论。 假设工具状态传感器失真，candidate action 可能在错误工具配置下进入工作区。安全案例应分别追踪：工具身份与校准要求、启动握手、确定性 workspace/tool predicate、独立 inhibit、故障注入、物理状态确认和人工复位。若 HIL 只验证了数字信号切换，就只能支持接口层主张；对真实夹具、载荷保持和停止距离仍是证据缺口。页面把这种缺口显示为 unverified 或 out_of_scope，不能用绿色总状态遮蔽。

变更影响审查从“什么被改了”扩展到“哪些主张的前提被改了”。更换 camera 可能改变 OOD detector、遮挡假设和时间同步；更新 processor 可能改变 grounding；更换工具改变质量、几何、碰撞体和 safe state；UI 文案变化可能改变接管认知时间。审查人沿依赖图找出失效的 requirement、test 和 evidence，冻结受影响批准，再选择最小充分的重验集合。无法证明影响隔离时，按扩大范围处理，而不是沿用旧签字。

Safety case 还要表达时间。设计证据、上线证据、维护证据和事件后证据属于不同阶段；一年前的 proof test 不证明今日传感器健康。Manifest 因此记录版本、现场、设备状态、有效期和复核触发器。任何“已批准”都应读作“在这个边界、这个 ODD、这些版本和这段有效期内，由这些角色批准”，而不是系统永久安全。

物理、语义与运行安全的纵深防御

三域与横切面

| 域 | 主要问题 | 示例 | | — | — | — | | physical safety | 动作与能量会不会造成物理 harm | 关节越界、碰撞、挤压、载荷掉落 | | semantic safety | “做什么/对谁/为何”是否允许且正确 | 错对象、危险任务、未成年人、越权指令 | | operational safety | 系统在故障、维护和变更中是否受控 | 陈旧相机、断网、错版本、自动重启 | | security（横切） | 是否被未授权改变、诱导或控制 | injection、凭证泄露、工具越权 | | privacy（横切） | 人与环境数据如何最小化和治理 | 视频、语音、身份、位置、事件日志 |

三域不能互相替代：语义安全通过不证明碰撞约束；物理 gate 通过不证明任务被授权；运行可靠不证明语义正确。

  • detection and reaction time；
  • required sensors/energy；
  • diagnostics；
  • proof test/maintenance；
  • bypass path；

动作许可链

候选动作必须按确定顺序处理：

candidate → schema/finite → session/authority → freshness → contract hash → decode/unnorm → reference state → frame/unit → kinematic feasibility → joint/workspace → speed/accel/jerk → collision/contact/force → tool/payload/human predicates → semantic authorization → independent safety permission → controller submit → ack/tracking

每一步有三态，而不是只有 true/false：

  • allow；
  • reject/escalate；
  • unavailable/fault。

unavailable 不得默认 allow。对于 safety-critical predicate，缺失通常进入经批准 safe state；具体反应由 hazard analysis 决定。

Constraint 分类

  • joint position/velocity/acceleration/jerk；
  • Cartesian pose/twist/acceleration；
  • workspace keep-in / keep-out；
  • self-collision / environment collision；
  • singularity/manipulability；
  • force/torque/wrench/contact duration；
  • gripper force/aperture/object retention；
  • tool orientation/energization；
  • payload mass/center of gravity；
  • human separation/speed and separation monitoring；
  • stability/support polygon for mobile/humanoid；
  • cable/hose/fixture constraints；
  • task-phase and authorization constraints。

Clip、project、reject 与 stop

| 行为 | 适用 | 风险 | | — | — | — | | clip | 对明确、局部、单维、已批准边界的小偏差 | 隐藏单位/frame 错误，改变轨迹意图 | | projection | 将候选投影到可行集，且可证明连续/可控 | 求解失败、约束不完整、延迟 | | reject | 语义/契约/权限/新鲜度不满足 | 需要定义拒绝后的安全状态 | | controlled stop | 允许受控减速以降低风险 | 需验证停止时间/距离和载荷 | | protective stop | 由适用安全功能触发的保护性停止 | 复位/重启按设备与风险评估 | | emergency stop | 紧急情况下的补充保护措施 | 不是主要风险降低手段或完整安全 |

不得将 clip_count=0 写成策略安全；也不得只记录 clip 后动作，必须保留 candidate 与变换原因。

独立安全控制器

页面用原则而非硬件选型说明独立性：

  • 与 VLA process、GPU、模型服务器、普通 logger 不共享单一故障域；
  • 能直接阻止或限制 actuator energy/command path，具体由平台实现；
  • 输入来自经批准的安全相关 sensing/logic；
  • 网络/AI 栈失效时仍执行定义的安全功能；
  • 自身 diagnostics、proof test、maintenance 和故障响应明确；
  • 不接受 policy 自报“我安全”作为唯一许可；
  • 配置写权限受控、变更可追踪；
  • 不因高层 retry/restart 自动 re-arm。

具体 safety integrity/performance level 不能由本页选择，必须来自风险评估和适用标准。

把候选动作变成许可决定

纵深防御的关键不是层数多，而是每层回答不同问题且不会被同一个故障同时绕过。机械限制减少可产生的能量；guard/interlock 控制人员暴露；drive 或 controller safety function 处理平台级停止；独立安全控制器拥有与 AI 栈分离的 veto；deterministic action gate 检查数据与物理约束；语义层判断任务、对象和权限；人员与程序处理无法自动证明的上下文。遥测与事件治理记录这些层是否真的参与，而不是给模型输出增加一条解释文本。

动作许可链应采用逐项、短路、可追踪的判定。Schema 或 finite 检查失败时，不应再尝试通过 clip 修复；session、authority 或 freshness 不一致时，动作已经失去上下文；contract hash 不匹配时，即使向量维数相同也不能解释。Decode 与反归一化后才知道物理量，但 reference state、frame、unit 或旋转约定缺失时仍不能进入运动学判断。后续每个 predicate 返回 allow、reject/escalate 或 unavailable，并记录输入摘要、版本、最大年龄和 owner。最终许可引用所有必要 predicate 的同一 evaluation epoch，避免把不同时间片的“绿色”拼成一次虚假允许。

约束之间还存在顺序与耦合。单关节限位通过不代表 Cartesian 路径无碰撞，末端位姿可达不代表中间轨迹、线缆、工具或载荷安全，速度合规也不代表停止距离适合当前人员位置。力/力矩阈值依赖传感器、滤波、安装、工具重力补偿和任务相位；human separation 依赖感知覆盖、延迟和制动性能。页面因此要求每个 limit 绑定来源、单位、frame、margin、采样与反应路径，不允许只保存一个匿名数字。

Clip 适合经批准的小范围、局部、连续修正，但必须保留原 candidate 和被修改原因。若大量 candidate 持续撞边界，clip 可能把模型退化隐藏成表面稳定；若错误来自单位或坐标系，clip 后的方向仍可能错误。Projection 只有在可行集、求解器状态、超时和不连续行为都被验证时才有意义；求解失败是 unavailable，不是默认接受原动作。Reject 后必须有安全状态，不能让 controller 继续持有一个无限期旧命令。Controlled stop、protective stop 与 emergency stop 的目的、触发者、物理后果和复位路径不同，页面不把这些词互换。

独立安全层的“独立”需要证据。仅将 watchdog 放进另一个进程或容器并不足够；仍可能共享电源、时钟、网络、传感器、配置仓库、编译链和错误数据。分析应列出 common-cause failure，说明哪些依赖被隔离、哪些通过多样性监测、哪些只能作为残余风险。安全层必须能在 policy/GPU/server/logger 停止响应时执行批准的限制或 inhibit，并有自身 diagnostics 与 proof test。它不接受 policy 自报的 confidence 或解释作为唯一许可，也不被高层 restart 自动 re-arm。

Physical confirmation 是许可链的末端证据。Controller ack 只证明命令被接受，不一定证明速度下降、制动建立、能量隔离或载荷稳定。对于需要确认的安全状态，应使用经批准的反馈组合，区分“请求停止”“控制器报告停止”“物理状态满足”三个事件。若确认通道自身故障，状态保持 unknown，并进入对应故障响应；不能因为超时就推断成功。

语义安全和物理安全必须并行。一个被授权的任务仍可产生碰撞候选，一个轨迹在几何上可行也可能针对错误对象或未获授权人员。Capability allowlist 限制模型可请求的动作类别，deterministic gate 限制候选能否进入控制器，独立安全功能处理高层系统不可控的危险。三者的日志用同一 trace 关联，但审批、配置写权限和故障域不合并。这样才能在事件后区分是模型提出危险、语义层授权错误、物理 gate 漏检，还是控制器未按命令执行。

维护模式、调试 override 与 proof test 也是安全功能的一部分。任何 bypass 都要有受限角色、明确范围、可见指示、自动到期和审计记录；离开维护状态时重新核对 interlock、predicate 配置、authority 和物理区域。生产模式不得继承调试期间放宽的门禁。若某项安全功能需要周期测试，测试失败或过期应影响 readiness，而不是只产生无人处理的告警。

OOD、不确定性、拒绝与指令防护

OOD 轴

至少覆盖：

  • visual appearance：光照、背景、遮挡、反射、污渍；
  • geometry：object pose、scale、clutter、workspace；
  • object/category/material；
  • task/language/intent；
  • embodiment/tool/payload；
  • dynamics/contact/friction；
  • human presence/behavior；
  • sensor/calibration/time；
  • runtime/network/resource；
  • adversarial/intentional manipulation。

OOD 评测必须保留 ID、near-boundary OOD、known OOD 和 adversarial slices；不能只用明显不同的数据集获得漂亮 AUROC。

风险信号

可使用但不得神化：

  • input validity / schema / missingness；
  • embedding distance/density；
  • deep ensemble disagreement；
  • predictive entropy / energy / likelihood proxy；
  • reconstruction/error proxy；
  • temporal inconsistency；
  • action disagreement or volatility；
  • state/action envelope violation；
  • grounding consistency；
  • detector over image/text/tool output；
  • runtime health and drift；
  • human escalation history。

每项说明 failure modes：共享偏差、过度自信、distribution shift、尺度、阈值漂移、攻击可绕过、计算延迟。

校准与选择性执行

页面给出选择性执行的抽象：

\[\mathrm{coverage}(\tau)=P(s(x)\le \tau), \qquad \mathrm{risk}(\tau)=P(\mathrm{unsafe}\mid s(x)\le \tau),\]

其中分数方向必须明示；“unsafe”标签和事件窗口必须预注册。至少报告：

  • coverage；
  • safe risk / unsafe rate；
  • false negative rate at threshold；
  • false positive/refusal burden；
  • precision/recall for intervention/hazard；
  • detection lead time；
  • per-task/per-ODD slice；
  • calibration error（若分数声称概率）；
  • threshold drift across versions；
  • abstention/takeover load；
  • confidence interval。

不得仅报告 AUROC；安全运行需要具体 operating point 下的漏报、反应时间和后果。

决策梯

从低风险到高风险的响应不是统一数字：

  1. allow；
  2. allow with tighter envelope；
  3. ask clarification；
  4. request supervisor confirmation；
  5. refuse task/action；
  6. transfer authority；
  7. controlled stop / safe state；
  8. emergency path 由独立安全功能处理。

响应必须绑定 hazard、可用时间和人工反应能力。低 confidence 不得未经 action semantics 定义映射为零向量。

指令信任与权限

指令 pipeline：

source identity → authorization → canonical task → conflict check → capability allowlist → object/person grounding → hazard policy → plan validation → action gate

必须区分：

  • authenticated 不等于 authorized；
  • 用户指令、系统策略、现场 supervisor、维护 override 的优先级；
  • scene text/QR/web/retrieval/tool output 是 untrusted data；
  • 数据内容不能自行升级为 instruction；
  • prompt/constitution 不能授予超出外部 policy 的权限；
  • “忽略安全规则”“关闭 detector”“进入维护模式”等指令必须被确定性权限层拒绝；
  • 多指令矛盾时停止并请求澄清，不自行猜测；
  • 语义拒绝不阻断独立物理 stop；
  • tool call 只使用 allowlist、typed schema、least privilege 和后置验证。

Prompt injection 与恶意输入

威胁模型至少包括：

  • direct jailbreak；
  • indirect injection in scene text/image/QR；
  • retrieved document/web page；
  • memory poisoning；
  • tool output injection；
  • instruction smuggling across modalities；
  • data exfiltration；
  • unauthorized tool/robot capability use；
  • denial of service / resource exhaustion；
  • adversarial object/patch；
  • compromised model/processor/artifact。

缓解层：

  • trust labels and provenance；
  • separate instruction/data channels；
  • content canonicalization and parsing；
  • capability allowlist；
  • policy enforcement outside model；
  • output schema validation；
  • human confirmation for high-impact intent；
  • no raw secret in prompt；
  • sandbox/least privilege for digital tools；
  • deterministic physical gate；
  • red-team/evaluation/regression；
  • monitoring and incident response。

明确写出：没有单一 system prompt、filter 或 red-team 能证明 injection 已被消除。

Hallucination 与 grounding

VLM/VLA 可能：

  • invent object/attribute；
  • confuse person/target；
  • misread tool state；
  • claim nonexistent clearance；
  • infer wrong affordance；
  • lose identity across time；
  • ignore occluded hazard；
  • fabricate completion；
  • explain confidently after wrong action。

防护要求：

  • action requires grounded object/region ID；
  • target presence/identity checks；
  • multi-view or sensor cross-check where approved；
  • temporal persistence and revalidation；
  • negative evidence/unknown state；
  • capability/affordance constraints；
  • execution feedback；
  • no sole self-critique oracle；
  • ambiguous target triggers clarify/refuse；

从风险分数到选择性执行证据

OOD detector 的评测对象必须包含分数定义、输入版本、校准数据、阈值、事件窗口和响应策略。只报告 AUROC 无法回答运行问题：在指定 operating point 下会漏掉多少危险窗口、提前量是否足够、多少正常任务会被拒绝、拒绝是否让人工负荷失控。数据划分应区分 ID、接近边界的 shift、已知 OOD 与对抗切片，并防止同一场景、对象或会话泄漏到校准与测试。对每个 ODD/task slice 单独报告，避免总体平均掩盖一个关键场景的漏报。

风险分数不是事故概率，除非标签、校准、分布和时间窗口都支持这种解释。Ensemble disagreement 可能共享同一数据偏差，embedding distance 可能对语义危险不敏感，likelihood proxy 可能对无关视觉变化敏感，模型自评又可能与 policy 共享幻觉。页面要求记录每个信号的适用范围、失效模式、延迟和缺失语义，并把 detector failure 当作独立故障。多个信号聚合时，确定性 violation 不能被平均掉；缺失值也不能被当成低风险。

选择性执行的 coverage-risk 曲线应绑定真实后果。降低 coverage 可能减少 unsafe execution，却增加 refusal、takeover 和生产中断；提高 coverage 可能把人来不及响应的危险留给人工。阈值选择因此由 hazard 的可用反应时间、人工能力和 safe-state 成本共同决定，而不是在离线数据上追求一个最大 F1。版本变化后重新校准并比较 threshold drift；若新版本只能依靠明显提高拒绝率维持安全结果，应公开这一代价。

Decision ladder 把不确定性翻译为有限动作：收紧 envelope、请求澄清、请求 supervisor、拒绝、移交 authority 或请求安全状态。每个等级都写清触发信号、最大等待、允许继续的动作和超时结果。自然语言模糊不能自动转成物理零动作，因为零向量在 absolute、delta、velocity 或 torque contract 下语义不同。若没有安全定义，正确响应是拒绝新动作并走批准的状态转换。

把指令和数据分开

指令可信链从 source identity 开始，但 authenticated 只说明“是谁”，authorized 才说明“在当前 ODD 与角色下能要求什么”。系统把现场 supervisor、普通用户、维护 override、系统策略和独立安全功能放在显式优先级中；冲突时停止并请求裁决，而不是让模型根据措辞猜。Scene text、二维码、网页、检索片段、memory 和 tool output 即使包含命令式语言，也保持 untrusted data 标签，不能自行改变角色、能力或门禁配置。

Prompt injection 防护依赖模型外的权限分离。解析层将候选意图规范化为 typed task；capability allowlist 限制可调用工具与机器人 primitive；外部 policy 检查对象、人员、区域和任务相位；每个 tool call 使用最小权限并验证结果；物理动作仍经过 deterministic gate 与独立许可。System prompt、内容 filter 或 red-team 都只能贡献证据，不能证明攻击已消失。任何“关闭 detector”“进入维护模式”“忽略安全规则”之类高影响意图，都需要模型外的身份、角色和现场条件验证。

攻击面不仅是文本。视觉标签可以把数据伪装成指令，检索文档可能携带恶意段落，工具返回可诱导下一步调用，memory poisoning 能跨会话保留错误权限，资源耗尽会让安全相关 detector 超时。威胁测试要覆盖跨模态 smuggling、数据外泄、未授权工具、拒绝服务和 artifact 篡改，并检查 provenance、签名、schema、超时与 fail-safe。日志不保存真实 secret，也不能把敏感环境图像无限期保留为“安全证据”。

Hallucination 与 grounding 错误必须落到执行前可验证对象。候选任务引用稳定 object/region ID，执行前检查目标仍存在、身份一致、状态新鲜；遮挡或多视角冲突时保留 unknown。模型声称“路径已清空”不是 clearance evidence，解释文本也不是 permission。执行反馈验证实际对象和任务进度，若身份跨时间漂移、affordance 不匹配或完成状态无法证实，则澄清、拒绝或升级，而不是用更自信的解释覆盖不确定性。

Unknown unknown 不能被测试集证明消除。页面允许的主张是：在声明的 ODD、已知扰动和对抗集合上，给定版本的 detector 与响应链显示了这些 FNR、FPR、提前量和后果；范围外仍有残余风险。上线监控关注输入与风险信号漂移、拒绝负荷、unsafe proposal、人工接管和新型事件，并设置触发再评测的门槛。发现新模式后更新 hazard、测试与回归集，而不是只微调阈值让告警消失。

五字段故障闭环

每个故障条目强制五字段：

  1. detector：谁、用什么信号、多少延迟；
  2. owner：谁处理、谁批准；
  3. safe state：当下进入什么状态；
  4. recovery：检查、复位、重新授权条件；
  5. audit evidence：保存哪些版本、时间、信号和结果。

Watchdog 设计

Watchdog 必须检查：

  • monotonic heartbeat sequence；
  • heartbeat age and deadline；
  • observation age；
  • policy response age；
  • action validity horizon；
  • queue time-to-empty/stale；
  • controller ack age；
  • tracking error；
  • current authority；
  • deployment/session/contract hash；
  • sensor/model/controller health；
  • safety controller self-health；
  • system mode and ODD state；
  • reset/re-arm authorization。

仅检查 TCP connection 或 process PID 不足。heartbeat 也不能由与被监控任务同一 blocked thread 虚假刷新。

Watchdog 输出是结构化事件：

event_id, monotonic_time, wall_time, source, predicate, observed, bound_ref, severity, requested_safe_state, authority, trace_id

故障到状态的规则

  • critical sensor stale：禁止新 policy action，按批准路径停止；
  • policy timeout：旧 action 是否还能执行取决于 validity 和 hazard，不默认重放；
  • network disconnect：禁止远程控制继续占有 authority；
  • queue starvation：不把 delta/torque 最后一项无限保持；
  • queue overflow：丢弃/替换规则不破坏顺序和 authority；
  • wrong contract/hash：fail closed，禁止进入 motion-ready；
  • invalid/NaN：拒绝且记录 candidate；
  • controller reject：不重复发送未分析命令；
  • tracking error：触发 limit/stop/takeover 按 hazard；
  • safety sensor self-fault：安全功能按其设计进入故障响应；
  • logging failure：不阻塞 safety/control；但若证据是运行许可条件则停止受控运行；
  • privacy boundary breach：隔离数据路径并按 incident 流程处置；
  • cyber unauthorized command：拒绝、保全证据、撤销会话/凭证并检查物理状态。

Recovery 与 re-arm

恢复流程：

  1. contain hazard；
  2. freeze new commands and preserve evidence；
  3. identify actual physical state；
  4. identify fault and affected version/scope；
  5. repair/replace/reconfigure；
  6. re-run required self-test/proof test；
  7. revalidate sensors/calibration/contract；
  8. clear stale queue/session/memory；
  9. confirm human/actuator authority；
  10. obtain reset authorization；
  11. start new session in restricted mode；
  12. monitor exit criteria；
  13. only then return to approved ODD。

reset 只清故障锁存；re-arm 恢复执行许可；resume 重新开始任务。三者不能用一个按钮或事件混同。

Degraded mode

每个 degraded mode 必须定义：

  • triggering fault；
  • allowed ODD subset；
  • allowed tasks/capabilities；
  • tighter speed/workspace/force envelope；
  • human supervision；
  • maximum duration；
  • telemetry；
  • exit/escalation；
  • prohibited auto-update；
  • evidence and approval。

“使用备用模型”只有在备用 artifact、adapter、contract、safety behavior 和切换过程均已验证时才可成为 degraded mode。

把故障矩阵变成状态转换

Fault register 不只列“组件可能坏”，而要写故障如何传播到危险。Sensor frozen 可能保持数值合法，却让 freshness 与真实环境脱节；clock jump 可能让陈旧数据看似年轻；network retry 可能复制请求；queue mixed-version 可能把旧动作接到新会话；controller mode mismatch 可能用另一种单位解释命令。每项都绑定可观察信号、检测限制、负责模块、fault containment region 和请求状态，并指出 detector 可能漏掉什么。

五字段闭环要求 detector、owner、safe state、recovery 和 audit evidence 始终同表出现。只有 detector 而没有 owner，会产生无人响应的告警；只有 safe state 名称而没有场景依据，无法判断重力载荷或夹持物是否更危险；只有 recovery 脚本而没有重验证，会把故障状态带回运行；只有日志而没有版本与时间关系，无法复盘。Severity 可以决定通知和升级，但不能替代 hazard-specific response。

Watchdog 检查进展而非存活。Heartbeat sequence 必须单调，且由真正完成工作的一侧更新；observation、response、action validity、queue、controller ack 和 tracking 都有各自 age。一个进程持续发 heartbeat 但主线程阻塞、相机冻结或 controller 不跟踪时，functional health 已失败。Watchdog 还核对 deployment/session/contract hash、authority、ODD state 和安全层自身 diagnostics。被监控系统不能拥有修改 watchdog 阈值、伪造 authority 或清除故障锁存的唯一权限。

独立 watchdog 也会失败，因此要说明 self-test、proof-test interval、失联语义和共因。若它与 policy 共用同一主机、电源、时钟或网络，分析必须承认共同失效并设置补充机制；“不同进程”不是充分独立。Watchdog event 使用单调时间和关联 ID，保存 observed value、bound reference、requested state 与 authority。事件发出后还需确认请求被仲裁器接收、controller 响应和物理状态达到，不能把告警本身当作停止证据。

安全状态是场景化决策

Safe hold 可能适合稳定保持，却可能持续加热、夹持或储能；de-energize 可能让重力轴或载荷下落；release payload 可能造成掉落；retain payload 又可能让人继续暴露。Controlled stop 依赖经验证的停止时间、距离与路径；restricted retreat 只有在退路感知和几何仍可信时才可选。页面将这些列为候选，真实绑定由 hazard、平台能力和现场评估决定，并保存状态请求与物理确认之间的差异。

故障到状态的映射要考虑动作语义。Policy timeout 时，absolute hold、delta、velocity、torque 和 chunk suffix 的继续执行后果不同；网络断连不能让远程 authority 永久占有 writer；queue starvation 不能无限重复最后一项；controller reject 不能无分析自动重发。Wrong contract/hash、invalid/NaN 和 authority ambiguity 采用 fail-closed，禁止进入 motion-ready。若 logging 是发布许可的必要证据，日志故障可以终止受控试验，但记录线程自身不能阻塞安全与控制路径。

恢复从确认现实物理状态开始，而不是从重启服务开始。Contain 后冻结新命令并保全易失证据，识别故障影响的版本、会话和时间窗，再修复或替换。随后分别做 self-test、传感器/校准/contract 复验、清理旧 queue/session/memory、确认 authority、执行 reset 授权并以受限模式开启新会话。每一步生成事件和结果；任何一步 unknown 都阻止扩大 ODD。reset、re-arm 和 resume 分离，避免一个按钮同时清锁存、恢复能量和续接旧任务。

Degraded mode 是新的受限运行契约，不是“先凑合”。它声明触发故障、允许 ODD 子集、能力、收紧后的 envelope、人工监督、最长持续时间、遥测、退出条件与审批。备用模型只有在 artifact、adapter、I/O contract、安全行为和切换过程都已验证时才可使用；否则它只是另一个未知来源。达到期限、再出现故障、人工链路丢失或必要证据中断时，degraded mode 自动退出到批准安全状态，不能无限续期。

故障注入遵循最低风险阶梯。先验证 schema、state machine 和纯软件超时，再做 replay/SIL，之后才在经界定的 HIL 或现场条件下验证真实接口。每个注入有终止条件、预期 detector、最大反应窗口、预期安全状态和观察者；注入工具本身不能获得未受控 actuator authority。未完成的平台级验证只支持软件逻辑主张，不能写成真实停止性能已证明。

人在回路、控制权与接管交接

人的角色

  • observer：只能看，无控制权；
  • supervisor：可批准/拒绝/请求停止；
  • shared-control operator：与自动系统按明示仲裁共同贡献；
  • teleoperator：直接生成参考命令；
  • safety monitor：拥有独立 stop 权限；
  • maintenance authority：在隔离模式下操作；
  • approver：批准 ODD/release/re-arm；
  • incident owner：保全证据与协调处置。

同一个人可多角色，但 UI、授权和日志必须记录当前角色；“有人在场”不是角色定义。

Authority 状态机

推荐状态：

NO_AUTHORITY → READY_SUPERVISED → AUTONOMOUS → TAKEOVER_REQUESTED → TAKEOVER_PENDING → HUMAN_CONTROL → HANDOFF_REVIEW → READY_SUPERVISED

任何状态可进入 SAFE_STOP；SAFE_STOP → RECOVERY_LOCKED → READY_SUPERVISED 需要显式复位与重新授权。

关键规则：

  • request 不等于 confirm；
  • TAKEOVER_PENDING 记录实际 executed source；
  • 旧 chunk、in-flight response 和 cached plan 必须以 epoch/session 失效；
  • actuator writer 只接受已确认 authority；
  • handoff 前建立新 observation，重新推理，不续用旧计划；
  • 严重事件后不能直接从 SAFE_STOP 回 AUTONOMOUS；
  • authority display 来自 controller/arbitrator 真值，不来自 UI 本地猜测；
  • shared control 的组合函数、优先级和饱和行为必须可审计；
  • lost human link 有预定义 safe state；
  • emergency stop 可从状态机外部打断，但复位必须重新进入受控状态。

接管延迟

至少分解：

\[T_{\mathrm{takeover}} = T_{\mathrm{detect}} + T_{\mathrm{notify}} + T_{\mathrm{human}} + T_{\mathrm{input}} + T_{\mathrm{arbitrate}} + T_{\mathrm{controller}} + T_{\mathrm{physical}}.\]

记录 p50/p95/p99/max 还不够；必须与 hazard 可用反应时间比较。人的 reaction 不是固定常数，需要覆盖视线、认知负荷、设备、任务、训练、疲劳和环境。

人机接口

  • mode/authority 显示显著且同源；
  • 控制源切换有触觉/视觉/听觉反馈，至少两种适合现场的渠道；
  • alarm 可区分 priority、来源和要求动作；
  • 不能用颜色作为唯一状态；
  • deadman/enabling device 行为按平台批准；
  • 输入映射、方向、比例、离合和按钮经只读/dry-run 验证；
  • 错误按钮/抖动/stuck input 有检测；
  • 网络 teleop 显示延迟/freshness；
  • 无效输入不保持旧危险命令；
  • UI 不允许普通角色解除 safety lock；
  • 人必须能知道接管是否真正生效；
  • 日志保存 raw input、mapped command、executed action 与 authority。

人的局限

安全案例必须分析：

  • line of sight；
  • occlusion and camera latency；
  • attention/workload；
  • alarm fatigue；
  • mode confusion；
  • reaction time；
  • training/competence；
  • language/accessibility；
  • staffing/shift handover；
  • remote connectivity；
  • conflicting responsibilities；
  • automation complacency；
  • stress after incident。

不得把“训练有素的人”作为未验证的万能缓解措施。若安全目标依赖人，必须证明人能在可用时间内感知、理解、决定并行动。

  TAKEOVER_PENDING --> HUMAN_CONTROL: controller confirms writer
  HUMAN_CONTROL --> HANDOFF_REVIEW: task stable
  HANDOFF_REVIEW --> READY_SUPERVISED: fresh observation + new epoch
  AUTONOMOUS --> SAFE_STOP: safety event
  HUMAN_CONTROL --> SAFE_STOP: safety event
  SAFE_STOP --> RECOVERY_LOCKED: contain + preserve evidence
  RECOVERY_LOCKED --> READY_SUPERVISED: reset + revalidation + re-arm

图 5｜控制权状态机与证据链。 takeover request 不是 takeover confirmation；actuator writer 的真值来自 controller/arbitrator，旧 chunk 与 in-flight response 在 epoch 切换时失效。

Authority 是可验证状态，不是 UI 标签

人在回路首先要区分角色。Observer 看见信息但不能发命令；supervisor 可批准、拒绝或请求停止；shared-control operator 与自动系统通过显式仲裁组合；teleoperator 直接产生参考命令；safety monitor 保有独立 stop；maintenance authority 只在隔离模式操作；approver 决定 ODD、release 与 re-arm。一个人可以兼任，但系统记录当时激活的角色和凭证，权限不会因为“操作者很熟练”自动扩大。

Authority source of truth 位于真正控制 actuator writer 的仲裁器或 controller。UI 发出 takeover request 后，旧 policy 仍可能有 committed command、网络中仍有 response、queue 中仍有 chunk；因此 request、pending 和 confirmed 是不同事件。进入 pending 时先提高 epoch、拒绝旧 session、处理 committed prefix 并禁止新 policy candidate，直到 controller 确认 writer 切换。UI 只有读取该确认后才能显示 HUMAN_CONTROL，不能用本地按钮状态猜测。

交还自动控制同样需要握手。Human command 停止并不表示 policy 可以立即续接旧 plan；系统先确认稳定物理状态，采集 fresh observation，重建 reference state，开启新 session/epoch，再由 supervisor 明确批准。严重事件后的 SAFE_STOP 必须经过 RECOVERY_LOCKED、诊断、复验和 re-arm，禁止直接回 AUTONOMOUS。Shared control 还要公开组合函数、优先级、饱和、冲突和失联行为，确保任一时刻仍只有一个已确认 writer。

Takeover latency 分成检测、通知、人的理解与反应、输入传输、仲裁、controller 和物理响应。P99 只是观测，不足以判断能否避免 hazard；要和可用反应窗口及最坏物理后果比较。人的反应时间受视线、遮挡、相机延迟、设备位置、任务复杂度、训练、疲劳和惊吓影响，不能用固定常数覆盖。若 hazard 的时间窗短于可靠人工响应，人只能参与监督或批准，不能被列为唯一实时缓解。

HMI 需要让模式、authority、health 和所需动作一眼可区分。关键信号不只靠颜色，告警按 priority、来源和响应动作分层，避免 alarm flood。切换使用现场适合的视觉、听觉或触觉反馈，且 UI 明确显示“已请求”“等待确认”“已控制”。Teleop 显示延迟与 freshness；deadman/enabling device、方向、比例、离合和按钮映射都绑定平台验证。Stuck input、抖动、断线和无效值有检测，失效时不保持危险旧命令。

日志同时保存 policy candidate、human raw input、mapped command、executed action、controller ack 和 authority state，并用单调时间与 trace 关联。记录这些不是为了监控个人绩效，而是为了回答谁在何时拥有执行权、系统实际执行了什么以及交接延迟在哪里。访问、保留与训练复用遵循最小化和审批；涉及人员图像、声音、身份或行为的数据不因“安全研究”自动无限保留。

人的能力也有运行边界

安全案例描述人员可见性、培训、语言、无障碍、工作负荷、班次、远程连接和冲突职责。监督者同时关注多个机器人时，takeover load 与告警排队会改变可用反应时间；夜班、长时任务或事件后的压力也会改变表现。Staffing 和 shift handover 应进入 ODD 与发布条件，交班时复核未决告警、当前 authority、degraded mode、维护 bypass 和 re-arm 状态。

Loss of human link 采用预定义响应，而不是把 authority 静默交回模型。远程视频卡顿、控制设备断开或 supervisor 心跳过期时，系统根据 hazard 进入收紧 envelope、拒绝新任务、controlled stop 或其他批准状态；在恢复链路并重新确认物理状态前不自动续接。若当前处于需要持续人工输入的 teleop，断线后的行为必须在现场验证，并由独立安全链约束。

与 HG-DAgger 的数据边界保持清楚：安全接管记录的首要目的是真实控制和证据，是否纳入训练由后续数据治理决定。保护人和设备不等待“高质量示范”条件；接管失败或动作混乱也不能从日志中删除。训练管线使用这些记录时保留 consent、provenance、failure label 与 intervention timing，不把 human action 自动当作最优或安全标签。

Authority 验收应覆盖正常交接、双方同时请求、消息重复/乱序、旧 response 晚到、UI 与 controller 状态不一致、人链路丢失、SAFE_STOP 中请求运动以及严重事件后的错误 auto-rearm。每个用例检查 single-writer 不变量和实际 actuator source，而不只检查界面状态。任何 overlap 或无法确定 writer 的窗口都是 hard error，立即进入批准的安全处理。

验证阶梯

  1. 文档/静态：schema、hash、权限、traceability；
  2. unit/property：边界、NaN、单位、状态机不变量；
  3. golden/replay：candidate/filter/executed 对齐；
  4. adversarial semantic：矛盾、越权、injection、hallucination；
  5. fault injection：sensor/network/model/queue/controller/log/safety self-fault；
  6. SIL：完整实际软件链、无 actuator authority；
  7. HIL：真实接口/控制器或经界定设备；
  8. shadow：观察候选，不能控制；
  9. restricted canary：现场批准、受限 ODD、可立即停止；
  10. 扩展：只在预注册 exit criteria 满足后由人批准。

Incident 流程

事件发生后：

  1. protect people and contain energy；
  2. stop new commands；
  3. preserve volatile evidence without delaying safety action；
  4. identify physical state and authority；
  5. quarantine affected artifact/session/data；
  6. classify severity and scope；
  7. notify designated internal owners；
  8. protect privacy and access；
  9. reconstruct timeline；
  10. identify root and contributing causes；
  11. define corrective/preventive actions；
  12. add regression tests；
  13. reassess hazard/ODD/safety case；
  14. obtain reauthorization；
  15. communicate lessons within permitted scope。

不得自动 retry incident-causing action；不得为“保留日志”延迟 emergency response；不得在未确认物理状态时只重启模型。

  • purpose specification；
  • data minimization；
  • consent/notice where applicable；
  • capture zone and bystander handling；
  • edge redaction where feasible；
  • access least privilege；
  • encryption/integrity；
  • retention and deletion；
  • incident hold exception with approval；
  • separate identifiers from telemetry；
  • no credential/secret in logs；
  • export approval；
  • audit access；
  • model/training reuse boundary；
  • legal/organizational review。

页面不提供法律结论；不同地区和场景需专业评估。

发布门禁

发布必须同时满足：

  • scope/ODD frozen；
  • hazard register reviewed；
  • requirements traced；
  • independent safety functions verified in scope；
  • policy/deployment/safety contracts hashes match；
  • detector thresholds/version/evidence present；
  • fault matrix complete；
  • authority/takeover tested；
  • safe states validated on platform；
  • privacy/security review complete；
  • incidents/CAPA resolved or explicitly accepted；
  • rollback and recovery tested；
  • last-known-good identified；
  • approvers signed；
  • expiry/review date set；
  • no unresolved critical blocker。

Release decision 只可为：

  • DENY；
  • RESTRICTED：明确 ODD subset、期限、监护、退出条件；
  • APPROVE_WITHIN_SCOPE。

不能使用模糊“看起来可以”。

让指标暴露风险，而不是美化结果

安全报告以 task outcome 与 safety outcome 的 2×2 为骨架。Unsafe success 不能留在普通成功率里，safe failure 也不应被误读为系统毫无价值。Unsafe proposal、blocked unsafe proposal 与 executed unsafe action 分开统计：blocked 增加可能说明 gate 有效，也可能说明 policy 正在退化。Protective stop、emergency stop、near miss、hazard exposure、takeover 和 refusal 都绑定事件定义与分母；零事故只说明样本中未观察到，不证明风险为零。

每个 rate 明确按 trial、action、时间、hazard opportunity 或 person-hour 计算。Aborted、invalid、human-assisted、retry 和 reset 保留独立状态，不能通过分母清洗提高成功率。事件级数据与 trial 级结果并存，一个 trial 可包含多个 detector、多个 proposal 和一次最终 outcome。报告按 ODD、任务、对象、人员出现、版本和会话切片，并给小样本区间；总体数字不能覆盖关键子群的漏报。

Traceability matrix 是发布门禁的索引，而不是文档装饰。Reviewer 从 hazard 正向找到 requirement、mechanism、verification 和 evidence，也从 test 反向确认覆盖哪些 hazard；change 触发器能找出失效证据，incident 能定位缺失或失败 requirement，residual risk 能找到接受者。Evidence hash 绑定不可变产物，结果还注明设备、配置、ODD、时间和 reviewer。截图或视频没有版本关联时只能作为观察材料，不能独立支持实现正确。

验证阶梯逐层扩大现实性与后果。静态与 property test 验证 schema、单位、权限和状态机；golden/replay 检查 candidate、filter、execution 对齐；adversarial semantic 覆盖矛盾、越权、injection 与 hallucination；fault injection 验证失败传播；SIL 运行真实软件链但无 actuator authority；HIL 验证真实接口或界定设备；shadow 只观察候选；restricted canary 才在现场批准的受限 ODD 中运行。每一级都写明不能证明什么，失败时不自动升级。

安全测试预注册 linked hazard、版本、前置状态、注入场景、预期 detector、最大响应窗口、安全状态、authority 和证据。实际 timeline 保存触发、检测、仲裁、controller 响应与物理确认；偏差不靠事后改期望消除。故障注入从最低风险环境开始，公共页面不提供能驱动真机的一键脚本。结果若依赖人工判断，记录观察者角色、盲法或裁决规则。

事件、隐私与重新授权

Incident 流程先保护人和控制能量，再保全证据；不能为等待日志写盘延迟紧急响应。受影响 artifact、session、凭证和数据被隔离，事件 owner 重建时间线并区分 root cause 与 contributing factors。CAPA 同时包含修复、流程变化、回归测试和防复发监控；关闭事件前重新评估 hazard、ODD、safety case 和 residual risk。造成事件的动作禁止自动 retry，未知物理状态下也不只重启模型。

日志设计与隐私评审同步进行。摄像头、语音、家庭或工厂布局、屏幕、身份和位置只按明确目的采集，使用访问最小化、完整性、保留期限与删除规则。事件 legal hold 需要单独批准，不能变成无限保留默认。Telemetry 尽量与个人标识分离，导出需要审批，访问本身也进入审计。安全复盘之外的训练复用是新的目的，必须重新检查权限、告知、范围和偏差。

Release gate 不把多个失败项压成“总体绿色”。Scope/ODD、hazard register、traceability、独立安全功能、contract hash、detector、fault matrix、authority、safe state、privacy/security、incident/CAPA、rollback/LKG 与审批逐项有状态和证据。任何 critical blocker 未解决时只能 DENY；RESTRICTED 明确子 ODD、期限、监护和退出条件；APPROVE_WITHIN_SCOPE 也只在声明范围内有效。Decision、approver、evidence bundle 和 expiry 形成不可分割记录。

独立评审抽样从最终 claim 反查原始 evidence，也从原始事件正查是否进入报告，防止只选择有利结果。执行变更的人不单独批准自己的安全主张；无法完全分离时记录组织限制并增加复核。标准引用只帮助检查术语、方法和适用性，不意味着认证或合规；具体条款、目标等级和法律责任由合格人员针对现场判断。

运行中的保证需要持续维护。Proof test、校准、人员培训、签名、凭证和 review date 到期会改变 readiness；新事件、drift、unsafe proposal 增长、拒绝负荷或工具/载荷变化会触发 impact analysis。撤销批准与发布批准同样可追踪，并能让相关 session 停止获得新许可。旧 evidence 不被删除，但状态改为 superseded，并链接替代版本。

最终专题出口只表示读者已获得统一分析框架，不表示任何机器人可启动。实际真机页必须引用本页、具体 safety interface version/hash、现场 risk assessment、设备手册和批准记录；缺少任一项时显示未就绪。这样安全页既不会吞并模型实现细节，也不会成为无人落实的免责声明，而是把每个真机主张接到可检查的责任与证据链。

跨层闭环一：从危险场景追到执行证据

一个可审查条目从具体场景开始：谁在何处暴露于什么能量或错误行为，哪些前置条件使伤害成为可能。Hazard register 不直接写“模型出错”，而是说明例如目标身份漂移、工具状态未知与人员进入动态区如何共同形成 hazardous situation。Safety goal 再声明不可接受的后果，requirements 分别分配给身份确认、ODD entry、workspace predicate、authority、独立 inhibit 和物理反馈。每项 requirement 有唯一 ID、owner、适用模式、最大信息年龄和 unavailable 行为；缺少这些字段时，机制只能算设计意图。

验证时 reviewer 不只从 requirement 找测试，也从实际 executed action 反查许可链。一次成功 trial 应能关联 candidate、object/region ID、session/authority、所有 predicate 决定、独立 permission、controller command、ack、tracking 与最终 outcome。若系统只保留 clip 后向量，就无法判断模型原始风险；若只保留 safety event 而无正常样本，也无法估计 false positive 与运行负荷。Evidence bundle 同时保存通过与失败、拒绝与执行、正常与 degraded，避免报告只呈现顺利路径。

每条证据带 scope。Replay 能说明历史输入经过当前逻辑会得到什么决定，但不能证明传感器在线诊断或物理停止；HIL 能说明真实接口与部分设备行为，但不能覆盖现场人员、工具和全部环境；受控真机证据也只适用于声明的 ODD 和版本。Claim 页面因此并排展示 supported、partially supported、unsupported 与 out_of_scope，不使用一个“安全评分”抹平证据层级。若最高层 claim 依赖一条 unsupported requirement，发布门禁继承该阻断。

跨层闭环二：语义许可与物理许可不可互相代签

任务规范先把自然语言转成 canonical intent：动作对象、目标区域、允许工具、任务相位、人员与能力范围。语义层核对 source identity、authorization、冲突指令和 capability allowlist，并把不可信 scene text、retrieval 与 tool output 保持为数据。通过语义许可只表示“这个角色可在当前上下文请求此类任务”，不表示轨迹可执行。Candidate 仍须经过 contract、freshness、kinematic、collision、contact、payload 与 human predicates，并获得独立安全层许可。

相反，物理 predicate 全部通过也不能为越权或错误目标背书。一个在 workspace 内、速度受限的动作仍可能拿取错误对象、泄露隐私或执行未批准工具调用。两条许可链在最终仲裁点合流，任一路 reject 或 unavailable 都不能被另一路的高 confidence 覆盖。日志分别记录 semantic decision 与 physical decision，便于事件后判断是授权错误、grounding 漂移、几何漏检、传感器失效还是 controller 偏差。

澄清也是受限操作。系统可以请求人确认模糊对象或意图，但问题本身不能暴露秘密、诱导授权或让普通角色进入 maintenance override。确认绑定当前 session、object、任务和有效期；环境变化、对象移动或 authority 切换后旧确认失效。高影响意图需要平台规定的强确认路径，模型生成的“用户已同意”文本不构成授权事件。

跨层闭环三：故障、人工接管与恢复使用同一时间线

当 watchdog 发现 observation stale，第一条事件记录 observed age、bound reference、session、authority 和 requested state。仲裁器冻结新 policy command，处理已 committed 的动作范围，独立安全链请求场景批准的 transition；controller ack 与物理确认作为后续事件到达。若 supervisor 同时请求 takeover，系统仍遵循 single-writer：先让旧 epoch 失效，再等待 controller 确认 human authority。人的按钮时间、authority confirmation 与首个 human executed action 分别记录，因此接管延迟不会被 UI 点击时间低估。

进入安全状态后，incident owner 保护人员和能量，随后才冻结 artifact、保存易失 trace 并确认实际物理状态。诊断可能发现相机冻结、时间映射错误或日志丢包，但 recovery 不因找到原因而自动开始。修复之后按受影响 requirement 重跑 self-test、calibration、contract handshake、queue/session 清理和 proof test；reset 只清锁存，re-arm 需要授权，新会话先在 restricted mode 观察 exit criteria。若人工链路、关键 telemetry 或独立 safety health 仍未知，系统保持锁定。

这个时间线还揭示恢复竞争：服务自动重启、远程操作者重连和本地人员复位可能同时发生。Recovery contract 明确优先级，所有旧 credential、session 与 in-flight response 失效，任何一方都不能单独恢复 actuator writer。重复或乱序事件按 epoch 和幂等 ID 处理，但安全状态请求不得因为重复而被撤销。只有明确的 cancel/reauthorize 事件在满足前置条件时改变状态。

跨层闭环四：发布、运行监控与撤销形成闭环

发布评审从 manifest 固定 policy I/O、deployment bundle、safety interface、ODD、hazard register、threshold 与测试集摘要。Reviewer 对 critical requirement 做反向抽样，确认 evidence 文件可读取、hash 匹配、结果没有被新版本覆盖，测试环境与 claim scope 对齐。对 failure、unknown、not_run 和 deviation 分别计数；not_run 不能当作 pass，缺少证据也不能由负责人签字替代。审批者只在自己的责任范围签署，并记录依赖的其他批准。

APPROVE_WITHIN_SCOPE 不代表永久开放。运行时持续检查 ODD、artifact identity、authority、watchdog、unsafe proposal、blocked/executed ratio、takeover load、near miss、关键 drift 和证据管道健康。监控阈值本身绑定版本和校准来源；告警达到预设条件时可以收紧范围、进入 RESTRICTED 或撤销许可。为了可用性而静默提高阈值属于新的安全变更，必须重新评审。

撤销记录说明触发原因、受影响版本/会话、停止授予新许可的时刻、现场处置和所需 reauthorization。已生成证据不删除，而是标记 superseded、quarantined 或 invalid-with-reason，保留因果链。若事件影响多个机器人或场地，先按最保守的已知范围 containment，再通过证据逐步缩小，而不是等待完整根因才行动。Privacy/legal hold 与工程隔离分别审批，避免用事件调查名义无限扩大敏感数据访问。

专题验收的最后问题不是“有没有安全功能”，而是：任何候选动作能否说明谁授权、哪些独立条件允许、实际执行什么；任何故障能否在有界时间进入经批准状态；任何恢复能否证明旧权限与旧动作已经失效；任何安全主张能否追到版本化证据、限制和残余风险 owner。四个问题中任一无法回答，页面将其显示为发布缺口，而不是以免责声明掩盖。

证据缺口与保守显示

页面和后续实现必须把 pass、fail、unknown、unavailable、not_run、out_of_scope 与 expired 作为不同状态。Unknown 表示需要的事实尚未确定，unavailable 表示 predicate 或数据源当前不能给出决定，not_run 表示验证未执行，out_of_scope 表示证据从未承诺覆盖，expired 表示原证据超过批准有效期；这些状态都不能在聚合视图中被映射为 pass。若某项不是当前 claim 的必要条件，可以显示 not_applicable，但必须附适用性理由和 reviewer，不能由字段缺失自动推断。

汇总卡显示最严重的未闭环状态，并允许下钻到 requirement、test、evidence、limitation 与 owner。颜色只作辅助，文本、图标和机器可读字段同时表达；导出 YAML 与页面使用同一枚举，避免报告生成阶段“翻译”掉缺口。任何人工 override 都创建带范围、理由、批准者和到期日的新决策事件，不修改原始测试结果。Override 到期或前提变化后自动失效，不能跨版本继承。

对关键安全 requirement，缺失或不可用采用规格规定的 fail-bounded 行为；但“fail safe”不能被写成所有故障都急停，因为不同载荷、能量和人员位置需要不同批准状态。页面只证明决策链是否完整、状态是否被验证和责任是否可追踪，不提供公共停止参数。最终读者看到的是证据边界，而不是一个容易被误读的安全徽章。

必须纠正的误读

  • “急停能保证安全”错误；急停是特定安全功能，不能替代风险降低层级、预防、验证和恢复。
  • “速度低就是安全”错误；风险还取决于质量、工具、接触、距离、停止性能、姿态和环境。
  • “没有碰撞就安全”错误；夹持、挤压、烫伤、倾倒、跌落、越界、隐私和语义伤害都可能存在。
  • “模型拒绝危险指令，所以系统安全”错误；低层 motion/force/collision 仍需独立防护。
  • “安全层把动作裁剪到范围内即可”错误；非法语义、坐标系错误和路径碰撞通常应拒绝或停止，不能静默裁剪。
  • “置信度 0.9 就有 90% 安全概率”错误；需定义标签、校准集、分布和事件窗口。
  • “OOD 等于 ODD 之外”不完整；ODD 是批准运行域，模型 OOD 是相对训练/校准分布的统计判断，两者可交叉但不等价。
  • “任一 OOD 分数低即可执行”错误；多信号 detector、确定性约束和安全状态缺一不可。
  • “不确定就输出零动作”危险；零向量在 delta/velocity/torque/absolute position 中含义不同。
  • “watchdog 收到心跳就健康”错误；必须检查序号、新鲜度、进展、deadline、controller ack 和依赖。
  • “断网后重复上个动作”危险；重复 delta、torque 或过期 chunk 可能累积。
  • “fallback policy 是安全策略”未经证明；它同样可能 OOD、超时或违反约束。
  • “冗余传感器越多越安全”错误；要分析共因、同步、仲裁和错误一致性。
  • “人工在场即可兜底”错误；需可见性、反应预算、设备、权限、培训、负荷和交接验证。
  • “人按下接管键时已经接管”错误；必须等待 actuator authority/旧命令失效确认。
  • “自动交还可提升效率”不等于安全；严重事件后不得无人工确认自动 re-arm。
  • “任务成功且无人接管就是安全成功”错误；仍需检查约束、near miss、unsafe proposal 和授权。
  • “安全停止次数越少越好”不完整；可能是 detector 漏报。
  • “availability 越高越安全”错误；安全系统应在某些条件下拒绝服务或停止。
  • “通过 SIL/HIL 就符合标准”错误；验证层级不是认证。
  • “引用标准编号即可选择 PL/SIL”错误；目标等级来自具体风险评估和适用方法。
  • “日志越全越好”错误；实时干扰、敏感信息、数据最小化和保留期限需要权衡。
  • “prompt injection 只来自用户文本”错误；视觉场景、二维码、标签、网页、检索文档和工具返回都可能是不可信内容。
  • “system prompt 能彻底阻止 injection”错误；需要权限分离、allowlist、输出验证和独立物理 gate。
  • “VLM judge 能验证 VLM policy”存在共享偏差风险；不能成为唯一 oracle。
  • “偏好对齐后的策略能取代 deterministic safety layer”禁止。
  • “安全案例完成后不需更新”错误；本体、工具、载荷、模型、camera、adapter、阈值和 ODD 变化都触发 impact analysis。

读者必须能：

  1. 画出系统边界和安全相关外部实体。

  30. 为每类故障填写 detector、owner、safe state、recovery、audit evidence。
  31. 设计独立 watchdog 的 failure domain。
  32. 检查心跳 freshness、monotonic progress 与 deadline。
  33. 区分 liveness、readiness、functional health 和 safety health。
  34. 按上下文定义 safe hold/controlled stop/de-energize 等状态。
  35. 解释“去能”在重力载荷下未必安全。
  36. 限制 degraded mode 的 ODD、任务、速度和时间。
  37. 禁止严重事件后自动 re-arm。
  38. 定义 authority 的单写者不变量。
  39. 验证接管请求与接管确认不是同一事件。
  40. 使旧 chunk/in-flight response 在交接时失效。
  41. 记录 policy command、human command 与 executed action。
  42. 估计 end-to-end takeover latency。
  43. 将 human workload/visibility/training 纳入安全案例。
  44. 区分 supervisory、shared control 与 direct teleoperation。
  45. 设计 loss-of-human-link 的预定义响应。
  46. 将任务成功与安全成功组成 2×2 矩阵。
  47. 分开 unsafe proposed/blocked/executed。
  48. 定义 near miss 与 hazard exposure 的计数口径。
  49. 设计 hazard-to-evidence traceability matrix。
  50. 设计 fault injection 和 adversarial test matrix。
  51. 区分 unit、replay、SIL、HIL、shadow 和 canary 能证明什么。
  52. 记录每级测试不能证明什么。
  53. 建立 incident preservation、triage、RCA、CAPA 和 reauthorization。
  54. 将安全事件日志与隐私/访问/保留规则同时设计。
  55. 判断标准适用性，而不宣称认证。
  56. 输出 safety interface contract 与 release gate。
  57. 让所有真机页引用本页和具体 contract hash。

版本注记

  • ISO 10218-1/-2 使用 2025 版，旧 2011 版已撤销，不并列写成现行。
  • ISO 12100:2010 截至核验日仍为现行，但处于修订中；页面显示“现行/待修订”。
  • IEC 62061 页面应标 base edition 与修订；不凭修订标题推断具体条款。
  • IEC 61508 Edition 3 在核验日是预发布/FDIS 流程，不写成已正式替代 2010 版。
  • ISO/TS 15066 的适用性与 ISO 10218:2025 关系由专业评审判断，不自行声称覆盖。
  • ASIMOV、Gemini Robotics、RoboART 结果不能外推到未测试机器人或场景。
  • OWASP/NIST security guidance 不替代机械安全标准。
  • UL 4600 的 autonomous product scope 不自动适用于所有工业机器人项目；只借鉴 safety case 思路。

跨页一致性门禁

与机器人学/控制页

必须一致：

  • frame/unit/rotation；
  • controller mode；
  • calibration；
  • joint/workspace/force semantics；
  • tool/payload；
  • safety function owner。

若控制页没有某约束，不得在本页假定已实现；标为 required input。

与动作表示页

必须一致：

  • absolute/delta/velocity/torque semantics；
  • action horizon/chunk；
  • decode/unnorm；
  • discrete token meaning；
  • scheduler/reference state；
  • zero action meaning。

与训练/适配页

必须一致：

  • checkpoint/processor/stats hash；
  • OOD calibration version；
  • data/feedback provenance；
  • catastrophic forgetting checks；
  • release/rollback candidate；
  • online update approval。

训练改善不能自动改写安全批准。

与长时序页

必须一致：

  • planner/policy/tool ownership；
  • memory trust/retention；
  • subgoal authorization；
  • termination/replanning；
  • recovery plan；
  • hallucinated completion。

高层 planner 不得绕过低层 safety gate。

与统一评测页

必须复用：

  • policy instance；
  • trial protocol；
  • 2×2 task/safety outcome；
  • failure taxonomy；
  • denominator/CI；
  • latency/recovery/intervention；
  • unsafe proposal blocked/executed；
  • evidence hash。

与实时部署页

必须消费：

  • health/readiness；
  • observation/action age；
  • timeout/stale/invalid；
  • queue starve/overflow/reorder；
  • session/deployment/contract hash；
  • controller ack/tracking；
  • trace；
  • fallback request；
  • authority channel；
  • rollback。

安全页补充：

  • hazard mapping；
  • independent watchdog；
  • safe-state selection；
  • takeover/re-arm；
  • incident and approval。

与 HG-DAgger / RTC / Harness / RLT / RLHF-VLA

  • HG-DAgger：人工门控的数据用途不覆盖现场 authority。
  • RTC：实时 chunk 改善不覆盖安全性。
  • Harness：primitive/memory/flash 受 capability 和 safety gate 约束。
  • RLT：在线 rollout 先满足 safety approval，不能用 reward 替代 constraint。
  • RLHF-VLA：偏好优化不能替代物理、运行或 security controls。
