数据采集与保存

从 VR 手柄输入到 HDF5 落盘的完整数据链路——采样节流、多路相机选帧、帧对齐锚点设计、字段全表与恢复数据闭环

← 项目主页 ·系统架构 ·PyRoki 逆解器 ·数据采集与保存 ·工程问题记录

一条 episode 要同时记录：三路 640×480 的图像、七个关节的实测角与下发指令、夹爪的期望态与真实开口、以及每一项数据各自的时间戳与对齐误差。难点不在于「写文件」，而在于这四路数据的节拍互不相同——相机 30 fps（33 ms 一帧）、关节后台轮询 50 Hz（缓存最旧 20 ms）、夹爪状态 50 Hz、控制主循环 110 Hz。如果各取各的「最新值」，同一行数据里会混进相差 30–50 ms 的内容。

一、现场：一次采集是怎么进行的

恢复数据采集现场 · 93 秒 · 原速
恢复数据采集现场 · 93 秒 · 原速

采集时同时开四个终端：夹爪守护、夹爪状态回传、遥操作、数据采集。启动顺序有讲究——遥操作进程必须先起来并开始广播状态包，采集进程才能订阅到。采集进程启动后自己再派生一个独立的相机进程。

按键分工全部在 VR 手柄上，操作者不用回头看键盘：

  • 右手 A — 开始录制。录制中再按一次 = 丢弃当前这条、就地重录。
  • 右手 B — 停止录制（或到达单条上限 3000 步自动停）。
  • 左手 Y — 保存。左手 X — 丢弃，且编号不递增，下一条仍用同一个号。
  • 左手摇杆按下 — 回 home 位。终端 e 键 — 正常退出。

有一条硬约束：必须等上一条彻底保存完成，A 键才重新生效。任何在忙碌期的非法按键都会打印出被拒绝的原因，而不是静默忽略。

采集入口命令与参数

遥操作进程先在 110 Hz 下发并广播状态；采集端随后用下面的入口订阅状态、按 30 Hz 取样并写三路视频。路径与设备号用变量表示，避免把某台机器的 /dev/videoN 固定写进文档：

cd "$D/data_collection"
"$PY" record_collector.py --dataset-name pick_cube --max-steps 3000 --head-dev "$HEAD_DEV" --arm-dev "$ARM_DEV" --third-dev "$THIRD_DEV" --preview-port 9001
参数 本项目值 作用与边界
--dataset-name pick_cube 决定会话目录与任务分组名称，不改变控制或采样算法
--max-steps 3000 单条 episode 上限；30 Hz 下约 100 秒，到点后自动停止并等待保存/丢弃
--head-dev / --arm-dev / --third-dev 三个稳定设备标识 固定三路相机语义，避免重启后 /dev/videoN 漂移导致视角互换
--preview-port 9001 只改变监控页端口，不改变录制频率或数据内容
--record-hz 默认 30 从 110 Hz 状态流抽样的频率；卡顿时不追补，不参与机械臂下发
--state-port 默认 5604 接收遥操作进程的 128 字节状态包，发布端与订阅端必须一致
--gripper-state-port 默认 5601 接收 50 Hz 夹爪真实开口；缺失时不能用期望值静默冒充实测值

正式采集前可用 view_cameras.py --probe 查设备标识，再用 --web 核对三路视角；预览进程必须在采集启动前退出，否则会与录制进程争用 V4L2 独占设备。

二、录制状态机与采样节流

录制器内部是一个七态状态机：IDLE → PREPARING → RECORDING → STOPPING → ASK → SAVING/DISCARDING → IDLE。主循环每一轮只做四件轻量的事：收一个状态包、检查遥操作是否失联、驱动状态机、扫一次按键。所有会阻塞的事——等相机确认、写 HDF5、编码视频——都甩给一个后台工作线程，主循环只改状态字。

采样节流做在录制器内部：按 30 Hz 的目标周期判断是否到点，没到就直接返回。这里有个细节值得说：如果因为卡顿落后了多个周期，实现上不做「追补」，而是直接把下一次采样时刻对齐到当前时刻。追补会让时间步之间的实际间隔失真，而数据集里 timestamp 的等间隔性比「一帧都不少」更重要。

遥操作进程失联也有兜底：状态包超过 1 秒没来就判定断开，如果此时正在录制，自动执行「停止 + 丢弃」，不会留下一条只有前半段的残缺数据。

三、三路相机：抓帧、缓冲、选帧、编码

相机跑在独立进程里，每一路配三样东西：

  • 抓帧线程：不断抓图。时间戳在 grab() 一返回就立刻打上——这个位置比取回图像数据之后再打更接近真实曝光时刻。
  • 环形缓冲：15 帧，约 0.5 秒的历史。这是整个对齐方案能成立的物质基础。
  • 录制线程：从队列取采样请求，按时间戳选帧，写进 ffmpeg 管道。

这样切分的目的是：所有可能阻塞的动作（等帧、编码）都在录制线程里，抓帧线程和 UDP 收包线程永远保持响应。

视频用 ffmpeg 编 H.264（veryfast 预设、CRF 20、yuv420p、faststart），编码发生在 ffmpeg 自己的进程里，连相机进程的 GIL 都不占。

帧数严格等于时间步数：每个采样请求写且只写一帧。取不到帧时不推进写入指针、留一个缺口，等下次成功取帧时由补帧逻辑回填，并把那些帧标记为「重复帧」。这样 视频帧数 == T 这条不变式永远成立，而且哪些帧是补的、补了多少，数据集里查得到。

四、进程间状态协议：128 字节定长

遥操作进程每帧向采集端广播一个 128 字节的定长二进制包（UDP，fire-and-forget）。

字段 含义
magic / version / seq 包标识、协议版本、自增序号
t_align 关节真实被测量到的时刻（对齐锚点）
t_send 发包时刻
q_meas[7] / q_cmd[7] 实测关节角 / 下发关节指令（单位：度）
v[7] 关节速度（度/秒）
trigger 右手扳机原始值
grip_desired 夹爪期望态：1.0 全开 / 0.5 半开 / 0.0 夹紧
qpos_age 关节读数的陈旧度
homing_evt 回位事件编码（自增序号 × 4 + 触发来源）
flags（8 位） A/B/X/Y 键、机械臂正常、回位中、急停、夹爪通道正常

为什么用二进制而不是 JSON：打包一次约 1–2 μs，而 JSON 序列化约 30–50 μs。这发生在 110 Hz 的主循环里，差别不能忽略。

接收端采用 latest-wins：收到一个包之后把内核缓冲排空、只留最新的一个。这带来一个副作用——单帧脉冲型的事件会丢。回位事件因此不能传「这一帧按了没有」，而要传「累计按了多少次」的自增序号：这样即便中间丢掉任意多个包，只要后面任何一个包到达，接收端仍能发现事件发生过。

新增回位事件字段时没有扩容、也没有升版本号：协议末尾本来就有一个恒为 0、无人读取的预留浮点位，直接用它承载，包长仍是 128 字节，完全向后兼容。（flags 的 8 个位当时已经用满了。）

五、帧对齐：让能回头的去对齐不能回头的

这是整条链路里最花心思的一处设计。

四路数据分成两类：不能回头的（关节角——重新读一次要阻塞 6.5 ms 的 TCP 往返，会打爆 110 Hz 的时间预算）和能回头的（相机——有 0.5 秒的环形缓冲，随时可以往回翻）。

结论就很清楚了：锚点定在关节被真正测量到的那一刻，让相机回头去缓冲里挑最接近那一刻的帧。

每一步涉及三个时刻：

  • t_step — 名义采样时刻，按 30 Hz 等间隔推进，写进数据集的 timestamp，保证时间轴均匀；
  • t_align — 对齐锚点，取关节后台轮询线程记下的真实测量时刻，通常比 t_step 早 0–20 ms；
  • t_frame — 每一帧图像的曝光时刻。

相机按 |t_frame − t_align| 最小来选帧。因为锚点在过去，那一帧早就在缓冲里了，根本不用等——离线单测实测选帧耗时 0.00 ms。对齐更准的同时延迟反而更低。锚点若因为轮询卡顿而过旧（超过 0.2 秒），就退回用 t_step，这样更安全。

所有进程统一使用单调时钟。容器内实测两种单调时钟源的差异为 3e-7 秒，环境自检每次都会复验这一项。

实测对齐误差：

测量批次 相机 p50 p95 最大
两路相机阶段（90 步） 全局视角 7.3 ms 11.3 ms 13.0 ms
两路相机阶段（90 步） 腕部视角 6.5 ms 11.0 ms 14.4 ms
三路相机阶段（汇总） 三路整体 ≈ 9 ms 14.3–16.2 ms ≤16.7 ms

前两行是接入第三路相机之前做的逐路端到端实测；接入第三路之后重新测量，只保留了三路汇总的分位数，因此第三视角没有单独一行——这也是为什么后一批的 p95 比前一批高了约 3 ms。

16.7 ms 是 30 fps 下的理论半周期上限，两批测量全部落在里面，补帧 0 步。

诚实的边界。 这几台 USB UVC 相机没有硬件同步（无外触发、无 PTP），做不到严格同曝光。本方案能保证的是每一步的对齐误差都被测量并写进文件，训练前可以据此筛掉超差的 episode，而不是假装数据是对齐的。另外，软件时间戳打的是「数据到达容器的时刻」而非「设备真实采样时刻」，残余的系统性偏差约十几毫秒，尚未测量。若需要更严格的同步，正确做法是换支持外触发的相机，而不是在软件层继续加补偿。

六、数据长什么样

6.1 内存缓冲

录制开始时按单条上限一次性预分配 numpy 数组，录制期间零内存分配、零磁盘 IO；按下保存键后，再由后台线程一次性写 HDF5。视频则相反，是边采边写。

6.2 HDF5 字段全表（22 个）

组 字段 形状 类型 含义
observations qpos (T, 8) float32 前 7 维：实测关节角（度）；第 8 维：夹爪真实开口归一化
observations qvel (T, 8) float32 关节速度（度/秒）+ 夹爪速度
observations gripper_raw (T,) float32 夹爪原始角度；通道失联时为 NaN
observations trigger (T,) float32 右手扳机原始值
observations head/arm/third_frame_seq (T,) int32 三路相机各自被选中那一帧的序号

根级 action (T, 8) float32 前 7 维：下发关节指令（度）；第 8 维：1.0/0.5/0.0

关键定义澄清两处：

action 是「下发的关节指令」，不是「实测角」。 它取自经过逆解、安全层、限速限加速度之后真正发给机械臂的那组目标角。这一点在做恢复数据时曾出过问题，见本页第七节。

单位统一用「度」。 这是机械臂 SDK 的原生单位，全程零换算，并在文件属性里显式标注 joint_unit=deg。

根级属性还记录了：机器人型号、episode 编号、总步数 T、采样频率、臂自由度、夹爪自由度、夹爪归一化分母、相机名称与分辨率、每路视频的实际帧数、video_frames_match_T 是否为真、夹爪降级步数、对齐超差步数、开始时刻（单调时钟与墙钟各一份）、会话名、关节限位。

6.3 目录结构

<数据集根>/
└── 20260827_082313_pick_cube/          时间戳 + 自定义名
    ├── episode0000.hdf5
    ├── episode0001.hdf5

编号由扫描已有文件取最大值加一得到，支持中断后续采。丢弃的那一条不占号。

写 HDF5 时先写成临时文件、最后原子替换，绝不会留下半截文件。三路数据的落盘顺序也有严格约束：先等相机进程确认视频写完，再读回它落下的对齐信息，最后写 HDF5——全部完成才把状态机切回空闲，A 键才重新生效。

七、恢复数据集：把失败也变成训练数据

模型只学成功轨迹时，一旦在真机上偏离了训练分布，就没有能力自己走回来。解决办法是把「人把它救回来」的过程也录下来。

这不是「人为把机器人摆到失败位姿再示教」，而是模型在线跑失败时人接管——起点就是策略自己跑出来的那个真实的将败状态。

为什么必须做成单进程

这里和前面的分体架构正好相反。既有的运行纪律写得很清楚：采数与推理绝对不能同时跑——两者会争抢相机的 V4L2 独占、夹爪的 UDP 端口、以及 CAN-FD 通道。而这个需求偏偏要求两者在同一个会话里共存。再加上机械臂建连非幂等、VR SDK 进程内全局这两条铁律，结论只有一个：必须单进程融合，由一个模式仲裁器在四个状态之间切换。

状态 含义
AUTO 模型自主推理，按预测动作块执行
SOFT_STOP 收到介入请求，沿原规划轨迹的时间轴在 0.25 秒内减速
HANDOFF 交接期，后台仍以 110 Hz 重发冻结点，保证指令流不断
TELEOP 人工控制，此时才开始记录

软急停这一步值得单独说：它不是「位置冻结」，而是把原来的规划轨迹在时间轴上压缩减速，保证位置、速度、加速度三重连续。触发方式是左手握把按到 80% 以上并保持 100 毫秒——加保持时间是为了防误触。

记录门控：从 61.6% 的教训里长出来的

第一批恢复数据采完后做质量审计，发现了一个严重问题：5 条 episode 共 5659 帧里，3486 帧（61.6%）根本不是人工遥操作，而是模型推理期录进去的；其中两条 episode 是 100% 推理期。

更麻烦的是这些帧不只是「没用」，而是有害：非人工控制期间，仲裁器每帧会把「下发指令」同步成实测角，于是 action 退化成了观测的拷贝——有 57–60% 的帧里 action 与 state 逐位完全相同（差值小于 1e-9），其余帧差值中位数也只有 0.003°。拿这种标签训练，等于在教模型「下一步动作 = 当前位置」，学出来的行为就是静止不动，而且夹爪永远张开。

这批数据最后是这样用的：数据本身没有损坏，但不能整包拿去训练；筛选方法很直接——observations/trigger 为 NaN 的帧全部剔除（非人工控制期不写扳机值），剩下 2173 帧可用。同时在录制入口加了 TELEOP-only 门控：开始录制键只在人工控制状态下才生效，从根上杜绝了推理期被录进去。

恢复阶段的 30 Hz 动作怎样变成 110 Hz 指令

恢复运行里的模型动作块处在 30 Hz 名义时间轴上，前七维是绝对关节角，第八维是夹爪档位。配置 speed_scale=s=0.35 后，模型时间轴实际按

\[f_{step}=30s=10.5\ \text{step/s}\]

推进；CAN-FD 发送仍保持 110 Hz。对动作块起始时刻 $t_0$ 和任一发送时刻 $t_m$，代码按单调墙钟求

\[u=f_{step}(t_m-t_0),\qquad k=\lfloor u\rfloor,\qquad \lambda=u-k,\] \[\mathbf q(t_m)=(1-\lambda)\mathbf q_k+\lambda\mathbf q_{k+1}.\]

这样处理的原因是 $110/10.5$ 不是整数：若机械地在每两个路点之间固定塞入相同数量的帧，动作时间轴会持续漂移。墙钟线性插值让发送拍自然落在不同相位；块执行完而新块尚未到达时继续保持末帧，避免 CAN-FD 指令流断开。夹爪不做连续插值，而是取最近路点并吸附到 0 / 0.5 / 1 三个真实档位。

当前历史配置使用 E=25 个执行步、V=10 个重叠步：在 $E-V=15$ 步时触发下一次推理。按 10.5 step/s 换算，一块计划覆盖约 2.38 秒，约 1.43 秒后开始请求下一块，重叠窗约 0.95 秒。推理 p50 118.0 ms 相当于约 1.24 个当前速度下的模型步；执行器按向上取整补偿时会跳过新块前 2 步，避免把已经过时的块头重新执行。

新块到达后，旧块和新块先在同一个墙钟时刻各自插值，再用五次 smootherstep 在重叠窗内融合：

\[w(z)=6z^5-15z^4+10z^3,\qquad \mathbf q_{blend}=(1-w)\mathbf q_{old}+w\mathbf q_{new},\quad z\in[0,1].\]

它满足 $w’(0)=w’(1)=w’‘(0)=w’‘(1)=0$，所以融合权重不会在窗口两端额外制造速度或加速度突变。--blend-max-jump-deg 2.0 是融合安全闸：110 Hz 融合结果单帧跳变超过 2° 时放弃本次混合，切换到经安全链处理的纯新块。历史日志记录到 266 次平滑融合和 rejected=0 / aborted=0，只说明该次运行，没有外推成长期成功率。

融合之后仍按“EMA 0.25 → 144 °/s 限速 → 15° 软限位刹车 → 接近目标减速 → 1000 °/s² 限加速度 → 硬限位兜底”的顺序处理。线性插值负责时间升频，C² 融合负责块接缝，五级安全链负责噪声、速度、加速度和关节边界，三者不能互相替代。

软急停怎样交给人工控制

左手握把达到 80% 并持续 100 ms 后，仲裁器才从 AUTO 进入 SOFT_STOP，短暂保持用于防止误触。软急停不会瞬间把速度写成零，也不会停止 110 Hz 发送；它停止继续消费自主动作，把原规划轨迹的时间推进在 0.25 秒窗口内逐步降到零，再由同一套状态化滤波、限速和限加速度链输出。停稳后进入 HANDOFF，后台继续以 110 Hz 重发冻结点；完成 VR 离合重锚后才进入 TELEOP，也只有此时才允许把人工纠正写入 recovery episode。

这是一条软件层的平滑交接路径，目标是避免从模型轨迹瞬间跳到人工参考；它不等同于 Ctrl+C 的紧急停止，更不能替代机械臂控制器或现场硬件的安全急停。

历史规模与成功率待复核：原页面曾写“733 + 580 = 1313 条、796,412 帧、64%→92%”，本次在允许查看的容器中没有找到对应清单或逐次评估表；检索到的另一个项目文档则写“1393 条 / 859,154 帧 / 164 GB”和“92%”，同样缺少当前可访问的完整数据集与成功/失败明细。因此本页只展示第 6.4 节的已挂载文件统计，并把这些历史数字保留为待追溯线索。

恢复数据在落盘上与常规数据完全同构（同样是上表那 22 个基础字段），只靠数据集名字前缀区分，训练时可以单独加权。后来又可选地增加了 5 列 VR 手柄位姿字段（位置、四元数、握把、扳机、数据陈旧度）——开启后是 27 列，并在文件属性里打标记；这 5 列默认可关，关掉时仍是标准的 22 列，因此新旧数据始终能混用。

八、怎么验证数据是对的

回放：一个独立脚本读 HDF5，把关节角序列灌进 MuJoCo 里的 RM75 模型逐帧回放，无头渲染后推成 MJPEG 流，浏览器直接看。画面右上角用大号数字显示夹爪开合（取自 action 的第 8 维，回放界面按开 / 合两态呈现），左上是进度，底部是七个关节角。

上真机前的环境自检：九项，包括 numpy 与 h5py 可用、OpenCV 带 FFMPEG 与 V4L2 支持、两种单调时钟同源、三路相机能以 640×480 打开、MP4 编码解码往返一致等。

离线单测：十一组，覆盖录制状态机、相机通信协议、分体模式、状态流、回位事件、滤波器同步、左手控制器、松手保持等。另有一个干跑冒烟测试，会真实启动整条遥操作链路（约 19 秒），专门用来抓那些纯离线测试发现不了的问题——比如某个功能因为上层包装对象不转发属性而静默失效。

每条数据的自检指标（都写在文件属性里，可批量筛选）：

  • video_frames_match_T 是否为真
  • 三路对齐误差的 p50 / p95 / 最大值
  • 补帧步数是否为 0
  • 夹爪通道降级步数是否为 0
  • 全部字段是否无 NaN
  • 时间戳是否单调
