③ Docker 工程环境📑 论文索引

具身智能项目的环境复杂度与算法复杂度是同一个量级的问题。一台机器上同时要跑 CUDA、ROS 2、JAX、PyTorch、仿真器与大量 Python 包，而它们对系统库、Python 版本、驱动版本的要求经常互相排斥。容器在这里不属于可选的工程规范，而是让这些项目在同一台机器上共存的前提条件。

1 项目对应 1 个镜像
2 类卷代码卷与数据卷分开
0 改动宿主机系统环境
本页所有需要填写的位置一律使用占位符，例如 <宿主机路径>、<容器名>、<镜像名:标签>。实际使用时替换成自己的名称与路径。

为什么具身智能项目几乎必须用容器

不用容器的典型结果是：装完第二个项目，第一个项目跑不起来。冲突不是偶发的，而是这个领域的结构性问题。

  • CUDA 与深度学习框架版本绑定。不同版本的 PyTorch 与 JAX 各自锁定一段 CUDA 版本区间，两个项目要的版本很可能不重叠。而 JAX 与 PyTorch 装在同一个环境里争抢显存与 cuDNN 也是常见麻烦。
  • ROS 2 绑定操作系统发行版。每个 ROS 2 发行版基本只在特定的 Ubuntu 版本上受支持，想同时用两个发行版，靠一台裸机做不到。
  • 仿真器有自己的系统依赖。物理引擎与渲染后端会拉一串图形库依赖，与桌面环境的既有版本冲突时很难两全。
  • Python 虚拟环境不够用。virtualenv 与 conda 只隔离 Python 包，隔离不了系统动态链接库、驱动接口与 apt 装的东西——而冲突恰恰多发生在这一层。
  • 可复现性。论文复现、他人接手、换机部署，靠一份 Dockerfile 比靠一篇「环境配置说明」可靠得多。

三个具体的冲突例子

「依赖冲突」这个说法过于笼统，下面三类是实际项目里最常出现的具体形态。

  • numpy 主版本互斥。numpy 2.x 改变了 ABI，为 numpy 1.x 编译的二进制扩展在 numpy 2.x 下导入时直接报错。而具身智能项目里同时存在大量带二进制扩展的包：仿真器绑定、点云处理库、部分数据集工具。项目 A 的某个依赖只支持 1.x，项目 B 的框架版本要求 2.x，两者在同一个 Python 环境里没有可行解——升级则 A 的二进制扩展导入失败，降级则 B 的框架装不上，锁在某个中间版本则两边都不满足。
  • CUDA 运行时与驱动的上下界夹击。宿主机驱动决定了能跑的最高 CUDA 版本，框架版本决定了能跑的最低 CUDA 版本。两个项目分别落在不同区间时，裸机上只能选一个。容器把 CUDA 运行时装进镜像，宿主机只留驱动，两个区间就可以同时满足。
  • JAX 与 PyTorch 的显存策略冲突。JAX 默认会预占大部分显存，PyTorch 按需分配。两者在同一进程或同一张卡上共存时，后启动的一方常常直接拿不到显存。分容器之后至少可以按卡隔离，问题从「无法启动」降级为「资源规划」。

容器解决不了的那部分

把边界划清楚，才不会在排查问题时朝错误的方向找。

  • 内核是共享的。容器与宿主机用同一个内核，需要特定内核版本或内核模块的功能（实时补丁、某些设备驱动）无法靠容器解决。
  • 驱动是共享的。GPU 驱动装在宿主机，所有容器共用一份。两个项目需要不同大版本的驱动时，容器无法解决。
  • 硬件资源是共享的。显存、内存、磁盘带宽都没有默认的硬隔离，一个容器把内存吃满，其他容器同样会受影响。
  • 架构不能跨越。为一种 CPU 架构构建的镜像不能直接在另一种架构上运行，边缘设备与工作站之间搬运镜像时要留意这一点。
一个实际可用的组织原则：一个项目一个镜像，一个实验一个容器。镜像负责「依赖装好」，容器负责「这次跑什么」。容器随时可删，代码与数据都在挂载卷上，删容器不会丢东西。

镜像与容器的关系

这是初学时最容易混的一对概念。可以类比成「安装包与已安装的程序」，也可以类比成「类与对象」。

  • 镜像（image）是只读模板，由一层层文件系统叠加而成，每条 Dockerfile 指令生成一层，层之间可以复用与缓存。
  • 容器（container）是镜像的运行实例，在镜像之上加了一层可写层。同一个镜像可以同时跑出多个互不干扰的容器。
  • 容器内对文件系统的修改默认只落在那层可写层里，容器删掉就没了——这是新手最常踩的坑。
  • 想把容器里的改动固化成新镜像，用 commit；但更推荐的做法是把改动写回 Dockerfile 重新构建，这样过程是可追溯的。
  • 镜像可以导出成 tar 文件在机器之间搬运，也可以推到镜像仓库（registry）分发。

分层与可写层

flowchart TB
  BASE["基础镜像层：发行版根文件系统加 CUDA 运行时"] --> L1["构建层 1：apt 装的系统依赖与图形库"]
  L1 --> L2["构建层 2：Python 依赖，框架与仿真器"]
  L2 --> L3["构建层 3：项目自身的安装与环境变量设置"]
  L3 --> IMG["只读镜像：以上各层的有序叠加，内容寻址且不可修改"]
  IMG --> W1["容器 A 的可写层"]
  IMG --> W2["容器 B 的可写层"]
  IMG --> W3["容器 C 的可写层"]
  W1 --> F1["容器 A 看到的完整文件系统"]
  W2 --> F2["容器 B 看到的完整文件系统"]
  W3 --> F3["容器 C 看到的完整文件系统"]

多个容器能共享同一份镜像层，靠的是两条机制：

  • 层是只读且按内容寻址的。同一层在磁盘上只存一份，谁引用它都指向同一份数据。三个容器同时跑，磁盘上并没有三份 CUDA 运行时。
  • 写时复制（copy-on-write）。容器要修改只读层里的某个文件时，先把它复制到自己的可写层再改，之后所有读写都落在副本上。只读层始终不变，因此其他容器完全不受影响。

这两条机制解释了几个常见现象：起一个新容器几乎是瞬时的（不需要复制文件系统，只需要新建一层可写层）；容器占用的磁盘远小于镜像（只有改动的部分）；在容器内大量写文件会让可写层膨胀，而这部分数据在容器删除时一并消失。

概念 是什么 生命周期 典型误区
镜像 只读的分层文件系统模板 长期保留，可复用 以为改了容器就等于改了镜像
容器 镜像加一层可写层的运行实例 随用随删 把代码和数据直接写在可写层里
卷 挂进容器的宿主机目录或命名卷 独立于容器存在 忘记挂载，训练结果随容器一起删掉
Dockerfile 构建镜像的脚本 应纳入版本管理 只在容器里手动装，不回写文件

Dockerfile 的分层顺序

Dockerfile 的写法直接影响构建速度：把变动最少的步骤（系统依赖、框架安装）放在前面，把变动最频繁的步骤（项目代码相关的安装）放在后面。层缓存从上往下逐层比对，一旦某层失效，它之后的所有层都要重建。顺序放反的直接后果是每改一行代码都要重装一遍 CUDA 相关的依赖。

一个符合这个原则的骨架大致是这样（占位符请自行替换）：

FROM <带 CUDA 的官方基础镜像:标签>

# 第一段：系统依赖。几个月才动一次，放最上面
RUN apt-get update && apt-get install -y --no-install-recommends \
      <系统包列表> \
    && rm -rf /var/lib/apt/lists/*

# 第二段：Python 依赖清单单独复制。只要清单没变，下一层的缓存就有效
COPY <依赖清单文件> /tmp/
RUN pip install --no-cache-dir -r /tmp/<依赖清单文件>

# 第三段：环境变量与运行时配置
ENV <环境变量名>=<取值>
WORKDIR <容器内工作目录>

# 第四段：项目代码不进镜像，靠挂载卷提供
CMD ["/bin/bash"]

三处值得注意：

  • apt 的清理与安装写在同一条 RUN 里。分成两条时，第一条产生的缓存文件已经固化进那一层，第二条的删除只是在上层把它标记为不可见，镜像体积并不会变小。
  • 依赖清单单独复制，而不是把整个项目复制进来再安装。整个项目复制进来时，改任意一行代码都会让这一层失效，下面的依赖安装全部重跑。
  • 项目代码不进镜像。代码走挂载卷，镜像只负责依赖。这样改代码不需要重建镜像，镜像也能在多个分支之间复用。

常用命令速查

下面这张表只列日常最高频的几条。所有需要填写的位置都用尖括号占位符表示，实际使用时替换成自己的名称与路径。

命令 作用 常配合的选项
docker run 从镜像创建并启动一个新容器 -it 交互终端，-d 后台运行，--name 指定容器名
docker exec 在已运行的容器里再开一个进程 -it 进入一个新的交互 shell
docker ps 列出容器 -a 连同已停止的一起列出
docker logs 查看容器主进程的输出 -f 持续跟随，--tail 只看末尾若干行
docker commit 把容器当前状态固化成新镜像 应急手段，正式做法是改 Dockerfile 重建
docker save 把镜像导出成 tar 文件 用于无网络环境下搬运镜像
docker load 从 tar 文件导入镜像 与 save 配对使用
docker cp 在宿主机与容器之间复制文件 应急用，常态化的文件交换应当走挂载卷
docker images 列出本地镜像 定期清理无用镜像，单个镜像常在若干 GB 量级
docker stop 停止运行中的容器 停止不等于删除，容器仍在
docker rm 删除容器 删容器不影响挂载卷上的数据

一条典型的启动命令大致是这个形状（占位符请自行替换）：

docker run -it -d \
  --name <容器名> \
  --gpus all \
  --network host \
  --shm-size=16g \
  -v <宿主机代码目录>:<容器内代码目录> \
  -v <宿主机数据目录>:<容器内数据目录> \
  <镜像名:标签> \
  /bin/bash
  • exec 与 run 的区别务必分清：run 是新建容器，exec 是进入已有容器。反复用 run 会攒出一堆同源容器。
  • 容器退出后不会自动删除，除非显式加了自动清理选项；定期用 ps -a 检查残留。
  • 给容器起名时用项目加用途的组合，不要沿用默认的随机名，否则时间一长无法分辨容器与实验的对应关系。
  • docker cp 看起来方便，但它绕过了挂载卷，复制进去的文件落在可写层上，容器一删就没。只在临时排查时用。
  • docker logs 只能看到主进程的输出。用 exec 另开 shell 跑起来的训练进程，其输出不会进日志，需要显式重定向到挂载卷上的文件，否则终端一断输出不会留下。
  • docker commit 出来的镜像没有构建记录，无法回答「里面到底装了什么」。它适合的场景只有一个：环境已经调通但当时没记录步骤，先固化下来避免丢失，随后补写 Dockerfile 重建并验证。
  • docker save 导出的是镜像的全部层，体积等同于镜像本身，几 GB 到几十 GB 是常态。跨机器搬运前先确认目标磁盘空间与传输时间。

容器与宿主机的资源关系

上面那条命令里的每一个参数，本质上都在决定「容器能看到宿主机的哪一部分」。

flowchart LR
  HOST["宿主机：内核、NVIDIA 驱动、物理磁盘、网卡、物理内存"]
  HOST --> MNT["挂载卷：把宿主机目录直接映射进容器命名空间"]
  HOST --> GPU["GPU 直通：设备节点与驱动用户态库注入容器"]
  HOST --> NET["网络：host 模式共享网络命名空间，bridge 模式独立命名空间加端口映射"]
  HOST --> SHM["共享内存：容器内的 /dev/shm，容量由启动参数决定"]
  MNT --> CTR["容器内的进程"]
  GPU --> CTR
  NET --> CTR
  SHM --> CTR
  CTR --> FS["容器文件系统：只读镜像层加自己的可写层"]
  FS --> GONE["可写层的内容随容器删除一起消失"]
  MNT --> KEEP["挂载卷的内容独立于容器存在"]

图里要抓住的关键对比在右侧：容器自己的文件系统是易失的，挂载卷是持久的。所有需要保留的东西——代码、数据集、权重、日志——都必须落在挂载卷上，落在别处等于随时会丢。

启动参数逐项拆解

下表按「作用 / 典型取值 / 不这样配会出什么具体错误」三列排列。第三列尽量写成可以直接搜索的现象与报错文本，因为容器相关的故障有一个共同特点：报错信息几乎从不指向真正的原因，缺共享内存报的是总线错误，缺图形能力报的是显示设备找不到，按字面搜索只会搜到不相关的答案。

参数 作用 典型取值 不这样配会出什么具体错误
--name 给容器一个稳定的可读标识 「项目 + 用途」的组合，训练与推理各一个；同名容器在一台机器上唯一，删除后名字才能复用 不指定时由守护进程分配随机名，脚本无法稳定引用，exec 前必须先查表；多个同源容器并存时容易操作到错误的那个
-it 与 -d 分配伪终端并保持标准输入；让容器在后台运行 长期驻留的开发容器两个都加，主进程给一个 shell；一次性任务用前台运行加 --rm 只给 -d 而主进程是 shell 时，shell 读到文件结束符立即退出，容器状态变成已退出且返回码为 0，用 ps 看不到、要用 ps -a 才发现；只给 -it 时终端一断容器随之停止
--gpus 把 GPU 设备节点与驱动用户态库注入容器 独占机器用 all；共用机器按索引传入指定的若干张卡 不给时容器内没有任何 GPU 设备节点，框架报找不到 CUDA 设备；更麻烦的是部分框架会静默回退到 CPU，训练照常进行但慢一到两个数量级，容易被误判成模型太大或数据管线太慢
NVIDIA_DRIVER_CAPABILITIES 声明容器需要驱动的哪些能力集 纯训练用默认值（计算与工具类）；容器内做仿真器渲染或离屏渲染时额外声明图形相关能力 缺图形能力时报无法创建渲染上下文、找不到可用的显示设备，或某个图形库初始化失败；这些报错里不含任何与 GPU 权限有关的字样，常被误判成缺少图形库或缺少显示服务
--shm-size 设定容器内 /dev/shm 的容量 训练任务给到若干 GB 量级，随 worker 数、批大小与单样本体积增长；只能在创建容器时指定 默认仅 64 MB。DataLoader 的多 worker 把张量存储放进 /dev/shm 里的匿名文件再传给主进程，在途批次数约等于 worker 数乘预取深度，很快超过 64 MB，随后报总线错误或 worker 被信号杀死
--ipc=host 与宿主机共享 IPC 命名空间，容器内的 /dev/shm 直接是宿主机那一份 需要与宿主机进程做共享内存通信时使用；纯训练容器改用 --shm-size 与 --shm-size 同时给出时后者不再生效，容量由宿主机决定；反过来，通信对端在宿主机而没有共享 IPC 时，两侧的共享内存段互不可见，表现为握手超时或读到空数据
--network 选择网络命名空间的模式 需要与机器人本体、相机或其他节点通信的容器用 host；纯训练容器保持默认 bridge bridge 下 UDP 组播默认不跨容器，ROS 2 节点互相发现不到，现象是进程都正常但话题列表为空；host 下两个容器用同一默认端口时，后启动者报地址已被占用，或连到前一个实例上
-v 代码卷 把宿主机上的代码目录映射进容器 只挂项目根目录一层；容器内路径写死，宿主机侧路径参数化 不挂时代码写在可写层，容器一删即失；宿主机侧目录写错或不存在时会被自动创建成 root 属主的空目录，现象是容器内该目录为空而没有任何报错
-v 数据卷与只读挂载 映射数据集、权重、日志所在的大容量目录，并按需追加只读标志 数据集卷对训练容器挂只读；权重与日志卷可写，与代码卷分开 写只读卷报只读文件系统；不加只读时训练脚本可能覆盖原始数据。挂载在容器启动时解析，宿主机上删除并重建同名目录后容器内仍指向旧的目录对象，现象是宿主机有新文件而容器内看不到
--user 指定容器内进程的用户与组 传入与宿主机当前用户一致的 uid 与 gid 默认以 root 运行，写到挂载卷上的文件在宿主机看属主是 root，后续在宿主机上改删要提权；团队共用机器时会互相干扰
--privileged 解除大部分设备与内核能力限制，容器内进程近似拥有宿主机 root 权限 默认不加。需要串口、CAN、USB 等硬件时优先用设备传入选项逐个传节点，仅在节点热插拔或需改内核参数时开启 不加而直接访问宿主机设备节点时报权限不足或找不到设备；开启后容器可以挂载宿主机块设备、修改内核参数，隔离基本失效，一次误操作即波及宿主机
--restart 声明容器退出后的重启策略 长期驻留的服务型容器用「除非手动停止否则重启」；一次性实验保持默认的不重启 不设置时宿主机或守护进程重启后容器不会恢复，需要人工介入；一次性实验设成总是重启，失败任务会被反复拉起，新一轮输出把有价值的报错顶掉
--rm 容器退出后自动删除 一次性的测试与调试命令加上；长期开发容器不要加 不加时残留容器不断累积，占用磁盘并让 ps -a 的输出无法阅读；加在开发容器上则一次退出就丢掉容器内的全部临时状态

表里有三行值得连起来读：--gpus、NVIDIA_DRIVER_CAPABILITIES 与 --privileged 都在回答「容器能碰宿主机的什么」，但粒度依次放宽——前两者是按设备与能力精确授予，最后一个是整体解除限制。工程上的次序应当是：先尝试精确传入需要的设备节点，不够再补能力集，只有在设备节点会热插拔或必须修改内核参数时才动 --privileged。

数据挂载：代码卷与数据卷分开

挂载（bind mount）用 -v <宿主机路径>:<容器内路径> 指定，把宿主机的目录直接暴露给容器。这是容器化工作流里最关键的一条设计决策。

  • 代码必须放挂载卷。这样可以在宿主机上用熟悉的编辑器改代码，容器里立刻生效，不必重新构建镜像，也不怕容器被删。
  • 大文件放另一个卷。数据集、模型权重、训练日志、录制的轨迹数据，单独挂一个卷。理由有三：它们和代码的生命周期不同；它们通常在另一块大容量盘上；它们不应该进版本管理。
  • 两个卷分开还有个好处：代码卷可以做成只读或频繁同步，数据卷可以在多个容器之间共享，互不干扰。
  • 注意文件属主。容器内进程默认以 root 身份运行，写到挂载卷上的文件在宿主机看属主也是 root，后续在宿主机上删改会碰到权限问题。可以在启动时指定用户 id，或在容器内建一个与宿主机同 uid 的用户。
  • 不要把整个家目录挂进去。挂载范围越大，容器内进程能改动的宿主机文件越多，一次误删或误写的影响面也越大。只挂需要的两三个目录。

卷与容器生命周期解耦的意义

把「卷独立于容器存在」这件事讲透，能解释很多工程习惯的由来。

  • 容器变成可丢弃的。依赖装错了、环境搞脏了，直接删掉重建，代价只有几秒钟，因为所有有价值的状态都不在容器里。反过来，如果状态在容器里，人就不敢删容器，于是容器越用越脏，最终回到「裸机装环境」的老问题。
  • 镜像升级不影响数据。框架版本要升级时，改 Dockerfile 重建镜像，用新镜像起一个新容器挂上同样的卷，数据一行没动。旧容器可以留着做对照，随时切回去。
  • 同一份数据服务多个容器。数据集卷可以同时挂给训练容器与数据检查容器，甚至挂给另一个项目的容器做只读复用，不必复制多份。
  • 备份的边界清晰。需要备份的就是那几个卷，容器本身不需要备份。这条在制定备份策略时能省掉大量讨论。
  • 代价是路径约定必须写下来。容器内路径由启动命令决定，换一台机器如果映射到不同的容器内路径，脚本里的相对引用就会断。实践上的做法是固定容器内路径，只让宿主机侧路径变化。

一份可复用的挂载约定

把约定固定下来，换机器时只需要改启动脚本的左半边，右半边与所有代码都不动。

  • 容器内路径写死，宿主机路径参数化。启动脚本里宿主机侧的路径来自一个变量或配置文件，容器内侧永远是同一个固定路径。这样代码里可以放心地引用容器内的绝对路径。
  • 代码卷只挂项目根目录，粒度再细会导致某些文件在容器里看不到，再粗则把无关目录暴露进去。
  • 数据卷按用途再分子目录：数据集、模型权重、训练输出各一个子目录，而不是全部堆在一起。清理与备份时可以按子目录处理，误删的影响面小。
  • 输出目录必须在挂载卷上，且在启动前就存在。由容器进程创建的目录属主是容器内的用户，宿主机上可能改不动。
  • 只读挂载能用就用。数据集卷对训练容器挂成只读，可以杜绝训练脚本意外写入或删除原始数据这一类事故。

GPU 直通

容器默认看不到显卡。要让容器用上 GPU，宿主机需要装好 NVIDIA 驱动与容器运行时支持，然后在启动时把设备传进去。

  • --gpus all 把宿主机所有 GPU 交给容器；也可以只传其中若干张，做多项目的显卡分配。
  • 驱动装在宿主机，CUDA 运行时库装在镜像里。这是容器化 GPU 方案的基本分工：镜像不需要也不应该装驱动。
  • 因此镜像里的 CUDA 版本不能高于宿主机驱动所能支持的上限，这是选基础镜像时的首要约束。
  • 进容器后先确认 GPU 可见，再确认框架真的认出了 GPU——这是两件事，前者通过后者仍可能失败（通常是 CUDA 版本与框架不匹配）。

--gpus 与 NVIDIA_DRIVER_CAPABILITIES 各自控制什么

这两者经常被一起复制粘贴，但管的是完全不同的两件事，混淆之后排查方向会整个走偏。

  • --gpus 控制「哪些设备可见」，是数量与身份问题。它决定容器里能看到几张卡、是哪几张。不设置时容器里没有任何 GPU 设备节点，框架初始化 CUDA 会直接失败，或者静默回退到 CPU——后者更危险，因为训练照常跑，只是慢几十倍，很容易被误判成「模型太大」。
  • NVIDIA_DRIVER_CAPABILITIES 控制「能用驱动的哪些能力」，是功能子集问题。计算与工具类能力管的是 CUDA 计算与查询工具；图形相关的能力管的是 OpenGL、EGL、Vulkan 这些渲染接口。
  • 默认的能力集只包含计算与工具类，不包含图形。只做训练时够用；一旦要在容器里跑仿真器的可视化界面或做离屏渲染，缺了图形能力就会失败。
  • 缺图形能力的典型报错指向性很差：提示无法创建渲染上下文、找不到可用的显示设备，或者是某个图形库的初始化失败。这些信息里没有一个字提到 GPU 权限，因此常被误判成缺少图形库、缺少显示服务或驱动装错。判断依据是：计算任务正常但渲染任务失败，基本就是能力集的问题。
  • 排查顺序建议固定成三步：先确认设备可见，再确认框架认出了 GPU，最后确认渲染相关的能力集是否声明。三步各自对应不同的修法，混在一起试会浪费大量时间。

多卡机器上的分配

一台多卡机器同时跑几个项目时，显卡分配是常态而不是例外。

  • 按卡分容器，而不是按容器分卡。启动时就用 --gpus 指定这个容器可以用哪几张，容器内的框架看到的就只有这几张，编号从 0 重新开始。这比在代码里用环境变量限制可见设备更可靠，因为后者依赖每份代码都正确读取它。
  • 容器内的卡号与宿主机的卡号不一致。容器里看到的 0 号卡可能是宿主机的第 2 张。写日志与排查时要意识到这一点，不要拿两边的编号直接对照。
  • 显存没有硬隔离。同一张卡分给两个容器时，两边都能看到全部显存并按需申请，先申请的一方占住，后申请的一方直接申请失败。需要严格隔离时只能整卡独占。
  • 驱动升级要重启容器。宿主机驱动升级后，已运行的容器里注入的驱动库版本与新内核模块不匹配，表现为突然找不到设备。重建容器即可恢复。

网络模式

网络模式决定容器是否拥有独立的网络命名空间，这个选择在具身智能项目里出现频率极高。

选项 作用 好处 代价
默认 bridge 网络 容器有独立网络命名空间 隔离性好，端口需显式映射 组播与自动发现容易不通
--network host 容器直接使用宿主机网络栈 端口无需映射，组播可用 隔离性丧失，端口易冲突
--network none 完全没有网络 最强隔离 无法下载依赖与通信

关于 --network host：

  • ROS 2 的默认通信中间件依赖 UDP 组播做节点自动发现，跨容器与跨主机时经常在桥接网络下发现不到彼此，使用宿主网络可以绕开这一层网络配置。
  • 需要访问机器人本体、相机或其他设备的网络接口时，宿主网络模式也省掉一层映射。
  • 代价是容器不再有网络隔离：容器里监听的端口就是宿主机上的端口，两个项目同时起来会撞端口；也意味着容器内的服务对同网段是直接可见的，安全边界变弱。
  • 端口冲突的表现往往不是明确的报错。同一个可视化工具或调试服务在两个容器里都用默认端口时，后启动的一方要么报地址已被占用，要么连到了前一个容器的实例上——后者更难发现，因为界面能打开，只是数据对不上。
  • ROS 2 场景下还有一层额外的干扰：宿主网络模式下所有容器共享同一个网络，同一个域 id 的节点会互相发现。两个人在同一台机器上跑两套仿真时，话题会串在一起。解决办法是给不同实验分配不同的域 id，而不是退回桥接模式。
  • 折中做法是只对确实需要设备通信的容器用宿主网络，纯训练容器仍用默认桥接。桥接模式下需要暴露的服务用端口映射显式声明，映射关系写在启动脚本里，冲突在启动时就会暴露而不是运行时才发现。

共享内存

--shm-size 设置的是容器内 /dev/shm 的容量。它与网络模式经常被写在同一条启动命令里，但作用完全无关，不理解的话很容易在换环境时漏掉。

  • 容器默认的共享内存空间很小（通常只有 64 MB）。PyTorch 的 DataLoader 在多 worker 模式下用共享内存在进程间传张量，很容易耗尽。
  • 具体机制是：每个 worker 进程在自己的地址空间里把样本组装成张量，张量的存储被放进 /dev/shm 下的一个匿名文件，主进程按文件描述符或文件名把同一块内存映射进来，从而避免序列化与复制的开销。同时在途的批次数量约等于 worker 数乘以预取深度，全部占用共享内存。worker 开到十几个、每个样本又是几张高分辨率图像时，几百 MB 是常态，64 MB 远远不够。
  • 关键在于这块空间是按容器分配的固定上限，而不是从宿主机内存里按需借用：宿主机还有几十 GB 空闲内存，也不影响容器内 /dev/shm 在写到 64 MB 时就写不下去。这解释了为什么「宿主机内存充足」不能作为排除共享内存问题的理由。
  • 典型症状是训练刚开始几十步就报「bus error」或 worker 进程意外退出，错误信息不会直接说共享内存不够，很容易误判成数据集损坏。另一种常见误判是怀疑内存泄漏，因为现象同样是运行一段时间后进程退出。
  • 判断依据很直接：把 worker 数量降到 0 之后如果不再崩溃，几乎可以确定是共享内存不足而不是数据问题。
  • 训练任务建议在启动时把它调到若干 GB 量级；具体数值取决于 worker 数量、batch 大小与单样本的体积（图像与点云数据尤其占空间）。它占的是宿主机物理内存，设得过大会挤压其他进程，按需给足即可。
  • 这个值只能在创建容器时指定，已运行的容器改不了，要改只能重建容器——所以启动命令里一开始就带上它。

--ipc=host 与 --shm-size 的关系

这两个参数经常被一起抄进启动命令，但它们是替代关系而不是叠加关系，同时写上去只会让其中一个失效。

  • --shm-size 的含义是：容器仍然拥有自己独立的 IPC 命名空间与自己的 /dev/shm，只是把这块空间的容量上限调大。隔离性保持不变，容量是个确定值。
  • --ipc=host 的含义是：容器不再有自己的 IPC 命名空间，直接使用宿主机的那一套，容器内的 /dev/shm 就是宿主机的 /dev/shm。容量由宿主机决定，此时 --shm-size 不再起作用。
  • 判断依据很直接：进容器后查看 /dev/shm 的容量，若它等于宿主机的容量而不是启动命令里写的值，说明 IPC 命名空间是共享的，--shm-size 已被忽略。
  • 两者的取舍：容器内的多进程数据加载只需要 --shm-size，它容量可控且不破坏隔离；只有当共享内存的另一端在宿主机上（例如与宿主机侧的相机采集进程或某些中间件做零拷贝传输）时，才需要 --ipc=host，因为不同 IPC 命名空间里的共享内存段互相不可见。
  • 共享 IPC 命名空间的代价与共享网络命名空间类似：命名空间内的共享内存段对所有参与方可见，名字冲突与残留段会跨容器互相影响，容器异常退出后残留的段也不会随容器一起清理。
