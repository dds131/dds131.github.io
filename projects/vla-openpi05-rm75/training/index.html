模型训练与三次对照实验

pi05_rm75_rawact_3cam 配置逐项解读、delta 动作与分位数归一化、第三个图像槽此前是死的这一缺陷的定位与修复、batch 24 与 256 的对照实验，以及 loss 低不等于效果好的反复证伪

← 项目主页 ·数据集与数据质量 ·模型训练 ·真机部署 ·动作块平滑 ·效果与失败分析

本项目一共做过三次成规模的后训练：0814、0825、0828。三次用的是同一个基座（pi05_base）与同一套任务；0825 与 0828 用的几乎是同一份数据，0814 的数据只有它们的一半左右。差别集中在 batch、训练步数与 decay_steps 上，真机成功率却分别是 64%、约 10%、92%。

本页讲三件事：训练配置的每一项是怎么定的、这三次训练到底差在哪里、以及一路被实测证伪的几个直觉。π0.5 的模型原理见知识点 · openpi 0.5，本页不重复。

一、训练配置

配置名 pi05_rm75_rawact_3cam，定义在自包含目录 my_custom_code_files/ 下的独立模块里，通过 get_rm75_configs() 注册进 openpi 的 _CONFIGS。

1.1 模型本体

项 取值 说明
pi05 True 走 π0.5 分支而不是 π0
action_dim 32 模型内部动作维度
action_horizon 50 一次输出 50 步动作块
discrete_state_input True 状态以离散 token 形式进入前缀
paligemma_variant gemma_2b 视觉语言主干
action_expert_variant gemma_300m 动作专家
dtype bfloat16 训练精度
参数量 3,353,433,872 51 个浮点张量拼接后的总长度
初始权重 pi05_base gs://openpi-assets/checkpoints/pi05_base/params
优化器 AdamW(b2=0.95, wd=1e-10) 梯度裁剪阈值 1.0

三点需要说明。action_horizon = 50 在 30 fps 下等于 1.667 秒，部署时块内是开环执行的，所以动作块后段的预测质量直接决定闭环成败，这一点在第三、四节会反复出现。action_dim = 32 是模型内部维度而不是机器人自由度：真机的 8 维动作（7 关节加 1 夹爪）进入模型前被补零到 32 维，输出侧再切回前 8 维；这是 openpi 为跨构型复用留的接口，本项目未做跨构型验证。freeze_filter 未设置，因此全部参数可训练——这是全参后训练，不是 LoRA，也不是只训动作专家，第六节的权重漂移实测正是建立在这个前提上。

还有两个术语在表里只有名字，这里补上定义。动作专家是挂在视觉语言主干之后的一个较小分支 （gemma_300m）：主干负责理解画面与语言指令，动作专家负责把这份理解变成 50 步关节增量。 第六节 D 条把它单列一列做权重漂移统计，正是因为它是整个模型里离动作最近、也最需要被本任务改造的部分。 离散状态输入（discrete_state_input = True）指的是 8 维的机器人状态先被离散成 token， 再与语言 token 一起放进视觉语言主干的前缀序列，而不是以连续向量的形式旁路接入； 代价是模型对本体状态的感知精度受量化粒度限制。具体的分桶方式沿用 openpi 上游实现， 本项目未改动、也未测量它带来的量化误差。 两者的方法层面说明见 知识点 · openpi 0.5。

1.2 对上游源码的改动只有几行

训练配置、输入变换、输出变换全部写在 my_custom_code_files/ 下的独立模块里，上游的 src/openpi/training/config.py 只增加两处：一行 import，以及组装 _CONFIGS 时的一行 splat 展开。

这样做的理由是把改动面压到最小。 上游 openpi 会持续更新，改动一旦分散进上游源码，每次同步都要重新合并。把全部新增内容放进一个自包含目录，完全回退就等于删除该目录加撤销那一行 splat，不需要逐文件比对。同一套原则在数据侧也用过一次，形式是「包装加运行时替换」，见数据集与数据质量一页。

LerobotRm75DataConfig 这个类定义在 get_rm75_configs() 函数内部而不是模块顶层。原因是它要继承上游 config.py 里的 DataConfigFactory，而 config.py 又要 import 本模块的 get_rm75_configs，在模块顶层 import 会形成循环。放进函数体内则是延迟求值：该函数只在 config.py 组装 _CONFIGS 时才被调用，此时那些基类均已定义完毕。

1.3 delta 动作：七关节做增量，夹爪保持绝对

delta_mask = make_bool_mask(7, -1)
           = (True, True, True, True, True, True, True, False)

前七位为 True 的关节走 DeltaActions，即减去当前 state；第八位为 False 的夹爪保持绝对值，训练与推理成对互逆（输出侧对应 AbsoluteActions）。

夹爪为什么不能做 delta：它是离散档位，取值只有 {0, 0.5, 1} 三个。一旦做差分，取值集合会从 3 个膨胀到差分对的组合数，而且每个差值都不再对应任何一个物理档位，「张开到底」这类语义会彻底消失。归一化统计能反证这一点：action 第八维的 q01 = 0.0000 为非负，若做过增量，0 − 0.53 = −0.53 这类值必然出现，q01 不可能为零。

DeltaActions 是沿 50 步 horizon 轴广播相减的。 实现里 state 被 expand_dims 到 horizon 轴之前，因此 delta[k] = action[t+k] − state[t]，k 取 0 到 49。也就是说归一化统计里 action 的分位数区间衡量的是50 步（1.667 秒）内的累计位移，而不是单帧差分。J6 的 q01 到 q99 是 −91.2 度到 +80.4 度，量级几十度而非几度，正是这个原因。

1.4 分位数归一化

π0.5 会自动启用分位数归一化（use_quantile_norm 由 model_type != PI0 置 True），不需要在配置里写：

z = (x − q01) / (q99 − q01 + 1e-6) × 2 − 1

即把 1% 到 99% 分位区间映射到 [−1, 1]，尾部允许超出。用分位数而不是均值与标准差，是因为它对离群值稳健：遥操作数据里少数快速运动会产生长尾。

关键数值（口径：0814 三相机数据集的 norm_stats，采样 100,000 帧） 值 含义
state J3 的 mean / std −82.34 度 / 19.65 度 state 仍是绝对角度，未被误做 delta
state J6 的 q99 − q01 179.9 度 所有维度里区间最宽的一维
state 夹爪的 q01 / q99 −0.0207 / 0.5316 连续实测开口的实际量程
action 七关节的 |mean|/std 0.003–0.113 delta 确实生效
action 夹爪的 q01 0.0000 非负，证明夹爪是绝对量

J6 区间最宽这一条解释了一个长期观察到的现象：无论哪个检查点，J6 的预测误差始终是七个关节里最大的。归一化把最宽的一维压进同样的 [−1, 1]，等价于在这一维上放大了误差的物理量纲。健全性核验的结论是数据侧不存在数值隐患：非有限值 0 个、退化维（q99 == q01，会导致除零）0 个、归一化后 |z| 最大 2.57、|z| > 10 的占比 0.0000%。

1.5 一个判据陷阱

判断 delta 是否真的生效，不能看「mean 接近 0」。50 步位移的均值本来就没有必须为零的道理，它取决于任务里手臂伸出与收回是否对称。正确的判据是 |mean| / std 远小于 1：实测七个关节是 0.003 到 0.113，说明位移在正负方向上大体抵消；若没做 delta，这个比值会是关节绝对角的量级，约 4。

这条判据是在一次误判之后才总结出来的：早期一次比对误用了原始的绝对动作做参照，得到 90% 以上的假「偏差」，一度以为归一化统计算错了。判据本身选错时，实测数据越多只会让错误结论更难被推翻。

二、三路相机怎么接进模型

第三个图像槽的修复前后对照。π0.5 的图像槽位固定为三个；两相机版把第三槽当成占位，填 arm_camera 的副本并置 image_mask=False，虚线表示该路对模型输出零影响。修复后第三槽换成真实的 third_camera 并置 True，三路画面都真正参与计算。

2.1 缺陷是什么、为什么长期没被发现

两相机版需要填满三个图像槽，做法是把 arm_camera 复制一份放进 right_wrist_0_rgb，并把它的 image_mask 置为 False。在 π0.5 下这个后果是彻底的：embed_prefix 与 make_attn_mask 会把该槽从注意力的 query 与 key 两侧同时排除，位置编码的 cumsum 也跳过它。它既看不到别人，也不被别人看到，反向传播时该路梯度恒为 0。

结论是 third_camera 的真实画面此前从未进入过模型。 数据侧已经忠实解码并落盘了第三路，转换器的帧数校验也通过，但训练侧在第一层就把它丢掉了。

它长期没被发现的原因恰恰是它的影响为零。 一个对输出零贡献的输入，不会让 loss 变差、不会让梯度范数异常、不会触发任何守门判据，训练日志与 loss 曲线上都看不出丝毫痕迹。能暴露它的只有两种手段：读 embed_prefix 的实现，或者做消融。

2.2 修复方式与验证

修复方式是新写一个 RuiermanInputs3Cam，而不是改两相机版的 RuiermanInputs。两相机版已经跑通过多批数据、产出过 0.9 度的权重，逐字未动；两个配置在 get_rm75_configs() 里并存，各自用独立的数据集环境变量与独立的归一化统计目录，互不影响。回退三相机版就是删掉新文件加改回 return 列表。槽位映射固定为三条：

base_0_rgb        ←  head_camera    （全局视角）
left_wrist_0_rgb  ←  arm_camera     （腕部视角）
right_wrist_0_rgb ←  third_camera   （第三视角）

三个键都做了别名容错：训练时进来的是 LeRobot 的列名（head_camera 等），推理时部署端可能直接给 openpi 的键名（base_0_rgb 等），输入变换按别名元组逐个尝试取第一个命中的；全部落空则抛异常并列出现有键名，而不是静默补零——静默补零正是上一版缺陷的成因。

验证靠消融而不是靠读代码。 在 0828 权重 step 40000 上把第三路置黑后重新评测（52 个样本），动作误差放大到 5.48 倍，这从反面证明它确实进了模型并且承担了相当大的权重。各路相机之间的消融排序见真机部署一页——注意那张表是三相机改造刚完成时在 0814 权重上测的，绝对倍率与这里的 5.48 不可直接比较。

2.3 完整数据流

parquet 列  observation.images.head_camera / arm_camera / third_camera
            observation.state (8,)   action (8,)
   ▼ RepackTransform       列名 → data["images"] / ["state"] / ["actions"] / ["prompt"]
   ▼ RuiermanInputs3Cam    三路映射到三个图像槽，image_mask 全 True
   ▼ DeltaActions(mask)    前 7 维沿 horizon 轴减去 state[t]，第 8 维不动
   ▼ Normalize             (x−q01)/(q99−q01+1e-6)×2−1   ← 在 model_transforms 之前
   ▼ ResizeImages          统一到 224×224
   ▼ TokenizePrompt        语言指令转 token（state 的离散化也在这一步）
   ▼ PadStatesAndActions   8 维补零到 action_dim=32
   ▼ Pi0(pi05=True)

反向：Pi0 输出 (50,32) ▼ Unnormalize（同一份 norm_stats 还原量纲）
                       ▼ AbsoluteActions（前 7 维加回 state[t]，还原绝对关节角）
                       ▼ RuiermanOutputs（切回前 8 维）→ (50,8) 送往真机
正向的 DeltaActions 与反向的 AbsoluteActions 用的是同一个 mask 对象，正向的 Normalize 与反向的 Unnormalize 用的是同一份 norm_stats（归一化统计在训练时被写进检查点的 assets/，推理时从检查点内读取）。这保证了换数据集重算统计不会影响已有权重的推理。

loss 一栏的口径。表中给的是日志里最后一个记录点的原始值。 同一批日志另有一套指数滑动平均值，两者不可混用——例如 0814 的原始末点是 0.0021， 其滑动平均是 0.0012。下文比较 loss 时会标明用的是哪一种。

3.3 梯度范数

0825　batch 24，step 40,000 附近平滑值 0.0377
0828　batch 256，同一步附近平滑值 0.0129

一个 batch 的梯度是 B 个样本梯度的平均，其噪声部分的标准差按 1/√B 缩放。当训练接近收敛、真实梯度信号已经很小时，观测到的梯度范数主要就是噪声，因此应当满足 grad_norm(B₂)/grad_norm(B₁) ≈ √(B₁/B₂)。代入本项目的两次训练：

实测比  grad_norm(0828) / grad_norm(0825) = 0.0129 / 0.0377 = 0.342
理论值  sqrt(24 / 256)                                      = 0.306

两组比值都落在理论值同侧、量级一致（另一组 0828 对 0814 的实测比是 0.392，对理论 0.306 偏高约 28%）。这与batch = 24 时梯度以采样噪声为主是一致的。

3.4 机理

小 batch 的破坏不在于「学得少」，而在于学到的映射本身带抖动。AdamW 的更新量是 Δθ = −lr · m / (√v + ε)，分母的归一化会把更新幅度拉回到约 lr 的量级，不管一阶矩 m 里装的是信号还是噪声。大 batch 时 m 主要是信号，每一步朝正确方向走满 lr；小 batch 时 m 主要是噪声，每一步仍然走满 lr，但方向基本是随机的。这解释了一个看似矛盾的实测：0814（batch 24）的参数范数涨得比 0828（batch 256）还多（+9.90 对 +8.65（均为 step 40,000 处的 param_norm，kernel 口径）），参数动得更多，效果却更差。

离线单帧误差看不出这个问题，因为它衡量的是单步预测，而每一帧的抖动都很小。但部署时块内是开环的，模型在块内不重新观测，越靠后的步条件分布方差越大、越难估准；执行到设定的触发点时机器人已经偏出去了，下一次推理是在一个「已经偏掉」的状态上做的，逐块叠加就是任务失败。

结论：后续训练不再使用 batch 24。

3.5 归因必须严谨

0828 相对 0814 同时变了两件事：batch 从 24 提到 256，数据集从 733 条扩到 1,393 条。只看这两次，无法把成功率的提升单独归因于 batch——数据规模是一个共变量。

0825 恰好构成需要的对照。 它的数据集规模与 0828 几乎相同（1,407 对 1,393，只差被剔除的 14 条「严重反复」，总帧数差 1.0%），数据来自同一批采集；而它的 batch 仍是 24，真机成功率只有约 10%。也就是说：0814 与 0828 之间两个变量共变、不能定论，而 0825 与 0828 之间数据几乎不变，主要差别是 batch 从 24 变成 256，同时 decay_steps 由 50,000 回到 100,000（见下方注），成功率就从约 10% 变成 92%。因此 batch 是最可能的主因，数据规模不是。 数据从 733 条扩到 1,407 条这一步（0814 到 0825）真机成功率反而从 64% 掉到约 10%，也从另一侧证明了「加数据本身不会自动变好」。

0825 为什么反而更差：小 batch 与更大的数据集叠加，把有效 epoch 数压到不足。 batch 保持 24 意味着每一步只消化 24 个样本，而数据集从 733 条翻到 1,407 条之后， 跑完一个 epoch 需要的步数也从 19,701 步涨到 36,157 步；这一轮的总步数却只有 50,000（另两次是 100,000）。三者相乘的结果是：在同一个 step 40,000 上， 0814 已经过了 2.03 个 epoch，0828 过了 11.92 个， 而 0825 只有 1.11 个——数据集里绝大多数轨迹，模型只见过一遍。

更麻烦的是这一批数据的风格更杂（新增了失败恢复等更多样的操作方式）， 需要的遍数本来就比风格单一的数据更多，而它拿到的遍数反而是三次里最少的。 所以「batch 太小」在这一轮是通过两条路径同时起作用的： 一是梯度被采样噪声主导（3.4 节的机理），二是每步消化的样本太少、 在扩大后的数据集上凑不出足够的 epoch。两条都指向同一个可调项。

但必须如实说明一个未被单独控制的变量。 0825 的 decay_steps 是 50,000，而 0814 与 0828 都是 100,000。这导致三者在 step 40,000 处的学习率并不相同：0825 只有 4.82e-6，另两次都是 1.764e-5。0825 在这一点上已经退火到接近尾声，累计更新预算（∫lr dt，0 到 40,000）只有 0814 的 74%。0814 与 0828 的最佳点都落在余弦进度 38.8% 处，这个巧合暗示「学习率日程位置」可能比「epoch 位置」更能决定最佳点，但只有 2 个数据点，不足以定论。要验证它需要一次专门的对照实验：同数据集、同 batch，只改 decay_steps。这次实验尚未做。

五、算力与成本

5.1 FSDP 是 JAX 原生分片，不是 PyTorch FSDP2

openpi 的 fsdp 与 PyTorch 生态里的 FSDP2 包没有任何关系。实现只用了 jax.sharding.Mesh 加 NamedSharding，网格上只有两个轴：BATCH_AXIS 与 FSDP_AXIS。命令行的 --fsdp-devices 只设定分片轴的大小，其余卡数自动落到 batch 轴上。由此得到两个实际约束：不存在第三方 fsdp2 依赖，所以没有版本不匹配或装不全的问题；分片数必须整除模型维度，实际可选的只有 2、4、8 三档。0814 与 0825 用 4，0828 用 8（实测 8 比 4 快 2% 到 5%）。

5.2 显存为什么几乎不随 batch 增长

按材料中约 2.6B 可训练参数的近似口径（1.1 节那个 3,353,433,872 是 51 个张量拼接后的精确长度，两者是不同口径），训练态需要同时持有三份东西：

参数（fp32）                    10.4 GB
AdamW 的一阶矩 mu 与二阶矩 nu    20.8 GB
梯度                            10.4 GB
────────────────────────────────────────
合计                            41.6 GB

4 路 FSDP 分片后，每卡只承担约 10.4 GB，80 GB 卡上剩下的 60 GB 以上全部是激活值余量；而激活值又按 batch 轴分到各卡，每卡只担 1/4。所以在很宽的范围内，增大 batch 只是在消耗那部分本来就闲置的余量，显存曲线几乎是平的。实测把 batch 从 24 一路加到 224（每卡 56）仍然正常，是原配置的 9.3 倍。

这也解释了一个反直觉的现象：单卡跑 batch 8 反而会 OOM，还差 29 GB。 单卡时参数不分片，那 41.6 GB 全压在一张卡上，加上激活值就超了。「减少卡数可降低复杂度」在这里不成立。

5.3 单步耗时的成本模型

用差分法测两个档位的稳态单步耗时（去掉启动与编译开销），解出线性模型：

t_step = 1.267 s + 0.02847 s × batch

batch = 24   →  1.95 s/步   吞吐 12.3 样本/秒
batch = 96   →  4.00 s/步   吞吐 24.0 样本/秒

方法的可靠性有一个独立校验：batch 24 测得 1.950 s/步，与正式训练 100,000 步平均的 2.1 s/步只差 7%，差值来自每 5,000 步的检查点保存开销。

那笔固定的 1.267 秒最可能来自 FSDP 的参数 all-gather（未做 profiling 验证）。 参数按 4 路分片，每步的前向与反向都必须先聚合出完整参数，通信量只取决于模型大小，与 batch 完全无关。在 batch 24 下，这笔固定成本占单步耗时的 65%——约三分之二的单步时间用于参数聚合通信，而非梯度计算。

以上全部是 4 卡 fsdp4 口径（用 batch 24 与 96 做差分测得），由此得到该配置下吞吐的硬上限 35.1 样本/秒（等于 1 / 0.02847），固定通信开销永远摊不掉。0828 换成 8 卡 fsdp8 后这条外推不再适用：按它外推 batch 256 应是 8.56 秒每步，实跑是 5.68 秒每步。把 batch 提高的边际收益因此衰减得很快：在同样跑完 5.08 个 epoch 的口径下，batch 从 24 提到 96，总时间从 54.2 小时降到 27.8 小时，省 49%；再从 96 提到 192 只再省 16%（27.8 小时降到 23.4 小时）而更新次数减半；从 192 提到 224 只再省 3%，没有意义。选 256 是在这条曲线的平坦段上取的值，取值依据是梯度信噪比，而非吞吐。

六、训练过程中的问题与归因

A · 28 度失效权重：根因是相机文件夹装反

现象。 用新增数据重训后，step 20,000 检查点的关节平均误差约 28 度、夹爪准确率约 50%——那一轮夹爪还是二值指令（三状态是 2026-08-13 才引入的），50% 即随机水平；step 5,000 的检查点更糟，采样直接发散。

排查。 逐项取证排除：训练日志健康（loss 从 0.065 降到 0.006、零次非有限跳过、参数范数持续上升）；归一化统计新旧逐维差小于 2 度，且 compute_norm_stats 在采样时 shuffle=True 覆盖全集；非有限守门从未触发；与官方 openpi 逐文件比对，compute_loss / sample_actions / embed_prefix 逐字节一致，训练与推理共用同一前向、归一化与 delta 成对互逆。训练与推理代码无致错缺陷。

根因在数据。 那次训练新增的 157 条数据里，head 与 arm 的相机文件夹装反了。转换器按文件夹名做死映射、按文件夹名原样存下了错误的映射，导致 24% 的样本图像与动作相矛盾；flow 模型学不出这种自相矛盾的条件映射，采样塌到噪声尺度，于是输出 28 度量级的无效动作。

修法在数据侧，转换器代码未改（相对基线 tag 逐字节零差异）。留下的规矩：模型输出接近随机水平时，先查数据与标注的对应关系，再查代码；代码逐字节一致这条证据的价值在于它一次性排除了代码这一半的排查范围。

B · loss 变成 inf 的三次定案

这条是本项目最有价值的一次排查，因为它被定案过两次又被推翻一次。

① 先查清失效机制。 optax.clip_by_global_norm(1.0) 遇到含 inf 的梯度时会走 g / ‖g‖ × max_norm 这条分支：‖g‖ 本身是 inf，于是有限元素被除成 0，inf 元素变成 inf / inf = nan。nan 一旦进入 AdamW 的一阶矩与二阶矩，参数就被永久污染，此后无论数据是否正常都不可能恢复。离线自检实测：{a:[1,2], b:[inf,3]} 经裁剪后变成 {a:[0,0], b:[nan,0]}。

由此得到一个重要推论：因为裁剪存在，任何有限梯度都不可能破坏训练。 梯度再大也会被裁到范数 1.0。这一条直接排除了「某条数据导致梯度爆炸」这个假设，后续排查不必再往数据方向找。

② 据此加固 scripts/train.py。 相对上游共四处独立改动、每处都带 【回退】 注释。非有限守门：判据是 isfinite(loss) & isfinite(global_norm(grads))，非有限则把梯度整体置零；判据必须同时看 loss 与梯度范数（只判 loss 无法拦截「loss 有限但梯度含 inf」），且范数必须在梯度置零之前计算，否则永远是 0。两个监控字段：param_norm_all（全部参数的范数，补上原有 param_norm 排除 bias / scale / embedding 的盲区）与 nonfinite_skip（本步是否被跳过），纯观测不参与计算。启动自检：进训练循环前校验全部参数有限，非有限即非零退出——实测出现过 step 0 就 param_norm=inf，而此时学习率 1.25e-8、更新量约 1e-18 倍参数，参数不可能被训练本身改坏，说明损坏发生在加载阶段。看门狗：连续 10 个日志点 nonfinite_skip > 0 就等检查点写完再 SystemExit，把「静默运行 40 小时后存出未训练的权重」变成「数分钟内报错退出」，实战中在 step 90（约 3 分钟）触发过一次。对正常训练零影响：全部有限时置零操作 where(True, g, 0) 恒等于 g，训练数学与上游逐位一致，代价只是每步多一次范数规约。

③ 曾定案为「残留孤儿进程干扰跨卡通信」。 证据看起来相当硬：同一条命令、同一批 GPU、同一份数据，只差有没有清理上一轮训练残留的进程——清理前 param_norm = inf，清理后 param_norm = 1802.3864，而梯度范数与 loss 逐位相同（1.0044 与 0.0591）。前向反向一直是对的，坏的只是参数更新时的跨卡通信。

④ 后被推翻。 完全相同的配置，只差一次容器重启：

阶段 重启前（容器已连续运行 8.5 天） 重启后
step 0 到 6 健康，loss 0.0670 到 0.0784 健康
step 7 loss = inf，此后永不恢复 正常
step 39 — loss 0.0491
退出码 rc=1（看门狗 FATAL） rc=0 跑完

三次启动前均已确认容器内 python 进程为 0，并逐个扫过 /proc/*/fd 确认无进程持有 nvidia 设备句柄，故障照常复现——第 ③ 条的结论不成立。

真根因是容器长时间连续运行累积的进程与驱动级状态损坏，修复方式是重启容器。 它与此前的几处矛盾现象不冲突（换任何卡组都失败、清编译缓存无效），但这几条并未被逐一重新验证——它们原本是上一版「残留孤儿进程」假说的解释，而该假说已被推翻。

⑤ 留下的判据与工具。 param_norm 冻结是区分「真在训练」与「看着在跑」的关键指标：loss 曲线在故障时可能仍然打印数值，但参数范数不动就说明什么都没学。6 分钟快速判定法：用正式训练的全部环境变量，只改 --num-train-steps 40 --log-interval 1 加一个临时检查点目录，若出现「前几步健康 → 突变 inf → 永不恢复 + param_norm 冻结」，就是这个故障。num_workers=0 能规避但不是修复：它只绕开 spawn 子进程路径，速度从 2.0 秒每步劣化到 9.5 秒每步，10 万步要跑 11 天，不可采用。另外 nonfinite_skip = 0.5000 不等于「奇偶交替」，那是崩溃点恰好落在 10 步日志窗口中间造成的假象，判断真实模式必须用 --log-interval 1 看逐步原始值。

0828 的非有限跳过比例：7,562 个日志点全部为 0，一条贴底的直线。
全部参数的范数：4789.23 持续上升到 4793.26，证明参数确实在被更新。

C · decay_steps 必须与 num_train_steps 对齐

optax 的余弦调度在超过 decay_steps 之后会恒定在 decay_lr，而不是继续衰减或报错。三相机版把 num_train_steps 从 40,000 提到 100,000 时，如果忘了把 decay_steps 一并改成 100,000，那么 4 万步之后学习率会一直卡在 2.5e-6，后 6 万步等于用极小学习率空跑，既浪费算力又不会有任何报错。这一条已经写进配置文件的注释里。

D · 三个被证伪的直觉

1）「epoch 甜区在 1.52 到 2.54 之间」。 这个假设基于 0814 与 0825 的三个观测提出：窗口内的检查点真机好，窗口外的差。0828 把它证伪了——它在 step 40,000 处的 epoch 是 11.92，是所谓上界的 4.7 倍，效果却是三次里最好的。该假设在当时的观测下成立，是因为 0814 与 0825 的 batch 都是 24，epoch 与其它变量共变：在固定 batch 下，epoch 数只是「数据量与步数之比」的代理量，一旦 batch 变了这个代理关系就断了。真正起作用的是「看过多少样本 × 每次更新的信噪比」。

2）「loss 低就是效果好」。 这条被反复证伪，至少三次：

检查点 loss（平滑值） 真机
0828 / 40000 0.00125 最好，92%
0828 / 68000 0.00067（更低） 更差
0814 / 40000 0.0033 64%
0825 / 49999 0.0024（更低） 约 10%

原因有两层，其中第一层是机理推断、本项目没有直接实测证据。第一，flow-matching loss 是 MSE 型的，而「多个有效模态取平均」恰好就是最小化 MSE 的解——模态平均会降低 loss 数值，同时让动作变得不可用（两条都可行的绕行路径取平均，得到的是一条穿过障碍物的无效路径）。第二，loss 是在所有 horizon step 上取平均的，靠前的步误差小且主导数值，而闭环成败偏偏取决于后段。0828 训练的末端 loss 是 0.0006，比 step 40,000 的 0.00125 低一半，真机却更差。

3）「偏离初始权重太远导致效果差」。 这条需要真正的距离而不是范数：param_norm 测的是 ‖θ‖，两个权重向量可以范数完全相同却相距很远。因此另写了一个测量脚本，把每个检查点与 pi05_base 逐张量、逐元素相减再累加平方和，51 个浮点张量全部匹配、全覆盖、无采样，‖θ₀‖ = 4789.23：

0814 / 40000 3.6477%（最远） 5.0045% 3.2801% 9.2772% 64%

假设被推翻，而且方向恰好相反：真机最差的 0825 偏离得最少，三者之间没有任何单调关系。结合第三节看，0825 的问题是「偏离得不够」，即欠训练。分模块的三列有一个稳定的模式：动作专家被改动最多，约为语言塔的 3 倍，视觉塔居中——这符合预期，后训练主要是在教模型这个机器人的动作分布，语言理解能力基本沿用预训练。

这条测量另有一个独立的交叉验证：脚本算出的 ‖θ₀‖ = 4789.2324 与三次训练日志 step 0 的 param_norm_all 完全一致。四个独立来源给出同一个数，说明脚本的拼接顺序与 optax 一致，且三次训练确实都从同一份 pi05_base 出发。但要注意结论只在跨训练轮次比较时成立：在同一次训练内部，距离随步数单调增长，0828 从 40000 走到 75000 相对距离从 3.35% 涨到 3.72%，真机确实变差了——「走得太远」能解释「同一次训练里为什么不是越练越好」，但解释不了 0825 为什么比 0814 差。

E · 方法论上的教训

  • 双峰分布不能用中位数概括。 曾把 30.001 Hz 的实际帧率误判成 27.44 Hz。中位数与均值相差数倍时，本身就是强烈的偏斜信号（夹爪半开档也出现过同类误判，见数据集与数据质量第六节）。
  • 单帧图像不能当证据。 靠目视检查一两帧判断「相机装对了没有」「误差大不大」，在本项目里失效过多次；需要的是全量统计或逐像素比对。
  • 跨轮比较必须固定评测集。 曾因两轮评测用了不同的采集 session，得出「主导相机翻转」这样的假结论。第四节的交叉评测正是为此才新写了一个脚本，把「读哪份归一化统计」与「用哪份数据评测」拆成两个独立参数。
  • pgrep -f 与 pkill -f 会匹配到自己所在的 shell 命令行，本项目因此误终止过三次进程。判定容器是否干净要用 ps -eo pid,args 看完整列表，杀进程按 PID 而不是按模式匹配。

七、方法论上最大的欠账

所有离线评测都在训练集上做，三次训练都没有留验证集。 最硬的一条证据是：0814/40000 与 0825/40000 在同一份离线评测集上的误差几乎完全相同（1.4455 度对 1.4620 度，差 1.1%），而真机成功率是 64% 对约 10%。（这份评测集与第四节那份不是同一个：第四节用 0828 数据集的 180 个样本，同一对权重是 3.145 度对 1.542 度。两组数字口径不同，不可互换。）

现有的离线评测体系对真机成功率几乎没有预测力。 它能做的只有三件事：验证推理链路是否通、看误差随 horizon 的增长形状、看夹爪的半开档是否学到了。它不能用来选部署检查点。

第四节的逐步误差与真机排序对上了，但那只有 3 个训练轮次的样本，且比的是同一份数据上的逐步误差而不是 loss，口径与前两次相反的记录不同，不足以推翻上面这条结论。

待办已经明确：下次训练必须留出 5% 到 10% 的 episode 作验证集。 划分要按 episode 而不是按帧，否则同一条轨迹的相邻帧会同时落进训练集与验证集，验证误差会被严重低估。

另需如实注明：92% / 64% / 约 10% 这三个数字来自真机实测，每轮 100 次连续取放试验（验收方法见效果与失败分析第 1.4 节），但每次的成败序列没有逐条留档。 它们足以支撑「差异巨大」这个定性判断与第三节的归因，但不足以给出置信区间。真机验收的方法与失败模式见效果与失败分析一页。
