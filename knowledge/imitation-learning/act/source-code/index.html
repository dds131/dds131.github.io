本页与前面五个子页的组织方式不同，需要先说清楚。

前面各页按知识点组织：先讲一个概念，再引用与之相关的源码片段。好处是概念清楚，代价是源码被拆散在六个页面里，读完仍然不知道「这个仓库该从哪个文件看起」。

本页按文件与调用链组织，提供的是一张读码地图：仓库里有哪些文件、各自管什么、谁调用谁、一次训练与一次推理分别经过哪些函数。凡是前面讲过的机制，本页只给指针，不重复讲解。

版本基准：本页的文件数量、字节数、硬编码位置与调用关系，均以 ACT 官方仓库 commit 742c753c0d4a5d87076c8f69e5628c79a8cc5488 为准。源码链接使用该 commit 的固定地址；若阅读其他版本，应重新核对差异。
18 个本页覆盖的 Python 文件（仓库共 20 个）
约 140 KB全部 Python 代码体量
4 个核心文件，占理解成本的八成
3 条需要理清的调用链
5 层模型构建的调用深度
1 路 / 4 路仿真与真机的相机数差异
本页最需要记住的三条：这个仓库不是从零写的，detr/ 下大部分文件来自 Facebook 的 DETR，分清哪些改过很重要；模型构建有 5 层调用，从 make_policy 一路到 detr_vae.py 的 build；仿真只用 1 路相机，子页 ④ 的维度推算是按真机 4 路做的，两套口径不能混。

二、哪些沿用或改写自 DETR，哪些是 ACT 仓库特有

官方 README 明确说 ACT 的模型定义是「modified from DETR」。分清改动边界，读码时才知道哪些地方可以直接套用 DETR 的理解、哪些地方必须重新看。

2.1 三类归属

归属 文件 读法
ACT 仓库特有，上游 DETR 无同路径对应 imitate_episodes.py、policy.py、utils.py、constants.py、sim_env.py、ee_sim_env.py、scripted_policy.py、record_sim_episodes.py、visualize_episodes.py 按 ACT 的数据与控制语义阅读，不能直接套用 DETR
由 DETR 改写，结构相似但语义有变 detr/models/detr_vae.py（对应 DETR 的 detr.py）、detr/models/transformer.py、detr/main.py 最需要小心，见 2.2
基本沿用 DETR detr/models/backbone.py、detr/models/position_encoding.py、detr/util/* 可按 DETR 的理解读，注意 ACT 只用到其中一部分

2.2 改写文件里最容易踩的坑

中间那一类最危险，因为代码看起来像 DETR，但行为已经变了。子页 ④ 记录过一个具体例子：

项 原版 DETR ACT
Transformer.forward 的返回 二元组 单个张量
调用处 self.transformer(...)[0] self.transformer(...)[0]
[0] 的含义 解包元组 索引层维度

调用写法一字未改，语义却完全不同。 详细的事实链与自查方法见子页 ④ 第十节，本页不重复。

由此可以总结出读这类改写代码的通用方法：

先看函数签名有没有变参数增减、返回类型改变，是语义漂移最常见的来源。ACT 给 Transformer.forward 加了 latent_input、proprio_input、additional_pos_embed 三个参数，并改了返回类型。
凡遇裸索引就回头确认类型[0]、[-1] 这类写法在原项目里可能索引的是元组，在改写后可能变成索引张量维度。
以逐函数差异为准文件名是否变化不能可靠反映改动规模。detr_vae.py 与 transformer.py 都应对照上游 DETR 检查函数签名、返回形状、掩码与调用处，不能只按文件名判断。

2.3 ACT 没有沿用 DETR 的哪些机制

子页 ④ 第 2.3 节已列出完整清单（二分图匹配与集合级损失、类别与框回归头、无物体类别、各层辅助损失），本页只补一条代码层面的印证：detr/util/box_ops.py 与 detr/util/plot_utils.py 这两个纯检测相关的文件在已核验范围内无任何引用。

把这条与子页 ④ 的结论合起来看：ACT 继承并改造了 DETR 的架构（encoder-decoder 加 query 并行解码），但没有采用 DETR 的二分图匹配、类别预测与边界框损失。仓库只残留了 box_ops.py 等部分检测工具，完整的匹配与检测损失流程并不在 ACT 训练路径中。静态 import 关系可以帮助缩小核查范围，但必须结合函数实现与运行调用链，不能单独作为机制存在与否的证明。

三、按目的选择阅读顺序

不存在一个万能的阅读顺序，因为读码的目的不同。下面给四条路径，按目的选。

3.1 路径 A：只想搞懂算法（最短，约 9 KB）

1. policy.py（3.3 KB）全文只有两个类，一眼能看完。训练分支与推理分支的差异、L1 与 KL 怎么组合，全在这里。它是理解 ACT 的最佳起点——最短，却把「模型」「损失」「训练推理差异」三件事同时摆出来了。
2. detr_vae.py 的 DETRVAE.forward（约 5 KB）只读 forward，不看 build。重点是 if is_training 的两个分支：训练分支怎么从动作块得到 latent，推理分支怎么用零向量代替。
3. imitate_episodes.py 的 eval_bc 中 temporal_agg 那一段（约 1 KB）二维缓冲区的行写列取，见子页 ⑤。

读完这三处，ACT 的四层设计就都见过实现了。跳过：所有仿真文件、detr/util/、transformer.py 的内部实现。

def forward_pass(data, policy):
    image_data, qpos_data, action_data, is_pad = data
    image_data, qpos_data, action_data, is_pad = image_data.cuda(), qpos_data.cuda(), action_data.cuda(), is_pad.cuda()
    return policy(qpos_data, image_data, action_data, is_pad)

注意它始终传入 action_data。因此验证时也走训练分支、也使用 CVAE encoder——这就是子页 ⑥ 第 9.2 节所说「验证损失与真机推理不是同一口径」的代码依据。

5.3 三个不能从流程图中忽略的实现风险

调用链能说明“谁调用谁”，但下面三处会影响正确性或框架兼容性，需要单独核对：

位置 当前实现 风险与正确理解
时间集成有效性判断 torch.all(actions_for_curr_step != 0, axis=1) 零张量同时被当作“尚未写入”的哨兵；若合法动作任一维恰好为零，整条候选预测会被丢弃。更稳妥的实现是单独维护布尔有效性掩码。
DETRVAE.is_pad_head 模型计算并返回 is_pad_hat，但 ACTPolicy 的损失没有使用它 该头没有对应监督，不能解释为模型已经学会预测动作块结束位置；训练屏蔽依赖数据集提供的 is_pad。
ACTPolicy.__call__ 策略类覆盖 nn.Module.__call__，而不是实现 forward 普通前向与反向仍可运行，但会绕过 nn.Module.__call__ 的标准调度路径，影响模块级 forward hooks 等工具。重构时应把计算逻辑移入 forward()。
此外，评估代码中的 qpos_history 被写入但未参与后续决策；EpisodicDataset 读取 qvel 却不把它返回给策略。这些属于维护性线索：前者可在重构时清理，后者意味着数据文件目前仍必须提供 qvel 键。

七、仿真数据是怎么生成的

这部分前面五个子页完全没有涉及，但它解释了仿真任务的示范数据从哪来，也解释了为什么仓库里会有两个仿真环境文件。

7.1 两阶段设计

record_sim_episodes.py 的 docstring 把流程写得很清楚：

Generate demonstration data in simulation.
First rollout the policy (defined in ee space) in ee_sim_env. Obtain the joint trajectory.
Replace the gripper joint positions with the commanded joint position.
Replay this joint trajectory (as action sequence) in sim_env, and record all observations.
Save this episode of data, and continue to next episode of data collection.

拆成四步：

① 在末端空间跑脚本策略用 ee_sim_env，动作是末端位姿。脚本策略（PickAndTransferPolicy、InsertionPolicy）在这个空间里很容易写——直接指定「手要移动到哪个位姿」，不必解逆运动学。跑完得到一条关节轨迹。
② 夹爪关节改用指令值源码把轨迹里的夹爪实测位置替换为控制指令。这样记录的动作标签与关节空间环境接收的目标量一致；“减小执行滞后对标签的影响”是基于控制语义的解释，不是源码注释直接给出的实验结论。
③ 在关节空间回放并记录切到 sim_env，把上一步的关节轨迹当作动作序列逐步执行，同时记录每一步的观测（图像、qpos、qvel）与动作。
④ 存成 hdf5一个 episode 一个文件。

7.2 为什么官方实现采用两阶段生成

训练动作标签需要与部署时策略输出的量保持相同语义。官方 ACT 输出目标关节位置，而末端空间脚本策略更容易按任务轨迹编写，因此仓库采用“EE 空间生成 → 关节空间回放记录”的工程方案。它不是 ACT 的数学要求：直接编写关节空间专家、显式做逆运动学或使用遥操作示范，也可以得到兼容的关节动作标签。

两个环境之间靠 BOX_POSE 这个全局变量对齐物体初始位姿：

env = make_sim_env(task_name)
BOX_POSE[0] = subtask_info   # make sure the sim_env has the same object configurations as ee_sim_env

若不对齐，回放时物体位置与生成时不同，记录下的图像就与动作对不上了。

flowchart LR
  SP["scripted_policy.py<br/>末端空间脚本策略"] --> EE["ee_sim_env.py<br/>末端空间环境"]
  EE --> TRAJ["得到关节轨迹"]
  TRAJ --> FIX["夹爪关节改用指令值"]
  FIX --> SIM["sim_env.py<br/>关节空间环境"]
  BOX["BOX_POSE 对齐物体初始位姿"] --> SIM
  SIM --> REC["逐步回放并记录观测"]
  REC --> H5["episode_i.hdf5"]

7.3 hdf5 的结构

data_dict = {
    '/observations/qpos': [],
    '/observations/qvel': [],
    '/action': [],
}
for cam_name in camera_names:
    data_dict[f'/observations/images/{cam_name}'] = []

这些键只是兼容条件的一部分。自采数据不必沿用仿真生成流程，但需要同时满足下面的数据契约：

约束 当前加载器的要求
文件命名 连续命名为 episode_0.hdf5 到 episode_{N-1}.hdf5；num_episodes 必须与实际文件一致
根属性 必须提供 root.attrs['sim']，它决定动作序列从 start_ts 还是 max(0, start_ts-1) 开始
必需数据 /observations/qpos、/observations/qvel、/action 和配置中每个相机对应的图像键都必须存在；qvel 虽未送入策略，当前代码仍会读取
形状与长度 qpos、qvel、action 与图像的时间轴要对齐；当前 get_norm_stats 用 torch.stack，因此各 episode 的 qpos/action 形状必须一致
图像 相机键与 camera_names 完全一致，布局为 T × H × W × C，像素数值需符合随后除以 255 的处理
控制语义 qpos/action 的关节顺序、单位、夹爪编码和时间对齐必须与部署接口一致；形状相同不代表语义相同
任务配置 episode_len、相机列表、状态维度、动作维度和控制频率应与数据及部署系统一致

因此，真正的兼容条件是键、形状、时间、数值范围、控制语义与配置共同一致，而不只是“存在同名 HDF5 键”。

另注意一处时间对齐处理：

# because the replaying, there will be eps_len + 1 actions and eps_len + 2 timesteps
# truncate here to be consistent
joint_traj = joint_traj[:-1]
episode_replay = episode_replay[:-1]

回放机制会多出一个动作和两个 timestep，因此这里通过截尾统一序列长度。真机分支的 max(0, start_ts - 1) 则是数据加载阶段的动作—观测对齐补偿。两者都与时序一致性有关，但前者解决回放计数差，后者补偿真机采集对齐，不能假定具有相同的物理来源。

对只关心真机算法语义的读者，这四个仿真文件可以暂缓阅读。真机示范由遥操作采集，论文把 leader 机器人关节位置记录为动作，策略学习输出 follower 的目标关节位置，因此不需要复现“EE 脚本策略转关节轨迹”的仿真步骤。但当前入口仍有前述 sim_env.py 顶层导入，运行依赖与概念依赖需要分开判断。

8.2 由相机数差异导出的维度差异

子页 ④ 第 5.1 节按真机 4 路推算过视觉 token 数。换成仿真的 1 路，整条链按比例缩小：

量 仿真（1 路） 真机（4 路）
单路 layer4 输出 \(512 \times 15 \times 20\) \(512 \times 15 \times 20\)
沿宽度维拼接后 \(512 \times 15 \times 20\)（无拼接） \(512 \times 15 \times 80\)
视觉 token 数 300 1200
主视觉 Transformer encoder 序列长度（含 latent 与 proprio） 302 1202

由于分辨率相同，视觉 token 数随相机数从 300 增至 1200。主视觉 Transformer encoder 的自注意力分数矩阵二次项比例为：

\[\left(\frac{1202}{302}\right)^2 \approx 15.84.\]

这个 15.84 倍只描述自注意力分数矩阵的理论计算量与权重矩阵规模，不能代表完整 ACT 前向耗时，因为：

  • Q/K/V 投影和 FFN 的主要项随序列长度近似线性增长；
  • decoder cross-attention 约按 \(O(HN)\) 增长；
  • 视觉主干需要分别处理各路图像，其计算量近似随相机数线性增长。

因此，四路真机输入确实显著增加算力与显存需求，但“整个模型比仿真慢 16 倍”不是由上述公式能够推出的结论。

8.3 chunk 相对 episode 的占比差异

这一条影响的是子页 ⑥ 讲过的 padding 掩码等效权重。设随机起点在长度为 \(T\) 的 episode 中均匀采样，且 \(T \ge H\)。

仿真分支从 start_ts 开始取动作，因此：

\[P_{\mathrm{sim}}(m<H)=\frac{H-1}{T},\] \[\mathbb{E}_{\mathrm{sim}}\!\left[\frac{m}{H}\right]=1-\frac{H-1}{2T}.\]

真机分支从 max(0, start_ts-1) 开始，首部多保留一步，因而：

\[P_{\mathrm{real}}(m<H)=\frac{H-2}{T},\] \[\mathbb{E}_{\mathrm{real}}\!\left[\frac{m}{H}\right]=1-\frac{(H-2)(H-1)}{2TH}.\]
配置 \(H / T\) 受 padding 影响的样本占比 平均等效权重
仿真 \(T=400\)，\(H=100\) 25% 24.8% 0.876
真机 \(T=600\)，\(H=90\) 15% 14.67% 0.92748
真机 \(T=1000\)，\(H=90\) 9% 8.80% 0.95649

仿真 \(T=400,H=100\) 时，受 padding 影响的起点占 24.75%，平均等效权重为 0.87625。真机两行必须使用 start_ts-1 分支的公式；若误用仿真公式，会分别得到约 14.83%/0.92583 与 8.90%/0.95550，口径会发生偏差。

一条实践提醒：官方仿真结果不足以直接证明真机配置有效。 相机数、episode 长度、动作来源和 chunk 占比都会改变输入分布与训练信号。仿真可以验证代码路径、张量形状和基本优化行为，也能提供定性调参线索；迁移到真机后仍需按真实数据分布、控制频率和安全约束重新验证。

十、要改 ACT，该动哪里

10.1 状态维度与动作维度：必须分开参数化

官方 ALOHA 配置中 qpos 与 action 恰好都是 14 维，源码因此用同一个 state_dim 概念覆盖两者。迁移到一般机器人时应显式区分 \(D_q=\dim(qpos)\) 与 \(D_a=\dim(action)\)；二者可能不同。

位置 当前写法 正确参数归属
imitate_episodes.py state_dim = 14，并用于时间集成缓冲区 action_dim
detr_vae.build() state_dim = 14 # TODO hardcode action_dim
DETRVAE.action_head nn.Linear(hidden_dim, state_dim) 输出 action_dim
input_proj_robot_state（两个分支各一处） nn.Linear(14, hidden_dim) 输入 qpos_dim
encoder_action_proj nn.Linear(14, hidden_dim) 输入 action_dim
encoder_joint_proj nn.Linear(14, hidden_dim) 输入 qpos_dim
CNNMLP.mlp_in_dim 768 * len(backbones) + 14 加上 qpos_dim
CNNMLP.mlp 输出 output_dim=14 输出 action_dim

只改 build() 里的 state_dim 不够：输入投影和评估缓冲区仍可能保持 14 维。若张量最后一维不同，通常会立即报矩阵乘法或赋值形状错误；真正的“静默错误”主要发生在维度仍为 14、但关节顺序、单位或夹爪含义已经改变时。

可靠改法是让配置显式携带 qpos_dim 与 action_dim，分别贯穿数据校验、归一化统计、模型输入投影、动作头、时间集成缓冲区和部署后处理，而不是把所有硬编码机械替换成同一个变量。

10.4 一个建议的改造顺序

第一步：定义接口契约先确定 qpos_dim、action_dim、关节顺序、单位、夹爪编码、控制频率、相机键和动作—观测对齐。不要为了“先跑通”而把非 14 维动作任意补零或截断。
第二步：完成维度参数化按 10.1 让 qpos 与 action 分别贯穿模型和评估缓冲区，再用小规模合成数据检查数据读取、前向、loss、反向和 checkpoint 恢复。若保留 CNNMLP 基线，也要覆盖其输入/输出硬编码。
第三步：接入真实数据按 7.3 的数据契约检查每个 episode，重新生成归一化统计量，并先验证小数据过拟合与离线动作误差，再进入完整训练或受控部署。
第四步：最后调超参kl_weight 应根据新任务上实测的 L1/KL 相对尺度重新标定；L1 对动作维度取均值，动作维度增加本身不会使它按维度数线性放大。chunk_size 则应结合控制频率、动作时间尺度和推理延迟确定。

十一、算法创新、架构继承与工程实现的边界

读源码时需要区分“论文方法贡献”和“这份仓库恰好采用的实现方式”，否则容易把工程细节误写成 ACT 的创新点。

类别 内容 正确理解
ACT 核心方法 动作分块、CVAE 风格变量、时间集成 分别对应降低有效决策时域、建模示范中的动作风格，以及在推理期融合对同一时刻的重叠预测
继承并改造的架构 ResNet、2D 位置编码、DETR-style encoder-decoder、query 并行解码 这些提供视觉表征与并行序列解码骨架，不是 ACT 从零提出的结构
当前仓库的实现选择 多相机共享主干、推理令 \(z=0\)、L1 加 KL、固定层数与超参 是理解和复现该版本所必需的事实，但不能自动推广为所有 ACT 实现都必须遵循的定义
仿真数据工程 EE 脚本策略、关节轨迹回放、HDF5 录制 用于生成与部署动作空间一致的仿真示范，不属于 ACT 模型创新
工程耦合与遗留 二次解析命令行、14 维硬编码、未监督的 is_pad_head、零值哨兵 是迁移和维护风险，不应包装成算法设计优势
判断“创新点”的依据应优先来自论文的问题定义、方法章节与消融实验；源码负责确认这些思想在当前版本中如何落地。仅由某一处代码差异，不能推出作者动机或方法贡献。
