RTC 复现、参数与 VR 接管架构

OpenPI RTC + DAgger RM75 的复现步骤、参数语义、异步队列、五相位交接、单一下发链和验收方法

项目概览 RTC 复现与接管 纠正数据 数据与训练 安全与验证 工程迭代 论文与路线
REPRODUCTIONRTCVR → IK

先把时间轴、动作块和队列复现正确，再让 RTC 与 DAgger 共用一条安全下发链。

本页从可复现配置、延迟测量和离线检查开始，逐步接入异步队列、低速真机与 VR 接管；每个参数都说明单位、来源、约束和调错方向，避免把“打开 RTC 开关”误当成复现完成。

一、先分清四种“状态口径”

需求概览中的“六态机”、本页的“五相位”和 AUTONOMOUS / CORRECTING 并不互相矛盾，它们描述的是不同层。如果把它们混成一套枚举，读者会误以为页面少写了一个状态。

层次 本页采用的口径 负责什么 不应怎样理解
RTC 算法与队列层 异步产块、动作队列、pause / resume / reset 让新动作块与已承诺前缀连续，并管理在途推理与旧队列 不是 DAgger 接管状态机
DAgger 会话层 IDLE → AUTO → SOFT_STOP → HANDOFF → TELEOP 决定当前由 RTC、保持参考还是 VR 提供目标 五相位不是底层控制器全部状态
底层 RTC / 安全控制层 需求所称的既有六状态控制器；设计上保持原实现 处理运行、停止、故障、复位等硬件生命周期及安全约束 本页不重命名其内部状态
叙述层 AUTONOMOUS / CORRECTING 对“自主段 / 人工纠正段”的简写 不是新增的代码枚举
本页重点：按需求设计，DAgger 只在既有 RTC 与安全控制器之上增加“谁提供目标”的会话仲裁；底层六状态控制器和三道安全闸仍由原 RTC 路径负责。该结构仍需项目源码与运行证据确认。

二、四层职责与三个调度域

策略产块

RTC 在后台根据最新观测生成下一动作块，并利用尚未执行的前缀保持块间连续。推理耗时会变化，因此它是异步任务，不是固定频率“时钟”。

实时下发

约 110 Hz 的单一发送路径消费当前参考，执行插值、运动约束与夹爪门控。只有这一条路径拥有硬件写权限。

纠正采样

约 30 Hz 采样观测、实际下发命令和三路图像。控制热路径只复制或 append；编码与落盘延后到 episode 收尾。

会话编排

事件驱动的纯逻辑 FSM 把按键和运行状态转换为动作列表，再由 Runner 执行副作用。它不是第四个周期时钟。

三个调度域故意解耦：策略产块受推理延迟影响，下发必须保持稳定节拍，数据采样只需与训练集 fps 对齐。若把视频编码、磁盘写入或网络传输塞进 110 Hz 热路径，I/O 抖动会直接侵占约 $1/110\approx9.1\,\mathrm{ms}$ 的单周期预算。

最容易复现错的地方：110 Hz 是 RM75 安全下发链的伺服节拍，30 Hz 是策略动作块与数据记录的时间网格；RTC 的 inference_delay、动作块索引和 execution_horizon 使用 30 Hz 策略动作步。二者不能混算：约 183 ms 推理对应约 5.5 个策略步，而不是 20 个伺服周期。

当前真机运行锚点：推理、接块与发送周期

本轮对一份 speed_scale=1.0、chunk_exec_steps=25、exec_horizon=30、非 dry-run 的代表性记录进行了分段复算。只在连续 ACTIVE 段内计算相邻发送时间，避免把 episode 间停顿误算成周期长尾。

三、RTC 复现路线：从固定基线到受限真机

RTC 的复现对象不是一个布尔开关，而是“同一 checkpoint、同一观测预处理、同一动作表示、同一归一化统计、同一时间基准”上的队列与引导行为。建议按下列阶段门推进；前一阶段没有证据时，不进入后一阶段。

冻结复现身份

记录代码 commit、checkpoint 摘要、模型配置、归一化统计、任务文本、相机物理映射、动作单位、动作块长度 H、策略动作频率 f_a 与随机种子。只保存“权重目录名”不足以复现。

建立关闭 RTC 的基线

在相同观测与 checkpoint 下保存原始动作块、推理耗时和执行结果；同步阻塞基线用于确认策略本身可工作，异步但不做 RTC 引导的基线用于分离“不断流”和“块间连续”两种收益。

测量端到端推理延迟

从观测快照可用到新动作块可入队为止测量，而不只计 GPU forward；至少保存 P50、P95、P99、最大值以及每次对应的动作步数，分别标出预处理、排队、模型、后处理与传输。

离线复现 RTC 数值路径

固定一组观测、旧块和随机种子，对比无 RTC 与 guided RTC；检查 Hard/Soft/Free 三段 mask、VJP/引导修正为有限值、旧块与新块按同一物理时刻对齐，并确认动作 shape、dtype、device 与归一化一致。

只接队列，不驱动执行器

让控制循环消费动作、后台线程产块，验证触发阈值、实际延迟裁剪、队列替换、下溢、reset 与 generation 失效。故意制造慢推理和晚到结果，确认不会从新块索引 0 重放过期动作。

进入既有安全链的低速真机阶段

RTC 仍只产生候选动作；110 Hz 唯一下发线程负责插值、限位、限速/限加速度、夹爪门控与故障处理。先在无障碍、保守边界和可立即停止条件下扩大速度与工作空间。

接入 DAgger 会话仲裁

接管时暂停新 RTC 请求、使在途 generation 失效、清空旧队列并软停；人工纠正只记录安全链之后真正发送的命令。交还时用最新观测重新产块，不能恢复接管前队列。

锁定协议做配对评测

至少比较无 RTC/无平滑、仅异步、仅 RTC、RTC 加执行侧平滑；固定 checkpoint、初始条件与任务判据，以 trial 为统计单位报告成功率、时长、块边界 jerk、deadline miss、下溢和人工接管率。

推荐的最小证据包：versions.json（commit 与依赖）、policy_config、checkpoint 摘要、归一化统计、延迟 CSV、队列事件日志、离线 RTC 可视化、受限真机配置摘要和 A/B trial 表。网页不公开设备地址、凭据、端口或内部绝对路径。

四、参数逐项解释与本项目取值边界

先定义 RTC 使用的时间轴。设动作块含 $H$ 个策略动作，策略动作频率为 $f_a$，端到端推理时间为 $T_{\mathrm{infer}}$，则本轮延迟步数应按策略动作网格换算：

\[\widehat d=\left\lceil \widehat T_{\mathrm{infer}}f_a\right\rceil,\qquad d_{\mathrm{real}}=\left\lceil T_{\mathrm{infer}}f_a\right\rceil .\]

若新块返回时已过去 $d_{\mathrm{real}}$ 个策略动作，下一可用后缀为

\[A_{\mathrm{usable}}^{\mathrm{new}}=A^{\mathrm{new}}[d_{\mathrm{real}}:H].\]

$f_a$ 必须来自 checkpoint/数据配置与运行时动作语义，不能从 110 Hz 伺服插值频率或 30 Hz 记录频率猜测。例如仅在确认 $f_a=30\,\mathrm{Hz}$ 时，100 ms 推理才对应 $\lceil0.1\times30\rceil=3$ 个 RTC 步；若误乘 110，会错误冻结 11 步。

参数 本项目应怎样取 单位与作用 调大后的主要影响 必须记录/校验什么
mode 现有普通 Flow/VLA checkpoint 先用 guided；只有训练时显式做过前缀条件化才用 trained 模式枚举 不是连续可调参数 checkpoint 是否声明 trained 兼容；不能凭模型名称猜
H / chunk_size 从 checkpoint 配置读取，不在部署时单独臆改 策略动作步；完整预测长度 覆盖更久，但内存和陈旧风险增大 与训练时动作块长度一致
$f_a$ / policy action fps 从训练数据和运行配置锁定 Hz；RTC 索引时间基准 更高意味着相同秒级延迟占更多动作步 与动作时间戳、插值器输入一致
伺服下发频率 项目记录约 110 Hz Hz；安全链和插值输出节拍 更高只缩短伺服周期，不自动提高策略刷新率 实际周期 P50/P99、deadline miss；名义周期约 9.1 ms
纠正采样频率 项目记录约 30 Hz Hz；图像/state/action 记录节拍 数据更密但复制、内存与落盘压力更大 不把它默认成 $f_a$；检查时间戳与丢帧
inference_delay / $\widehat d$ 运行时根据端到端延迟预测；离线示例应把选定的保守延迟统计量按策略频率换算并向上取整 策略动作步；Hard Prefix 长度 过大更保守，过小会约束不足或重放过期语义 同时保存预测值与 $d_{\mathrm{real}}$，不能写死“4 步”后长期不测
execution_horizon / $K$ 官方 LeRobot 起步示例常用 10，文档给出 8–12 的典型起始区间；本项目最终值必须实测 策略动作步；旧块参与一致性约束的最大窗口 更平滑但更迟钝，且可能与 $H$ 冲突 明确所用 LeRobot/RTC commit；不同实现同名参数可能不是同一语义
max_guidance_weight 10 步 flow 采样的官方起步示例为 10.0；先离线验证，再做小范围扫描 无量纲；限制引导修正强度 连续性更强，但过大可能振荡、NaN 或压制新观测 记录 flow 步数、修正范数、有限值与任务反应性
prefix_attention_schedule 初次复现可用官方建议的 EXP，再与 LINEAR 对照 枚举；控制 Hard 后重叠区权重衰减 ONES 最强、ZEROS 退化为硬截断，不能简单按“更大”排序 保存每个位置的实际权重曲线
queue_threshold / $q_{\mathrm{thr}}$ 依据保守延迟步数、块长与模式约束设置，不从 execution_horizon 照抄 剩余动作步；qsize <= threshold 时启动下一次产块 越大越早推理并提供更多延迟余量，也可能让较旧动作保留更久；不会改变模型块长 触发时队深、请求/返回时刻、underflow；trained 模式需覆盖训练最大延迟
flow num_inference_steps 保持 checkpoint/基线使用的实际值；若改变则重新标定延迟和 guidance 去噪/流积分步数 通常质量提高但推理变慢 不把“10 步模型下 10.0 guidance”的经验外推到任意步数
debug / debug_maxlen 离线与短时联调用；真机长跑关闭或严格限长 布尔/条数；保存 mask、修正与中间轨迹 观测性更强，但增加显存/内存与 I/O 调试数据不能进入 110 Hz 热路径
三路图像 项目数据契约为 3 路、224×224、约 30 Hz 视觉观测 更多/更大图像增加预处理和延迟 物理相机身份、颜色顺序、时间戳、训练键映射
state / action 项目契约为 8 维 + 8 维，但第八维的测量与命令语义不同 7 关节 + 夹爪 不适用 状态夹爪开度、命令夹爪类别/值域、归一化与安全后记录

官方示例值的作用是建立第一条可检查的离线曲线，不是 RM75 的最终参数。对 guided 模式，最小结构约束是

\[0\le \widehat d\le K < H,\qquad d_{\mathrm{real}}<H.\]

trained 模式若训练时最大前缀延迟为 $d_{\mathrm{train,max}}$，固定 LeRobot 文档还要求

\[d_{\mathrm{train,max}}\le K\le H-d_{\mathrm{train,max}}, \qquad q_{\mathrm{thr}}\ge d_{\mathrm{train,max}}.\]

若 $d_{\mathrm{real}}\ge H$，新块已经整体过期，正确处理是拒绝该块并进入既定保守路径，而不是执行索引 0 或重复最后一个高层动作。若某固定版本把 execution_horizon 用作 Soft Prefix 权重终点，它也不等于“两次推理之间执行多少步”；复现记录必须同时保存 $H$、$K$、触发阈值、实际启动间隔和有效权重长度。

可审计的配置骨架

下例只表达字段关系，不包含设备、网络或可直接驱动机械臂的命令；尖括号字段必须从当前 checkpoint 与实测日志填写。

policy:
  checkpoint: <immutable-checkpoint-id>
  chunk_size: <H-from-checkpoint>
  action_fps: <f_a-from-training-and-runtime>
  flow_inference_steps: <keep-baseline-value>
rtc:
  enabled: true
  mode: guided
  execution_horizon: 10        # 仅作为官方起始参考，需满足 K < H
  max_guidance_weight: 10.0    # 与 flow 步数、数值稳定性一起复验
  prefix_attention_schedule: EXP
runtime:
  queue_threshold: <from-P99-latency-steps-plus-margin>
  servo_send_hz: 110           # 项目记录值；不是 RTC 动作 fps
  correction_record_hz: 30     # 项目记录值；不是 RTC 动作 fps
  reject_stale_generation: true
  reject_chunk_when_delay_ge_H: true

命令落地 A：先做官方离线 RTC 数值复现

下面命令来自 LeRobot 当前 RTC 官方示例和 examples/rtc/eval_dataset.py 配置定义，用数据集样本比较普通生成与 RTC 生成，不连接机器人。它是核对 RTC 数值路径的上游参考，不是本项目私有部署脚本，也不能替代锁定项目 commit 后的离线测试。

python examples/rtc/eval_dataset.py \
  --policy.path=<PINNED_CHECKPOINT> \
  --dataset.repo_id=<PINNED_REFERENCE_DATASET> \
  --rtc.mode=guided \
  --rtc.execution_horizon=10 \
  --rtc.max_guidance_weight=10.0 \
  --rtc.prefix_attention_schedule=EXP \
  --inference_delay=<MEASURED_DELAY_IN_POLICY_STEPS> \
  --device=cuda \
  --output_dir=<RTC_DEBUG_OUTPUT_DIR> \
  --seed=<FIXED_SEED>
命令项 值从哪里来 作用与可见效果 错配时会怎样
python examples/rtc/eval_dataset.py 锁定 LeRobot commit 后的官方离线入口 依次加载基线与 RTC 策略并输出调试图；不应触碰机器人 不同 commit 的入口和字段可能变化，不能只保存网页命令
--policy.path 与部署候选相同的不可变 checkpoint 同时决定权重及其策略配置；换值就不是同一组复现 checkpoint、config 或归一化统计不配套会使对比失效
--dataset.repo_id 与 checkpoint 特征契约兼容的固定数据集 提供观测、动作真值与统计；决定离线样本分布 相机键、动作维度或统计不匹配会在加载或预处理阶段失败
--rtc.mode=guided 普通 flow-matching checkpoint 的起始模式 在推理去噪期间施加一致性引导 未经 trained RTC 训练却改成 trained 应被拒绝，而不是静默回退
--rtc.execution_horizon=10 官方起始参考；最终值由 $H$、延迟和 A/B 决定 规定旧块参与一致性约束的最大策略动作步数 过小可能仍跳变；过大可能迟钝或违反块长约束
--rtc.max_guidance_weight=10.0 官方 10 步 flow 示例值 限制 guided 修正强度，增大通常更强调连续性 过大可能压制新观测、放大数值不稳定；不是速度比例
--rtc.prefix_attention_schedule=EXP 官方建议的起步衰减 决定 Hard Prefix 后各重叠位置的权重曲线 改为 LINEAR/ONES/ZEROS 会改变整个重叠区，而非只改一个常数
--inference_delay 端到端实测延迟按策略动作周期换算并向上取整 告诉离线例程有多少前缀已在推理期间被承诺 四舍五入、向下取整，或按 110 Hz 插值频率换算都会低估/错置前缀
--device=cuda 当前锁定环境的可用计算设备 决定模型在哪个设备推理；影响延迟与显存 它不选择具体机器人，也不构成安全限制
--output_dir 本轮独立、可追踪的输出目录 保存对比图和调试产物，便于把结果绑定到版本 复用旧目录可能混入上一轮证据
--seed 预先固定并写入 run manifest 控制可控随机源，便于同配置重复比较 同 seed 也不能抵消非确定性算子或输入差异

--inference_delay 接收的是整数策略动作步，不是毫秒。若本轮采用的端到端推理延迟统计量为 $T_{\mathrm{inf}}$ 秒、策略动作频率为 $f_{\mathrm{policy}}$ Hz，则应记录

\[d=\left\lceil T_{\mathrm{inf}}f_{\mathrm{policy}}\right\rceil .\]

这里必须同时写明 $T_{\mathrm{inf}}$ 的统计口径（例如固定样本与预热条件下的保守分位数）；110 Hz 只是执行侧插值线程频率，不能代替策略动作频率。当前 LeRobot RTC 运行时也把秒级延迟除以单步周期后用向上取整得到步数。

离线命令的合格结果不是“脚本退出码为 0”这么简单：还应确认基线和 RTC 使用同一批样本、同一 checkpoint 与预处理，所有输出有限，Hard/Soft/Free 区域长度符合配置，前缀对齐的是同一物理时刻，并把命令、commit、实际解析后的配置和输出摘要一起保存。

五、调参顺序、故障定位与 DAgger 接入

调参应一次只改变一类变量：先把时间对齐和队列正确性做对，再调 overlap/guidance，最后才调执行侧平滑。否则“运动变顺”可能只是强淡化掩盖了 RTC 索引错误。

现象 先看哪条证据 优先修复 不应先做什么
块间仍有突跳 旧/新块按绝对时刻对齐、动作坐标与归一化、mask 曲线 修正时间轴/相对动作重锚，再比较 EXP 与 LINEAR 直接把 guidance 提到很大
周期性停顿或队列下溢 P99 端到端延迟、触发时 queue depth、后台异常 提前触发、减小推理耗时或增加可用覆盖 把问题归咎于 110 Hz 发送线程
轨迹过度迟钝 $K$、guidance、执行侧二次平滑、任务反应时间 降低重叠约束或避免双重过强平滑 只看视觉“更顺”就接受
振荡、NaN 或修正爆炸 每个 flow step 的修正范数、dtype、mask 端点 降低 guidance，检查时间方向和 VJP 符号 在真机上反复试更大权重
reset/接管后旧动作复活 generation id、在途请求、队列清空事件 原子失效旧 generation，并从最新观测重启 只把 FSM 状态改回 AUTO
相机流畅但动作语义错 物理相机身份、action/state 第八维、时间戳年龄 修正数据契约和预处理映射 用成功视频掩盖 schema 错误
推理请求过密、GPU 负载升高 queue threshold 与实际启动间隔 降低过早触发，保留足够延迟余量 把 queue_threshold 当 execution_horizon

DAgger 应在 RTC 基线通过后接入，具体交接顺序是：

  1. AUTO 中收到接管请求后，停止接受新 RTC 块并为当前 generation 标记失效；
  2. 唯一下发线程继续运行，经状态化安全链进入 SOFT_STOP，而不是瞬间把速度清零；
  3. 队列清空、停稳并完成 VR 离合重锚后进入 TELEOP；
  4. 只有 TELEOP ∧ ARMED ∧ Grip ∧ ACTIVE_EPISODE 的帧才按约 30 Hz 进入纠正缓冲，动作字段取安全链之后的真实下发值；
  5. 纠正结束后显式保存或丢弃 episode，保持机械臂稳定，采最新观测并创建新 generation；
  6. 新 RTC 块通过新鲜度、长度和安全校验后才允许回到 AUTO；否则退回 IDLE。
复现通过的判据：不是“机器人看起来更顺”，而是同一日志能证明无过期动作重放、无旧 generation 复活、预测/实际延迟可追溯、队列下溢和 deadline miss 在预注册阈值内、块边界指标改善且任务成功率没有因过度约束下降。DAgger 还要额外证明纠正帧来源、保存/丢弃决策和回训练血缘可追溯。

六、五相位接管协议

会话相位 参考来源 RTC 生命周期 硬件侧行为 记录资格
IDLE 安全保持参考 暂停或未启动 默认不动，等待显式开始 无
AUTO RTC 动作块 产生并消费新块 自主执行 无
SOFT_STOP 关节保持参考 停止接受新块 发送链继续运行，由既有限速/限加速度状态平滑减速 无
HANDOFF 关节保持参考 暂停且旧块不得重新生效 停稳，等待有效 Grip 与离合重锚 无
TELEOP, Grip=1 VR 增量映射 → IK 暂停 人工关节目标进入同一安全链 满足其余录制门时有
TELEOP, Grip=0 关节保持参考 暂停 冻结/保持，不追随手柄 无

软停止不是“把目标瞬间设为零速度”。它先阻止新的 RTC 块进入，再把关节参考切到保持目标；真正的减速由仍在运行的状态化限速、限加速度和滤波链完成。停稳后进行离合重锚，是为了避免把手柄当时的绝对姿态直接解释为机械臂的新绝对目标。

页面中的 Grip 指需求文档所描述的有效接管门。现有文档按右 Grip 描述，但真机前仍需用按键检查工具核对 SDK 键值；需求概览中的“双 Grip 接管”只能视为高层描述，不能替代实际映射验证。

从人工控制交还 RTC 时必须满足什么

若一轮纠正后允许在同一会话回到 AUTO，至少要完成四件事：结束并保存或丢弃当前录制段；保持机械臂稳定；清空或失效化接管前的旧 RTC 队列/在途结果；用最新观测生成可用的新块后再显式恢复自主控制。否则旧块可能把机械臂拉回接管前轨迹。若当前版本没有实现这条原子化交还路径，应先回到 IDLE，不能仅把相位变量改回 AUTO。

七、单一下发不变量及正确的数学表达

先区分“观测状态”和“硬件命令”：

  • $x_t=[q_t,w_t]\in\mathbb R^8$：七个实测关节角 $q_t$ 与连续夹爪开口 $w_t$；
  • $u_t=[q_t^{cmd},c_t]\in\mathbb R^7\times\mathcal C$：七个最终关节命令与离散夹爪命令，$\mathcal C={\text{open},\text{hold},\text{close}}$；
  • $h_t$：插值器、限速/限加速度器和其他状态化安全模块的内部状态。

令 $r_t$ 为会话仲裁后的参考，$\mathcal S$ 为唯一安全下发链，则

\[(u_t,h_{t+1})=\mathcal S(r_t,x_t,h_t), \qquad r_t= \begin{cases} r_t^{RTC}, & z_t=\mathrm{AUTO},\\ r_t^{hold}, & z_t\in\{\mathrm{IDLE},\mathrm{SOFT\_STOP},\mathrm{HANDOFF}\},\\ r_t^{VR\rightarrow IK}, & z_t=\mathrm{TELEOP}\land g_t=1,\\ r_t^{hold}, & z_t=\mathrm{TELEOP}\land g_t=0. \end{cases}\] \[r_t^{hold}=[q_t,c_{t-1}^{safe}],\]

这里的保持参考使用当前实测关节角和上一条已接受的安全夹爪命令，不能直接写成 $r_t=x_t$：$x_t$ 的第八维是连续夹爪测量，而命令第八维是离散类别，二者语义不同。公式显式保留 $h_t$，因为软停止是否平滑取决于上一周期命令和滤波器状态；仅写 $\mathcal S(r_t,x_t)$ 会把安全链误画成无记忆函数。

单一下发不变量包含三层意思：

  1. RTC 与 VR 只能产生候选参考，不能各自写硬件；
  2. 参考来源的切换发生在安全链之前；
  3. 记录器保存的是安全链之后真正下发的 $u_t$，而不是未通过约束的 VR/RTC 候选值。

八、控制门与记录门不是同一个开关

令 $m_t$ 表示录制已武装，$e_t$ 表示当前存在活动 episode，$g_t$ 表示有效 Grip，则“本帧进入纠正缓冲”的条件是

\[y_t= \mathbf 1\!\left[ z_t=\mathrm{TELEOP} \land m_t=\mathrm{ARMED} \land g_t=1 \land e_t=\mathrm{ACTIVE} \right].\]

TELEOP ∧ Grip 只说明 VR 可以驱动；$y_t=1$ 才说明本帧应追加到缓冲。它仍不等于 episode 已持久化：用户完成恢复后还要显式保存，坏段则应丢弃。因此可以先进入 TELEOP 做离合校准，再武装录制；中途松开 Grip 时机械臂保持且不新增冻结帧，重新握住后继续同一恢复段。

九、知识点、重点与工程创新

KNOWLEDGE

异步产块不等于控制频率

RTC 解决动作块推理延迟与块间连续性；110 Hz 是硬件下发节拍，30 Hz 是数据采样节拍，三者不能混写。

FOCUS

交接是一段协议

暂停新块、状态化软停、离合重锚和旧队列失效共同构成接管边界；单独切换一个布尔变量不够。

ENGINEERING

单写者仲裁

工程创新在于把 RTC 与 VR 的仲裁放到既有安全链之前，并让记录器观察安全后的真实命令；它不是新的 RTC 或 DAgger 理论。

DATA SEMANTICS

控制与采集解耦

人工拥有控制权并不自动产生训练样本；明确的武装、Grip、活动 episode 和保存步骤共同保证数据来源可审计。

十一、RTC 与既有动作平滑的关系

本任务的现场观察是：RTC 的实际运动观感与动作平滑工程页中的“异步推理 + 动作块间平滑过渡”接近。源码复核后可以把实际轨迹处理拆成四层：

  1. RTC 生成层：服务端把旧块未执行尾部重锚到当前 state，以冻结前缀、soft mask 和 guided flow 生成新的 50×8 动作块；这不是客户端事后平均。
  2. 时间插值层：7 个关节在 30 Hz 路点之间做线性插值，并以 110 Hz 取样下发；夹爪是离散三档，取最近路点后吸附到 {0, 0.5, 1}，不做连续插值。
  3. 状态化安全平滑层：先 EMA，再整体同比例限速、软限位刹车、目标接近刹车、整体同比例限加速度，最后做硬限位裁剪；所有关节使用同一缩放因子，保持关节空间方向。
  4. 可选输出低通层：7 关节经过单/双级 EMA，$a=1-e^{-2\pi f_c/f_s}$；夹爪不滤。保留文档的 ss1.0 离线结果为：fc=5 Hz 时指令加速度 RMS 262→113、换向 9.5→3.9 次/s、低于 1.5 Hz 主运动保留 99.8%，估算群延迟约 55 ms。它主要处理高于约 6 Hz 的毛刺，对 3–6 Hz 残留主体仅约 7% 位置幅值下降。

这条链是“模型空间轨迹约束 + 时间插值 + 有状态约束 + 可选低通”，不是一个统一的最优控制求解器，也没有在线优化碰撞距离、力或全局最短路径。现场观感和上述离线频谱结果仍不能替代锁定条件下的真机任务 A/B。

机制 作用位置 连续性从哪里来 不能单独解决什么
RTC 新动作块的生成/推理阶段 把已承诺执行的动作作为前缀条件，只补全尚未承诺的后缀，并按实际推理延迟确定重叠 执行器限速、通信抖动、异常队列、策略语义错误
执行侧动作平滑 动作块已生成后的调度/下发阶段 用当前实测状态锚定、跨块淡化、队列守卫等方式抑制边界跳变 从生成分布上修正新块，也不等价于策略理解了失败
二者组合 生成与执行两层 RTC 减少计划边界冲突，执行侧再处理残余抖动和安全约束 仍需截止期监控、失败检测与真机安全链

之所以“感觉差不多”，是因为最终可见信号都是关节命令和运动轨迹：只要块边界附近的位置、速度或加速度更连续，操作者就会感到更顺滑。但相似观感不能推出内部机制、延迟鲁棒性、峰值 jerk、任务成功率或故障恢复能力等价。尤其是强执行侧淡化可能掩盖 RTC 生成的不连续，也可能因过度平滑而造成相位滞后。

应在同一 checkpoint、观测序列、控制频率、网络延迟分布和安全参数下做四组配对试验：基线、仅 RTC、仅执行侧平滑、RTC + 执行侧平滑。同时报告 deadline miss、块边界位置/速度/jerk、任务成功率、人工接管率和安全限幅触发数；只有组合组在连续性与任务指标上稳定优于单独组，才能主张二者互补。RTC 数学原理另见 RTC 原理专题。

历史需求记录：原始项目文档把 DAgger FSM 正常/异常事件、mock VR、导入链和自动化 dry-run 标为通过；本轮未复跑，且当前网页工作区未定位到表中的同名实现文件。
这些记录不能证明：当前代码仍存在或仍通过，也不能证明真实 SDK 按键映射、软停真机动力学、离合方向、安全裕量和接管体验；这些都需要绑定 commit、配置、日志的复验。
