## 问题一：本地挂载点不可写

| 项       | 内容                                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **现象** | 在本地 `/home/dds/.../project_files` 下执行 `touch` 报「权限不够」                                                           |
| **根因** | 挂载出来的文件属主是容器内的 `root`，本地用户 `dds` 无写权限                                                                 |
| **影响** | 无法在本地直接创建/修改项目文件                                                                                              |
| **解决** | 所有文件写入改为通过容器执行：本地写到 scratchpad，再用 `docker exec -i <容器> bash -c 'cat > <路径>'` 以 stdin 方式送入容器 |
| **状态** | ✅ 已解决                                                                                                                    |

## 问题二：无法非交互 ssh 到 GPU 服务器

| 项       | 内容                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **现象** | `ssh -o BatchMode=yes dongdesheng@192.168.2.122` 返回 `Permission denied (publickey,password)`                                                                                                         |
| **根因** | 未配置免密公钥，本地也没有 `sshpass`                                                                                                                                                                   |
| **解决** | 使用 OpenSSH 自带的 `SSH_ASKPASS` 机制，无需安装任何软件：写一个临时 askpass 脚本输出密码，配合 `SSH_ASKPASS_REQUIRE=force` + `setsid` 实现非交互登录。脚本只存在于本地 scratchpad，不进入服务器和容器 |
| **状态** | ✅ 已解决                                                                                                                                                                                              |

## 问题三：目标仓库名与用户名不匹配，会导致全站资源 404

| 项                   | 内容                                                                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**             | 最初指定的仓库是 `dds131/dds-1-github.github.io`，名字以 `.github.io` 结尾，看起来像用户主页站                                                                                     |
| **根因**             | GitHub 判定用户主页站的**唯一条件**是仓库名 == `<用户名>.github.io`。用户名是 `dds131`，而 `dds-1-github` ≠ `dds131`，因此会被判定为**项目站**                                     |
| **潜在后果（严重）** | 若按主页站配置把 `baseurl` 留空，实际站点在 `https://dds131.github.io/dds-1-github.github.io/` 下，所有 `/assets/...` 路径都会指错 → **全站 CSS/JS/图片 100% 404，页面变成裸文字** |
| **发现方式**         | 部署前通过 GitHub API 核对 `login` 与 `full_name`，比对命名规则                                                                                                                    |
| **解决**             | 改用 `dds131/dds131.github.io`，仓库名与用户名精确匹配，`baseurl` 正确留空                                                                                                         |
| **验证**             | 首页引用的 12 个资源全部返回 200，零失败                                                                                                                                           |
| **状态**             | ✅ 已解决（在造成损失前发现）                                                                                                                                                      |

## 问题五：`pages build and deployment` 构建失败

| 项       | 内容                                                                                                                                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象** | 推送源码到 `main` 后，`pages build and deployment #2` 失败                                                                                                                                                                                                                            |
| **根因** | 此时 Pages 的发布源仍是 `main` 分支 + 内置 Jekyll（`build_type: legacy`）。GitHub 内置 Jekyll 只支持 9 个白名单插件，而 al-folio 依赖 `jekyll-scholar`、`jekyll-imagemagick`、`jekyll-minifier` 等 20 余个插件，官方明确「GitHub Pages cannot build sites using unsupported plugins」 |
| **解决** | 把 Pages 发布源改为 `gh-pages` 分支（GitHub Actions 构建出的产物），GitHub 不再需要自己构建                                                                                                                                                                                           |
| **验证** | `pages build and deployment #3`、`#4`（分支 `gh-pages`）均成功                                                                                                                                                                                                                        |
| **状态** | ✅ 已解决（属于预期内的中间状态）                                                                                                                                                                                                                                                     |

## 问题六：强制推送后 `Deploy site` 未自动触发

| 项           | 内容                                                                                                                                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **现象**     | `git push --force` 成功（`a0732c3c...af9a8d53`），但 `Deploy site` workflow 没有运行，只跑了 CodeQL 和 Prettier                                                                                                                |
| **根因**     | `deploy.yml` 的触发条件带 `paths:` 过滤器（只在 `assets/**`、`**.yml`、`**.md` 等变更时触发）。强制推送带来的是**与远端历史无共同祖先的全新历史**，GitHub 无法正常比对「变更了哪些路径」，因此路径过滤判定为不匹配，跳过了触发 |
| **解决**     | `deploy.yml` 带 `workflow_dispatch`，通过 API 手动触发一次：`POST /repos/{owner}/{repo}/actions/workflows/deploy.yml/dispatches`                                                                                               |
| **后续验证** | 第二次（正常增量、非 force）推送时，`Deploy site #2` **自动触发**并成功。确认该问题仅在首次强制推送时出现                                                                                                                      |
| **状态**     | ✅ 已解决                                                                                                                                                                                                                      |

## 问题七：`_pages/` 被 GitHub 内置 Jekyll 吞掉（本次核心修正）

| 项           | 内容                                                                                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**     | 站点上线后，`https://dds131.github.io/_pages/dropdown/` 返回 **404**，但该文件确实存在于 `gh-pages` 分支                                                                                                                                              |
| **根因**     | Pages 发布源虽已改为 `gh-pages`，但 `build_type` 仍是 `legacy`，GitHub 会对**已构建好的产物**再跑一遍内置 Jekyll。官方文档：「By default, Jekyll doesn't build files or folders that start with `_`, `.`, or `#`」。产物根目录的 `_pages/` 因此被丢弃 |
| **官方解法** | 外部 CI 推产物到 `gh-pages` 时应包含 `.nojekyll` 文件，GitHub 据此识别该分支无需构建步骤，直接部署                                                                                                                                                    |
| **上游线索** | al-folio 的 `_config.yml` 原本就有 `keep_files: [CNAME, .nojekyll]`，说明上游预期该文件存在，但从未真正创建 —— 是 al-folio 自身的缺口                                                                                                                 |
| **解决**     | ① 仓库根目录新建空文件 `.nojekyll`；② `_config.yml` 的 `include: ["_pages"]` → `include: ["_pages", ".nojekyll"]`（必需，否则 Jekyll 不会把点开头的文件复制进 `_site`）                                                                               |
| **验证**     | `/_pages/dropdown/` **404 → 200**；`/.nojekyll` 返回 200；全站 20 项回归测试 **0 失败**                                                                                                                                                               |
| **附带收益** | 同时解决了官方文档提到的「使用 `GITHUB_TOKEN` 的 workflow 提交不触发 Pages 构建」问题                                                                                                                                                                 |
| **状态**     | ✅ 已解决                                                                                                                                                                                                                                             |

## 问题九：`Prettier code formatter` workflow 失败（本次修正）

| 项                       | 内容                                                                                                                                                                                                                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**                 | 提交 `dds_custom/` 文档后，`Prettier code formatter #3` 失败，日志显示 `Code style issues found in 5 files`                                                                                                                                                                                                            |
| **根因**                 | 仓库的 `.github/workflows/prettier.yml` 执行 `prettier . --check`，会扫描仓库内**所有**文件。新增的 6 个中文 Markdown 文档的表格对齐与换行风格不符合 Prettier 的 markdown 规范                                                                                                                                         |
| **命中的文件**           | `dds_custom/README.md`、`dds_custom/docs/01~05_*.md`                                                                                                                                                                                                                                                                   |
| **官方依据**             | Prettier 官方文档 <https://prettier.io/docs/ignore>：`.prettierignore` 位于项目根目录、使用 gitignore 语法、对 `--check` 同样生效；Markdown 另支持 `<!-- prettier-ignore-start -->` / `<!-- prettier-ignore-end -->`。al-folio 的 `docs/CONTRIBUTING.md` 也说明「all new submitted code must conform to its standard」 |
| **考虑过但未采用的方案** | 把 `dds_custom/` 加进 `.prettierignore`。可行且是官方机制，但需要**再修改一个原有文件**，且等于让自己的文档游离在仓库代码风格之外                                                                                                                                                                                      |
| **最终采用的方案**       | 在容器内安装 node，用仓库自带的 Prettier 直接把文档格式化成合规样式。**不修改任何额外的原有文件**                                                                                                                                                                                                                      |
| **具体做法**             | ① 容器内 `apt-get install -y nodejs npm`（Debian 13 提供 nodejs 20.19.2，与 CI 的 Node 20 一致）；② 在 al-folio 目录执行 `npm ci`，按 `package-lock.json` 安装 prettier 3.8.0 与 `@shopify/prettier-plugin-liquid`；③ `npx prettier "dds_custom/**/*.md" --write`                                                      |
| **验证**                 | 本地执行与 CI 完全相同的 `npx prettier . --check`，输出 `All matched files use Prettier code style!`                                                                                                                                                                                                                   |
| **副作用说明**           | `npm ci` 只创建 `node_modules/`（已在 `.gitignore` 中，不会提交）；`package.json` 与 `package-lock.json` 经 `git status` 确认**未被改动**                                                                                                                                                                              |
| **状态**                 | ✅ 已解决                                                                                                                                                                                                                                                                                                              |
