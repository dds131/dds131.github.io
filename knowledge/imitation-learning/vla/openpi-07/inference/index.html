π0.7 总览/CFG、RTC 与异步推理

必需先修： 先阅读 RTC Foundations 的共同时间域、动作块与事件语义，再返回本页看 π0.7 实例。ready、merge committed、first dispatched 与笼统“延迟”不能混作同一时刻；无需先读完整个 RTC 专题。

PROMPT ASSEMBLY · ACTION CFG · TRAINING-TIME RTC · ASYNCHRONOUS CONTROL

模型生成、运行时调度、控制执行是三层：Action Expert 生成连续动作块；运行时决定何时请求、合并与派发；PD / IK 再把动作送入机器人。

CFG、RTC 和异步分别处理条件引导、动作块接续与慢速 producer 不阻塞控制的问题；任何一个都不自动提供安全、稳定、时限或任务正确性保证。本页中的 π0.7 读作 pi zero point seven。

一、运行合同与 Prompt 装配

Algorithm 1 的初始输入是 initial observation (\mathbf o_0)、task instruction (\ell)、episode metadata (m) 和 control mode (c)。subtask (\hat\ell) 可由学习高层、人类 coaching 提供或省略；若启用视觉目标，world model 从 (\mathbf o_0,\hat\ell,m) 生成 (g^)。完整组合可概括为 (C={\ell,\hat\ell,g^,m,c})，但它不能覆盖 Prompt dropout 产生的可选分支，也不是已公开的调用 schema。PI07_ALGORITHM_1

字段角色、论文实验赋值和未公开接口必须分开

二、5 步生成与 50 步动作块

低层 Action Expert 输出 50-step continuous action chunk；论文所称固定 50 个 action tokens 指 50 个连续动作位置，不是运行时 FAST 离散 token 解码。所有 π0.7 实验使用 5 个 denoising / Flow integration steps。Algorithm 1 在距上次 inference 经过 (\hat H) 步时请求下一块，实验取 (\hat H\in{15,25})。PI07_PAPER

5、15/25、50 分属生成求解、执行重请求与预测 horizon
量 语义 50Hz 标注算术 20Hz 标注算术
5 每次 chunk 的 denoising / Flow integration steps 不是 5 个控制 tick 不是 5 个控制 tick

论文没有给 15 或 25 与具体平台、任务的一一映射，四个墙钟换算不代表实际调度组合或完成周期保证。只执行块的一部分允许重新读取观测，却不证明闭环稳定、轨迹连续或最大反应时间；新 chunk 何时 ready、何时 merge，以及 (\hat H) 是否随 jitter 调整，都必须由运行时合同另行定义。

prediction horizon、request interval 与实际可执行队列长度还不是同一个量：50 个位置描述模型一次预测的范围，15/25 只锚定何时发起下一次 inference，而异步计算期间旧块可能继续被消费。新块 ready 后仍可能需要校验上下文和前缀，再形成 committed merge；first dispatched 又是控制器第一次收到新块动作的时刻。论文没有给这几个事件之间的最大间隔，因此页面不能用“每 15/25 步重规划”替代完整的端到端时序保证。

三、低层 CFG 与 attention tree

论文对每个动作 denoising step 给出的 Classifier-Free Guidance 为：

[ \nabla_{\mathbf a}\log\pi(\mathbf a\mid\mathbf o,C)+\beta!\left[\nabla_{\mathbf a}\log\pi(\mathbf a\mid\mathbf o,C)-\nabla_{\mathbf a}\log\pi(\mathbf a\mid\mathbf o,C_{\mathrm{uncond}})\right]. ]

按这一系数约定，可代数写作 ((1+\beta)s_c-\beta s_u)，因此 (\beta=0) 退化为普通条件分支；页面不把 score 记号翻译成未公开的 velocity 更新代码。Prompt dropout 原则上允许对不同 context 部分做 CFG，但 π0.7 实验只明确对 episode metadata 做 CFG，以引导更快、高质量、无错误模式，并使用 (\beta\in{1.3,1.7,2.2})。论文没有给 beta 到具体任务的一一映射。PAPER_RUNTIME_SETTING

精确 negative serialization、多个 metadata 字段共同还是分别移除均未公开。control mode 明确不 drop，不能写成已验证的 control-mode CFG；world model 的三个 CFG groups 属于上一页，不能与低层两分支混写。过强 guidance 导致的具体故障只能在有实验时记录，本页不把机制风险冒充 π0.7 已测定律。

四、training-time RTC 集成边界

π0.7 明确使用 training-time RTC：训练时模拟 0–12 timesteps 延迟，在 50Hz 下最大换算 240ms。Appendix 说明它不同于 test-time RTC，且不增加额外 inference-time overhead；“无额外开销”只指 training-time action conditioning 本身不需要测试期反向引导，不代表运行队列、网络或整个 RTC 系统零开销。RTC_PREREQUISITE

方法论文解释机制；π0.7 论文只锚定自己的披露范围
层 可确认内容 不可移植或保持未知

RTC_METHOD_SOURCE 本页不重写 RTC 的 (H/s/d)、wall-clock / control-tick / generative-time、绝对 tick 对齐或适用条件；这些由先修页负责。training-time RTC 也不负责 world goal 正确性、高层 subtask 正确性、传感器 timestamp、碰撞 / 力安全或替代 PD。

Algorithm 1 的 (a_{t:}) 只支持“把仍将执行的动作作为条件”这一接口语义，不能据简写决定 prefix 包含已派发、仅在通信队列、已经 committed 但尚未 dispatch，还是模型预测却仍可撤销的动作。若这些状态混用，prefix 与真实机器人时间轴就可能错位；这属于运行时需要验证的接口风险，而不是可以从方法名推导出的官方队列实现。

五、三类异步与 Algorithm 1

Algorithm 1 先生成初始 subgoal/context 和初始 action chunk，再进入逐 tick 循环：若 subtask 改变或自上次 subgoal produced 起达到 (\Delta=4) seconds，则非阻塞请求新 subgoal；若距上次 inference 经过 (\hat H) 个控制步，则用当前 observation history、context 与 RTC action prefix 异步请求新 chunk；每个 tick 执行当前 (a_t)。4 秒是 world-model regeneration interval，不是动作 horizon、history stride、控制周期、goal prediction horizon 或高层 query cadence。

visual subgoal 仅在启用时刷新，双触发按 whichever happens first；动作重请求由 15/25 个 control ticks 触发，两者不是同一节拍。在 50Hz 下 15/25 步为 0.3/0.5 秒，在 20Hz 下为 0.75/1.25 秒；world model 约 1.25 秒生成可能跨越多个低层请求，这只是由报告口径得到的接口推论，不证明“4 秒内必有新 goal”或固定最大 goal age。

latest available 只表示最近完成的产物，不等于与当前 observation 同步、没有陈旧、与当前 subtask 同版本或安全可用。高层 latency/cadence、旧请求取消、乱序完成、timer 从 request 还是 produced 重置等均未报告；仅“last produced”有论文锚点。Algorithm 1 异步调用后的 context 更新是语义简写，不能据此虚构瞬时完成。

三类并发的失效也应分开定位：chunk ready 过晚会影响动作前缀长度；goal ready 过晚会扩大视觉目标年龄；subtask 更新过晚会让语义 intent 滞后。它们可能同时发生，但论文没有给统一优先级、backpressure 或 deadline。尤其不能把 world model 的 4 秒再生成间隔当作高层每 4 秒查询一次，也不能把低层 15/25 tick 的重请求节拍当作 goal 的刷新频率。

38/127ms 不能与 50Hz 的 20ms tick 直接比较后宣称 deadline pass/fail，因为论文没有 latency 起止事件、P50/P95/P99、host preprocessing、网络、queue 或 controller acknowledgement。建议观测 observation ID/tick、inference request/ready、chunk ID、prefix length / delay estimate、merge / first dispatch、subtask/goal version、context snapshot hash、controller ack；这些字段全部是 SITE_RUNTIME_RISK，不是论文 schema、clock source 或已部署日志。端到端性能保持 NOT_RUN。

这些观测字段的目的，是让“条件是否正确、产物何时完成、哪个版本被消费、哪段动作已经不可撤销”可以逐项核对。没有共同 clock、ID 关联和清楚的事件定义，即使单个模型延迟数值看似较小，也无法计算真实 goal age、chunk handoff gap 或从 request 到 first dispatch 的时延分布。本页只冻结应区分的量，不规定字段名、采样率、日志格式或告警阈值。

八、失败边界、来源与下一页

失败分类只作诊断入口：条件错覆盖 metadata/control/subtask/goal；生成错覆盖 CFG 或 action chunk；时序错覆盖旧 chunk、prefix 或 goal version；控制错覆盖 IK/PD/limit；语义错覆盖 task 或 subtask 本身。分类不代表已测频率，也不能把某个现象唯一归因到一个模块。能力数字、消融和真实失败例统一交给下一页，不在本页预写结果。
