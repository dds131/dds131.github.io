二、实时记录为什么要离开 110 Hz 热路径

110 Hz 的名义周期只有：

[ T=\frac{1}{110}\approx9.091\ \mathrm{ms}. ]

三路 224×224 RGB 图像若按未压缩字节估算，单帧约为 (3\times224\times224\times3) bytes；30 Hz、60 秒量级约 775 MiB，尚未包含 Python 对象、数组元数据和编码缓冲。控制线程只做必要复制或 append，编码和落盘放在 episode 收尾，才能避免 I/O 抖动直接占用控制预算。

实测日志 当前代表性记录的 P50/P95/P99/P99.9 为 9.092/9.379/9.638/10.063 ms，最大 11.161 ms。该结果说明本次会话节拍稳定，但不能外推为所有磁盘、最长 episode 或后台编码配置都安全。

三、为什么跨段差分会制造假速度和假 jerk

若把暂停前最后一帧与恢复后第一帧直接视为相邻控制帧，时间间隔和状态跳变不再属于连续控制过程。正确流程是：

  1. 用状态和时间戳识别每个连续 ACTIVE 段；
  2. 在每个段内部按时间戳计算位置差分；
  3. 速度、加速度和 jerk 均不得跨段；
  4. 每个统计表同时保存段数、有效周期数和排除规则。

这次分段口径得到 10 个 ACTIVE 段和 20,338 个有效周期。旧的 40 万°/s²和 1e8 级 jerk 峰值是分析错误，不是机器人真实运动。

四、为什么 LPF 延迟不能加入 RTC 延迟步

RTC 延迟步描述的是“从观测到动作块返回期间，30 Hz 策略时间轴已经前进多少步”。输出 LPF 发生在动作块生成之后，描述“安全命令到机械臂响应”的相位滞后。把约 55 ms LPF 群延迟加入 RTC 的 (d) 会错误扩大冻结前缀，使首个有效执行步与新块比较基准错位。

修复后遵循：

  • 推理延迟步只统计预处理、传输、排队、推理和后处理；
  • LPF 延迟单独作为执行链动态特性报告；
  • 高速时首步连续性对比首个实际执行步，而不是原始 chunk[0]。

五、动作块和队列的三道闸

  1. 新鲜度闸：结果必须属于当前 generation，旧请求晚到直接失效；
  2. 长度/时间闸：按真实延迟裁去过期前缀，整块过期则拒绝；
  3. 运动安全闸：检查有限值、首步偏差、块内变化和限位，再进入唯一发送链。

该会话 241 个接块事件中有 223 个 RTC 融合块、18 个首块、2 个拒块、0 个过期块。它能展示机制实际工作过，但不是长期拒块率或过期概率。

六、优化优先级

P0 · 时间语义先修 30/110 Hz 混算、跨段差分、真实延迟裁前缀和旧 generation 失效。
P1 · 热路径把编码、落盘和大对象复制移出 110 Hz 控制循环，并给后台队列设上限。
P2 · 连续性在 RTC 正确后再扫描 horizon、guidance、schedule 和输出低通，分别记录收益与滞后。
P3 · 训练决策统一 optimizer step 和 samples/s，锁定硬件后再决定 JAX/PyTorch。
P4 · 任务证据最后用相同 checkpoint、初始条件和安全参数完成四组配对真机 A/B。
面试一句话：我重点解决的不是单一参数，而是三个跨层错误：控制日志必须按连续段分析、输出 LPF 不能污染 RTC 推理时间轴、异步结果必须随 generation 原子失效；每个修复都保留了可复算证据和未覆盖风险。
