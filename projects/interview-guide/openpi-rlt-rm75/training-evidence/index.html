命令能跑、训练健康、动作过闸，仍然不等于任务得到提升

一、复现不是“一条命令”，而是一条逐层放行链

Stage-1训练 RL-Token 风格 encoder/decoder，审计结构、norm stats 与 VLA 逐比特冻结。
L1 / L2先用假特征和假机器人打通服务，再只加载冻结特征服务验证形状、数值和资源。
E-2冻结 VLA 为主、人类必要时接管，采集实际动作、source、reward 与完整 step trace。
F / G离线预训练 Actor-Critic，再对安全整形前的原始 Actor 输出做严格动作准入。
L4.0 / L4.1分别建立纯 VLA 零接管基线和冻结 Actor 上机证据，隔离执行链与策略作用。
L4.2允许人类纠正并在线更新，同时监控 Replay、UTD、Critic、Actor 版本和任务结果。
逐层证据原则：离线测试通过不能证明真实特征服务；特征服务通过不能证明 Actor 动作安全；动作闸通过不能证明 episode 成功；在线 loss 健康也不能替代统一真机 A/B。

二、先看 L4.2 现场视频：这是负结果证据

可直接观察 1自主推理与动作执行未形成稳定、连续的完整任务推进。
可直接观察 2关键步骤失败后，当前策略无法在录像所示状态下自行恢复并继续完成任务。
可直接观察 3操作者进行了多次主动接管，用于避免错误累积并采集恢复动作。
可直接观察 4多轮采集与训练后，现场仍未观察到可归因于本轮 RLT 的提升。
不能从视频推出：不能精确计算 RLT 比 π0.5 下降或提升多少；不能把反复接管当成 DAgger 已经有效；也不能把这一个现场记录写成算法普遍无效。它支持的是“本项目当前方案没有建立任务收益证据”。

运行前先只读检查 GPU 使用情况；示例索引 0,1,2,3 只表示逗号分隔格式，不代表这些卡当前可用。

变量 / 参数 本次值 作用 修改时的实际风险
RM75_RLT_GPUS 4 张人工确认的空闲卡 设置可见物理卡并计算设备数 脚本不会替操作者判断卡是否属于别的任务
RM75_RLT_BATCH 128 全局 batch，需被卡数整除 四卡 batch 256 实测约 77.74 GiB/卡，稳定余量不足
RM75_RLT_FSDP 4 指定参数分片设备数 与可见卡数口径不一致会导致启动或分片错误
RM75_RLT_STEPS 12000 同时设置总更新数与 decay steps step 从 0 开始，末 checkpoint 是 11999
RM75_RLT_SAVE_INTERVAL 2000 同时设置保存间隔和周期保留 它控制产物密度，不改变训练总步数
warmup / peak / decay LR 1000 / 2.5e−5 / 2.5e−6 只优化 rlt_module 不能据此推断 VLA 也在更新

核心训练入口等价于：

.venv/bin/python -u scripts/train_rlt.py rlt_pi05_rm75_3cam \
  --exp-name rlt_rm75_3cam_frozen \
  --checkpoint-base-dir <STAGE1_CHECKPOINT_ROOT> \
  --num-train-steps 12000 \
  --batch-size 128 \
  --fsdp-devices 4 \
  --lr-schedule.warmup-steps 1000 \
  --lr-schedule.peak-lr 2.5e-5 \
  --lr-schedule.decay-steps 12000 \
  --lr-schedule.decay-lr 2.5e-6 \
  --save-interval 2000 \
  --keep-period 2000 \
  --num-workers 8 \
  --no-wandb-enabled \
  --overwrite

rlt_pi05_rm75_3cam 选择从 RM75 三相机 BC 配置派生的 RLT 配置，不只是日志名；--overwrite 是新运行语义，不能拿来续训或无审计覆盖有效产物；--no-wandb-enabled 只关闭外部上报，本地日志与 checkpoint 仍写入。

长期服务使用 XLA_PYTHON_CLIENT_PREALLOCATE=false 关闭 JAX 默认整块预占，并以 --mem-fraction 0.74 限制本项目当前设备的显存比例；实测约占 12.7 GiB。0.74 是本机口径，不是跨硬件常数。就绪日志必须同时出现 z_rl=(2048,)、ref_chunk=(50,8) 和服务创建完成，不能只看端口可连接。

推理耗时只在相同测量边界内比较

探针 样本数 min / p50 / p95 / max 测量边界
基础 VLA 内存探针 60 101.0 / 103.7 / 106.4 / 108.3 ms 已加载模型的一次 VLA 推理；不含相机、网络和机械臂
L2 真冻结特征服务 12 142.2 / 142.5 / 142.8 / 142.8 ms 返回 RL Token、proprio 与 reference 的一次服务请求

L2 验收时显存峰值为 12,697 / 16,376 MiB。该结果证明当次冻结特征服务能在目标显存内完成请求；它不能预测并发 Learner、控制侧 IK 或其他 JAX 进程加入后的资源竞争，也不能与 0.952 s chunk 时长相加成端到端延迟。

五、E-2：采集的是含接管的 Replay，不是自主成功率

40episodes
2,811写入 transitions
2,443BASE transitions
368HUMAN transitions
246采集期 drop，未写入
33 / 40含接管条件下成功

82.5% 只说明允许人工接管的 40 条采集中有 33 条被运行时判为成功，不是纯 VLA 或 RLT Actor 的自主成绩。Replay 中只有 32 条 episode 带正奖励，与 33 条 success 相差 1，因此运行时成功标志与可训练的 +1 奖励必须分别审计。

质量闸 准入线 本次怎样解释
Transition 总数 ≥600 只满足 warm-up 最小规模，不证明覆盖充分
成功 episode ≥1 至少存在正奖励链
BASE 比例 ≥50% 避免数据完全被人工动作主导
动作退化 七关节 $\lvert action-proprio\rvert$ 的 p95 <0.01° 排除动作块退化成当前状态拷贝
夹爪覆盖 每条不恒定；全局出现 {0,0.5,1} 证明必要档位出现，不证明所有值严格在三档网格

十终端为什么不能合并成“一键启动”

终端角色 真实责任 必须等待的证据
清理与 pre-check 只清本项目孤儿；检查端口、相机、GPU、共享内存 任一失败就停止，不代替现场清场
夹爪 daemon / state pub 执行夹爪命令并发布真实开口 已定位 gripper_joint
Machine A 冻结 VLA + RL-Token 特征服务 模型与服务创建完成
唯一控制端 唯一连接机械臂，负责 VR、动作闸和实际执行回传 人工大写确认，急停可达
Replay / rollout E-2 不启动 Actor/Learner，回退为 VLA reference journal、source 与 episode 持续更新
console / monitor / camera 成功失败裁决、训练与相机监视 三者只监视或裁决，不拥有硬件写权 
MAXCHUNK=300 EPS=20 bash "$RUN/e2_rollout.sh"

"$PY_OPENPI" "$RLT_ONLINE/tools/check_base_data_quality.py" \

MAXCHUNK=300 是因为任务通常需要 65–85 个 chunk；脚本旧默认 40 会提前截断。EPS=20 只是本次运行上限，不是训练 epoch。质量检查把 clean 结果写到新文件，不覆盖原 journal；本次 40/40 episodes 通过后验硬闸，额外剔除 0 条。

真机安全边界：控制终端会连接真实机械臂，必须由受训人员在清场、急停可达、夹爪与相机就绪后人工启动。本页解释参数和证据，不把十终端编排合并为绕过人工确认的一键脚本。

参数 作用 关键边界
RM75_DELTA_DIMS=7 把上游六关节切片扩为 RM75 七关节 漏设时程序可能仍运行，但关节 7 与正则语义静默错误
online_rl_f7.yaml 锁定七关节度制配置与 delta_weight=0.014415 启动日志需显示偏差 0.00%
--replay 指定 E-2 原始 journal 不能误指向 L4 后续追加数据
STEPS=300 只做短冒烟 300 步模型不作为上机 bundle
不设置 STEPS 使用脚本正式预算 仍要核对输出目录和 snapshot
--fail-under 100.0 原始 Actor 任一违规即非零退出 100% 是动作闸通过率，不是成功率

F 段 fit 不是训练 loss，而是原始物理单位下 Actor 均值与冻结 VLA reference 的平均绝对偏差：

$$ fit(D)=\frac{1}{\lvert D\rvert\cdot10\cdot8} \sum_{x\in D}\lVert a_{actor}(x)-a_{ref}(x)\rVert_1, \qquad gap=\frac{val\_fit-train\_fit}{train\_fit}. $$
口径 train / val n train_fit val_fit gap 正确解读
source=all 2,671 / 140 0.5003 0.4879 −2.5% 部署模型主视角；含 HUMAN/MIXED
source=base 2,321 / 122 0.3457 0.3395 −1.8% 只诊断贴近 VLA 的 BASE 子集

负 gap 只表示本次切分的验证误差略低于训练误差，不表示“负过拟合”或优于 VLA。G 闸检查确定性均值的原始输出：数值有限、首步七关节离当前 state 不超过 10°、块内相邻七关节跳变不超过 10°。种子 Actor 四组 4/4 通过；在线模型曾下降到 99.75% 和 99.90%，说明运行时整形可能掩盖 Actor 漂移。

七、L4.0、L4.1、L4.2 分别回答什么

阶段 Actor Learner 人工接管 本来要回答 实际结论
L4.0 关 关 禁止 同一执行链上的纯 VLA 零接管基线 12 条中 3 条作废且终止口径不统一，正式基线缺失
L4.1 冻结 关 禁止 Actor 是否真实进入执行链并具备粗粒度能力 能接近、抓取和搬运，精密插装仍失败
L4.2 在线 Actor 开 允许 人工纠正与在线更新能否产生任务收益 训练健康，但未观察到成功率提升

在线 rollout 使用：

RM75_HUMAN_IDLE_MODE=drop \
TASK="$TASK" \
EPS=30 \
MAXCHUNK=300 \

在线 Learner 的实际更新吞吐

累积 metrics 中可恢复 119,477 个相邻、连续的更新间隔；另有 407 个重启、跳步或日志复用造成的不连续区间，未混入分布统计。

指标 日志值 解释
更新间隔 p50 / p95 / p99 11.27 / 19.68 / 25.15 ms 连续更新之间的日志时间差
更新间隔均值 12.62 ms 受长尾影响，高于 p50
按均值折算吞吐 79.24 update/s 用于容量估算
p50 倒数 88.75 update/s 典型局部速度，不能替代平均吞吐
不连续区间 407 重启、跳步或日志复用边界

79.24 update/s 表示已经记录的连续 Learner 更新吞吐，不是 rollout 产生 transition 的速度。累积日志也不能恢复一次不间断训练的总 wall-clock，不能补写 GPU 利用率、功耗、温度或 I/O 占比。

正确停机顺序也是数据契约

先在 console 用 d finalize 当前 episode，再退出 rollout；随后让 Machine B 自行 flush checkpoint，最后停控制端、Machine A 和监视器。Machine A 不能过早停，因为 finalize 还需要为人工接管期批量补算 $z_{rl}$ 与 reference。强杀进程可能同时丢最后一个 episode 和最后一版 Actor。

九、为什么训练健康仍然任务无效

1. 长任务把终局 1 bit 奖励折扣得很弱

完整任务约 65–85 个 chunk、每块 10 步。若 $\gamma=0.99$，从前段看终局奖励的尺度为

$$ 0.99^{650}\approx1.45\times10^{-3}, \qquad 0.99^{850}\approx1.94\times10^{-4}. $$

这不是 Critic 误差的直接测量，但说明从抓取前段到最终成功的信用传播很弱；“第一步抓取失败”和“已经插入、后来取出失败”又都得到 0，奖励没有表达阶段进展。

2. 直接人工监督没有集中到最后几毫米

历史 HUMAN 中 81.8% 位于轨迹前 40%，后 20% 只有 2.7%；L4.2 把后 20% 最好提高到 23.1%，仍低于本项目 >40% 的诊断目标。人工步是 BC 项里唯一把目标从 VLA reference 切到真实执行动作的来源，因此末段密度不足会直接限制“最后几毫米怎么修”的示范。

十二、面试讲述方式与结论边界

3 分钟证据版

先讲链路：Stage-1 训练 RL Token，L1/L2 验证假链和真特征，E-2 采集含接管 Replay，F/G 离线训练并做原始动作闸，最后才进入 L4。

再讲训练量化：Stage-1 用 4 卡、batch 128 跑 12,000 次更新，稳态约 4.0–4.1 s/it，总日志时长 14:13:12；51/51 逐比特一致证明没有改写基座。

再讲数据瓶颈：23.1% 说明人类纠正虽后移，但仍没有集中到最后 20% 的精密阶段；在线 Learner 约 79.24 update/s 只说明优化链能消化 Replay，不代表任务收益。

然后讲视频：现场能看到任务中断和多次接管，但它不是严格 A/B，因此我只结论为“没有建立收益证据”，不计算虚假的下降百分点。

最后讲判断：系统和训练健康都通过，任务仍无提升，所以继续采同分布数据不会回答核心问题；下一步应先裁出 3–8 秒精密阶段做冻结配对实验。

不能说错的五件事

  • 92% 不是 RLT 同链零接管基线。
  • 82.5% 是含人工接管的 E-2 采集比例，不是自主成功率。
  • G 的 100% 是原始动作三项硬闸通过率，不是安全认证。
  • critic_loss≈4.4×10⁻⁴ 不能证明 Q 排序正确。
  • 负结果的准确结论是“当前方案未建立任务收益证据”，不是“RLT 理论被否定”。
